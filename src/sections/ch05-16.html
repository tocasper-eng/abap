3. Domain、Data Element 與兩層式 Domain 概念（Unit 2 Lesson 1）

Domain 管技術、Data Element 管語意。這是整門課的第一條口訣。

物件管什麼程式能否直接用重點屬性
Domain技術屬性：資料型別、長度、小數位；值域（固定值、Value Table）；輸出特性不能（程式無法 TYPE 一個 Domain）Format、Output Characteristics、Conversion Routine、Sign、Lowercase、Value Range
Data Element語意：欄位標籤（短／中／長／標題）、F1 文件、Search Help、SET/GET 參數可以Data Type 頁籤（Domain 或 Built-in Type 或 Reference Type）、Field Label、Further Characteristics

兩層式 Domain 概念（Two-Level Domain Concept）——原廠的經典例子：航班時刻表 SPFLI 的 AIRPFROM（出發機場）與 AIRPTO（抵達機場）都使用 Domain S_AIRPID（技術上都是機場代碼），但語意不同，所以分別用 Data Element S_FROMAIRP 與 S_TOAIRP。

常用 Built-in Type（Col18 p23–p24）：

  • CHAR：表格中最多 255 字元；更長要用 LCHR（或新開發用 STRING／SSTRING）。在結構中沒有此長度限制。
  • DATS：固定 8 碼（YYYYMMDD），輸出格式依使用者設定檔。
  • DEC：最多 31 位，含小數點、正負號、千分位。
  • NUMC：最多 255 字元，只能放數字（但本質是字元型別！）。
  • CURR／QUAN 必須有參考欄位（CUKY／UNIT），見第 6 節。

Domain 的輸出特性：

  • Output Length：依格式自動計算，可覆寫。
  • Conversion Routine：例如 ALPHA（補前導零）、MATN1、CUNIT。畫面欄位在「顯示格式 ↔ 內部格式」轉換時執行，WRITE 時也會執行。
  • Sign：DEC、FLTP、QUAN、CURR 可勾「+/-」，畫面輸出長度會自動 +1。
  • Lowercase：沒勾的話，使用者按 Enter 後小寫會被轉成大寫。

Data Element 的其他選項（Further Characteristics）：

  • Documentation：寫了就是所有參照畫面欄位的 F1。
  • Search Help：附加在 Data Element 上的 F4（第 18 節的第三種附加機制）。
  • SET/GET Parameter ID：例如物料的 MAT、公司代碼的 BUK。離開畫面時把值寫進 SAP Memory，下一個參照同一 Data Element 的畫面自動帶入；只在登入期間有效，登出即消失，與 SAP GUI 本機輸入歷史無關。
  • Default Component Name：只在 Data Element 被用於 BAPI 結構時有意義（BAPI 欄位用英文長名稱）。
  • Change Document：勾了此旗標，變更文件（CDHDR／CDPOS）才會記錄該欄位。
  • Input History：關閉 SAP GUI 對該欄位的輸入歷史。
  • Reference Type：Data Element 也可以定義成 REF TO 任何 DDIC 型別或泛型 ANY／OBJECT／DATA，等同程式中的 TYPES tr_dt TYPE REF TO data。
欄位標籤要翻譯：SE11 初始畫面 Goto → Translation，或 SE63。長度要預留——同一個詞在德文、日文可能長很多。

4. Structure、Table Type、深層結構與 Ranges Table Type（Unit 2 Lesson 2、3）

Structure 的元件可以是：Data Element、Built-in Type、Table Type、資料庫表或 View 的定義、其他 Structure。

  • Flat Structure（扁平結構）：元件全部參照 Data Element，產生的資料物件是一維的。用 結構名-元件名 存取。
  • Nested Structure（巢狀結構）：元件本身又是結構。以 Include 方式納入時可以給一個 Group 名稱，程式中可用群組名一次存取整組元件。
  • Deep Structure（深層結構）：只要有一個元件是 Table Type 就是深層。該元件可以像內表一樣 LOOP AT、INSERT … INTO TABLE。
資料庫表只能 Include 扁平結構。深層結構不能當表格欄位。

原廠的 EMPLOYEE 例子：結構 EMPLOYEE 有 NAME、ADDRESS、TELEPHONE 三個元件；NAME 是結構（FIRST NAME、LAST NAME）、ADDRESS 是結構的結構（STREET、HOUSE NO、ZIP、TOWN…）、TELEPHONE 用 Table Type——因為一個員工可以有多支電話。

Table Type 的定義要素：

要素選項備註
Line Type資料庫表、Structure、View、Data Element、直接型別、其他 Table TypeDomain 與 Type Group 不能當行型別（評量題）
Access ModeStandard／Sorted／Hashed／Index Table／Not Specified後兩者是泛型
Primary KeyUnique／Non-unique／Not specifiedHashed 必為 Unique；Sorted 三者皆可
Secondary Key（選用）Hashed 或 Sorted；Sorted 可 Unique／Non-unique對應 7.02+ 的內表次要鍵

泛型 Table Type：Access Mode 選 Index Table 或 Not Specified、未指定鍵、未指定鍵類別、或允許更多次要鍵時，就是泛型——用來定義函數模組的泛型表格參數。

Ranges Table Type：SE11 建 Table Type 時選 Edit → Define as ranges table type。行結構固定為 SIGN、OPTION、LOW、HIGH，永遠是 Standard Table、非唯一標準鍵。用於 SELECT、IF、WHILE、CHECK 的 IN 條件，或傳給選擇表。

5. Type Group：已不建議使用（Unit 2 Lesson 4）

Type Group（Type Pool）是 4.5A 以前字典還不支援複雜型別時的產物，可以放全域的 TYPES、CONSTANTS 與巨集。規則：

  • 名稱最多 5 個字元（評量題）。
  • 第一句一定是 TYPE-POOL <name>.；所有型別與常數名稱必須以「群組名＋底線」開頭，例如 zmytp_。
  • 可在 SE11 或 SE38 維護。
  • NW AS 7.02 以前程式要宣告 TYPE-POOLS zmytp. 才能用；7.02 起不必宣告，直接使用即自動載入。

原廠明確說：「仍有程式在用，但不再建議。」替代方案：複雜型別用 DDIC Structure／Table Type；全域常數用類別的常數屬性。常見仍會碰到的標準 Type Group：ABAP（abap_true）、SLIS（舊 ALV）、ICON、CNTL。

6. 透明表、Include 結構與參考欄位（Unit 3 Lesson 1）

應用物件的結構對應到資料庫的表格，物件屬性對應表格欄位。表有名稱與屬性（Delivery Class、維護權限）；欄位有唯一名稱與屬性（是否鍵欄位）。一或多個鍵欄位合稱主鍵（Primary Key），其值唯一決定一筆資料。

  • 欄位不是獨立物件，只能在表中維護。可以不用 Data Element、直接給型別與長度（Predefined Type／直接型別），但失去 F1、標籤與重用性。
  • 透明表啟用時自動建到資料庫，同名、同欄位名；DDIC 型別轉成資料庫對應型別。
  • DDIC 中的欄位順序可以和資料庫不同——所以新增欄位不必轉換表格，資料庫只做 ALTER TABLE 修改目錄（第 14 節）。
  • ABAP 存取透明表兩種方式：用 ABAP SQL（舊稱 Open SQL；或 Native SQL）讀寫資料；或把表格當作結構型別宣告變數。
  • 字典中「沒有對應資料庫物件」的結構化型別就是 Structure。

參考欄位規則：型別 CURR（金額）或 QUAN（數量）的欄位必須指定「參考表」與「參考欄位」，參考欄位型別必須是 CUKY（幣別）或 UNIT（單位）。執行時才依參考欄位決定小數位——例如日圓 0 位小數、台幣在 SAP 內部也以 2 位存放（TCURX 設定例外幣別）。

Include 結構：避免重複定義。

  • 結構可以被 Include 到表或其他結構；Include 可以再 Include。
  • 表不能 Include 另一張表（2007 筆記的說法是「一條 Include 鏈只能容納一張資料庫表」）。
  • Include 結構上定義的外來鍵會傳遞到包含它的表——所以外來鍵依賴 Include 中的定義。

7. 技術設定：Data Class、Size Category、Logging（Unit 3 Lesson 1）

技術設定（SE13，或 SE11 → Technical Settings）決定表在資料庫的儲存需求與存取行為：建在哪、預期多大、要不要緩衝、要不要記日誌。完整的操作畫面見 1-2 章第 3 節，這裡補原廠的「為什麼」。

Data Class意義例子
APPL0 主資料很少修改客戶名稱、地址、電話
APPL1 交易資料經常修改倉庫庫存（每張採購單都會變）
APPL2 組織資料安裝／Customizing 時定義，之後幾乎不變國家代碼
系統資料（SDIC、SSRC、SLOAD…）R/3 系統本身需要程式原始碼、系統設定
USER、USER1… 客戶資料類客戶開發用須在資料庫另外配置儲存區

Data Class 在 Oracle 對應 Tablespace。選對了，啟用時表就自動建在正確的儲存區。

Size Category：預期資料量。建表時先配一個初始 extent（所有類別大小相同），不夠再依 Size Category 決定的固定大小追加 extent。選太小 → 大量小 extent、碎片化；選太大 → 浪費空間。2007 筆記寫 0～4，Col18 寫 0～9，以你系統 SE13 的下拉選單為準。

碎片化（Col18 新增）：交易資料表因快速成長、頻繁新增刪除，配置空間會有大量空洞；索引也會碎片化。

  • 索引可重建（rebuild）。重建期間程式仍可讀表，但該索引不能用，大表（> 100,000 筆）可能數分鐘到數小時，期間可能 Full Table Scan。
  • 表格重建（透過資料庫工具／SE14）期間不能讀也不能改，要排在夜間離峰，由 Basis／DBA 執行；重建前先檢查並調整 Size Category。

Log Data Changes（表格日誌）：

  • 技術設定勾 Log Data Changes 還不夠，必須系統參數 rec/client 也開啟：ALL（所有用戶端）、000[,…]（指定用戶端）、OFF（不記錄）。
  • 日誌與更新（update）獨立記錄，寫在表 DBTABLOG；用 SCU3（Table History）顯示。
  • 代價：每次修改都多一次寫入；所有使用者共用同一張日誌表，即使大家改的是不同應用表，也可能互相鎖住。

其他設定（Col18）：

  • Write Access Only with Java：限定只有 Java 端能改；ABAP 寫入的資料不保證 Java 讀得正確（ASCII 資料除外）。
  • DB-Specific Properties：NW 7.4 起可選 SAP HANA 的 Row Store／Column Store；在 HANA 上用 DDIC 建的表預設 Column Store（整欄連續序列化存放）。

8. Pooled Table 與 Cluster Table（Unit 3 Lesson 2）

除了透明表（DDIC 與資料庫一對一），SAP 還有兩種「多張邏輯表放進一張實體表」的型態，主要用於系統內部資料；業務資料應存在透明表。

Cluster Table（表叢集）Pooled Table（表池）
放什麼功能相依、分散在多張表的資料互不相依的小表
實體鍵各邏輯表鍵欄位的交集＝Cluster Key，加 PAGNO 保證唯一TABNAME（邏輯表名）＋VARKEY（邏輯表鍵欄位串接，所以鍵欄位必須是 C 型）
非鍵資料壓縮存在 VARDATA；放不下產生 overflow 記錄；TIMESTAMP、PAGELG 是管理欄位壓縮存在 VARDATA，長度在 DATALN
經典例子BSEG（RFBLG）、KONV（KOCLU）、CDPOS（CDCLS）A0xx 條件表（KAPOL）、部分 Customizing 表（ATAB）

優點：表與欄位數少、資料壓縮（省記憶體與網路）、SQL 陳述種類少、管理簡單；Cluster 的相依資料一次讀回。缺點：不能 Native SQL、不能建 View 或 ABAP JOIN、不能建二級索引、不能 Append；Pooled 只把鍵欄位條件送到資料庫，Cluster 只把 Cluster Key 條件送到資料庫，非鍵欄位的 ORDER BY／GROUP BY 不會下推；Pooled 需要比語意更長的鍵。技術設定多一個 Convert to transparent table 旗標。

S/4HANA 現況：在 SAP HANA 上，Pool／Cluster 表已全面轉成透明表（depooling／declustering）。BSEG 在 S/4HANA 是透明表；KONV 被 PRCD_ELEMENTS 取代；財務明細的單一事實來源是 ACDOCA。新開發不要再建立 Pool／Cluster 表。舊程式裡「因為 BSEG 是 cluster 表所以不能 JOIN」的繞路寫法，在 S/4HANA 可以改回正常 JOIN——但仍要評估改讀 ACDOCA 或標準 CDS View（例如 I_JournalEntryItem）。

9. 索引：Primary、Secondary、Extension（Unit 4 Lesson 1）

索引可以看成「資料庫表縮減到特定欄位的排序副本」，讓資料庫用二分搜尋快速定位，並帶一個指回原表記錄的指標以讀取其他欄位。

種類說明
Primary Index由主鍵組成，永遠唯一；表第一次啟用時自動建立；索引 ID 0 保留給它
Secondary Index大表經常以非鍵欄位查詢時建立；多數非唯一，也可唯一（唯一索引保證資料不重複）
Extension Index（Col18 新增）屬 Enhancement Framework。以前客戶直接在 SAP 表加 Z 索引，升級後會被刪掉要重建；Extension Index 升級時自動帶過、不需修改調整

規則：索引 ID 三碼；客戶在 SAP 表上建的索引 ID 必須以 Y 或 Z 開頭。可指定「啟用時是否建到資料庫」以及只建在特定資料庫系統清單上（有些索引只對某些 DB 有效）。建立步驟：SE11 → 表名 → Indexes → Create → 選欄位 → 選 Unique／Non-unique → 啟用。Secondary 與 Extension Index 步驟相同。

設計索引的原則（兩版教材一致）：

  • 索引要小，只放 WHERE 中常用的欄位；最常被篩選的欄位放前面，WHERE 的欄位順序配合索引順序。
  • 只放有鑑別度的欄位（能有效縮小資料量）。
  • 每次新增、修改、刪除都要調整所有索引；經常異動的表不要建太多索引。
  • 同一張表的索引彼此盡量不重疊。
  • 用哪個索引由資料庫最佳化器（Optimizer）決定，不是 ABAP 決定。
2007 筆記寫「索引只能用到選擇中最後指定的欄位」，原意是：索引只能用到從最左邊開始、連續有指定條件的欄位為止。例如索引 (A, B, C)，WHERE 只給 A 和 C，則只有 A 能走索引，C 要逐筆比對。

10. 表格緩衝：三種型態與決策樹（Unit 4 Lesson 2）

被緩衝的表，記錄直接從執行該交易的應用伺服器本地緩衝區讀取，免去資料庫存取，效能提升 10～100 倍。緩衝區滿了，最久未被存取的資料被替換（非同步、動態決定時機，只在剩餘空間低於門檻或存取品質不佳時才替換）。

型態讀一筆時載入什麼適用注意
Full Buffering（全緩衝）整張表小、讀多、寫少；經常查「不存在」的記錄（緩衝區就能判斷不存在）緩衝區內依主鍵排序；只能用到「最後一個有指定的鍵欄位」為止——第一個鍵欄位沒給就是整張表掃描，此時若有合適二級索引，直接查 DB 可能更快
Generic Buffering（一般緩衝）與該筆一般鍵（主鍵左邊 n 欄）相同的所有記錄只有少數一般區域常被處理一般鍵太小→區域太多太碎（不如全緩衝）；太大→一筆異動就讓大量資料失效。依用戶端的全緩衝表會自動變成以 MANDT 為一般鍵的一般緩衝；語言相依表的一般鍵是到語言欄位為止的所有鍵
Single-Record Buffering（單筆緩衝）只有被讀的那一筆大表，但經常以 SELECT SINGLE 重複讀少數幾筆省空間但管理成本高、載入需多次 DB 存取；查無資料也會記成「不存在」避免重查；不是 SELECT SINGLE（完整主鍵）的存取一律繞過緩衝

設定位置：SE11 → Technical Settings（或 SE13）→ Buffering not allowed／Buffering allowed but switched off／Buffering switched on → 選型態（Generic 要填一般鍵欄位數）。Database View 也能緩衝（第 16 節）。

附錄二：緩衝決策樹（强晟筆記 p147、Col18 p89，依原圖整理）：

  1. 讀資料時能否接受暫時不一致？否 → 不緩衝。
  2. 大多數存取是唯讀嗎？否 → 不緩衝。
  3. 預估表大小 < 8 KB？是 → 全緩衝。
  4. 否則：大多用 SELECT SINGLE 存取嗎？是 → 單筆緩衝。
  5. 否則：預估 > 1 MB（超過約 1000 筆）？是 → 依系統安裝狀況決定，需再考慮「全緩衝或一般緩衝？」「二級索引還是緩衝？」
  6. 否則：存取時經常指定鍵的左邊部分？是 → 一般緩衝（一般鍵欄位數適當）；否 → 全緩衝。

*& 會「用到緩衝」與會「繞過緩衝」的寫法
*&   SCARR 在航班模型中是全緩衝的小表
*&---------------------------------------------------------------------*

11. 緩衝同步：12 個時間點（Unit 4 Lesson 2）

緩衝區在各應用伺服器本地，某台改了資料，其他台怎麼知道？答案：固定間隔同步。間隔由系統參數 rdisp/bufreftime（秒）設定，範圍 60～3600，建議 60～240。

Col18 英文教材 p83 把參數名印成「rdisp/buffertime」，是錯字；正確名稱是 2007 筆記寫的 rdisp/bufreftime（同步模式另有 rdisp/bufrefmode）。

原廠用兩台應用伺服器、全緩衝表（2007 版叫 TAB，Col18 用 SCARR）演示：

時間點伺服器 1伺服器 2
起始兩台都還沒讀過該表，本地緩衝都沒有
1從資料庫讀取記錄
2整張表載入本地緩衝，之後讀緩衝
3本地還沒有，從資料庫讀
4整張表載入本地緩衝
5刪除記錄並更新資料庫
6在同步表（DDLOG）寫入一筆異動紀錄
7更新自己的本地緩衝
8讀不到已刪記錄（正確）仍從本地緩衝讀到已被刪除的記錄——程式行為取決於跑在哪台伺服器
9同步時間到，兩台都去檢查同步表
10是自己改的，不必失效發現被伺服器 1 改過 → 本地緩衝該表失效
11再讀時走資料庫
12重新載入緩衝，三方再度一致

優點：網路負載最小（若每次異動都立即廣播給所有伺服器，效能會很差）。缺點：兩次同步之間，本地緩衝可能是過時資料。結論：

  • 只緩衝很少寫入（讀多）或暫時不一致無所謂的表。
  • 經常異動的表不要緩衝，否則不斷失效、重載，反而更慢。
命令列輸入 /$TAB 會重置目前這台應用伺服器的表格緩衝（/$SYNC 重置所有緩衝）。只在確定緩衝不一致時使用——大型系統重新填滿緩衝可能要數小時，期間效能明顯下降。生產機上請找 Basis 評估，不要當作「資料怪怪的就按一下」的萬用鍵。

12. 輸入檢查：固定值、外來鍵、Value Table、Text Table（Unit 5）

固定值（Fixed Values）：Domain 的值域若只允許有限幾個值，就定義為固定值（可逐一列出或定義區間）。固定值同時提供 F4 清單與畫面輸入檢查。Col18 新增 Fixed Value Append：一個 Append 只屬於一個 Domain，一個 Domain 可有多個；是免修改的標準增強，升級時自動帶過。

强晟筆記 p52、p53、p64 三頁的原文完全一樣（都在講 cardinality），他自己也吐槽「SAP 犯錯了」。正確內容以 Col18 為準：p52 應是固定值（上一段）、p53 應是 Value Table（下方）、p64 才是語意屬性（Cardinality、外來鍵欄位型態）。

外來鍵（Foreign Key）——原廠例子：客人要訂美國航空（AA）0017 班機，在 8 號櫃台訂位。SBOOK 存所有訂位，SCOUNTER 存各航空公司的有效櫃台。AA 沒有 8 號櫃台，所以 SCOUNTER 查不到 → SBOOK 的輸入被拒絕。

  • 定義：一張表中的某個欄位組合，若是另一張表的主鍵，就稱為外來鍵。外來鍵連接兩張表。
  • 檢查表（又稱參考表）＝被檢查的那張；檢查欄位＝外來鍵表中要被檢查的欄位。
  • 只在畫面輸入與 F4 時檢查。ABAP 程式直接 INSERT／MODIFY 資料庫完全不會檢查外來鍵——這是新手最常誤會的一點。
  • 檢查欄位與檢查表對應鍵欄位必須用同一個 Domain（Data Element 可以不同）；其他外來鍵欄位只要型別與長度相同即可，但仍應盡量同 Domain——日後改長度時才不會失去一致。

Value Table 與 Check Table 不同：

  • Value Table 寫在 Domain 上，只是讓系統在你定義外來鍵時自動提出檢查表建議。光設 Value Table 不會有任何 F4 或檢查，一定要再定義外來鍵（Col18 p106 明講；2007 筆記把它理解成「值範圍存在表中」，不完整）。
  • 建議不一定對：SBOOK-AGENCYNUM 的 Domain 的 Value Table 是 SBUSPART（所有航空公司業務夥伴），但這個欄位只允許旅行社，正確的檢查表是 STRAVELAG（SBUSPART 的子集）。必須手動覆蓋建議；不知道該選哪張，系統可列出所有以 Domain S_BUSPANUM 為鍵欄位的表。
  • SAIRPORT-AIRPORT 所用 Domain 的 Value Table 就是 SAIRPORT 本身——這是正確的，但這個欄位本身不會定義外來鍵（避免自我循環）。

語意屬性：

  • Cardinality（基數）：一律從檢查表的角度描述，例如 1:N、1:CN。
  • 外來鍵欄位型態：Not specified；No key fields/candidates（外來鍵欄位不是外來鍵表的主鍵，也不能唯一識別）；Key fields/candidates（是主鍵或候選鍵）；Key fields of a text table（後者的特例：外來鍵表是檢查表的文字表）。

Text Table：SMEAL（機上餐點）的名稱存在 SMEALT。SMEALT 的鍵＝SMEAL 的全部鍵＋一個語言欄位（型別 LANG）。外來鍵從 SMEALT 指向 SMEAL，外來鍵欄位型態選 Key fields of a text table。一張表最多只能有一張 Text Table。

13. 字典物件的相依：啟用版本、Runtime Object、Where-Used（Unit 6）

Active／Inactive 版本：

  • Active 版本：執行環境（ABAP 處理器、資料庫介面）讀的版本。
  • Inactive 版本：修改已啟用物件時產生，可不檢查就存檔，不影響執行系統。
  • 啟用（Activate）：先做一致性檢查，通過才取代 Active 版本。例：結構原有 3 欄，加 1 欄後同時存在 3 欄的 Active 與 4 欄的 Inactive；啟用後 Active 變成 4 欄。
  • 相依物件多、預期執行很久（例如改一個被大量表使用的 Domain）時，選 Activate in background。

Mass Activation（大量啟用，Col18）：傳輸請求匯入時自動呼叫。優點：多個 Domain／Data Element 影響同一張表時只重新啟用一次；相關物件（如 Domain 與其 Value Table）可一起啟用。單獨啟用則要自己照順序——先 Domain、Data Element，再表。

Runtime Object（執行時期物件，俗稱 Nametab）：表或結構的資訊分散在 Domain、Data Element、結構定義裡；啟用時合併成一個為 ABAP 最佳化的物件並被緩衝。內容包含：

  • 整體資訊：欄位數等。
  • 各欄位：名稱、位置、型別、長度、小數位、參考欄位、參考表、檢查表、轉換常式。
  • 資料庫介面需要的：是否依用戶端、緩衝、鍵欄位。

可在 SE11 → Utilities → Runtime Object 檢視。會產生 Runtime Object 的物件：Data Element、Table Type、View、Structure、Table——也就是所有能在 ABAP 當型別用的字典物件。啟用時，Runtime Object 與所有使用它的程式、畫面的時間戳都會被調整（所以程式下次執行會重新產生）。

相依物件處理：已啟用物件被修改並啟用時，系統找出相依物件並重新啟用它們的 Active 版本（相依物件自己的 Inactive 新版本不會被動到）。例如改 Domain 型別 → 所有用到它的 Data Element、結構、表自動重新啟用；若相依的是資料庫表，還可能觸發表格調整（第 14 節）。

Where-Used List：每個字典物件的維護畫面都能叫出。可選要找的使用物件類型（例如「所有用到此 Data Element 的結構與表」），也能找非字典物件（「所有用到這張表的程式」），可限縮套件（2007 版叫開發類）或命名空間；使用者很多時放背景執行。

Repository Information System：SE84（整體）、SE15（ABAP 字典部分）。可依屬性（例如表的緩衝型態）、套件、短描述、作者、最後修改日期找物件，清單可直接跳到維護交易。

14. 表格轉換：QCM 暫存表與中止處理（Unit 7 Lesson 1）

ABAP 程式要能正確存取表，Runtime Object 必須與資料庫結構一致。每次在 DDIC 改表並啟用，系統都判斷資料庫要不要跟著調整。有些修改不必動資料庫——例如調整非鍵欄位的順序。

三種調整方式：

方式做法資料
刪除重建刪掉資料庫表、啟用新定義、重建全部遺失（表是空的才會這樣做）
ALTER TABLE只改資料庫目錄保留；索引可能要重建
表格轉換（Conversion）建新表、搬資料保留；最耗時、最耗資源
2007 筆記把「轉換表」寫成「最節約時間的辦法」，是翻譯錯誤；原廠原文是 the most time-consuming way（最耗時）。系統的判斷順序：表沒資料 → 刪除重建；有資料 → 先試 ALTER TABLE；資料庫做不到 → 轉換。

轉換流程（例：表 TAB 的欄位 3 從 60 字元縮成 30，有二級索引 A11，表內已有資料）：

  1. 鎖表，禁止再改結構；轉換中止時鎖會保留。所有相依 View 被停用。
  2. 資料庫表 TAB 改名為 QCMTAB（若已存在舊的 QCMTAB 先刪除）；所有二級索引被刪除。
  3. 啟用 DDIC 的 Inactive 版本，以新結構建立 QCM8TAB（含主索引），此時是空表。資料庫裡此刻不存在名為 TAB 的表，存取它的程式都會失敗。
  4. 用 MOVE-CORRESPONDING 把 QCMTAB 的資料搬回 QCM8TAB；縮短的欄位多餘部分被截掉。每搬 16 MB 做一次資料庫 Commit（所以 Rollback Segment 需要 16 MB），Commit 釋放鎖、下一段再申請。
  5. 全部搬完後刪除 QCMTAB（若因縮短主鍵產生重複而有記錄沒搬過去，為安全起見保留 QCMTAB）。
  6. QCM8TAB 改名回 TAB，重建二級索引，重新啟用第 1 步停用的 View。
  7. 解除第 1 步的鎖；刪除重啟日誌（reset/restart log）。
2007 筆記的第 5、6 步順序是「先改名、再刪 QCMTAB」，Col18 是「先刪 QCMTAB（或保留）、再改名」，並補了「有重複就保留 QCMTAB」的安全機制；以 Col18 為準。

轉換可能的問題：

  • Tablespace 溢位：轉換期間資料同時存在兩張表，空間需求加倍。溢位就中止，擴充後在 SE14 重新開始。大表轉換前先確認空間。
  • 縮短主鍵造成資料遺失：移除鍵欄位或縮短鍵長度 → 多筆記錄鍵值相同，只能搬回其中一筆，無法預測是哪一筆。移除用戶端欄位時，甚至無法保證留下來的都來自同一個用戶端。要保留特定記錄就必須轉換前先清資料。
  • 不合法的型別變更：只有 MOVE-CORRESPONDING 能做的型別轉換才允許，否則搬回時中止。此時要用資料庫工具刪表、把 QCM 表改回原名、在 SE14 重建 Runtime Object、DDIC 結構改回原狀再啟用。
  • Pool／Cluster 表轉換時，QCM 表以透明表建立；欄位數若超過資料庫單表上限就無法轉換。

恢復中止的轉換：鎖還在，SE11 不能再改這張表。用 Database Utility SE14 分析：先看物件日誌（Object Log），沒線索再看 SM21 系統日誌或 ST22 短傾印。修正原因後按 Continue adjustment 從中止處繼續。另一個按鈕 Unlock table 只刪鎖——若資料只存在暫存表（在第 3、4 步中止）絕對不能按。

原廠用粗體寫：不可以在生產期間做結構調整；所有存取該表的應用必須停用。實務上，Z 表改鍵、縮長度這類變更要排維護時段，並在 QAS 用生產資料量先演練一次，量測轉換時間。

15. Append Structure、Customizing Include 與 Enhancement Category（Unit 7 Lesson 2）

Append Structure 讓客戶不修改表定義就能在 SAP 標準表或結構尾端加欄位：

  • 一個 Append 只屬於一張表；一張表可有多個 Append。
  • 表啟用時，系統找出所有已啟用的 Append，把欄位接在後面；Append 建立或修改後啟用，所屬表也會一起啟用。
  • Append 本身也是結構，可當 ABAP 型別。
  • 4.6C 起，可用 Append 為表中既有欄位加外來鍵與 Search Help。
  • 建在客戶命名空間 → 升級時不會被覆蓋，不需要 SPDD 調整；新版標準表啟用時自動把 Append 欄位接上。
  • 因為 DDIC 欄位順序可與資料庫不同，加 Append 或在 Append 加欄位不必轉換，只做 ALTER TABLE。
  • 複製一張帶 Append 的透明表時，Append 的欄位會變成一般欄位（Col18 提示）。
Append 的限制：① Pool／Cluster 表不能加 Append；② 表中有 LCHR／LRAW 長欄位就不能加（長欄位必須在最後）；③ Append 中的欄位名必須在客戶命名空間 YY 或 ZZ 開頭（强晟特別提醒：SAP 自己也有 Y、Z 開頭的欄位，只用單一 Z 仍可能撞名）；④ 有自己保留命名空間的合作夥伴要用自己的命名空間。

兩種增強方式：

  • Customizing Include（CI_ 開頭）：SAP 在標準結構／表中預留位置，客戶在預留處填欄位（例如銷售文件的 CI_ 結構）。
  • Append：不需預留，接在尾端。

Append 可能帶來的問題：被增強的結構若被其他結構以 Include 方式放在中間，後面欄位會位移；Unicode 檢查開啟的程式，增強會影響賦值、運算元檢查、offset/length 存取（例如在純字元結構中插入數值或深層元件，片段視圖改變）。

Enhancement Category（SE11 → Extras → Enhancement Category）：

類別意義
Not classified未分類
Cannot be enhanced不可增強
Can be enhanced (character-type)所有元件與增強都必須是字元型（C、D、N、T）
Can be enhanced (character-type or numeric)不可含深層型別（STRING、XSTRING、內表）
Can be enhanced (deep)任意型別

含 Include 或子結構時，Include 的等級不能比外層結構更寬鬆（例如外層含一個 level 4 的 Include，外層就不能選 level 2、3）。

16. Database View、Inner／Outer Join 與 Append View（Unit 8 Lesson 1）

一個應用物件的資料常分散在多張表，View 讓你用「應用的角度」看資料。建構 View 的三個動作：

  • Join（連接）：從兩表的笛卡兒積出發，用連接條件留下有意義的組合（例：SCARR-CARRID = SFLIGHT-CARRID）。
  • Projection（投影）：只留想看的欄位（例：隱藏 PLANETYPE）。
  • Selection（選擇）：用選擇條件限縮記錄（例：只看 CARRID = 'DL'）；條件可以用 View 中沒有的欄位。

原廠例子：旅行社要查「哪位客人訂了哪些航班」，資料分散在 SCUSTOM（客戶）、SBOOK（訂位）、SPFLI（航班）。連接條件：

  • SBOOK-MANDT = SCUSTOM-MANDT；SBOOK-CUSTOMID = SCUSTOM-ID
  • SPFLI-MANDT = SBOOK-MANDT；SPFLI-CARRID = SBOOK-CARRID；SPFLI-CONNID = SBOOK-CONNID
  • 選擇條件：只看未取消的訂位 SBOOK-CANCELLED <> 'X'（教材寫 CANCELED，實際欄位名是 CANCELLED）

連接條件可以從既有外來鍵複製（維護畫面有 Relationships 按鈕）。兩表有同名欄位要放進 View 時，必須替其中一個改名。

Inner vs. Outer Join：Inner 只取「所有表都有對應記錄」的資料；Outer 則即使部分表沒有對應也會選出。Inner 的結果是 Outer 的子集。Database View 一律 Inner Join；Maintenance View（與 Help View）是 Outer Join。

Database View 的特性：

  • 啟用時在資料庫建立；存取直接交給資料庫執行。改定義時只要刪掉重建（View 不存資料）。
  • 可用 ABAP SQL 與 Native SQL 存取。
  • 多表 View 只能讀（Maintenance Status 設為 read only）。
  • 可以緩衝，設定同表格緩衝；任何基底表異動就讓緩衝的 View 資料失效。
  • 用 View 選取比分別存取個別表快，但仍要確認基底表有合適索引。原廠註明：ABAP SQL JOIN 的效能不如靜態定義的 Database View（這在傳統資料庫成立；HANA 上兩者都會下推，差異不大）。
  • 整張表 Include 進 View：View field 填 *、Table 填表名、Field name 填 *；要排除某欄，View field 填 -、Field name 填該欄。基底表加欄位（含 Append）時 View 自動跟著調整。
  • Append View（4.6C 起）：不修改就把基底表欄位加進 Database View；一個 Append View 只屬於一個 View，一個 View 可有多個 Append View。
  • External View（NW 7.4 起、Col18 新增）：HANA 資料庫上的 HANA View 在 ABAP 端的代理物件，只能用 ADT 建立，SE11 只能顯示。

17. Maintenance View、SE54 與 View Cluster（Unit 8 Lesson 2、3）

分散在多張表、構成一個邏輯單元的資料稱為應用物件。使用者不在乎資料分在幾張表——Maintenance View 讓你一次維護，系統自動把資料分配回各基底表。

  • 所有表必須以外來鍵相連，連接條件一律從外來鍵來，不能像 Database View 那樣直接輸入。
  • 維護介面要用 SE54（Generate Table Maintenance Dialog）或 SE11 → Utilities → Table Maintenance Generator 產生；產生時會自動產生把資料分配到基底表的函數模組。
  • 用 SM30 維護資料。

建立 Maintenance View 的要點：View Type 選 Maintenance View；主表的所有鍵欄位都要放進 View；依用戶端的表要包含 MANDT（畫面不顯示）；文字表的語言欄位不要複製（維護時自動帶登入語言）；先放鍵欄位再放功能欄位。步驟：① 複製表（在主表上按 Relationships 選外來鍵；基數不適合的關聯列在「Relationships with unsuitable cardinality」下）→ ② 複製 View 欄位（主表全部鍵欄位，以及次表中未透過連接條件連到已選鍵欄位的鍵欄位）→ ③ 選擇條件（選用）→ ④ Maintenance Status → ⑤ 啟用（Utilities → Activation log）。

維護屬性意義
R（Read only）畫面不可輸入；新增記錄時必須在背景自動填值。參照表的欄位固定是 R
H（Hidden）畫面不顯示；存檔時 R、H 欄位與其他欄位一樣寫入資料庫
S（Subset）限縮工作範圍：只顯示該欄位為指定值的記錄，新增時也受限
P可在 SE11 的 View 定義中對個別欄位指定

Maintenance View Variant：產生好的維護對話的「部分視圖」（更少欄位或更嚴的選擇），沒有自己的維護對話。注意：View 的選擇條件要在產生維護對話之後才會生效；事後在字典加條件但沒重新產生，Variant 不會套用。

SE54 產生時要填：Function Group（沒有就建）、Authorization Group（誰能維護）、Maintenance Type（一步式：只有總覽畫面；二步式：總覽只顯示鍵與長度 > 20 的文字欄位，雙擊進明細）、Maintenance Screen 編號（Find Screen Numbers 可建議）、Recording Routine（維護的資料是否、如何進傳輸請求）。

優缺點：能很快做出簡單維護畫面；但沒有非同步更新，只適合少數人維護Customizing 表與中小量客戶表，不該讓大量使用者日常使用。

View Cluster（Col18 新增，Unit 8 Lesson 3）：把多個已產生的維護對話組成一個維護單元。

  • Maintenance View 只能維護 1:1 關係的表（語言相依文字表例外）；View Cluster 可維護 N:M，也能組合沒有鍵相依的 View。
  • 適合多層 Master–Detail；一或多個根對話；最多 14 個維護對話；每個可以是一步或二步式。
  • 先為每個 View 產生維護對話，再組成 Cluster；用 SM34 維護。
  • 好處：對話間導覽方便；刪除、複製、存檔、取回、手動傳輸時保持一致——刪上層記錄會自動刪下層相依記錄。

18. Elementary Search Help 與附加機制（Unit 9 Lesson 1）

F4 輸入說明是 SAP 標準功能，整個系統外觀與行為一致。F4 必須滿足四個需求：考慮上下文（使用者已輸入的值、前面步驟的資訊）、決定可選值與輔助資訊、提供對話（清單＋必要時的條件畫面）、把選中的值傳回（包括更新其他顯示欄位）。

Search Help 的結構——和函數模組一樣分介面與內部行為：

元件說明
Selection Method資料從哪張表或 View 來。資料在一張表（含其文字表）就用表，系統自動以登入語言取文字；跨多表用 View。不可用 Maintenance View；一般用 Database View（Inner Join），需要 Outer Join 時用 Help View。選擇方法依用戶端時只查登入用戶端，參數中不可有用戶端欄位
Dialog Type限制條件畫面是否先於命中清單出現：Display values immediately／Dialog with value restriction／Dialog depends on set of values（筆數少直接列、多則先給條件畫面）
Parameters用選擇方法的欄位（用戶端除外）與文字表非鍵欄位；LPos＝命中清單位置、SPos＝條件畫面位置；型別由 Data Element 決定
IMPORT／EXPORTIMPORT：從畫面帶進 F4；EXPORT：從 F4 傳回畫面。兩者合起來就是介面。也可以有不出現在兩個對話框、只負責回填畫面欄位的介面參數
Default Value可給固定文字、系統欄位、GET 參數；可用來做簡單的選擇條件
Hot Key一個字母或數字；畫面輸入 =<hot key>.<SEL1>.<SEL2> 按 F4 會直接以此條件（尾端自動加 *）顯示命中清單
Search Help Exit見第 19 節

搜尋欄位（Search Field）是特例：只有它的內容是搜尋字串（含 * 或 +）且對應參數為 IMPORT 時，才會帶進 F4。只含輔助資訊的參數不要設 IMPORT，否則使用者每次重新選值前都得先清空那些畫面欄位。

强晟筆記 p128 寫「搜尋欄位必須分配成搜尋說明的輸入參數」，與原廠不符。Col18 p198 原文：搜尋欄位必須對應到 EXPORT 參數（才能把值傳回），而也應該是 IMPORT 參數（才能利用使用者已輸入的搜尋樣式）。

Search Help 附加到字典欄位的三種方式：

  1. 直接附加到表或結構的欄位：定義方式類似外來鍵，依系統建議對應介面參數與欄位。
  2. 透過檢查表：欄位有檢查表時，檢查表的鍵欄位自動成為 F4 可選值；若檢查表有文字表，顯示其第一個字元型非鍵欄位。不滿意標準顯示，可把 Search Help 附加到檢查表，所有以它為檢查表的欄位都受用。
  3. 附加到 Data Element：所有參照它的欄位都有效；必須指定一個 EXPORT 參數做資料傳遞。

附加到檢查表或 Data Element 重用性高，但介面能傳的值較受限制。一個欄位、表或 Data Element 只能附加一個 Search Help——要多條搜尋路徑，就附加 Collective Search Help。

輸入說明機制的優先順序（原廠總覽圖，由左至右、由上至下，先找到先用）：

  1. 畫面的 PROCESS ON VALUE-REQUEST（POV 自寫 F4）
  2. 畫面欄位附加的 Search Help（Screen Painter）
  3. 畫面流程邏輯中的輸入檢查（FIELD … VALUES／SELECT，已過時）
  4. 字典欄位附加的 Search Help
  5. 檢查表附加的 Search Help
  6. 檢查表＋文字表／檢查表的鍵值
  7. Domain 固定值
  8. Data Element 附加的 Search Help
  9. 日曆／時間說明（DATS／TIMS）
搞不清楚 F4 是哪個機制在作用？在命中清單按右鍵 → Technical Info，會顯示是哪個 Search Help、從哪層附加。

F4 效能：大量資料時要限縮命中清單（從上下文或條件畫面）；對用來限縮的欄位建索引通常效果顯著；選擇方法的資料量小時，檢查能否緩衝。顯示方式：List Box（單欄、無條件，在 Screen Painter 設定，見 5-9 章 BC410）、Control（非模態，可 Hold list 連續填多欄）、Dialog（模態）；使用者可在 Help → Settings 選偏好，管理員可設預設值。

Help View：只能當 Search Help 的選擇方法，定義方式同 Maintenance View、使用 Outer Join 邏輯；因為系統無法把 Help View 直接下推到資料庫，要產生自己的存取常式，所以優先用 Database View。命名慣例 H_，客戶用 H_Y／H_Z。表＋文字表的選擇等同一個「虛擬 Help View」，不必另建——除非主表與文字表有同名的非鍵欄位且 F4 需要文字表那一欄。

增強搜尋（Col18 新增）：SE11 中每個 Elementary Search Help 可開啟 Proposal Search for Input Fields（Type-ahead，邊打邊列出建議，預設 10 筆，所有資料庫都可用，欄位出現放大鏡圖示）、Multi-column Full Text Search（資料庫支援時才有，選擇方法限表、文字表、標準／Projection View）、Accuracy Value（0～1 的容錯值，Fuzzy Search 目前僅 HANA）。前提：SAP GUI for Windows 7.30 PL5（建議 PL6）以上、NW 7.4 SP06；Web Dynpro 不支援（SAP Note 1861491）。全系統可在 SDSH_CONFIG 關閉（需 S_DEVELOP 活動 02）。

19. Collective Search Help、Append Search Help 與 Search Help Exit（Unit 9 Lesson 2）

替代搜尋路徑：關聯式模型用形式鍵（員工編號）識別實體，但現實中人們用屬性（姓名、住址）描述它，而且每個人、每個情境用的屬性不同——所以一個欄位需要多條搜尋路徑。

  • Collective Search Help：把多個 Elementary Search Help 組合起來，每個以分頁呈現；重複使用時自動停在上次用的分頁。它有 IMPORT／EXPORT 介面，可像 Elementary 一樣附加到欄位、表、Data Element；沒有選擇方法與對話行為，取而代之的是包含的 Search Help 清單與參數對應。一個 Search Help 可被多個 Collective 包含，Collective 也能包含 Collective。
  • 要讓 Collective 支援 Type-ahead，至少一個被包含的 Elementary 要開啟 Proposal Search；有兩個以上開啟時，以第一個的設定為準（順序可在 SE11 或 Exit 中調整）。
  • Append Search Help（4.6 起）：免修改增強標準 Collective Search Help。它本身是 Collective，指派給另一個 Collective（其 appending object），並使用對方的介面。放在客戶命名空間；包含的 Elementary 可以自建，也可以是 SAP 既有的。SAP 自己也用它做元件分離，客戶增強應另建獨立的 Append Search Help。
  • 隱藏不需要的分頁：把那個 Elementary 放進你的 Append Search Help，勾 Hidden——不必修改標準。
典型實務：物料 F4 的 Collective Search Help MAT1、客戶的 DEBI、供應商的 KRED。要加「依舊料號搜尋物料」，就建 Append Search Help 掛到 MAT1，裡面放你的 Elementary（選擇方法 MARA，參數 BISMT、MATNR…）。這正是「先標準再客製」中「用增強點而非修改」的範例。

Search Help Exit：當欄位語意特殊、需要偏離標準時使用。

  • 是一個有標準介面的函數模組，範本 F4IF_SHLP_EXIT_EXAMPLE。
  • F4 處理的每一個步驟之前都會被呼叫，透過介面傳入 F4 處理器的管理資料（含「下一步」資訊）。Exit 可做該步驟的前置處理，或自己完成該步驟（例如無法用單純 SELECT 表或 View 取得資料）並修改下一步。
  • 前綴 F4UT_ 的函數可直接當 Exit，或用來在 Exit 中處理管理資料；例如 F4UT_OPTIMIZE_COLWIDTH 會依內容調整命中清單欄寬（適合姓名這種欄位定義很寬、實際值很短的情況）。
  • 原廠警告：只在例外情況使用，它會導致非標準解法、讓 F4 更難維護。

*"  TABLES
*"      SHLP_TAB TYPE  SHLP_DESCT
*"      RECORD_TAB STRUCTURE  SEAHLPRES
*"  CHANGING
*"     VALUE(SHLP) TYPE  SHLP_DESCR
*"     VALUE(CALLCONTROL) LIKE  DDSHF4CTRL STRUCTURE  DDSHF4CTRL
*"----------------------------------------------------------------------
* 需求：航線 F4 只列「未來 90 天內還有空位」的航線——
*       單純的表/View SELECT 做不到「計算後過濾」，因此在 SELECT 步驟自己撈資料
*"----------------------------------------------------------------------

  CASE callcontrol-step.

    WHEN 'SELONE' OR 'PRESEL1' OR 'PRESEL'.
      " 選擇 Search Help 前／條件畫面前：此例不處理，交回標準流程
      RETURN.

    WHEN 'SELECT'.
      " 讀取畫面帶入的航空公司條件（IMPORT 參數 CARRID）
      DATA(lv_carrid) = CONV s_carr_id(
        VALUE #( shlp-selopt[ shlpfield = 'CARRID' ]-low OPTIONAL ) ).

      DATA(lv_today) = sy-datum.
      DATA lt_r_carr TYPE RANGE OF s_carr_id.
      IF lv_carrid IS NOT INITIAL.                 "列舉條件，而非 BT 區間
        lt_r_carr = VALUE #( ( sign = 'I' option = 'EQ' low = lv_carrid ) ).
      ENDIF.
      DATA(lv_to)    = CONV d( lv_today + 90 ).

      SELECT FROM sflight AS f
        INNER JOIN spfli AS p ON  p~carrid = f~carrid
                              AND p~connid = f~connid
        FIELDS p~carrid, p~connid, p~cityfrom, p~cityto,
               MIN( f~fldate ) AS fldate
        WHERE f~fldate BETWEEN @lv_today AND @lv_to
          AND f~seatsocc < f~seatsmax
          AND f~carrid IN @lt_r_carr
        GROUP BY p~carrid, p~connid, p~cityfrom, p~cityto
        ORDER BY p~carrid, p~connid
        INTO TABLE @DATA(lt_result).

      " 把自己的結果對應到 Search Help 參數（依欄位名），並套用使用者條件
      CALL FUNCTION 'F4UT_RESULTS_MAP'
        EXPORTING
          apply_restrictions = abap_true
        TABLES
          shlp_tab           = shlp_tab
          record_tab         = record_tab
          source_tab         = lt_result
        CHANGING
          shlp               = shlp
          callcontrol        = callcontrol
        EXCEPTIONS
          illegal_structure  = 1
          OTHERS             = 2.
      IF sy-subrc = 0.
        callcontrol-step = 'DISP'.          "資料已備妥，直接跳到顯示步驟
      ELSE.
        callcontrol-step = 'EXIT'.                 "對應失敗：結束 F4
      ENDIF.

    WHEN 'DISP'.
      " 顯示前：調整欄寬（等同把 F4UT_OPTIMIZE_COLWIDTH 當工具函數呼叫）
      CALL FUNCTION 'F4UT_OPTIMIZE_COLWIDTH'
        TABLES
          shlp_tab    = shlp_tab
          record_tab  = record_tab
        CHANGING
          shlp        = shlp
          callcontrol = callcontrol.

    WHEN OTHERS.
      RETURN.
  ENDCASE.

ENDFUNCTION.
Search Help Exit 的介面是 SAP 規定的，必須保留 TABLES 參數與 STRUCTURE 寫法，這是「函數介面相容性」的例外，不是新寫法。步驟代碼：SELONE（選 Elementary 前）、PRESEL1、PRESEL（條件畫面前後）、SELECT（選資料）、DISP（顯示命中清單前）、RETURN（傳回值前）、EXIT、CREATE、APP。

練習與自我檢核

  1. Domain 與 Data Element：SPFLI 的 AIRPFROM 與 AIRPTO 為什麼用同一個 Domain、不同的 Data Element？程式能不能 DATA x TYPE s_airpid.（S_AIRPID 是 Domain）？
    要點：技術相同（機場代碼）→ 同 Domain；語意不同（出發／抵達）→ 不同 Data Element，各有標籤與 F1。程式不能直接參照 Domain，必須透過 Data Element 或表欄位。
  2. Table Type：下列哪些可當 Table Type 的行型別——資料庫表、Structure、Domain、Data Element、Type Group？
    要點：資料庫表、Structure、Data Element 可以；Domain 與 Type Group 不行。
  3. 技術設定：你勾了某 Z 表的 Log Data Changes，但 SCU3 看不到任何紀錄，可能原因？這個設定對效能有什麼影響？
    要點：系統參數 rec/client 為 OFF 或未包含該用戶端；日誌寫在 DBTABLOG，每次異動多一次寫入、共用日誌表會造成鎖等待。
  4. 緩衝型態：(a) 國家代碼表（約 250 筆）(b) 一張 5 百萬筆、但程式總是以完整主鍵 SELECT SINGLE 讀幾百筆的表 (c) 每秒都在更新的庫存表——各選哪種緩衝？
    要點：(a) 全緩衝（且依用戶端的話自動以 MANDT 為一般鍵）；(b) 單筆緩衝；(c) 不緩衝。
  5. 緩衝同步：兩台應用伺服器，伺服器 1 刪了一筆全緩衝表資料，伺服器 2 在下次同步前讀這筆會發生什麼？間隔由哪個參數控制、建議值？
    要點：伺服器 2 仍從本地緩衝讀到已刪資料；rdisp/bufreftime，60～3600 秒，建議 60～240（Col18 印成 rdisp/buffertime 是錯字）。
  6. 索引：SBOOK 有索引 (MANDT, CUSTOMID, FLDATE)，下列 WHERE 何者能充分利用？ (a) CUSTOMID = … AND FLDATE IN … (b) FLDATE IN … (c) CUSTOMID <> …
    要點：只有 (a)。(b) 跳過最左欄；(c) 否定條件通常無法走索引。另：在 S/4HANA 建索引前先用 ST05 證明需要。
  7. 外來鍵：程式用 INSERT sbook FROM @ls_book 寫入一筆 COUNTER 不存在於 SCOUNTER 的資料，會被拒絕嗎？
    要點：不會。外來鍵只在畫面輸入與 F4 時檢查，程式寫入要自己驗證。
  8. Value Table：Domain 設了 Value Table，畫面欄位就有檢查與 F4 了嗎？SBOOK-AGENCYNUM 的系統建議為什麼是錯的？
    要點：沒有，Value Table 只用來提出外來鍵建議，必須另定義外來鍵；建議的 SBUSPART 包含所有業務夥伴，但此欄只能是旅行社，正確檢查表是 STRAVELAG。
  9. Text Table：SMEALT 與 SMEAL 的外來鍵方向與欄位型態？一張表能有幾張文字表？
    要點：從 SMEALT 指向 SMEAL，型態選 Key fields of a text table；最多一張。
  10. 表格轉換：依序說出轉換七步驟中 QCMTAB 與 QCM8TAB 各在哪一步出現、何時消失；轉換在第 4 步中止時，SE14 能不能按 Unlock table？
    要點：步驟 2 原表改名 QCMTAB；步驟 3 建空的 QCM8TAB；步驟 4 以 MOVE-CORRESPONDING 搬資料（每 16 MB Commit）；步驟 5 刪 QCMTAB（有重複則保留）；步驟 6 QCM8TAB 改回原名、重建索引與 View；步驟 7 解鎖。第 3、4 步中止時資料只在暫存表，絕不能按 Unlock table，要修正原因後按 Continue adjustment。
  11. 縮短主鍵：把 Z 表主鍵移除一個欄位前要做什麼？
    要點：用 GROUP BY 新鍵＋HAVING COUNT(*) > 1 找出重複；有重複就先清理，否則每組只會留下不可預測的一筆。排在維護時段、QAS 先以正式資料量演練。
  12. Append：哪些表不能加 Append Structure？Append 欄位的命名規則？加 Append 需要表格轉換嗎？
    要點：Pool／Cluster 表、含 LCHR／LRAW 長欄位的表不行；欄位以 YY／ZZ 開頭；不需轉換，只 ALTER TABLE；升級不需 SPDD。
  13. View：Database View、Maintenance View、Help View 分別是 Inner 還是 Outer Join？哪一種可以直接輸入連接條件？哪一種可以當 Search Help 的選擇方法？
    要點：Database View＝Inner，可直接輸入連接條件；Maintenance View／Help View＝Outer，連接條件只能來自外來鍵；Database View、Help View 可當選擇方法，Maintenance View 不行。
  14. View Cluster：什麼時候需要 View Cluster 而不是 Maintenance View？最多幾個維護對話？用哪個 TCODE 維護？
    要點：N:M 或多層 Master–Detail、需要跨對話一致刪除／傳輸時；最多 14 個；SM34。
  15. Search Help 附加：列出附加到字典的三種方式，以及 F4 機制的優先順序前三名。
    要點：欄位直接附加、檢查表、Data Element；優先順序：POV → 畫面欄位 Search Help → 流程邏輯輸入檢查（再往下才是字典欄位、檢查表、固定值、Data Element、日曆）。
  16. Search Help 參數：搜尋欄位要設成 IMPORT 還是 EXPORT？
    要點：必須 EXPORT（傳回值），也應該 IMPORT（利用已輸入的搜尋樣式）。强晟筆記寫「輸入參數」不完整。
  17. 增強標準 F4：要在物料 F4（MAT1）加一個「依舊料號」分頁、並隱藏一個用不到的分頁，而且不修改標準，怎麼做？
    要點：建 Z 開頭的 Append Search Help 掛到 MAT1，包含自建的 Elementary（選擇方法 MARA，參數含 BISMT、MATNR），並把要隱藏的 Elementary 也包含進來、勾 Hidden。
  18. Search Help Exit：Exit 在什麼時候被呼叫？在 SELECT 步驟自己取資料後要做哪兩件事？
    要點：F4 每個步驟之前；用 F4UT_RESULTS_MAP 把結果對應到 RECORD_TAB，並把 CALLCONTROL-STEP 設為 'DISP'。
  19. S/4HANA 綜合題：一支 R/3 時代的程式讀 BSEG、KONV，用 SE11 Database View 取資料、用 Type Group 定義常數。搬到 S/4HANA 時各該怎麼處理？
    要點：BSEG 已是透明表，財務明細優先讀 ACDOCA 或標準 CDS；KONV 改讀 PRCD_ELEMENTS；Database View 改 CDS View（1809 用 DDIC-based，7.55+ 用 View Entity）；Type Group 改類別常數；所有「取第一筆」補 ORDER BY。
