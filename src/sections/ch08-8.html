2. 共同骨架與選型：Proxy（SPROXY）vs CL_HTTP_CLIENT 直連

原程式通病：例外後用 MESSAGE ID sy-msgid TYPE sy-msgty … 取訊息。CX_AI_SYSTEM_FAULT 是類別型例外，不會填 sy-msgid／sy-msgno；那行只會丟出上一個殘留訊息或空白訊息（sy-msgty 為空時甚至直接 DUMP）。正確做法是讀例外物件的 get_text( )，或 CX_AI_SYSTEM_FAULT 的公開屬性 CODE、ERRORTEXT。ZSDU005、ZSDU011、ZFIU006 都有這個錯。
同步與非同步的 COMMIT WORK：非同步（Outbound Asynchronous）介面在呼叫方法時只是把訊息放進本地佇列，要等 COMMIT WORK 才真正送出，而且「呼叫成功」只代表進了佇列，不代表對方收到——要看 SXMB_MONI。ZSDU011 的 SI_TRANSACTION_ALL_SYNC_OUT 只有 output、沒有 input，極可能是非同步介面，因此它在 ALV 上顯示的「發送成功！」其實只是「已排入 PI 佇列」。同步介面則不需要 COMMIT WORK；原程式在同步呼叫後照樣 COMMIT，會順帶提交同一 LUW 內其他尚未提交的更新，要小心。

7. ZSDU011：增量水位線、刪除同步與「發送後才推進水位」

這支程式最值得學的是增量抽取的設計，最值得警惕的也是它的實作錯誤。原程式背景模式的 CDHDR 條件如下（用文字描述）：

  • 上次執行是今天：（UDATE＝上次日 且 UTIME ≥ 上次時）且（UDATE＝今天 且 UTIME ≤ 現在）——正確。
  • 上次執行不是今天：（UDATE＝上次日 且 UTIME 介於上次時～23:59:59）或（UDATE＝今天 且 UTIME ≤ 00:00:00 且 UTIME ≤ 現在）——錯。第二段應是 UTIME ≥ 00:00:00，寫成 ≤ 之後，今天午夜之後到現在的變更全部漏抓；而對應 LIKP 的那段（lv_sql1）卻寫對了，兩段邏輯不一致。
  • 若背景作業停過一天以上（例如系統維護），中間那幾天完全不在任何條件內。
  • 水位線在取數時就更新並 COMMIT，此時資料還沒送出；若之後發送失敗，下一次執行會從新水位開始，失敗的那批再也不會自動重送。
  • 時間窗兩端都用 ≥／≤，邊界那一秒的變更會被抓兩次——下游必須能處理重複（冪等，第 16 節）。

10. OAuth token 取得與快取（通用元件）

ZMMU024 每次執行都先呼叫 SI_TOKEN_OUT 取一次 token，這在一天跑幾次的批次沒問題；但若把同樣寫法放進「每張單據觸發一次」的增強點（例如交貨單過帳時即時回寫），就會對 token 端點造成大量請求，常見後果是被對方限流或封鎖。正確做法是取一次、在有效期內重用、快到期才更新。

SAP 標準提供 OAuth 2.0 用戶端：OA2C_CONFIG 建立 OAuth 2.0 Client（Client ID／Secret 存在系統安全儲存），程式用 CL_OAUTH2_CLIENT 取得並把 token 附到 HTTP 請求上；token 的保存與更新由框架負責。能用標準就用標準。以下是對方不是標準 OAuth（例如自訂的 app_key＋app_security 換 token）時的自製快取寫法：

*&-------------------------------------------------------------*
*& Token 快取：Singleton + 到期前 60 秒更新
*&  金鑰由 SM59 目的地的 Basic 認證帶入，程式裡看不到任何密鑰
*&-------------------------------------------------------------*
CLASS zcl_if_token_provider DEFINITION PUBLIC FINAL CREATE PRIVATE.
  PUBLIC SECTION.
    CLASS-METHODS get_instance
      IMPORTING iv_dest           TYPE rfcdest
      RETURNING VALUE(ro_instance) TYPE REF TO zcl_if_token_provider.
    METHODS get_token
      RETURNING VALUE(rv_token) TYPE string
      RAISING   zcx_if_error.
  PRIVATE SECTION.
    TYPES: BEGIN OF ty_token_resp,
             access_token TYPE string,
             token_type   TYPE string,
             expires_in   TYPE i,
           END OF ty_token_resp.
    CLASS-DATA go_instance TYPE REF TO zcl_if_token_provider.
    DATA mv_dest       TYPE rfcdest.
    DATA mv_token      TYPE string.
    DATA mv_expires_at TYPE timestamp.
    METHODS fetch RAISING zcx_if_error.
ENDCLASS.

CLASS zcl_if_token_provider IMPLEMENTATION.
  METHOD get_instance.
    IF go_instance IS NOT BOUND OR go_instance->mv_dest <> iv_dest.
      go_instance = NEW #( ).
      go_instance->mv_dest = iv_dest.
    ENDIF.
    ro_instance = go_instance.
  ENDMETHOD.

  METHOD get_token.
    GET TIME STAMP FIELD DATA(lv_now).
    IF mv_token IS INITIAL
       OR cl_abap_tstmp=>add( tstmp = lv_now secs = 60 ) >= mv_expires_at.
      fetch( ).
    ENDIF.
    rv_token = mv_token.
  ENDMETHOD.

  METHOD fetch.
    DATA lo_http TYPE REF TO if_http_client.
    cl_http_client=>create_by_destination(
      EXPORTING  destination = mv_dest            "例：Z_EXPENSE_TOKEN（型別 G，Basic＝client id/secret）
      IMPORTING  client      = lo_http
      EXCEPTIONS OTHERS      = 1 ).
    IF sy-subrc <> 0.
      RAISE EXCEPTION NEW zcx_if_error( textid = zcx_if_error=>destination_error ).
    ENDIF.

    lo_http->propertytype_logon_popup = if_http_client=>co_disabled.
    lo_http->request->set_method( if_http_request=>co_request_method_post ).
    cl_http_utility=>set_request_uri( request = lo_http->request uri = '/oauth/token' ).
    lo_http->request->set_content_type( 'application/x-www-form-urlencoded' ).
    lo_http->request->set_cdata( `grant_type=client_credentials` ).

    lo_http->send( EXCEPTIONS OTHERS = 1 ).
    IF sy-subrc = 0.
      lo_http->receive( EXCEPTIONS OTHERS = 1 ).
    ENDIF.
    IF sy-subrc <> 0.
      lo_http->close( ).
      RAISE EXCEPTION NEW zcx_if_error( textid = zcx_if_error=>communication_error ).
    ENDIF.

    lo_http->response->get_status( IMPORTING code = DATA(lv_code) ).
    DATA(lv_json) = lo_http->response->get_cdata( ).
    lo_http->close( ).
    IF lv_code <> 200.
      RAISE EXCEPTION NEW zcx_if_error( textid = zcx_if_error=>http_error ).   "不要把回應內文寫進日誌：可能含敏感資訊
    ENDIF.

    DATA ls_resp TYPE ty_token_resp.
    /ui2/cl_json=>deserialize( EXPORTING json        = lv_json
                                         pretty_name = /ui2/cl_json=>pretty_mode-low_case
                               CHANGING  data        = ls_resp ).
    GET TIME STAMP FIELD DATA(lv_now).
    mv_token      = ls_resp-access_token.
    mv_expires_at = cl_abap_tstmp=>add( tstmp = lv_now secs = ls_resp-expires_in ).
  ENDMETHOD.
ENDCLASS.
快取的生命週期：CLASS-DATA 只活在同一個內部 Session（同一次程式執行、同一個背景作業步驟）。這對批次已經足夠——ZMMU024 一次執行只要取一次 token。若要跨使用者、跨作業共用，可用 Shared Objects（SHMA）；不建議把 token 寫進資料庫表，那等於多一份需要保護的憑證。Singleton 模式的更多討論見 7-5 章。pretty_mode-low_case 讓 ABAP 欄位 ACCESS_TOKEN 對映 JSON 的 access_token；若對方用 camelCase（accessToken）則改用 pretty_mode-camel_case。

*& 重送作業：每 15 分鐘由 SM37 排程；指數退避 + 上限 + BAL 日誌
*&-------------------------------------------------------------*
CONSTANTS c_max_retry TYPE i VALUE 5.

GET TIME STAMP FIELD DATA(lv_now).
SELECT msg_guid, if_id, obj_key, retry_cnt
  FROM zif_msg_log
  WHERE status        = 'R'
    AND next_retry_at <= @lv_now
    AND retry_cnt     <  @c_max_retry
  ORDER BY created_at                             "先進先送，順序要明確
  INTO TABLE @DATA(lt_retry)
  UP TO 500 ROWS.

DATA lv_log_handle TYPE balloghndl.
DATA(ls_bal) = VALUE bal_s_log( object    = 'ZIF'              "SLG0 建立的物件／子物件
                                subobject = 'RETRY'
                                extnumber = |{ sy-datum }{ sy-uzeit }|
                                aluser    = sy-uname
                                alprog    = sy-repid ).
CALL FUNCTION 'BAL_LOG_CREATE'          "CALL FUNCTION 的實參請用資料物件，不要放建構運算式
  EXPORTING  i_s_log      = ls_bal
  IMPORTING  e_log_handle = lv_log_handle
  EXCEPTIONS OTHERS       = 1.

LOOP AT lt_retry INTO DATA(ls_r).
  DATA(lv_result) = zcl_if_dispatcher=>resend( ls_r-msg_guid ).     "回傳 S / E / R
  DATA(lv_cnt)    = ls_r-retry_cnt + 1.
  " 指數退避：2、4、8、16… 分鐘
  DATA(lv_wait)   = CONV i( 60 * 2 ** lv_cnt ).
  DATA(lv_next)   = cl_abap_tstmp=>add( tstmp = lv_now secs = lv_wait ).
  DATA(lv_status) = COND char1( WHEN lv_result = 'R' AND lv_cnt >= c_max_retry THEN 'X'
                                ELSE lv_result ).
  UPDATE zif_msg_log SET status        = @lv_status,
                         retry_cnt     = @lv_cnt,
                         next_retry_at = @lv_next,
                         sent_at       = @lv_now
    WHERE msg_guid = @ls_r-msg_guid.

  IF lv_status = 'X'.
    DATA lv_text TYPE c LENGTH 200.
    lv_text = |{ ls_r-if_id } { ls_r-obj_key } 重送 { lv_cnt } 次仍失敗，已停止重送|.
    CALL FUNCTION 'BAL_LOG_MSG_ADD_FREE_TEXT'
      EXPORTING  i_log_handle = lv_log_handle
                 i_msgty      = 'E'
                 i_text       = lv_text
      EXCEPTIONS OTHERS       = 1.
  ENDIF.
  COMMIT WORK.                                   "逐筆提交：中途 DUMP 不影響已處理者
ENDLOOP.

DATA(lt_handles) = VALUE bal_t_logh( ( lv_log_handle ) ).
CALL FUNCTION 'BAL_DB_SAVE'
  EXPORTING  i_t_log_handle = lt_handles
  EXCEPTIONS OTHERS         = 1.
COMMIT WORK.
重送的三條規則：① 只重送「可能自己會好」的錯（通訊失敗、逾時、HTTP 429/5xx），資料錯（HTTP 4xx、BAPI E 訊息）重送一百次也一樣錯，要轉人工；② 有上限，超過就停並告警（原 ZSDU028 會無限重送）；③ 重送用同一個訊息 GUID。若公司已有 AIF（見 5-22 章與 5-24 第 12 節），把這些規則交給 AIF 的錯誤處理與重處理，比自己寫更好維護。背景作業排程與工作日誌見 4-4 章。

16. 冪等性（Idempotency）：重送一百次，結果都一樣

介面「至少送一次」很容易做到，「剛好一次」很難；實務上的解法是允許重送，但讓重複的訊息不產生重複的效果。本章各程式在這方面的表現：

程式重複執行會怎樣冪等手段（現況 → 建議）
ZSDU005 重新訂閱對方同一單號重複訂閱，多半覆蓋舊訂閱對方天然冪等（以單號為鍵）；保留即可，但要限制頻率
ZSDU028 軌跡回推同一 UUID 可能多次送達下游已帶 PUID（UUID）→ 要求下游以 PUID 去重
ZSDU011 交貨單同步時間窗邊界、手工重送都會重複下游應以「交貨單＋行」做 upsert；另帶訊息 GUID
ZSDU019 U 訂貨發貨可能重複入庫（平台端若以新增處理）無日誌 → 加日誌表；請平台以交貨單號去重，或送 Idempotency-Key
ZMMU024 收款人同步新增若重送，對方會出現兩個收款人以 ZMMT021 的 ID 判斷新增或更新 ✓；但新增成功、寫日誌前失敗的空窗仍會重複 → 新增前先以供應商編號查詢對方
ZFIU006 PayPal 查詢查詢本身無副作用狀態轉換加條件 WHERE zstatus = 'S'（第 11 節）
ZSDU030 換貨訂單可能重複建單ZSDT030 以交貨行為鍵 ✓ → 加鎖、與 BAPI 同一 LUW 提交（第 13 節）

Outbox 模式：在業務交易（例如交貨單過帳的增強點）中只寫一筆「待送」紀錄，由背景作業負責真正發送。好處是 SAP 交易不會因為外部系統慢或掛掉而卡住，也不會出現「SAP 回滾了、外部卻已收到」的不一致。這正是 tRFC／qRFC／bgRFC 與非同步 Proxy 的原理（見 4-1 第 3 節）；在增強點裡直接同步呼叫外部 HTTP，是最常見的反模式。

  1. 找錯：ZSDU019 背景作業排了三個月，對方說從沒收到任何資料，工作日誌也全部「已完成」。請指出原因並寫出修正。

  2. 找錯：ZSDU005 上線後客服反映「A 客戶收到 B 客戶包裹的物流簡訊」。可能的程式原因？
    參考答案：迴圈內 READ TABLE INTO 工作區讀不到時不清空，ls_zwmt011 殘留上一張交貨單的收件人電話，接著被填進本張的 PHONE 參數。每圈開頭 CLEAR，或改一次 JOIN 取回。

    參考答案：半開區間 [上次水位, 現在－安全邊界)：( udate > 起日 OR ( udate = 起日 AND utime >= 起時 ) ) AND ( udate < 迄日 OR ( udate = 迄日 AND utime < 迄時 ) )；水位只在資料成功送出（或已落地到可重送的日誌表）後才更新。
  4. 觀念：CX_AI_SYSTEM_FAULT 被 CATCH 後，用 MESSAGE ID sy-msgid TYPE sy-msgty NUMBER sy-msgno … 取錯誤訊息，有什麼問題？
    參考答案：類別型例外不填 sy-msg* 系統欄位，得到的是殘值或空白（sy-msgty 空白時可能 DUMP）。應用 lx->get_text( ) 或 CODE／ERRORTEXT 屬性。
  5. 觀念：非同步 Outbound Proxy 呼叫方法後沒有例外，是否代表對方已收到？
    參考答案：否。只代表訊息進了本地佇列，且要 COMMIT WORK 才會送出；是否送達要看 SXMB_MONI／PI 監控。
  6. 資安：ZMMU024 以 IF sy-mandt = … 切換正式／測試金鑰。請提出至少三項改善。
    參考答案：① 金鑰移到 SM59 目的地（或 OA2C_CONFIG／PI Channel），各系統各自設定、不隨傳輸；② 舊金鑰到對方平台作廢重發；③ token 只放記憶體並快取到期前重用，不放進會寫入日誌的結構；④ 回應內文不整段寫日誌。
  7. 找錯：ZSDU030 連續建立兩張換貨訂單後，第二張的價格明顯不對。原因？
    參考答案：每張訂單開始時沒有 REFRESH lt_conditions，第二張帶著第一張的條件行（行號 10、20…對到錯的品項）。改為迴圈內宣告／清空全部 BAPI 內表。
  8. Casper 經驗：退換貨平台依交貨行「依序扣減」本月換貨額度。為什麼同一份資料在 HANA 上每次跑出的分配可能不同？怎麼修？
    參考答案：HANA 沒有預設排序，SELECT 未 ORDER BY 時回傳順序不固定，依序扣減的結果就會變。扣減前明確 SORT（例如過帳日期、交貨單、行號），或在 SQL 加 ORDER BY。
