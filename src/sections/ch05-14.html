2. 調整 SAP 標準的五個層級與決策流程

原廠把「讓 SAP 符合需求」的手段分成五層（强晟 p7–8；Col18 p13）：

層級做什麼工具升級影響
Customizing（組態）依 IMG 設定業務流程與功能SPRO（IMG）無
Personalization（個人化）不寫程式，調整欄位屬性、預設值、隱藏欄位，建立使用者選單SHD0、PFCG、GuiXT極小
Enhancement（增強）在 SAP 預留（或隱式存在）的位置掛上客戶物件，不改 SAP 物件本身ABAP Workbench通常免調整（新框架可能需 SPAU_ENH）
Modification（修改）直接修改 SAP Repository 物件ABAP Workbench＋Modification Assistant每次升級／Support Package 都要做修改調整
Customer Development（客戶開發）在客戶命名空間（Y*/Z*）新建物件，可呼叫 SAP 物件ABAP Workbench被呼叫的 SAP 物件變了才受影響

後三者都在 ABAP Workbench 完成。增強與客戶開發的角色是反過來的：客戶開發是「你的程式呼叫 SAP」；增強是「SAP 程式呼叫你建立的物件」。增強可以發生在五種位置（强晟 p14；Col18 p18）：

  • ABAP 程式 → Program Exit（函數模組出口、BTE、BAdI 方法、增強點）
  • GUI Status → Menu Exit（功能碼以 + 開頭）
  • 畫面 → Screen Exit（在 SAP 預留的 Subscreen Area 放客戶子畫面）
  • 畫面欄位 → Field Exit（已屬遺留技術，見 §21）
  • ABAP Dictionary 表格／結構 → Table Enhancement（Append、CI Include）

決策流程（强晟 p9–10；Col18 p14）：Customizing／個人化能滿足嗎？→ 不能 → SAP 標準有沒有類似功能？→ 沒有就走客戶開發，或購買 SAP 認證的 CSP（Complementary Software Program）；有 → 增強能滿足嗎？→ 能就增強，不能才考慮修改或「把 SAP 物件複製到客戶命名空間再改」。修改只在以下三個條件同時成立時才做：①Customizing／個人化無法滿足；②找不到合適的增強；③無法把 SAP 物件複製到客戶命名空間。

不論哪一代，Menu Exit 與 Screen Exit 都只能有一個有效實作（兩個實作要顯示哪個選單、哪個子畫面會衝突）；只有 Program Exit 在 BTE/BAdI 技術下才可能有多個有效實作、執行時依序呼叫。
Casper 的實務原則：先找標準，再想客製。標準設定 → BAdI／Enhancement Spot → Enhancement Point → 修改標準，每往右一步，升級成本高一個量級。本課程的整個結構，其實就是在教你「往右走之前，先把左邊每一格都確認過」。

3. 個人化：交易變式 SHD0、畫面變式、變式交易與 GuiXT

終端使用者通常只用到交易的一小部分功能。個人化不需要開發就能簡化交易（强晟 p23–35；Col18 p33–42）。手段包括：交易變式、SET/GET 參數、依使用者或用戶端（client）儲存的 Table Control 設定、角色選單、我的最愛、桌面捷徑。

區域選單（Area Menu）角色選單（Role-Based Menu）
維護交易SE43PFCG
權限不含權限維護含權限維護（角色同時產生權限設定檔）
指派方式選單指派給使用者（例如當起始選單）角色指派給使用者；4.6A 起登入後以樹狀出現在 SAP Easy Access

交易變式（Transaction Variant）能做的事：

  • 預先填入畫面欄位值（使用者仍可覆寫）；
  • 移除不需輸入欄位的「可輸入」狀態；
  • 隱藏不需要的畫面元素（欄位、按鈕、Table Control 欄）；
  • 整個畫面略過不顯示；
  • 以錄製方式（WYSIWYG）維護。
Col18 的測驗題特別考「交易變式不能做什麼」：它不能覆寫錯誤訊息。能做的是預填值、隱藏元素、隱藏整個畫面、取消可輸入狀態（隱藏選單功能是透過隱藏功能碼達成）。

兩種用法（强晟 p26；Col18 p36）：

  1. 變式交易（Variant Transaction）：建立一個新 TCODE＝SAP 交易＋變式，使用者要執行這個新交易碼才會套用。要放進使用者選單或 PFCG 角色，也必須建這種交易碼（SHD0 選單 Goto → Create Variant Transaction，或 SE93 建立時選「Variant Transaction」類型）。
  2. 標準變式（Standard Variant）：把變式「掛」在原交易上，執行原 TCODE 就自動套用。每個 SAP 交易只能有一個標準變式。

畫面變式（Screen Variant）：交易變式是一組畫面變式的參照；一個畫面可以有任意多個畫面變式。畫面變式是獨立的 Repository 物件，名稱由「變式名＋用戶端（僅 client 相依時）＋畫面號碼」組成。

建立步驟（依講義步驟整理）：SHD0 → 輸入 SAP 交易碼與新變式名稱（系統內唯一、客戶命名空間）→ 需要 client 相依或跨 client 時從 Goto 選單切換 → 按建立，系統以「呼叫模式」啟動交易 → 每個畫面觸發 PAI 後跳出對話框，勾選要帶入的欄位值、「隱藏」「不可輸入」「必填」等屬性 → 按 Continue 存成畫面變式 → 全部完成後存檔。測試：在 SHD0 輸入交易碼與變式名按 F8。

GuiXT：以腳本語言重新排版畫面——移動物件、插入圖片、插入按鈕、插入值說明（F4）、改欄位輸入屬性、刪除畫面元素；腳本可從本機匯入／匯出。完整文件隨 GuiXT 安裝提供，供應商為 Synactive。

另一個常被忽略的個人化工具是 SET/GET 參數（Parameter ID）：欄位在 Screen Painter 勾了 SET/GET 後，系統會記住使用者上次輸入的值；使用者也可在「系統 → 使用者設定檔 → 自己的資料 → 參數」固定預設值。程式裡則常用它帶參數跳到標準交易：

*& 用 SET/GET 參數把採購單號帶進 ME23N，並略過第一個畫面
*&---------------------------------------------------------------*

START-OF-SELECTION.
  " 先確認單據存在（明列欄位、主機變數加 @）
  SELECT SINGLE ebeln, bukrs, lifnr

  TRY.
      CALL TRANSACTION 'ME23N' WITH AUTHORITY-CHECK AND SKIP FIRST SCREEN.
    CATCH cx_sy_authorization_error INTO DATA(lx_auth).

4. 資料字典增強（一）：Append Structure 與 Customizing Include

兩種技術都能「不修改表格本身」替 SAP 表格／結構加欄位（强晟 p37–42；Col18 p48–51）。字典基礎請見 1-2 章 與 BC430（5-16 章）。

比較Append StructureCustomizing Include（CI Include）
是否需 SAP 預先規劃不需要，客戶隨時可建需要：SAP 已在表格中寫好 .INCLUDE CI_xxx
參照方向Append 指向它所屬的表格；表格本身不變表格以 .INCLUDE 行參照子結構
對應關係一個 Append 只屬於一個表格；一個表格可有多個 Append同一個 CI Include 可出現在多個表格／結構，確保一致
命名Append 名稱在客戶命名空間；欄位以 ZZ 或 YY 開頭名稱一律 CI_ 開頭；欄位同樣 ZZ/YY 開頭
SAP 未實作時—CI Include 不存在也不會出錯（SAP 標準不交付其內容）
建立方式SE11 表格 → Append Structure特定 Customizing 交易，或透過 CMOD 增強專案的元件建立
常見搭配Screen Exit 顯示新欄位常與 Program Exit／Screen Exit 成套（例如採購單 CI_EKKODB 搭配 MM06E005）

運作與升級：表格啟用時，系統會搜尋該表所有已啟用的 Append 並附加上去；Append 建立或修改後啟用，所屬表格也會跟著啟用。複製一個有 Append 的表格時，Append 欄位會變成新表的一般欄位。因為 ABAP Dictionary 的欄位順序可以與資料庫不同（3.0 起），加 Append 或在既有 Append 插欄位不需要表格轉換，只要 ALTER TABLE 調整資料庫目錄。升級時新版標準表載入後第一次啟用，Append 欄位就自動接回去。

使用限制：

  • Enhancement Category（Col18 正式寫進投影片；L29 Col92 2010 版的 Append 練習已要求啟用前選 Extras → Enhancement Category）：表格／結構被分類為「未分類／不可增強／可增強（字元型）／可增強（字元或數值型，不可含 deep 型別）／可任意增強」。Append 與 CI Include 的欄位型別必須符合此分類，否則 Unicode 檢查會報錯。
  • 不能對 Pool Table 或 Cluster Table 建 Append（强晟 p40）。Col18 p51 補充：唯一例外是 BSEG。
  • 表格含 LCHR／LRAW 長欄位時不能加 Append（長欄位必須是最後一欄）。
  • CI Include 加欄位的規則與 Append 相同，所以同樣不能用在 Pool／Cluster 表。

5. 資料字典增強（二）：文字增強、Append Search Help、Extension Index、Fixed Value Append

5.1 文字增強（Text Enhancement）

客戶可以覆寫 SAP 資料元素的欄位標籤（短／中／長／表頭）與 F1 說明文件。它是全域增強：所有使用該資料元素的應用都會變（强晟 p43–48；Col18 p53–59）。

前提：只能覆寫畫面設計者沒有自己寫死文字的欄位。畫面欄位的屬性「Dict. Modified（字典已修改）」決定取哪個標籤：

值意義
SPACE取最適合欄位長度的標籤
1 / 2 / 3 / 4短／中／長／表頭標籤
V從字典變動傳輸文字（同 SPACE）
F固定，不從字典傳文字——這種欄位客戶標籤不會生效
  • 升級後要「還原客戶欄位標籤」：SAP 在升級或 Note 中重新交付標籤時會蓋掉你的文字，SAP 建議每次版本升級後都執行一次還原。
  • 撤銷修改用「Restore SAP Version」：由背景程式檢查所有改過的資料元素並還原；Col18 特別註明只能全部還原，不能只還原單一資料元素。
  • BUKRS、MANDT 這類核心資料元素，請在使用它們的表格內容沒有被異動的時段做編輯與還原，否則資料元素啟用可能失敗、只部分啟用。
  • 客戶說明文件：CMOD → Goto → Global Enhancements → Data Elements → 新增客戶文件。選「Original Text」是在 SAP 文件後加註（F1 同時顯示兩者）；選「Template」是另寫一份不含 SAP 文字的文件。刪掉自己的文件即恢復 SAP 原文。

5.2 Append Search Help（4.6 起）

Append Search Help 是一個「掛在另一個 Collective Search Help 上」的 Collective Search Help，沿用被附加物件的介面，用它所含的 Elementary Search Help 來擴充標準 F4，而不必修改。它也能用來隱藏不需要的標準 Elementary Search Help：把該 Search Help 納入 Append 並勾選「Hidden」。客戶增強一律另建自己的 Append Search Help，不要改 SAP 已存在的 Append。

步驟：SE11 → 顯示 Collective Search Help → Goto → Append Search Helps → Create Append → 輸入客戶命名空間名稱 → 如同建立一般 Collective Search Help 繼續維護。

5.3 Extension Index（NW 7.0 起）

在 SAP 表格上建一般次索引（即使名稱在客戶命名空間）也算修改；NW 7.0 起可以建立 Extension Index，屬免修改增強，升級時自動帶過去、不需修改調整。

5.4 Fixed Value Append（NW 7.0 起）

替 SAP 標準 Domain 加固定值而不修改。一個 Fixed Value Append 只能屬於一個 Domain；一個 Domain 可以有多個 Fixed Value Append。步驟：SE11 輸入 Domain → Display → Goto → Fixed Value Append → 輸入客戶命名空間名稱（已有者會列出可選）→ 短描述 → Value Range 頁籤輸入新值（Show Domain Values 可看原值）→ 存檔啟用。它在 Repository 裡本身也是一個 Domain 物件，搜尋 Domain 時會一起出現，別和 Append Structure 搞混。

6. Customer Exit（一）：SMOD／CMOD 與增強專案

Customer Exit 是 SAP 預先規劃好、交付時為未啟用的應用增強，通常由數個元件組成（强晟 p51–59；Col18 p75–82）。特徵：

  • 每個增強提供一組預先規劃、精確定義的功能；SAP 與客戶功能之間的介面清楚定義；
  • 客戶不需要深入了解 SAP 應用的實作；
  • SAP 在升級中開發新功能時，客戶的增強不需要調整。

兩個交易、兩層物件：

SAP 增強（SAP Enhancement）客戶增強專案（Enhancement Project）
誰建SAP 應用開發者客戶
交易SMOD（查看、看文件、看範例程式碼）CMOD（Project Management）
組成元件：Program Exit（函數出口）、Menu Exit、Screen Exit、（CI Include）SAP 增強
唯一性一個元件只能屬於一個 SAP 增強一個 SAP 增強只能放進一個客戶專案

SAP 端流程：規劃可能的增強並定義元件 → 把元件組成 SAP 增強 → 撰寫文件，讓客戶不必分析原始碼就能實作。（强晟在 p54 吐槽：「SAP 在給自己吹牛，其實增強的文件相當少，並不容易使用。」——實務上確實常要看原始碼。）

客戶端流程：

  1. CMOD 建立專案並命名。SAP 建議訂命名規則，例如名稱含被增強的交易或模組池；專案名稱在系統中唯一。
  2. Attributes 輸入短文字（狀態、建立人、時間戳由系統填）。
  3. Enhancement Assignment 輸入要用的 SAP 增強（可用搜尋功能看目錄）。
  4. Components：依元件類型分別進 Function Builder（函數出口）、對話框（選單文字）、Screen Painter（子畫面）。
  5. 替整個專案寫文件。
  6. 啟用專案：所有元件一起啟用；含元件的程式、畫面、選單會重新產生（Col18 補充：實際上是在執行時才重新產生）。「Deactivate」可把專案改回未啟用，效果不如預期時很好用。
  7. 傳輸：專案建立時就指派變更請求，所有相關物件（程式、子畫面、選單出口⋯）放進同一張請求，才能整包一起傳輸。

找出口的方法（强晟 p64–65；Col18 p86）：①執行交易 → 系統 → 狀態 → 雙擊程式名 → 全域搜尋字串 CALL CUSTOMER；②找不到就擴大範圍，用環境分析（Environment Analysis）在整個程式環境中搜尋；③Repository Information System（SE80/SE84）→ Enhancements → Customer Exits → Enhancements，按「所有選項」（Shift+F9），元件名輸入 EXIT_<程式名>*；④以套件（Package）、技術名稱、描述限定；⑤應用階層 SE81、IMG SPRO。更多方法與工具程式見 3-3 章 §9～§10。以下是用管理表直接查的精簡版：

*&---------------------------------------------------------------*
*& 依程式名找出 Customer Exit，並顯示是否已放進 CMOD 專案、專案是否啟用
*& MODSAP ：SAP 增強的元件（TYP：E=函數出口 S=畫面 C=選單 T=表格）
*& MODACT ：客戶專案包含哪些 SAP 增強
*& MODATTR：客戶專案屬性（STATUS：A=已啟用）
*& TFDIR  ：函數模組 → 所屬主程式（找出口所在的 X 函數群）
*&---------------------------------------------------------------*
PARAMETERS p_prog TYPE progname DEFAULT 'SAPMM06E'.

START-OF-SELECTION.
  DATA(lv_pattern) = |EXIT_{ p_prog }_%|.

  SELECT s~name   AS enhancement,
         s~member AS exit_fm,
         f~pname  AS exit_fugr,
         a~name   AS project,
         t~status AS project_status
    FROM modsap AS s
    INNER JOIN tfdir AS f
      ON f~funcname = s~member
    LEFT OUTER JOIN modact AS a
      ON a~member = s~name
    LEFT OUTER JOIN modattr AS t
      ON t~name = a~name
    WHERE s~typ    = 'E'
      AND s~member LIKE @lv_pattern
    ORDER BY s~name, s~member             " 固定排序，輸出才穩定
    INTO TABLE @DATA(lt_exit).

  IF lt_exit IS INITIAL.
    MESSAGE |程式 { p_prog } 沒有第二代函數出口，改找 BAdI／增強點| TYPE 'S'.
    RETURN.
  ENDIF.

  TRY.
      cl_salv_table=>factory( IMPORTING r_salv_table = DATA(lo_alv)
                              CHANGING  t_table      = lt_exit ).
      lo_alv->get_functions( )->set_all( abap_true ).
      lo_alv->display( ).
    CATCH cx_salv_msg INTO DATA(lx_salv).
      MESSAGE lx_salv->get_text( ) TYPE 'E'.
  ENDTRY.

7. Customer Exit（二）：Program Exit 與 X 函數群的結構

SAP 開發者決定出口在程式中的位置與傳遞哪些資料，並建立出口函數模組（含短文字、介面、文件）。客戶只負責在函數模組裡寫程式；需要畫面、文字元素、額外 INCLUDE 時，也必須建在同一個函數群。程式啟用了還不夠，必須把 CMOD 專案啟用，出口才會被執行（强晟 p60–74；Col18 p83–95）。

  • SAP 端呼叫語法：CALL CUSTOMER-FUNCTION 'nnn'（三位數字）。
  • 函數模組命名：EXIT_<呼叫程式名>_<nnn>，例如 EXIT_SAPMM06E_012。
  • 出口函數模組一律屬於名稱以 X 開頭的函數群（X 函數群，主程式 SAPLX…）。
  • CALL CUSTOMER-FUNCTION 只在專案啟用後才執行；同一個出口函數被呼叫多次時，啟用對所有呼叫點都有效。

X 函數群的 INCLUDE 規則（以 aaa 代表函數群代號）：

INCLUDE內容誰可以改
LXaaaTOPSAP 全域資料＋FUNCTION-POOL 陳述式（L29 Col92 版補充：更精確地說，LXaaaTOP 只放 FUNCTION-POOL 與 INCLUDE LXaaaTAP.、INCLUDE ZXaaaTOP. 兩行；SAP 的全域資料放在 LXaaaTAP，客戶的放在 ZXaaaTOP）SAP（不可改）
LXaaaUXX依序 INCLUDE 各函數模組的 LXaaaUnnSAP
LXaaaUnn出口函數模組本體，裡面有一行 INCLUDE ZXaaaUnnSAP（不要改函數模組與介面）
LXaaaFnnSAP 建議的範例程式碼（SMOD 的 Sample Code 按鈕）SAP；可複製到 ZXaaaUnn
LXaaaF01 / E01 / O01 / I01SAP 交付的子程序／事件區塊／PBO 模組／PAI 模組SAP
ZXaaaTOP客戶自己的全域資料客戶
ZXaaaUnn客戶程式碼（技術上位於 FUNCTION … ENDFUNCTION 之間）客戶
ZXaaaZZZ客戶額外 INCLUDE 的收納處：ZXaaaFnn（子程序）、ZXaaaOnn（PBO）、ZXaaaInn（PAI）、ZXaaaEnn（事件）客戶

四個必背限制：

  1. X 函數群不能再加函數模組；只能編輯 Z 開頭的 INCLUDE（L 開頭屬 SAP 命名空間）。
  2. ZXaaaUnn 位於 FUNCTION…ENDFUNCTION 之內，所以不能寫事件區塊、FORM、MODULE；在這裡用 DATA 宣告的變數只在該函數模組內有效。
  3. LXaaaTOP 的 FUNCTION-POOL 陳述式不能改，也就不能加預設訊息類別；發訊息時必須在 MESSAGE 裡寫明訊息類別，例如 MESSAGE e500(eu)。
  4. 自己的畫面用 CALL SCREEN 呼叫，以向前導航建立；畫面屬於 SAPLXaaa，PBO/PAI 模組放在 ZXaaaOnn／ZXaaaInn，再由 ZXaaaZZZ 納入。
强晟 p66 記下的「變態陷阱」：從 CMOD 雙擊 ZX INCLUDE 名稱時，系統提示「Function module is reserved for program include / 程式 INCLUDE 保留」，接著按什麼按鈕都過不去——按一下 Enter 鍵就會進到（並建立）INCLUDE。這個對話框到今天的 SAP GUI 仍然存在。

8. Customer Exit（三）：Menu Exit 與 Screen Exit

8.1 Menu Exit

SAP 開發者在 GUI Status 中預留以加號 + 開頭的功能碼，這些功能碼在出口未啟用前不出現在選單上；同時在程式中提供一個 Program Exit，使用者選到該選單時執行（强晟 p75–77；Col18 p97–100）。客戶在 CMOD 的 Components 雙擊 Menu Exit，於對話框輸入依語言的選單文字（Function text），再實作對應的函數出口。不能對 GUI Status 做任何其他修改。

8.2 一般子畫面的規則（先懂這個）

子畫面是主畫面上保留的矩形區域，執行時在 PBO 決定要放哪個 Subscreen 型畫面：CALL SUBSCREEN <area> INCLUDING <prg> <dynnr>。每個子畫面的 PBO/PAI 都像一般畫面一樣被處理，處理順序依主畫面流程邏輯中 CALL SUBSCREEN 的順序。重要限制（詳見 BC410，5-9 章）：

  • 功能碼只能由主畫面處理；子畫面不能有具名的 OK_CODE 欄位；
  • 子畫面不能定義 GUI Status；
  • 子畫面的流程邏輯不能指定下一個畫面。

8.3 Screen Exit

SAP 開發者在主畫面 PBO 用 CALL CUSTOMER-SUBSCREEN <area> INCLUDING 'SAPLXaaa' <dynnr>：子畫面區名稱不加引號；函數群必須以引號靜態指定；畫面號碼可以用變數，但一律 4 位字元。沒有實作時標準畫面照常顯示、子畫面區留白；建了子畫面並啟用專案後才生效。子畫面建立在 X 函數群中（通常同時含對應的函數出口）（强晟 p78–85；Col18 p101–108）。

資料怎麼傳？X 函數群看不到呼叫程式的全域資料，所以 SAP 會搭配兩個 Program Exit：一個在主畫面 PBO 把資料「送進」X 函數群的全域變數，一個在主畫面 PAI 把子畫面修改後的資料「取回」。若 SAP 沒打算讓子畫面回寫資料，第二個出口可能根本不存在——動手前先確認。

Screen Exit 在 CMOD 中的技術名稱由「呼叫程式＋4 位主畫面號碼＋子畫面區名稱」與「X 函數群主程式＋子畫面號碼」組成。以向前導航（雙擊）建立子畫面時，畫面類型一定要選 Subscreen。

9. Business Transaction Events（BTE）：FIBF 與 Publish & Subscribe

為什麼有 BTE？軟體交付鏈變長了：SAP → 產業事業單位（IBU）→ 合作夥伴的 CSP → 客戶。每一方都可能想用同一個出口，但 Customer Exit 只能實作一次。於是 SAP 從 FI 模組發展出 BTE（4.0 起），讓出口可以重複使用（强晟 p86–101；Col18 p115–127）。

10. Classic BAdI（一）：架構、搜尋、實作與定義

動機（强晟 p103）：早期技術各有缺陷——Customer Exit 只能用一次；BTE 沒有畫面增強、沒有選單增強、（强晟版）沒有管理層。新技術要可重用、涵蓋程式／選單／畫面三種出口、有管理層，並用最新技術（ABAP Objects）實作。BAdI 可以說是集大成：管理層與多種元件學自 Customer Exit，可重用學自 BTE，實作採物件導向（Col18 p167）。

OO 前置觀念（强晟 p104–109；Col18 p133–135；詳見 5-2 章）：介面只定義方法名稱與簽章、沒有實作；由實作類別實作；介面不能實例化（不能對介面型別的參考變數 CREATE OBJECT），但介面參考可以指向任何實作類別的物件，呼叫同一方法時執行各類別自己的程式碼。强晟也用「函數群一次只能有一個實例、類別可以有任意多個實例」說明為何從函數群走向類別。

架構：定義 BAdI 時產生兩個元件：①介面 IF_EX_<BAdI>；②系統產生、實作該介面的 BAdI 類別（Adapter Class）CL_EX_<BAdI>。Adapter 負責兩件事：過濾（只呼叫符合過濾值的實作）與控制（呼叫所有有效實作）。執行流程：①程式呼叫服務類別 CL_EXITHANDLER=>GET_INSTANCE 取得 Adapter 實例（隱含向下轉型，參考變數只能呼叫介面方法）；②呼叫介面方法，Adapter 找出所有有效實作並逐一呼叫。

搜尋 Classic BAdI：①在程式中搜尋字串 CL_EXITHANDLER（一定會呼叫 GET_INSTANCE）；②向前導航：雙擊參考變數 → 雙擊介面 → 介面的 Where-Used 清單 → 找到 CL_EX_<BAdI> → SE18 看定義與文件；③Repository Information System → Enhancements → Business Add-Ins，可用應用階層限定；④IMG 相關節點。實務上最快的是在除錯器對 CL_EXITHANDLER=>GET_INSTANCE 下中斷點（3-4 章 §6、BC403 5-4 章）。

實作（SE19）：7.0 起初始畫面分 New／Classic 兩區，選 Classic BAdI → 輸入 BAdI 名 → Create Impl. → 輸入實作名稱。也可從 SE18 選單 Implementation 看既有實作或新建。雙擊方法進 Class Builder 撰寫；可在實作類別加私有方法以模組化。方法啟用之外，實作本身也要按「啟用」。

  • 停用實作後方法不再被呼叫，但應用程式中的呼叫仍會執行，只是 Adapter 找不到有效實作。這與 CALL CUSTOMER-FUNCTION（專案未啟用就完全不執行）不同。
  • 實作只能在原始系統啟用或停用，再以傳輸帶到後續系統。
  • 非 Multiple Use 的 BAdI 仍可在同系統存在多個實作，但同時只能有一個是啟用的。

定義（SE18；7.0 之後要用選單 Utilities → Create Classic BAdI）：兩個重要屬性——

  • Multiple Use（可重用）：可有多個有效實作，執行順序未定義。
  • Filter-Dependent（過濾相依）：以 DDIC 資料元素（或單欄位結構）當過濾型別，其 Domain 值表即有效過濾值；呼叫方法時必須傳 flt_val，每個介面方法也必須有輸入參數 FLT_VAL。實作可指定多個過濾值，也可用 * 當泛用值。
  • 可擴充過濾型別（Enhanceable）：實作可使用值表中尚不存在的過濾值，存檔時系統自動寫入值表、刪除實作時移除。條件嚴格：Domain 連到跨用戶端值表且只有一個 Key；有兩個 Key（過濾型別＋語言）的文字表、欄位名含 TEXT／TXT；兩表交付類別為 E 或 S。
  • Default Code／Sample Code：定義者可提供預設實作（沒有其他有效實作時執行，Goto → Default Code）與範例實作（Goto → Sample Code，當實作者的範本）。

11. Classic BAdI（二）：Menu Exit 與 Screen Exit

BAdI Menu Exit（强晟 p121–123；Col18 p147–149）：前提是 SAP 已為程式規劃增強，且在一個 BAdI 實作中實作了選單增強。功能碼同樣以 + 開頭；有啟用的 BAdI 實作含該增強時，選單項目才出現；使用者選到時，程式在 CASE ok_code 的 WHEN '+XXX' 分支呼叫 BAdI 方法。方法呼叫與選單增強不可分離，所以兩者必須在同一個 BAdI 中。限制：有選單增強的 BAdI 不可 Multiple Use，也不可 Filter-Dependent。

13. Enhancement Framework 概要（Unit 8～9）：顯式與隱式增強

本節只列 BC425 的觀念地圖與限制，完整操作、Composite 結構、衝突處理請見 BC427（5-15 章）與 3-4 章 §13～§15（强晟 p212–223；Col18 p209–251）。

  • Enhancement Spot 管理顯式增強點、顯式增強段與 New BAdI；Composite Enhancement Spot 可包含 Simple Spot 或其他 Composite Spot，作語意分組。一支程式所有顯式增強的 Spot 通常命名 ES_<SAP 程式名>。顯式增強點／段不能全域搜尋，但可搜尋它們所屬的 Spot（SE84 → Enhancements → Enhancement Spots，或 SPAU_ENH）。

14. 修改（一）：原始與副本、SSCR 註冊與修改守則

原始（Original）與副本（Copy）：一個 Repository 物件只在一個系統是原始的。SAP 交付的物件原始系統在 SAP，客戶系統（包含開發機與其後的所有系統）裡都只是副本；你自己開發的物件，原始系統是你的開發機，放在「Development/Correction」類型的變更請求中傳輸（强晟 p146–149；Col18 p256–258）。傳輸與套件的基礎見 1-1 章。

名詞定義任務類型
Correction（更正）修改原始物件Development/Correction
Repair（修復）修改副本（在非原始系統改物件）Repair
Modification（修改）對 SAP 物件的 RepairRepair

自己的物件在生產機出錯時，應回到原始系統（開發機）更正再傳輸，保持各系統一致；若不得已在副本上修了，必須立刻回原始系統更正。SAP 物件沒有原始系統在你手上，所以只能「修改」。

升級衝突：升級、套 Support Package 或匯入傳輸時，若你改過的 SAP 物件也被 SAP 交付了新版本，就會發生衝突；想保留修改就要做修改調整（§18）。修改越多，升級越慢。調整只在開發機做，再傳到後續系統。

SSCR（SAP Software Change Registration）：修改 SAP 原始碼或手動修改 DDIC 物件前，每個物件都要到 SAP 註冊取得存取金鑰（Access Key）。不需註冊的例外：Matchcode、資料庫索引、緩衝設定、客戶物件、Patch、自動產生的物件（例如 Customizing 產生的）。金鑰存在本機，之後任何已註冊開發者再改同一物件都不必再輸入，版本升級後仍有效。好處：①SAP 一線支援能快速定位問題、提高可用性；②避免無意間修改；③修改少，升級容易。

執行註冊修改時要提供 SSCR 金鑰＋變更請求，物件自動加入 Repair 任務，並帶來三種效果：

  • Change Lock：任務指派後只有擁有者能改；
  • Import Lock：物件不會被匯入（升級、SP）覆蓋；
  • 版本建立：系統產生新版本。

開發完成釋放任務時要記錄修改內容；Change Lock 與 Import Lock 轉到變更請求。若釋放時確認 Repair，Import Lock 才轉到請求；不確認就留在原處，只有該開發者能解除。釋放變更請求後所有鎖解除，物件匯出到 OS 目錄由管理員匯入後續系統；進 QAS 後開發者要測試並檢查匯入日誌。

版本：釋放請求時，所有物件的完整版本寫入版本資料庫；之後再傳輸，現行物件成為完整副本，新舊差異以 backward delta 保存。第一次修改時系統會先建完整副本（SAP 不交付版本）。版本資訊同時記錄是 SAP 或客戶建立的，這是修改調整的基礎。

修改的成功要素（强晟 p155–157；Col18 p263–264）：

  1. 把客戶程式碼封裝在模組化單元（呼叫客戶函數模組、客戶子畫面），不要直接塞進 SAP 程式碼；封裝時用窄介面以控制資料。
  2. 使用標準化的行內文件（Modification Assistant 支援）；不刪 SAP 程式碼，改用註解。
  3. 維護修改日誌（Modification Log）：物件類型、物件名、子程序、主題區（依藍圖／技術設計）、Repair 的請求號、修改日期、修改人、是否為預先更正、SAP Note 號與有效至哪個版本、調整時預估還原所需時間。可用 SE95 的清單當基礎。
  4. 不要修改 Basis 核心 DDIC 物件（除非 SAP Note 或 Hotline 指示）：屬 Basis 元件（例如 ABAP Workbench）的 DDIC 修改在升級時會被還原、且沒有調整支援，可能造成表格內容遺失。
  5. 升級或匯入 SP 之前，釋放所有含 Repair 的請求，讓客戶版本寫入版本資料庫。

17. SAP Note Assistant（SNOTE）

沒有 Note Assistant 以前（强晟 p173–186）：所有 Note 的修正都要手動改，錯誤機率高；改 SAP 物件前要輸入註冊金鑰；很難自己看出 Note 之間及與既有更正的相依性；套 SP 或升級後還要手動調整。

Note Assistant 解決了大部分問題：①不需註冊金鑰；②自動透過 Modification Assistant 把更正匯入系統；③自動辨識 Note 相依性並建議先匯入前置 Note；④Note 有有效期，套 SP／升級時系統檢查更正是否仍有效，失效可一鍵撤銷；⑤可列出系統中所有已套 Note 的概覽。注意：它是為修正單一錯誤設計的，不是用來取代 Support Package。

  • SNOTE 工作清單節點：指派給我處理的 Note、所有新 Note、狀態不一致的 Note；可套用者有對應按鈕（Utilities → Color Legend 看圖例）。
  • 下載：以 RFC 連線直接下載（Note → Download），或先存到本機再上傳（Note → Upload）。
  • Note Browser（Goto → Note Browser）：所有已套 Note 的概覽，可跳到 Modification Browser 看某個 Note 改了哪些物件，也可依狀態（可套用、已套用、過時）查詢。
  • 套用前仔細閱讀；綠燈表示可自動套用；找不到上下文區塊等衝突時，用特殊版的分割畫面編輯器手動套。
  • Note Queue：有前置 Note 時一次列出，必須依順序套。選項：一次套多個（僅當相關 INCLUDE 都沒被你修改過）、逐一套用（可追蹤每段原始碼改動並自行調整）、取消。
  • 套 SP 後在 SPAU 看到的 Note 狀態：無色燈＝更正已包含在 SP 中、Note 已過時，須把物件還原為 SAP 原始；黃燈＝Note 已套但 SP 未包含、會被覆蓋，須重新套用（工作清單狀態為不一致）；綠燈（罕見）＝Note 中部分更正指令已被 SP 取代、部分仍有效。
  • 在有 Note Assistant 之前就手動套過的 Note，可用程式 SCWN_REGISTER_NOTES 登錄為「已套用」：輸入 Note 號 → 系統載入 Note → 檢查在目前版本與 SP 等級是否有效 → 檢查是否已登錄。好處：Note Browser 看得到、當成前置 Note 時不會被要求重套、升級後會出現在 SPAU 的「Note Corrections」目錄中。
現況：强晟筆記中的「SAP Service Marketplace／SAPNet-R/3 前端」已由 SAP for Me／SAP ONE Support Launchpad 取代；現行 SNOTE 要求下載數位簽章的 Note，並支援以傳輸包交付修正指令的 TCI（Transport-Based Correction Instruction）。升級工具也從筆記中的 R3UP 變成 SUM（Software Update Manager）。

Classic BAdI 移轉為 New BAdI：New BAdI 呼叫快得多，SAP 建議只定義 New BAdI，並把自己的 Classic BAdI 移轉（絕不要移轉 SAP 的 BAdI）。在 SE18 以選單執行，只需幾分鐘；但因兩者差異無法全自動，建議半自動：系統自動建 Spot 與 New BAdI 後，①刪除 Classic BAdI 定義；②把程式中的 CL_EXITHANDLER=>GET_INSTANCE 與方法呼叫改成 GET BADI／CALL BADI。不改程式也能運作（bridge method 內已用 GET BADI／CALL BADI），但要享受效能就得改。只能在原始系統移轉；移轉後在 Classic BAdI 仍存在期間不可改 New BAdI。若是 SAP 移轉了自己的 Classic BAdI，客戶的實作要在 SPAU 初始畫面選「Migrated Objects」手動移轉（3-4 章 §12）。

19. Switch Framework：SFW1／SFW2／SFW5 與 Conflict Switch

Switch Framework 的目的是把各產業解決方案（Industry Solution）與 Enhancement Package 都以「未啟用」狀態放進標準系統，客戶不必另外安裝，用開關啟用即可（强晟 p234–235；Col18 p309–318）。

  • 層級：Business Function Set（一套產業解決方案，只能啟用一個）→ Business Function → Switch → Package（及其中的選單項目、畫面元素、增強實作⋯）。用 SFW5 啟用／停用 Business Function（同時只能有一個使用者在 SFW5 的變更模式）。
  • 客戶自己的用法：用 SFW1 建 Switch 並指派含增強實作的套件（不能指派個別增強實作）→ 用 SFW2 建 Business Function（不含產業元件時用類型 G，Enterprise Business Function）並指派 Switch → 用 SFW5 開關。SFW1 按「Activate」只是啟用 Switch 物件本身，不代表增強生效。
  • 指派類型：Activation（套件所有物件隨之啟用，控制增強實作時選它）；Standby（只啟用宣告性增強，如 DDIC Append、static 程式增強）。
  • 要能再關閉，Business Function 必須勾 Reversible，且不含 DDIC 物件。產業解決方案與 Enhancement Package 啟用時會產生程式與 DDIC 物件，不可逆。
  • 只有 Enhancement Framework 的實作可開關；Customer Exit、Classic BAdI、User Exit、BTE 不受影響。變通：在這些實作（例如 Classic BAdI 實作類別的方法）開頭或結尾用隱式增強寫程式，隱式增強就可以掛 Switch。
  • 程式碼中增強實作永遠標示為「active」，看不出是否被 Switch 關掉；要雙擊實作名 → Properties 頁籤查看 Switch 與其狀態。

Conflict Switch：兩個以上 Switch 都含同一個增強段或 Single-Use BAdI 的實作、又同時打開，就衝突。Conflict Switch 可指派多個一般 Switch：全部 ON 時它才 ON，任一 OFF 就 OFF。指派 Conflict Switch（而非一般 Switch）的增強實作稱為衝突解決實作，它必須涵蓋所有可能同時啟用之實作的共同語意，並在衝突時優先執行；多個衝突解決實作時，解決最多衝突者優先。每一種可能衝突的組合都要有對應的 Conflict Switch 與衝突解決實作。

S/4HANA 中許多 Business Function 已預設啟用或被標為不再相關，客戶自建 Business Function 來開關增強的做法在實務上不常見；更常見的是在增強程式裡讀自訂 Customizing 表（例如公司代碼＋功能開關）決定是否執行，並把這張表納入傳輸。

21.1 Field Exit

替畫面上「參照 DDIC 資料元素的可輸入欄位」掛一支函數模組，在 PAI 的特定時點執行（强晟 p236–245；Col18 p333–338）。使用者離開畫面時的處理順序：①檢查必填欄位（空的就重顯畫面）→ ②檢查輸入格式 → ③執行 Field Exit（發錯誤訊息會重顯畫面）→ ④欄位傳輸 → ⑤外鍵檢查 → ⑥畫面 PAI 模組。

  • 全域 Field Exit：不限畫面，所有用到該資料元素的畫面都生效；可修改內容、發錯誤強迫重輸、阻擋特定使用者。
  • 本地 Field Exit：只對指定程式的指定畫面有效。一個資料元素要嘛一個全域、要嘛最多 36 個本地，不能同時。建立本地前必須已有全域；定義本地後全域函數不再使用，但不可刪除全域函數模組（從清單刪掉會連 Field Exit 一起刪除）。
  • 命名：FIELD_EXIT_<資料元素>，本地再加 _0～_9、_A～_Z；名稱由系統給，不可改；函數建在客戶函數群；介面固定只有 INPUT 與 OUTPUT。
  • 建立：强晟版為 CMOD → Goto → Global Enhancements → Field Exits；Col18 改為執行報表 RSMODPRF。（L29 Col92 版補充：2010 版投影片已寫 RSMODPRF，解答還提醒「不要從 Function Builder 自己建 Field Exit」；啟用方式是回到 RSMODPRF 選擇畫面、兩欄留空按 F8 列出所有 Field Exit，選取後 Field exit → Activate。）
  • 一定要給 OUTPUT 賦值，否則執行後畫面欄位變成初始值。
  • 禁用陳述式：CALL SCREEN、CALL DIALOG、CALL TRANSACTION、SUBMIT、COMMIT WORK、ROLLBACK WORK、COMMUNICATION RECEIVE、EXIT FROM STEP-LOOP、MESSAGE I、MESSAGE W、STOP、REJECT。
  • 除錯器會略過 Field Exit 程式碼，只能在 Function Builder 測試環境除錯；多個欄位都有 Field Exit 時處理順序無法控制，也不能讀其他畫面欄位。
  • 要生效，所有應用伺服器都必須設定參數 abap/fieldexit = YES（預設 NO）。參考 SAP Note 29377。
FUNCTION field_exit_s_carr_id.
*"----------------------------------------------------------------------
*"  IMPORTING VALUE(INPUT)

*"----------------------------------------------------------------------
  " 航空公司代碼轉大寫並只允許列舉的代碼
  DATA(lv_carr)    = to_upper( CONV string( input ) ).

Field Exit 早已停止發展，Col18 已把它歸為 Legacy。維護舊系統時要認得它（看到欄位值莫名其妙被改，檢查 abap/fieldexit 與 FIELD_EXIT_* 函數），但新開發一律不要再建：GUI 畫面改用 Screen Exit／BAdI 或 Dynpro 的 FIELD … MODULE … ON INPUT 檢查；Fiori／RAP 應用用 Validation 與 Determination。

21.2 Business Data Toolset（BDT）

BDT（前身為主資料管理／業務夥伴管理）是維護主資料與簡單交易資料的中央控制工具，支援對話、Direct Input、函數模組三種維護方式；並提供通用物件服務（變更文件清單、欄位修改、刪除程式）。BDT 管理物件的通用部分，透過預先定義的介面（控制表與事件）呼叫各應用，例如讀寫應用表格。合作夥伴與客戶可透過 BDT 介面不修改原始碼地增強這些物件；UI 與程式邏輯分離，因此可換用不同使用者介面。

設計目標：可擴充、可配置、可切分、替代 UI、易用、開發快、通用物件服務。不用 BDT 時，欄位修改、變更文件評估、依 DDIC 的畫面檢查等都要自己開發；用了 BDT，應用只需實作業務功能，代價是失去一點個性。

以 BDT 開發的物件：中央業務夥伴（夥伴維護、關係維護）、應收應付合約帳戶、IBU Banking（銀行帳戶、定期委託、金融產品、財務條件、風險物件、各種交易）、IBU Insurance（理賠、損失事件、佣金協議）、不動產管理 RE（不動產合約、成本效益分析）。

事件與程式流程：起點是一般交易碼，一律啟動程式 BUSSTART；BDT 依交易碼從控制表讀取所有資訊，在各事件中動態呼叫各應用的函數模組。每個應用在獨立函數群中開發：子畫面、PBO/PAI 模組、函數模組；PBO 模組只呼叫一支 BDT 服務函數設定欄位屬性，PAI 模組只呼叫一支取得游標位置。事件分為應用事件（讀、檢查、存）、表格事件（應用與函數群之間的溝通）、View 事件：PBC（格式化表格，如排序）、PBO（輸出前，如讀 Customizing 文字）、PAI（輸入後，如檢查輸入值）。同一段程式碼在無對話的 Direct Input 模式也會執行，不必重寫。

BDT 在 S/4HANA 並未消失：交易 BP（業務夥伴，已取代 XD01／XK01 系列）仍建立在 BDT 上，BP 畫面加客戶欄位的標準做法就是「Append＋BDT 設定（區域選單 BUPT 下的應用、欄位群、View、Section、Screen 設定）」。和 BP 相關的 BAPI 與 CVI 整合見 4-1 章。

Col92 的 GET BADI 說明要修正：p300 寫「GET BADI 找不到有效實作就觸發 CX_BADI_NOT_IMPLEMENTED」。實際規則是：只有 Single-Use BAdI 找不到實作、且沒有預設實作與 Fallback 類別時才拋；Multiple-Use BAdI 沒有實作時照樣拿到 Handle，CALL BADI 等於什麼都不做（§12 的程式碼註解就是這個規則）。如果照 Col92 的字面理解，在每個 GET BADI 外都寫「CATCH 後 RETURN」，對 Multiple-Use BAdI 不會出錯，但會誤以為「沒拋例外＝一定有實作」而寫出依賴實作存在的邏輯。

    MESSAGE e010(bc425) WITH input.    " E 訊息 → 畫面重顯；禁止 I／W 訊息
  ENDIF.
ENDFUNCTION.
SBC00E03 原解答提醒：「剩餘座位數」不要加進 Append 結構，因為講師用程式填 Append 欄位，Append 一改就可能出錯。這個提醒放到實務上一樣成立：計算欄位（可由其他欄位推得的值）不要落地成資料庫欄位，放在畫面用全域變數或 CDS 計算欄位即可。另外 Field Exit 只是教學用的遺留技術（§21），權限檢查在新開發中應放在交易的 PAI 或 RAP 的 Authorization 控制，不要再建 Field Exit。

22.7 練習改寫三：全域類別的 Post 方法（Col92 p294 的隱式增強）

Col92 是第一個把「Pre／Post／Overwrite 方法」寫進 BC425 的版本：在 Class Builder 選 Class → Enhance，選取 SAP 方法後 Edit → Enhancement Operations → Insert Pre-Method／Post-Method 或 Add Overwrite Method，再按該列新出現的「Pre／Post／Overwrite Exit」按鈕實作。這些方法是系統自動產生之本地類別的實例方法，有屬性 CORE_OBJECT 指向目前的 SAP 物件實例。一個方法可同時有 Pre 與 Post，但 Overwrite 與它們互斥（§13）。

*&---------------------------------------------------------------*
*& 示意：假設某全域類別有方法 GET_PRICE（IMPORTING iv_carrid、EXPORTING cv_price）
*& 與公開屬性 MV_CURRENCY；Enhancement Implementation 名為 ZEI_FLIGHT_PRICE
*& Post 方法：原方法 GET_PRICE 執行完後自動被呼叫
*& 本地類別與介面名稱（此處 LCL_/IPO_ 開頭）由系統產生，請以實際畫面為準；
*& 簽章＝原方法的 IMPORTING（唯讀）＋EXPORTING／CHANGING（以 CHANGING 提供，可修改）
*&---------------------------------------------------------------*
METHOD ipo_zei_flight_price~get_price.
  " 只在列舉的航空公司套用客製折扣（列舉，不用區間）
  DATA(lt_carriers) = VALUE string_table( ( `LH` ) ( `SQ` ) ).
  CHECK line_exists( lt_carriers[ table_line = CONV string( iv_carrid ) ] ).

  cv_price = cv_price * '0.95'.

  " 需要讀原物件的公開屬性時，透過 CORE_OBJECT
  IF core_object->mv_currency IS INITIAL.
    RETURN.
  ENDIF.
ENDMETHOD.
Casper 的升級成本階梯在 Col92 已經看得到雛形：正課教 Customer Exit、BTE、Classic BAdI（都是 SAP 預留），附錄才教「不需 SAP 準備」的隱式增強點與 Pre／Post／Overwrite。後者看似萬能，但它掛在 SAP 的內部實作細節上，SAP 一改方法簽章或刪掉 FORM，SPAU_ENH 就要處理衝突。所以順序永遠是：標準設定 → BAdI／Enhancement Spot → Enhancement Point（顯式優先於隱式）→ 修改標準。

練習與自我檢核

  1. 下列哪些調整 SAP 標準的技術需要使用 ABAP Workbench？A Customizing、B Personalization、C Enhancement、D Modification。
    答：C、D（以及客戶開發）。Customizing 用 IMG，個人化用 SHD0／PFCG 等，不寫程式。
  2. 哪些增強技術提供 Menu Exit？
    答：Customer Exit、Classic BAdI、New BAdI。BTE 與顯式增強都沒有。
  3. 一個 SAP 交易最多能有幾個「標準變式」？變式交易和標準變式差在哪？
    答：一個。變式交易是新的交易碼（要執行新碼才套用，且放進角色選單必須用它）；標準變式掛在原交易碼上自動套用。交易變式不能覆寫錯誤訊息。
  4. Append Structure 與 CI Include 各舉三個差異；Fixed Value Append 能否同時指派給兩個 Domain？
    答：Append 不需 SAP 規劃、只屬一個表、一表可多個；CI Include 需 SAP 預先 .INCLUDE、可用在多個表、名稱 CI_ 開頭。欄位都要 ZZ/YY 開頭，都不能用在 Pool/Cluster 表（BSEG 例外）。Fixed Value Append 只能屬於一個 Domain，但一個 Domain 可有多個。
  5. 在 ZXaaaUnn 裡為什麼不能寫 FORM？為什麼 MESSAGE 一定要帶訊息類別？
    答：ZXaaaUnn 位於 FUNCTION…ENDFUNCTION 之內，FORM／MODULE／事件要另建 ZXaaaFnn 等並由 ZXaaaZZZ 納入。LXaaaTOP 的 FUNCTION-POOL 陳述式不可改，無法設定預設訊息類別。
  6. CALL CUSTOMER-SUBSCREEN 的語法規則？資料如何在主畫面與 X 函數群子畫面間傳遞？
    答：子畫面區不加引號、X 函數群以引號靜態指定、畫面號可用 4 碼變數。靠兩個 Program Exit：主畫面 PBO 送資料進 X 函數群全域變數、PAI 取回；SAP 若沒提供第二個出口就無法回寫。
  7. 實作 BTE 的六個步驟？哪兩個陳述式禁止？BTE 相對 Customer Exit 的三個優勢？
    答：複製 SAMPLE_INTERFACE_* 為 Z 函數（不改介面）→ 寫程式 → 啟用函數 → FIBF 建產品 → 以產品把函數指派給事件 → 啟用產品。禁止 COMMIT WORK、ROLLBACK WORK。優勢：可多重實作、Client 相依、可依國家／應用過濾。
  8. Classic BAdI 停用實作後，應用程式中的 GET_INSTANCE 還會執行嗎？和 Customer Exit 有何不同？
    答：會執行，只是 Adapter 找不到有效實作；Customer Exit 的 CALL CUSTOMER-FUNCTION 在專案未啟用時根本不執行。實作只能在原始系統啟用／停用後傳輸。
  9. Classic BAdI Screen Exit 在主畫面 PBO 的五個步驟？沒有實作時會顯示什麼？
    答：GET_INSTANCE → SET_INSTANCE_FOR_SUBSCREENS → GET_PROG_AND_DYNP_FOR_SUBSCR → 呼叫 BAdI 方法傳資料 → CALL SUBSCREEN。無實作時回傳 SAPLSEXM 的空白子畫面 0200。
  10. New BAdI：GET BADI 何時拋 CX_BADI_NOT_IMPLEMENTED？預設實作與 Fallback 類別誰先？提供 Screen Exit 的 BAdI 實例建立模式要選哪個？
    答：Single-Use BAdI 找不到實作（且無預設／Fallback）時；Multiple-Use 不拋。先執行所有非預設實作，都沒有才跑預設實作，再沒有才用 Fallback 類別。Screen BAdI 必須是 Reusing Instantiation、不可 Multiple Use；Menu BAdI 不可過濾、不可 Multiple Use、不可掛 Switch。
  11. 一個增強段有兩個啟用中的實作，執行時會 dump 嗎？怎麼解？
    答：不會 dump，只有語法警告，但執行哪一個不可知。用 Switch Framework 建 Conflict Switch 與衝突解決實作。增強點多實作則是順序不可知——邏輯不可互相依賴（同 HANA 無預設排序的道理）。
  12. SSCR 金鑰在哪些情況不需要？釋放 Repair 任務時若不確認 Repair 會怎樣？
    答：Matchcode、DB 索引、緩衝設定、客戶物件、Patch、自動產生物件不需註冊；透過 SNOTE 套 Note 也不需要。未確認 Repair 時 Import Lock 留在原處，只有該開發者能解除，物件不會被升級覆蓋。
  13. SPDD 與 SPAU 各調整哪些物件？為什麼 SPDD 要在主匯入前？SPAU 免金鑰期限是幾天？
    答：SPDD：Domain、資料元素、表格；SPAU：程式、選單、畫面、Search Help、View、Lock Object（及 Note、增強）。DDIC 物件若在產生後才調整可能遺失資料。Col18 為 14 天（2008 年版為 30 天）。
  14. User Exit 為什麼「是修改」卻不會出現在修改調整清單？
    答：它要改 SAP 命名空間的 INCLUDE（如 MV45AFZZ），技術上是修改；但 SAP 交付後承諾不再改這些 INCLUDE（新出口放新 INCLUDE），所以升級不會產生衝突、不列入調整。
  15. （L29 Col92）Classic BAdI 與 New BAdI 在執行架構上的關鍵差異是什麼？為什麼 SAP 說 New BAdI 比較快？
    答：Classic BAdI 定義啟用時產生 Adapter 類別 CL_EX_<BAdI>，程式要先用 CL_EXITHANDLER=>GET_INSTANCE 實例化它，再呼叫其中自動產生的 bridging method，由它依序轉呼叫各有效實作；New BAdI 沒有 Adapter 類別，GET BADI 由核心直接產生 BAdI Handle，CALL BADI 直接呼叫實作方法，省掉實例化與轉呼叫。
  16. （L29 Col92）Col92 p300 說「GET BADI 找不到有效實作就拋 CX_BADI_NOT_IMPLEMENTED」，這句話哪裡不精確？
    答：只有 Single-Use BAdI、且沒有預設實作與 Fallback 類別時才拋；Multiple-Use BAdI 沒有實作也會拿到 Handle，CALL BADI 什麼都不做。CALL BADI 時 Handle 為初始值才拋 CX_BADI_INITIAL_REFERENCE。
  17. （L29 Col92）比較强晟 2008、Col92 2010、Col18 2023 三版：哪些內容在 2010 版已經出現、哪些要到 Col18 才有？
    答：2010 版已有：SE18/SE19 的新舊兩區、附錄中的隱式／顯式點與段、New BAdI 的 GET BADI／CALL BADI、多過濾與運算子、SFW5 概念、Field Exit 改用 RSMODPRF、Append 的 Enhancement Category；且 SNOTE 一課已刪。Col18 才有：New BAdI 升為正課、Fallback 類別與實例建立模式、SPAU_ENH 增強調整與 Classic BAdI 移轉、SFW1/SFW2 與 Conflict Switch、Extension Index、Fixed Value Append、SPAU 期限 14 天、BSEG 例外、BTE 禁止 ROLLBACK WORK。
  18. （L29 Col92）X 函數群中 LXaaaTOP、LXaaaTAP、ZXaaaTOP 各放什麼？為什麼在出口裡發訊息一定要寫訊息類別？
    答：LXaaaTOP 只有 FUNCTION-POOL 與 INCLUDE LXaaaTAP、INCLUDE ZXaaaTOP；LXaaaTAP 放 SAP 的全域資料；ZXaaaTOP 放客戶的全域資料。FUNCTION-POOL 陳述式在 SAP 的 LXaaaTOP 裡不能改，無法加 MESSAGE-ID，所以要寫成 MESSAGE e011(bc425) 這種形式。
  19. 實作題：用本章 §6 的程式找出 SAPMV45A 與 SAPMM06E 的所有函數出口，再用 SE84 搜尋 Enhancement Spot「ES_SAPMV45A」，列出它有哪些顯式增強點；最後說明你會用哪一種技術實作「銷售單存檔前檢查客戶採購單號」，並依 Casper 的升級成本階梯說明理由。
