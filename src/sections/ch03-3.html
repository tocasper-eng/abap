1. 增強的概念：什麼時候該用增強

增強（Enhancement）的概念其實非常廣：建在 SAP 標準系統之上的所有二次開發，都可以理解為增強。但 ABAP 開發講的「增強」，特指標準系統事先預留好的介面——SAP 在自己的程式裡寫了一個空的鉤子，我們把程式碼掛上去，執行時就會被呼叫。這種開發稱為增強，也叫出口（Exit）。

老師的一句話定調：「如果增強滿足不了，就只能修正（Modification）。」 修正＝改 SAP 標準碼，要申請 Access Key、升級時會在 SPAU 跟你要帳，是最後手段。順序永遠是：Customizing（設定）→ 增強（Exit / BAdI）→ 自建程式（Z*）→ 最後才是修正。

1-1．典型的增強需求

  • 業務流程檢查：在某個工廠發貨，設定「在某個庫位的出貨只能使用某種移動類型」；訂單存檔前檢查信用額度、檢查客戶是否黑名單。
  • 介面（欄位）增強：使用者對某個欄位要求大寫，但最終使用者不照規範打，可以在出口中自動轉換；有些模組能自訂資料庫欄位，並在出口中增加欄位輸入；也能對輸入資料做檢查，甚至自動替代（Substitution）。
  • 不規則業務的處理：按某種特殊條件定價——從自己定義的 Z 表中按條件取值再回填價格。
  • 搜尋說明（Search Help）的出口：對 SAP 標準搜尋說明做權限控制，例如業務員只能查到自己負責的客戶。

2-1．選用決策樹（實務順序）

  1. 先問：能不能用 Customizing 解決？（SPRO、條件技術、輸出控制、複製控制）→ 能就不要寫程式。
  2. 有沒有 new/classic BAdI？（SE18 / SE84 找 Enhancement Spot）→ 有就用 BAdI。BAdI 支援多重實作，最不容易和其他顧問打架，也是 SAP 在 S/4HANA 唯一持續增修的介面。
  3. 有沒有第二代 Customer Exit？（SMOD／CMOD）→ 有就用。缺點：一個增強組件在整個 client 只能被一個 CMOD 專案啟用，多顧問搶同一個出口會衝突。
  4. 有沒有第一代 User Exit？（MV45AFZZ 之類）→ SD 很多情境只有第一代做得到（例如 USEREXIT_SAVE_DOCUMENT_PREPARE、USEREXIT_MOVE_FIELD_TO_VBAP），該用還是要用。
  5. 有沒有隱式／顯式 Enhancement Point？→ 都沒有出口時的最後救援（比修改標準碼安全）。
  6. 都沒有 → 才考慮修正（Modification），要 Access Key，升級走 SPAU/SPDD。
老師特別提醒第一代的兩個致命傷：（1）系統升級時可能被新版本覆蓋而失效；（2）因為它看得到全部全域變數，如果你在裡面改了全域變數，可能破壞系統原有的邏輯。所以「光是這一點，就不要輕易碰觸了，瞭解就行」——但既有專案裡到處都是它，你一定要看得懂。

3. 第一代 User Exit：原理與命名規則

第一代的做法是：SAP 提供一個空程式碼的子常式（FORM），在這個子常式中使用者可以加入自己的代碼。它的規律是：

  • 需要修改的 SAP 標準碼，集中在一些名稱倒數第二個字元為 Z 的 INCLUDE 程式中（MV45AFZZ、MV45AOZZ、MV45AIZZ、MV45ATZZ…）。
  • 子常式一般以 USEREXIT_ 起頭。
  • 在出口裡，呼叫程式的所有全域資料都可以使用（XVBAP、XVBEP、VBAK、KOMK…直接拿來用），這是第一代最強、也最危險的地方。
  • 螢幕增強以客戶螢幕（Include Screen）形式發佈，包含在標準程式中，沒有什麼特別規律，要看該模組的 IMG 說明。
  • 表／結構的增強是 Append Structure。
  • 原始碼增強和螢幕增強的說明，可以從 SPRO 後臺設定中相關模組的路徑裡面找到。
第一代出口不需要 Access Key（那些 include 是 SAP 交付給客戶修改的），但它們是 SAP 物件，儲存時會被要求指定 Request，並可能提示是「修改」。這也是為什麼它們在升級時要進 SPAU 對帳。

4. 怎麼找第一代出口：三種可操作的方法

先記住這句話：第一代增強無法用 Z_FIND_USEREXITS 找出來。 那支程式（第 8 節）掃的是 TADIR 裡的 SMOD／SXSD 物件，也就是第二、三代。第一代是 FORM 子常式，不在 TADIR 裡，只能靠下面三招。

4-1．方法一：利用 SPRO（最正統，附官方說明文件）

  1. 執行 SPRO → 按「SAP 參考 IMG（SAP Reference IMG）」。
  2. 走到目標模組的節點，找名稱含 System Modifications／系統修改／User Exits 的子節點。SD 的路徑是：Sales and Distribution → System Modifications → User Exits。
  3. 點該節點左邊的文件圖示（IMG 說明），SAP 會列出這個領域所有可用的 INCLUDE 與 USEREXIT_* 子常式，以及每一個出口的呼叫時機（例如「呼叫於 FORM BELEG_SICHERN 開頭」）。
  4. 把要用的 INCLUDE 名稱抄下來，到 SE38 開啟它，找到對應的 FORM 寫碼。

（依講義步驟整理）

4-2．方法二：利用 SE80 ＋ Package VMOD

  1. 執行 SE80，物件類型下拉選 Package（套件／開發類別）。
  2. 輸入 VMOD（SD 使用者出口的專屬套件；講義寫成「vomd」是筆誤）→ Enter。
  3. 展開 Programs／Includes，就會看到 MV45AFZZ、MV45AFZA、MV45AFZB、MV45AOZZ、MV45AIZZ、MV50AFZ1、RV60AFZZ… 這一整批第一代出口 include。
  4. 雙擊任一支，用「其他功能 → 尋找（Ctrl+F）」搜 USEREXIT_，就能列出這支 include 內所有可用出口。
其他模組也有類似的套件；找不到套件時，改用方法三（從主程式反推）最快，因為那不需要背套件名稱。

4-3．方法三：由 TCODE 找主程式，再從主程式找出口（最通用）

  1. 在目標交易畫面按 系統 → 狀態（System → Status），看「程式（畫面）」欄位，或直接跑 SE93 輸入交易碼看它掛的程式。例如 VA01 → SAPMV45A、ME21 → SAPMM06E、VL01N → SAPMV50A、VF01 → SAPMV60A。
  2. SE38 開啟該主程式 → 看它的 INCLUDE 清單，找倒數第二個字元是 Z 的 include（多半集中在註解 U S E R - E X I T S 底下）。
  3. 雙擊進入 include，搜尋 FORM USEREXIT_，挑選符合時機的那一支。
  4. 不確定會不會被呼叫？在 FORM 第一行設中斷點，跑一次交易，停下來就是對的；停不下來就換一支。

典型路徑：SAPMV45A ⇒ MV45AFZZ ⇒ FORM USEREXIT_SAVE_DOCUMENT。

老師的驗證法：「是否成功，可以靠 DEBUG 來確認；怕影響所有人，可以用 IF 做小範圍的測試。」——所有教學／測試用的出口碼，一律先包一層 IF sy-uname = '你的帳號' AND sy-mandt = '你的 client'，這是第一代出口的鐵律，因為它對整個 client 的所有使用者生效。

5. 第一代增強實作：訂單存檔前的檢查

最常用的出口是 MV45AFZZ / USEREXIT_SAVE_DOCUMENT_PREPARE——它是存檔前最後一個可以改資料、可以擋下單據的地方（呼叫於 FORM BELEG_SICHERN 的開頭）。

MESSAGE 型別的坑（S/4HANA 尤其重要）：這支出口不只被 VA01/VA02 呼叫，BAPI_SALESORDER_CREATEFROMDAT2、IDOC、Fiori／OData、批次背景作業也都會走到。在那些情境下：
・TYPE 'I' / 'W' 會試圖跳出對話框 → 背景或 RFC 會 DUMP（MESSAGE_TYPE_X / 無畫面可顯示）。
・TYPE 'E' 在 BAPI 中不會回到 RETURN 表，而是直接讓程式中斷。
正確做法：先判斷 sy-batch／sy-binpt／呼叫來源，或把錯誤寫進不完整性紀錄（Incompletion Log）；教學測試完務必把程式碼註解掉。

5-5．USEREXIT_SAVE_DOCUMENT：寫自建統計表

FORM userexit_save_document.

  " 此出口在 FORM BELEG_SICHERN 的 COMMIT 之前被呼叫
  " → 這裡的 DB 動作會和單據在同一個 LUW，不需要（也絕對不可以）自己 COMMIT WORK
  DATA lt_log TYPE STANDARD TABLE OF zsd_order_log.

  LOOP AT xvbap INTO DATA(ls_vbap) WHERE updkz <> 'D'.
    APPEND VALUE #( mandt = sy-mandt
                    vbeln = ls_vbap-vbeln
                    posnr = ls_vbap-posnr
                    matnr = ls_vbap-matnr
                    kwmeng = ls_vbap-kwmeng
                    ernam = sy-uname
                    erdat = sy-datum
                    erzet = sy-uzeit ) TO lt_log.
  ENDLOOP.

  IF lt_log IS NOT INITIAL.
    MODIFY zsd_order_log FROM TABLE lt_log.
  ENDIF.

  " 若變更了標準欄位，必須設定 r185d-dataloss = 'X'，
  " 系統在安全常式開頭會檢查此旗標，維護自建表時也要一併設定
  " r185d-dataloss = 'X'.

ENDFORM.
絕對不要在任何 User Exit / Customer Exit 裡下 COMMIT WORK 或 ROLLBACK WORK。出口是在標準交易的 LUW 中間被呼叫的，你一 COMMIT，SAP 標準的更新流程就被切成兩段，輕則單據不完整、重則資料不一致。要非同步處理請用 CALL FUNCTION … IN UPDATE TASK 或 IN BACKGROUND UNIT。

7. VOFM 常式：SD 的另一種第一代增強

VOFM 是 SD／定價／輸出控制專用的「常式維護器」。它產生的也是 FORM 子常式（第一代的親戚），但是由 VOFM 統一產生、統一啟用，並在 Customizing 中被掛號使用。

7-1．VOFM 的四大類

選單中文用途產生的 FORM / 程式
Requirements → Pricing需求常式（定價）決定某個條件類型要不要被存取／計算。掛在 V/08 定價程序的 Requirement 欄FORM KOBED_9xx（含明細檢查）與 KOBEV_9xx（前置檢查，不可用明細欄位）；程式 LV61A9xx

7-2．需求常式範例（KOBED / KOBEV）

*&--- VOFM → Requirements → Pricing → 901（程式 LV61A901）
*     邏輯：只有銷售組織 1000 且料號以 DXTR 開頭時，這個條件類型才生效
FORM kobed_901.

  sy-subrc = 4.                     " 預設「不符合需求」→ 條件不被存取

  CHECK komk-vkorg = '1000'.
  CHECK komp-matnr(4) = 'DXTR'.

  sy-subrc = 0.                     " 符合 → 條件生效

ENDFORM.

*     KOBEV 是「前置檢查」：在還沒有明細資料時被呼叫，
*     因此 **絕對不可以** 存取 KOMP（明細）欄位，只能用 KOMK（抬頭）
FORM kobev_901.

  sy-subrc = 4.
  CHECK komk-vkorg = '1000'.
  sy-subrc = 0.

ENDFORM.
KOBED 與 KOBEV 一定要成對維護且邏輯相容。最經典的錯誤是：KOBEV 寫了 KOMP 的條件，結果前置檢查時 KOMP 還是空的，導致條件時有時無——症狀就是「同一張單，重跑定價結果不一樣」。這個「不穩定」的症頭和第 1 章講的 SELECT 無排序保證是同一類問題：只要結果不穩定，先懷疑「輸入資料的順序／完整性」。

7-3．定價公式範例（FRM_KONDI_WERT_9xx）

*&--- VOFM → Formulas → Condition value → 901（程式 RV64A901）
*     邏輯：從自建表 ZSD_SPECIAL_PRICE 取特殊單價，找不到就沿用標準計算結果
FORM frm_kondi_wert_901.

  " XKWERT 是這類公式的回傳欄位；XKOMV 是目前處理中的條件行
  SELECT SINGLE price
    FROM zsd_special_price
    WHERE kunnr = @komk-kunnr
      AND matnr = @komp-matnr
      AND datab <= @komk-prsdt
      AND datbi >= @komk-prsdt
    INTO @DATA(lv_price).

  IF sy-subrc = 0.
    " 單價 × 數量；注意幣別小數位，必要時用 CURRENCY_CONVERSION 類函數處理
    xkwert = lv_price * komp-mgame / 1000.
  ENDIF.

ENDFORM.
VOFM 常式裡只能使用定價通訊結構（KOMK／KOMP／KOMT1／XKOMV／TKOMV…）。要多帶欄位進來，就得回頭用 USEREXIT_PRICING_PREPARE_TKOMK / TKOMP 把欄位塞進 KOMK／KOMP（先在 KOMKAZ／KOMPAZ 這兩個 include 結構裡 Append 欄位）。這就是第一代出口與 VOFM 的標準搭檔打法。

7-4．VOFM 的存取碼（Access Key）問題

  • VOFM 產生的程式（LV61A9xx、RV64A9xx…）本質上是 SAP 物件，因此在許多系統上「新建／修改常式」時，會跳出要求輸入 物件存取碼（SSCR Object Key / Access Key） 的視窗。
  • 正規解法：到 SAP Support Portal（原 OSS）用該系統的安裝號碼申請該物件的 Registration Key；有些版本改為只要開發者鑰匙即可。相關說明可查 SAP Note 關鍵字 VOFM namespace / VOFM modification（例如 Note 356737 一系列，實際 Note 號請以你系統上 SNOTE 查到的為準）。
  • 啟用旗標：VOFM 畫面上每一列前面有「Active（啟用）」欄，新建後必須把它打勾（選單「編輯 → 啟用」），否則常式不會被呼叫——這是最常見的「我明明寫了怎麼沒進來」的原因。
  • 升級陷阱：升級或 Support Package 之後，VOFM 常式的啟用旗標可能遺失，或產生程式 T-code 表（TFRM／TFRMT）與程式不同步，需重新啟用並重新產生。上線前的升級測試務必把所有客戶編號常式跑過一遍。
  • 傳輸：VOFM 常式和它的啟用登錄（TFRM/TFRMT）是分開的物件，傳輸時容易漏——傳完到目標系統再開一次 VOFM 確認狀態。

8. 第二代 Customer Exit：概念與四種類型

第二代的原始碼增強以函數模組形式發佈：在 SAP 的發行版本中，用 CALL CUSTOMER-FUNCTION 'nnn' 呼叫這些函數模組，它們在發佈時只有一句程式碼 INCLUDE ZXxxxxxx.。使用者增強時無需申請物件鍵（Access Key），直接建立這個 INCLUDE、編寫相應的程式碼即可。

第二代與第一代最大的差別：這些函數模組中只能使用介面（EXPORTING／IMPORTING／TABLES）中傳遞的參數，不能使用呼叫程式的全域變數。這是優點（安全、不會破壞標準邏輯），也是限制（想要的資料沒傳進來就是拿不到，只能改用第一代或 BAdI）。

8-1．標準程式裡長什麼樣

*--- SAP 標準程式 SAPMM06E 裡的一段（示意）
  CALL CUSTOMER-FUNCTION '007'
    EXPORTING
      i_ekko = ekko                  " 只有這裡列出的東西，出口才拿得到
    IMPORTING
      e_ci_ekko = ci_ekko
    EXCEPTIONS
      OTHERS = 1.

*--- 命名規則（背起來）：
*    CALL CUSTOMER-FUNCTION 'nnn'  ⇒  函數名 = EXIT_<主程式名>_<nnn>
*    SAPMM06E + '007'              ⇒  EXIT_SAPMM06E_007
*    SAPMV45A + '003'              ⇒  EXIT_SAPMV45A_003

*--- 而 EXIT_SAPMM06E_007 的原始碼裡「只有一行」：
FUNCTION exit_sapmm06e_007.
  INCLUDE zxm06u38.                  " ← 雙擊它，系統會問你要不要建立，這才是你寫碼的地方
ENDFUNCTION.

9. 怎麼找第二代出口：六種可操作的方法

這一節是本章的核心。照順序試，一定找得到。

方法 A（首選）：用 Z_FIND_USEREXIT 依 TCODE 一次列出

  1. SE38 執行 Z_FIND_USEREXIT（自建工具程式，見第 10 節）。
  2. 輸入交易碼（如 ME21N、VA01）或直接輸入程式名。
  3. 報表會分兩區列出：Enhancement（SMOD，第二代） 與 Business Add-in（SXSD，第三／四代），並顯示筆數。
  4. 雙擊清單中的名稱可直接跳到 SMOD（第二代）或 SE18（BAdI）。
原理：由 TCODE → TSTC 找主程式 → TADIR 找該程式的開發類別（Package / DEVCLASS） → 再列出同一個 Package 底下所有 SMOD 與 SXSD 物件。所以它列出來的是「這個模組領域的所有出口」，不是「這個交易一定會呼叫的出口」——還是要靠 DEBUG 確認。

方法 B：SE84 Repository Information System

  1. SE84 → 展開 增強（Enhancements）。
  2. Customer Exits → Enhancements：可用增強名稱（如 MM06E*）、Package、元件名（如 EXIT_SAPMM06E*）反查增強組件。
  3. Customer Exits → Function Exits：直接用 EXIT_* 樣式搜函數出口。
  4. Enhancement Spots / BAdIs：找第三、四代（第 3-4 章）。

方法 C：SE16N 查 MODSAP / MODSAPT

  1. SE16N → 表名 MODSAP。
  2. MEMBER 欄位輸入 EXIT_SAPMM06E*（用你猜到的主程式名組出來的樣式）→ 執行，即可看到所有相關的增強名與類型。
  3. 反過來也行：知道增強名（如 MM06E005）填 NAME，就能看到它底下所有元件（E／S／C／T 各是什麼）。
  4. 要中文／英文說明就查 MODSAPT（SPRSL = 語言）。

方法 D：在標準程式中直接搜尋 CALL CUSTOMER-FUNCTION（最可靠）

  1. SE93 由交易碼查出主程式（例：ME21N → SAPLMEGUI；ME21 → SAPMM06E；VA01 → SAPMV45A）。
  2. SE38 開該程式 → 功能表「其他功能 → 搜尋／取代」（或 Ctrl+F）。
  3. 搜尋字串輸入 CUSTOMER-FUNCTION，範圍選 「在所有 Include 中（In main program）」、勾選「所有出現位置」。
  4. 結果每一行像 CALL CUSTOMER-FUNCTION '007'，把 主程式名 + 編號 組起來就是函數名：EXIT_SAPMM06E_007。
  5. 螢幕出口就搜 CALL CUSTOMER-SUBSCREEN；菜單出口搜 GUI Status 中以 + 開頭的功能碼。
  6. 拿函數名回到 MODSAP（方法 C）反查它屬於哪個增強組件（NAME），才知道 CMOD 要掛哪一個。

方法 E：SE37 直接猜／查 EXIT_ 函數

  1. SE37 函數名輸入 EXIT_SAPMM06E* → 按 F4，列出所有符合的出口函數。
  2. 雙擊進去看它的介面參數——這一步很關鍵：介面裡沒有的資料，你在出口裡就拿不到，決定了這支出口能不能用。
  3. 看它的原始碼（只有一行 INCLUDE ZX…），記下 INCLUDE 名稱。

方法 F：追不到時的 DEBUG／Trace 大絕

  1. 敘述中斷點：進入交易 → /h 開 Debug → 功能表「中斷點 → 中斷點於 → 敘述（Breakpoint at Statement）」→ 輸入 CALL CUSTOMER-FUNCTION。之後每次標準碼呼叫任何出口都會停下來，sy-repid 就是主程式、參數就是編號。同理可設 CALL CUSTOMER-SUBSCREEN、CALL BADI、CALL METHOD。
  2. 函數中斷點：「中斷點 → 中斷點於 → 函數模組」→ 輸入 MODX_FUNCTION_ACTIVE_CHECK。每次系統檢查「這個出口有沒有啟用」都會停，在 Local 頁籤看參數就知道正在檢查哪一支出口（第 12 節詳述）。
  3. 執行時期分析：SAT（舊版 SE30）錄一次交易，在結果的「呼叫階層／Hit List」中用 EXIT_ 或 ZX 過濾，可以看到實際被執行過的出口與先後順序——這是判斷「哪一支出口真的會跑」最省時間的方法。
  4. SQL Trace：ST05 看標準程式讀了哪些表，反推該從哪個時點切入。
老師的實戰忠告：「畫面上的程式應是 EXIT_SAPMM06E_006，而且有可能會有多支增強，要耐心的 DEBUG。」 找出口沒有一步到位的魔法，方法 A/C/E 先縮小範圍，方法 F 定生死。

11. SMOD 與 CMOD：查看與實現增強的完整操作

兩個交易碼的分工，一句話記住：SMOD 是「看有什麼出口」（SAP 交付的增強組件，唯讀）；CMOD 是「我要用哪些出口」（客戶專案，可寫可啟用）。

11-1．SMOD：查看增強組件

  1. SMOD → 增強名稱輸入（如 MM06E005、V45A0003），或按 F4 用說明文字模糊搜尋。
  2. 選 Components（元件） → 顯示。畫面分區列出：Function exits（EXIT_*）、Screen areas（螢幕出口的程式＋螢幕編號）、Menu entries、Include structures（CI_ 結構）。
  3. 按 Documentation（文件） 讀 SAP 的官方說明：這個增強什麼時候被呼叫、能改什麼、不能改什麼。這一步千萬別跳過。
  4. 雙擊某個 EXIT_ 函數即可進入 SE37 看介面與 INCLUDE 名稱。

（依講義步驟整理）

講義另外提到一個很實用的練習題：「SAP 記錄 CO02 生產訂單修改日誌的增強」——用 Z_FIND_USEREXIT 輸入 CO02，會列出 PP 模組的一整批 SMOD／BAdI，再用 SMOD 的文件逐一看說明，挑出能攔截「訂單修改」的那一支。這是練習「找出口」最好的自我訓練。

11-2．CMOD：建立專案並實現增強（標準八步驟）

  1. CMOD → 專案（Project）輸入自訂名稱（Z 開頭，例如 ZPO、ZSD01）→ 按建立。
    命名策略：老師的做法是「ZPO 是指將所有的 PO 相關增強都放在此 PROJECT」——依模組／主題分專案，不要一個出口開一個專案，否則以後沒人管得動。
  2. 輸入簡短說明 → 存檔 → 指定套件與傳輸請求。
  3. 按 Enhancement assignments（增強指派） → 在清單中列舉由 SMOD 所找到的、想要增強的增強組件名稱（可一次填多個）→ 存檔。
  4. 按 Components（元件） → 可看到已經預設好的增強函數名稱（例如 EXIT_SAPMM06E_007）。
  5. 雙擊該函數名 → 進入函數群組（例如 XM06）→ 函數原始碼中只有一行 INCLUDE ZXM06U38.。
  6. 雙擊 INCLUDE 名稱 → 系統詢問「此 Include 尚不存在，要建立嗎？」→ 按是，指定套件與請求 → 建立 ZXM06U38，裡頭就可以自行新增程式碼了。
  7. 寫完程式碼 → 啟用（Ctrl+F3） → 退出回到 CMOD。
  8. 在 CMOD 專案畫面按 啟用（Activate，火柴人／閃電圖示）。啟用成功後，回到 Components 會發現增強函數名稱前面有一個綠色 ✔。

（依講義步驟整理）

老師的鐵律：「增強要生效必須啟動；增強要刪除必須取消啟動。」
・只寫程式碼、沒按 CMOD 的「啟用」＝完全不會被呼叫（TFDIR-MAND 不會變成 'C'）。這是初學者最常卡住的地方。
・要移除增強，順序是：先 Deactivate 專案 → 再刪除指派／程式碼。直接刪 Include 會讓函數變成語法錯誤，整個交易碼掛掉。
・一個增強組件（SMOD name）只能被一個 CMOD 專案指派。若已被別的專案佔用，系統會擋下來——這時要去談，把邏輯合併進既有專案，不要另開專案硬幹。

11-3．第一代與第二代在「建程式」上的差別

口訣：「第一代程式會先建好，第二代則由自己新增。」 第一代的 MV45AFZZ、USEREXIT_SAVE_DOCUMENT_PREPARE 已經存在，你打開就能寫；第二代的 ZXM06U38 一開始不存在，要你雙擊建立；螢幕出口的螢幕 0101 也不存在，要你自己到 SE38/SE80 建。

練習題：在採購單上增加客制的欄位，並處理它。 這個練習一次用到第二代的三種類型：T（結構）→ S（螢幕）→ E（函數）。

12-1．步驟總覽

12-2．欄位結構增強（EKKO）

  1. SE11 → 結構 CI_EKKODB → 若不存在則建立（它是 SAP 預留給客戶的 Customer Include，名稱固定，不要自己另取）。

  1. 用 SE38 進入 SAPMM06E，搜尋 CALL CUSTOMER-SUBSCREEN，確認 SAP 預留的子螢幕區域名稱與呼叫的程式（SAPLXM06）。

13. 超級函數 MODX_FUNCTION_ACTIVE_CHECK 與出口觸發順序

MODX_FUNCTION_ACTIVE_CHECK 的參數是由功能模組名稱而來——標準程式在真正呼叫 EXIT_ 之前，會先用這支函數問「這個出口啟用了沒」。所以只要在它上面設一個中斷點，整個交易會呼叫哪些出口、以什麼順序呼叫，就全部無所遁形。這就是老師說的「超級函數」。

13-1．用它來反查出口（操作步驟）

  1. SE37 開啟 MODX_FUNCTION_ACTIVE_CHECK → 在第一行可執行敘述設外部中斷點（Session Breakpoint）。DEBUG 技巧：也可以直接由函數設定 DEBUG。
  2. 執行目標交易（例如 ME21N）。
  3. 每次停下來時，切到 Debugger 的 Locals（本地）頁籤，看傳進來的函數名參數——那就是系統正在檢查的出口。
  4. 把每次停下來的函數名依序抄下來，就得到「這個交易的出口觸發時序表」。
  5. 找到目標出口後，把中斷點移到該出口的 ZX… include 上，取消 MODX 的中斷點。
同理，螢幕出口用 MODX_SUBSCREEN_ACTIVE_CHECK、菜單出口用 MODX_MENUENTRY_ACTIVE_CHECK 或 MODX_ALL_ACTIVE_MENUENTRIES。這三支加上 MODX_FUNCTION_ACTIVE_CHECK，就是第二代增強的「四把萬能鑰匙」。
*--- 在自己的程式裡也能判斷某個出口是否已啟用（少用，但除錯很好用）
DATA(lv_active) = abap_true.

CALL FUNCTION 'MODX_FUNCTION_ACTIVE_CHECK'
  EXPORTING
    funcname   = 'EXIT_SAPMM06E_007'
  EXCEPTIONS
    not_active = 1
    OTHERS     = 2.

IF sy-subrc <> 0.
  lv_active = abap_false.
ENDIF.

" 介面參數名稱會因版本略有差異，請以你系統上 SE37 顯示的為準
WRITE: / |EXIT_SAPMM06E_007 啟用狀態：{ COND string( WHEN lv_active = abap_true
                                                     THEN '已啟用' ELSE '未啟用' ) }|.

15. 菜單出口與欄位出口

15-1．Menu Exit（菜單出口）

  1. SAP 在標準的 GUI Status 中預留了功能碼，以 + 開頭（例如 +CUS、+C01）。
  2. 在 SMOD 該增強的 Components 中，Menu entries 區塊會列出程式名、Status、功能碼。
  3. 在 CMOD 的 Components 中雙擊該功能碼，填入功能表文字（多語系可分別維護，文字存在 CUATEXTS）。
  4. 功能碼被按下時，會經由對應的函數出口（通常是同一個增強裡的某支 EXIT_，介面帶有 SY-UCOMM／FCODE）交給你處理。
  5. CMOD 專案啟用後，該功能表項目才會出現在交易畫面上。

（依講義步驟整理）

系統背後是用 MODX_ALL_ACTIVE_MENUENTRIES / MODX_MENUENTRY_ACTIVE_CHECK 判斷菜單項目是否啟用，資料放在 CUATEXTS。菜單項目沒出現，先查這兩個地方。

15-2．Field Exit（欄位出口）

欄位出口是掛在資料元素（Data Element）上的檢核／轉換：只要畫面上任何欄位用了那個資料元素，離開欄位時就會呼叫你的函數。

  1. CMOD → 功能表 Goto → Text enhancements → Field exits（或直接執行程式 RSMODPRF）。
  2. 建立 → 輸入資料元素名稱 → 系統自動產生函數 FIELD_EXIT_<資料元素>（可加尾碼 _A、_B 產生多個版本）。
  3. 在函數中處理：介面固定為 INPUT（使用者輸入值）與 OUTPUT（要寫回畫面的值）。
  4. 可以指定只對某一個程式／螢幕編號生效（全域 vs 區域欄位出口）。
  5. 啟用欄位出口，而且系統參數 abap/fieldexit = YES 必須設定（要 BASIS 改 profile 並重啟，這也是它很少被用的原因）。
FUNCTION field_exit_zzcontract.
*"----------------------------------------------------------------------
*"*"Local Interface:
*"  IMPORTING
*"     REFERENCE(INPUT)
*"  EXPORTING
*"     REFERENCE(OUTPUT)
*"----------------------------------------------------------------------

  " 典型用途：使用者不照規範打小寫 → 自動轉大寫並補零
  output = to_upper( condense( CONV string( input ) ) ).

ENDFUNCTION.
Field Exit 在新版本（ECC 6.0 之後、S/4HANA）已被 SAP 視為過時（obsolete）技術，不再建議使用，且對 Web Dynpro／Fiori 畫面完全無效。要做欄位層級的轉換／檢核，改用：資料元素的 Conversion Exit（CONVERSION_EXIT_xxxxx_INPUT/OUTPUT）、畫面 PAI 檢核、或 BAdI。這裡列出來只是為了讓你看得懂舊系統。

17. S/4HANA 注意事項

17-1．第一、二代仍然存在且可用，但已停止擴充。 S/4HANA 1809 以後，SD／MM 的傳統交易（VA01、ME21、VF01）大多還在，MV45AFZZ、MM06E005 也都還在被呼叫。但 SAP 不再新增第一、二代出口，所有新功能只提供 BAdI / Enhancement Spot。新開發一律優先找 BAdI（第 3-4 章）。
17-2．走 Fiori / OData / BAPI / RAP 的路徑，出口不一定會被呼叫。 例如：
・ME21N（Enjoy 交易）不使用 MM06E005 的子螢幕出口，客制欄位的畫面要改用 BAdI ME_GUI_PO_CUST，邏輯用 ME_PROCESS_PO_CUST。舊的 SAPLXM06 0101 只在舊式 ME21／ME22／ME23 有效。這正是講義所說「有些練習環境有可能無法啟動／很難有環境讓您試」的技術原因之一。
・銷售訂單若由 Fiori App 或 API_SALES_ORDER_SRV（OData）建立，走的是不同的服務層，第一代 SD user exit 不保證被觸發。
做法：導入前一定要把「所有建單通路」列出來（GUI／BAPI／IDoc／OData／CPI），逐一 DEBUG 驗證出口有沒有跑到。
17-3．標準程式被改寫後，出口可能失效。 S/4HANA 的簡化清單（Simplification List）改寫了大量標準程式：MB5B／MSEG 相關邏輯改走 MATDOC、BSEG／BKPF 相關改走 ACDOCA、SD 的狀態表 VBUK／VBUP 已被併入 VBAK／VBAP。所以：
・RV45PFZA 的 USEREXIT_SET_STATUS_VBUK / _VBUP 在 S/4HANA 上因 VBUK/VBUP 被移除（改為 CDS 相容視圖），行為與 ECC 不同，升級專案必須逐一重測。
・出口裡若有 SELECT … FROM vbuk、FROM bseg、FROM mseg，升級時要改成新表或 CDS View。
17-4．升級與 Note 的衝突處理。
・SPDD：升級時處理字典物件的修改對帳（Append Structure、資料元素、Domain）。在匯入階段就要做，錯過會遺失。
・SPAU：升級後處理 Repository 物件（程式、函數、螢幕）的修改對帳。第一代出口 include 若被 SAP 改版，會出現在這裡，要人工合併。
・SPAU_ENH：專門處理增強實作（第三、四代）的調整。
・SNOTE 套 Note 時，若 Note 改到你動過的 include，會要求 Access Key 或提示衝突——先用 SE95（修改瀏覽器）確認自己動過哪些標準物件。
治本建議：把出口裡的邏輯全部搬進自建的 Z 類別／Z 函數，出口 include 裡只留一行呼叫。這樣升級時 SPAU 只要處理那一行，維護成本降到最低。
*--- 建議的出口寫法：出口 include 內只留「一行呼叫」，邏輯全在自建類別中
*    INCLUDE ZXVVAU05
zcl_sd_order_exit=>check_before_save( ).

*--- 自建類別（可單元測試、可版本管理、升級時不受 SPAU 影響）
CLASS zcl_sd_order_exit DEFINITION PUBLIC FINAL CREATE PUBLIC.
  PUBLIC SECTION.
    CLASS-METHODS check_before_save
      RAISING cx_static_check.
ENDCLASS.

CLASS zcl_sd_order_exit IMPLEMENTATION.
  METHOD check_before_save.

    TRY.
        " 真正的商業邏輯寫在這裡：可以寫 ABAP Unit、可以被別的程式重用
        DATA(lo_checker) = NEW zcl_sd_credit_checker( ).
        lo_checker->validate( ).

      CATCH zcx_sd_check INTO DATA(lx).
        " 統一的錯誤處理：介面情境寫 log，對話情境才丟訊息
        IF sy-batch = abap_true OR sy-binpt = abap_true.
          zcl_app_log=>add( lx->get_text( ) ).
        ELSE.

        ENDIF.
    ENDTRY.

  ENDMETHOD.
ENDCLASS.
出口撰寫的七條軍規（把它貼在你的螢幕邊）：
① 不下 COMMIT WORK / ROLLBACK WORK。
② 不改不屬於自己的全域變數。
③ 不在出口裡做大量 DB 存取或呼叫 RFC（會拖垮交易反應時間）。
④ 訊息型別要看情境：對話用 E／W，背景與 BAPI 用 log。
⑤ 一律先做 IF 條件縮小生效範圍（公司代碼／單據類型／工廠），不要對全公司生效。
⑥ 邏輯搬進 Z 類別，出口只留一行呼叫。
⑦ 每一段增強都要在程式開頭寫註解：誰、哪一天、哪張需求單、為什麼。
