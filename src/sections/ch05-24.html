2. SAP HANA：記憶體運算、欄式儲存與 OLTP／OLAP 合一

課程第一課開門見山問：「現有資料庫早就會把資料快取在記憶體，為什麼還需要一個 in-memory 平台？」答案分三層：

  • 硬體演進：多核心 CPU 加大型快取、記憶體容量「幾乎無上限」且價格下跌，足以放下企業全部業務資料；記憶體存取比磁碟快 100 萬～1,000 萬倍（原文 1M–10M times）。
  • 從三層到記憶體內：過去 40 年的商業軟體（含 SAP Business Suite）都是 3-tier：用戶端／應用伺服器（RAM 小但快）／資料庫伺服器（磁碟大但慢）。資料庫只被當作「儲存機制」，大量查詢把資料搬回應用伺服器處理——這個分離如今反而變成效能障礙。
  • 欄式儲存（Columnar Data Storage）：因為在記憶體中，可以重新組織表格的儲存方式，帶來 ①高壓縮率 ②高速彙總 ③資料載入 CPU 最佳化。例：只想知道「每個國家的金額」時，欄式只需讀國家欄與金額欄；列式儲存（row store）則要讀每一筆 tuple。

避開資料傳輸瓶頸：把彙總計算下放到記憶體資料庫層執行，應用層負擔變輕。OLTP 與 OLAP 回到同一個資料庫：過去因為磁碟運算，交易與分析被迫分家（資料要搬去 BW、要預先彙總、要夜間批次），HANA 讓「在交易系統直接做即時分析」變得可行。課程用蜘蛛圖說明舊技術只能在「廣而深的分析」與「快而簡單的報表」之間取捨，而且兩者都做不到即時；HANA 可以取消中間彙總表、直接從交易資料分析。

SAP HANA 被定位為「One Platform for Any Application」：資料庫＋資料處理＋應用平台，附帶預測、規劃、文字處理、空間（spatial）、商業分析等函式庫。課程也提到當時的雲端版圖：On Premise、HANA Enterprise Cloud（HEC，SAP 代管的月租服務）、HANA Cloud Platform（PaaS）、以及 SaaS（SuccessFactors、Ariba、SAP Jam、Hybris）。

對 ABAP 開發者，這一課的結論只有一句：把「資料密集」的運算交給資料庫（Code-to-Data），不要把資料搬回 ABAP 再 LOOP。

3. HANA 開發模型、與 AS ABAP 的整合情境、S/4HANA 概覽

HANA 上的軟體開發三層（p17）：

HANA 與 AS ABAP 的兩種整合情境（p17–p18）：

  • Side-by-Side：HANA 裝在 Business Suite 旁邊（Suite 用任何資料庫），資料複寫到 HANA（例如 SLT）做分析加速。
  • HANA as Primary Persistence：HANA 直接當 AS ABAP 的主資料庫。傳統 3-tier 應用可以與新的 2-tier 應用共存，並逐步用 HANA 能力強化（Business Suite on HANA 就是這樣演進的）。

S/4HANA 名稱與定位（p19–p24）：S 代表 Simple 也代表 Suite，4 代表第四代；全名 SAP Business Suite 4 SAP HANA；因為原生跑在 HANA 且高度最佳化而得名，被稱為 R/3 以來最大的創新。與「Business Suite powered by SAP HANA」的差別：後者只是把既有應用移植到 HANA 並最佳化程式（只需資料庫遷移，兩年內超過 1,850 家客戶採用）；S/4HANA 則是結合 HANA 與 Fiori UX 的新一代套件，簡化資料模型（例如財務的 Simple Finance）。

課程列出的特性：資料量更小、吞吐量更高、分析更快、流程步驟更少、ERP/CRM/SRM/SCM/PLM 共同部署、實際資料（25%）與歷史資料（75%）分層、預測／建議／模擬、HANA 多租戶、Fiori 支援任何裝置。部署選項：on-premise edition 與 cloud edition；不支援不同 OS／資料庫平台的組合（單一平台、單一程式碼線）。三種導入情境：

5. NetWeaver 開發工具、UI 技術與混合雲情境

Eclipse 是一切工具的共同底座（p29、p33）：

  • ABAP in Eclipse（ABAP Development Tools，ADT）：NetWeaver 7.31 SP4 起可在 Eclipse 開發 ABAP。行為類似 SE80：先建立與後端的線上連線，依偏好顯示 ABAP 套件，可同時連多套系統、多個物件各自一個分頁；Eclipse 不原生支援的物件就用內嵌 SAP GUI 開啟。詳見 5-5 章。
  • NetWeaver Developer Studio（NWDS）：Java（AS Java）開發，也是 PI/BPM 建模工具移到 Eclipse 後的家。
  • SAP HANA Studio、SAPUI5 設計時工具、HANA Cloud 工具，全部是 Eclipse 外掛——同質工具環境讓學習曲線平緩。

UI 技術（p33–p35）：交易型、給 power user 的 UI 用 Web Dynpro 與 Floorplan Manager（FPM）（見 5-23 章）；給偶爾使用者、行動與雲端的新 UI 用 SAPUI5——SAP 對 HTML5 標準的實作，平台獨立，可跑在 AS ABAP、AS Java、NetWeaver Cloud、HANA XS；資料經 Gateway 服務取得；7.4 起與 NetWeaver 整合。SAP Visual Business：用地圖、3D 場景直接呈現與操作業務物件（例如運輸管理），並提供 ABAP 介面讓開發者填資料、寫事件處理。

8. SAP Process Integration（PI）：中央整合平台

為什麼需要 PI（p51）：異質系統之間各自點對點（point-to-point）連線，資料結構與協定都不同、需要大量 mapping 程式；流程改變或新增系統時，每條介面都要改。課程歸納的痛點：任意技術的點對點整合、拼湊式方案、沒有集中的介面知識、自製基礎架構難以調整且維護昂貴、升級成本高。PI 提供共同技術、中央整合點，集中掌握流程、系統、介面資訊。

PI 的關鍵能力：Connectivity（多種協定）、Routing（公司內 A2A、夥伴間 B2B）、Mapping（訊息格式轉換）、Stateful processing（ccBPM）。以開放標準（XML、Java）為基礎。服務包括：介面設計的中央儲存庫、訊息流設定、內容轉換、訊息交換執行環境、流程建模與執行。

PI SOAP 訊息結構：以 XML＋HTTP 的 SOAP 為核心，執行時由 Integration Engine（IE）傳遞。Integration Server 的處理是無狀態（stateless）的：訊息到達 → 決定接收者 → 立即轉送。訊息由 message header（寄件者等屬性，用來決定接收者）、payload（業務資料）、任意數量的 attachments 組成，header 與 payload 都是 XML。

9. Web Service 與 SOA、Enterprise Services、Switch Framework

Web Service 範式（p63–p64）：① 服務提供（provisioning）② 在服務註冊表建立參照（選擇性）③ 在應用中使用服務（consumption）。三個關鍵名詞一定要分清楚（這也是自我檢核第 4、5、9 題的陷阱）：

名詞是什麼常見錯誤說法
WSDLWeb Service Description Language，描述 web service 的文件，可存放於服務目錄—
UDDIUniversal Description, Discovery, and Integration，網路上的註冊表，只存 WSDL 的參照，不存文件本身「UDDI 是呼叫 web service 的協定」→ 錯（那是 SOAP）
SOAP在分散式環境中呼叫 web service 的協定，走 HTTP；訊息有 header（安全、交易資訊）與 body。原意 Simple Object Access Protocol，現已當專有名詞「SOAP 是網路註冊表」→ 錯（那是 UDDI）

使用端流程：在 UDDI 找到服務、下載 WSDL → proxy 產生，得到一個可本機呼叫的函數（proxy）→ 呼叫 proxy 時在本機建立 SOAP request 送到服務 → 結果回到呼叫端。NetWeaver AS 自 Basis 6.40 起提供自己的 web service 基礎架構：可互通的 SOAP runtime（ABAP／Java）、SE80 中建立或引用 web service、NWDS、UDDI 註冊工具。

Enterprise Services（p65–p67）：技術上就是 web service，但 SAP 另外交付「可直接執行的業務內容」——SAP 不只給 SOA 基礎架構，也給ready-to-run SOA。SAP 定義 Enterprise Service 的條件：依模型建模（business object、process component、interface pattern、Global Data Types（GDT））、發佈於 ESR（metadata）、有文件且行為穩定、基於開放標準（WSDL、XML、SOAP）。GDT 依據 ISO 15000-5 與 UN/CEFACT CCTS，解決「介面欄位語意是否一致」的難題。範例服務：查客戶財務狀態、寄確認給客戶、查物料庫存、讀客戶資料、顯示銷售訂單。為了結構化搜尋，SAP 以 process component 作為 business object 與服務的分類傘（ERP、CRM、SRM、SCM、Financials），當時可在 ES Workplace 查詢。

Enhancement Package（EhP）：Enterprise Services 隨 ERP 6.0 的 EhP 交付。EhP 是選擇性安裝與啟用的新功能、累積式（每包含前面所有內容），不是 Support Package；可以只裝需要的、只啟用想用的功能、成本更可預估、並提供 SAP 測試案例。注意：NetWeaver 也有 EhP，但 NetWeaver EhP 匯入即生效，switch 原則只適用業務應用（ERP、SRM、SCM）。

SOA 的關鍵元件：建立服務的工具、儲存 metadata 與管理服務的工具（repository／registry）、訊息分派基礎架構、使用服務的工具、BPM 工具。PI 扮演 SOA middleware：設計時 metadata 放 ESR（ESR 是 PI 7.0 Integration Repository 的強化），執行時用 PI runtime 呼叫；也可以不經 PI，直接點對點呼叫後端。整個架構稱為 Business Process Platform（BPP）；Composite Application（xApps）分為 enterprise services 層、local services 層（本地持久）、UI 層、流程建模層，開發環境是 Composition Environment（CE）。

Switch Framework（SFW）（p71–p73）：用 switch 從外部控制 repository 物件或其組件的可見度；產業解決方案與部分 repository 物件隨系統交付但處於未啟用狀態，套件指派 switch 後可啟用或隱藏其功能，switch 也可被上層 switch 控制。SFW5 啟用 business function 並查文件（文件列出相依的 business function、軟體元件與使用到的 enterprise services）。教材例子：合約帳（FI-CA）的催收——擴充既有交易 FP03E、FP03D、FP03，以及新交易 FKKCOL_MONI、FP03I、FP03P；新交易在服務未啟用時會報「Enterprise Services not activate, function cannot be used」。

Business function 啟用後多數不可逆（reversible 的極少），在 S/4HANA 也一樣：SFW5 按下去前務必確認文件與影響範圍、先在沙盒試。S/4HANA 的新介面方向是 OData／REST API（SAP Business Accelerator Hub），SOAP Enterprise Services 仍大量存在（例如 BP、財務付款的 SOAP API），ABAP 端觀念與本節相同。

11. SAP Process Orchestration（PO）與 HANA Cloud Integration（HCI）

PO（p89–p96）＝ PI 的 Advanced Adapter Engine Extended（AEX）整合能力 ＋ BPM 的流程建模、營運、監控 ＋ BRM。因為 AEX 是 Java-only，PO 也是 Java-only，建模用 NWDS 的 Process Composer；相對地 ccBPM 基於 dual stack，建模在 ESR（integration process 設計物件）。PO 的工作：基本設定（NWDS 設定）、流程建模（design time）、用 NW Administrator 監控 BPM 系統／流程／任務、用 Process Desk 管理流程。

  • 流程模型物件：Activities（步驟）、Roles（執行者，人或系統）、Artifacts（被處理的物件，如業務文件）。
  • Process Controlled Solutions：重用既有技術能力而非介面；部門驅動、以使用者為中心、跨系統與企業邊界、分層架構。適用：公司特有流程或現有應用的缺口、高度溝通協調、需要可重用業務規則、人機混合活動、輕量 B2B（無大量 mapping）、自助服務（請假、出差、申請護照、損害申報）、經常變動或有即時需求的流程。
  • 教材的披薩訂單範例：用 REST 服務依郵遞區號找外送地點，依訂單金額決定是否檢查，透過 SOAP 送給供應商並查天氣服務，最後 e-mail 確認。
  • 例外處理：技術錯誤會終止活動，程式設定的例外不一定終止；分 terminating／non-terminating event；用 event-based choice gateway＋中介計時器避免流程死結（呼叫先到或逾時先到）。
  • AEX：PI 的一種安裝選項，只裝在 Java stack；BPMN 流程的所有進出通訊都經過 AEX；支援 QoS EO（Exactly Once）與 EOIO（Exactly Once In Order）。BPM、BRM、AEX 裝在同一台 Java EE 伺服器上。訊息設定與監控在 http://<host>:<port>/pimon，系統設定在 /nwa（Availability and Performance → Process Monitoring／System Overview）。

12. Business Rules Management（BRM）與 Application Interface Framework（AIF）

SAP BRM（p121–p124）：為組合式流程與應用建模關鍵業務規則、自動化規則式決策。三部分：

  • Rules Composer：design time，NWDS 內的獨立視角，給業務分析師建模、給規則開發者實作；也可在 Process Composer 中於流程情境建規則。
  • Rules Manager：Web 工具，業務分析師維護規則；管理版本、儲存庫、權限、存取控制與治理，並可驗證、測試、產生報表。
  • Rules Engine：runtime，以 stateless session bean 形式存在；BRM runtime 是獨立 Java 應用，以 web service 溝通，任何應用都能用。它讓規則集中管理，而不是寫死在程式裡。

規則寫法：If-Then 與 Decision Table（表格式、可整合 Excel、可回傳多列、動態呼叫），另有 Flow Rules（gateway、rule script、if-then、decision table、其他 flow 組成，可迴圈）。Condition＝LHS（業務物件屬性）＋比較子＋RHS（比較值），例：保險公司自動檢查肇事駕駛是否在保單上。Action 類型：Assert、Assign、Execute、Re-evaluate、Retract、Evaluate Decision Table——其中 Execute、Assign 作用於應用；Assert、Retract、Re-evaluate 影響其他規則如何評估（控制 Rules Engine）。

17. SAP BW：EDW 的持久層與資料供應

為什麼要資料倉儲（p289–p291）：每個 SAP 方案都有標準報表，也能用查詢工具或 ABAP 自寫報表讀正式系統（見 5-6 章、1-4 章）；但決策者要的是單一入口、涵蓋所有流程、跨系統跨流程、高品質且不需大量人工整理的資訊。教材當時已有超過 6,000 家客戶使用 BW。OLTP 與資料倉儲的差異：

面向OLTP資料倉儲（OLAP）
明細程度極細彙總（壓縮）以求高效存取
歷史封存後只留少量歷史完整歷史
可變性頻繁修改某時點後「凍結」
整合低要求高度整合
正規化高度正規化、表很多為檢索效能降低正規化
存取最佳化讀寫刪改都要快讀取最佳化

BW 架構：底層來源系統 → BW server（metadata、主資料、交易資料；查詢時由 Analytical Engine 讀資料）→ 報表工具（BEx Analyzer 嵌在 Excel、BEx Web Analyzer）。Data Warehousing Workbench（RSA1）建模與管理所有資料擷取流程、排程與監控；資料要先經 ETL。建模觀念：Key figure（值或數量：營收、固定成本、人數、訂單量）、Characteristic（key figure 的參照：客戶、產品）、Dimension（容納 characteristic），而且一定要加時間維度。BW 中的業務評估物件叫 InfoObject（最小資訊單元），分 characteristic 與 key figure，另有 unit、time、technical 三種特殊 characteristic；啟用後 characteristic 產生主資料表，key figure 成為 fact table 的一部分。實體模型是星狀綱要（Star Schema），定義 InfoCube 時產生 fact table，另有固定的時間與單位兩張 dimension table。

  • 資料來源：SAP Business Suite（預設擷取結構與程式，來源系統需裝 PI_BASIS plug-in）、多層 BW、經 PI 的 SOAP、市場研究資料（ACNielsen、Dun & Bradstreet）、DB Connect、UDI（JDBC、XMLA）；7.0 起有圖形化 Transformation。
  • 儲存區：Data Marts（InfoCube＋主資料，長期彙總資料）、Operational Data Store（明細，DSO 與 RDA 物件）、Data Warehouse 層。
  • Business Content：以 add-on 交付、基於資料模型可整批啟用（含資料流與預設查詢）；用 RSORBCT 或 RSA1 的 Metadata Repository 查找；比對原則「自上而下」。
  • Nearline：NW 7.0 起查詢可同時讀封存資料與線上資料。RDA（Real-time Data Acquisition）：只用於需要極即時資料的特定情境，不取代 delta 載入（BW350）。
  • BW Accelerator（BWA）：把 InfoProvider 資料建成壓縮但不彙總的記憶體索引，查詢快 10～100 倍；一套 BW 只能用一台 BWA，但一台 BWA 可給多套 BW 用（以系統 ID 區分）；跑在刀鋒伺服器、基於 TREX 技術；7.20 起有 BWA-based InfoCube 與 DSO 索引。教材自己註明：BW on HANA 後 BWA 基本上多餘。
  • 評估工具（L2）：BEx Query Designer（在 InfoProvider 上定義查詢：Rows／Columns、Free Characteristics、Filter——Filter 區的值執行時不能動態改；多個 InfoProvider 要先合成 MultiProvider，因為一個查詢只能建在一個 provider 上）、BEx Web Application Designer（web item → web template → web application）、BEx Analyzer（Excel）、BEx Report Designer（格式化報表，經 Adobe server 轉 PDF；靜態與動態報表）、Information Broadcasting（排程、事件觸發、多格式、發佈到 Portal KM）。
  • ODP（Operational Data Provisioning，NW 7 EhP3 起）：在營運系統直接做 OLAP 查詢與複寫的單一介面；兩層——Analytic Query（分析前端讀取介面）與 BW Service API DataSource（擷取介面）；ODP 層決定走 BWA 還是直接讀 extractor。BW 7.40 起 ODP 來源系統可依階層選取（例如依 HANA 套件）。

18. BusinessObjects BI 平台與 HANA 記憶體運算建模

BusinessObjects BI 平台（p303–p305、p323–p326）：SAP 收購 Business Objects 取得 BI 與資訊管理平台。概念分層：Web tier、管理 tier、儲存 tier（Input／Output File Repository Server、報表快取）、Processing tier（唯一直接存取報表資料庫的層）。工具：CMC（Central Management Console，管理使用者、內容、伺服器、安全）、BI Launch Pad（使用者檢視、排程、追蹤 BI 文件）、Universe（語意層，用 Information Design Tool 建；舊版用 Universe Design Tool）、BICS（BI Consumer Services，4.0 存取 BEx 查詢的最佳做法）。當時的產品策略：儀表板往 Xcelsius（後來 Dashboard Design、Design Studio）、企業報表往 Crystal Reports（BEx WAD 進入維護模式）、OLAP 分析往 Analysis。

HANA 系統架構（p327–p330）：HANA 是記憶體內、欄式、關聯式資料庫。核心 Index Server：session 管理、授權、交易管理、指令處理，並管理記憶體映像、log 與永久儲存之間的持久化；內含 Connection and Session Management、Transaction Manager（交易隔離）、Authorization Manager（SAML、OAuth、Kerberos）、Request Processing and Execution Control（SQL；分析應用也支援 MDX）、SQL Processor 等。HANA Studio 視角：Modeler、Development（HANA XS）、Debug、Administration Console。資料夾：Catalog（字典；schema 分使用者定義、系統定義、SLT 產生）、Content（設計時儲存庫，依 package 組織）、Provisioning（Smart Data Access，遠端資料以 virtual table 呈現）、Security。系統 schema：

Schema內容
_SYS_BIC已啟用物件的所有 column view
_SYS_BIcolumn view 的 metadata、變數表、時間資料、schema／content mapping
_SYS_REPO已啟用與未啟用物件清單、package、runtime 物件資訊
_SYS_STATISTICS系統設定與參數（統計服務）
_SYS_XSHANA XS 使用

HANA 建模三種 view：Attribute View（提供情境，選主資料的欄與列，不做量值與彙總）、Analytic View（含量值，最快的彙總模型，像 cube，只能有一張 fact table，資料不存放、join 與計算量值在執行時求值）、Calculation View（圖形或腳本式；可 join 多張 fact table、做進階計算；存取時隱含執行一個 SQLScript 函數）。使用案例：財務（FICO）、銷售（CRM）、出貨（LE-SHP）、採購（P2P／SRM）即時報表。報表介面：ODBO（MDX）、ODBC（SQL）、JDBC、BICS（SAP 專屬、OLAP 比 MDX 有優勢）、Excel 樞紐分析（定義只在本機、受桌機效能限制）。資料整合：即時複寫 SLT（SAP Landscape Transformation Replication Server）、批次 ETL SAP Data Services。BO 工具與 HANA：Crystal Reports、Web Intelligence（SQL＋universe），Design Studio 走 BICS，架構師要決定語意層放 HANA 模型、universe 或兩者。

19. Master Data Management 與 Master Data Governance（MDG）

主資料管理有兩種路線（p343–p344）：傳統做法是各系統各自建主資料，再合併（consolidation）成單一視圖供全球報表、同步與分析——這是 SAP NetWeaver MDM（aggregate、harmonize、enrich）；新做法是在業務流程前端就把主資料建對（正確、一致、完整）——這是 MDG，業界第一個以集中治理流程管理主資料的應用，涵蓋 business partner、客戶、供應商、物料、財務與自訂網域，並與 SAP Information Steward、Data Services 整合。兩者可單獨或一起部署。

MDG 概念說明
技術基礎建在 AS ABAP 上、嵌入 ERP：部分元件在 ERP 下層可被 ERP 重用，部分在上層並重用 ERP 既有驗證；UI 是 Web Dynpro ABAP（經 Portal 或 NWBC）；用 EIM 的模糊搜尋、Data Services 驗證地址
Change Request新增或變更請求會產生 change request——一個容器，把預定變更放在暫存區（staging）、與 active 主資料分開，最終核准後才進正式；可儲存不完整資料；依 workflow template 流轉
驗證維護過程持續用既有業務邏輯與客製設定驗證，可加自訂規則（BRFplus）
Workflow用 SAP Business Workflow；線性或分散式模型（各部門只維護、核准自己負責的資料）；角色如 Business User、Master Data Steward
重用與擴充可直接把 Business Suite 既有的擴充欄位納入 MDG 資料模型
搜尋建立前先全面搜尋避免重複：搜尋方法（含 fuzzy）、儲存搜尋、條件組合、結果排序
Edition財務主資料用，控制核准資料的生效日：先建 edition → change request 指派到 edition → 全部核准或撤回後 release → release 後不能再加 → 複寫可由單一 CR 或整個 edition 觸發
DRF（Data Replication Framework）自動或手動複寫到 SAP 與非 SAP；技術：ALE／IDoc、SOA 服務、RFC、File、SCM 用 CIF、CRM／SRM 用 middleware；可用過濾條件只送部分資料
Key mapping追蹤既有主資料在各分散系統中不同的歷史鍵值，確保中央只維護一份
Value mapping接收系統對屬性值的理解不同時做轉換（例：物料類型 FERT 在另一系統叫別的代碼）
部署① 全新專用的主資料 hub（完整 ERP 系統，只用 MDG 功能）② 裝在既有 ERP 上、針對特定網域（可與業務共存於同一系統，啟用 MDG business function）
Unit 5 答案：第 1 題 MDG 能做 A 建立、C 維護、D 複寫（B 合併是 NetWeaver MDM 的強項）；第 2 題「只能單獨部署」→ 錯；第 3 題 key mapping → D（追蹤既有主資料的不同歷史鍵值）；第 4 題 → 對。
2026 現況：NetWeaver MDM 已終止，MDG 改名 SAP Master Data Governance on S/4HANA（另有雲端版 MDG, cloud edition），UI 轉向 Fiori／RAP。S/4HANA 的客戶與供應商一律走 Business Partner（BP），MDG 的 BP 網域就是治理 BUT000 系列與 CVI 同步出來的 KNA1／LFA1（見 4-1 章、1-3 章）。寫主資料介面時，用列舉的代碼（物料類型、帳戶群組）比用區間篩選安全——value mapping 的存在本身就說明「同一個值在不同系統意義不同」。

練習與自我檢核

  1. 欄式儲存：為什麼「每個國家的總金額」這種查詢在欄式儲存特別快？列式儲存要多做什麼？
    要點：欄式只讀國家與金額兩欄，且同欄資料型別一致、易壓縮、易向量化彙總；列式要逐列讀完整 tuple。延伸：這也是 SELECT 一定要明列欄位、不要 SELECT * 的理由。
  2. Code Pushdown：把「SELECT * 回 ABAP 再 LOOP + COLLECT」改寫成 pushdown 版本，並說明至少三個好處。
    要點：用 ABAP SQL 的 SUM／COUNT／GROUP BY（或 CDS、AMDP）；好處：傳輸資料量少、DB 平行運算、應用伺服器記憶體與 CPU 負擔低；記得 ORDER BY。
  3. 不穩定的結果：一支報表在 Oracle 上每次結果一樣，搬到 HANA 後「取第一筆」的欄位值時好時壞，原因與解法？
    要點：HANA 沒有預設排序（欄式、平行掃描）；任何取第一筆、SELECT SINGLE 多筆符合、UP TO 1 ROWS 都要明確 ORDER BY。Casper 的成本評價案例：H（item category）與 E（cost component）兩種角度欄位數不同，沒排序就一下抓 H 一下抓 E，結論是固定抓 H。
  4. AS 元件：請說明 dispatcher、work process、ICM、SAP Gateway、Message Server 各自的職責，以及觀察它們的 TCODE。
    要點：dispatcher 分派請求（每 instance 一個，忙時排 queue）；WP 執行邏輯（SM50／SM66）；ICM 處理 HTTP 等協定並判斷送 ABAP 或 Java（SMICM）；Gateway 提供 RFC（SMGW）；Message Server 負載平衡與 instance 間訊息，每系統一個（SM51、SMMS）。
  5. ABAP vs Java 開發：為什麼說 ABAP 是「集中式」而 Java 是「分散式」開發？NWDI 的 DTR、CBS、CMS 各解決什麼？
    要點：ABAP 的開發與執行環境都在 AS ABAP、未啟用前不影響他人、CTS/TMS 傳輸；Java 在本機開發無共用儲存。DTR 版本控制、CBS 集中建置、CMS 傳輸；CTS+ 讓 CTS 也能傳部分 Java 物件。
  6. 增強 vs 修改：客戶要求在標準交易加一個檢查，請依成本由低到高列出可選方案；為何不建議「複製標準程式到 Z」？
    要點：標準設定 → BAdI／Enhancement Spot → Enhancement Point → 修改（需 object key，SAP 不再支援、每次升級要 SPAU）。Z 副本不會跟著 SAP 更新，S/4 簡化項目一變就壞。
  7. WSDL／UDDI／SOAP：判斷真假——「UDDI 是呼叫 web service 的協定」「SOAP 是網路註冊表」「WSDL 描述 web service」。
    要點：前兩句錯（UDDI 是註冊表、SOAP 是協定），第三句對。
  8. Proxy：非同步 outbound proxy 呼叫後資料沒送出，SXMB_MONI 也看不到，最可能漏了什麼？同步 web service consumer 要捕捉哪兩種例外？
    要點：漏了 COMMIT WORK。例外：CX_AI_SYSTEM_FAULT（系統、連線層）與 CX_AI_APPLICATION_FAULT（服務端業務錯誤）；連線設定在 SOAMANAGER 的 logical port。
  9. Enhancement Package 與 Switch Framework：ERP 的 EhP 與 NetWeaver 的 EhP 在啟用上有何不同？在 SFW5 啟用 business function 前要注意什麼？
    要點：ERP EhP 要用 SFW5 開 business function 才生效；NetWeaver EhP 匯入即生效。多數 business function 不可逆，先讀文件（相依與使用的 enterprise services）並在沙盒測試。
  10. 流程工具選型：「單一系統內的採購申請核准」「跨系統、無人工介入的訊息編排」「跨系統且需要人工任務的流程」分別對應教材的哪個工具？今天呢？
    要點：Business Workflow（今日照用＋Flexible Workflow）；ccBPM（已退場→Integration Suite）；SAP BPM（→ SAP Build Process Automation）。Guided Procedures 已被 BPM 取代。
  11. BPMN：sequence flow 與 message flow 的使用範圍差在哪？BPMN 2.0 的五大核心元素？
    要點：sequence flow 只在單一 pool 內，pool 之間用 message flow；五大元素：Flow objects、Data、Connecting objects、Pools（swim lanes）、Artifacts。
  12. BRM 動作：Assert、Assign、Execute、Retract、Re-evaluate 中，哪些作用於應用、哪些影響規則評估？ABAP 端對應的規則引擎是什麼？
    要點：Execute、Assign 作用於應用；Assert、Retract、Re-evaluate 控制規則引擎。ABAP 端用 BRFplus（CL_FDT_FUNCTION_PROCESS=>PROCESS）。
  13. Fiori 架構：Central Hub 與 Embedded 部署差在哪？為什麼 Gateway 與後端的使用者名稱必須相同？
    要點：Hub 是 UI 層＋Gateway 在獨立 front-end server；Embedded 是 Gateway 與業務系統同一台（S/4HANA 常見）。OData 請求以同一身分在後端執行授權檢查，名稱不同就對不上 PFCG 角色（用 CUA／IdM 同步）。
  14. OData 分頁：在 GET_ENTITYSET 實作 $top／$skip 時，最容易漏掉哪一個子句？後果是什麼？
    要點：ORDER BY。沒有排序時 HANA 每次回傳順序可能不同，第 2 頁會重複或漏掉第 1 頁資料；OFFSET 也需要 ORDER BY。
  15. Screen Personas：Personas 與 Fiori 的關鍵差異？它能不能改 Web Dynpro 畫面？
    要點：Personas 內建於 kernel（ITS），個人化既有 Dynpro 交易，不寫程式；Fiori 是重新設計的 app。Personas 只支援經典 Dynpro，不支援 Web Dynpro、CRM/SRM Web UI。
  16. BW 基本觀念：key figure、characteristic、InfoObject、InfoCube、DSO、MultiProvider 各是什麼？一台 BWA 可以給幾套 BW 用？
    要點：量值／參照值／最小資訊單元／星狀綱要的彙總提供者／文件層明細提供者／合併多個 provider 供單一查詢使用。一套 BW 只能用一台 BWA，但一台 BWA 可服務多套 BW。
  17. HANA 建模：Attribute、Analytic、Calculation View 的差別？今天在 S/4HANA 的 ABAP 專案該用什麼？
    要點：Attribute＝主資料情境、不彙總；Analytic＝量值、單一 fact table；Calculation＝多 fact table、進階計算。前兩者已過時；ABAP 專案用 CDS（分析用 @Analytics 註解），複雜程序邏輯才用 AMDP（自己處理 MANDT 與權限）。
  18. MDG：change request 與 edition 各解決什麼問題？key mapping 與 value mapping 有何不同？
    要點：CR 把變更放在 staging、核准後才進 active；edition 控制財務主資料的生效日。key mapping 追蹤既有主資料在各系統的不同鍵值；value mapping 轉換屬性值（如物料類型代碼）。
  19. Solution Manager：導入五階段？Root Cause Analysis 的四個 E2E 診斷？CDMC 的兩個分析對 ABAP 團隊有什麼用？
    要點：Project Preparation、Business Blueprint、Realization、Final Preparation、Go Live & Support；E2E Change、Workload、Exception、Trace（沒有 Error Analysis）；Clearing Analysis 找可刪的 Z 物件、Upgrade/Change Impact Analysis 找升級受影響的客製——今日用 SCMON／SUSG＋ATC 延續。
  20. ILM：三大支柱是什麼？legal hold 與保存期衝突時以何者為準？
    要點：Data Archiving、Retention Management、System Decommissioning。legal hold 優先，被凍結的資料即使過了保存期也不會被銷毀，直到解除 hold。
  21. 安全程式設計：一支報表讓使用者輸入排序欄位與客戶號碼組成動態 SQL，請列出至少三個安全措施。
    要點：AUTHORITY-CHECK（或 CDS DCL）；欄位名用 CL_ABAP_DYN_PRG=>CHECK_WHITELIST_STR 白名單；值用 QUOTE( ) 跳脫或改用主機變數 @；限制筆數；捕捉 CX_SY_DYNAMIC_OSQL_ERROR；SU53 協助使用者查缺少的權限。
  22. 列舉 vs 區間：在 BRFplus decision table、MDG 複寫過濾條件、或報表選擇條件中，為什麼 Casper 建議用多筆 EQ 列舉而不是 BT 區間？
    要點：區間比的是字典序而不是業務語意；遇到號碼段不連續、ALPHA 前導零（'0000001000' vs '1000'）、編碼規則改過，就會漏抓或多抓。列舉明確、可稽核。

    要點：SAP Integration Suite（Cloud Integration）的預包 iFlow；Build Work Zone／Fiori launchpad 上的 MSS Fiori app；報表改 SAC 或 Analysis for Office（資料來自 BW/4HANA 或 S/4 的 CDS 分析查詢）。
