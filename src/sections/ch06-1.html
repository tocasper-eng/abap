2. 動手之前：倒推法——先想清楚要停在哪裡

情境：使用者說「這張報表的某個金額欄位特別小，不合理」。新手的反應是 /h 然後一路 F5，按了一個小時還在選擇畫面事件裡打轉。

操作步驟（整理自〈Debug前章〉的實例）（依截圖整理）：

  1. 在報表畫面選 System → Status，從 Repository Data 找到程式名稱，雙擊直接跳進 SE38。
  2. 找輸出點：ALV 報表先看 START-OF-SELECTION 最後呼叫的顯示程序，確認輸出內表（例：GT_DISPLAY）與欄位目錄（GT_FIELDCAT）。
  3. 欄位標題若來自文字符號（例：TEXT-016），到 Goto → Text Elements → Text Symbols 找編號，再全域搜尋 TEXT-016 就能找到技術欄位名（例：WRTFW_KPF10）。
  4. 全域搜尋輸出內表的 APPEND／INSERT，找到填值的地方；看出該欄位來自工作區 GWA_CKIS1 乘上某變數。
  5. 繼續往上追：GT_CKIS1 由迴圈讀 GT_CKIS4 組成，GT_CKIS4 又由另一段計算產生。
  6. 最後只在那一個計算迴圈設中斷點（最好是條件式中斷點，見第 8 節），F8 直達。

為什麼這樣做：標準程式或大型客製程式從頭跟可能一整天都跟不完；從「結果」往回推，範圍每一步都在縮小。錯誤訊息的情況也一樣：先用訊息號定位（第 7 節），再從發訊息的地方往上推。原文作者的結論是「倒推法 + 排除法」最省時。

Casper 實務經驗：HANA 沒有預設排序。這個案例恰好是成本估算明細（CKIS）。成本評價同時存在 item category「H」與 cost component「E」兩種角度，兩者的成本構成欄位數量不同；程式若用 SELECT SINGLE、READ TABLE … INDEX 1 或「迴圈第一筆就 EXIT」取值卻沒先排序，就會一下抓到 H、一下抓到 E。這類 bug 最難除錯的地方在於你在 Debugger 裡看到的那一次可能剛好是對的。倒推到「取第一筆」的邏輯時，第一件事就是檢查有沒有 ORDER BY／SORT（該案最後的結論是固定抓 H）。

4. 彈出視窗除錯：/h 捷徑檔

情境：按下某個按鈕後跳出對話框（Modal Dialog），例如確認視窗、預覽視窗，想看按下「是」之後做了什麼；但對話框沒有命令列，/h 無處可打。

操作步驟：

  1. 在桌面新增一個文字檔（例如 debug.txt），內容如下，存檔。
  2. 彈出視窗出現時，把這個檔案拖曳到彈出視窗上放開，視窗狀態列會顯示除錯已開啟。
  3. 在彈出視窗按你要追的按鈕，Debugger 就會停在該按鈕的 PAI 處理。
[FUNCTION]
Command=/H
Title=Debugger
Type=SystemCommand

方法二（〈sap各种场景下的DEBUG方法〉）：在 SAP GUI 用「建立捷徑」功能產生一個 .sap 捷徑檔，類型選 System command、命令填 /h，存到桌面；彈出視窗出現時雙擊捷徑檔即可。捷徑檔的內容和上面的文字檔本質相同，只是多了系統與使用者區段：

[System]
Name=S4D
Client=100
[User]
Name=CASPER
Language=ZF
[Function]
Title=Debugger
Command=/H
Type=SystemCommand

為什麼有效：拖放或雙擊時，SAP GUI 會把 /H 當成 OK-Code 送給目前取得焦點的那個視窗，等於替沒有命令列的對話框補上一個命令列。

三份素材的寫法略有差異：有的寫 [Function]，有的寫 [FUNCTION]、有的多一行 Title=Debugger，實測區段名稱大小寫都可以，Title 可有可無。〈sap ABAP 断点调试〉把三行寫在同一行（[Function] Command=/H Type=SystemCommand），那是部落格排版把換行吃掉了，檔案裡必須分三行才有效。

5. 中斷點種類怎麼選：範圍 × 生命週期

「中斷點設了卻不停」十之八九是選錯種類。四種中斷點的設定方式請看 5-4 章第 6 節，這裡只給選擇準則，並彙整素材中的說法：

種類素材中的說法什麼時候用
Debugger 中斷點（除錯時在 Debugger 裡設）「程式跑完就消失」已經在除錯中，臨時多停幾個地方
Session 中斷點「同一次登入的不同視窗都有效，登出後消失」自己在 SAP GUI 操作的報表、交易
External（User）中斷點「登出再登入仍有效，只對同一使用者有效」；電子書稱「外部斷點」RFC、HTTP、OData、Web Dynpro、背景以外「不是從你這個 GUI 視窗發起」的請求；有效期預設 2 小時
靜態中斷點（寫在程式碼）BREAK-POINT「所有使用者都停」、BREAK user「只對該使用者停」開發初期；正式做法請綁 Checkpoint Group（第 6 節）

〈sap ABAP 断点调试〉另外提供兩種分類角度，可以幫助理解：

  • 依生命週期：BREAK-POINT 敘述建立的中斷點跟著主程式「無限期」存在；Debugger 建立的有「有限生命週期」。
  • 依可見範圍：會話級（Session）、調試器級（Debugger）、外部使用者級（External）。
  • 依類型：一般中斷點、Script 中斷點（由 Debugger Script 觸發）；Watchpoint 則是「特殊用途的條件中斷點」。

選擇準則（一句話版）：請求是從你自己這個 SAP GUI 視窗發出的 → Session；不是（RFC、HTTP、別的使用者、別的系統） → External；已經停在 Debugger 裡 → Debugger 中斷點，覺得有用就按 Save as Session BP 或 Save as External BP 升級（Break./Watchpoints 頁籤上的按鈕，電子書圖 6-12 可見）。

〈SAP debug调试方法〉與〈ABAP断点调试〉都把 F8 寫成「跳過後面所有斷點，程式執行完」——這是錯的。F8（Continue）是執行到下一個中斷點或 Watchpoint，沒有就執行完畢；〈调试技术详解〉與英文的〈ABAP Debugging & Smart Forms〉說法才正確。想真的「略過所有中斷點直接跑完」，要先在 Breakpoints 頁籤停用全部中斷點（Deactivate all BPs），或用 Debugger → Exit (Application continues running)。

6. 靜態中斷點的正確姿勢：BREAK-POINT ID、TRMAC 巨集與 SU01 參數

情境：某支介面程式需要長期、反覆除錯，每次都手動設中斷點太麻煩；但直接寫 BREAK-POINT. 又怕忘了拿掉被傳到正式區。

素材裡出現了四種「寫在程式碼裡的中斷點」，逐一評估：

寫法原理評價
BREAK-POINT.所有使用者執行到都停只限開發初期；傳輸前務必刪除
BREAK zcasper.SE16 看表 TRMAC：巨集 BREAK 的內容是 if sy-uname = '&1'. break-point. endif.綁個人帳號，換人維護就失效，也最常被遺忘在正式區
BREAKRC.表 TRMAC 中的內容是 if not sy-subrc is initial. message a895(CJ) with sy-repid. endif.素材說它是「返回碼非 0 條件斷點」——錯誤，見下方說明
CALL FUNCTION 'C160_BREAK_POINT'. + SU01 參數 ESP = X函數讀使用者參數 ESP（短文為「EHS: (developers only) = 'X': BREAK_POINT starts debugger」），有值才停可用但不建議：這是 EHS 模組內部函數，非公開 API
BREAK-POINT ID zgroup.綁 SAAB 的 Checkpoint Group，可依使用者／伺服器啟用，並設到期日標準答案：忘了拿掉也不會停；ATC 可檢查沒綁群組的 BREAK-POINT
教材錯誤修正：BREAKRC 不是中斷點。〈sap ABAP 断点调试〉把 BREAKRC 列為「標準巨集 2，返回碼非 0 條件斷點」，但同一篇文章的 TRMAC 截圖清楚顯示它的內容是 message a895(CJ) with sy-repid——A 類型訊息會直接終止交易，註解甚至寫著「Programmfehler bei SY-Subrc <> 0」（sy-subrc 不為 0 時視為程式錯誤）。它是專案系統（CJ）的斷言式巨集，不是除錯工具。想要「sy-subrc 不為 0 就停」，請用條件式中斷點（第 8 節）或 ASSERT ID … CONDITION sy-subrc = 0。

正式做法：SAAB 建立 Checkpoint Group（例如 ZIF_ORDER_DEBUG），程式中寫 BREAK-POINT ID；平時群組 inactive，要查時在 SAAB 對自己的使用者把 Breakpoints 設為 Break，並給一個短的到期時間。語法細節與 ASSERT ID／LOG-POINT ID 見 5-4 章第 6 節。

7. 動態特殊中斷點：從錯誤訊息一路追到發出點

情境：使用者回報錯誤訊息「00 055」之類的紅字，你不知道是哪一行程式發出的。〈ABAP Debugging & Smart Forms〉稱之為最常見的除錯用途。

操作步驟（依截圖整理）：

  1. 在測試系統重現錯誤；點狀態列的訊息，Performance Assistant 顯示訊息類別與號碼（例：類別 00、號碼 055）。
  2. 回到出錯前一個畫面（或錯誤畫面本身）輸入 /h Enter。
  3. 再觸發一次動作進入 Debugger 後，選 Breakpoints → Breakpoint at → Breakpoint at Message，輸入訊息類別與號碼。
  4. 按 F8，程式會停在 MESSAGE 敘述發出該訊息的那一行；打開 Call Stack 往上看是誰呼叫的。

8. 迴圈裡的中斷點：條件式、Skip 次數與 Watchpoint 實戰

情境：1,000 筆的內表迴圈，問題只出在第 670 筆，或只出在物料 7185002CAD0000M10。在迴圈裡設一般中斷點，F8 要按 670 次。

素材提供了四種解法，由簡到繁：

  1. Skip 次數（電子書 6.6 Tip）：在 Break./Watchpoints 頁籤的 Breakpoints 子頁，找到該中斷點的 Skip 欄位輸入 99，就會略過 99 次、在第 100 次停；停下後看 SY-TABIX = 100 確認。
  2. 條件式中斷點（〈SAP debug调试方法〉、ADT 素材）：中斷點加上條件，例如物料號碼等於某值才停。要跳出迴圈時，在 Breakpoints 子頁把該中斷點刪除即可。
  3. Watchpoint（〈程序跟踪调试〉實踐 7）：點工具列 Watchpoint，變數填 MATERIALID、Free Condition Entry 填 = '1076'，F8 會停在它變成 1076 的那一刻。
  4. 靜態化：需要長期反覆除錯時，把條件寫進程式並綁 Checkpoint Group（第 6 節）。
電子書 6.6：Watchpoint 的 Free Condition Entry 語法規則

實踐 7 的完整流程（依截圖整理）：在 SELECT 與 LOOP AT 兩行設 Session 中斷點 → 執行並輸入客戶 C10002 → 停在 SELECT，F5 一步後雙擊內表 order_i_itab，值顯示 [15x18(524)]，表示 15 列、18 欄 → 雙擊進 Tables 頁籤看內容，發現 MATERIALNAME、IAMOUNT 都還是空的 → 建 Watchpoint（條件 = '1076'）並按 F8，停下時前面幾筆的名稱與金額已被填上，證明填值邏輯正常 → 再用 Create Breakpoint 對 WRITE 敘述設「Debugger 中斷點」（程式結束後自動消失）→ 在 Detail Display 把 oamount 改成 1000，輸出結果跟著改變。最後一步是改變數值，它的風險請看第 19 節的警告。

Watchpoint 看不到別的程式的變數？〈sap各种场景下的DEBUG方法〉說「Watchpoint 只能對目前程式的變數設，不能對被 CALL 的 FM 裡的變數設，要靠 SLAD」。這是舊版 Debugger 的限制；New Debugger 可以用 (程式名)變數名 的寫法指定其他已載入程式的全域變數，例如 (SAPLZFG_ORDER)GT_ITEM。但如〈sap ABAP 断点调试〉第四篇所強調：該程式必須已被載入（已經執行過一次呼叫）才建得起來；還沒載入時，先對 FM 設 Breakpoint at Function Module，停下後再建 Watchpoint。

Casper 實務經驗：條件用列舉比用區間安全。條件式中斷點與 Watchpoint 條件也一樣：寫 MATNR = 'A100' OR MATNR = 'A105'，不要寫成「MATNR 介於 A100 到 A199」。區間比的是字典序而不是業務語意，遇到 ALPHA 前導零（內部值 000000000000001076 與畫面上的 1076 不同）、號碼段不連續、編碼規則改過，中斷點就會「該停不停、不該停亂停」，讓你誤判邏輯正常。另外記得條件裡的值要用內部格式——實踐 7 的 '1076' 能成立，是因為該欄位是自訂的字元欄位而非 MATNR。

9. 儲存與載入斷點；把內表下載回本機

情境：分析標準程式時好不容易設了十幾個中斷點，結果逾時登出（TIME OUT）或隔天要繼續，全部要重來。

操作步驟（電子書 6.7）（依截圖整理）：

  1. 除錯中選 Debugger → Debugger Session → Save。
  2. 在 Save Current Debug Session 視窗選 Target Medium：File（存本機檔）或 Database（存系統）；輸入 Name of Session 與 File Name。
  3. Components 勾選要存的內容：Layout、Breakpoints、Settings、Options（只要斷點就只勾 Breakpoints），按儲存。
  4. 之後重新登入、在除錯模式下執行程式，選 Debugger → Debugger Session → Load（Shift+F11），選檔案後按載入，之前的中斷點全部回來。

Classic Debugger 的對應功能是 Debugging → Sessions：輸入 Name 與 Expiration Date（有效日）後儲存；清單中可 Load、Extend by 1 Week（延長一週）或 Delete。書中示範用 /nex 關閉所有 SAP GUI 視窗並登出後再重新登入，驗證斷點確實被保留。

存成 File 可以把整組中斷點寄給同事，讓他在自己的帳號重現同一個除錯路徑；多人追同一個標準程式問題時非常實用。另外 Breakpoints 選單的 Save Debugger BPs as 可以把 Debugger 中斷點直接轉成 Session 或 External 中斷點。

把內表下載回本機（電子書 Tip）：欄位很多的內表在畫面上左右捲動很辛苦。New Debugger 的 Tables 工具右上角有 Services of the Tool 按鈕 → Save to Local File，指定資料格式（例如含分隔符號的文字）與起訖列即可下載成 Excel 可開的檔案；Classic Debugger 則有 TABLE2EXCEL 按鈕，輸入 From Line／To Line。CD260 講義的練習 4 也要求把 IT_SFLIGHT 下載到本機，並把 FM 參數下載成 SE37 的測試資料，再用這份資料單獨測試函數——這是「把正式問題帶回開發區重現」的好方法。

從 QAS／PRD 除錯時下載的內表常含個資或財務資料。存到本機前先確認公司的資料保護規定；檔案用完即刪，不要放在同步到雲端的資料夾。

10. 背景作業除錯：SM37 JDBG、SM50 與等待點

情境 A：已完成（或失敗）的背景作業——結果不對，想重跑一次看過程。

  1. SM37 查出作業，勾選該作業（只勾一筆）。
  2. 命令列輸入 JDBG Enter，進入 Debugger。
  3. 一開始停在背景處理的系統程式裡。素材說「狂按 F7 直到進入目標程式」；更聰明的做法是事先在目標程式設好 Session 中斷點，進入 Debugger 後直接按 F8。

〈sap ABAP 断点调试〉的兩個注意事項照錄：(1) 已完成與執行中（Active）的作業都可以 JDBG；(2) JDBG 等於用同一個變式把作業再執行一次，要先確認業務上能不能重跑。

  1. SM50（或 SM66 找到所在伺服器後再去該伺服器的 SM50）找到跑該程式的 BGD 工作程序。
  2. 選取後選 Administration → Program → Debugging（舊版選單為 Program/Mode → Program → Debugging）。
  3. Debugger 會在下一個可中斷的 ABAP 敘述掛上去；看 Call Stack 就知道卡在哪個 SELECT 或迴圈。

12. RFC 與外部系統呼叫：外部斷點、RFC 使用者與 SRDEBUG

情境：外部系統（MES、WMS、Java／.NET 程式、另一套 SAP）呼叫你寫的 RFC 函數，回傳結果不對；你在函數裡設 Session 中斷點，永遠不停。

為什麼不停：RFC 請求是由另一個使用者（通常是通訊用帳號，例如 RFC_USER）在另一個工作階段執行；Session 中斷點只對「你這次登入」有效。

操作步驟：外部中斷點（依截圖整理，素材〈外部断点设置〉只有兩張截圖）：

  1. SE37 開啟 RFC 函數 → 選單 Utilities → Settings。
  2. ABAP Editor 頁籤 → Debugging 子頁籤 → 「Debugging External Requests (e.g. RFC, HTTP)」區塊，User 欄位改成呼叫端使用的帳號（例：RFC_USER）。
  3. 視需要勾 Only Current Application Server（見下方陷阱）。
  4. 回到原始碼，在要停的行設 External Breakpoint（Utilities → External Breakpoints，或工具列的外部中斷點按鈕）。
  5. 請外部系統觸發呼叫；Debugger 會在你的 SAP GUI 開啟。
〈sap ABAP 断点调试〉的經驗：「使用者設錯」與「Only Current Application Server 設錯」是 RFC 中斷點不停的兩大原因。勾了 Only Current Application Server，外部中斷點只在你目前登入的那台應用伺服器有效；若 RFC 請求被負載平衡分到另一台伺服器，就不會停。多台應用伺服器的環境請不要勾，或改用 SRDEBUG 指定所有伺服器。另外，外部中斷點一律在設定中斷點的 client 開啟 Debugger，client 不同也不會停在你眼前。

SRDEBUG（電子書 6.8）（依截圖整理）：用在從外部環境（Java、C 等）呼叫 SAP RFC 時，確認資料是否正確傳入。

  1. 在 SE37 的 RFC 函數設好外部中斷點。
  2. 執行 SRDEBUG，Activate Remote ABAP Debugging 視窗中：Debuggee-Info 的 User-ID 填呼叫端帳號；Set breakpoints 選 all Appl. Servers 或 for LOGON group（例：PUBLIC）；Breakpoints Info 選 External breakpoints already set，或選 New breakpoints 直接輸入最多三個 Function Module 與三組 Class／Method。
  3. 按確認後出現 Remote ABAP Debugging 等待視窗；外部系統呼叫時會自動切到 Debugger。
  4. 要結束時在等待視窗按 Yes（Stop Debugging?）。
教材修正：不要為了除錯把 RFC 帳號改成 Dialog 類型。電子書說「先在 SU01 把外部連線用的使用者類型從 C（Communications Data）改成 A（Dialog）」。這是舊版本的權宜做法，在現行版本用外部中斷點 + 呼叫端使用者（或 SRDEBUG）就能讓 Debugger 在你的 GUI 開啟，不需要改使用者類型。把正式區的通訊帳號改成 Dialog 等於讓一個通常權限很大、密碼很少輪替的帳號可以登入 SAP GUI，是稽核必查的重大風險。唯一與使用者類型有關的情境是：在 SAP 對 SAP 的呼叫中，從呼叫端 Debugger 用 F5 直接步入 CALL FUNCTION … DESTINATION 的遠端程式碼，一般需要目標系統的 RFC 使用者可開啟對話（Dialog 類型或 Trusted RFC 的本人帳號）；這種需求請在開發／測試系統、用專用測試帳號進行。

14. SmartForms 與 SAPscript 除錯

情境：採購單列印出來某個欄位是空的，或金額格式錯，要找出是表單的哪一段程式碼（Program Lines 節點）造成的。SmartForms 的結構見 4-3 章、5-19 章。

SmartForms 操作步驟（〈ABAP Debugging & Smart Forms〉與〈sap各种场景下的DEBUG方法〉整理）（依截圖整理）：

  1. SMARTFORMS 顯示表單，在左側樹狀結構找到要除錯的 Program Lines 節點，複製其中一行程式碼備用。
  2. 選 Environment → Function Module Name，記下產生的函數名稱（形如 /1BCDWB/SF00000227，每個系統不同）。
  3. SE37 開啟該函數 → Goto → Main Program；最後一個 Include 最有用，雙擊進入。
  4. 用 Find（望遠鏡）搜尋剛才複製的程式碼（或搜尋節點名稱，例如 %CODE14），在那一行設中斷點。
  5. 重新執行列印程式或交易的預覽，Debugger 就停在表單內部。

為什麼不能直接在 SmartForms 編輯器設中斷點：Program Lines 只是節點，啟用時才被組合成一支產生的函數模組；編輯器不允許在節點上設中斷點。另一種做法是在節點裡寫 BREAK-POINT ID（第 6 節），但每想停一個地方就要改一次表單。

*&---------------------------------------------------------------*
*& 列印程式：先取得表單產生的 FM 名稱，再動態呼叫
*&  除錯技巧：在 SSF_FUNCTION_MODULE_NAME 設 Breakpoint at Function Module，
*&  就能確認「這次列印實際用的是哪一張表單」
*&---------------------------------------------------------------*
DATA lv_fm_name TYPE rs38l_fnam.

CALL FUNCTION 'SSF_FUNCTION_MODULE_NAME'
  EXPORTING
    formname           = lv_formname          "例：從輸出條件設定讀出
  IMPORTING
    fm_name            = lv_fm_name
  EXCEPTIONS
    no_form            = 1
    no_function_module = 2
    OTHERS             = 3.
IF sy-subrc <> 0.
  MESSAGE e030(zsf) WITH lv_formname.         "表單 &1 不存在或未啟用
ENDIF.

" 在這一行按 F5，就會進入 /1BCDWB/SF0000xxxx 產生的程式

〈sap各种场景下的DEBUG方法〉的經驗：在 SSF_FUNCTION_MODULE_NAME 設中斷點，從預覽進入後看 formname，可以準確知道實際使用的是哪張表單——從 NACE 看到的設定不一定就是列印時用的那張（可能被輸出程式或 BAdI 換掉）。這也是「先查標準設定、再看客製」的具體例子。

SAPscript（舊技術，見 5-18 章）：SE71 → Utilities → Activate Debugger，之後列印時會進入 SAPscript 專用的表單除錯器；更快的方法是另開一個視窗執行程式 RSTXDBUG（選單其實就是呼叫它）。原文舉 HRBEN0001 為例：不知道某個按鈕印的是哪張表單時，先執行 RSTXDBUG 再按按鈕，表單會在除錯模式下開啟，就能看到表單名稱。若要除錯列印程式的 ABAP 部分，在 WRITE_FORM 設 Breakpoint at Function Module 效率最高。

素材整理了 SAPscript 與 SmartForms 的差異：SmartForms 啟用時自動產生函數模組、SAPscript 不會；SmartForms 可以直接用 Program Lines 節點寫程式，SAPscript 只能用控制指令 PERFORM 呼叫外部子程式；SAPscript 是 client 相依、SmartForms 跨 client；SmartForms 字型可用顏色；SAPscript 每一頁的方向必須一致，SmartForms 可以不同。

15. 巨集的除錯：ABAP Byte Code (Debug Macro)

情境：舊程式大量使用 DEFINE 巨集，F5 按下去整個巨集一步就執行完，看不到裡面發生什麼事。一般高階語言的巨集無法除錯，但 ABAP 例外。

操作步驟（〈ABAP宏的调试〉）（依截圖整理）：

  1. 讓程式停在呼叫巨集的那一行（範例停在第 23 行的 BREAK-POINT，下一行開始呼叫 insert_table）。
  2. 在 Source Code 工具右側按 Services of the Tool 按鈕。
  3. 在 Editor Services 視窗展開 Services → Tool-Specific → Source Code，雙擊 ABAP Byte Code (Debug Macro)。
  4. 畫面改成以位元組碼（Byte Code）顯示，按 F5 就能逐步執行巨集展開後的每個指令；例如原始碼一行 CHECK strlen( &1 ) >= 5. 會對應到位元組碼中的 STRLEN、IF、CHECK 幾個步驟。
*&---------------------------------------------------------------*
*& 素材中的巨集（已改寫為現代語法），以及它藏著的陷阱
*&---------------------------------------------------------------*
DATA lt TYPE string_table.

DEFINE insert_table.
  CHECK strlen( &1 ) >= 5.          "← 陷阱：CHECK 失敗會離開「整個處理區塊」
  INSERT &1 INTO TABLE &2.
END-OF-DEFINITION.

START-OF-SELECTION.
  insert_table `jerry1` lt.
  insert_table `ss`     lt.         "長度 < 5 → CHECK 失敗 → START-OF-SELECTION 直接結束！
  insert_table `jerry2` lt.         "這一行永遠不會執行

*&---------------------------------------------------------------*
*& 建議改寫成方法：可以正常 F5 步入、可以設中斷點、不會誤殺整個事件
*&---------------------------------------------------------------*
CLASS lcl_util DEFINITION FINAL.
  PUBLIC SECTION.
    CLASS-METHODS add_if_long IMPORTING iv_text TYPE string
                              CHANGING  ct_tab  TYPE string_table.
ENDCLASS.
CLASS lcl_util IMPLEMENTATION.
  METHOD add_if_long.
    IF strlen( iv_text ) >= 5.
      INSERT iv_text INTO TABLE ct_tab.
    ENDIF.
  ENDMETHOD.
ENDCLASS.
巨集定義可以放在程式內（DEFINE），也可以是系統全域巨集（存在表 TRMAC，可用 SM30 維護，第 6 節的 BREAK、BREAKRC 就是這類）。〈sap ABAP 断点调试〉建議自訂除錯巨集時用 SYST 欄位當條件才有重用性；但在 S/4HANA 的新程式中，不建議再新增巨集——除錯困難、ATC 會提示、ADT 的支援也有限，用方法取代即可。

16. 進階武器速覽：Diff、Debugger Script、SLAD、表達式步進

CD260 講義（SAP TechEd 2010）把 New Debugger 的進階能力歸納成三件事：基於請求的除錯（/htid）、基於軟體層的除錯（SLAD）、自動除錯（Debugger Script）。它也解釋了 New Debugger 為什麼能做到這些——雙程序架構：

  • Classic Debugger 與被除錯程式在同一個內部工作階段，畫面直接取代被除錯程式的畫面，所以 Conversion Exit／Field Exit 無法除錯、不能用 F1／F4、清單輸出會被干擾。
  • New Debugger 在另一個外部工作階段執行（輸入 /h 後會開新視窗）：被除錯程式的畫面仍看得到；除錯結束後 Debugger 保持開啟但處於非啟用狀態，設定、變數、中斷點都保留；在被除錯程式的視窗輸入 /hx 才會關閉。
工具用在哪種情境講義範例
Diff 工具兩個「看起來一樣」的內表／結構／字串為什麼 <>練習 5：itab_copy = itab 之後 IF itab_copy = itab 卻不成立；用 Diff 找差異，再對 ITAB 設 Watchpoint 找出是誰改的
表達式步進（Step Size）複雜的 IF a AND ( b OR c )，到底是哪個條件不成立啟用後逐一經過每個條件並顯示計算結果
SLAD（Layer Aware Debugging）在框架（ALV、Web Dynpro、Gateway）底下只想看自己那一層練習 6：用層 ZSALV 與 ZS_ST22 找出 ST22 呼叫 ALV 的所有位置；按 Next Object Set 跳下一層
Debugger Script（SAS）要記錄「所有 SELECT／AUTHORITY-CHECK」、或自動略過某個 FM練習 7：寫腳本追蹤程式中所有 SELECT 與權限檢查；讓 Z_TSTECHED05_SFLIGHT_OUTPUT 被跳過不輸出

〈sap ABAP 断点调试〉的作者說 Script「一般很少需要用到」，但示範了一個最實用的入門腳本：在 sy-subrc 不為 0 時自動停下並記錄位置。以下是精簡骨架（實際請在 Debugger 的 Script 頁籤用精靈產生，類別與方法名稱以精靈為準；完整 API 見 5-4 章第 19 節）：

17. ADT（Eclipse）除錯

情境：S/4HANA 的新開發（類別、CDS、RAP、Console App）都在 ADT 中進行，需要在 Eclipse 內除錯。ADT 的整體介紹見 5-5 章（BC404）。

基本操作（SAP Learning〈Debugging an ABAP Program〉）：

  • 設中斷點：在編輯器左邊界右鍵 → Toggle Breakpoint，或雙擊左邊界。程式必須先啟用才能設。
  • 中斷點是使用者層級且持續存在的：登出 ADT 再登入仍有效。不想停時要刪除（Toggle）或在右鍵選單停用。這點和 SAP GUI 的 Session 中斷點不同，它的性質接近 External 中斷點，因此 ADT 設的中斷點也攔得到 Fiori、OData、RFC 請求。
  • 中斷點觸發時，ADT 會詢問是否切換到 Debug 視角（Perspective），可勾 Remember my decision。
  • F5 Step Into、F6 Step Over、F7 Step Return、F8 Resume。out->write( ) 不是 ABAP 敘述而是一段可重用程式碼，F5 會進到它裡面，應該用 F6 跳過。
  • Breakpoints 檢視的下拉選單可建立 Statement Breakpoint（例如輸入 EXIT，所有 EXIT 敘述都停）與 Exception Breakpoint（例外被引發就停，不論是否被處理）。
  • 條件式中斷點：在 Breakpoints 檢視選取中斷點，於 Condition 欄位輸入條件後按 Enter，例如 sy-index > 20 會略過 DO 迴圈的前 20 圈；有條件的中斷點圖示下方會多一個小尾巴。
  • Watchpoint：在 Variables 檢視對變數右鍵 → Set Watchpoint。
  • 改值（依權限）：簡單變數右鍵 Change Value…；內表在 ABAP Internal Table (Debugger) 檢視右鍵有 Change Value…、Insert Row…、Delete Selected Rows…、Delete Rows…（指定起訖列）。
*&---------------------------------------------------------------*
*& ADT 練習（改寫自 SAP Learning 的貸款試算範例，已精簡）
*&  類別須實作 IF_OO_ADT_CLASSRUN；F9 執行為 Console App
*&  ① 在 loan_remaining = loan_total 設中斷點
*&  ② 對 loan_remaining 設 Watchpoint，F8 觀察每月遞減
*&  ③ 對內圈中斷點加條件 months_counter > 20
*&  ④ Statement Breakpoint：EXIT
*&---------------------------------------------------------------*
CLASS zcl_00_debug DEFINITION PUBLIC FINAL CREATE PUBLIC.
  PUBLIC SECTION.
    INTERFACES if_oo_adt_classrun.
ENDCLASS.

CLASS zcl_00_debug IMPLEMENTATION.
  METHOD if_oo_adt_classrun~main.
    TYPES t_amount TYPE p LENGTH 8 DECIMALS 2.
    CONSTANTS lc_loan_total    TYPE t_amount VALUE '50000.00'.
    CONSTANTS lc_rate_pct      TYPE t_amount VALUE '2.0'.
    CONSTANTS lc_payment_month TYPE t_amount VALUE '1000.00'.

    DATA lt_plan TYPE string_table.
    DATA(loan_remaining) = lc_loan_total.         "① 中斷點
    DATA(months_counter) = 0.
    DATA interest_total TYPE t_amount.

    WHILE loan_remaining > 0.
      months_counter = months_counter + 1.        "③ 條件 months_counter > 20
      DATA(interest_month) = CONV t_amount( loan_remaining * lc_rate_pct / 100 / 12 ).
      interest_total = interest_total + interest_month.
      loan_remaining = loan_remaining - ( lc_payment_month - interest_month ).  "② Watchpoint
      APPEND |Month { months_counter }: interest { interest_month }, remaining { loan_remaining }|
        TO lt_plan.
    ENDWHILE.

    out->write( |Total months: { months_counter }, total interest: { interest_total }| ).  "用 F6
    out->write( name = `Repayment plan` data = lt_plan ).
  ENDMETHOD.
ENDCLASS.

SAP GUI 與 ADT 的中斷點是兩套：在 ADT 設的中斷點，SAP GUI 的 Debugger 不一定看得到，反之亦然。若 ADT 的中斷點要攔「另一個使用者」的請求（例如 RFC 帳號），可在 ADT 專案的 Properties → ABAP Development → Debug 設定中斷點生效的使用者。Debugger Script、SLAD 在 ADT 沒有對等功能，需要時回 SAP GUI（5-4 章第 20 節）。

18. S/4HANA Cloud：Custom Logic 的 ADT 除錯與追蹤

情境：S/4HANA Cloud（3-system landscape、Developer Extensibility）中，Key User 用 Fiori App「Custom Logic」寫了 BAdI 實作，現在要除錯。雲端沒有 SAP GUI、沒有 /h、沒有 SE38，唯一的工具就是 ADT。

操作步驟（SAP Community 部落格〈Debugging custom logic using ADT in SAP S4 Hana Cloud〉）（依截圖整理）：

  1. 找技術名稱：在 Fiori「Custom Logic」App 搜尋（範例關鍵字 Order Operation），滑鼠移到實作上會以提示顯示技術實作名稱；或用齒輪圖示個人化清單，加入 Implementation ID 欄位後複製。沒有這個 ID，很難在系統裡找到自訂邏輯實際放在哪裡。
  2. 在 ADT 找到實作類別：在已連線的專案中 Search 該 ID，結果同時列出實作與實作類別；開啟實作後點 Implementing Class 連結，自訂邏輯位於類別中「payload」註解之間。
  3. 設中斷點：雙擊左邊界。邏輯在迴圈中、不想每圈都停時，右鍵 → Breakpoint Properties… 加條件（範例：只在第一筆停）。
  4. 觸發：用會呼叫該 BAdI 的 Fiori App 正常操作（範例：Change Production Order 開啟工單編輯）；Fiori 會停在等待狀態，ADT 在工作列閃爍，切過去並同意切換到 Debug 視角。
  5. 分析：看 Variables（範例展開 MFGORDEROPERATIONS_CHANGED 內表）與呼叫堆疊，按 Resume 讓 Fiori 繼續完成。
  6. 追蹤效能：切到 ABAP Profiling 視角 → ABAP Trace Requests 檢視 → 在租戶上右鍵 Create Trace Request…（範例：追蹤自己帳號的所有 HTTP 請求，標題 MyFirstTraceFile；參數頁可選 Custom Statements）→ 在 Fiori 重做一次操作 → 到 ABAP Traces 檢視 Refresh，開啟 Overview，再看 Hit List 並以實作類別前綴過濾。
S/4HANA Cloud（ABAP Cloud）除錯的限制，動手前要知道：
  • 沒有 SAP GUI：本章第 3～16 節的 /h、捷徑檔、SM37 JDBG、SM13、SRDEBUG、Debugger Script、SLAD 全部不適用。
  • 一般而言只能除錯自己的（客戶命名空間）程式碼；SAP 交付的程式與已發布 API 內部是黑盒子，步入時會被略過或看不到原始碼。問題若在 SAP 標準，請走 SAP 支援單，不是自己追到底。
  • 除錯通常在開發（或測試）租戶進行；正式租戶能否除錯、能否改變數值，取決於 SAP 版本與使用者被指派的業務目錄權限，請以 SAP Help「ABAP Development User Guide → Using Troubleshooting Tools」為準，不要假設可以。
  • Key User 在 Fiori 寫的 Custom Logic 也是 ABAP Cloud 語法的子集，除錯方式相同，但修改仍應回到 Custom Logic App 進行，而不是直接在 ADT 改產生的類別。

  • 會留下紀錄：Debugger 中修改欄位內容會寫入系統日誌 SM21（含使用者、程式、欄位），稽核一查就知道。

  • 正規替代：主檔、交易資料用標準交易或 BAPI 修正；自訂表用 SE54 產生維護畫面、以 SM30 維護；一次性資料修正寫有傳輸、有審核、有測試的修正程式；緊急情況走 Firefighter（GRC）等受控的緊急權限流程，事後覆核。細節見 6-2 章。

  5. 在 IN UPDATE TASK 函數中設的中斷點為什麼不停？操作上要在哪一個時點、打開哪一個設定？

參考答案要點：

  1. 建立文字檔，內容分三行 [FUNCTION]、Command=/H、Type=SystemCommand（可加 Title=Debugger），拖放到對話框上；或用 SAP GUI 產生 System command 類型的 .sap 捷徑並雙擊（第 4 節）。
  2. RFC 由另一個使用者在另一個工作階段執行，Session 中斷點只對自己的登入有效。做法：SE37 → Utilities → Settings → Debugging 的 User 改為 RFC_MES，設 External 中斷點；或用 SRDEBUG。常見不停原因：使用者設錯、勾了 Only Current Application Server 而請求被分到別台伺服器（另有 client 不同、超過 2 小時效期）。不需要把 RFC 帳號改成 Dialog（第 12 節）。
  3. TRMAC 中 BREAKRC 的內容是 MESSAGE A895(CJ)，會以 A 訊息終止交易，不是中斷點。應使用條件式中斷點（條件 SY-SUBRC <> 0）、Watchpoint 條件、ASSERT ID … CONDITION sy-subrc = 0，或 Debugger Script（第 6、8、16 節）。
  4. Skip 欄位輸入 669；條件式中斷點 SY-TABIX = 670；對 SY-TABIX 設條件 Watchpoint；或以關鍵值（列舉）作條件（第 8 節）。
  5. 更新函數在 COMMIT WORK 後由更新工作程序執行。在 COMMIT WORK 之前進入 Debugger，Settings → Display/Change Debugger Settings 勾 Update Debugging，F8 後會開新視窗進入更新程序（第 11 節）。
  6. JDBG 等於用同一變式再跑一次、會真的更新資料庫；除錯時 SY-BATCH = X 但實際在對話程序中，依批次判斷的邏輯（例如寫檔路徑、權限）可能不同（第 10 節）。
  7. SMARTFORMS → Environment → Function Module Name 取得產生的 FM → SE37 → Goto → Main Program → 最後一個 Include → Find 節點程式碼 → 設中斷點 → 重新預覽。在 SSF_FUNCTION_MODULE_NAME 設中斷點看 formname 即可確認實際表單（第 14 節）。
  8. ADT 中斷點是使用者層級、持續有效到刪除為止，能攔到 Fiori／OData／RFC；Session 中斷點登出即消失、只攔自己 GUI 發起的請求。S/4HANA Cloud 先在 Custom Logic App 取得 Implementation ID，再到 ADT 搜尋實作類別（第 17、18 節）。
  9. 需要 S_DEVELOP（DEBUG / 02），正式區不應授予；改值寫入 SM21；繞過商業檢查與變更文件，屬內控缺失；應改用標準交易／BAPI、SM30 維護畫面、經審核與傳輸的修正程式或 Firefighter 流程（第 19 節）。
  10. 先懷疑 HANA 無預設排序：取第一筆的邏輯沒有 ORDER BY／SORT，成本估算的 H 與 E 兩種角度交替被抓到；其次檢查是否在除錯時改過值、SY-BATCH 或日期條件是否不同（第 2、19 節）。
