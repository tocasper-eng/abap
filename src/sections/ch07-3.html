2. 封裝：用 getter／setter 守住帳戶資料（5.1～5.4、5.7）

觀念。封裝（Encapsulation）是把資料藏在類別裡（PRIVATE），外界只能透過公開方法讀寫，類別因此可以在 setter 裡把關。書中的 ZCL_ACCOUNT_BALANCE 有兩個屬性 MV_ACCOUNT_NUMBER（帳號）、MV_ACCOUNT_BALANCE（餘額），以及四個存取方法：

  • 5.1 get_account_number、5.3 get_account_balance：單純回傳屬性。
  • 5.2 set_account_number：先 SHIFT … LEFT DELETING LEADING '0' 去掉前導零，再用 CP 'CA277*' 檢查是否以 CA277 開頭；不符合就把帳號設成 '0000000000' 當作「無效」記號。
  • 5.4 set_account_balance：直接指定，沒有任何驗證。
  • 5.7 只是一行被註解掉的 lo_account_balance->account_number = '12111111232'，說明「如果屬性是 PUBLIC，外界就能直接改寫、繞過 setter 的驗證」——這正是封裝要防止的事。

範例（改寫後） （依範例呼叫方式重建）：先建一個例外類別（SE24 建 ZCX_ACCOUNT_ERROR，超類別 CX_STATIC_CHECK），用來取代「魔術值 '0000000000'」。

CLASS zcl_account_balance IMPLEMENTATION.
  METHOD get_account_number.                            " 5.1
    rv_account_number = mv_account_number.
  ENDMETHOD.

  METHOD set_account_number.                            " 5.2
    " shift_left( sub = ) 會把左側連續出現的 '0' 全部去掉，等同 SHIFT ... DELETING LEADING '0'
    DATA(lv_stripped) = shift_left( val = CONV string( iv_account_number ) sub = `0` ).
    IF lv_stripped NP 'CA277*'.
      RAISE EXCEPTION TYPE zcx_account_error
        EXPORTING iv_text = |帳號 { iv_account_number } 不是 CA277 開頭，拒絕設定|.
    ENDIF.
    mv_account_number = iv_account_number.
  ENDMETHOD.

  METHOD get_account_balance.                           " 5.3
    rv_account_balance = mv_account_balance.
  ENDMETHOD.

  METHOD set_account_balance.                           " 5.4：補上驗證
    IF iv_account_balance < 0.
      RAISE EXCEPTION TYPE zcx_account_error EXPORTING iv_text = `期初餘額不可為負數`.
    ENDIF.
    mv_account_balance = iv_account_balance.
  ENDMETHOD.

  METHOD assert_account.
    IF mv_account_number IS INITIAL.
      RAISE EXCEPTION TYPE zcx_account_error EXPORTING iv_text = `尚未設定有效帳號`.
    ENDIF.
  ENDMETHOD.

  METHOD deposit.   " 5.5，見第 3 節
    assert_account( ).
    IF iv_deposit_amount <= 0.
      RAISE EXCEPTION TYPE zcx_account_error EXPORTING iv_text = `存款金額必須大於 0`.
    ENDIF.
    mv_account_balance = mv_account_balance + iv_deposit_amount.   " 7.54+ 可寫 mv_account_balance += iv_deposit_amount.
    rv_account_balance = mv_account_balance.
  ENDMETHOD.

  METHOD withdraw.  " 5.6，見第 3 節
    assert_account( ).
    IF iv_withdraw_amount <= 0.
      RAISE EXCEPTION TYPE zcx_account_error EXPORTING iv_text = `提款金額必須大於 0`.
    ENDIF.
    IF iv_withdraw_amount > mv_account_balance.
      RAISE EXCEPTION TYPE zcx_account_error
        EXPORTING iv_text = |餘額 { mv_account_balance } 不足以提領 { iv_withdraw_amount }|.
    ENDIF.
    mv_account_balance = mv_account_balance - iv_withdraw_amount.
    rv_account_balance = mv_account_balance.
  ENDMETHOD.
ENDCLASS.
版本門檻：計算指派 +=、-= 是 ABAP 7.54（S/4HANA 1909）才有的語法。上面 deposit 只在註解中示範；1809（7.53）請一律寫成 a = a + b，本章程式碼都照這個寫法。

與原範例的差異。

  • 原 5.2 驗證失敗時把帳號設成 '0000000000'，呼叫端完全不知道失敗了；改寫後丟出類別式例外，呼叫端必須處理（CX_STATIC_CHECK 會被語法檢查強制 CATCH 或往上宣告）。
  • 原 5.4 可以把餘額設成負數；改寫補上檢查。書中 5.4 的用意是「最單純的 setter」，但實務上 setter 的存在意義就是驗證，沒有驗證的 setter 跟 PUBLIC 屬性差不多。
  • CP 比對不分大小寫（除非在樣式中用 # 跳脫），所以 'ca277…' 也會通過；若業務規則要求大寫，請先 to_upper( ) 或改用 matches( val = … pcre = … )（PCRE 需 7.55，1809 用 regex =）。
  • 原範例屬性型別：帳號用資料元素 STRING10、餘額用 DMBTR（金額，CURR 13,2）。改寫把帳號型別定義在類別的 TYPES 裡，讓類別自成一體。
  • 5.7 的註解「Public attribute could be access directly」文法有誤（應為 accessed），重點是觀念：屬性預設放 PRIVATE；真的要讓外界讀，就用 PUBLIC SECTION … DATA … READ-ONLY，外界可讀不可寫。
實務提醒：DMBTR 是「本位幣金額」，單獨存在時沒有幣別。真正的帳戶類別至少要多一個 WAERS 屬性，並在 SE11 的結構中把金額欄位參照到幣別欄位，否則畫面輸出與 ALV 的小數位會出錯（例如日圓、台幣沒有小數）。

3. 存款與提款：把業務規則放進方法（5.5、5.6）

觀念。封裝不只是「藏資料」，更是「把規則放在資料旁邊」。書中 5.5 deposit 規定帳號有效（不是 '0000000000'）且金額 > 0 才入帳；5.6 withdraw 規定餘額 ≥ 提款額才扣款。改寫後的完整方法已列在第 2 節的類別中，這裡說明原範例的三個邏輯問題：

原範例問題改寫
5.5 條件不成立時什麼都不做RETURNING 參數保持初始值 0，呼叫端拿到「餘額 0」會誤以為帳戶被清空丟 ZCX_ACCOUNT_ERROR，訊息說明原因

4. 帳戶測試程式：從 CALL METHOD 到函數式呼叫（5.8）

觀念。5.8 ZREP_CLS_27_1 是帳戶類別的測試程式，作者刻意在同一支程式展示三種呼叫方式：① CALL METHOD obj->m EXPORTING … RECEIVING …、② CALL METHOD obj->m( p )、③ 函數式 x = obj->m( p )（註解寫「New format of calling method」）。

REPORT zrep_cls_27_1.

PARAMETERS: p_numbr TYPE zcl_account_balance=>ty_account_number OBLIGATORY,
            p_blnce TYPE dmbtr,
            p_dpst  TYPE dmbtr,
            p_wdrw  TYPE dmbtr.

START-OF-SELECTION.
  DATA(go_account) = NEW zcl_account_balance( ).
  DATA(go_out)     = cl_demo_output=>new( ).

  TRY.
      go_account->set_account_number( p_numbr ).
      go_account->set_account_balance( p_blnce ).
      go_out->write( |帳號 { go_account->get_account_number( ) }，期初餘額 { go_account->get_account_balance( ) }| ).

      DATA(gv_balance) = go_account->deposit( p_dpst ).
      go_out->write( |存入 { p_dpst } 元，餘額 { gv_balance }| ).

      gv_balance = go_account->withdraw( p_wdrw ).
      go_out->write( |提領 { p_wdrw } 元，餘額 { gv_balance }| ).
    CATCH zcx_account_error INTO DATA(gx_error).
      go_out->write( |錯誤：{ gx_error->get_text( ) }| ).
  ENDTRY.

  go_out->display( ).

與原範例的差異。

  • CREATE OBJECT: go_account_balance. → DATA(go_account) = NEW zcl_account_balance( )。
  • 所有 CALL METHOD 改為函數式呼叫；RECEIVING 改為直接指派回傳值。原範例第二種寫法 CALL METHOD obj->m( p ). 是「新舊混搭」，語法雖然合法但兩頭不討好，不要用。
  • 原程式把 p_numbr = go_account_balance->get_account_number( ) 寫回選擇畫面參數——若帳號驗證失敗，輸出的就是 0000000000，而且第一行 WRITE 印出的 p_blnce 是設定之前的輸入值，不是類別裡的餘額。改寫一律從物件取值。
  • 原程式先呼叫 deposit 拿到回傳值，下一行又用 get_account_balance 覆蓋，等於白接；改寫直接用回傳值。
  • WRITE 清單改為 CL_DEMO_OUTPUT（示範用，正式程式請用 CL_SALV_TABLE 或訊息）。PARAMETERS 型別直接參照類別的公開型別 zcl_account_balance=>ty_account_number，類別改長度時畫面跟著變。
CL_DEMO_OUTPUT 是 SAP 的示範用類別，官方明言不要用在正式產品程式；本部（第七部）為了貼近原書的 WRITE 輸出，範例統一用它，搬到正式程式時請換成 SALV 或應用程式日誌（BAL）。

設計評論：這個介面讓一個方法同時帶 es_sflight 與 es_sflights 兩個輸出，而每個實作只填其中一個——呼叫端必須知道「現在是哪個實作」才知道該讀哪個參數，這其實抵銷了多型的好處。較好的設計是讓介面回傳雙方共用的抽象結果（例如一個描述字串表，或各自獨立的兩個介面）。這正是介面隔離原則（ISP）要解決的問題，見 7-4 章。

練習與自我檢核

  1. 範例 5.2 的 setter 驗證失敗時把帳號設成 '0000000000'，這樣做有什麼問題？現代寫法怎麼處理？
    參考答案要點：呼叫端不知道失敗、無效值與合法值混在同一個欄位（魔術值）；改丟類別式例外（CX_STATIC_CHECK 子類），強迫呼叫端 TRY…CATCH。
  2. 請用一句話區分 Overriding 與 Overloading，並說明 ABAP 支援哪一個。
    參考答案要點：Overriding＝子類別重新定義父類別方法（ABAP 的 REDEFINITION）；Overloading＝同一類別同名不同參數，ABAP 不支援。原書第 147 頁英文對調（勘誤第 3 條）。
  3. 範例 5.10 把 CALL METHOD super->set_material_id 註解掉，自己再寫一次指派。會有什麼風險？
    參考答案要點：複製父類別邏輯；父類別日後加驗證或記錄，子類別不會跟著更新。應呼叫 super->set_material_id( ) 再加子類別專屬邏輯。
  4. 若依原書把 zcl_pear 繼承自 zcl_apple，下列哪個轉型會「錯誤地成功」？ DATA(lo_a) = CAST zcl_apple( lo_food )（lo_food 指向梨子物件）
    參考答案要點：會成功，因為梨子被定義成蘋果的子類別；修正為繼承 zcl_fruit 後才會正確丟 CX_SY_MOVE_CAST_ERROR（勘誤第 4 條，5.14 也有同樣錯誤）。
  5. 範例 5.32 第 5 段，go_civi_soldier->self_introduce( ) 印出「我是花弧」，這是多型的效果嗎？
    參考答案要點：不是。self_introduce 沒有被重定義，印出花弧是因為第 4 段 setup_profile 改了資料；多型體現在 show_capability 執行花木蘭的實作。原註解「重新聲明過的自我介紹」不正確。
  6. 為什麼 go_civi_soldier->make_up( ) 是語法錯誤，而不是執行期錯誤？
    參考答案要點：能呼叫哪些方法由參考變數的靜態型別（zcl_beichao_civilian）在編譯時決定；執行哪個實作才由動態型別決定。
  7. DATA(lo) = NEW zcl_sub_matl_raw( 'RAW001' ). 之後 lo 的靜態型別是什麼？如何得到父類別型別的變數？
    參考答案要點：zcl_sub_matl_raw；明確 DATA lo TYPE REF TO zcl_super_matl，或 DATA(lo) = CAST zcl_super_matl( NEW zcl_sub_matl_raw( 'RAW001' ) )。
  8. 範例 5.33 的 SELECT SINGLE … WHERE connid = @iv_flight_no 在 HANA 上會出什麼問題？請改寫。
    參考答案要點：CONNID 非完整主鍵，HANA 無預設排序，每次可能回不同航空公司／日期的資料。補 CARRID，並用 ORDER BY fldate DESCENDING ＋ INTO TABLE … UP TO 1 ROWS 明確決定取哪一筆。
  9. 5.36 在方法呼叫後檢查 sy-subrc 為什麼不可靠？
    參考答案要點：類別方法呼叫不設定 sy-subrc（除非用傳統 EXCEPTIONS），讀到的是方法內部最後一個敘述留下的值；應以輸出參數、回傳值或例外傳達結果。
