2. 共用骨架：BAPI 呼叫與 BAPIRET2 判斷

五個案例有四個要呼叫「寫入型」BAPI 或函數。原程式各寫各的判斷，而且各有漏洞：案例二先 COMMIT 才看回傳、只判斷 TYPE = 'E'；案例三只看「有沒有拿到請購單號」；案例四在沒有 EXCEPTIONS 的函數後面檢查 sy-subrc。先把判斷規則收斂成一個 local class，後面每個案例都用它。

CLASS lcl_bapi DEFINITION FINAL.
  PUBLIC SECTION.
    "BAPIRET2 中出現 E（錯誤）或 A（中止）就算失敗；W／I／S 不算
    CLASS-METHODS has_error
      IMPORTING it_return      TYPE bapiret2_t
      RETURNING VALUE(rv_error) TYPE abap_bool.
    CLASS-METHODS first_error
      IMPORTING it_return     TYPE bapiret2_t
      RETURNING VALUE(rv_text) TYPE string.
    "依回傳決定 COMMIT 或 ROLLBACK；回傳 abap_true 代表真的寫進資料庫
    CLASS-METHODS finish
      IMPORTING it_return  TYPE bapiret2_t
                iv_testrun TYPE abap_bool DEFAULT abap_false
      RETURNING VALUE(rv_ok) TYPE abap_bool.
ENDCLASS.

CLASS lcl_bapi IMPLEMENTATION.
  METHOD has_error.
    rv_error = xsdbool( line_exists( it_return[ type = 'E' ] )
                     OR line_exists( it_return[ type = 'A' ] ) ).
  ENDMETHOD.

  METHOD first_error.
    LOOP AT it_return INTO DATA(ls_ret) WHERE type CA 'EA'.
      rv_text = |{ ls_ret-id }/{ ls_ret-number }: { ls_ret-message }|.
      RETURN.
    ENDLOOP.
  ENDMETHOD.

  METHOD finish.
    IF has_error( it_return ) = abap_true OR iv_testrun = abap_true.
      CALL FUNCTION 'BAPI_TRANSACTION_ROLLBACK'.
      rv_ok = abap_false.
      RETURN.
    ENDIF.
    DATA ls_commit TYPE bapiret2.
    CALL FUNCTION 'BAPI_TRANSACTION_COMMIT'
      EXPORTING
        wait   = abap_true          "等更新任務寫完再往下，後續才讀得到新資料
      IMPORTING
        return = ls_commit.
    rv_ok = xsdbool( ls_commit-type NA 'EA' ).
  ENDMETHOD.
ENDCLASS.
BAPIRET2 判斷三原則：（1）看 TYPE 是 E 或 A，不要只看 E，A（abort）更嚴重；（2）先判斷、再決定 COMMIT 或 ROLLBACK，不能先 COMMIT 再看結果——BAPI 失敗時通常不會自己寫庫，但同一個 LUW 裡前面成功的呼叫會被一起提交；（3）有 RETURN 表格的 BAPI 就看表格，不要用「有沒有拿到單號」或 sy-subrc 代替。BAPI 的基本觀念請見 4-1 章 RFC 與 BAPI。

3. 案例一：用 RFC 函數讀即時庫存——情境與架構

業務情境

公司的外部系統（講義稱 EEPCLOUD，一套以 .NET 撰寫的雲端應用）需要查詢 SAP 的即時庫存。做法是在 SAP 寫一支遠端啟用的函數 ZMATERIAL_STOCK_LIST，外部用 SAP .NET Connector（NCo）呼叫，把結果存進 SQL Server 的暫存表 eep_MARD（欄位 MATNR、WERKS、LGORT、LABST，主鍵為前三者）。講義註記此片段「已於 20220817 成功」。

輸入與輸出

項目原設計說明
介面只有一個 TABLES 參數 T_MARD STRUCTURE ZMARD，同時當輸入也當輸出呼叫端填 MATNR、WERKS（可填 LGORT），函數清空後回填彙總結果
資料來源MARD（儲存地點庫存）以 FOR ALL ENTRIES 依物料＋工廠讀取
輸出依 MATNR＋WERKS 以 COLLECT 加總 LABST（非限制使用庫存）LGORT 欄位回傳時是空白——雖然輸入可以填儲位，但彙總時被丟掉
測試方式SE37 單一測試：在 T_MARD 表格輸入 MATNR、WERKS → 返回 → 執行 → 點結果看即時庫存；SE38 寫測試程式呼叫並 WRITE 輸出（依講義步驟整理）

程式架構（現代版）

  1. 介面改用明確的 IMPORTING／EXPORTING 表格類型（RFC 函數一律傳值），輸入鍵與輸出結果分開。
  2. 輸入為空時直接回傳空表——這是原程式最嚴重的漏洞（見 §4）。
  3. 去重 → 讀 MARD → 依「物料＋工廠」彙總（要保留儲位就依「物料＋工廠＋儲位」）。
  4. 函數屬性頁勾選 Remote-Enabled Module，並在 SE37 標記為「Released」之前先談好介面版本管理，外部系統一旦串上就很難改參數。

4. 案例一：關鍵段落現代改寫與原程式問題

函數本體改寫如下。介面中的 ZMM_T_STOCK_KEY（行型含 MATNR、WERKS、LGORT）與 ZMM_T_STOCK_SUM（MATNR、WERKS、LGORT、LABST）是在 SE11 自建的表格類型。

FUNCTION z_material_stock_list.
*"----------------------------------------------------------------------
*"*"Remote-Enabled Function Module
*"  IMPORTING
*"     VALUE(IT_KEY)      TYPE  ZMM_T_STOCK_KEY
*"     VALUE(IV_BY_LGORT) TYPE  ABAP_BOOL DEFAULT ABAP_FALSE
*"  EXPORTING
*"     VALUE(ET_STOCK)    TYPE  ZMM_T_STOCK_SUM
*"----------------------------------------------------------------------
  "空輸入直接返回：FOR ALL ENTRIES 遇到空表會「忽略整個 WHERE」，變成全表讀取
  IF it_key IS INITIAL.
    RETURN.
  ENDIF.

  DATA(lt_key) = it_key.
  SORT lt_key BY matnr werks.
  DELETE ADJACENT DUPLICATES FROM lt_key COMPARING matnr werks.

  SELECT matnr, werks, lgort, labst
    FROM mard
    FOR ALL ENTRIES IN @lt_key
    WHERE matnr = @lt_key-matnr
      AND werks = @lt_key-werks
    INTO TABLE @DATA(lt_mard).

  "呼叫端有指定儲位的物料，只保留該儲位
  LOOP AT it_key INTO DATA(ls_key) WHERE lgort IS NOT INITIAL.
    DELETE lt_mard WHERE matnr = ls_key-matnr
                     AND werks = ls_key-werks
                     AND lgort <> ls_key-lgort.
  ENDLOOP.

  LOOP AT lt_mard INTO DATA(ls_mard)
       GROUP BY ( matnr = ls_mard-matnr
                  werks = ls_mard-werks
                  lgort = COND #( WHEN iv_by_lgort = abap_true THEN ls_mard-lgort ) )
       INTO DATA(ls_grp).
    APPEND VALUE #( matnr = ls_grp-matnr
                    werks = ls_grp-werks
                    lgort = ls_grp-lgort
                    labst = REDUCE #( INIT s = CONV labst( 0 )
                                      FOR m IN GROUP ls_grp
                                      NEXT s = s + m-labst ) ) TO et_stock.
  ENDLOOP.
ENDFUNCTION.

原程式問題

問題後果修正
沒有檢查 T_MARD 是否為空就 FOR ALL ENTRIES空表 = 讀整張 MARD。講義的 .NET 片段先 Invoke 一次再填參數，註解寫「這裏會等好幾秒」「取得的 T_MARD 就是 3 萬多筆的資料表」——正是這個漏洞的症狀空輸入直接 RETURN；.NET 端先 SetValue 再 Invoke，只呼叫一次
TABLES 參數兼作輸入與輸出，函數內 CLEAR t_mard[]呼叫端的輸入被覆蓋，除錯困難IMPORTING／EXPORTING 分開
接受 LGORT 輸入卻不使用、輸出 LGORT 永遠空白外部系統以為拿到的是儲位庫存，其實是工廠總量；eep_MARD 以 MATNR＋WERKS＋LGORT 當主鍵，全部 LGORT 空白時照樣成立，不會報錯明確提供 iv_by_lgort 選項
LIKE mard OCCURS 0 WITH HEADER LINE、SELECT *、COLLECT讀了 MARD 全部欄位，只用 4 個明列欄位＋GROUP BY／REDUCE
只回傳 LABST品檢庫存（INSME）、凍結庫存（SPEME）都沒算，業務說「系統有貨卻說沒有」需求訪談時先定義「可用庫存」的口徑

上線注意

  • 先找標準：標準已有 BAPI_MATERIAL_AVAILABILITY（依 ATP 檢查規則回傳可用量，等同 CO09 的角度）與 BAPI_MATERIAL_STOCK_REQ_LIST（庫存／需求清單，等同 MD04）。講義沒有用這兩支；若外部系統要的是「可承諾量」而非帳面庫存，應優先評估它們（參數請以 SE37 確認，S/4HANA 的物料號欄位多有 *_LONG 版本）。
  • S/4HANA 的 MARD 是由物料文件 MATDOC 即時彙總的相容性視圖（proxy），大量頻繁查詢的成本比 ECC 高；外部系統每幾秒輪詢一次就該改成批次同步或只查異動物料。
  • RFC 使用者要給最小權限（S_RFC 限定函數群組），外部系統的連線帳密不要寫死在程式裡。

5. 案例二：Excel 批次更新前置時間——情境與暫存表

業務情境

採購每季跟供應商重談交期後，要把幾百顆物料的「計畫交貨時間」（MARC-PLIFZ，MM02 MRP 2 視圖）一次更新。講義的做法分三段：Excel → 自建暫存表 ZMARC_PLIFZ → 用 BAPI 寫回 MARC，最後用 SM30 維護畫面顯示匯入結果，「不必一行一行的寫 ALV」。

講義步驟 （依講義步驟整理）

  1. 2-01 在 SE11 建暫存表 ZMARC_PLIFZ（MANDT、NUM、MATNR、PLIFZ）。
  2. 2-02 產生表格維護畫面：講義由 SE80 進函數群組 ZIT03 的畫面 0001（產生器是 SE54／SE11「表格維護產生器」）。
  3. 2-03 確認 SM30 看得到畫面。
  4. 2-04 寫主程式 ZALSM_EXCEL_TO_INTERNAL_TABLE；2-05 用 Excel 整理資料（第 1 列欄名 NUM_COL、MATNR、PLIFZ，第 2 列起為資料，例如「1、MAT-A、123」「2、MMC-252、43」）。

原程式寫法問題改法

                      purch_org     = p_ekorg

原程式問題

  • 以 IF LV_BANFN IS NOT INITIAL 判斷成功：有警告以外的錯誤時 BAPI 不會給號碼，這樣判斷大致可行，但訊息全被丟掉——失敗時使用者只看到空白畫面。應該看 RETURN，並把錯誤顯示出來。
  • 數量 10、交貨日「今天」寫死：今天的交貨日在 MRP 裡會直接變成過期需求。

12. 案例四：資料擷取改寫——多筆確認與排序

一個採購項目可以有多筆確認（ETENS 1、2、3…）。原程式先 READ TABLE IT_EKES WITH KEY EBELN EBELP 取「第一筆」放進主列，再用另一個巢狀迴圈把 ETENS <> 主列那筆的其他確認 APPEND 到 IT_ZMMB0021_EXTRA、最後併回主表（註解還寫著「會進入死循環 盪掉」——這正是在 LOOP 同一張表時 APPEND 的後果，才改成先放 EXTRA 表）。問題是：取「第一筆」之前 IT_EKES 沒有排序（SORT 寫在後面），HANA 回傳順序不固定，主列今天是 ETENS 1、明天可能是 2。現代寫法直接用左外連接一次展開，每筆確認一列：

METHOD select.
  SELECT k~ebeln, p~ebelp, p~werks, p~lgort, p~matnr, p~matkl, p~mtart,
         p~menge, p~meins, p~elikz, p~insmk, p~kzabs, p~berid,
         k~bstyp, k~lifnr, l~name1, k~ekorg, k~ekgrp, k~aedat, k~bedat, k~bukrs,
         e~etens,
         e~eindt AS ekes_eindt,
         e~menge AS ekes_menge,
         e~dabmg AS ekes_dabmg,
         e~ebtyp
    FROM ekko AS k
    INNER JOIN ekpo AS p ON p~ebeln = k~ebeln
    INNER JOIN lfa1 AS l ON l~lifnr = k~lifnr
    LEFT OUTER JOIN ekes AS e ON e~ebeln = p~ebeln
                             AND e~ebelp = p~ebelp
    WHERE k~bedat IN @s_bedat
      AND k~lifnr IN @s_lifnr
      AND p~matnr IN @s_matnr

13. 案例四：寫回確認——ME_CONFIRMATION_UPDATE 與風險

原程式的存檔邏輯（FORM FORM_ME_CONFIRMATION_UPDATE）規則寫得很清楚，這部分值得保留：已交貨完成不可改、已有交貨數量不可改、沒填新日期也沒填新數量就略過、新舊日期相同就略過；原本沒有確認記錄的算「新增（I）」，確認序號給 1、確認量帶採購量；有記錄的算「修改（U）」；沒填新量就帶舊量、沒填新日期就帶舊日期。寫回用的是 ME_CONFIRMATION_UPDATE，傳入 UEKES 結構：

14. 案例五：發票重複檢查——先找標準（OMRDC、M8108）

業務情境

會計發現同一張供應商發票被 MIRO 過帳兩次（一次由採購、一次由會計；或同一號碼打錯一個字元），造成重複付款。需求是「檢查廠商發票是否重複開」。依 Casper 的第三個實務原則——標準設定 → BAdI → Enhancement Point → 修改標準，先確認標準功能有沒有打開。

層次內容設定／查詢
1. 供應商主檔公司代碼層的「重複發票檢查」旗標 LFB1-REPRF（BP／供應商「付款交易」頁籤）BP、SE16N 查 LFB1
2. 後勤發票驗證的檢查條件除了供應商、幣別、金額（一定比對）之外，可再勾選是否比對「公司代碼」「參考文件號碼（XBLNR）」「發票日期」OMRDC（SPRO：MM › 後勤發票驗證 › 輸入進項發票 › 設定重複發票檢查）
3. 訊息強度命中時出現訊息 M8 108（「請確認發票是否已以會計文件 & 輸入」），預設是警告，可改成錯誤直接擋下OMRM（發票驗證的訊息控制）
4. 暫存發票暫存（parked）的發票也要納入比對，否則兩張都先暫存就抓不到依版本行為測試確認
標準檢查為什麼還會漏：標準是「完全相等」比對。參考號碼一張打「AB-001」、一張打「AB001」，金額一張含稅一張未稅，或發票日期差一天，就不會觸發 M8108。另外供應商主檔沒勾 REPRF 時整個檢查都不做。所以客製報表的價值在「事後稽核＋模糊比對」，而不是取代標準檢查；第一步永遠是把標準打開並改成錯誤訊息。

15. 案例五：素材 ZMMR0004——用 GR／IR 數量找「多開」的發票

新版講義的 ZMMR0004 實際做法不是比對發票號碼，而是從數量面偵測：同一採購項目的發票數量（IR）大於收貨數量（GR），就代表發票多開或重開。欄位、按鈕與選擇畫面（「Cleared items too」欄位 AM07M-MB5S_ZERO、權限按鈕 cl_mmim_auth、採購歷史 RM06EHBE）明顯是仿標準 MB5S（GR/IR 餘額清單）改寫而來。

17. 批次 BAPI 共通的四個坑

坑一：逐筆 COMMIT 還是整批 COMMIT？
  • 逐筆 COMMIT（案例二、案例三的多張請購單）：一筆失敗不影響其他筆，能精確回報哪一筆錯；缺點是慢（每次都等更新任務），且中途中斷會留下「部分完成」，所以一定要有暫存表記錄每筆狀態、能續跑。會鎖主檔的 BAPI（BAPI_MATERIAL_SAVEDATA）只能逐筆。
  • 整批 COMMIT：同一個業務單位必須「全有或全無」時才用，例如同一張採購單的所有確認（案例四以採購單為單位）。整批中任何一筆回傳 E／A，就整批 ROLLBACK。
  • 不要在一個 LUW 裡累積上千筆 BAPI 再 COMMIT：鎖表會爆、更新任務會逾時，出錯時也不知道是哪一筆。
坑二：BAPIRET2 只看 TYPE E／A。W（警告）在 BAPI 裡不會擋存檔，但要記錄給使用者；S 不代表整體成功，同一張 RETURN 表可能同時有 S 與 E。BAPI_TRANSACTION_COMMIT 也有自己的 RETURN，要一起看。
坑三：條件用列舉，不用區間。案例四原本用 EBELN LIKE '4%' 判斷「是採購單」，號碼範圍一改（例如新開 45 開頭的號段給其他文件類型）就會多抓或漏抓；改用業務欄位 BSTYP／BSART 的列舉。案例五的 VGABE 也用 IN ( '1', '2' ) 而不是區間。選擇畫面上物料、採購單讓使用者貼多筆 EQ，比讓他輸入 BT 區間安全——區間比的是字典序，遇到前導零、英數混合的號碼就會出錯。
坑四：HANA 沒有預設排序。本章四個地方都踩到：案例一輸出沒排序、案例四 EKES 取「第一筆」前沒排序、EKET 用 SELECT SINGLE 取不固定的一條計畫行、案例五 FOR ALL ENTRIES 後直接把第一筆當原始發票。凡是「取第一筆」「用 BINARY SEARCH」「AT NEW／AT END OF」「GROUP BY 後取代表」的邏輯，前面都要有明確的 ORDER BY 或 SORT。這也是 Casper 在成本評價專案上踩過的坑：同一料號同時有 H 與 E 兩種角度的資料，沒排序時一下抓到 H、一下抓到 E，結果就不穩定。
