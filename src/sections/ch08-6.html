第 8-6 章 實戰源碼庫（六）：MM／SD 查詢報表

這一章拆解某醫療器材公司實際上線的七支 MM／SD 查詢與對照表維護程式：採購訂單查詢、供應商到貨單、交貨單明細、產品退貨查詢、客戶合作夥伴功能報表，以及兩張用通用維護框架管理的自建對照表。它們的共同點是「撈資料 → 補欄位 → 丟進 ALV」，但同時也把舊寫法的所有坑都示範了一遍：REUSE_ALV 與 OOALV 混用、MSEG／VBUK 等 S/4HANA 已變動的資料模型、FOR ALL ENTRIES 吃掉重複列、「取第一筆」沒排序、權限過濾反而把整張單刪掉。讀完你會得到一個可以直接套用的 CL_SALV_TABLE 報表骨架、一個共用 ALV 輔助類別，以及一張「什麼時候才需要 CL_GUI_ALV_GRID」的判斷表。本章與 2-3 章 ALV、3-2 章 OOALV 與 Screen 互補：那兩章講工具本身，本章講工具在真實專案裡被怎麼用、又該怎麼改。

2. 共通骨架：從 REUSE／OOALV 收斂到 CL_SALV_TABLE

七支程式用了四種 ALV 寫法：ZMMF010N 是 CL_GUI_ALV_GRID 宣告卻走 FO2N include 顯示、ZPUR007 與 ZSDR018 用 REUSE_ALV_GRID_DISPLAY_LVC、ZSDR007N 用最舊的 SLIS 版 REUSE 函數、ZSDR040 用 Docking Container＋Splitter＋CL_GUI_ALV_GRID 的全套 OOALV。但仔細看需求，七支都是唯讀報表：沒有任何一支真的讓使用者改儲存格再存回去（ZSDR018 明細的「選擇」勾選框只是用來選列）。這正是 CL_SALV_TABLE 的主場。

原程式的問題與改進：

  • O(n²) 巢狀迴圈：2023 年追加的 LOOP AT lt_mseg … LOOP AT lt_mseg2 … MODIFY lt_mseg 對每一組都 MODIFY，不管有沒有對到。資料一多就是效能災難；改成 HASHED 表查找或上面的 GROUP BY。
  • 物料權限「連坐」：frm_auth_data 對權限群組 N 的物料，從 MSEG 反查出所有相關 PO，再把這些 PO 的所有行項目都刪掉——使用者只是沒權限看某一個物料，卻整張 PO 都看不到。而且 SELECT ebeln FROM mseg WHERE matnr IN gr_matnr 沒有其他條件，是全表掃描。正確做法是在主查詢以 NOT IN 排除受限物料，或 JOIN MARA 以 BEGRU 過濾到「行」的層級。
  • 「排除 SAP_ALL」的權限技巧：原程式先檢查 BEGRU = 'N' 成功後，再檢查 BEGRU = 空白也成功就視為全權限。這是利用「有 * 權限的人兩個檢查都會過」的推論，可讀性差且容易誤判；應直接以使用者對每個 BEGRU 的檢查結果組成排除清單。
  • 品檢狀態：frm_deal_data 裡曾依 MSEG-QINSPST = '1'（需檢驗）決定合格量初值，這段在改版後被丟在不再呼叫的 FORM 裡，行為悄悄改變。改版時「舊 FORM 留著不刪」是最危險的習慣。
  • DELETE TABLE gt_out FROM gs_out：在 LOOP 中依「表格鍵」刪除，標準表的預設鍵是所有字元欄位，可能刪錯列；改為 DELETE gt_out WHERE budat NOT IN s_budat，或更好——在 SQL 就過濾。
  • 輸出了集團（MANDT）欄位，對使用者沒有意義，移除。

關鍵邏輯一：定價條件轉欄位。原程式把 PRCD_ELEMENTS 中 PR00（含稅報價）、PR01（含稅單價）、MWSI（稅）、ZK02（折扣率）、ZK03（折扣額）分別 READ 出來放到不同欄位；模板 A 用 PR02 與 ZD00（權益金額）。問題在於「發貨數量不含稅金額」寫成 kbetr_2 / '1.13' * lfimg——稅率 13% 寫死在程式裡，稅率一調整（或出口零稅率訂單），整欄就錯。改成以條件金額 KWERT 按數量比例計算，不必知道稅率：

SELECT r~vgbel, r~vgpos, SUM( r~fkimg ) AS fkimg
  FROM vbrp AS r
  INNER JOIN vbrk AS k ON k~vbeln = r~vbeln
  WHERE k~fksto = @space                          " 已被取消的發票不算

    AND r~vgbel IN ( SELECT vbeln FROM likp       " 子查詢：與主查詢相同的交貨單範圍
                       WHERE vstel IN @s_vstel
                         AND vbeln IN @s_vbeln
                         AND erdat IN @s_erdat )
  GROUP BY r~vgbel, r~vgpos
  INTO TABLE @DATA(lt_billed).

13. ZALV_COMM 共用 include 的問題與共用 ALV 類別的設計

ZSDR040 的架構。主程式 7 個 include：TOP（先 INCLUDE ZALV_COMM，再宣告 GT_ALV 等）、C01（事件接收類別 LCL_EVENT_RECEIVER_GRID：DOUBLE_CLICK、BUTTON_CLICK、DATA_CHANGED、TOP_OF_PAGE，每個方法只是 PERFORM 到 FORM）、S01（選擇畫面＋5 個功能鍵）、F01（建立 Docking Container → Splitter 兩列 → 上格放 HTML 表頭、下格放 Grid；Field Catalog 用 REUSE_ALV_FIELDCATALOG_MERGE 讀內表宣告再轉 LVC；排除工具列按鈕；註冊 ENTER／MODIFIED 編輯事件）、F02（INITIALIZATION、FETCH_DATA）、O01（PBO：GUI Status、第一次建立 ALV 否則 refresh）、I01（PAI）。從 include 註解可以看出它是從一支名為 YS_AVL_SAMPLE 的範本複製而來。

先標準、再客製。「依訂單類型決定出貨移動類型」在 SAP 標準是由計劃行類別決定的（VOV6 設定計劃行類別的移動類型；VOV5 依項目類別＋MRP 類型決定計劃行類別），樣品、免費品通常用不同的訂單類型／項目類別就能分流；科目則由移動類型的帳戶修改碼與評價設定（OBYC）決定。只有「同一訂單類型、同一項目類別，卻要依客戶帳戶群組或是否帶成本中心而改變移動類型」這種標準做不到的組合，才值得自建表＋增強。Casper 的經驗是：標準設定 → BAdI／Enhancement Spot → Enhancement Point → 修改標準，每往右一步，升級成本高一個量級。

原框架的問題與改進：

  • 動態表名未驗證：函數以 SELECT * FROM (i_view_name) 讀取、並可更新任意傳入的表，若有人以 SE37 測試或寫支程式傳入標準表名，就可能維護到不該維護的表。動態名稱要用白名單檢查（例如 cl_abap_dyn_prg=>check_whitelist_tab( )，或限制 Z／Y 開頭且屬於指定套件），並做 S_TABU_NAM 權限檢查。
  • 整表讀取：不論過濾條件，先 SELECT * 整張表再在 ABAP 過濾（frm_set_filter）；大表會很慢，過濾應轉成 WHERE。
  • 欄位命名：勾選框欄位取名 KOSTL、AUFNR，會讓後人以為存的是成本中心／內部訂單號碼。應命名如 ZZ_HAS_KOSTL。
  • 欄寬以 strlen( coltext ) * 2 估算中文字寬（原程式用 COMPUTE），可接受但屬經驗值；SALV／LVC 的 cwidth_opt 已能自動處理。

15. ZSDU021 SO 物料轉換關係：一對多規則與單位換算

業務情境。客戶以「散裝物料＋EA」下單，公司實際出貨卻是另一個「整箱物料＋CV（箱）」，例如 8 EA 的來源物料轉成 1 CV 的目的物料。轉換規則存在自建表 ZSDT020（物料轉換），維護程式 ZSDU021 與 ZSDF016 完全同一個模式（同一支共用函數、同一段 FORM），只改表名、欄位文字與數量欄位的單位參照（QFIELDNAME）。

欄位鍵資料元素畫面文字
MANDT✓MANDT集團
MATNR_F✓MATNR（40）源物料
MATNR_T✓MATNR（40）目的物料
MENGE_FMENGE_D（QUAN 13,3）源數量（單位參照 MEINS_F）
MEINS_FMEINS源單位
MENGE_TMENGE_D目的數量（單位參照 MEINS_T）

關鍵觀察：鍵值是「來源＋目的」，所以同一個來源物料可以對應多個目的物料——匯出範本與結果截圖都能看到同一個來源物料有兩列不同目的物料。任何「給我來源物料、回傳目的物料」的程式如果寫成 SELECT SINGLE … WHERE matnr_f = …，在 HANA 上每次拿到哪一列都不保證，這就是 Casper 所說「HANA 沒有預設排序，取第一筆必須先明確排序」的標準案例；而在這裡，連排序都不夠——一對多本身就是業務決策，必須由呼叫端指定或另設優先順序欄位。

METHOD convert.
  " iv_matnr_f / iv_menge / iv_meins：訂單上的來源物料與數量；iv_matnr_t：指定的目的物料（可空）
  DATA lr_matnr_t TYPE RANGE OF matnr.
  IF iv_matnr_t IS NOT INITIAL.                 " 空範圍＝不限制目的物料
    lr_matnr_t = VALUE #( ( sign = 'I' option = 'EQ' low = iv_matnr_t ) ).
  ENDIF.

  SELECT matnr_t, menge_f, meins_f, menge_t, meins_t
    FROM zsdt020
    WHERE matnr_f = @iv_matnr_f
      AND matnr_t IN @lr_matnr_t
    ORDER BY matnr_t
    INTO TABLE @DATA(lt_rule).

  CASE lines( lt_rule ).
    WHEN 0.
      RETURN.                                   " 沒有規則：不轉換
    WHEN 1.
      DATA(ls_rule) = lt_rule[ 1 ].
    WHEN OTHERS.
      " 一對多：不可自行「取第一筆」，要求呼叫端指定目的物料
      MESSAGE |物料 { iv_matnr_f ALPHA = OUT } 有多個轉換目的物料，請指定| TYPE 'E'.
  ENDCASE.

  " 訂單單位與規則的來源單位不同時，先換成來源單位（依物料的單位換算 MARM）
  DATA(lv_qty_f) = iv_menge.
  IF iv_meins <> ls_rule-meins_f.
    CALL FUNCTION 'MD_CONVERT_MATERIAL_UNIT'
      EXPORTING
        i_matnr              = iv_matnr_f
        i_in_me              = iv_meins
        i_out_me             = ls_rule-meins_f
        i_menge              = iv_menge
      IMPORTING
        e_menge              = lv_qty_f
      EXCEPTIONS
        error_in_application = 1
        error                = 2
        OTHERS               = 3.
    IF sy-subrc <> 0.
      MESSAGE ID sy-msgid TYPE 'E' NUMBER sy-msgno WITH sy-msgv1 sy-msgv2 sy-msgv3 sy-msgv4.
    ENDIF.
  ENDIF.

  " 8 EA → 1 CV：目的數量 = 來源數量 ÷ 來源基數 × 目的基數，並檢查是否整箱
  DATA(lv_qty_t) = CONV decfloat34( lv_qty_f ) / ls_rule-menge_f * ls_rule-menge_t.
  IF frac( lv_qty_t ) <> 0.
    MESSAGE |數量 { lv_qty_f } { ls_rule-meins_f } 無法整除為 { ls_rule-meins_t }| TYPE 'E'.
  ENDIF.
  es_result = VALUE #( matnr = ls_rule-matnr_t menge = lv_qty_t meins = ls_rule-meins_t ).
ENDMETHOD.
上例方法內用 TYPE 'E' 訊息是為了示意；若這段邏輯會在訂單增強（例如 MV45AFZZ，見 8-1 章）或背景介面中被呼叫，請改為拋出 class-based exception，由呼叫端決定如何呈現（見 3-2 章例外處理）。
先找標準：若來源與目的其實是「同一個物料的不同包裝單位」，用物料主檔的替代計量單位（MARM，MM02 附加資料 → 計量單位）加銷售單位就夠了，完全不需要自建表；若是「客戶下 A 料、系統自動換成 B 料」，標準有物料決定（Material Determination，VB11）；若是「一個銷售料號出貨時展開成多個組件」，標準有銷售 BOM。ZSDT020 只適用於「換料＋換單位＋固定比例」同時發生、標準都不合的情況——做之前把這三個標準方案逐一排除，並寫進設計文件。
