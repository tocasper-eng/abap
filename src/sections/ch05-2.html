2. 資料型別與資料物件細節（2007 版第二單元）

資料物件用 DATA 宣告，TYPE 後面的型別在編譯時就「靜態綁定」，執行期不能改。所有型別最後都建立在預定義 ABAP 型別上：

型別是否完整指定長度 / 值域初始值重點
i完整4 bytes，-2147483648 ～ 21474836470整數運算最快；除法自動四捨五入（4/10＝0、5/10＝1）
p需 LENGTH／DECIMALS1～16 bytes，預設 8 bytes（15 位數）、0 位小數；小數最多 14 位0每 byte 存 2 位數，最後半 byte 存正負號；p LENGTH 2 DECIMALS 2 值域為 -9.99～9.99；商業運算首選

c / n / x需 LENGTH1～65535 字元（x 為 byte）；未指定長度預設 1空白 / '0…' / X'00'n 只存數字，指定時忽略字母、右靠左補 0

運算型別規則（原教材重點）：預設用定點（p）運算；只有全部運算元都是整數才用整數運算；只要有一個 f 就用浮點運算；所有運算元先轉成計算型別，算完再轉成結果欄位型別。所以「同一個式子，不同型別組合會得到不同結果」。數值文字若在 i 範圍內當整數，否則當 p：1000000000 / 300000000 * 3 得 9（整數運算，中間值 3 已四捨五入），10000000000 / 3000000000 * 3 得 10（超出 i 範圍改用 p）。程式屬性中的「定點運算（Fixed point arithmetic）」必須保持勾選，否則 DECIMALS 只影響輸出。

回傳 f 的內建函數：cos acos sin asin tan atan tanh sinh cosh exp log log10 sqrt。建議：只有整數用 i；商業小數用 p；極大極小的粗略運算才用 f（SELECT 的某些聚合函數也會回傳 f）。

結構：可用 TYPES BEGIN OF … END OF 先定義型別再宣告，也可直接 DATA BEGIN OF（隱含定義型別）；組件用 struct-comp 存取，因此變數名不能含連字號。結構可任意巢狀；包含 string、內表或參照的叫深層結構（deep structure），限制包括：不能整個放在 SELECT 的 INTO 後面、不能做 offset 存取（SAP Note 176336）。需要「分組但仍是扁平結構」時用具名 INCLUDE：INCLUDE TYPE … AS name [RENAMING WITH SUFFIX …]，資料庫表與 ALV、Table Control 只接受扁平結構時特別好用。

型別群組（Type Group）：名稱最長 5 字元，全域常數必須放在型別群組中，所有常數與型別名都要以群組名為前綴；R/3 4.5 以前這是定義複雜全域型別的唯一方法。

S/4HANA 現況：① S/4HANA 系統一定是 Unicode，原教材的「Unicode Checks Active」旗標、Unicode 片段視圖（fragment view）、對齊間隙（alignment gap）等規則你只會在舊程式轉換時遇到；現代程式請不要再用 offset/length 對結構做字元運算。② TYPE-POOLS 敘述已過時（7.02 起型別群組會自動載入），全域常數改放在介面或類別的 CONSTANTS，例如 abap_true／abap_false。③ 原教材的 MOVE p_date TO s_date、COMPUTE、ADD 等語法一律改成 = 與運算式。
相容與轉換：兩個基本型別「型別與長度相同（p 還要小數位相同）」才相容；結構要「結構相同且組件相容」；表型別要「行型別相容、主鍵與表種類相同」。相容就不轉換；不相容但有轉換規則就先轉再算；沒有轉換規則時，靜態型別會語法錯誤（例如把 d 型 field symbol 指派給 t 型 field symbol），TYPE any 的泛型則要到執行期才 DUMP。完整轉換規則見關鍵字文件的 conversion rules（舊版寫在 MOVE 關鍵字下）。

3. 內表進階（2007 版第三單元）

內表是執行期可變長度的資料物件，行數只受系統記憶體限制。每個內表有三個屬性：行型別（有哪些欄）、鍵（唯一／非唯一）、表種類（決定能用哪些存取方式）。完整的內表與 ABAP SQL 現代語法見 2-2 章，這裡聚焦 BC401 強調的「表種類 × 存取方式 × 效能」。

7.40 的 FILTER #( ) 只能用在排序表／雜湊表或有次要鍵的內表；由 @DATA( ) 內嵌宣告的 SELECT 結果是空鍵標準表，所以上例改用 DELETE … NOT IN。另外，READ … BINARY SEARCH 必須建立在明確排序之上：資料若直接來自 HANA 又沒寫 ORDER BY 或 SORT，二分搜尋會「偶爾找不到」，而且每次執行結果還不一樣——這正是 Casper 在成本評價專案遇到 H／E 兩種角度輪流被抓到的根因。任何「取第一筆」或二分搜尋前，一定先排序。
列舉優於區間：組 RANGE 時請優先用多筆 option = 'EQ'，少用 BT。BT 比的是字典序不是業務語意：物料號碼段不連續、ALPHA 前導零（'0000001234' 與 '1234'）、編碼規則改過，都會讓區間多抓或漏抓。原教材的效能提示也支持這一點：排序表的鍵以 = 指定才能走二分搜尋。

Field symbol 效能要點：READ … ASSIGNING 與 LOOP … ASSIGNING 不拷貝資料，行寬大（原教材：純讀取約 1000 bytes 以上、讀後要修改則約 100 bytes 以上）或迴圈次數多（約 5 次以上）時比 INTO 快；巢狀內表時差距更大，因為 INTO 會把整個子表拷貝一次。限制：LOOP … ASSIGNING 中不能在控制層級處理用 SUM，也不能在迴圈內對該 field symbol 重新 ASSIGN 或 UNASSIGN；排序後 field symbol 仍指向原來那一行。

表頭行（Header Line）已淘汰：原教材列出 WITH HEADER LINE、OCCURS 0、DATA BEGIN OF itab OCCURS 0 三種寫法，並提醒 CLEAR itab 對有表頭的表只清表頭、要清表身得寫 CLEAR itab[] 或 REFRESH。類別與介面中根本不能使用表頭行，新程式一律不用。SELECT-OPTIONS 產生的選擇表本身仍帶表頭，這是唯一合法殘留，存取表身時請寫 so_carr[]。

4. 呼叫程式與傳遞資料（2007 版第四單元）

在同一個使用者交易中，完整的 ABAP 程式只能循序執行；要平行執行得用 CALL FUNCTION … STARTING NEW TASK（見 4-1 章 aRFC 與 5-12 章 BC415）。呼叫程式分兩種模式：插入（Insert）——目前程式暫停、被呼叫程式跑完後回來；重新開始（Restart）——結束目前程式、改跑新程式。

5. 從程序式到物件導向（Unit 1 L1／2007 第五單元／BC404 第二、八單元）

ABAP 的演進：ABAP 之前 SAP 用巨集組譯器；ABAP 是為了改進報表而開發的內部語言，受 COBOL 與 Pascal 影響；ABAP Objects 是 ABAP 的相容擴充，OO 部分吸收了 Java、C++、Smalltalk 的概念，並刻意不納入在其他語言證明失敗的設計。它與其他 OO 語言最大的差別在於開發環境：可以用整套 ABAP Workbench。

程序式模型的特徵：資料與功能分離；可用模組化（副程式、函數模組）封裝功能；主程式的全域資料沒有任何保護，任何地方都能讀寫。原教材用函數群組 S_VEHICLE 示範：它提供 INC_SPEED、DEC_SPEED、GET_SPEED、STOP 四個服務，全域變數 speed 只能透過函數模組存取——函數群組其實已經是「資料＋管理資料的功能」的封裝單位，主程式是 client、函數群組是 server。BAPI 正是這樣實作的：商業物件是函數群組，BAPI 是函數模組。

問題在於多重實例：函數群組被載入內部 session 後只有一份全域資料，同一時間只能代表一台車；想同時管理四台車就得自己寫陣列、索引與管理邏輯。能以同一個程式內容建立多個執行期實例，正是 OO 語言的核心特性。

OO 的技術概念：

  • 封裝（Encapsulation）：物件的實作對系統其他部分隱藏，外界拿不到內部狀態，也就不會產生相依。
  • 多型（Polymorphism）：不同類別的物件對同一訊息有不同反應。
  • 繼承（Inheritance）：子類別共享父類別的結構與行為；ABAP 只允許單一繼承。
  • 事件控制：物件不直接呼叫對方，而是觸發事件，由有興趣的物件反應。
  • Client/Server 關係與委派（Delegation）：物件呼叫他人方法時就成為 client，必須遵守 server 的協定，協定也必須清楚到 client 能照做；服務在物件間無重複地分配，自己不負責的就委派給別人。

ABAP Objects 的相容性與設計目標：不是新語言而是向上相容的擴充；OO 環境的型別檢查更嚴格（方法參數必須指定型別，呼叫時檢查）；SAP 趁機「清理」語言——過時敘述在 OO 環境中直接語法錯誤，在程序式環境則為了相容仍被允許，但原廠建議也不要用。這也是本圖書館「新程式一律用類別」的依據。

BC404 第八單元「摘要與展望」（BC401 沒有）：70–80 年代的目標是「正確且健壯」；程式變大後重點轉向擴充性（在相同環境加功能）與重用性（把程式搬到別的環境做不同的事）。OO 對應：類別（資料與功能在獨立單元、簡單重用）、封裝（只透過介面溝通、不依賴實作）、多型（擴充時影響最小）、繼承（實作的繼承）。優點：擴充性（多型、繼承）、重用性（類別、封裝、繼承）、所有參與者在所有階段使用統一語言、軟體概念直接反映現實（物件→物件、狀態→屬性、功能→方法）。

筆記錯誤修正：强晟 BC404 筆記 p18 的標題寫「面向對象方法的優點」，但內容其實是缺點：① 第一個成果出現前需要更長的開發時間；② OO 程式與關聯式資料庫之間的典範斷裂（paradigm break）；③ OO 程式通常比程序式效率低。p19 的「展望」提到「業務物件知識庫（BOR）的 OO 視圖將整合進類別庫」，作者猜測「大概就是 ECC5 裡的 BAPI」——這只是推測；BOR 物件型別（SWO1）與 BAPI 確實是當年的方向，但到了 S/4HANA，真正落實「商業物件即類別」的是 RAP 商業物件（CDS 行為定義＋行為實作類別）。

6. 分析與設計：UML（Unit 1 L2／2007 第六單元／BC404 第三單元）

類別與物件：相似的物件歸成一個類別，類別只宣告一次，物件照藍圖建立。「類別是具有相同結構與行為的一組物件的描述」；物件（＝實例）有身分（兩個同高同色的杯子仍是兩個杯子）、狀態（屬性值集合）與行為（方法與事件）。抽象是把現實簡化成有意義的維度：同樣叫 lcl_vehicle，在汽車迷系統與廢車回收系統中是完全不同的抽象；課程範例的 lcl_vehicle 指四輪機動車。

UML 由 OMG 於 1997 年 9 月發布為工業標準，SAP 以它為 OO 建模的公司標準。UML 不描述開發流程步驟，只定義圖。BC404 筆記列出的圖種類：

圖視角用途
使用案例圖（Use Case）外部行為者與使用案例的關係，從使用者視角描述系統行為
類別圖（Class）靜態元素（類別、物件）、內部結構（屬性、方法）、關係（一般化/特殊化、關聯）
互動圖：循序圖（Sequence）／協作圖（Collaboration）動態循序圖強調方法呼叫的時間順序；協作圖著重物件關係與拓樸
狀態圖（Statechart）／活動圖動態物件生命週期中的狀態與觸發原因；活動圖是只含行為的特殊狀態圖
元件圖（Component）實作元件的組織與相依
部署圖（Deployment）實作軟體與硬體的相依

類別圖的符號：類別框分三格（名稱、屬性、方法，後兩格可省）；可見性以 +（public）、#（protected）、-（private）表示；靜態成員加底線；方法簽名可寫成 method(參數) : 回傳型別；ABAP 事件不畫在類別圖裡。關係：

  • 關聯（Association）：兩類別間一條線，兩端標多重性（1、0..1、1..*、* 或 0..*），可加斜體名稱與閱讀方向箭頭；每個關聯有兩個角色。例：lcl_customer 1 —books— 0..* lcl_booking（一個客戶可訂多筆，一筆訂位只屬一位客戶）。關聯可遞迴（類別與自己關聯）。
  • 聚合（Aggregation）：「由…組成／是…的一部分」，整體端畫空心菱形，例：lcl_vehicle 1 ◇— 0..* lcl_wheel。
  • 組合（Composition）：更強的聚合，部分不能脫離整體存在，整體端畫實心菱形、多重性只能是 1，部分與整體同生共死，例：lcl_rental 1 ◆— 1..* lcl_booking。
  • 一般化/特殊化：子類別以空心三角箭頭指向父類別，多個箭頭可合成樹狀。
  • 介面：名稱上標 <<interface>>；使用關係為虛線箭頭，實作關係為虛線＋空心三角。

循序圖：物件生命線為垂直虛線；控制焦點（activation）是生命線上的長方形，表示物件正在執行（或間接等待子程序）；訊息是生命線之間的水平箭頭，寫成「方法(參數)」，回覆可用回傳箭頭；循序圖沒有表示靜態方法的符號。範例「委派」：司機 lcl_driver 呼叫汽車 lcl_car 的 get_fuel_level，汽車自己無法處理，轉呼叫油箱 lcl_tank 的 get_fuel_level。好處是執行期可以換油箱而不影響 client；好的封裝通常會「強迫」使用委派（油箱是汽車的 private 屬性，外界只能透過汽車）。

强晟在筆記裡吐槽：「既然使用者看不懂程式語言，也不要指望他看懂 UML……跟使用者談 UML，還不如請他吃頓飯。」實務上 UML 是給開發團隊的溝通工具；對業務顧問與使用者，流程圖與畫面雛形更有效。在 ADT 可用 ABAP Class Diagram（或 SE80 的 UML 產生功能，NW 7.0 EhP2 起）從既有程式碼反推類別圖，交接時很好用。
新版教材強調：OO 的分析與設計決策對實作的影響比程序式大得多，因此需要建模語言或工具把分析設計階段標準化；開發是「需求 → 分析設計 → 實作 → 測試」的循環過程。

7. 區域類別：屬性、方法與可見性（Unit 2 L1／2007 第七單元第一課）

類別分定義部分（CLASS … DEFINITION，宣告所有組件）與實作部分（CLASS … IMPLEMENTATION，只放方法實作）。組件包括：屬性、方法、事件、型別、常數、介面、別名。CLASS 敘述不能巢狀（不能在類別裡定義類別）。區域類別只存在於定義它的程式中，就像 TYPES 定義區域資料型別一樣，CLASS 定義的是區域物件型別。

BC404 筆記的「物件就像雞蛋」比喻：外層蛋殼是公開組件（屬性、方法、事件），所有使用者都能直接存取，是物件的對外聯絡點；內層蛋黃是私有組件，只有物件自己看得到。為什麼要隱藏？這叫資訊隱藏／封裝：類別改了私有實作而介面不變，使用者完全不受影響；一旦改了公開組件，所有使用者都得跟著改。

  • 屬性型別可以是：DDIC 型別（資料元素、結構、表型別）、ABAP 內建型別、物件參照、介面參照。類別中只能用 TYPE 指定型別；LIKE 只能參照區域資料物件，不能參照 DDIC 物件。
  • READ-ONLY：只能用在 PUBLIC SECTION 與介面中，外界可讀、只有類別自己的方法能改。
  • 實例屬性（DATA）每個物件一份；靜態屬性（CLASS-DATA）整個類別一份，所有實例共用，常用於計數器等管理資訊。官方術語是「靜態」而非「類別屬性」。UML 以底線表示靜態成員。
  • 方法簽名：IMPORTING、EXPORTING、CHANGING、RETURNING 與例外；參數可傳值（VALUE( )）或傳參照（預設）。RETURNING 只能有一個且必須傳值，有它就不能再有 EXPORTING／CHANGING（7.40 SP02 起可與 EXPORTING/CHANGING 並存，但 BC401 仍建議功能性方法保持單純）。IMPORTING／CHANGING 可加 OPTIONAL 或 DEFAULT。
  • 靜態方法（CLASS-METHODS）只能存取靜態組件，不需要實例就能呼叫。
  • 命名空間：類別內屬性、方法、事件、常數、型別、別名共用一個命名空間；方法內的區域變數可遮蔽同名屬性（此時用 me-> 取屬性）。
筆記更正：强晟筆記 p156 寫「SAP R/3 Basis 6.10 以後不能為例外再使用 EXCEPTIONS 參數，而代之以 RAISING」。正確說法是：6.10 起多了類別式例外（RAISING），但傳統 EXCEPTIONS 仍然可用；限制是同一個方法只能擇一，不能混用兩種例外。新程式請一律用 RAISING。

8. 建立物件、呼叫方法、建構子與 ME（Unit 2 L2–L5／2007 第七單元第二～五課）

實例化：類別本身在執行期不是獨立物件；程式執行時才依類別在主記憶體建立實例。參照變數 DATA lo_vehicle TYPE REF TO lcl_vehicle 是指向物件的指標，CREATE OBJECT（7.40 起可用 NEW）向執行環境要記憶體並配給物件；參照變數之間可以互相指派，兩個變數會指向同一個物件。參照可以放進單欄內表，用 LOOP 逐一處理多個物件（原教材稱「緩衝參照」）。

垃圾回收器（Garbage Collector）：當沒有任何參照指向某物件時，系統程式會自動把它從記憶體移除。流程：從全域記憶體的所有獨立參照出發標記活動物件，再沿類別參照與其他物件的實例屬性繼續標記，最後刪除所有未被標記的物件。注意：註冊為事件處理者的物件，只要事件仍活著，就不會被回收（第 12 節）。

呼叫類型原教材寫法現代寫法
實例方法CALL METHOD ref->meth EXPORTING … IMPORTING …ref->meth( iv_a = 1 IMPORTING ev_b = lv_b )（6.10 起可省 CALL METHOD）
靜態方法CALL METHOD class=>methclass=>meth( )
只有一個 IMPORTING 參數—ref->meth( value )，可省形參名
功能性方法CALL METHOD … RECEIVING re_fuel = avg_fuelDATA(lv_avg) = ref->get_average_fuel( im_distance = 500 im_fuel = 50 ).
公開屬性實例：ref->attr；靜態：class=>attr（-> 與 => 稱為元件選擇器）

功能性方法（有 RETURNING 的方法）可直接用在運算式位置：邏輯運算式（IF、ELSEIF、WHILE、CHECK、WAIT）、CASE／WHEN、LOOP、算術運算式、位元運算式與指派右側；7.40 起幾乎所有運算元位置都可以。

實例建構子 CONSTRUCTOR：每個類別只有一個；在 CREATE OBJECT／NEW 時由系統自動呼叫，不能顯式呼叫（子類別呼叫 super->constructor( ) 除外）；建構子中發生例外，物件就不會被建立，也不佔記憶體。需要建構子的時機：要配置外部資源、要初始化無法用 VALUE 指定的屬性、要修改靜態屬性（例如計數器）。

靜態建構子 CLASS_CONSTRUCTOR：每個程式（內部 session）只執行一次，在類別第一次被存取時自動呼叫，時機早於：建立實例、存取靜態屬性（class=>attr）、呼叫靜態方法、以 SET HANDLER 註冊靜態事件處理方法。不能顯式呼叫、沒有參數、不能丟出例外。

教材版本差異：强晟筆記 p171 寫「必須在 PUBLIC SECTION 中定義建構子」，這是 NW 7.0 以前的規則。新版教材（Col18 p290）說明：自 SAP NetWeaver 7.0 起，建構子可以宣告在 PROTECTED 或 PRIVATE SECTION，只要不比 CLASS 敘述的 CREATE 附加更嚴格；真正決定「誰能實例化」的是 CREATE PUBLIC／PROTECTED／PRIVATE（第 18 節）。

9. 繼承與重定義（Unit 3 L1／2007 第八單元）

繼承是「是一種（is-a）」關係：卡車是一種車輛。父類別是子類別的一般化，子類別是父類別的特殊化。重點規則：

  • ABAP 只允許單一繼承（一個直接父類別），但繼承樹可以任意多層；多重繼承用介面模擬。
  • 繼承是單向關係：子類別知道直接父類別，父類別不知道自己有多少子類別。
  • 只能增加，不能刪除：父類別所有組件自動出現在子類別；子類別可加新組件、重定義繼承來的方法。
  • 重定義（REDEFINITION）：只能重定義 public／protected 的實例方法；REDEFINITION 必須寫在與原方法相同的區段（所以 private 方法不能重定義，子類別根本看不到）；不必重寫簽名、也不能改簽名。用 super->method( ) 呼叫父類別實作，這個虛擬參照只能用在重定義的方法中。
  • ABAP 不支援多載（Overloading）：同名方法不同簽名是不允許的；建構子是唯一「可以有不同簽名」的例外。
  • 子類別建構子必須呼叫 super->constructor( )，因為只有類別自己能正確初始化自己的私有組件；靜態建構子則由系統自動確保父類別先執行。
  • 實例化時該填哪些參數：類別有自己的建構子就依它的簽名填；沒有就沿繼承樹往上找第一個有建構子的父類別，依那個簽名填；都沒有則不用填。
  • 子類別看不到父類別的 private 組件，包括屬性。這保護父類別：它可以自由修改私有實作而不讓子類別失效。
  • 靜態組件在每個 roll area 只有一份：父類別的 public/protected 靜態屬性由所有子類別共用，子類別不會各自得到副本。
  • 區段順序慣例：PUBLIC → PROTECTED → PRIVATE。

10. 轉型與多型（Unit 3 L2–L4／2007 第九單元）

靜態型別與動態型別：參照變數有兩種型別——靜態型別由 TYPE REF TO 決定，永遠不變，決定「能存取哪些組件」；動態型別是目前實際指向的物件的類別，執行期可變，決定「重定義方法跑哪一份程式碼」。除錯時可以看 ME 或參照變數得知動態型別。

Up-Cast（2007 稱 Narrowing Cast，收縮轉型）Down-Cast（2007 稱 Widening Cast，擴展轉型）
方向子類別參照 → 父類別（或介面）參照父類別（或介面）參照 → 子類別參照
語法lo_vehicle = lo_truck.lo_truck ?= lo_vehicle. 或 lo_truck = CAST #( lo_vehicle ).（7.40）
檢查時機編譯期靜態檢查，永遠安全只能在執行期檢查
失敗時—丟出 CX_SY_MOVE_CAST_ERROR（可捕捉），目標變數保持原值
可見組件只剩父類別定義的組件（看不到 get_cargo）恢復子類別的完整組件
用途泛型存取、多型在泛型清單中找出特定子類別做特殊處理
術語陷阱：2007 版把 Up-Cast 叫「收縮（Narrowing）」，意思是「可見的組件變少」；把 Down-Cast 叫「擴展（Widening）」。强晟筆記 p195 寫擴展轉型「從一個具有較多細節的視角轉向了較少細節的視角」，方向寫反了——Down-Cast 是從「較少細節（父類別）」轉向「較多細節（子類別）」。新版教材改用 Up/Down-Cast 就是為了避免這種混淆，本圖書館統一使用新術語。另，原教材的 MOVE … ?TO … 等價語法已過時。

多型：子類別實例可以用在任何需要父類別實例的地方（因為它繼承了全部組件、有相同介面）。當實例收到訊息，若自己的類別有實作就執行，否則沿繼承樹往上找——依據的是動態型別。好處：用單一呼叫取代 CASE／IF，可讀性更高，新增子類別（例如 lcl_motorbike）時既有程式一行都不用改。程序式寫法則必須每次調整 CASE 敘述。

繼承的正確語意（原教材第九單元第三課）：子類別實例出現在父類別的任何上下文時，使用者不知道也不在乎它是哪個子類別，因此繼承來的組件必須保持原本語意，重定義時不能改變方法的意義。常見誤用：

  • 為了重用程式碼而繼承（code inheritance）：只因某類別已經實作了部分功能就去繼承它，是錯的。
  • 用繼承取代屬性：父類別 car 底下開 green_car、red_car 子類別——顏色應該是屬性。
  • 角色會變的情境：employee 底下分 full_time、part_time；兼職轉正職時，物件無法變更自己的類別，只能新建物件再搬資料，手上還握著舊參照的使用者就會處理一個「邏輯上已不存在」的兼職員工。應改用角色（role）設計模式，把「雇用型態」做成可替換的關聯物件。
  • 正方形繼承長方形：長方形有獨立設定寬、高的方法，正方形卻只該有邊長，繼承就破壞了父類別的語意（這就是 Liskov 替換原則）。
實務判斷：先問「子類別能不能在所有使用父類別的地方完全替代它？」答案不是百分之百「能」，就改用介面＋組合（委派）。SAP 標準程式也愈來愈偏向「介面＋Factory」而不是深繼承樹，例如 SALV 與 RAP。

11. 介面（Unit 4／2007 第十單元）

介面是與類別無關的額外「協定」：只宣告與類別溝通的外部點，不含任何實作。通常由使用者（client）定義——它需要哪些服務（技術與語意），就寫進介面；使用者不知道提供者是誰，只透過介面溝通，因此能以相同方式處理不同類別。這就是介面的多型。範例：旅行社 lcl_travel_agency 透過介面 lif_partner 使用航空公司 lcl_carrier、飯店 lcl_hotel、租車 lcl_rental 的相同服務（display_partner、book、cancel_booking、check_availability）。

  • 介面可含屬性、方法、事件、型別、常數、別名，但沒有可見性區段——實作類別只能在 PUBLIC SECTION 用 INTERFACES 納入（否則父子類別可能各自私下實作同一介面）。
  • 介面組件在類別中以 介面名~組件名 存取，~ 稱為介面解析運算子（interface component selector）；可用 ALIASES 取短名（只能寫在類別定義部分或介面定義中）。
  • 一個類別可實作任意多個介面、一個介面可被任意多類別實作——實作多個介面時，行為近似多重繼承。
  • 全域介面若少實作或多實作方法只會警告；區域介面則必須全部實作（7.40 SP08 起介面方法可宣告 DEFAULT IGNORE／DEFAULT FAIL 讓實作變成可選）。
  • 修改介面通常會讓所有實作它的類別失效——介面一旦發布就要非常謹慎。
  • UML：介面上標 <<interface>>；「使用」畫虛線箭頭；「實作」畫虛線加空心三角，刻意與繼承相同——介面可視為類別實作的一般化。
  • 介面參照：物件參照指派給介面參照＝Up-Cast，只看得到介面定義的組件（且用短名存取）；介面參照轉回類別參照、或轉成另一個無關介面參照＝Down-Cast，必須用 ?=／CAST，執行期失敗丟 CX_SY_MOVE_CAST_ERROR。注意：物件參照的類別本身沒實作該介面時，不能指派給介面參照——即使它的子類別有實作也不行。
  • 複合介面（Compound Interface）：介面內再 INTERFACES 其他介面（組件介面）；不含其他介面的叫基本介面。組件保持原名 組件介面名~組件名，全部在同一層級，不會加前綴；實作類別中每個介面組件也只存在一次。UML 上複合介面被視為組件介面的特殊化。

12. 事件（Unit 5／2007 第十一單元／BC404 第六單元）

透過觸發事件，物件或類別宣告「狀態改變了」或「到達某個狀態」。範例：類別 lcl_car 在建立時觸發 car_created，租車公司、監理站等其他類別有興趣就處理它。這裡的事件不是 ABAP 執行期事件（INITIALIZATION、START-OF-SELECTION 等），也不是背景作業或工作流事件。

特性：事件讓物件之間的耦合比直接呼叫方法更鬆——觸發者不需要知道誰會處理，處理者的反應也與觸發者無關。這很適合 GUI（例如 ALV 的 double_click）；COM、ActiveX 等其他物件模型也都支援事件。

步驟語法規則
1. 定義事件EVENTS evt EXPORTING VALUE(p) TYPE …／CLASS-EVENTS事件只能有 EXPORTING 參數，且必須傳值
2. 觸發事件RAISE EVENT evt EXPORTING p = …實例方法可觸發實例與靜態事件；靜態方法只能觸發靜態事件
3. 定義處理方法METHODS on_evt FOR EVENT evt OF class IMPORTING p sender只能 IMPORTING 事件定義中的參數（不能自己定型別）；實例事件另有隱含參數 sender（觸發物件的參照）
4. 註冊SET HANDLER lo_h->on_evt FOR lo_sender／FOR ALL INSTANCES；靜態事件不加 FOR只有註冊過的處理方法會被呼叫；註冊只在執行期有效（不持久）
5. 取消註冊SET HANDLER … ACTIVATION space預設 ACTIVATION 'X'（註冊）
  • RAISE EVENT 的效果：程式流程在該點中斷 → 依序呼叫所有已註冊處理方法 → 全部執行完才繼續；處理方法內再觸發事件就形成巢狀。
  • 每個定義事件的物件都有一張處理者表（內部內表）；註冊時寫入、觸發時照表呼叫。
  • 多個處理者的呼叫順序沒有定義，不能依賴順序。處理中途新註冊的處理者排到最後、輪到時會執行；中途取消註冊的會從序列中移除。
  • 註冊給仍活著的事件的物件也會保持活著，即使程式已沒有任何參照指向它——事件處理者表本身就是一個參照，GC 不會回收。忘記取消註冊是 OO 程式常見的記憶體洩漏。
  • 可見性：事件本身可為 PUBLIC（所有使用者可處理）、PROTECTED（類別與子類別）、PRIVATE（只有類別內部）；處理方法的可見性要與事件相同或更嚴格，並決定 SET HANDLER 可以寫在哪裡。
  • 處理方法也可以像一般方法一樣被直接呼叫。
  • 介面中的事件（Unit 5 L2）：事件也可以定義在介面中，實作類別以 RAISE EVENT lif~evt 觸發；處理方法寫 FOR EVENT evt OF lif_xxx，再以 FOR ALL INSTANCES 註冊，就能一次接收「所有實作該介面的類別」的事件。

13. 全域類別、全域介面與 Class Builder（Unit 6／2007 第十二單元）

區域類別/介面只在所屬程式中使用，不是 TADIR 項目，也無法被其他程式存取；全域類別/介面則是獨立的 Repository 物件，享有啟用、版本管理、傳輸等所有 Workbench 功能，命名空間與其他 Repository 物件相同（Y*、Z* 或客戶命名空間），全域類別與全域介面共用同一個命名空間。維護工具是 SE24 Class Builder（也可在 SE80 導覽區按右鍵建立）；每個方法的實作存在自己的 include，因此方法可以個別傳輸。

建立類別時的選項（2007 版對話框）：實例建立（Instantiation：Public／Protected／Private／Abstract，預設 Public）、例外類別、持久類別、Final（繼承樹末端）、Only Modeled（只為建模）。Class Builder 各頁籤：Properties（父類別、實例化、Final）、Interfaces、Friends、Attributes、Methods（Parameter 按鈕編簽名、Source Code 按鈕寫實作、Constructor 按鈕自動建立建構子）、Events、Types、Aliases。

  • 測試環境：啟用後按 F8（Class → Run → In Test Environment），靜態組件直接可測，實例組件要先按 Create Instance；只列 public 組件；可註冊處理者測事件。
  • 在程式中使用：把類別名從導覽區拖到編輯區，自動產生 CREATE OBJECT 與建構子參數；拖方法名產生呼叫敘述。建議在 Utilities → Settings → Pattern 勾選 Functional Writing Style for Call Method，產生現代寫法。
  • 全域介面：命名 SAP 用 IF_、客戶用 ZIF_／YIF_；在類別的 Interfaces 頁籤加入後，介面方法以 介面~方法 自動列在 Methods 頁籤，雙擊實作。
  • 把區域類別匯入成全域類別：SE24 → Object type → Import → Local classes in program（不能從 Object Navigator 執行），輸入主程式名（類別在 include 中時勾 Explode INCLUDEs）→ Display Classes/Interfaces → 輸入全域名稱（注意客戶命名空間）→ Import。
  • UML 產生：NW 7.0 EhP2 起可對套件產生 UML 類別圖（選套件顯示全域類別；選程式則顯示區域類別與全域介面）。
  • 全域類別的繼承：Properties 頁籤按 Superclass 指定父類別；要重定義就選方法按 Redefine；子類別按 CONSTRUCTOR 時系統會建議沿用父類別建構子簽名並產生 super 呼叫。
  • 全域類別中的區域型別：兩個 include——Class-Relevant Local Definitions（舊稱 Local Types，放 private section 會用到的區域型別/類別，例如方法參數型別）與 Local Definitions/Implementations（舊稱 Local Class Implementations，放其他區域類別、區域介面）；另有 Test Classes include 放 ABAP Unit（第 17 節）。
  • 顯示設定：User-Specific Settings 的 Group by Classes and Interfaces 可把繼承/介面組件分組顯示；Sort 按鈕可依五種條件分三層排序。
Class Pool 的結構（在 ADT 或 SE24 → Source Code-Based 模式可直接看到）：一個全域類別就是一支 CLASS-POOL 程式，裡面有 CLASS zcl_xxx DEFINITION PUBLIC 與 IMPLEMENTATION。SE24 的 Form-Based 表格編輯與 Source Code-Based 編輯可切換；ADT 只有原始碼模式。
S/4HANA 現況：SAP 對新開發的建議工具是 ADT（Eclipse），SE24 仍可用但不再新增功能；而且 CDS View、RAP 行為定義、ABAP Cloud 物件只能在 ADT 維護（見第 15 節、5-5 章）。全域類別的傳輸與套件規則見 1-1 章。

14. OO 應用實例：ALV Grid Control 與 BAdI（Unit 7／2007 第十二單元第三課）

SAP Control Framework 是一組全域類別與介面，讓你在 ABAP Objects 程式中加入與平台無關的 SAP GUI 控制項。ALV Grid Control 用標準化表格顯示非階層式清單，內建排序、篩選、隱藏欄位、合計、列印、匯出等功能，開發者可隱藏標準功能或在工具列加自己的功能。Container Control 提供畫面與應用控制項（ALV Grid、Tree、Picture）之間的技術連結；容器本身也是控制項，可以巢狀，是其控制項的 parent。

原教材步驟：① 用 Screen Painter 全螢幕編輯器在畫面上畫 Custom Control 區（固定大小）；② 建立 CL_GUI_CUSTOM_CONTAINER 實例並傳入區域名稱；③ 建立 CL_GUI_ALV_GRID 實例並把容器參照傳給 i_parent（ALV 物件以私有屬性記住自己屬於哪個容器）；④ 呼叫 SET_TABLE_FOR_FIRST_DISPLAY 傳入內表（行型別是 DDIC 結構時可傳 i_structure_name，系統自動產生欄位目錄）；之後內容改變只要在該對話步驟呼叫 REFRESH_TABLE_DISPLAY。

教材注意事項與錯字：傳給 SET_TABLE_FOR_FIRST_DISPLAY 的內表必須是全域的（程式全域變數或類別的公開/私有屬性），因為控制項在之後的對話步驟仍會存取它；傳區域變數會出現空白或 DUMP。Col18 p198 寫的 CL_GUI_GUI_ALV_GRID 是錯字，正確為 CL_GUI_ALV_GRID。Enjoy 控制項示範程式可在 DWDM（Development Workbench Demos）找到。

BAdI（Business Add-In）：與 Customer Exit 不同，BAdI 針對「多層交付鏈」最佳化：SAP → 夥伴（例如產業解決方案 IBU）→ 客戶都可能要擴充同一支程式。BAdI 以介面＋實作該介面的 adapter 類別提供擴充點；介面可被交付鏈中多方實作（多重實作），實作本身也可以再提供 BAdI。

16. 類別式例外（Unit 9／2007 第十四單元）

例外是「程式已無法依正常流程繼續」的狀況。SAP NetWeaver AS 6.10 引入以類別為基礎的例外概念，與既有的 sy-subrc 機制並存。例外以例外物件（例外類別的實例）表示，屬性值描述錯誤狀況；「觸發」＝建立例外物件並設定屬性，「處理」＝評估例外物件。類別式例外不限於 OO 環境，任何處理區塊都能觸發與處理；以前「可捕捉的執行期錯誤」也都能當類別式例外處理。

父類別語法檢查未處理也未宣告時典型成員
CX_STATIC_CHECK（預設）必須處理或以 RAISING 宣告，否則語法檢查警告執行期錯誤應用程式自己定義的錯誤狀況
CX_DYNAMIC_CHECK不檢查執行期若發生卻未處理/未宣告 → 執行期錯誤多數 CX_SY_…（除以零 CX_SY_ZERODIVIDE、溢位 CX_SY_ARITHMETIC_OVERFLOW、轉型 CX_SY_MOVE_CAST_ERROR）
CX_NO_CHECK不能用 RAISING 宣告自動往上傳遞到最頂層，仍未處理則執行期錯誤資源不足等「隨時可能發生」的錯誤
  • 所有例外類別都繼承自 CX_ROOT（可用 REF TO CX_ROOT 泛型接收），但新例外類別不能直接繼承 CX_ROOT，必須繼承上述三者之一。全域例外類別命名 <namespace>CX_（客戶 ZCX_），執行環境用的是 CX_SY_，區域例外建議 LCX_。
  • CX_ROOT 的方法：GET_SOURCE_POSITION（主程式/include 名與行號）、GET_TEXT（例外文字字串；新版教材指出它定義在 CX_ROOT 實作的介面 IF_MESSAGE 中）、GET_LONGTEXT；屬性 TEXTID、PREVIOUS、IS_RESUMABLE、KERNEL_ERRID（由執行環境觸發時存執行期錯誤名稱，例如除以零的 COMPUTE_INT_ZERODIVIDE）。
  • TRY 結構：TRY 區塊放要保護的程式；CATCH 可列任意多個例外類別（含其子類別），依序比對、執行第一個符合者——所以子類別要寫在父類別前面；找不到就往外層 TRY、再往呼叫者傳遞；因此離開而由外層處理時，本層的 CLEANUP 區塊會先執行。TRY、CATCH、CLEANUP 區塊內都可再巢狀 TRY。
  • CATCH … INTO：取得例外物件參照；參照型別決定能存取哪些組件（REF TO CX_ROOT 只能用 CX_ROOT 的組件）。沒有 INTO 時系統為了效能不會真的建立例外物件，除錯器的 Last Exception Object 按鈕也不會出現（可在除錯器設定中強制建立）。除錯時「Exception Raised」欄位顯示例外類別名。
  • 傳遞（Propagation）：區域類別方法與副程式直接在簽名寫 RAISING cx_a cx_b；全域類別方法在 Class Builder 的例外表勾選 Exception Class；函數模組在 Function Builder 的 Exceptions 頁籤勾選。同一個程序只能用一種例外（類別式或傳統式）。最高只能傳到「沒有區域資料的處理區塊」——事件區塊（START-OF-SELECTION 等）與對話模組，那裡一定要處理，否則執行期錯誤。
  • 例外文字：6.40 以前存在 OTR（Online Text Repository），6.40 起可勾選 With Message Class，重用 T100（SE91）訊息；同一個例外類別不能混用兩者。文字可用 &屬性名& 帶參數；第一個文字一律用與類別同名的預設常數 ID，其他文字的 ID 由 Class Builder 產生同名 public 常數，觸發時傳給建構子參數 TEXTID。公開屬性會自動加到建構子成為同名可選 IMPORTING 參數。
  • 觸發：RAISE EXCEPTION TYPE cx [EXPORTING …]（建立新物件）或 RAISE EXCEPTION lx_obj（重拋既有物件，通常來自前一個 CATCH INTO）。

CATCH 之後可以怎麼做（Unit 9 L3）：① 在 ENDTRY 之後繼續（忽略、發警告、寫日誌、修正狀況）；② 排除原因後重來——RETRY 回到 TRY 區塊開頭，或 RESUME 回到觸發點的下一行（兩者都是 NW 7.0 EhP2 起）；③ 再拋出同一個物件或新例外。RETRY 要小心：沒真正排除原因就會無限迴圈。

可續行例外（Resumable）的三個前提：① 以 RAISE RESUMABLE EXCEPTION 觸發；② 傳遞途經的每一層都以 RAISING RESUMABLE( cx_… ) 宣告；③ 以 CATCH BEFORE UNWIND 捕捉，讓例外發生處的上下文在 CATCH 期間保持存活。處理者應先檢查 IS_RESUMABLE；對不可續行的例外 RESUME 會造成 CX_SY_ILLEGAL_HANDLER 執行期錯誤。

例外映射（Mapping）與串鏈：離開 CATCH 區塊後例外物件就失效，最上層只能看到最後一個例外；把舊例外物件傳給新例外建構子的 PREVIOUS 參數，就能形成串鏈，最上層沿 PREVIOUS 逐層追溯整個呼叫階層的錯誤歷史。

17. ABAP Unit 單元測試（Unit 10，2007 版無）

單元測試是開發者驗證「最小可測單位」（例如方法）行為的流程，讓品質保證、重構、回歸測試與測試驅動開發（TDD）更容易。ABAP Unit 是內建於語言的測試框架：

  • 測試寫成區域測試類別（全域類別放在 Test Classes include），扮演使用者角色，只應存取受測類別的 public 組件；每個測試方法獨立執行。
  • 測試類別加 FOR TESTING，並以 RISK LEVEL（HARMLESS／DANGEROUS／CRITICAL，例如會更新持久資料）與 DURATION（SHORT／MEDIUM／LONG）分類；測試方法是無參數的實例方法（建議 private）、同樣加 FOR TESTING。
  • 測試碼隨 Repository 物件一起傳輸，但 profile 參數 abap/test_generation 決定哪些系統產生測試 load，生產系統通常不產生，不影響效能。一般程式碼不能存取測試類別（編譯器禁止）。
  • CL_ABAP_UNIT_ASSERT 的靜態方法 ASSERT_EQUALS、ASSERT_DIFFERS、ASSERT_BOUND、ASSERT_NOT_BOUND、ASSERT_INITIAL、ASSERT_TRUE、ASSERT_SUBRC、FAIL 等；參數 act（實際值）、exp（期望值）、msg（訊息）、level（TOLERABLE／CRITICAL／FATAL）、quit（NO／METHOD／CLASS／PROGRAM）；回傳 assertion_failed。
  • Fixture 方法（固定名稱、private、無參數）：SETUP（每個測試方法前）、TEARDOWN（每個後）、CLASS_SETUP（靜態，第一個測試前一次）、CLASS_TEARDOWN（靜態，最後一個測試後一次）。執行順序：建立測試類別內部 session → 類別建構 → CLASS_SETUP →〔每個測試方法：建立實例 → SETUP → 測試方法 → TEARDOWN〕→ CLASS_TEARDOWN。使用同一個 fixture 的測試必須放在同一個測試類別；有繼承時 setup 由父到子、teardown 由子到父。
  • 執行：Workbench：Program → Execute → Unit Tests（類別：Class → Run → Unit Tests）；ADT：Run As → ABAP Unit Test（Ctrl+Shift+F10）；大量測試：ATC 檢查 BC_AUNIT／BC_AUNIT_M／BC_AUNIT_L，或 SCI 檢查變式的 Dynamic Tests → ABAP Unit；可對整個套件執行。
  • 覆蓋率：Execute → Unit Tests With → Coverage（ADT：Coverage As → ABAP Unit Test）；Statement（綠/紅）、Branch（綠＝真假都跑過、黃＝只跑過一邊、紅＝沒跑）、Procedure 覆蓋率，ADT 直接在原始碼上標色。

18. 進階 OO 技巧（Unit 11 L1／2007 第十三單元第一～二課）

抽象類別（ABSTRACT）：有定義也可有實作，但不能實例化；典型用途是父類別——自己不被實例化，子類別才被實例化，並作為「不完整藍圖」統一介面。抽象類別中可定義抽象方法（只宣告、不實作），第一個非抽象子類別必須以 REDEFINITION 實作它。抽象類別的參照仍然非常有用，可多型地指向子類別實例（2007 版教材的 CREATE OBJECT ref TYPE 子類別，現代寫法為 NEW 子類別( )）。靜態方法與建構子不能是抽象的（無法重定義）。

筆記更正：强晟筆記 p243 寫「只要包含了一個抽象方法的類就是抽象類」，容易誤會成「系統會自動視為抽象」。實際上 ABAP 要求明確在 CLASS 敘述加 ABSTRACT，非抽象類別宣告抽象方法會語法錯誤。

Final：CLASS … FINAL 不能被繼承（避免失控的特殊化）；METHODS … FINAL 不能被重定義。Final 類別的方法隱含 final，不能再重複寫 FINAL；方法不能同時 FINAL 又 ABSTRACT；同時 ABSTRACT 又 FINAL 的類別只應包含靜態組件（工具類別的常見寫法）。在 Class Builder 中這些旗標在 Attributes／Properties 頁籤。

含物件參照的內表：用內表存參照是實作關聯（association）的標準方式。要依條件找出某個物件，可以：① 在內表同時存鍵值與參照（造成資訊重複）；② 把鍵屬性設為 PUBLIC READ-ONLY，在 READ TABLE／LOOP 中用 table_line->attr 直接比對。原教材坦承：公開屬性違反 OO 原則，只因為 ABAP 不允許在 WHERE 與 WITH KEY 左側用功能性方法，所以只在唯讀的特殊情況使用。

導覽方法與方法串接：回傳所關聯物件參照的方法稱為導覽方法（navigation method），例如 LCL_RENTAL 的 GET_VEHICLE；可直接串接 lo_rental->get_vehicle( 1 )->display( )，串接層數不限。

NEW 運算子（7.40）：取代 CREATE OBJECT；NEW #( ) 由目標變數推導類別，建立子類別實例時要明寫類別名；只能傳建構子的 IMPORTING 參數，不能處理傳統 sy-subrc 例外，類別式例外照樣用 TRY 包起來。NEW 可放在各種運算式位置（APPEND 的來源、方法實參、巢狀建立 ALV 容器）。IS INSTANCE OF（7.50）判斷參照是否指向某類別或其子類別的實例；CASE TYPE OF（7.50）依動態型別分支，WHEN TYPE … INTO 順便完成 Down-Cast（範例見第 10 節）。

19. Factory、Singleton 與 Friendship（Unit 11 L2–L3／2007 第十三單元第二～三課）

Factory 方法：限制建構子可見性之後，類別通常提供一個 public 靜態方法建立實例並回傳參照，這就是 factory 方法。相較於建構子的優點：

  • 實例化之前就能執行程式：檢查、讀資料庫、上鎖；出錯就不建立實例、不配記憶體。
  • 可以有多個 factory 方法，各有不同簽名與實作（例如一個傳全部屬性建立新實例、一個只傳鍵值再從資料庫讀其他屬性）——彌補 ABAP 不能多載的限制。
  • 可以在類別內管理實例：把每個實例參照存在 private 靜態內表，呼叫時先查是否已有相同鍵的實例，有就回傳既有的，避免重複建立。因為 factory 在類別內，可直接讀私有屬性，不需要把鍵屬性公開。
  • 可以依條件建立子類別實例，例如依機型決定建立貨機或客機。

Singleton：確保同一個程式上下文中類別只被實例化一次。三種寫法：① factory 方法 GET_INSTANCE 第一次呼叫時建立、之後回傳同一個；② 在靜態建構子中預先建立，GET_INSTANCE 只回傳；③ 把靜態屬性 GO_INSTANCE 設為 PUBLIC READ-ONLY，連 GET_INSTANCE 都不需要。

筆記錯誤修正：强晟筆記 p245 寫「如果允許多次實例化一個類（例如作為資料管理員或資料容器），可以使用單獨概念（Singleton）」，意思正好相反：Singleton 是「只允許實例化一次」，作法是類別宣告 CREATE PRIVATE＋FINAL，在靜態建構子中建立唯一實例，再以公開靜態組件提供給外界。

Friendship：有些類別必須緊密合作，需要存取彼此的 protected／private 組件，或不受建構子可見性限制建立對方實例；為了不把這些能力開放給所有人，類別可以用 FRIENDS 附加（或 Class Builder 的 Friends 頁籤）把友誼授予其他類別與介面（進而授予所有實作該介面的類別）。規則：

  • 授予是單向的：授予友誼的類別不會自動成為對方的朋友。
  • 「朋友」身分會被繼承：朋友的子類別、以及把朋友介面當組件介面的介面，也都成為朋友——所以授予友誼要極度謹慎，朋友在繼承樹越上層，能存取的子類別越多。
  • 「授予」不會被繼承：父類別的朋友不會自動成為其子類別的朋友。
  • 典型應用是 Factory 類別：LCL_AIRPLANE 宣告 CREATE PRIVATE FRIENDS lcl_factory，只有 LCL_FACTORY 能建立飛機並讀私有屬性；把實例管理外包給專責類別，讓 LCL_AIRPLANE 更小、更好懂，也能由 factory 決定建立 LCL_CARGO_PLANE 或 LCL_PASSENGER_PLANE。持久化服務的類別代理（第 21 節）就是這個模式。

20. 動態程式設計與 RTTI（2007 第十五單元／Unit 12）

Field symbol 細節：用 FIELD-SYMBOLS <fs> 宣告（角括號是名稱的一部分），ASSIGN do TO <fs> 指向資料物件後，所有存取都作用在該資料物件上（值語意，類似被解參照的指標）；泛型 TYPE any 會採用資料物件的型別，指定具體型別則只能指派相容物件。<fs> IS ASSIGNED 檢查是否已指派，UNASSIGN 取消。CASTING／CASTING TYPE t／CASTING TYPE (name) 讓存取「好像資料物件是另一個型別」（原教材例：把 c 長度 65535 的 line 以透明表行型別存取；前面放一個 i 型 dummy 是為了對齊）。

動態指定語法元素：靜態文字的地方換成變數（CALL TRANSACTION lv_tcode）；靜態識別字的地方換成括號中的變數，括號與變數之間不能有空白（SUBMIT (lv_prog)）；清單換成內表（SET PF-STATUS … EXCLUDING lt_fcodes）；文字內容必須大寫。ABAP SQL 的 WHERE、FROM（含 JOIN）、GROUP BY、HAVING、欄位清單都可動態指定。動態方法呼叫：CALL METHOD lo->(lv_meth) PARAMETER-TABLE lt_ptab EXCEPTION-TABLE lt_etab；參數表型別 ABAP_PARMBIND_TAB（NAME、KIND、VALUE＝REF TO data），例外表型別 ABAP_EXCPBIND_TAB（NAME、VALUE＝要給 sy-subrc 的整數）。

資料參照：TYPE REF TO type 或泛型 TYPE REF TO data；初始為空指標；以 GET REFERENCE OF do INTO ref（7.40 起 REF #( do )）取得參照，或以 CREATE DATA ref TYPE (lv_type)／TYPE STANDARD TABLE OF (lv_tab) 在執行期建立匿名資料物件（只能透過參照存取）。解參照：有完整型別可直接 ref->comp／ref->*；泛型參照要 ASSIGN ref->* TO <fs>（成功 sy-subrc＝0；參照為空或無效則 4，field symbol 不變）。

RTTI（Run Time Type Identification）：以類別為基礎的型別描述系統，涵蓋所有 ABAP 型別，取代已過時的 DESCRIBE FIELD／DESCRIBE TABLE（6.10 起有內建函數 lines( )）。描述類別的階層對應 ABAP 型別階層：CL_ABAP_TYPEDESCR → CL_ABAP_DATADESCR（ELEMDESCR、STRUCTDESCR、TABLEDESCR、REFDESCR）／CL_ABAP_OBJECTDESCR（CLASSDESCR、INTFDESCR）。用 CL_ABAP_TYPEDESCR 的靜態方法 DESCRIBE_BY_DATA、DESCRIBE_BY_NAME、DESCRIBE_BY_OBJECT_REF、DESCRIBE_BY_DATA_REF 取得描述物件；回傳型別是父類別參照，所以要 Down-Cast 成具體描述類別。每個型別在執行期只有一個描述物件。結構描述的 COMPONENTS 屬性是內表；物件描述的 GET_RELATIVE_NAME( ) 回傳類別名。

21. 持久化物件與 OO Transaction（Unit 13／2007 第十三單元第四課）

持久化服務（Persistence Service）：ABAP 程式執行期的資料與物件是暫時的（transient），程式結束就消失；要永久保存就得寫進資料庫。SAP R/3 6.10 起提供 ABAP Objects 的持久化服務：開發者可把物件目前的屬性值寫進對應的透明表，也能把表中的值讀回事先定義為持久的物件；底層使用 Open SQL。等於用關聯式資料庫＋ABAP Objects「模擬」物件導向資料庫。

  • 在 Class Builder 建立持久類別（Persistent Class）ZCL_<name>，表示其實例與狀態由持久化服務管理；實例必須有鍵屬性——全球唯一的 GUID 或語意鍵；Class Builder 自動產生各屬性的 GET/SET 方法。
  • 同時產生類別代理（Class Agent／Class Actor）ZCA_<name> 與其抽象父類別 ZCB_<name>：程式必須透過代理的方法管理持久物件，代理也負責實際資料庫存取；代理從 CB 類別繼承方法、可重定義（例如擴充 DB 存取），CB 類別不能修改。代理是 CREATE PRIVATE 的 Singleton，並且是持久類別的 friend。
  • 靜態屬性 AGENT：第一次存取時代理的靜態建構子建立唯一實例；全部程式只有一個代理物件，無法從外部 CREATE OBJECT。
  • 建立：agent->create_persistent( 鍵… )；同鍵物件已存在於程式中則丟 CX_OS_OBJECT_EXISTING。預設以非同步更新寫入，必須 COMMIT WORK 之後才真正成為持久物件。
  • 讀取單筆：get_persistent( 鍵… )，找不到丟 CX_OS_OBJECT_NOT_FOUND；多筆用 Query Service（可給類似 WHERE 的條件與排序）。
  • 建立持久類別步驟：① 建模；② 找或建一張透明表，每個屬性一個欄位（必要時調整屬性型別）——表的每個主鍵欄位都要對應類別的鍵屬性；③ 在 Class Builder 建立持久類別並定義 Persistence Mapping。

OO Transaction：在 SE93 建立交易碼時，Initial Object 選 Method of a Class (OO Transaction)，把交易碼連到：① 勾選 OO Transaction Model＝連到持久物件的交易服務；② 不勾選＝連到全域類別或某程式區域類別（勾 Local in Program 並填程式名）的任意 public 方法。呼叫連到實例方法的 OO 交易時，系統會在自己的內部 session 自動建立該類別實例再執行方法。

OO Transaction 的限制：全域類別不能包含畫面定義，所以連到全域類別時：建構子不能有 IMPORTING 參數、不能處理 ABAP 清單輸出。違反時不會有語法錯誤或擴充檢查訊息，而是執行期錯誤或畫面一片空白——必要時改連到程式中的區域類別，就能用所有傳統對話技術；畫面欄位仍需要程序式的框架程式。
S/4HANA 現況：Object Services 持久化類別仍在系統中，但 SAP 已不再推廣，新專案幾乎不會用。現代替代方案是 CDS View Entity ＋ RAP 商業物件（Managed 情境由框架處理 CRUD、鎖、交易緩衝與 COMMIT；Unmanaged 情境自己寫儲存邏輯），前端用 Fiori Elements／OData V4。若只是想把 SQL 包進類別，直接寫 DAO 類別（ABAP SQL＋介面）即可，也更容易寫 ABAP Unit。資料庫更新、LUW 與鎖物件見 5-11 章 BC414。

22. 綜合案例：航班候補名單（Unit 14）

CLASS lcl_waitlist_buffer DEFINITION DEFERRED.

CLASS lcl_waitlist DEFINITION CREATE PRIVATE FRIENDS lcl_waitlist_buffer.
  PUBLIC SECTION.
    TYPES: BEGIN OF ty_key,
             carrid TYPE s_carr_id,
             connid TYPE s_conn_id,
             fldate TYPE s_date,
           END OF ty_key.
    EVENTS customer_moved_up EXPORTING VALUE(ev_customid) TYPE s_customer.
    DATA ms_key TYPE ty_key READ-ONLY.
    METHODS constructor IMPORTING is_key TYPE ty_key.   "CREATE PRIVATE：只有自己與 friend 能 NEW
    METHODS add_customer    IMPORTING iv_customid TYPE s_customer
                            RAISING   zcx_bc401_flight.
    METHODS remove_customer IMPORTING iv_customid TYPE s_customer.
    METHODS get_position    IMPORTING iv_customid TYPE s_customer
                            RETURNING VALUE(rv_pos) TYPE i.
    METHODS move_up_first.                                   "有空位時遞補第一位
  PRIVATE SECTION.
    DATA mt_customers TYPE STANDARD TABLE OF s_customer WITH EMPTY KEY.  "順序即順位
ENDCLASS.

CLASS lcl_waitlist_buffer DEFINITION FINAL CREATE PRIVATE.
  PUBLIC SECTION.
    CLASS-METHODS get_instance RETURNING VALUE(ro_buffer) TYPE REF TO lcl_waitlist_buffer.
    METHODS get_or_create IMPORTING is_key TYPE lcl_waitlist=>ty_key
                          RETURNING VALUE(ro_list) TYPE REF TO lcl_waitlist.
    METHODS delete_list   IMPORTING is_key TYPE lcl_waitlist=>ty_key.
  PRIVATE SECTION.
    CLASS-DATA go_instance TYPE REF TO lcl_waitlist_buffer.
    TYPES: BEGIN OF ty_entry,
             key  TYPE lcl_waitlist=>ty_key,
             list TYPE REF TO lcl_waitlist,
           END OF ty_entry.
    DATA wait_list TYPE HASHED TABLE OF ty_entry WITH UNIQUE KEY key.   "教材的 WAIT_LIST
ENDCLASS.

CLASS lcl_waitlist IMPLEMENTATION.
  METHOD constructor.
    ms_key = is_key.
  ENDMETHOD.
  METHOD add_customer.
    IF line_exists( mt_customers[ table_line = iv_customid ] ).
      RAISE EXCEPTION TYPE zcx_bc401_flight.                 "同一客戶不可重複登記
    ENDIF.
    APPEND iv_customid TO mt_customers.
  ENDMETHOD.
  METHOD remove_customer.
    DELETE mt_customers WHERE table_line = iv_customid.
  ENDMETHOD.
  METHOD get_position.
    rv_pos = line_index( mt_customers[ table_line = iv_customid ] ).   "0＝不在名單
  ENDMETHOD.
  METHOD move_up_first.
    CHECK mt_customers IS NOT INITIAL.
    DATA(lv_first) = mt_customers[ 1 ].                      "內表順序由程式維護，不靠 DB 排序
    DELETE mt_customers INDEX 1.
    RAISE EVENT customer_moved_up EXPORTING ev_customid = lv_first.
  ENDMETHOD.
ENDCLASS.

CLASS lcl_waitlist_buffer IMPLEMENTATION.
  METHOD get_instance.
    IF go_instance IS NOT BOUND.
      go_instance = NEW #( ).
    ENDIF.
    ro_buffer = go_instance.
  ENDMETHOD.
  METHOD get_or_create.
    ro_list = VALUE #( wait_list[ key = is_key ]-list OPTIONAL ).
    IF ro_list IS NOT BOUND.
      ro_list = NEW #( is_key ).                             "friend 才能 NEW
      INSERT VALUE #( key = is_key list = ro_list ) INTO TABLE wait_list.
    ENDIF.
  ENDMETHOD.
  METHOD delete_list.
    DELETE TABLE wait_list WITH TABLE KEY key = is_key.
  ENDMETHOD.
ENDCLASS.

練習與自我檢核

  1. 型別題：DATA lv TYPE i. lv = 5 / 10. 結果是多少？為何原教材 73050×0.0727 的例子用 f 算會得到 5310.73？
    要點：1（整數運算四捨五入）；f 是二進位分數，0.0727 無法精確表示，結果 5310.7349999…，轉成 p 時四捨五入成 .73。商業運算用 p（或 decfloat34）。
  2. 內表題：要以完整鍵讀單筆、且表有 10 萬筆，該選哪種表種類？只有部分鍵呢？標準表能宣告 UNIQUE KEY 嗎？
    要點：HASHED（與行數無關）；部分鍵選 SORTED（前 n 個鍵欄位用 = 可二分）；標準表只能 NON-UNIQUE。
  3. 記憶體題：程式 A 以 LEAVE TO TRANSACTION 呼叫 B，B 能 IMPORT 到 A EXPORT TO MEMORY 的資料嗎？改成 CALL TRANSACTION 呢？
    要點：不能——以 TCODE 重新開始會清空整個外部 session 的 ABAP Memory；CALL TRANSACTION 是插入，可以。SAP Memory（SET/GET PARAMETER）兩種都可以。
  4. 建構子題：說出實例建構子與靜態建構子各自何時被呼叫、各有哪些限制；建構子丟出例外時物件會怎樣？
    要點：實例：每次 NEW/CREATE OBJECT，可有 IMPORTING 與 RAISING；靜態：每個內部 session 第一次存取類別時一次，無參數；建構子例外 → 物件不建立。子類別建構子必須先 super->constructor( )。
  5. 轉型題：2007 版的「Narrowing Cast」「Widening Cast」各對應新版哪個術語？哪一個需要 TRY/CATCH？7.50 以後有哪兩種免例外的寫法？
    要點：Narrowing＝Up-Cast（安全）、Widening＝Down-Cast（可能丟 CX_SY_MOVE_CAST_ERROR）；IS INSTANCE OF、CASE TYPE OF … WHEN TYPE … INTO。
  6. 多型題：在 lcl_rental 新增 lcl_motorbike 子類別，calc_estimated_fuel 需要改幾行？為什麼？
    要點：0 行；呼叫依動態型別找實作，只要 lcl_motorbike 重定義 estimate_fuel。
  7. 介面題：為什麼介面只能在 PUBLIC SECTION 實作？複合介面的組件在實作類別中叫什麼名字？
    要點：避免父子類別各自私下實作同一介面；組件保持原介面名 lif_partner~display_partner，不加複合介面前綴。
  8. 事件題：事件處理方法沒被呼叫，列出三個可能原因；為什麼處理者物件沒被垃圾回收？
    要點：沒 SET HANDLER；在物件建立後才註冊但事件在建構子觸發（應 FOR ALL INSTANCES 且先註冊）；處理方法 FOR EVENT 指錯類別或可見性不足；處理者表持有參照，所以不會被回收，需 ACTIVATION space 取消註冊。
  9. 例外題：CX_STATIC_CHECK／CX_DYNAMIC_CHECK／CX_NO_CHECK 的差別？RESUME 的三個前提？
    要點：見第 16 節表；RAISE RESUMABLE、每層 RAISING RESUMABLE( )、CATCH BEFORE UNWIND（再檢查 IS_RESUMABLE）。
  10. 設計模式題：用 CREATE PRIVATE＋FINAL＋靜態建構子寫一個 Singleton；並說明 friend 關係「被繼承」與「不被繼承」各指什麼。
    要點：見第 19 節程式；朋友的子類別也是朋友（身分被繼承），父類別的朋友不是子類別的朋友（授予不被繼承）。
  11. ABAP Unit 題：SETUP 與 CLASS_SETUP 差在哪？為什麼生產系統跑不到測試類別？
    要點：每個測試方法前 vs 整個測試類別一次（靜態）；profile 參數 abap/test_generation 通常只在開發/測試系統產生測試 load。
  12. 動態題：寫一支程式，讓使用者輸入表名後顯示前 20 筆，需要注意哪兩件安全問題與一件 HANA 問題？
    要點：CL_ABAP_DYN_PRG 驗證表名、S_TABU_DIS/S_TABU_NAM 權限；ORDER BY PRIMARY KEY 才有穩定順序。
  13. 找錯題：指出以下原教材寫法在 S/4HANA 新程式中的問題：DATA itab TYPE scarr OCCURS 0 WITH HEADER LINE、MOVE a ?TO b、DESCRIBE TABLE itab LINES n、CALL METHOD cl_exithandler=>get_instance、持久化類別。
    要點：表頭行/OCCURS 過時且類別中禁用；改用 ?= 或 CAST；改用 lines( )；新開發用新式 BAdI（GET BADI/CALL BADI）；持久化服務改用 CDS＋RAP 或 DAO 類別。
  14. 實務題：客戶要在銷售訂單儲存時多檢查一個欄位，依 Casper「先標準再客製」原則，你的評估順序為何？
    要點：先查標準設定（不完整日誌、需求類型、SPRO）→ 找 BAdI／Enhancement Spot（SE18、搜尋 GET BADI）→ User Exit（MV45AFZZ）或隱含增強點 → 最後才考慮修改標準；每往後一步升級成本大增。
