2. 資料傳輸的任務與五種方法總覽

為什麼不能直接寫資料庫？外部資料直接進 R/3 表無法保證資料一致性。線上交易裡的檢查非常多、而且常常跨應用（一張 FI 憑證會檢查科目、成本中心、期間、稅碼…），自己重寫這些檢查幾乎不可能。所以 SAP 提供「特殊介面」，部分直接利用交易本身的檢查，把資料送進系統。

需要傳輸的兩種情境（p8）：① 新裝 SAP，資料要從舊系統一次搬過來（初始移轉）；② 資料固定在外部系統產生，要週期性整合進 SAP。

三個核心名詞（p13，課程全篇沿用）：

  • 格式化（Formatting）：把外部值轉成 SAP 可接受的值集合，例如舊系統語言代碼 E → EN。
  • 分配／對應（Mapping）：決定外部哪個欄位對到 SAP 哪個欄位。
  • 轉換（Conversion）＝格式化＋對應同時進行。

做對應之前要先分析交易（p11）：TCODE、必填欄位、可用預設值的欄位、欄位名稱／型別／長度；再分類（p12）：可直接搬的欄位、要先在外部系統修正的欄位、要轉型別或長度的欄位。轉換可以在哪裡做（p14）：外部系統、SAP 內用 ABAP（好處是自動型別轉換、可直接用 ABAP 字典結構）、Excel（平面結構）、LSMW 對應工具、SAP 認證的外部產品。

3. 專案概念：技術工具、專案組織與商業物件 BOR

第一課：技術與工具（p17–p23）。每個應用都提供自己的傳輸程式，介面各不相同；支援哪幾種方法（Batch Input、Call Transaction、Direct Input、BAPI）完全取決於應用，預期資料量通常是選方法的決定因素。少數應用沒有標準介面，才用交易記錄器（TA），它同時支援 Batch Input 與 Call Transaction。

  • Batch Input 分兩階段：① 建立含所有資料的 Session；② 處理 Session，把資料匯入 R/3。多數 SAP 標準傳輸程式底層都用 Batch Input。
  • Call Transaction：透過線上交易直接提交資料，功能與 Batch Input 相同。
  • Direct Input：檔案被徹底檢查後直接更新資料庫，以函數呼叫取代線上畫面；並非所有應用都有。
  • EDI：ALE 的入站／出站函數模組處理 IDoc，不用線上交易當檢查機制。
  • BAPI：定義在 BOR 中、屬於 SAP 商業物件或介面型別的方法，執行與線上相同的檢查。

第二課：專案組織（p24–p31）。ASAP 路線圖五階段：① 專案準備 ② 業務藍圖 ③ 實施（基線配置＋細節配置兩個工作包）④ 上線準備（系統管理與資料傳輸的測試、使用者訓練）⑤ 上線與支援。ASAP 路線圖中大約有 25 處提到資料傳輸。

  • 資料傳輸專案要為每個應用實施，可拆子專案；組專案團隊、指明任務、分配給成員（一人可兼多角）。
  • 先決條件：Customizing 至關重要。Customizing 一改，檢查與有效值就變，原本傳得過的資料可能就傳不過——所以每次 Customizing 修改後都要重測資料傳輸。
  • 專案任務五件事：萃取、格式化、對應、測試與執行傳輸、檢查資料。
  • 測試要用典型資料，「用 100 筆一模一樣的資料測試是完全沒有用的」；測試三階段：轉成介面格式 → 傳入 R/3 → 在 R/3 驗證。資料錯誤要回舊系統修正，舊系統資料必須百分之百正確。
  • 文件：SXDA →「說明 → 應用程式說明」；SAP Library「跨應用元件 → CA 資料傳輸」。其他外部資料傳輸工作台用於：資金管理 TR、核心業務夥伴、EIS、CO-PA、銀行 BCA；工廠維護物件用 IBIP。

第三課：商業物件（p32–p33）。BOR（Business Object Repository）是 R/3 的核心知識庫，收錄所有 SAP 商業物件型別、介面型別與它們的方法。到 4.6 版為止，所有傳輸程式都以 BOR 物件組織：每個 BOR 物件可以有多種傳輸方法（BAPI 或傳輸程式），所以 BOR 物件能列出自己可用的所有傳輸程式。BOR 的維護工具是商業物件建構器 SWO1，BAPI 瀏覽器是 BAPI。

「先測 10 筆、再加一個數量級」的測試節奏在附錄（p346）有明講，見第 23 節。

4. DX-WB（SXDA）：專案、子專案、Run 與 Task

資料傳輸工作台 DX-WB（SXDA）提供整合的專案管理：專案、子專案、Run（執行）、Task（任務）、排程、建立測試資料、檔案功能，並把標準傳輸程式、BAPI、客戶自己的程式與函數都註冊起來（p34）。「轉到 → 註冊程式」可看到所有商業物件已註冊程式的概覽（DX 庫，p35）。

5. Batch Input Session 的結構與 BDCDATA

Batch Input，又稱 BDC（Batch Data Communication），是不經對話、自動把資料傳入 SAP 的程序（p47）。為了讓檢查與更新跟對話處理完全一樣，它模擬使用者對話；核心元件是 Batch Input Session，由 Batch Input 程式建立，再用批輸入監視器處理。自動處理可用程式 RSBDCSUB（第 22 節）。

  • Batch Input 程式的功能（p48）：以內表（BDC 表）提供結構化工作區、匯入資料、放進 BDC 表、把 BDC 表寫進 Session。BDC 表結構永遠相同。
  • Session 格式（p49）：Session 表頭用字典結構 APQI 描述、交易資料用 APQD 描述；Session 完成（關閉）後才能在監視器處理。
  • 每個 Session 必須開啟與關閉；一個 Batch Input 程式可連續建立多個 Session，但 Session 不能平行建立（p50）。
  • 處理修改類交易時，先合併資料庫既有資料，再合併 Session 資料到畫面上（p52）。
  • Batch Input 一律同步提交；其他方法（Call Transaction）才可能非同步。

BDCDATA 的規則（p51）：每個畫面一筆記錄，用 PROGRAM、DYNPRO、DYNBEGIN='X' 標示；每個欄位值一筆記錄，用 FNAM、FVAL。OK 碼欄位名固定是 BDC_OKCODE：功能鍵用「/＋鍵值」（例如 '/11' 代表 F11）；選單、按鈕用「=＋功能碼」（例如 '=SAVE'）。BDC_CURSOR、BDC_SUBSCR 的用法詳見 4-4 章第 4 節。

7. 標準資料傳輸原則：格式化規則與 SAP 記錄佈局

SAP 交付的標準傳輸程式透過「SAP 記錄佈局結構（Record Layout）」這個介面讀檔，外部資料格式必須相容（p69）。轉換可一步完成，也可分格式化、對應兩步。

格式化規則（p70–p71，使用傳輸程式時）：資料要格式化成和線上使用者用鍵盤輸入一樣——

  • 資料必須是字元格式；
  • 欄位長度不能超過 SAP 欄位定義；
  • 比 SAP 欄位短的要靠左對齊，右邊補空白；
  • 除了 BAPI 與 IDoc 之外，都要考慮使用者特定設定（日期格式、小數點符號、使用者參數檔中的固定值）。線上傳輸用執行者的權限與設定；背景處理必須指定使用者，而這個使用者的設定要一致，權限卻可能不同（例如正式機上真正做傳輸的帳號），權限與設定不一致會造成錯誤（例如沒有該公司代碼的權限）。
  • 注意：BAPI、IDoc 例外，它們吃的是內部格式。

記錄佈局（p72–p76）：標準程式認定檔案就是相應的記錄佈局格式；不必用到所有結構，哪些必填、哪些選用見結構文件。每個佈局的結構都定義在 ABAP 字典裡。

9. 循序檔案：AL11 與 OPEN／READ／TRANSFER／CLOSE DATASET

ABAP 在應用伺服器上執行，支援應用伺服器與前端電腦兩邊的檔案傳輸：應用伺服器檔案用 ABAP 語言元素（OPEN DATASET、READ DATASET、TRANSFER、CLOSE DATASET），展示層檔案用函數（p92）。

檔案監視器 AL11（p93–p95）是 CCMS 工具：瀏覽 R/3 目錄結構（跨伺服器傳輸目錄 \trans、實例目錄 \work、\data、\DVEBMGS..），不能修改伺服器上的資料。左欄是系統內部目錄參數、右欄是實體目錄；DIR_TRANS 是全域傳輸目錄；子目錄長度顯示為 0。

語法筆記（R/3 4.6）說法Unicode／S/4HANA 的正確觀念
OPEN DATASET … FOR INPUT／OUTPUT／APPENDINGINPUT 讀（已開啟則從頭讀，為預設）；OUTPUT 寫（存在則清空、不存在則建立）；APPENDING 追加相同
IN BINARY MODE／IN TEXT MODEBINARY 為預設；BINARY 依結構長度讀寫、TEXT 依記錄結束符；TEXT 模式會刪除行尾空白Unicode 程式必須明確寫模式；TEXT MODE 必須加 ENCODING（UTF-8／DEFAULT／NON-UNICODE）
MESSAGE <field>開檔失敗時回傳作業系統訊息相同，排錯必備
sy-subrc開啟成功 0、失敗 8；READ 到檔尾 4相同；另有 CX_SY_FILE_OPEN、CX_SY_FILE_AUTHORITY、CX_SY_FILE_IO、CX_SY_CONVERSION_CODEPAGE 等例外要 CATCH
隱式開檔沒開檔就 READ／TRANSFER 會以預設模式自動開檔Unicode 程式不再允許，未開啟就讀寫會直接 runtime error——一定要明確 OPEN
TRANSFER … LENGTH <len>只寫前 len 個位元組；結構較短時 TEXT 補空白、BINARY 補 X'00'相同
READ DATASET … LENGTH <len>回傳實際讀到的長度；不做任何隱式轉換TEXT 模式讀入字元型目標
CLOSE DATASET畫面切換時所有檔案被關閉、再開時恢復；程式結束全部關閉；READ 到檔尾不會自動關閉相同；建議在 CLEANUP／finally 位置關檔
DELETE DATASET實體刪除作業系統檔案，成功 sy-subrc = 0相同

11. LSMW 基礎：專案結構、物件屬性與來源結構

LSMW（Legacy System Migration Workbench）是基於 R/3 的工具，支援從非 SAP 系統一次性與週期性傳輸資料：先轉換，再以 Batch Input、Call Transaction、Direct Input、BAPI 或 IDoc 匯入；另有「錄製」功能，可從新增／修改交易產生移轉物件（p123）。LSMW 不是標準 R/3 的一部分，3.0 版起以外掛（Add-on）提供（p124，資訊站 service.sap.com/lsmw，含實施檢查清單與簡報）；後來的 NetWeaver 版本才內建。

核心功能（p125）：從外部讀資料到 LSMW 內部格式 → 依規則格式化與分配 → 呼叫標準傳輸程式／BAPI／IDoc 寫入 R/3。LSMW 從結構定義與轉換規則產生兩支可執行的 ABAP 程式（讀取程式與轉換程式，p127）。

  • 進入：LSMW。三層識別：Project（專案，最多 10 字元；多個外部系統可各建一個專案）→ Subproject（最多 10 字元）→ Object（最多 10 字元，一個商業資料物件）。
  • 初始畫面：All objects、My objects、All objects in a project（樹狀）、Project documentation（可列印、寄送、存成各種格式）。
  • 共有 26 個工作步驟，顯示哪些依物件而定；基本設定只顯示主要步驟，其他可從「Extras → Personal Menu」加入個人選單。主要步驟：定義物件屬性 → 定義來源結構 → 定義來源欄位 → 維護結構關係 → 維護欄位對應與轉換規則 → 指定檔案 → 分配檔案 → 讀取資料 → 轉換資料 → 匯入資料。

物件屬性（p133–p135）：Owner 填使用者名稱，之後會出現在「My objects」；選擇只執行一次或週期性——週期性時不能讀 PC 檔案，並多一個步驟「週期資料傳輸的主程式」。匯入方法四選一：

匯入方法說明
Standard Batch/Direct Input選物件與方法；眼鏡圖示可看程式文件
Batch Input Recording用自己的錄製（第 18 節）；可按箭頭加入更多錄製
Business Object Method（BAPI）選商業物件、方法、訊息類型
IDoc選訊息類型與基本類型
選 BAPI 或 IDoc 並存檔時，系統會檢查夥伴參數是否已存在該訊息類型，沒有就嘗試自動建立（第 16 節）。另外在動手前先印出「物件概覽」做一份紙上對應（p135），把 R/3 目標結構欄位和來源欄位一一對好，這一步省不得。

來源結構的三種型態（p136–p137）：

  • 扁平結構：檔案每一行結構都一樣。
  • 多結構、固定模式：例如一個表頭兩個明細反覆出現，每種記錄類型建一個來源結構。
  • 表頭／明細、隨機模式：每一行第一個位置必須放記錄類型描述，稱為 ID 欄位，定義欄位時要指定。

維護來源結構時，建立多個結構會詢問關係是「相等（扁平）」或「不相等（層級）」。用交易錄製建立的移轉物件，每個錄製只能有一個來源結構，因為錄製只有一個扁平目標結構（p138）。來源欄位的型別決定匯入時的轉換（p139）：日期轉內部格式 YYYYMMDD；金額欄位轉計算格式（1234.56，無千分位，只能用於兩位小數）；PACn 表示 n 位小數的壓縮欄位。「Selection parameters for importing/converting data」旗標可讓最高層結構的欄位在讀取／轉換時當作選擇參數，常用於測試。

結構關係（p140–p142）：選好物件與方法後，系統列出可能的目標結構；必選的會提示「This structure must be selected」。游標放在目標結構 → 按「Relation」→ 從來源結構清單挑。要改關係得先刪除現有關係；有檢查功能（「No structure relationship errors found」）。許多 BI／CT／DI 程式用控制記錄 BGR00 或 BI000，一定要把來源的表頭結構指給它。也可以把多個來源結構指給同一目標結構（層級顯示），兩邊的欄位就都能在目標結構中使用。

12. LSMW 欄位對應與轉換規則

「Maintain field mapping and conversion rules」步驟列出所有目標結構的所有欄位，每個欄位顯示：欄位 ID、已分配的來源欄位、規則類型、程式碼（p143）。部分技術欄位已由系統預填預設規則，亂改可能嚴重影響轉換；不小心改了可用「Extras → Restore default」還原。技術結構（BGR00、IDoc 控制記錄）預設灰色，要看得用「Extras → Display variant」勾「Technical fields」；也可顯示「Display processing times」與「Global data definitions」（p144–p145）。

13. LSMW 讀取、轉換與匯入；管理與權限

指定檔案（p158–p161）：分三類——舊系統資料（在 PC 或 R/3 伺服器上）、匯入資料檔、轉換資料檔。

  • 舊系統資料：路徑、檔名、描述；「Code page ID」填外部系統的字元集；指定記錄描述與分隔符號。
  • R/3 伺服器上是以作業系統使用者 <sid>adm 身分存取，選定目錄必須有讀寫權限。
  • 含多個來源結構資料的檔案可分配給多個來源結構；只含一個結構的檔案只能分配給一個。
  • 匯入資料檔名由系統建議；轉換資料檔可用實體或邏輯路徑——只有後續呼叫的 BI／DI 程式支援時才需要填邏輯路徑與邏輯檔名。
  • 萬用字元：例如 PO Header 1.txt／PO Position 1.txt／PO Header 2.txt／PO Position 2.txt，用 *1.txt、*2.txt 兩組；匯入時先處理檔 1、2，再處理檔 3、4。匯入與轉換資料檔名也可用萬用字元。

分配檔案（p162）：把檔案分配給來源結構；之後改檔名或檔案特性，分配不變。

讀取資料（p163–p165）：可處理全部，或用「交易編號 從…到…」限制範圍；標記為選擇參數的來源欄位也會出現。兩個勾選框：金額欄位轉內部格式（帶小數點）、日期轉內部格式（YYYYMMDD）。有萬用字元時會多一個萬用字元值的選擇參數，不填就全部處理。「Display read data」可表格顯示、切換單行／多行、看顏色圖例。

轉換資料（p166–p167）：用定義好的規則把讀入資料轉成目標檔。系統會先檢查轉換程式是否最新，不是就自動重新產生。「Display converted data」同樣可檢視。

14. Direct Input：BMV0 監視器與重啟機制

Direct Input（DI）是 Batch Input 的替代方案（p173）：不建 Session、沒有畫面，透過呼叫函數直接更新資料庫表，並執行必要檢查，效率較高，特別適合大量資料。發生錯誤時有重啟機制，但前提是 DI 程式必須在 DI 監視器下以背景作業執行（程式 RBMVSHOW 或 BMV0）。處理測試資料可在前景直接執行，但此時沒有錯誤日誌，也沒有重啟能力。SAP 強烈建議正式傳輸一律用 BMV0。

BMV0 的工作流程（p175–p178）：① 為傳輸程式建變式（每支 DI 程式都要）→ ②「Job administration → Define new job」：作業名（在用戶端內唯一）、報表名（如 RMDATIND）、變式、背景伺服器（可之後覆寫）、執行使用者（需要所有相關應用的授權）→ ③「Start new job」：可改伺服器與使用者，接著輸入列印參數與開始時間（立即、日期時間、依作業、依事件）→ ④ 作業分析：「更新」看最新狀態；若因資料庫錯誤中止，狀態為「Batch: job terminated」，看「Display log」修正後選「Job administration → Reset job」，從中止點繼續。

重啟的原理：程式透過部分函數把同步資訊寫入系統表 TBIST（出錯的資料記錄編號、中止前最後處理的編號），確保不會有資料被重複提交或漏提交。但檔案有格式錯誤（記錄不符 SAP 記錄佈局）時重啟機制無效——處理前務必先用「檢查檔案」。

錯誤型態（p179–p181）：

  • FI 憑證（RFBIBL00）：傳輸前的格式檢查失敗（例如記錄沒有鍵）→ 作業中止、什麼都不提交，狀態「Background job terminated」。只有邏輯錯誤（例如缺金額）→ 作業完成（「Completed: job executed」），錯誤記錄被放進 Batch Input Session，名稱取第一筆 BGR00 的 Session 名；修正後處理 Session，再用「error processing」把作業設為「Set to done」。筆記另註：RFBIBL00 不經 BMV0 以 DI／CT 執行時只能處理 20 筆（筆記原文如此；總之正式量請走 BMV0）。
  • 物料主檔（RMDATIND）：可建立錯誤檔並顯示處理（「Applications → Material master industry → Display logical errors」），修正後「Error processing → Repost errors」——資料從處理檔而非原始檔讀取。
  • 銷售憑證：從詳細作業日誌找錯、修正後重新提交。

週期性作業（p182–p183）：作業定義勾「允許週期」、必須用 DI 監視器排程；要加額外步驟，先用「Start data transfer using direct input method」存開始資料，再到 SM37 編輯步驟清單。每次執行前檢查完整性——前一次中止，後續作業不會啟動，在「History」中標為「無效」；重啟中止作業前要確認輸入檔沒被換掉，否則會破壞一致性。

15. EDI／IDoc 基礎：結構、訊息類型與入站處理

EDI（Electronic Data Interchange）是不同應用之間以電子方式交換結構化業務資料。IDoc（Intermediate Document，中介文件）是 SAP 系統間交換資料的標準格式。R/3 內部只用 IDoc 格式，轉成其他 EDI 標準（EDIFACT、ANSI X12）交給 EDI 子系統（非 SAP 提供）——好處是 SAP 應用只需要懂 IDoc 一種格式（p185）。

  • IDoc 兩大概念（p186）：訊息導向（統一各應用、各廠商的不同格式）；非同步（應用文件建立前資料已在 IDoc 中，錯誤資料可以先在 IDoc 修正，再建應用文件）。
  • EDI 架構（p187）：支援 EDI 的應用、IDoc 介面（IDoc 型別＋函數模組，開放介面）、EDI 子系統。
  • EDI vs ALE（p188）：EDI 是不同獨立企業之間的電子資料交換；ALE 是同一企業內不同應用系統之間。應用必須是「IDoc-enabled」才能用。例：分公司 1 用 IDoc 和分公司 2 交換 FI 憑證（ALE），同時透過 EDI 把 FI 文件送給外部系統。
IDoc 組成（p189–p193）說明資料表（補充）
控制記錄（唯一一筆）系統內部指定、唯一的 IDoc 編號（外部狀態回覆都指向它）、夥伴參數鍵欄位、最後處理狀態EDIDC
資料記錄（多筆）控制部分＋應用部分；應用資料依區段（Segment）組織。每筆有 SEGNAM（區段）、MANDT、DOCNUM（IDoc 號）、SEGNUM（區段號）、PSGNUM（父區段號）、HLEVEL（層級）；區段欄位一律 CHAREDID4（舊版 EDID2/EDID3）
狀態記錄（多筆）處理步驟日誌（已建立、準備分送…）；外部系統送來的 IDoc 不含狀態記錄；通訊錯誤會觸發工作流通知負責人EDIDS
  • IDoc 型別由區段、區段階層、順序、是否可重複定義；SAP 交付的叫基本型別，可依規則與客戶擴充組合。顯示結構：WE30（Display tree）；區段與型別資訊：WE63。
  • 命名：區段型別與版本無關，以 E1 開頭（ABAP 字典結構）；區段名稱與版本有關，以 E2 開頭（客戶自訂為 Z1／Z2）。外部系統從區段名稱得知區段版本。
  • 訊息類型是 IDoc 型別的視圖（p194）：IDoc 型別 EMPINF 含員工全部資訊；訊息類型 EMPADD 只看地址、EMPSYS 只看系統權限。不同版本中，同一訊息類型可指向不同基本型別。
  • 出站處理（p196）：提交應用文件 → 建立出站 IDoc（ALE 可能產生多個通訊 IDoc）→ 找夥伴與埠 → 經埠送出。入站處理（p197–p198）：經入站埠收 IDoc → 建立入站 IDoc → 依夥伴參數找應用處理 → 提交應用文件；出錯則啟動獨立的例外處理。
  • 入站兩種處理方式：直接（函數模組把 IDoc 資料轉成應用文件；ALE 服務提供過濾與版本處理）；間接（經 SAP Business Workflow）。
  • 錯誤處理（p199）：無法提交的 IDoc 可修正後再提交，被編輯過的 IDoc 狀態為 69；系統會為修改前的內容另存一份副本（新編號，狀態 70），編修後的 IDoc 保留原編號。IDoc 只能透過歸檔刪除（設刪除旗標 → 歸檔 → 從系統刪除）。

16. LSMW + IDoc：以 FI 憑證為例（含 IDoc 管理設定）

用 LSMW 以 IDoc 傳輸的步驟（p200）：維護物件屬性 → 維護來源結構與欄位 → 維護結構關係 → 維護欄位對應與轉換規則 → 讀取 → 轉換 → Start IDoc generation → Start IDoc processing → Create IDoc overview → Start IDoc follow-up。選 IDoc 匯入技術並存檔時，系統檢查預設夥伴與訊息類型的夥伴參數，不存在就嘗試建立（p201）。

FI 憑證用 IDoc（訊息類型 FIDCC1、區段 E1FIKPF／E1FISEG）的特殊欄位（p205–p212）：

  • 跨系統公司代碼（ALE 場景）：分送時所有公司代碼欄位都換成跨系統公司代碼，目標系統收到再反向轉換。每個跨系統公司代碼有一個核心系統。設定：① 建立跨系統公司代碼 ② 指定給科目表（非核心系統才能確定核心系統的科目表）③ 指定給本地公司代碼。SAP 建議兩者用相同名稱。
  • 總帳科目補前導零：轉換出口 ALPHA（CONVERSION_EXIT_ALPHA_INPUT）——全數字（前後可有空白）則右對齊左補 0，例如 '1234 ' → '00001234'、' 1234 ' → '00001234'；含非數字則左對齊右補空白，例如 'ABCD ' 不變。反向用 CONVERSION_EXIT_ALPHA_OUTPUT。
  • 總帳交易類型：FISEG-VORGN = 'RFBU'。
  • 借貸標識 SHKZG：S＝借方、H＝貸方，依過帳碼決定。
  • 金額：兩個幣別欄位（本位幣 FIKPF-HWAER、憑證幣 FIKPF-WAERS）與兩個金額欄位（本位幣金額 DMBTR、憑證幣金額 WRBTR）都要填。

17. BAPI 資料傳輸：以固定資產 BUS1022 為例

從 DX-WB 呼叫 BAPI 時，外部資料必須是 IDoc 格式，所以要先用 LSMW 之類的對應工具轉成 IDoc 格式（p232）。BAPI 的特性（p233–p234）：

  • 每個建立或修改資料的 BAPI 都屬於一個能保持資料庫一致的物件：全部做完或完全不做。
  • BAPI 本身不下 COMMIT WORK，必須由呼叫程式下（BAPI_TRANSACTION_COMMIT）。
  • BAPI 是無對話的方法，不能出畫面。
  • 外部客戶端可以像呼叫物件方法一樣呼叫；SAP 保證 BAPI 介面不會被修改（相容性保證）；也可在本機用來存取業務資料。
  • 回傳參數 RETURN：依版本可能是不同字典結構（BAPIRETURN、BAPIRET1、BAPIRET2）；成功時為空或 TYPE = 'S'，詳見各 BAPI 文件。BAPIRET2 的正確判讀見 4-1 章。

商業物件「Asset」（p235–p236）：BUS1022 固定資產——企業長期使用、可在資產負債表中個別區分的項目，可整體或依組件（例如印刷機的「滾筒」、「替換軸」）檢視。在 SWO1 顯示 BUS1022 →「BOR 資料模型」→「Utilities → 圖形」可看資料模型。方法 CreateInclValues 用來移轉資產（含價值），對應函數 BAPI_FIXEDASSET_OVRTAKE_CREATE；可在 BAPI 瀏覽器「財務會計 → 資產會計 → 固定資產」找到。

DX-WB 中的 BAPI 處理（p237）：讀包（Package）中的外部資料 → 對包執行 ALE 入站處理（逐筆傳給 BAPI，收集回傳參數）→ DX-WB 評估狀態 → 寫日誌 → 出錯時建錯誤檔或直接在 R/3 建 IDoc → DX-WB 最後下 COMMIT WORK。LSMW 與 DX-WB 的差別（p238）：LSMW 先把 IDoc 建進資料庫再讀出來交給 BAPI；DX-WB 直接把 IDoc 格式檔交給 BAPI，不建資料庫 IDoc，速度較快。

建立測試資料（p239–p245）：先用線上交易建一筆（資產類別 3100 車輛，必填「描述」與「成本中心」；資本化日期由首次過帳自動帶入，手動設的日期不會啟用資產，但會作為資產價值日的建議，資料傳輸需要；存檔後記下狀態列的資產號碼）→ DX-WB「轉到 → 工具 → 欄位與資料結構 →用資料建立檔案」→ 系統要求輸入邏輯系統。邏輯系統在 SALE（Basis → 分送（ALE）→ 傳送與接收系統 → 邏輯系統 → 定義）；夥伴參數在 WE20 以夥伴類型 LS 建立，設出站參數（訊息類型最重要，BAPI 與訊息類型的對應在 BDBG），出站模式選「收集 IDoc」。4.6C 的 DX-WB 會自動建邏輯系統，4.6A/B 需手動建。

對應規則（p247–p249）：IDoc 號必須是流水號；「資產類別」與「成本中心」要定義翻譯；公司代碼、資本化日期、業務範圍只要 MOVE。部分 BAPI 有 X 結構：目標欄位有填值並要傳，對應的 X 欄位就要填 'X'。LSMW 的「填寫 X 結構」會自動產生程式碼（已自訂規則的欄位除外）；若欄位名與 X 結構不一致，產生的程式會有語法錯誤——用「語法檢查」找出位置，一定要在欄位對應中修正，不要改產生的程式。

BAPI Run 的屬性（p250）：包大小（每個 LUW 傳給 BAPI 的物件數）、中斷前錯誤數（0 或不填＝永不中斷）、輸入檔、刪除檔、無法傳輸的物件存到檔案還是 IDoc。錯誤處理兩條路（p251–p254）：

  • 錯誤檔：勾「把 IDoc 寫入檔案」；BAPI 提交無錯記錄，錯誤記錄收進錯誤檔，結束後錯誤檔複製回輸入檔。此時不要勾「刪除檔案」，否則含錯誤記錄的輸入檔會被刪。
  • 建 IDoc：勾「在 R/3 中儲存 IDoc」；錯誤記錄成為 IDoc，之後經 ALE 服務處理；此時可以勾「刪除檔案」。
  • 兩者後續相同：Customizing 錯誤 → 修正後「繼續 Run」／重送 IDoc；資料錯誤少 → 用編輯器改；錯誤多且有系統性 → 重新抽取、轉換、排除錯誤後開新 Run（筆記作者吐槽：「完全跟上一頁一樣，廢話連篇的 SAP」）。

18. 交易記錄器（SHDB）：錄製原理與限制

SAP 標準程式沒提供需要的傳輸功能時，才用交易記錄器（p257）。它以 Batch Input 或 Call Transaction 把資料傳入 R/3，只能處理扁平檔案（沒有階層、沒有子結構；表頭／明細不同記錄結構的檔案不能用）。LSMW 的「錄製」功能底層用的就是它（p258）。錄製前先啟動記錄器，然後像線上一樣執行交易；完成後，錄製內容包含所有畫面號碼、欄位名、欄位值、模組池與 TCODE（p259）。

錄製注意事項（p260–p266）：

  • 範例：FD02 修改客戶。除畫面欄位外，BDC_CURSOR、BDC_OKCODE 會自動記錄。
  • 之後資料傳輸會用到的欄位，錄製時都要「改一下值」——哪怕只是用同一個字元覆蓋一個字元；以 SET/GET 參數帶入的欄位也要改，否則不會被錄進去。
  • 線上執行時畫面出現順序可能和錄製不盡相同。
  • 子畫面會自動記錄，欄位 BDC_SUBSCR 存子畫面名稱（筆記寫作 BDC_SUBSCREEN）。客戶主檔的地址資料（中央地址管理）就是一個子畫面。頁籤（Tab strip）其實也是以子畫面實作，查名稱一樣用欄位的 F1。
  • 找模組池與畫面號：「系統 → 狀態」；找欄位名：游標放欄位上按 F1 →「技術資訊」。
  • Step Loop 與 Table Control：每一行欄位名相同，必須用索引（與行號對應）存取，例如 MSEG-MATNR(01)；只有畫面上看得到的列才能填，超出要錄翻頁。翻頁功能碼：/21 首頁、/22 上頁、/23 下頁、/24 末頁（許多新交易改用 =P+／=P-，以錄製結果為準）。
錄製方針（p266）：① F1、F4 以及自己寫的 PROCESS ON HELP-REQUEST／PROCESS ON VALUE-REQUEST 不會被錄，「系統」與「說明」選單的命令也不會；② 錯誤與警告對話框不會被錄，只錄 OK 碼與後續處理需要的欄位；③ 錄製時輸入的資料會真的寫進資料庫——在正式機錄製等於真的過帳；④ 4.6 版之後的 EnjoySAP 控件（ALV Grid、Tree、Text Edit…）除了 Table Control 與頁籤之外，都不支援 Batch Input／Call Transaction。所以 ME21N、MIGO、VA01 新畫面這類 Enjoy 交易錄出來的 BDC 非常脆弱，能用 BAPI 就用 BAPI（見 4-4 章第 9 節）。

在 LSMW 中錄製（p267–p274）：「Goto → Recordings」→ 建立（名稱、描述、擁有者）→ 輸入 TCODE → 執行交易並正常結束。一個錄製只能屬於一個專案，名稱必須唯一。結果以樹狀顯示，可增刪欄位。可為每個錄製欄位指定名稱（BDC_OKCODE、BDC_CURSOR、BDC_SUBSCR 除外）：「Default」依目標欄位名自動命名、「Reset」清除、雙擊可編輯名稱、描述與預設值；沒命名的欄位在建立 Session 時使用錄到的值（當常數用，對勾選框特別好用）。同一欄位名可用多次，但欄位對應中只會用一次，所以意義不大。LSMW 支援自動欄位對應（同名欄位自動配對），所以來源結構欄位名最好與目標相同或相近。之後新增畫面欄位時，只能加在畫面支援的位置，否則處理 Session 時會出錯。

19. SHDB 產生程式、函數模組與 BDCRECX1

SHDB 的錄製可以（p275–p287）：編輯（增刪改行、「檢查」語法、匯出到本機用 PC 編輯器改再匯入）、追加更多交易錄製、直接以 Call Transaction 重播、建立 Batch Input Session、建立測試資料檔（只能存在應用伺服器，未指定路徑則放在 work 目錄，同名檔會追加）、產生程式、產生函數模組。

  • 產生程式：兩種填值方式——① 直接用錄製的值；② 參數化，從檔案讀值（建議同時勾選產生測試檔）。程式可用 Batch Input 或 Call Transaction；選 ② 且 Call Transaction 出錯時，錯誤記錄會放進 Batch Input Session。
  • 產生函數模組：輸入函數名、函數群、短文。輸入介面＝技術參數＋每個輸入欄位一個參數；參數 CTU：空白＝建立 Session、'X'＝Call Transaction 直接更新；其他參數填 Session 表頭。輸出只有 SUBRC（僅 Call Transaction 有效，0＝成功）。表格參數存所有系統訊息（僅 Call Transaction）。每呼叫一次就建一個 Session；要一個 Session 放多筆交易，得把交易錄多次讓介面包含多段交易。

產生程式的結構（p288–p290）：主程式（產生部分）＋ SAP 標準 include BDCRECX1。BDCRECX1 定義 BDC 表與七個子程式：開關檔（open_dataset／close_dataset）、開關 Session（open_group／close_group）、填 BDC 表（bdc_dynpro／bdc_field）、放入 Session 或呼叫交易（bdc_transaction）。讀檔結構自動產生、通常叫 RECORD：每個欄位兩行，第一行是註解「* data element:」加資料元素，第二行是「欄位名＋三位數位置號」，長度取資料元素長度（無資料元素則取畫面欄位長度）。

BDCRECX1 的 bdc_field 有一個重要細節：值等於 NODATA 字元時不寫入 BDCDATA（筆記 p300 的 IF fval <> nodata）——這就是「沒給值的欄位不動畫面」的實作。筆記 p301 的範例還有兩個錯字：bdc_dynprt（應為 bdc_dynpro）與 'KNA1-SPRAS 少了結尾引號。

BDCRECX1 是全域 WITH HEADER LINE 的 BDCDATA 加一堆 FORM，新程式不要再 INCLUDE 它。下面是取代它的類別：同樣支援 NODATA 略過、鏈式呼叫，可以直接套在第 5、20 節的程式上。
*&---------------------------------------------------------------*
*& 取代 BDCRECX1 的 BDC 輔助類別（ABAP 7.52）
*&---------------------------------------------------------------*
CLASS lcl_bdc DEFINITION FINAL.
  PUBLIC SECTION.
    TYPES: tt_bdc  TYPE STANDARD TABLE OF bdcdata WITH EMPTY KEY,
           ty_fval TYPE bdcdata-fval.
    DATA mt_bdc TYPE tt_bdc READ-ONLY.

    METHODS constructor
      IMPORTING iv_nodata TYPE ty_fval DEFAULT '/'.
    METHODS dynpro
      IMPORTING iv_program     TYPE bdcdata-program
                iv_dynpro      TYPE bdcdata-dynpro
      RETURNING VALUE(ro_self) TYPE REF TO lcl_bdc.
    METHODS field
      IMPORTING iv_fnam        TYPE bdcdata-fnam
                iv_fval        TYPE simple
      RETURNING VALUE(ro_self) TYPE REF TO lcl_bdc.
    METHODS clear.
  PRIVATE SECTION.
    DATA mv_nodata TYPE ty_fval.
ENDCLASS.

CLASS lcl_bdc IMPLEMENTATION.
  METHOD constructor.
    mv_nodata = iv_nodata.
  ENDMETHOD.

  METHOD dynpro.
    APPEND VALUE #( program  = iv_program
                    dynpro   = iv_dynpro
                    dynbegin = abap_true ) TO mt_bdc.
    ro_self = me.
  ENDMETHOD.

  METHOD field.
    ro_self = me.
    " 數值請呼叫端先用 |{ x NUMBER = USER }|、日期用 |{ d DATE = USER }|
    DATA(lv_val) = condense( CONV ty_fval( iv_fval ) ).
    IF lv_val = mv_nodata.
      RETURN.                              " NODATA：這個欄位不動畫面
    ENDIF.
    APPEND VALUE #( fnam = iv_fnam fval = lv_val ) TO mt_bdc.
  ENDMETHOD.

  METHOD clear.
    CLEAR mt_bdc.                          " 每筆交易前清空（筆記：REFRESH）
  ENDMETHOD.
ENDCLASS.

整合進 DX-WB（p312–p314）：產生的程式可整合進 DX-WB，檔案結構要用 ABAP 字典建立，會寫入表 SXDA0～SXDA3。4.5 版在 DX-WB 初始畫面「轉到 → 初始化客戶資料傳輸物件」整合；4.5 版的傳輸物件不以 BOR 組織，而用 DX 號（0001～9999，9000～9999 保留給客戶）；新版要把程式指定給 BOR 物件、建短文、指定 include、為字典結構命名。產生的程式會出現在程式類型 BINP（不是 REPO）下。4.5 版工作台中的物件會自動出現在 4.6 版，除了「用傳輸資料建立檔案」外所有功能都能用。

20. Call Transaction：MODE、UPDATE、MESSAGES 與 CTU_PARAMS

Call Transaction 不建 Session，直接把 BDC 表（結構與 Batch Input 相同）餵給交易（p302）。平均比 Batch Input 快 1～3 倍。被呼叫的交易使用一個額外的 roll area，處理完釋放後回到原本的 roll area（p303）。與 Batch Input 不同：沒有錯誤日誌（錯誤 Session）、也沒有重啟功能；用呼叫者本人的權限；BDC 表每次只能放一筆交易的資料，呼叫下一筆前要清空。

選項值說明
MODE（DISMODE）A顯示所有畫面（MODE 的預設值）
E只在錯誤時顯示畫面，可修正
N完全不顯示；處理完才把控制權還給程式
UPDATE（UPDMODE）A非同步：不等資料庫更新，只交給更新服務；較快但不知道是否真的成功，要看 SM13；大量資料不建議。注意：這也是 UPDATE 的預設值
S同步：等更新結束，較慢，但更新錯誤會回報給程式——資料移轉請用 S
L本地更新：在呼叫程式的同一程序中更新（參考 SET UPDATE TASK LOCAL，見 5-11 章）

MESSAGES INTO：執行中所有系統訊息寫入內表，結構必須是 BDCMSGCOLL。OPTIONS FROM 用結構 CTU_PARAMS 控制，不能與 MODE、UPDATE 同時使用（p308–p309）：

CTU_PARAMS 欄位意義未指定 OPTIONS 時的預設
DISMODE處理模式取自 MODE
UPDMODE更新模式取自 UPDATE
CATTMODECATT 控制不啟用
DEFSIZE強制使用標準視窗大小不使用（背景處理永遠用標準大小）
RACOMMIT遇到 COMMIT WORK 不結束（交易中第一次提交不會讓錄製結束）COMMIT WORK 後成功結束
NOBINPT不以批輸入方式執行，即 sy-binpt = space，交易像線上一樣跑批輸入啟用（sy-binpt = 'X'）
NOBIENDBDC 資料用完後不再是批輸入模式（搭配 E 模式，錯誤時轉前景）BDC 資料用完後仍是批輸入模式

sy-binpt（p282）：不是所有交易都能在線上與批輸入兩種模式下執行，交易自己用 sy-binpt = 'X' 判斷是否處於批輸入（Call Transaction 同樣會設定）。

教材修正（p310）：筆記的回傳碼表寫成「成功 <1000、交易錯誤 >1000」，這是誤植。ABAP 文件的定義是：sy-subrc = 0 成功；< 1000 被呼叫的交易發生錯誤（若有送出訊息，存在 sy-msgid、sy-msgty、sy-msgno、sy-msgv1～v4）；1001 批輸入處理本身出錯。另外 sy-subrc = 0 也不代表單據一定建立成功（UPDATE 'A' 時更新可能事後失敗），一定要檢查 MESSAGES 中的成功訊息。

22. 背景處理：SM36／SM37 與 RSBDCSUB

R/3 背景處理用來自動化程式作業、最佳化資源使用（p334–p335）：可執行內部與外部程式，把多個程式定義為一個作業的多個作業步驟；有圖形化監視器、作業精靈、以及可程式化的 API。

建立背景作業六步驟（p336）：① 程式有選擇畫面就先建變式 ② 作業定義：作業名稱與優先順序（類別 A 最高、C 最低），目標伺服器可選 ③ 步驟清單：依序處理的所有程式 ④ 設定開始時間 ⑤ 時間到時在空閒的背景工作程序中處理 ⑥ 顯示作業日誌。

  • SM36 建立作業（p337–p340）：目標伺服器留空以自動負載平衡；開始條件可指定日期時間、過期日期（到期前沒跑到就永遠不跑，狀態設為「取消」）、週期性。
  • SM37 作業概覽（p340–p341）：依條件選擇作業；要看依事件排程的作業，「在事件後開始」欄位至少填 *。可從概覽跳到 Spool 看各步驟輸出、看作業日誌。
  • 作業狀態：已計劃（已定義、未指定開始時間）→ 已釋放（已指定開始時間）→ 準備（時間到、等待執行）→ 活動（執行中，可在 SM50 看到）→ 已結束（無錯誤）／已取消（有錯誤）。

RSBDCSUB 平行處理（p325–p327、p342–p345）：多個 Session 由外部資料產生時，RSBDCSUB 會為每個 Session 排一個獨立作業。步驟：① 先用測試模式熟悉選擇畫面 ② 建變式：Session 名稱（可萬用字元如 BC420*）、建立日期、Session 狀態、目標伺服器最好留空、擴充日誌 ③ 用此變式為 RSBDCSUB 建背景作業。典型作業是兩個步驟：第一步執行 Batch Input 程式讀外部資料、轉換並建立 Session；第二步執行 RSBDCSUB，把剛建的 Session 交給背景處理。結果可在作業概覽與批輸入監視器中檢視。

23. 附錄：測試階段、正式傳輸、欄位缺漏與系統全景

  • 測試階段（p346）：第一次測試少於 10 筆，每次成功後增加一個數量級，最後一次包含全部資料。錯誤分三類處理：資料錯 → 回外部系統修正；Customizing 錯 → 修正設定；轉換程式錯 → 修正程式。只有測試全部成功，才能確保正式傳輸不出錯。
  • 正式傳輸（p347）：測試結束也不要直接上，先做整合測試——用此時點匯入的資料跑完所有業務流程。整合測試中若改了 Customizing，就要再測一次傳輸。整個測試期間，正式業務仍在外部系統進行；正式傳輸期間所有系統都不能使用，之後由 SAP 接手正式系統的角色。
  • SAP 必填、外部系統沒有的欄位（p348）：所有記錄都相同 → 設固定值；有依存關係 → 為每筆記錄決定依存的值。
  • 外部有、SAP 沒有對應的欄位（p349）：先問業務流程需不需要，不需要就丟棄；或填到某些業務上不直接用到的 SAP 欄位（借用欄位，實務上要寫進規格文件，避免日後誤用）。
  • 物件順序：業務資料依存於主資料，主資料存在後才能傳業務資料——例如先科目、成本中心，再客戶／供應商，再物料，最後未結項目與庫存。
  • 系統全景（p350）：一定要區分用戶端相關與跨用戶端的 Customizing。例如在測試系統用戶端 100 測試前，必須先把設定從開發系統的設定用戶端傳過來。日常最常被遺忘的就是這一點，然後傳輸就出錯。傳輸請求的觀念見 1-1 章。

練習與自我檢核

  1. 說出 Batch Input 與 Call Transaction 的三個差異。
    參考答案要點：Batch Input 先建 Session 再由 SM35 處理、有錯誤 Session 可修正重跑、永遠同步提交；Call Transaction 直接呼叫交易、快 1～3 倍、沒有錯誤 Session 與重啟功能，要自己收 MESSAGES INTO，可選 UPDATE A/S/L。兩者都用 BDCDATA、都做完整線上檢查。
  2. 記錄佈局中哪些欄位要填 NODATA？沒填會怎樣？
    參考答案要點：所有不傳的欄位都要填 NODATA（預設 /，在 BGR00 的 NODATA 欄位指定）；沒填會傳入空白，可能覆蓋系統既有值。只適用於 BI／CT／DI，BAPI 不需要。
  3. 記錄類型 0、1、2 分別是什麼？以 RFBIBL00 為例說出對應結構。
    參考答案要點：0＝Session 表頭（BGR00）；1＝交易表頭（BBKPF，含 TCODE 與初始畫面值）；2＝交易資料（BBSEG 等，還要填結構名 TBNAM）。
  4. Direct Input 為什麼一定要在 BMV0 下執行？重啟靠什麼？什麼情況重啟無效？
    參考答案要點：BMV0 下以背景作業執行才有錯誤日誌與重啟機制；重啟靠 TBIST 記錄的處理位置，避免重複或漏提交；檔案格式錯誤（不符記錄佈局）時重啟無效，所以要先「檢查檔案」。
  5. CALL TRANSACTION 的 MODE、UPDATE 預設值各是什麼？資料移轉應該怎麼設？
    參考答案要點：MODE 預設 A（全顯示），UPDATE 預設 A（非同步）；移轉建議 DISMODE 'N'（或 'E' 測試）、UPDMODE 'S'，用 CTU_PARAMS 時不能再寫 MODE／UPDATE。
  6. sy-subrc = 0 就代表單據建立成功嗎？
    參考答案要點：不一定。<1000 是交易錯誤、1001 是批輸入處理錯誤；0 時仍應檢查 MESSAGES 中的成功訊息（如 F5 312），非同步更新還可能事後失敗（看 SM13）。
  7. 錄製交易時有哪些東西不會被錄進去？
    參考答案要點：F1、F4、自訂 POH／POV、系統與說明選單命令、錯誤與警告對話框；沒修改過值的欄位（包含 SET/GET 參數帶入的）；Enjoy 控件（Table Control 與頁籤除外）根本不支援。另外錄製時資料會真的寫入資料庫。
  8. LSMW 的區間翻譯有什麼風險？應該怎麼做？
    參考答案要點：區間比的是字典序，前導零、長度不同、號碼段不連續都會多抓或漏抓；應改用一對一列舉＋找不到就 skip_transaction 並記錄（Casper 第二條經驗）。
  9. FI 憑證 IDoc 中，借貸標識 SHKZG 應該怎麼決定？筆記的寫法錯在哪？
    參考答案要點：依過帳碼主檔 TBSL-SHKZG 決定；筆記寫死「50 = H，其他 = S」，遇到 31、39、11、19 等貸方過帳碼就錯。
  10. BAPI 用於資料傳輸時，誰負責 COMMIT？X 結構是做什麼的？
    參考答案要點：BAPI 本身不 COMMIT，由呼叫端呼叫 BAPI_TRANSACTION_COMMIT（WAIT = 'X'）；X 結構標示哪些欄位有值要更新，對應欄位填 'X'，LSMW 有「填寫 X 結構」自動產生程式碼。
  11. 設計一個兩步驟背景作業，把外部檔案轉成 Session 並自動處理。
    參考答案要點：步驟 1 SUBMIT 建 Session 的程式（讀應用伺服器檔，不能用前端檔案函數）；步驟 2 SUBMIT RSBDCSUB（變式：Session 名 ZBC420*、狀態、目標伺服器留空、擴充日誌）；JOB_OPEN → SUBMIT VIA JOB → JOB_CLOSE，結果看 SM37 與 SM35。
