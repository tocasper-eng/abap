2. ABAP SQL 更新總覽：Native vs Open、返回碼、權限與用戶端

ABAP 改資料庫有兩條路：

  • Native SQL：直接下資料庫專屬語法，換資料庫就要改程式；只有在 ABAP SQL 做不到時才用。
  • Open SQL（7.53 起正名為 ABAP SQL）：資料庫無關，由資料庫介面自動翻成對應 SQL；可以利用應用伺服器上的表格緩衝（在 SE11 技術設定開啟後，讀取自動走緩衝），降低資料庫負載。

四個觀念一次記住：

  1. 只有 DML、沒有 DDL：ABAP SQL 只做資料操作（SELECT / INSERT / UPDATE / MODIFY / DELETE），建表、改表結構屬於 ABAP 字典（見 1-2 章、5-16 章 BC430）。
  2. sy-subrc 與 sy-dbcnt：所有 SQL 都回傳 sy-subrc（0＝成功，其餘＝有問題），sy-dbcnt＝實際受影響筆數。一次處理多筆（集合操作）通常比迴圈單筆快，例外是 MODIFY（大量 MODIFY 要逐筆判斷存在與否）。
  3. ABAP SQL 不做自動權限檢查：要自己寫 AUTHORITY-CHECK。
  4. 用戶端（集團）自動處理：不寫任何用戶端附加，資料庫介面會自動加上 WHERE mandt = sy-mandt。要跨用戶端，舊寫法是 CLIENT SPECIFIED（並自己在 WHERE 寫 mandt）；新寫法是 USING CLIENT（教材註明 7.40 SP05 起、嚴格模式）。

LIKE 遮罩：'_' 代表一個字元、'%' 代表任意長度字串（SQL 標準）。

3. INSERT / UPDATE / MODIFY / DELETE：單筆、多筆與返回碼

四個指令都有「單筆（工作區）」「多筆（內表）」「條件（WHERE）」三種型態。工作區與內表的結構必須與資料庫表相同；工作區中的 mandt 欄位只有在 CLIENT SPECIFIED（或 USING CLIENT）時才會被採用，否則一律用登入用戶端。也可以對 維護狀態為「讀取與變更」、且只含單一表欄位的資料庫 View 做寫入。

4. 回復資料庫狀態：ROLLBACK WORK、A／X 訊息與例外處理

任何更新 SQL 的 sy-subrc 不是 0，都應該讓資料庫回到更新前的狀態，也就是資料庫回滾（DB Rollback），撤銷目前資料庫 LUW 內的所有變更。兩種做法：

  • 送出終止訊息（A 或 X 型）：回滾＋終止程式。E、W、I 型訊息只會出現對話，不會回滾。
  • ROLLBACK WORK：回滾但不終止程式。注意：程式上下文（全域變數、函數群組資料、類別屬性）不會被重置，要自己清。
*&---------------------------------------------------------------*
*& 一個 LUW 裡寫兩張表：任何一步失敗就整批回滾
*&---------------------------------------------------------------*
CLASS lcl_booking DEFINITION FINAL.
  PUBLIC SECTION.
    METHODS save
      IMPORTING is_book    TYPE sbook
      RETURNING VALUE(rv_ok) TYPE abap_bool.
ENDCLASS.

CLASS lcl_booking IMPLEMENTATION.
  METHOD save.
    TRY.
        INSERT sbook FROM @is_book.
        IF sy-subrc <> 0.
          ROLLBACK WORK.                       "4＝訂位號碼重複
          RETURN.
        ENDIF.

        UPDATE sflight
           SET seatsocc = seatsocc + 1
         WHERE carrid = @is_book-carrid
           AND connid = @is_book-connid
           AND fldate = @is_book-fldate.
        IF sy-subrc <> 0.
          ROLLBACK WORK.                       "航班不存在：連訂位一起撤銷
          RETURN.
        ENDIF.

        COMMIT WORK.
        rv_ok = abap_true.

      CATCH cx_sy_open_sql_db INTO DATA(lx_db).  "例如整批 INSERT 重複鍵
        ROLLBACK WORK.
        MESSAGE lx_db->get_text( ) TYPE 'I'.
    ENDTRY.
  ENDMETHOD.
ENDCLASS.
原廠的「隱式回滾」清單：① 執行時期錯誤（例如除以零）；② 對話步驟中送出終止訊息，通常是 A / X 型，但某些情況下 I、W、E 也會變成終止訊息（例如在畫面的 PBO 送 E 訊息）。

5. SAP LUW 與資料庫 LUW：隱式 COMMIT 是一切問題的根源

SAP LUW（Logical Unit of Work，作業邏輯單元）＝一組邏輯上屬於一體的對話步驟，它們的資料庫變更要全部成功或全部不做（all or nothing）。一個業務流程通常不只一個 SAP LUW——從接單到開發票，會切成好幾段，每段一個 SAP LUW。

資料庫 LUW＝從上一次 DB Commit 到下一次 DB Commit 之間的所有變更；在 Commit 之前可以 Rollback，Commit 之後就「封存」，不能再撤銷。

問題在於 AS ABAP 的三層主從架構（資料庫伺服器／應用伺服器／展示伺服器）：少數工作程序（work process）服務大量使用者；每處理完一個對話步驟，使用者與程式上下文就被 roll out，工作程序交給別人用。這讓系統很有擴充性（比「胖用戶端」架構更好，資料庫連線數遠少於使用者數），代價是：每次釋放工作程序都會觸發一次隱式的 DB Commit。

類型觸發情境
顯式 DB CommitCOMMIT WORK；呼叫函數 DB_COMMIT
隱式 DB Commit（等待情境）對話步驟結束（送出畫面）；同步或非同步 RFC 呼叫（或被呼叫的函數結束）；WAIT 中斷工作程序；在 LUW 中間送出 I / W / E 對話訊息；CALL TRANSACTION、LEAVE TO TRANSACTION（或被呼叫交易結束）；SUBMIT（或被呼叫程式結束）
顯式 DB RollbackROLLBACK WORK
隱式 DB Rollback執行時期錯誤；終止訊息（A / X，特定情境的 I / W / E）

結論：屬於同一個 SAP LUW 的變更，不能分散在不同的對話步驟裡直接寫進資料庫，因為它們不在同一個 DB LUW。要把跨多個畫面的使用者輸入合成一個 SAP LUW，只有三條路：① 全部集中在最後一個對話步驟寫（第 10 節）；② PERFORM ON COMMIT（第 10 節）；③ Update Task（第 11～13 節）。

6. SAP 鎖概念：為什麼資料庫鎖不夠

多個使用者競爭同一資源時必須同步存取以保護一致性。教材的例子是航班訂位：查空位、確認座位時，剩餘座位數這種關鍵資料不能在處理中被別人改掉。鎖的原則是：存取關鍵資料前先要鎖，用完盡快放，不要不必要地擋住別人。

資料庫鎖：DBMS 會實體鎖住「為了更新而讀取」的列（SELECT … FOR UPDATE），執行 INSERT / UPDATE / MODIFY / DELETE 時也會自動加鎖；但每次 DB Commit 都會釋放該 DB LUW 的所有鎖。在 AS ABAP 裡每換一個畫面就隱式 commit 一次，所以跨多畫面收集資料、又要在整段期間鎖住紀錄時，資料庫鎖完全不夠用。

SAP 邏輯鎖：AS ABAP 在應用伺服器層級維護一張全系統唯一的鎖表（lock table），由 Enqueue 工作程序／Enqueue Server（鎖伺服器）管理，所有伺服器的鎖請求都送到這裡。鎖表放在鎖伺服器的記憶體中；原廠建議使用獨立鎖伺服器搭配另一台機器上的鎖複寫伺服器做高可用（S/4HANA 1809 起預設為 Standalone Enqueue Server 2，ENSA2）。邏輯鎖還能鎖資料庫中還不存在的紀錄——新增資料時資料庫鎖幫不上忙，這時就靠它。

*&---------------------------------------------------------------*
*& 資料庫鎖：SELECT ... FOR UPDATE 只能撐到下一次 DB Commit
*&---------------------------------------------------------------*
SELECT SINGLE FOR UPDATE carrid, connid, fldate, seatsmax, seatsocc
  FROM sflight
  WHERE carrid = @lv_carrid
    AND connid = @lv_connid
    AND fldate = @lv_fldate
  INTO @DATA(ls_flight).

IF sy-subrc = 0 AND ls_flight-seatsocc < ls_flight-seatsmax.
  UPDATE sflight SET seatsocc = seatsocc + 1
    WHERE carrid = @lv_carrid AND connid = @lv_connid AND fldate = @lv_fldate.
ENDIF.
COMMIT WORK.        "DB 鎖在這裡（或任何隱式 commit）就消失

" 如果中間要 CALL SCREEN 讓使用者確認，DB 鎖在送出畫面那一刻就沒了
" → 跨畫面的保護一定要用 SAP 邏輯鎖（ENQUEUE_...）
SAP 鎖是「君子協定」：它只擋得住也呼叫同一組 ENQUEUE 的程式。直接 UPDATE 資料庫的程式完全不理會鎖表。所以原廠一再強調：所有會改這張表的程式都必須遵守同一套鎖物件與「鎖→讀→改→解鎖」順序。

7. 鎖物件與鎖模組：SE11 建立、ENQUEUE_ / DEQUEUE_

鎖物件在 SE11（ABAP 字典 → Lock Object）維護，客製鎖物件名稱必須以 EY 或 EZ 開頭（標準的以 E 開頭，例如訓練用的 ESFLIGHT）。建立時指定：

  • 主表（Primary / Basis table）：要鎖的表，例如 SFLIGHT。
  • 次表（Secondary table）：與主表有外鍵關係的表，例如 SBOOK。一個含 SFLIGHT（主）＋SBOOK（次）的鎖物件可以「一次鎖住一個航班及其所有訂位」。
  • 鎖模式：每張表的預設鎖模式（E / X / S），呼叫時可覆蓋。
  • 鎖參數（Lock Parameters）：系統依表的主鍵欄位自動建議名稱（可改），就是將來鎖模組的輸入參數。以 ESFLIGHT 為例：MANDT、CARRID、CONNID、FLDATE。

鎖物件啟用成功後，系統自動產生兩個函數模組：ENQUEUE_<鎖物件名>（設鎖）與 DEQUEUE_<鎖物件名>（解鎖），可在 SE37 或 SE11 的「Goto → Lock modules」檢視（詳見 1-2 章 資料字典）。

*&---------------------------------------------------------------*
*& 鎖模組的標準呼叫樣板（ESFLIGHT：SFLIGHT 為主表）
*&---------------------------------------------------------------*
CALL FUNCTION 'ENQUEUE_ESFLIGHT'
  EXPORTING

    carrid         = lv_carrid
    connid         = lv_connid

    _wait          = abap_false

    foreign_lock   = 1                  "別人已經鎖住
    system_failure = 2                  "鎖伺服器問題
    OTHERS         = 3.

    " 取得鎖 → 此時才讀資料
  WHEN 1.
    " sy-msgv1 帶的是目前持有鎖的使用者
    MESSAGE |航班 { lv_carrid } { lv_connid } 正由 { sy-msgv1 } 處理中，請稍後再試| TYPE 'E'.
  WHEN OTHERS.

" ... 讀取、修改、寫入 ...

鎖會在下列情況自動釋放：程式送出 A 或 X 型訊息、執行 LEAVE PROGRAM、LEAVE TO TRANSACTION、使用者在命令列輸入 /n。另外 DEQUEUE_ALL 會釋放目前程式設定的所有鎖。新版教材補一句：因為鎖會在程式結束時自動釋放、或交給更新程式處理，所以實務上 DEQUEUE 其實「很少用到」——但在直接更新（inline update）的程式裡，自己解鎖仍是好習慣。

SM12 是鎖表監控：可看到使用者、用戶端、鎖物件（表名）、鎖引數、鎖模式、時間。除錯時的經典動作是開兩個視窗（外部階段），第一個鎖住後，到 SM12 看鎖引數長什麼樣子；遇到當機遺留的鎖，也是在 SM12 由 Basis 手動刪除（刪之前先確認該使用者真的沒在處理）。

8. 鎖引數與 ENQUEUE 參數：泛型鎖、_SCOPE、_WAIT、_COLLECT、鎖容器

鎖引數（Lock Argument）是鎖條目的核心，由所有鎖參數的值組成，決定哪些列被鎖。規則：

  • 鎖參數沒傳或傳初始值＝萬用字元（generic）：鎖住「其他參數條件相符的所有列」。例如只傳 CARRID = 'LH'，整個 LH 的所有航班都被鎖。
  • 要鎖「欄位值真的是初始值」的列，改傳 x_<參數名> = 'X'（例如 x_connid）。
  • 用戶端參數例外：不傳＝只鎖目前用戶端（sy-mandt）；傳特定用戶端＝鎖該用戶端；傳 SPACE＝鎖所有用戶端。
參數意義
mode_<表名>覆蓋鎖物件中該表的預設鎖模式（E / X / S / O / R）
x_<鎖參數>把初始值當成「真的初始值」而非萬用字元
_scope1＝鎖屬於程式，只能由程式自己刪（直接更新用）；2（預設）＝鎖在 COMMIT WORK 時交給更新程式，由更新結束後自動刪（Update Task 用）；3＝設兩個鎖，一個留程式、一個交給更新程式（對同一筆紀錄做「部分更新」後還要繼續鎖著做下一次部分更新時用）
_wait第一次失敗時是否重試；重試次數／時間由 profile 參數 enque/delay_max（預設 5）決定（2007 筆記寫成參數 delaymax）
_collect= 'X' 時先把鎖請求存進本地鎖容器，稍後一次送出

鎖容器：每次向鎖管理員請求都是一次通訊，鎖很多物件時通訊次數就多。呼叫鎖模組時帶 _collect = 'X' 先收集，再用 FLUSH_ENQUEUE 一次送出：全部成功則清空容器；只要一個鎖失敗就觸發 FOREIGN_LOCK，而且容器內的鎖一個都不會設，容器內容保留供下次重試；用 RESET_ENQUEUE 清空容器。

*& 鎖容器：多個航班「全有或全無」地一次上鎖
*&---------------------------------------------------------------*
" 先排序：所有程式都用相同順序請求鎖，降低互相等待的機率

9. 鎖模式 E / X / S / O / R 與悲觀、樂觀鎖模式

模式名稱用途同一鍵可並存
SShared（共用鎖）只顯示、不打算改，但要確保顯示期間別人不能改（例：報價顯示給客戶考慮期間，價格不能變）多個 S（及 O）；不能再加任何排他鎖
EExclusive, cumulative（排他、可累積）要改資料（例：訂位時鎖住航班，避免最後一個座位被賣兩次）只能一個；同一程式可重複取得（累積）
XExclusive, non-cumulative（排他、不可累積）要改資料，而且連自己程式的其他功能也不能再鎖（例：同一航班只能在一個對話中編輯）只能一個；自己也不能再鎖
OOptimistic（樂觀鎖，7.0 EhP2 起）以「變更模式」顯示、可能會改；不阻擋其他人也進入變更模式多個 O（及 S）；排他鎖只能由一人升級取得
R（升級用）把自己的 O 鎖升級為 E 鎖；成功時會刪除別人在同一物件上的 O 鎖—

從其他程式看（不同程式實例／不同使用者）：已有 E 或 X → 拒絕任何新鎖；已有 S 或 O → 允許其他 S / O，拒絕排他鎖。强晟在 p53 註記「教材文字說共用鎖會被拒絕，依投影片應是文字錯誤」——他的判斷正確，新版教材也已寫成「S 允許其他 S」。

從同一程式看（累積）：已有 E → 可再加 E、O、S，拒絕 X；已有 X → 拒絕任何鎖；已有 S 或 O → 自己可再加 S / O，若沒有別人持有 S / O，還可再加 E；只要已有任何鎖，X 一律設不上。

  EXPORTING mode_sflight = 'R'

傳統悲觀鎖模式四步驟（新舊教材一致）：① 設 E 鎖 → ② 鎖成功才從資料庫讀最新資料 → ③ 修改並寫回資料庫 → ④ 解鎖。這個順序保證變更全程在鎖保護下，也保證讀到的是別的程式「一致存檔後」的資料。樂觀鎖不能防止外部變更，但能偵測變更；兩種模式的程式可以並存，不必一次全部改寫。

錯誤用法：先讀再鎖。如果先 SELECT 再 ENQUEUE，就算鎖成功了，你讀到並顯示給使用者的資料可能已被剛解鎖的別人改過——使用者等於在過期資料上輸入。「鎖→讀→改→解鎖」的順序一步都不能對調。

10. 在應用程式內直接更新與 PERFORM ON COMMIT

直接更新（Direct / Inline Update）：在對話程式本身執行 SQL。因為隱式 commit，所有資料庫更新必須集中在單一對話步驟（通常是最後一個），這是確保 all-or-nothing 的唯一方法；要寫入的資料得一直保存在全域程式資料裡，寫入的是最後一個對話步驟時的內容。鎖則由程式自己設、自己放：E 鎖 → 讀取顯示 → 寫資料庫 → 解鎖（DEQUEUE_<鎖物件> 或 DEQUEUE_ALL）。

延遲子程式 PERFORM <form> ON COMMIT：只登錄、不執行，等遇到下一個 COMMIT WORK 才依序執行所有登錄的子程式，並觸發 DB Commit。規則：

  • 同一個子程式在一個 SAP LUW 中只執行一次，重複登錄不會出錯、也只跑一次。
  • 4.6 起，巢狀的 PERFORM ON COMMIT（在 ON COMMIT 子程式裡再登錄）會執行時期錯誤。
  • 子程式不能有介面（參數），只能用全域資料，而且用的是「執行當下」的值，不是登錄當下的值。
  • 出錯時在子程式中送 A 型訊息終止，資料庫會回到 SAP LUW 開始前的一致狀態。
  • ROLLBACK WORK 會丟棄所有已登錄的 ON COMMIT 子程式。

原廠整理的直接更新優缺點：概念簡單、實作快；但使用者必須等更新完成、對話工作程序不會釋放、沒有錯誤日誌、多個對話程序同時打資料庫造成資料庫效能差、LUW 與鎖都得自己在程式裡做、系統功能幫不上忙。所以只適合「輕量」LUW：只更新單筆，或不在乎效能的情境。

11. Update Task（更新技術）：原理、更新模組與 SM13

更新技術把使用者對話和資料庫更新拆到不同程式、通常也在不同工作程序執行：對話程式負責收使用者輸入，最後把變更資料交出去，觸發更新程式寫資料庫；更新程式裡不跑任何對話。五個步驟：

  1. 寫請求：對話程式以 CALL FUNCTION … IN UPDATE TASK 呼叫更新模組，函數不立即執行，而是把「函數名＋傳入資料」寫進更新日誌表。可寫多筆，這些請求就是一個 SAP LUW。
  2. 完成請求：遇到 COMMIT WORK 時，系統為這批請求建立日誌表頭，關閉這個 LUW，並通知 dispatcher 有更新包待處理。
  3. 傳遞資訊：Basis 程式從日誌讀出該 LUW 的資料，交給更新程式。
  4. 執行更新：更新程式依日誌內容執行各個更新模組，全部在同一個 DB LUW 內（all or nothing）。
  5. 刪除請求：成功後 Basis 程式刪除該 LUW 的日誌；失敗則保留並標記錯誤，並寄 express mail 通知觸發者。

日誌表：可以是叢集表 VBLOG，或透明表 VBHDR（表頭，COMMIT WORK 時寫入）、VBMOD（更新模組資訊）、VBDATA（傳入資料）、VBERROR（錯誤）。每次 IN UPDATE TASK 呼叫寫一筆 VBMOD＋一筆 VBDATA；同一個 SAP LUW 的所有請求共用一把更新鍵（VB key），它是全球唯一的 SAP LUW 識別碼。

更新模組：在 SE37 屬性頁把處理類型設為 Update Module，並選擇：Start Immediately（V1，可重啟）、Immediate Start, No Restart（V1，不可重啟）、Start Delayed（V2）、Collective Run（V2 集體執行）。介面規則：

  • 只有 IMPORTING 與（為了相容性保留的）TABLES 參數，必須用字典型別、勾選 Pass Value（傳值）。
  • EXPORTING 與例外在更新情境中都會被忽略（可以定義，但沒有作用）。

12. 更新模式：非同步、同步、本地，以及更新中的鎖

模式語法行為適用
非同步（預設）COMMIT WORK對話程式寫完日誌、COMMIT 後立刻繼續，不等更新結束；更新在專用的 UPD 工作程序跑，甚至可在另一台應用伺服器對話處理的標準技術；使用者「感覺」快比立即知道結果更重要時
同步COMMIT WORK AND WAIT對話程式等更新結束才繼續；等待期間被 roll out，對話工作程序先釋放給別人；結果看 sy-subrc後續處理或程式結束方式取決於更新結果時（例如下一步要讀剛寫入的資料）
本地先 SET UPDATE TASK LOCAL，再 IN UPDATE TASK，最後 COMMIT WORK更新模組在同一個對話工作程序內同步執行；請求放主記憶體、不寫 VBDATA，沒有 I/O 所以最快，但獨占工作程序只適合批次（背景）模式

本地更新的規則：SET UPDATE TASK LOCAL 只能在目前 LUW 尚未產生任何請求時下，有效到下一個 COMMIT WORK 為止；錯誤時自動 DB 回滾，並以終止訊息結束對話程式。以上更新模式的討論只針對 V1 請求。

更新中的鎖：對話程式以 _scope = 2 設的鎖，會在 COMMIT WORK（AND WAIT）時交給 V1 更新任務，之後對話程式就碰不到了；V1 結束時無論成功或 A 訊息失敗都會自動刪除（預設）。所以鎖不能在對話程式裡顯式刪（太早，更新還沒寫），也不需要在更新模組裡刪（多餘）。若更新模組允許重新處理失敗的請求（V1 可重啟），要注意重處理時資料庫狀態可能已不同，而且通常已經沒有鎖了（例如表空間溢位造成寫入失敗，修復後重處理就很合理）。

BAPI 也是同一套機制：多數 BAPI 內部就是 CALL FUNCTION … IN UPDATE TASK，所以呼叫完一定要 BAPI_TRANSACTION_COMMIT（等於 COMMIT WORK），要立刻讀回結果就傳 WAIT = 'X'（等於 COMMIT WORK AND WAIT）。詳見 4-1 章 RFC / BAPI 與 5-12 章 BC415。

13. V1 / V2 更新與資料庫更新的最佳化

V1 / V2 把變更分成高優先與低優先，讓資料庫存取在時間上更分散。同一個 SAP LUW 可以混用：

  • 更新開始時，所有 V1 請求在一個獨立的 DB LUW 中執行（V1 更新工作程序，類型 UPD）；成功後刪除 V1 請求、刪除交給更新任務的鎖、DB Commit，然後觸發 V2。
  • V2 請求只有在所有 V1 都成功後才執行，自成另一個 DB LUW（V2 工作程序，類型 UP2；沒設 UP2 時在 UPD 中跑）；V2 一律不帶 SAP 鎖。典型用途：統計資料更新——和主變更相關，但不必在同一個 DB LUW。
  • V1 可設為可重啟／不可重啟；可重啟者在修正應用錯誤後可於 SM13 手動重啟。V2 一律可重啟。
  • Collective Run（集體執行）是特殊 V2：不在 V1 之後立即執行，要等收集程式 RSM13005（通常排程定期跑）才處理。
  • V1 請求在同步／非同步模式寫進日誌表，本地模式放主記憶體；V2 請求不論何種模式都寫日誌表。
失敗點系統動作
V1 模組送 A 訊息刪除交給更新的鎖（預設）、DB 回滾、寄信給建立 LUW 的使用者（預設）、V1 請求在日誌標記錯誤並記下訊息、V2 不會被觸發
V2 模組送 A 訊息DB 回滾，本 SAP LUW 的 V2 變更全部撤銷，V2 請求在 VBLOG 標記錯誤（V1 早已提交，不受影響）

最佳化：讓資料庫鎖越短越好。每筆被更新的紀錄都會被資料庫實體鎖到該 DB LUW 結束，SELECT … FOR UPDATE 也一樣。SAP 系統普遍採用 dirty read（未提交讀取），純讀取通常不受影響，但並行的更新會被擋。撰寫直接更新與更新模組時照這個順序：

  1. 先 INSERT 新紀錄：新列的 DB 鎖對別人干擾最小。
  2. 再 UPDATE 不影響效能的表：很少人同時存取的表。
  3. 最後才 UPDATE 中心資源表：很多人同時存取的表（例如庫存、座位數、號碼範圍）盡量放在 LUW 最後，讓鎖只擋一下下。

更新中的 PERFORM ON COMMIT：想把某張中心表的變更延到整個 DB LUW 最後，可把該表的更新包成更新模組所屬函數群組內的 FORM，再從更新模組中以 ON COMMIT 登錄；它會在該 SAP LUW 最後一個更新模組處理完之後才執行，且只能使用該函數群組的全域資料。這是 PERFORM ON COMMIT 在今日仍然合理的少數用途（標準 SAP 的過帳函數群組大量使用），但它屬於函數群組內部實作，新開發的業務邏輯仍以類別為主。

「V3 更新」你可能在 LO 抽取（BW / LIS）聽過，它不是 BC414 的內容；BC414 只講 V1、V2 與 V2 的 Collective Run。

14. 跨多支程式的 LUW：CALL FUNCTION、SUBMIT、CALL TRANSACTION 與鎖

同步呼叫其他程式有兩種：

  • 插入式（呼叫端暫停、被呼叫端結束後回來）：CALL FUNCTION、CALL METHOD（類別或物件）、CALL TRANSACTION、SUBMIT … AND RETURN。
  • 取代式（呼叫端結束、被呼叫端開始）：SUBMIT、LEAVE TO TRANSACTION。

SUBMIT 只能叫可執行程式（類型 1）；CALL / LEAVE TO TRANSACTION 叫交易碼。非同步呼叫則用 CALL FUNCTION … STARTING NEW TASK <task>，函數必須在屬性中標為 Remote-Enabled Module，結果用 RECEIVE RESULTS FROM FUNCTION 收回。

呼叫方式資料（上下文）SAP LUW適合
CALL FUNCTION／方法獨立相同（與呼叫端同一個 LUW）顯示；在同一 LUW 中修改（例如報表呼叫多個 BAPI，一次 COMMIT WORK 全部提交）
SUBMIT AND RETURN／CALL TRANSACTION獨立（新的內部階段）獨立（自己的更新鍵）顯示；在不同 LUW 中修改（巢狀 LUW）
SUBMIT／LEAVE TO TRANSACTION取代呼叫端的 LUW 結束流程交棒
CALL FUNCTION … STARTING NEW TASK獨立（新的主階段）獨立平行處理

重點規則：

  • SUBMIT AND RETURN／CALL TRANSACTION：被呼叫端結束後，呼叫端的 SAP LUW 繼續；兩邊的 LUW 各自獨立，更新請求與 ON COMMIT 子程式都要在各自的 LUW 裡各下一次 COMMIT WORK。巢狀呼叫交易時，每個交易都需要自己的 COMMIT WORK。
  • SUBMIT／LEAVE TO TRANSACTION：呼叫端的 LUW 結束。若在呼叫前沒用 COMMIT WORK 結束更新請求，該更新鍵不會產生表頭——這些請求永遠不會被執行；ON COMMIT 子程式同理。
  • SUBMIT、CALL TRANSACTION、LEAVE TO TRANSACTION 都會隱式 DB Commit：呼叫端到此為止的直接更新都自動提交。
  • 非同步 RFC：在新的階段跑、有自己的 SAP LUW；呼叫端只短暫中斷，已登錄的 IN UPDATE TASK 與 ON COMMIT 都保留，但會觸發隱式 DB Commit（直接更新落地）。

CALL TRANSACTION 的呼叫模式：用 USING <bdc 內表> 帶入批次輸入格式的畫面資料，就能在背景執行交易。MODE：A＝顯示（預設）、N＝不顯示、E＝只在錯誤時顯示、P＝在中斷點顯示除錯器。UPDATE：A＝非同步（預設）、S＝同步（被呼叫交易的更新完成才回來，結果看 sy-subrc）、L＝本地。後續處理依賴這筆交易成功時，就用 UPDATE 'S'（BDC 細節見 4-4 章）。

複雜 LUW 中的鎖：

  • 程式設了 E 鎖後，同一程式或同步呼叫的函數模組／方法中可以再設同一個 E 鎖（累積）。
  • 但從 SUBMIT AND RETURN 或 CALL TRANSACTION 叫起來的程式，不能對既有鎖再加鎖——會得到 FOREIGN_LOCK，因為那是新的 LUW。累積只在同一個 LUW 內有效。
  • SUBMIT／LEAVE TO TRANSACTION：呼叫端立即終止、所有鎖自動刪除，因此不會有鎖衝突。
  • 同一使用者從不同視窗（主階段）或不同登入發出的鎖請求，被當成不同使用者處理。
最常見的自我鎖死：程式先 ENQUEUE 了訂單，再 CALL TRANSACTION 標準交易（例如 VA02）去改同一張單——標準交易會回報「已被使用者 XXX（你自己）鎖定」。解法是在 CALL TRANSACTION 之前先 DEQUEUE 自己的鎖，或改用同 LUW 的 BAPI。這也是 Casper 經驗 3「先找標準（BAPI）再想客製（BDC）」的另一個理由。

强晟筆記 p119 的非同步技巧：想在另一個視窗（非模態）開一個交易，就寫一支自訂 RFC 函數，用 STARTING NEW TASK 非同步呼叫，在函數裡 CALL TRANSACTION。因為新階段有自己的 SAP 記憶體，資料要透過函數介面傳入，在函數內再 SET PARAMETER（或用 ABAP 記憶體、BDC 內表）交給交易。

15. 號碼範圍：SNRO、NUMBER_GET_NEXT 與緩衝模式

商業物件用唯一鍵識別，鍵的全部或一部分通常是一個號碼。號碼範圍管理負責把物件分配到特定的號碼區間，並保證每個號碼只發一次。

  • 號碼範圍物件（Number Range Object）：技術定義；在 SNRO 建立，客製物件以 Y / Z 開頭。每個物件下可有多個號碼範圍（以號碼範圍編號識別），每個範圍一個區間；也可依會計年度各設區間（To-year flag）。
  • 內部給號：系統自動給；外部給號：外部輸入，系統只檢查是否落在外部區間。內外部要用不同區間，區間不可重疊；外部區間可以是英數字。
  • 子物件（Subobject）：依某個值分開給號（例如每個公司代碼各自一套、每個工廠各自一套），子物件資料元素長度最多 6 碼，需有值表。
  • 群組表（Group table）：依分類條件決定號碼範圍（例如物料類型 → 原料、半成品、成品各一段），群組表每筆稱為一個元素，可存一個或兩個（內部＋外部）範圍編號；可與子物件合用。

一次要多個號碼時，匯入參數 QUANTITY 給需求量，匯出的 QUANTITY 是實得數量、NUMBER 是最後一個號碼，所以拿到的區段是（NUMBER − 實得數量 + 1）～ NUMBER。

緩衝模式（SNRO：Edit → Set up Buffering）行為優缺點
No buffering每次取號都直接讀 NRIV，並把該區間用資料庫鎖鎖到下一次 DB Commit（不用 SAP 鎖，否則鎖會跟著 V1 更新拖很久）無跳號、保證時間順序；但資料庫鎖造成序列化
Main Memory（預設）每台應用伺服器在記憶體中緩衝一包號碼，由號碼範圍伺服器（自己的 LUW）發號；用完自動補下一包；NUMBER_GET_NEXT 可用 IGNORE_BUFFER 略過緩衝效能最好；rollback、網路錯誤、系統重啟會跳號，各伺服器之間號碼不按時間順序
Parallel（Local File and Process ID）號碼包存在表 NRIVSHADOW 而非記憶體；ROLLBACK 時號碼寫回緩衝可再用，系統重啟也不遺失（SAP Note 599157）不需鎖 NRIV，效能遠優於不緩衝；緩衝數 1 時號碼遞減發放，直到第一次 ROLLBACK 前都無跳號；報表 RSSNR0S1 可列出未確定使用的號碼

法規要求「連續且遞增」時（例如某些國家的發票號碼），可以用平行緩衝的特殊變體 Italian solution（緩衝數 = 1；ROLLBACK 的號碼不會再發，而是寫進 NRIV_DOCU 留作文件），但它無法在 SNUM Customizing 直接啟用，需要在應用中透過 exit 修改（SAP Note 840901）。號碼範圍另有五個函數群組處理維護對話、資料庫存取等，只用標準取號功能時只需要 SNR3。

號碼範圍是典型的「中心資源」：不緩衝的物件在高併發下會讓大家排隊等 NRIV 的資料庫鎖——這就是第 13 節「中心表最後更新」原則的實例：取號放在 LUW 盡量晚的位置，或在法規允許的範圍內開緩衝。設計 Z 單據前先問清楚財會／稽核：到底需不需要「不跳號」？

16. 變更文件：SCDO、CDHDR / CDPOS 與產生的更新模組

要記錄「誰、何時、用哪個交易、把哪個欄位從什麼改成什麼」，就用變更文件。原則是：應用表與變更文件表必須在同一個 LUW 內一起更新，而寫變更文件的是系統產生的更新模組。要傳給它三類資料：變更前的應用資料、變更後的應用資料、管理資料。

表內容主要欄位
CDHDR（計畫變更：PCDHDR）變更文件表頭鍵：MANDANT、OBJECTCLASS（變更文件物件名）、OBJECTID（應用自訂，常用被改紀錄的鍵串接）、CHANGENR（變更號碼，取自號碼範圍物件 AENDBELEG、範圍 01）；非鍵：USERNAME、UDATE、UTIME、TCODE、CHANGE_IND（U / I / D）
CDPOS（計畫變更：PCDPOS）變更文件項目鍵另加 TABNAME、TABKEY、FNAME、CHNGIND（U / I / D，以及逐欄記錄的 J＝新增、E＝刪除）；非鍵：VALUE_NEW、VALUE_OLD

只有被標為變更文件相關的欄位（其資料元素勾選了「Change document」屬性）有變動時才會產生文件，也只記錄這些欄位。修改既有紀錄時每個相關欄位一個項目；新增或刪除紀錄時可選擇「每欄一個項目」或「整筆一個項目」。

建立變更文件物件（SCDO；選單：Tools → ABAP Workbench → Development → Other Tools → Change Documents）：名稱用 Z_ / Y_ 開頭、填描述；每張相關表填一列；多筆紀錄共用一個表頭時勾 Passed as internal table；刪除／新增時逐欄記錄分別勾 Doc. of individual fields at deletion / insertion；幣別與單位欄位參照其他表時要建參照結構（元件名＝表名＋欄位名，例如 T100WAERS）填入 Name of Ref. tab；不勾內表時可指定 old field string 名稱（空白則預設 *<TABLE>）。

產生程式物件（SCDO → Utilities → Generate update pgm.）：填 Include、函數群組、結構前綴後存檔，會產生：

  • 函數群組內的更新模組 <物件>_WRITE_DOCUMENT（封裝寫文件的全部程式）。
  • Include F<inc>CDF（與物件定義無關的變數）、F<inc>CDV（與物件定義相關的變數）、F<inc>CDT（含前兩者）、F<inc>CDC（呼叫更新模組的子程式 CD_CALL_<物件>）。
  • 勾了「內表傳遞」的表，還會產生字典結構 <前綴><TABLE>（含該表＋結構 ICDIND）。

傳統用法是 INCLUDE F<inc>CDT 與 F<inc>CDC、設好全域變數（OBJECTID、TCODE、UTIME、UDATE、USERNAME、新舊值、每張表的 UPD_<TABLE> 旗標 I / U / D / 空白）再呼叫子程式。教材也提到 SCDO 提供「ABAP OO generation style」，產生的是 DATA os_sbook TYPE sbook 這類宣告而非舊式表工作區。現代寫法建議直接呼叫產生的更新模組，不經過 include 與子程式：

17. Object Services：持久化服務與交易服務

Persistence Service 是介於 ABAP 程式與資料庫之間的軟體層，讓你透過持久化物件的屬性存取資料庫紀錄。在 Class Builder 建立持久化類別（persistent class）時，會自動產生類別代理（class agent / class actor，命名 CA_…）管理執行期物件；物件不能用 CREATE OBJECT 建立，而是由代理的方法取得，以確保初始狀態正確。「持久化類別」不代表類別本身被存起來，而是它的物件與狀態由 Persistence Service 管理。

  • 物件的狀態在實例化時等於資料庫當時的狀態；屬性的修改在 COMMIT WORK 之前不會寫入資料庫。
  • COMMIT WORK 在此被擴充：Persistence Service 的內部方法會把所有變更打包、交給特殊的更新模組（IN UPDATE TASK），關閉 SAP LUW、觸發更新，並重設所有持久化物件的屬性；要看最新狀態，再呼叫一次代理的 GET_PERSISTENT。
  • 所有更新模式都支援。仍然必須自己實作傳統的 SAP 鎖。

18. 叢集表：EXPORT / IMPORT TO DATABASE

資料叢集（data cluster）是一組資料物件（欄位、結構、內表、複雜結構）的組合，用 EXPORT、IMPORT、DELETE 處理，可存在叢集資料庫表中。叢集資料庫表依應用區域（2 碼，自訂）分區，區域內以叢集 ID 識別。

  • 叢集資料庫表必須在 ABAP 字典建成透明表，且有標準結構：MANDT（可省略、自動填）、RELID（區域）、叢集 ID 欄位（自取名）、SRTF2、使用者自訂欄位、CLUSTR、CLUSTD。RELID、SRTF2、CLUSTR、CLUSTD 與叢集 ID 在 EXPORT 時自動填，自訂欄位要在 EXPORT 前自己填，IMPORT 後可讀出。叢集資料長度＝結構總長減掉前六個欄位。
  • 通用的叢集表是 INDX：鍵長 31 bytes（用戶端、區域、叢集 ID〔預設 22 bytes〕、續行號）；資料大時系統自動續寫多列。INDX 還有 AEDAT、USERA、PGMID 等管理欄位，可用 SELECT 讀鍵與管理欄位。
  • EXPORT 沒有寫入保護：同 ID 再 EXPORT 一次就覆蓋；資料以壓縮形式儲存。
  • IMPORT 可以只取部分物件、順序不限；名稱必須與匯出時相同（可用 TO 對應不同變數名），結構必須相符，否則執行時期錯誤。sy-subrc 針對的是整個叢集是否存在，不是個別物件。
  • DELETE 只能刪整個叢集，不能刪其中單一物件。

別把兩種「叢集」搞混：本節是 EXPORT/IMPORT 用的叢集資料庫表（INDX 類），在 S/4HANA 仍完全有效。另一種是 ABAP 字典的 Pool / Cluster Table（例如 ECC 的 BSEG、CDPOS、KONV），S/4HANA 已全部轉成透明表（BSEG 另外被 ACDOCA 取代、KONV 由 PRCD_ELEMENTS 取代）。另外，INDX 類資料對 SQL 是黑盒子、無法查詢，只適合存快照與暫存，不要拿來存需要報表分析的業務資料。

19. 程式呼叫的記憶體模型：ABAP 記憶體、SAP 記憶體與 SUBMIT WITH

邏輯記憶體層級：一個使用者登入（user / terminal session）可開多個主階段（main session，外部階段，約等於一個 SAP GUI 視窗）；每個主階段最多 20 個內部階段，每支程式在一個內部階段執行，程式資料只在程式內可見。

  • SAP 記憶體：每個登入一份，所有主階段共用，整個登入期間保留；存放參數 ID 的值（表 TPARA，ID 最長 20 字元），常用來當畫面欄位預設值。因為所有階段都看得到，只「有條件地」適合在內部階段之間傳資料。
  • ABAP 記憶體：每個主階段一份，只能由 ABAP 程式存取；用來在同一主階段的內部階段之間傳遞變數（欄位、結構、內表、複雜物件）；主階段結束時自動釋放。
呼叫記憶體行為
CALL FUNCTION（同步）函數群組載入目前內部階段，其全域資料保留到呼叫端程式結束；再呼叫同群組的其他函數時不會重新載入、全域資料不會初始化
CALL TRANSACTION／SUBMIT AND RETURN開新的內部階段（新程式上下文），兩個內部階段共用同一份 ABAP 記憶體；結束後刪除新階段，回到呼叫端；被呼叫端可用 LEAVE PROGRAM 提早結束
SUBMIT呼叫端被移出目前內部階段，載入被呼叫程式；ABAP 記憶體不會初始化，仍可用來傳資料
LEAVE TO TRANSACTION移除目前主階段的所有內部階段、開新的內部階段；ABAP 記憶體被初始化，不能用它傳資料給被呼叫交易
STARTING NEW TASK（非同步）同一台應用伺服器上開新的階段平行處理；ABAP 記憶體與 SAP 記憶體都無法共用，只能透過函數介面

程式之間傳資料的五種管道：被呼叫端的介面（方法、函數、子程式、對話模組、報表的標準選擇畫面）、ABAP 記憶體、SAP 記憶體、資料庫表（含 EXPORT/IMPORT 與共用緩衝）、展示伺服器或應用伺服器上的檔案（GUI_UPLOAD / GUI_DOWNLOAD；OPEN DATASET、TRANSFER、READ DATASET，見 4-4 章）。

畫面欄位與 SAP 記憶體的互動（Dynpro 細節見 5-9 章 BC410、4-2 章）：欄位要以連到該參數 ID 的資料元素定義；勾 SET 時，使用者輸入會寫入 SAP 記憶體；勾 GET，且程式只給了初始值時，欄位會顯示 SAP 記憶體中的值當建議值。查欄位的參數 ID：在畫面上按 F1 → Technical Information。在 ABAP 編輯器用「Pattern」插入 SUBMIT 時，系統會自動用 WITH 列出被呼叫程式選擇畫面的所有元素。

現代版本注意：① CALL TRANSACTION 在 7.40 之後應明確寫 WITH AUTHORITY-CHECK（或有理由時 WITHOUT），否則延伸檢查會警告，因為它不會自動檢查 S_TCODE 以外的權限；② ABAP 記憶體（EXPORT/IMPORT MEMORY）與 SAP 記憶體（SET/GET PARAMETER）在 ABAP Cloud 不可用；物件導向程式裡跨類別傳資料，優先用方法參數或類別屬性，需要跨階段共用時用 Shared Objects（見 5-3 章 BC402）。

Casper 三條實務經驗在本課的對應：

  1. HANA 沒有預設排序：SELECT SINGLE … FOR UPDATE 或「取第一筆再更新」若條件不是完整主鍵，每次抓到的可能是不同筆——更新了錯的那筆，而且不會報錯。任何「取第一筆」都要完整主鍵或明確 ORDER BY；批次上鎖時也先依鍵排序，所有程式用相同順序請求鎖，才能避免互相等待（死結）。

METHOD save_booking.
  " ① 鎖（_scope 2：交給更新程式釋放）
  CALL FUNCTION 'ENQUEUE_ESFLIGHT'
    EXPORTING carrid = is_req-carrid connid = is_req-connid fldate = is_req-fldate
    EXCEPTIONS foreign_lock = 1 OTHERS = 2.
  IF sy-subrc <> 0.
    RAISE EXCEPTION TYPE zcx_bc414_locked EXPORTING locked_by = sy-msgv1.
  ENDIF.

  " ② 鎖成功才讀最新資料（完整主鍵，結果唯一）
  SELECT SINGLE seatsmax, seatsocc FROM sflight
    WHERE carrid = @is_req-carrid AND connid = @is_req-connid AND fldate = @is_req-fldate
    INTO @DATA(ls_seat).

  " ③ 業務檢查在對話端做，使用者能反應
  IF ls_seat-seatsocc >= ls_seat-seatsmax.
    RAISE EXCEPTION TYPE zcx_bc414_full.
  ENDIF.

  " ④ 取號（中心資源，盡量晚）
  cl_numberrange_runtime=>number_get( EXPORTING nr_range_nr = '01' object = 'ZBC414BK'
                                      IMPORTING number = DATA(lv_no) ).

  " ⑤ 登錄更新請求（應用資料＋變更文件，同一個 SAP LUW）
  DATA(ls_book) = CORRESPONDING sbook( is_req ).
  ls_book-bookid = CONV #( lv_no ).
  CALL FUNCTION 'Z_BC414_BOOK_CREATE' IN UPDATE TASK
    EXPORTING is_book = ls_book.

  " ⑥ 關閉 LUW；需要馬上讀回結果時用 AND WAIT
  COMMIT WORK AND WAIT.
  IF sy-subrc <> 0.
    RAISE EXCEPTION TYPE zcx_bc414_update_failed.   "詳情請看 SM13
  ENDIF.
  rv_bookid = ls_book-bookid.
ENDMETHOD.

練習與自我檢核

原廠教材的練習以航班模型（SPFLI / SFLIGHT / SBOOK）為主軸，逐步把一支直接更新的訂位程式改造成鎖＋更新模組的版本。以下題目依本章順序整理，附參考答案要點。

  1. 是非題：Open SQL 同時包含 DML 與 DDL。
    答：錯。只有 DML；DDL 由 ABAP 字典負責。
  2. INSERT spfli FROM TABLE @lt 時有一筆主鍵重複，會發生什麼？怎麼讓其他筆照樣寫入？
    答：執行時期錯誤、整批回滾（可用 CX_SY_OPEN_SQL_DB 捕捉）。加 ACCEPTING DUPLICATE KEYS：重複的略過，sy-subrc = 4，sy-dbcnt 為實際寫入筆數。
  3. 只想改兩個欄位，為什麼不建議 UPDATE dbtab FROM @wa？
    答：它以 wa 的主鍵整筆覆蓋；wa 中未填的欄位會被寫成初始值。應用 UPDATE … SET f1 = …, f2 = … WHERE 完整主鍵。
  4. 哪兩種方法會觸發資料庫回滾？差別是什麼？
    答：A／X 終止訊息（回滾並終止程式）與 ROLLBACK WORK（回滾但不終止，且程式上下文不重置）。
  5. 列出至少五種隱式 DB Commit 的情境。
    答：送出畫面（對話步驟結束）、同步／非同步 RFC、WAIT、LUW 中送 I/W/E 訊息、CALL TRANSACTION、LEAVE TO TRANSACTION、SUBMIT（及被呼叫端結束）。
  6. 為什麼跨多個畫面的交易不能只靠 SELECT … FOR UPDATE？
    答：資料庫鎖在每次 DB Commit 時釋放，而每換一次畫面就隱式 commit。
  7. 建立 Z 表 ZBC414_BOOK 的鎖物件，名稱規則？啟用後得到什麼？
    答：EZ 或 EY 開頭（如 EZBC414_BOOK）；自動產生 ENQUEUE_EZBC414_BOOK 與 DEQUEUE_EZBC414_BOOK。
  8. 呼叫 ENQUEUE_ESFLIGHT 只傳 CARRID = 'LH'，鎖住了什麼？若 mandt 傳 SPACE 呢？
    答：LH 的所有航班（其餘參數為萬用字元）；mandt 傳 SPACE 則鎖所有用戶端。要鎖「真的是初始值」的欄位用 x_ 參數。
  9. _SCOPE 的 1、2、3 各用在什麼情境？
    答：1＝直接更新，程式自己解鎖；2（預設）＝交給更新程式，更新結束自動釋放；3＝一個留程式、一個交給更新（部分更新後仍要持續鎖住整筆）。
  10. 鎖容器怎麼用？FLUSH_ENQUEUE 失敗時容器裡的鎖狀態如何？
    答：呼叫鎖模組帶 _collect = 'X'，再 FLUSH_ENQUEUE 一次送出；失敗時觸發 FOREIGN_LOCK，容器內的鎖一個都沒設、內容保留，可再試或用 RESET_ENQUEUE 清掉。
  11. 同一程式已有 E 鎖，再要求 E、S、X 各會如何？其他使用者要求 S 呢？
    答：同一程式：E 與 S（及 O）接受、X 拒絕。其他使用者：任何模式都被拒絕。
  12. 寫出悲觀鎖模式的四個步驟，並說明先讀後鎖的風險。
    答：鎖 E → 讀 → 改並寫入 → 解鎖。先讀後鎖會讓使用者在過期資料上作業。
  13. 樂觀鎖的兩個階段？O 升級失敗代表什麼？
    答：第一階段設 O 鎖並讀取；第二階段用 R 升級成排他鎖再存檔、解鎖。升級失敗代表別人已先升級（你的 O 被刪）或有人持有 S 鎖，須重新讀取。
  14. 更新模組的介面有哪些限制？可以在裡面 COMMIT WORK 嗎？
    答：只能有 IMPORTING 與 TABLES，字典型別、Pass Value；EXPORTING 與例外被忽略；不可 COMMIT WORK／ROLLBACK WORK，要回滾送 A 訊息。
  15. 寫出 Update Task 的五個步驟，以及日誌相關的四張透明表。
    答：寫請求 → 完成請求（COMMIT WORK 建表頭）→ 傳給更新程式 → 執行更新 → 刪除請求。VBHDR、VBMOD、VBDATA、VBERROR（或叢集表 VBLOG）。
  16. 非同步、同步、本地三種更新模式的語法與適用情境？
    答：COMMIT WORK（對話標準）；COMMIT WORK AND WAIT（後續依賴結果，看 sy-subrc）；SET UPDATE TASK LOCAL＋COMMIT WORK（主記憶體、最快、獨占工作程序，只適合批次）。
  17. V1 失敗時 V2 會執行嗎？V2 有鎖嗎？Collective Run 何時執行？
    答：V1 失敗則 V2 不觸發；V2 一律不帶 SAP 鎖；Collective Run 要等 RSM13005 執行。
  18. 在一個更新模組中同時要 INSERT 訂位、UPDATE 航班座位數、UPDATE 客戶統計，順序怎麼排？
    答：先 INSERT 新紀錄 → 再改少人存取的表（客戶統計，或乾脆放 V2）→ 最後改中心表（SFLIGHT 座位數）。
  19. 程式 A 登錄了 IN UPDATE TASK 後，沒有 COMMIT WORK 就 LEAVE TO TRANSACTION，結果如何？換成 CALL TRANSACTION 呢？
    答：LEAVE TO TRANSACTION 結束 A 的 LUW，更新鍵沒有表頭，請求永遠不執行。CALL TRANSACTION 則 A 的 LUW 在回來後繼續，請求仍保留，A 之後的 COMMIT WORK 會提交；但被呼叫交易有自己的 LUW，自己要 COMMIT。
  20. 程式設了 E 鎖，再 CALL TRANSACTION 一支也要鎖同一筆的交易，結果？
    答：FOREIGN_LOCK。CALL TRANSACTION 是新的 LUW，無法累積鎖。須先解鎖或改用同 LUW 的函數／BAPI。
  21. 號碼範圍三種緩衝模式各自的優缺點？法規要求不跳號時怎麼辦？
    答：不緩衝＝無跳號、依時序，但 NRIV 資料庫鎖造成序列化；記憶體緩衝＝最快但會跳號、跨伺服器無時序；平行緩衝＝存 NRIVSHADOW，rollback 號碼可回收。法規需求可評估 Italian solution（Note 840901）或不緩衝。
  22. 變更文件的表頭與項目存在哪裡？欄位要怎樣才會被記錄？
    答：CDHDR 與 CDPOS（計畫變更 PCDHDR / PCDPOS；ECC 時代項目在叢集 CDCLS，S/4HANA 已是透明表）；欄位的資料元素要勾「Change document」。變更號碼取自號碼範圍物件 AENDBELEG。
  23. 持久化物件修改屬性後何時寫入資料庫？需要自己上鎖嗎？
    答：COMMIT WORK（或 OO 模式下 top-level 交易 END( )）時才產生更新請求；仍要自己實作 SAP 鎖。
  24. EXPORT 到 INDX 同一個 ID 兩次會怎樣？DELETE 能只刪其中一個物件嗎？
    答：第二次覆蓋第一次（沒有寫入保護）；DELETE 只能刪整個叢集。
  25. LEAVE TO TRANSACTION 能用 ABAP 記憶體傳資料嗎？SUBMIT 呢？非同步 RFC 呢？
    答：LEAVE TO TRANSACTION 不行（ABAP 記憶體被初始化）；SUBMIT 可以（不初始化）；非同步 RFC 兩種記憶體都不行，只能用函數介面。
  26. 實作題：建立 Z 表 ZBC414_BOOK（含 BOOKID 以號碼範圍 ZBC414BK 給號）、鎖物件 EZBC414_BOOK、V1 更新模組 Z_BC414_BOOK_CREATE、變更文件物件 ZBC414_BOOK，寫一支對話程式完成訂位；故意在更新模組裡讓第二筆 SQL 失敗，到 SM13 看錯誤、到 SM12 確認鎖已被釋放、確認 CDHDR 沒有留下半套紀錄。
    答要點：鎖用 _scope 2、COMMIT WORK 後不 DEQUEUE；更新模組用 A 訊息；應用更新與 _WRITE_DOCUMENT 在同一 LUW，因此失敗時兩者一起回滾。
