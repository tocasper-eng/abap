1. 四代增強技術總覽：先搞清楚你在第幾代

SAP 的「增強（Enhancement）」演進了四代。每一代都還活著、都還會在標準程式裡遇到，所以你必須一眼認出現在看到的是哪一代，才知道要去哪個交易碼做。

代名稱在標準程式裡長什麼樣工具特性
第一代User Exit（客戶出口／原始碼出口）PERFORM userexit_xxx、SAPMV45A 的 MV45AFZZ 等 Z 開頭 IncludeSE38 直接寫 FORM其實是「被 SAP 預留的修改」，要 Access Key，會列入 SPAU

老師的選用順序（S/4HANA 一樣適用）：
① 先問「標準設定能不能做到？」（IMG／SPRO、容差、欄位選擇、訊息控制 OBA5）
② 做不到 → 找 BAdI（第三／四代）
③ 沒有 BAdI → 找 Enhancement Point（隱式／顯式）
④ 都沒有 → 才考慮 Modification（修改標準），需要 Access Key，且每次升級都要在 SPAU 對帳。
換句話說：能設定就不寫程式，能掛勾就不改標準。
第一條鐵律，老師在講義裡用最大的字寫著：一定要加上 IF sy-uname = 'ERPXXX' 防止干擾到全部的人。 教學機／開發機是共用的，你在 BAdI 裡寫的檢查會對所有人生效，沒有加帳號判斷，隔壁同學的 ME21N 全都會被你擋住。上正式環境時，這個條件要換成正式的判斷邏輯（工廠、公司代碼、料號群組、Z 表控制），而不是留著寫死的帳號。

2. 第三代 Classic BAdI 的運作原理

Classic BAdI 是一組互相搭配的物件，理解它們的關係，你才知道 SE18／SE19 每個畫面在做什麼：

物件命名慣例由誰產生作用
BAdI 定義（Definition）BADI_MATERIAL_CHECK、Z_BADIDEF_BADITEST2SE18 建立宣告「這裡有一個掛勾點」，資料存在 SXS_ATTR
BAdI 介面（Interface）IF_EX_<定義名>SE18 自動產生（可在 SE24 看）規範方法名稱與參數；實作類別必須實作它所有方法
介面卡類別（Adapter Class）CL_EX_<定義名>SE18 自動產生執行期由它負責把呼叫轉發給所有作用中的實作
BAdI 實作（Implementation）Z_BADI_ERP000_CHECKSE19 建立對應一個實作類別 ZCL_IM_*，資料存在 SXC_EXIT／SXC_CLASS
Exit HandlerCL_EXITHANDLERSAP 標準靜態方法 GET_INSTANCE，執行期動態產生介面卡實例

標準程式呼叫 Classic BAdI 的固定樣式長這樣，認得這 10 行，你就認得所有第三代增強點：

" 標準程式（例如 SAPLMIGO）裡的典型第三代 BAdI 呼叫
DATA lo_badi TYPE REF TO if_ex_mb_migo_badi.   "介面型別 = IF_EX_ + BAdI 名稱

CALL METHOD cl_exithandler=>get_instance
  EXPORTING
    exit_name              = 'MB_MIGO_BADI'    "BAdI 定義名稱
    null_instance_accepted = 'X'               "沒有任何實作時允許回傳空參照
  CHANGING
    instance               = lo_badi.

IF lo_badi IS BOUND.                            "沒有實作時就跳過
  CALL METHOD lo_badi->check_item
    EXPORTING
      i_line_id = lv_line_id
    CHANGING
      ct_msg    = lt_msg.
ENDIF.
為什麼 GET_INSTANCE 有時候沒有 EXPORTING？ 因為 exit_name 是選擇性參數。當 CHANGING 的參照變數型別是 IF_EX_XXX 時，框架可以由型別反推 BAdI 名稱，所以講義中的簡寫 CALL METHOD cl_exithandler=>get_instance CHANGING instance = exit. 也能跑。實務上建議明寫 exit_name，除錯時比較好讀。
介面卡的魔法：lo_badi 指向的不是你的 ZCL_IM_* 類別，而是 SAP 產生的 CL_EX_* 介面卡。你呼叫一次 check_item，介面卡會依序呼叫所有作用中的實作。這就是「Multiple Use（多重使用）」能成立的原因。

3. SE18：建立 Classic BAdI 定義（含多重使用與過濾器）

進入 SE18，輸入定義名稱（自建一律 Z／Y 開頭），按建立。畫面上有四個頁籤要填：（依講義步驟整理）

  1. Attributes（屬性）：
    • Type：Multiple Use（多重使用）／Filter-Dependent（依過濾器）
    • Filter Type：勾了 Filter-Dependent 才要填，通常填一個 Data Element（例如 BUKRS、WERKS_D、LAND1）
    • Instance Creation：預設每次呼叫產生新實例
  2. Interface（介面）：填介面名稱，預設就是 ZIF_EX_<定義名>。存檔後按介面名稱會跳到 SE24，在那裡定義方法與參數。
  3. Subscreens（子畫面）：需要在標準畫面上加自己的頁籤時才用。
  4. Imp. Example（範例實作）：可選，給實作者參考用的樣板類別。
選項意義什麼時候勾陷阱
Multiple Use同一個定義可以同時有多個作用中的實作，全部都會被呼叫純檢查、純寫 Log、純通知執行順序不保證！不要讓兩個實作互相依賴。這正是「沒排序就抓錯資料」那類 bug 的根源
Filter-Dependent實作上掛過濾值，只有值相符時才被呼叫不同公司代碼／國家／工廠要不同邏輯介面的每個方法會自動多出一個 FLT_VAL importing 參數，呼叫端必須傳值
Instance Creation實例產生模式幾乎都用預設Context-dependent 只在少數 SAP 內部 BAdI 使用

介面方法在 SE24 定義時，參數方向的意義要抓對：

方向你在實作裡能做什麼
IMPORTING只能讀。標準程式把當下的資料交給你判斷
CHANGING可讀可寫，寫回去會影響標準流程（例如改欄位值、加旗標）
EXPORTING你回傳結果給標準程式（例如回傳訊息表、回傳「檢查失敗」）
EXCEPTIONS／RAISING丟例外中斷流程；Classic BAdI 多半用訊息表或 MESSAGE 而非例外
講義第一頁的紅字：「同一個 interface 底下的所有 method 都要正確，否則會無效。」
Classic BAdI 的實作類別必須實作介面的每一個方法。你只想寫 PROCESS_ITEM，但介面還有 10 個方法，那 10 個方法也必須存在（可以是空的 METHOD ... ENDMETHOD.）。只要有一個方法語法錯誤，整個類別無法啟動，於是整個 BAdI 實作等於沒作用——而且不會有任何錯誤訊息告訴你，你會以為「BAdI 沒被呼叫」。這是初學者最常卡住的地方。

4. SE19：建立 Classic BAdI 實作

進入 SE19，在「Create Implementation」區選 Classic BAdI，輸入 BAdI 定義名稱，再給實作名稱（Z 開頭），系統會產生實作類別 ZCL_IM_<實作名>。（依講義步驟整理）

  1. 輸入短文字說明。
  2. 切到 Interface 頁籤，會看到介面的所有方法列表。
  3. 雙擊要寫的方法 → 進入類別編輯器 → 寫程式 → 存檔。
  4. 回到 SE19 按 Activate（啟動）。沒有啟動的實作等於不存在。
  5. 指定傳輸請求（Workbench Request）。

實作的骨架就是這樣，記得第一行永遠是帳號／範圍防護：

METHOD if_ex_z_badidef_baditest2~method.

  "★★ 防護：只對自己的帳號生效，避免干擾同一台機器的其他人 ★★
  CHECK sy-uname = 'ERP000'.

  "把傳進來的字串轉大寫後寫回去（CHANGING 參數）
  parameter = to_upper( parameter ).

ENDMETHOD.
講義原文寫的是 TRANSLATE parameter TO UPPER CASE.——這在 S/4HANA 仍可執行，但現代寫法建議用內建函數 to_upper( ) / to_lower( ) / to_mixed( )，可以直接寫在運算式裡，不必先搬到變數。
SE19 的另一個用法：反查。 講義 02-19 的「省思過程」就是這招——在 SE19 輸入你自己的實作名稱（例如 Z_BADI_ERP000_CHECK）按 Change / Display，畫面上就會顯示它屬於哪一個 BAdI 定義與哪一個 Enhancement Spot。忘記自己當初掛在哪裡時，這是最快的路。

5. 自建第三代增強完整實例：Z_BADIDEF_BADITEST2

講義第 03 節的完整流程，把「定義 → 實作 → 呼叫」三件事一次走完，這是理解 Classic BAdI 最好的沙盤。

步驟 1：SE18 建立定義 Z_BADIDEF_BADITEST2，介面 ZIF_EX__BADIDEF_BADITEST2，在 SE24 為介面新增一個方法 METHOD，參數 PARAMETER 型別 STRING，方向 CHANGING。

步驟 2：SE19 建立實作，方法內容如下。

METHOD zif_ex__badidef_baditest2~method.
  "示範：把呼叫端傳來的字串改成大寫再送回去
  parameter = to_upper( parameter ).
ENDMETHOD.

步驟 3：寫一支測試程式（講義的 Z_BUSINESSADDIN），親手做一次標準程式在做的事。以下是現代化改寫版：

REPORT z_businessaddin.

"講義原文有一行 CLASS cl_exithandler DEFINITION LOAD.
"那是舊式的「先載入類別定義」宣告，S/4HANA 已不需要，可直接刪除。

PARAMETERS p_word TYPE string LOWER CASE
           DEFAULT 'change to upper case'.

START-OF-SELECTION.

  DATA lo_badi TYPE REF TO zif_ex__badidef_baditest2.

  "① 由 Exit Handler 動態取得介面卡實例
  CALL METHOD cl_exithandler=>get_instance
    EXPORTING
      exit_name              = 'Z_BADIDEF_BADITEST2'
      null_instance_accepted = 'X'
    CHANGING
      instance               = lo_badi.

  "② 沒有任何作用中的實作時，lo_badi 會是空的，一定要擋
  IF lo_badi IS NOT BOUND.
    MESSAGE |目前沒有任何作用中的 BAdI 實作| TYPE 'I'.
    RETURN.
  ENDIF.

  DATA(lv_word) = p_word.
  WRITE: / |原始字串：{ lv_word }|.

  "③ 呼叫 BAdI，CHANGING 參數會被實作改掉
  lo_badi->method( CHANGING parameter = lv_word ).

  WRITE: / |增強後字串：{ lv_word }|.
不要忘了 IS BOUND 檢查。 若沒有作用中的實作，且呼叫時沒有傳 null_instance_accepted = 'X'，GET_INSTANCE 會丟出例外；若傳了 'X'，回傳的是空參照，接著直接呼叫方法就會得到 CX_SY_REF_IS_INITIAL 短傾印。標準程式一律先 IF lo_badi IS BOUND.，你自己寫也要照做。

如果這個 BAdI 是 Filter-Dependent，呼叫時要多帶過濾值：

"Filter-dependent 的 Classic BAdI：介面方法會自動多一個 FLT_VAL 參數
DATA lo_badi TYPE REF TO zif_ex_z_badi_by_bukrs.

CALL METHOD cl_exithandler=>get_instance
  EXPORTING
    exit_name = 'Z_BADI_BY_BUKRS'
  CHANGING
    instance  = lo_badi.

IF lo_badi IS BOUND.
  lo_badi->check_document(
    EXPORTING flt_val  = lv_bukrs      "只有掛這個公司代碼的實作會被執行
    CHANGING  cs_data  = ls_data ).
ENDIF.

6. 怎麼找到「該用哪個 BAdI」——五種找法

這是增強工作真正花時間的地方。寫程式 10 分鐘，找增強點 3 小時，講義 02-03 到 02-08 整整六頁都在做這件事。下面把老師的流程整理成可重複執行的 SOP。

找法 A：從畫面找到程式，再在程式裡搜尋關鍵字（講義主線）

  1. 在交易畫面（例如 MIGO）按 F1 → 技術資訊，或選單 System → Status，取得程式名稱（MIGO 是 SAPLMIGO）。
  2. 進 SE38 ／ SE80 開啟該程式 → 選單 Utilities → Find in Source Code（或 Ctrl+F 勾「In main program」＋「In includes」）。
  3. 搜尋這四組關鍵字，就能把四代增強一網打盡：
    • CL_EXITHANDLER → 第三代 Classic BAdI
    • GET BADI 或 CALL BADI → 第四代 New BAdI
    • CUSTOMER-FUNCTION → 第二代 Customer Exit
    • USEREXIT → 第一代 User Exit
  4. 找到後，看 exit_name = '...' 的字面值，那就是 BAdI 名稱（講義在 MIGO 找到的是 MB_MIGO_BADI）。
  5. 把候選 BAdI 拿到 SE18 看它的方法清單與文件，確認哪個方法在你要的時間點被呼叫。
講義 02-07 誠實寫著「再搭配問了 ChatGPT 之後，選定了 MB_DOCUMENT_BADI」。這一步的判斷準則是：MB_MIGO_BADI 偏畫面／逐行互動（適合即時檢查與加欄位）；MB_DOCUMENT_BADI 偏文件層級（適合過帳前的整份檢查）。要做「整張收貨單累加後判斷是否超交」，就該選文件層級的那一個。

找法 B：SE11 直接查 BAdI 目錄表（講義 03-04）

"SXS_ATTR  = BAdI 定義屬性；SXS_ATTRT = BAdI 定義的多語文字

  LEFT OUTER JOIN sxs_attrt AS t
    ON  t~exit_name = a~exit_name
    AND t~sprsl     = @sy-langu

cl_salv_table=>factory( IMPORTING r_salv_table = DATA(lo_alv)

找法 C：SE84 增強樹（講義 02-20 用它反查自己的實作）

SE84（Repository Information System）→ Enhancements 節點底下：

  • Customer Exits → Enhancements：第二代
  • Business Add-Ins → Definitions / Implementations：第三代，可用「Package（套件）」篩選，例如 MM 相關填 ME*、MB*
  • Enhancement Spots / Enhancement Implementations：第四代
用 Package 找 BAdI 是最高效的招式：先在交易畫面 System → Status 看該程式屬於哪個 Package（例如 MIGO 是 MB／MBGD），再到 SE84 用該 Package 列出全部 BAdI 定義，通常十來個，一眼掃過去就找到了。

找法 D：Debug 中設中斷點（最可靠，一定找得到「真正會被呼叫」的那一個）

  1. 執行交易 → /h 進入除錯器。
  2. 選單 Breakpoints → Breakpoint at → Method，輸入類別 CL_EXITHANDLER、方法 GET_INSTANCE。
  3. 按 F8 繼續，每停一次就看變數 exit_name，把過程中出現的 BAdI 名稱全部抄下來。
  4. 第四代則設 Breakpoint at Statement，輸入 GET BADI 或 CALL BADI。
這個方法的價值在於：它列出的是實際執行路徑上真的會被呼叫的 BAdI，不會像靜態搜尋那樣抓到一堆走不到的分支。缺點是清單很長（一次交易可能觸發數十個 BAdI），要有耐心。

找法 E：SAT／SE30 執行追蹤

SAT（S/4HANA 取代舊的 SE30）做一次交易的執行追蹤，在結果的「呼叫階層」裡過濾類別名稱含 CL_EX_ 或 CL_IM_／ZCL_IM_ 的項目，就能看到整個流程呼叫過哪些 BAdI 介面卡與實作。搭配 ST05（SQL Trace）還能同時看到它們讀了哪些表。

7. 實戰一：BADI_MATERIAL_CHECK 檢核物料主檔（MM02）

講義 01-02 到 01-04 的例子：用 BADI_MATERIAL_CHECK（介面 IF_EX_BADI_MATERIAL_CHECK）在 MM01／MM02 存檔前檢查物料主檔資料。這是第三代 BAdI 最經典的入門題：先在 SE24 看介面有哪些方法與參數，再到 SE18 看定義，最後到 SE19 寫實作。

*&---------------------------------------------------------------------*
*&  BAdI  : BADI_MATERIAL_CHECK
*&  Method: CHECK_DATA  （物料主檔存檔前檢查）
*&---------------------------------------------------------------------*
METHOD if_ex_badi_material_check~check_data.

  "★ 防護：只對自己的測試帳號生效
  CHECK sy-uname = 'ERP000'.

  "wmara / wmarc / wmard ... 是標準傳進來的工作區（結構視版本而異，
  "實際參數請以 SE18 → Interface → SE24 顯示為準）
  IF wmara-mtart = 'FERT' AND wmara-matkl IS INITIAL.
    "回傳訊息給 MM02 畫面：塞進標準的訊息表
    APPEND VALUE #( msgid = 'ZMM'
                    msgty = 'E'
                    msgno = '010'
                    msgv1 = wmara-matnr )
           TO ch_messages.
  ENDIF.

ENDMETHOD.

9. 第四代：Enhancement Spot 與 New BAdI 架構

第四代把「增強」抽象成兩個容器，觀念上就是「定義端」與「實作端」各有一個資料夾：

層級定義端（SAP 或你建立）實作端（你建立）
容器Enhancement Spot（增強點）Enhancement Implementation（增強實作）
內容BAdI Definition（可多個）BAdI Implementation（可多個）
最底層Interface（IF_*，名稱自由，不必 IF_EX_）Implementing Class（ZCL_*）
工具SE18 / SE80 / ADTSE19 / SE80 / ADT
另有一種Composite Enhancement Spot（把多個 Spot 群組起來）Composite Enhancement Implementation

New BAdI 相對第三代多出來的能力，每一個都很實用：

能力說明在哪裡設
Fallback Class（後備類別）當沒有任何作用中的實作時，框架自動改叫這個類別。等於「內建的預設行為」BAdI 定義的屬性頁
Default Implementation實作標成「預設」，只要有其他非預設實作作用中，它就自動退場BAdI 實作的屬性
Implementation Sequence（排序）多重使用時可指定執行順序，解決第三代「順序不保證」的老問題BAdI 定義勾「Sortable」，在實作上填順序號
Filter（過濾器）可定義多個過濾欄位，支援 =、BETWEEN、CP 等運算子與 AND/OR 組合BAdI 定義的 Filter 頁 ＋ 實作上填值
Instance Creation ModeNewly（每次新建）／Reusing（重用同一實例）／Context-dependentBAdI 定義屬性
Switch Framework整個 Enhancement Implementation 可掛在 Switch 上，靠 Business Function 開關建立時指定 Switch ID
Internal / External 呼叫控制SAP 可宣告某 BAdI 只供內部使用（客戶不得實作）BAdI 定義的 Contract
「重用實例（Reusing）」的重要性：如果你的 BAdI 實作需要跨方法保存狀態（例如在 OPEN 撈一批資料快取起來，給後面每個 PROCESS_ITEM 用），就必須把 Instance Creation Mode 設成 Reusing，否則每次呼叫都是新實例，類別屬性永遠是空的。第三代 BAdI 沒有這個選項，只能用 CLASS-DATA（靜態屬性）勉強達成——而靜態屬性在同一個 session 裡不會自動清空，是很常見的髒資料來源。

10. GET BADI / CALL BADI 語法與例外處理

第四代的呼叫語法變成兩個獨立的 ABAP 指令，不再是呼叫類別方法。這也是為什麼你在標準程式裡搜尋 CL_EXITHANDLER 找不到東西時，要改搜 GET BADI。

"===== 第四代 New BAdI 的標準呼叫樣式 =====
"① 宣告：型別直接就是「BAdI 定義名稱」（BAdI 參照型別）
DATA lo_badi TYPE REF TO zbadi_demo01.

TRY.
    "② 取得 BAdI handle；有 filter 就在這裡給值
    GET BADI lo_badi
      FILTERS
        bukrs = lv_bukrs
        werks = lv_werks.

    "③ 呼叫方法；多重使用時，框架會依序呼叫所有符合的實作
    CALL BADI lo_badi->print
      EXPORTING input  = lv_input
      IMPORTING output = DATA(lv_output).

  CATCH cx_badi_not_implemented.
    "沒有任何實作、也沒有 fallback class → 走原本的預設邏輯
    lv_output = lv_input.

  CATCH cx_badi_multiply_implemented.
    "非多重使用的 BAdI 卻有多個作用中實作 → 設定錯誤
    MESSAGE |BAdI 設定錯誤：同時有多個作用中實作| TYPE 'E'.

  CATCH cx_badi_filter_error.
    "過濾值缺漏或型別不符
    MESSAGE |BAdI 過濾器設定錯誤| TYPE 'E'.

  CATCH cx_badi_initial_reference.
    "handle 是空的就呼叫 CALL BADI
    MESSAGE |BAdI handle 尚未取得| TYPE 'E'.

  CATCH cx_root INTO DATA(lo_err).
    MESSAGE lo_err->get_text( ) TYPE 'E'.
ENDTRY.
指令作用要點
GET BADI handle向框架要一個 BAdI handle此時才決定「哪些實作符合過濾條件」；成本較高，不要放在迴圈裡
GET BADI ... FILTERS f = v帶過濾值定義有幾個 filter 就要給幾個；漏給會 CX_BADI_FILTER_ERROR
CALL BADI handle->meth呼叫方法多重使用時是「一次呼叫、多個實作依序執行」
GET BADI ... CONTEXT objContext-dependent BAdI少見，SAP 內部使用居多
效能口訣：GET 一次，CALL 多次。 GET BADI 會去查詢有哪些實作、算過濾條件，開銷不小。正確做法是在迴圈外面 GET，迴圈裡面 CALL： 
GET BADI lo_badi FILTERS bukrs = p_bukrs.   "★ 迴圈外，只做一次

LOOP AT lt_items INTO DATA(ls_item).
  CALL BADI lo_badi->check_item              "★ 迴圈內，只有呼叫
    EXPORTING is_item = ls_item
    CHANGING  ct_msg  = lt_msg.
ENDLOOP.
Fallback Class 讓 CX_BADI_NOT_IMPLEMENTED 幾乎不會發生。 如果 BAdI 定義掛了 Fallback Class，即使沒有任何客戶實作，框架也會呼叫 fallback，因此呼叫端不必寫「沒實作時的預設邏輯」。你自己設計 BAdI 時，建議一律準備 Fallback Class，把預設行為寫在裡面，呼叫端的程式碼會乾淨很多。

REPORT zbaditest.

12. Classic BAdI 被「強制升級」為 New BAdI

講義 02-11「被強迫升級」、02-17「強制轉回 NEW BADI 了」講的就是這件事。SAP 已經把大量 Classic BAdI 定義遷移（migrate）成 New BAdI，並收進 Enhancement Spot 裡。於是會發生這個現象：

  • 你在 SE19 選「Classic BAdI」輸入 MB_DOCUMENT_BADI，系統跳出訊息說這個 BAdI 已經遷移，要求你改用 New BAdI 的方式建立。
  • 照做之後，你得到的是一個 Enhancement Implementation（而不是舊的 Classic Implementation），它掛在 Enhancement Spot MB_GOODSMOVEMENT 底下（講義 02-21）。
  • 但介面名稱與方法簽章完全沒變，還是 IF_EX_MB_DOCUMENT_BADI~MB_DOCUMENT_BEFORE_UPDATE。所以你原本寫好的程式碼可以原封不動貼過去。
怎麼判斷一個 BAdI 是不是已經遷移？ 在 SE18 輸入名稱按「Display」，如果畫面直接開的是 Enhancement Spot 的樹狀結構，它就是（或已遷移成）New BAdI；如果開的是舊式的 Attributes／Interface 四頁籤畫面，那還是純 Classic。另一個線索：New BAdI 的定義畫面上會有 Fallback Class 與 Filter 這兩個 Classic 沒有的欄位。

MIGO 禁止超交（講義 02-01～02-18）的完整實作。這是全章最有價值的一段程式，我把它改寫成 S/4HANA 的現代寫法並修掉幾個坑：

*&---------------------------------------------------------------------*
*&  BAdI  : MB_DOCUMENT_BADI （已遷移，屬 Enhancement Spot MB_GOODSMOVEMENT）
*&  Method: MB_DOCUMENT_BEFORE_UPDATE
*&  目的  : MIGO 收貨時，料號 CHLK1300 且使用者 ERP000 不可超交
*&---------------------------------------------------------------------*
METHOD if_ex_mb_document_badi~mb_document_before_update.

  "① 防護：只針對 MIGO ＋ 指定使用者
  CHECK sy-tcode = 'MIGO' AND sy-uname = 'ERP000'.

  TYPES: BEGIN OF ty_po,
           ebeln    TYPE ekpo-ebeln,
           ebelp    TYPE ekpo-ebelp,
           po_qty   TYPE ekpo-menge,   "訂購量
           hist_qty TYPE ekpo-menge,   "歷史已收量
           new_qty  TYPE ekpo-menge,   "本次收貨量
         END OF ty_po.

  DATA lt_po TYPE SORTED TABLE OF ty_po WITH UNIQUE KEY ebeln ebelp.

  "② 收集本次過帳（XMSEG）內的目標 PO 行；同一 PO 行可能出現多次，要累加
  LOOP AT xmseg ASSIGNING FIELD-SYMBOL(<ls_mseg>)
       WHERE bwart = '101'                "採購收貨
         AND matnr = 'CHLK1300'
         AND ebeln IS NOT INITIAL.

    READ TABLE lt_po ASSIGNING FIELD-SYMBOL(<ls_po>)
         WITH TABLE KEY ebeln = <ls_mseg>-ebeln
                        ebelp = <ls_mseg>-ebelp.
    IF sy-subrc = 0.
      <ls_po>-new_qty += <ls_mseg>-menge.
    ELSE.
      INSERT VALUE #( ebeln   = <ls_mseg>-ebeln
                      ebelp   = <ls_mseg>-ebelp
                      new_qty = <ls_mseg>-menge ) INTO TABLE lt_po.
    ENDIF.
  ENDLOOP.

  "③ FOR ALL ENTRIES 空表陷阱：空表會變成「沒有 WHERE 條件」，撈回整張表！
  IF lt_po IS INITIAL.
    RETURN.
  ENDIF.

  "④ 取 PO 訂購量
  SELECT ebeln, ebelp, menge
    FROM ekpo
    FOR ALL ENTRIES IN @lt_po
    WHERE ebeln = @lt_po-ebeln
      AND ebelp = @lt_po-ebelp
      AND loekz = @space                  "排除已刪除的行
    INTO TABLE @DATA(lt_ekpo).

  "⑤ 從 EKBE 彙總歷史已收量；直接用 CASE 在資料庫端加總，少搬一次資料
  SELECT ebeln, ebelp,
         SUM( CASE shkzg WHEN 'H' THEN menge * -1 ELSE menge END ) AS qty
    FROM ekbe
    FOR ALL ENTRIES IN @lt_po
    WHERE ebeln = @lt_po-ebeln
      AND ebelp = @lt_po-ebelp
      AND vgabe = '1'                     "1 = 收貨
      AND bwart IN ( '101', '102', '122', '123' )
    GROUP BY ebeln, ebelp
    INTO TABLE @DATA(lt_ekbe).

  "⑥ 回填訂購量與歷史量
  LOOP AT lt_po ASSIGNING FIELD-SYMBOL(<po>).

    IF line_exists( lt_ekpo[ ebeln = <po>-ebeln ebelp = <po>-ebelp ] ).
      <po>-po_qty = lt_ekpo[ ebeln = <po>-ebeln ebelp = <po>-ebelp ]-menge.
    ENDIF.

    IF line_exists( lt_ekbe[ ebeln = <po>-ebeln ebelp = <po>-ebelp ] ).
      <po>-hist_qty = lt_ekbe[ ebeln = <po>-ebeln ebelp = <po>-ebelp ]-qty.
    ENDIF.
  ENDLOOP.

  "⑦ 超交判斷
  LOOP AT lt_po INTO DATA(ls_chk).
    IF ls_chk-hist_qty + ls_chk-new_qty > ls_chk-po_qty.
      "MESSAGE ... WITH 每個變數最多 50 字元，超過會被截斷，所以拆四段
      MESSAGE e001(zmm) WITH |CHLK1300 不可超交|
                             |PO { ls_chk-ebeln }-{ ls_chk-ebelp }|
                             |訂購 { ls_chk-po_qty NUMBER = USER }|
                             |已收 { ls_chk-hist_qty NUMBER = USER }|.
    ENDIF.
  ENDLOOP.

ENDMETHOD.
這段程式的五個關鍵坑：
① FOR ALL ENTRIES 空表 = 撈全表。lt_po 為空時，SAP 會把 WHERE 條件整段拿掉，你會把整張 EKPO 搬進記憶體。必須先 IF lt_po IS INITIAL. RETURN. ENDIF.
② FOR ALL ENTRIES 會自動去重複，且驅動內表的欄位型別必須與 DB 欄位一致，否則會有隱性型別轉換。
③ 方法選錯就沒救：MB_DOCUMENT_BEFORE_UPDATE 在對話工作程序執行，可以發 MESSAGE E 把使用者擋回畫面；但同一個 BAdI 的 MB_DOCUMENT_UPDATE 在更新工作（Update Task）執行，那裡發 E 訊息會造成更新中止（Update Terminated），使用者收到快遞郵件、資料半套，是很嚴重的事故。
④ EKBE 的 SHKZG：'S' 借方（收貨，加）、'H' 貸方（退貨／沖銷，減）。忘了處理 H，退貨過的 PO 會永遠被誤判為超交。
⑤ MESSAGE ... WITH 每個變數上限 50 字元，且最多 4 個。講義原文把兩段長字串用 & 接成一個變數傳，會被截掉一半。
先問「標準能不能做」！ 禁止超交其實是採購單的標準設定：EKPO-UEBTO（超交容差百分比）設 0、EKPO-UEBTK（無限超交）不勾，SAP 就會自己擋。或用 OMCQ 把訊息 M7 系列的超交警告從 W 改成 E。能設定就不要寫 BAdI——這是第 1 節那個口訣的活教材。會寫這支 BAdI 的理由，是需求裡有「只擋特定料號＋特定使用者」這種標準做不到的條件。

13. Enhancement Framework：隱式增強點（Implicit Enhancement Point）

這是第四代最強大也最危險的能力：SAP 在每一支 ABAP 程式的固定位置，都預先埋好了看不見的掛勾點，你不必等 SAP 提供 BAdI，就能在標準程式插入自己的程式碼，而且不算修改（Modification）、不需要 Access Key。

位置可以做什麼常見用途
程式／Include 的最開頭與最結尾宣告全域變數、寫收尾邏輯宣告要跨 FORM 使用的變數
FORM 的第一個可執行語句前、ENDFORM 前讀／改該 FORM 的區域變數與參數最常用的插入點
METHOD ... ENDMETHOD 的開頭與結尾同上OO 標準程式的插入點
FUNCTION ... ENDFUNCTION 的開頭與結尾同上改函數的回傳值
MODULE ... ENDMODULE 的開頭與結尾PBO/PAI 邏輯Dynpro 畫面控制
函數模組的參數介面末端新增選擇性參數擴充標準 FM 的介面
類別各 Section（PUBLIC/PROTECTED/PRIVATE）末端新增屬性與方法擴充標準類別
DDIC 結構的末端Append Structure（需 Enhancement Category 允許）加自訂欄位

操作步驟（在 SE38 或 SE80 開啟標準程式）：（依講義步驟整理）

  1. 顯示模式開啟程式後，按工具列的 Enhance（螺絲起子＋扳手圖示，或 Shift+F4），程式碼底色轉為灰／黃，進入增強模式。
  2. 選單 Edit → Enhancement Operations → Show Implicit Enhancement Options，程式碼中會出現一條條虛線——每一條虛線就是一個隱式增強點。
  3. 把游標放在要用的虛線上 → 右鍵 Enhancement Implementation → Create。
  4. 選 Code（Source Code Plug-In），輸入 Enhancement Implementation 名稱（Z 開頭）與短文字，選 Package 與傳輸請求。
  5. 系統在該位置產生一組 ENHANCEMENT ... ENDENHANCEMENT 區塊（底色亮黃），在裡面寫程式。
  6. 存檔 → 啟動（Ctrl+F3）。
*----------------------------------------------------------------------*
* 隱式增強：插在標準 FORM 的結尾（ENDFORM 之前）
* Enhancement Implementation: ZENH_MIGO_NO_OVERDELIVERY
*----------------------------------------------------------------------*
ENHANCEMENT 1 ZENH_MIGO_NO_OVERDELIVERY.    "active version

  "★ 防護：只對指定帳號、指定交易生效
  IF sy-uname = 'ERP000' AND sy-tcode = 'MIGO'.

    "此處可直接讀取這個 FORM 的區域變數與全域變數
    IF gs_goitem-matnr = 'CHLK1300'.

      SELECT SINGLE menge, uebto, uebtk
        FROM ekpo
        WHERE ebeln = @gs_goitem-ebeln
          AND ebelp = @gs_goitem-ebelp
        INTO @DATA(ls_ekpo).

      IF sy-subrc = 0 AND ls_ekpo-uebtk = abap_false.
        "已收量 ＋ 本次量 是否超過訂購量
        SELECT SINGLE
               SUM( CASE shkzg WHEN 'H' THEN menge * -1 ELSE menge END )
          FROM ekbe
          WHERE ebeln = @gs_goitem-ebeln
            AND ebelp = @gs_goitem-ebelp
            AND vgabe = '1'
          INTO @DATA(lv_hist).

        IF lv_hist + gs_goitem-erfmg > ls_ekpo-menge.
          MESSAGE |料號 CHLK1300 不可超交（訂購 { ls_ekpo-menge NUMBER = USER }）|
                  TYPE 'E'.
        ENDIF.
      ENDIF.
    ENDIF.

ENDENHANCEMENT.
隱式增強的三大風險：
① 你在標準程式裡執行任意程式碼，SAP 完全不保證上下文。 你用到的區域變數可能在下個 Support Package 就被改名或刪除，程式會在升級後語法錯誤，而且是在客戶的正式環境爆掉。
② 效能：插在迴圈裡的 SELECT 會被執行成千上萬次。要撈資料請先在迴圈外撈成內表。
③ 難以追蹤：別人看標準程式時，如果沒開 Enhance 模式就看不到你的程式碼。務必在增強區塊第一行寫清楚：誰、什麼時候、為什麼、對應的需求單號。
結論：隱式增強是最後手段，能用 BAdI 就不要用它。
怎麼找出系統裡已經有哪些隱式增強？ SE84 → Enhancements → Enhancement Implementations，或直接查表 ENHHEADER／ENHOBJ（ENHNAME LIKE 'Z%'）。接手一套別人做過的系統時，第一件事就是把這張清單印出來。

14. 顯式增強點：ENHANCEMENT-POINT 與 ENHANCEMENT-SECTION

顯式（Explicit）增強點是 SAP 或你自己在原始碼裡明寫出來的掛勾點，比隱式安全得多，因為位置是被官方承諾的。它有兩種：

種類語法行為
ENHANCEMENT-POINT單一敘述，標出一個位置你的程式碼插入在該位置，原始碼照常執行
ENHANCEMENT-SECTION一對 ENHANCEMENT-SECTION … END-ENHANCEMENT-SECTION 包住一段原始碼你的程式碼取代被包住的那段原始碼
 
*----------------------------------------------------------------------*
* 在你自己的程式裡「預留」增強點，讓別的顧問／客戶去實作
*----------------------------------------------------------------------*
REPORT zsd_price_check.

"① 先在 SE18 建立一個 Enhancement Spot：ZSPOT_SD_PRICE

"② 靜態增強點：STATIC 表示這裡可以「宣告資料」
ENHANCEMENT-POINT zep_price_data SPOTS zspot_sd_price STATIC.

DATA: lv_price TYPE netwr,
      lv_disc  TYPE p LENGTH 8 DECIMALS 2.

START-OF-SELECTION.

  lv_price = 1000.

"③ 一般增強點：這裡可以插入可執行的敘述
ENHANCEMENT-POINT zep_price_before SPOTS zspot_sd_price.

"④ 增強區段：被包住的預設演算法，可以被整段換掉
ENHANCEMENT-SECTION zes_price_calc SPOTS zspot_sd_price.

  lv_disc = lv_price * '0.05'.        "預設折扣 5%

END-ENHANCEMENT-SECTION.

  WRITE: / |折扣：{ lv_disc NUMBER = USER }|.

實作端在 SE38 開啟這支程式、進 Enhance 模式後，游標放在增強點上右鍵建立實作，產生的程式碼是：

"針對 ENHANCEMENT-SECTION 建立的實作：整段取代原本的預設演算法
ENHANCEMENT 1 ZENH_SD_PRICE_VIP.    "active version

  "台灣區 VIP 客戶折扣改成 12%
  IF sy-uname = 'ERP000'.
    lv_disc = lv_price * '0.12'.
  ELSE.
    lv_disc = lv_price * '0.05'.     "★ 記得補回原本的邏輯，否則會消失！
  ENDIF.

ENDENHANCEMENT.
ENHANCEMENT-SECTION 是「取代」不是「附加」。 一旦你為某個 Section 建立實作，被包住的原始碼就不會執行了。如果你只是想微調，記得把原本的邏輯抄一份進來。這是 Section 最常見的事故：折扣邏輯被整段吃掉，只剩你寫的那一行。
STATIC 的意義：加了 STATIC 的 ENHANCEMENT-POINT 才允許在實作裡宣告資料物件（DATA、TYPES、CONSTANTS）。沒加 STATIC 的只能放可執行敘述。另外，增強點若定義在被多支主程式共用的 Include 裡、且希望實作對所有引用該 Include 的程式都生效，定義時要加 INCLUDE BOUND（依 BC425 原廠教材；舊版此處誤寫為「DDIC 結構增強要用 INCLUDE BOUND」，已更正，詳見 5-15 章）。設計自己的程式時，習慣上會在「宣告區」放一個 STATIC 增強點、在「處理前／處理後」各放一個一般增強點，這樣別人要擴充就很方便。

15. Class / Function Module Enhancement：pre-exit、post-exit、overwrite-exit

對類別的方法與函數模組，第四代提供了三種「方法級」的增強，這是 OO 標準程式最乾淨的增強方式。在 SE24 開啟類別 → 按 Enhance → 建立 Enhancement Implementation → 在方法上右鍵選要建立哪一種。

種類執行時機能改什麼典型用途
Pre-Exit原方法執行前可改 IMPORTING／CHANGING 參數清洗輸入值、補預設值
Post-Exit原方法執行後可改 EXPORTING／CHANGING／RETURNING 結果調整回傳結果、追加資料、寫 Log
Overwrite-Exit完全取代原方法整個實作換掉標準演算法完全不適用時；風險最高

Overwrite-Exit 幾乎等同修改標準。 它會讓 SAP 未來對該方法的所有修正（Support Package、Note）完全失效，而且不會有任何警告。除非是 SAP 支援明確建議，否則不要用。真的用了，一定要在 Enhancement 的文件裡寫下「取代的原始版本是哪一個 SP」。

17. S/4HANA、Clean Core 與 ABAP Cloud 三層擴充模型

從 S/4HANA（特別是 Cloud 版與 2022 之後的 On-Premise）開始，SAP 主推 Clean Core（乾淨核心）：客戶的擴充不能弄髒標準，升級才能自動化。擴充被分成三層：

層名稱誰做工具典型內容
①Key User Extensibility（關鍵使用者擴充）顧問／業務端Fiori App：Custom Fields and Logic、Custom Business Objects、Custom CDS Views加自訂欄位、用受限的 ABAP 語言片段寫 BAdI 邏輯、做自訂報表
②Developer Extensibility（開發者擴充，In-App）ABAP 開發者ADT（Eclipse），語言版本 ABAP for Cloud Development寫 RAP 應用、CDS View、Behavior Definition、實作 Released BAdI
③Side-by-Side Extensibility（並列擴充）開發者SAP BTP（ABAP Environment／CAP／Node.js／Java）獨立跑在 BTP 上，用 OData／SOAP／Events 與 S/4 溝通
在 ABAP Cloud（語言版本 = ABAP for Cloud Development）裡，以下全部禁止：
・Classic BAdI（CL_EXITHANDLER）
・User Exit、Customer Exit（SMOD/CMOD）
・隱式增強點與 Source Code Plug-in
・直接 SELECT 未釋出的標準資料表（例如直接讀 MARA、BSEG）
・大部分傳統 UI（Dynpro、SAP List Viewer 的舊 FM、WRITE 清單）
唯一被允許的增強方式，是實作 SAP 標記為 Released（C1 契約）的 Enhancement Spot／BAdI，並且只能透過 ADT 建立。
怎麼知道一個物件有沒有 Released？
① 在 ADT 開啟該物件，看 Properties → API State，顯示「Released for Cloud Development / Use System-Internally」。
② 在 SAP 的 API Business Hub 或 Released Object 清單查詢。
③ 系統內可查 CDS View I_APIRELEASESTATE 之類的釋出狀態視圖（版本相依）。
On-Premise 的 S/4HANA 仍可用 ABAP 的標準語言版本（Standard ABAP）寫所有舊寫法，但 SAP 建議新開發一律用 ABAP Cloud 語言版本，只有真的做不到時才降級——這叫 Tiered Extensibility Model（三層優先序）。
務實建議（On-Premise S/4HANA 專案）：
・新做的增強，先在 SE18 查該 BAdI 是不是 Released；是的話盡量用 ADT 做，未來搬雲端不必重寫。
・隱式增強點只在沒有 BAdI 且時程緊迫時使用，並在增強文件裡寫下「這是技術債，未來要換成 BAdI」。
・自訂欄位優先用 Key User 的 Custom Fields（會自動延伸到 CDS／OData／Fiori），而不是 Append Structure ＋ 手改畫面。

傳輸（Transport）的五個坑：
① BAdI 定義與實作是兩個不同的物件，可能落在不同的傳輸單。只傳實作、忘了傳定義（自建 BAdI 時），目標系統會啟動失敗。
② Enhancement Implementation 與它產生的 Class 也是兩個物件；SE19 通常會一起放進同一個請求，但手動改過名稱／Package 之後就不一定。傳輸前用 SE09 展開請求內容逐項確認。
③ 啟動狀態不會自動帶過去：在開發機是 Active，到品保機若相依物件缺漏就會變成 Inactive，而且不會報錯，只是不生效。傳完一定要在目標系統用 SE19 確認狀態。

  2. 為什麼「同一個 interface 底下的所有 method 都要正確，否則會無效」？
    答案要點：實作類別必須實作介面的全部方法才能啟動；任一方法語法錯誤 → 類別無法啟動 → BAdI 實作形同不存在，而且執行時不會報錯，只是靜靜地沒作用。
  3. 你在 SE38 開啟 SAPLMIGO，要找出所有第三代與第四代的增強點，分別搜尋哪些關鍵字？

  6. （講義 02 節） 為什麼講義最後選了 MB_DOCUMENT_BADI 而不是 MB_MIGO_BADI？兩者的分工是什麼？

  7. MB_DOCUMENT_BEFORE_UPDATE 與 MB_DOCUMENT_UPDATE 有什麼致命差別？
    答案：前者在對話工作程序，可以發 MESSAGE E 擋下使用者；後者在更新工作，發 E 會造成更新中止、資料不一致，只能寫 Log 或用 MESSAGE ... TYPE 'E' INTO。
  8. 第 12 節那段超交檢查程式裡，如果把 IF lt_po IS INITIAL. RETURN. ENDIF. 拿掉會發生什麼事？
    答案：FOR ALL ENTRIES 遇到空的驅動表，會忽略整個 WHERE 條件，把整張 EKPO／EKBE 撈回來，在正式環境等於系統癱瘓。
  9. 解釋隱式增強點與顯式增強點的差別，並各舉一個 MIGO 情境。
    答案要點：隱式是 SAP 在每支程式的固定位置（程式／FORM／METHOD／FUNCTION 的頭尾）自動提供、看不見、不保證上下文；顯式是 SAP 在原始碼裡明寫 ENHANCEMENT-POINT／ENHANCEMENT-SECTION、位置被承諾。優先用顯式與 BAdI，隱式是最後手段。
  10. ENHANCEMENT-POINT 與 ENHANCEMENT-SECTION 最重要的行為差異是什麼？
    答案：POINT 是插入（原始碼照常執行）；SECTION 是取代（被包住的原始碼不再執行），所以要自己把原邏輯抄一份回來。
  11. Pre-Exit、Post-Exit、Overwrite-Exit 各在什麼時候用？哪一個最不該用？
    答案：Pre 改輸入、Post 改輸出、Overwrite 整個換掉。Overwrite 會讓 SAP 對該方法的所有後續修正失效，最不該用。
  12. New BAdI 的 Fallback Class 解決了 Classic BAdI 的什麼痛點？
    答案：Classic BAdI 沒有實作時回傳空參照，呼叫端必須自己寫 IS BOUND 判斷與預設邏輯；Fallback Class 讓框架在無實作時自動執行預設行為，呼叫端程式碼變乾淨。
  13. 為什麼 GET BADI 不能放在迴圈裡？
    答案：GET BADI 要查詢實作清單、計算過濾條件，成本高。正確做法是迴圈外 GET 一次、迴圈內 CALL 多次。
  14. 如果你的 BAdI 實作需要在 OPEN 撈一批資料快取，給後面每次 PROCESS_ITEM 使用，第四代要怎麼設定？第三代只能怎麼做？
    答案：第四代把 Instance Creation Mode 設成 Reusing；第三代沒這個選項，只能用 CLASS-DATA 靜態屬性，但要小心跨交易的髒資料，記得在 OPEN 時先清空。

    答案：SPDD（DDIC，升級中就要做）、SPAU（Repository 修改）、SPAU_ENH（Enhancement Framework 增強）。
  16. 在 ABAP Cloud（ABAP for Cloud Development）裡，第 5 節那支 Z_BUSINESSADDIN 測試程式為什麼一行都跑不動？
