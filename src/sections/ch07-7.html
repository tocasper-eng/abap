3. 報表變式呼叫框架：ZCL_CALL_REPORT_VARIANTS 的類別定義（9.02）

觀念：很多標準報表（例如 QA07 週期檢驗觸發、MRP 相關清單）要用十幾個變式分批跑。原作者的想法是：把「變式的報表名稱、描述關鍵字、每個變式之間的等待秒數」當成物件屬性，讓一個類別負責「找出這組變式 → 逐一執行 → 記錄日誌」，排程時只要排一支呼叫程式。

4. 找出要跑的變式：VARID／VARIT 與「描述分組」（9.02 GET_REPORT_VARIANTS；勘誤第 10 條）

觀念：原範例的分組方式是「在變式描述（VARIT-VTEXT）裡放一個組別代碼」，執行時用 LIKE '%代碼%' 把同組變式一次撈出來。書中第 352 頁以 QA07 為例：把 QA07 的變式命名為 QA07_G02_04 這類名稱，並把描述（Description）設成「G02」，執行時輸入 G02 就能跑完這一組。

勘誤表第 10 條：原書第 352 頁此句括號中的英文單字有誤，應為 Description——「僅需將新的參數存入 QA07 的參數如 QA07_G02_04，並將描述（Description）設定成為『G02』，儲存即可」。這裡的「參數」指的就是報表變式（Variant）。QA07 在 SE93 對應的報表程式名稱，請以你的系統為準後再填入 p_rep_id。

範例（改寫後）：

METHOD get_report_variants.

  • 會重複加 % 的 bug：原範例用 CONCATENATE '%' mv_variant_desc_c '%' INTO mv_variant_desc_c 直接改寫屬性本身，同一個物件第二次呼叫就變成 %%G02%%；而且 CHAR20 放滿 20 字再加兩個 % 會被截斷。改寫版用區域變數＋字串範本。

5. 以 SUBMIT 逐一執行變式並送 Spool（9.01／9.02 CALL_REPORT_BY_VARIANT）

觀念：SUBMIT (動態程式名) USING SELECTION-SET 變式 TO SAP-SPOOL SPOOL PARAMETERS … WITHOUT SPOOL DYNPRO AND RETURN——以變式執行指定報表，清單輸出直接進 Spool（SP01 可查），不跳列印對話框，執行完回到呼叫端。

METHOD call_report_by_variant.
  IF mt_report_variant IS INITIAL.
    add_msg( iv_msgty = 'W' iv_msgno = '002' iv_v1 = 'No variant found for ' iv_v2 = mv_rep_id iv_level = 1 ).
    save_log( ).
    RETURN.
  ENDIF.

  " 先取得一組有效的列印參數（原範例直接傳空白的 PRI_PARAMS）
  DATA lv_valid TYPE c LENGTH 1.
  CALL FUNCTION 'GET_PRINT_PARAMETERS'
    EXPORTING
      no_dialog      = abap_true
      immediately    = abap_false
      release        = abap_false
    IMPORTING
      out_parameters = ms_print_params
      valid          = lv_valid
    EXCEPTIONS
      OTHERS         = 1.
  IF sy-subrc <> 0 OR lv_valid IS INITIAL.
    add_msg( iv_msgty = 'E' iv_msgno = '002' iv_v1 = 'Invalid print parameters' iv_level = 1 ).
    save_log( ).
    RETURN.
  ENDIF.

  LOOP AT mt_report_variant INTO DATA(ls_var).
    DATA(lv_idx) = sy-tabix.          " SUBMIT 之後 sy-tabix 不可靠，先記下
    SUBMIT (mv_rep_id)
      USING SELECTION-SET ls_var-variant
      TO SAP-SPOOL
      SPOOL PARAMETERS ms_print_params
      WITHOUT SPOOL DYNPRO
      AND RETURN.

    add_msg( iv_msgty = 'I' iv_msgno = '002'
             iv_v1 = 'Program ' iv_v2 = mv_rep_id
             iv_v3 = 'submitted with variant ' iv_v4 = ls_var-variant
             iv_level = 3 ).

    IF mv_wait > 0 AND lv_idx < lines( mt_report_variant ).
      WAIT UP TO mv_wait SECONDS.     " 只為了錯開負載，不是等報表跑完
    ENDIF.
  ENDLOOP.

  save_log( ).                        " 全部跑完再一次存檔
ENDMETHOD.

與原範例的差異：

  • 原範例宣告了 ls_print_par TYPE pri_params 卻從未填值就傳給 SUBMIT；空白的列印參數（沒有輸出裝置等）在背景執行時很容易失敗或進到預設印表機。改寫版先用 GET_PRINT_PARAMETERS（NO_DIALOG）取得有效參數並檢查 VALID。
  • 原範例把 SUBMIT 包在 TRY … CATCH cx_root 裡，以為被呼叫的報表出錯可以「記一筆 E 再繼續下一個變式」。實際上被 SUBMIT 的程式內部發生的執行期錯誤會直接中止並產生 ST22 短傾印，不會回到呼叫端的 CATCH；報表若用 MESSAGE … TYPE 'E' 結束也只是回到呼叫端，SUBMIT 本身不會拋例外。所以原範例的 E 訊息分支幾乎不會發生，改寫版拿掉這個假安全感。
  • 原範例記的 I 訊息是「runs with variant」，但 SUBMIT … AND RETURN 回來只代表「程式跑完回來了」，不代表結果正確；改寫版的訊息改成「submitted」，避免誤導看日誌的人。
  • WAIT UP TO n SECONDS：SUBMIT … AND RETURN 本來就是同步的，不需要等報表完成；原範例每個變式後都 WAIT（包括最後一個）。另外 WAIT 會觸發隱含資料庫提交並讓出工作程序，放在交易邏輯中間要小心。
  • IF mv_wait IS INITIAL. mv_wait = 5. 在迴圈內重複執行，改寫版移到建構子的 DEFAULT 5。
變式很多、每支都要跑很久時，與其在一個對話程序裡 SUBMIT … AND RETURN 串行執行，不如每個變式開一個背景作業：JOB_OPEN → SUBMIT … VIA JOB … AND RETURN → JOB_CLOSE，交給 SM37 監控（見 4-4 第 15 節）。這樣單一變式失敗不會拖垮整批，也能平行執行。

6. OO 日誌：巨集 vs 私有方法、RECA 訊息清單與 SLG1（9.01／9.02 SAVE_LOG、CONSTRUCTOR）

觀念：原範例用 CF_RECA_MESSAGE_LIST=>CREATE 建立一個 IF_RECA_MESSAGE_LIST 物件（這是 RE-FX 套件提供、對應用日誌 BAL 的 OO 包裝），傳入日誌物件 Z_OOP_LOG（SLG0）、子物件 REPORT 與外部識別 OO_CALL_REP；每筆訊息是一個 RECAMSG 結構（MSGTY／MSGID／MSGNO／MSGV1~4／DETLEVEL），最後 STORE 存進資料庫、CF_RECA_STORABLE=>COMMIT( ) 提交，事後用 SLG1 依物件／子物件／外部識別查詢。

                     EXCEPTIONS error             = 1

12. 工廠模式＋RTTI：CL_ABAP_CLASSDESCR 依訂單類型建立處理類別（9.07）

觀念：不同訂單類型（AUART）的工時計算規則不同，每種規則一個 ZCL_PRD_ORDER 子類別。原範例的巧思是做一個「註冊類別」（屬性 MO_PRD_TYPE）：它的每個屬性名稱就是一個訂單類型、屬性值就是處理類別名稱。工廠用 CL_ABAP_CLASSDESCR=>DESCRIBE_BY_OBJECT_REF 取得註冊類別的屬性清單（ABAP_ATTRDESCR_TAB），找到與訂單類型同名的屬性後，ASSIGN obj->(屬性名) 取值，再 CREATE OBJECT … TYPE (類別名) 動態建立物件。新增訂單類型時只要在註冊類別加一個屬性、再寫一個子類別。

METHOD get_order_instance.
  " iv_order_type TYPE aufk-auart；回傳 ro_prd_order TYPE REF TO zcl_prd_order
  DATA(lo_registry) = NEW zcl_prd_type( ).               " 註冊類別（示意名）
  DATA(lo_descr)    = CAST cl_abap_classdescr(
                        cl_abap_typedescr=>describe_by_object_ref( lo_registry ) ).

  DATA(lv_attr) = to_upper( condense( iv_order_type ) ).  " RTTI 的屬性名一律大寫
  IF NOT line_exists( lo_descr->attributes[ name = lv_attr ] ).
    RAISE EXCEPTION TYPE cx_sy_create_object_error
      EXPORTING classname = CONV #( |ORDER TYPE { iv_order_type }| ).
  ENDIF.

  ASSIGN lo_registry->(lv_attr) TO FIELD-SYMBOL(<lv_class>).
  IF sy-subrc <> 0.
    RAISE EXCEPTION TYPE cx_sy_create_object_error
      EXPORTING classname = CONV #( lv_attr ).
  ENDIF.

  DATA(lv_class) = to_upper( CONV string( <lv_class> ) ).  " 類別名必須大寫
  " NEW 只能用靜態型別；「型別名稱在執行期才知道」時仍要用 CREATE OBJECT … TYPE (…)
  CREATE OBJECT ro_prd_order TYPE (lv_class).              " 失敗時拋 CX_SY_CREATE_OBJECT_ERROR 給呼叫端
  mo_prd_order = ro_prd_order.
ENDMETHOD.

與原範例的差異：

  • 原範例每次都 CREATE OBJECT mo_prd_type 再 LOOP AT gt_attr_desc 逐筆比對名稱；改寫版直接用 line_exists( lo_descr->attributes[ name = … ] )。原範例區域變數用 gt_／gs_（全域）前綴，命名不一致，改寫版改內嵌宣告。
  • 原範例找不到對應屬性時什麼都不做，回傳一個空參照；呼叫端 9.10 接著呼叫 mo_prd_order->cal_work_hour( ) 就會 CX_SY_REF_IS_INITIAL 短傾印。改寫版明確拋例外。
  • 原範例在工廠方法內 CATCH cx_sy_create_object_error 後 MESSAGE exc_text TYPE 'I'：類別方法不應該自己彈出對話框（背景作業、RFC、Fiori 呼叫都沒有畫面），改寫版把例外往上拋，由 UI 層決定怎麼顯示。
  • mo_class_desc ?= … 改成 CAST cl_abap_classdescr( … )；TRANSLATE … TO UPPER CASE 改成 to_upper( )。
  • 這裡保留 CREATE OBJECT … TYPE (lv_class) 不是疏忽：NEW 運算子的型別必須在編譯期已知，動態類別名只能用 CREATE OBJECT。
設計評論：「屬性名＝訂單類型」這招有三個限制——(1) ABAP 屬性名必須以字母開頭，數字開頭的訂單類型無法註冊；(2) 每新增一個訂單類型就要修改並傳輸註冊類別，其實沒有做到開放封閉；(3) 對應關係藏在程式裡，業務顧問看不到。實務上建議改成一張 Z 設定表（AUART → 類別名，SM30 維護，逐筆列舉訂單類型，不要用區間），或者乾脆用 BAdI（多個實作＋過濾值 AUART），這才是 SAP 標準的「依條件選實作」機制（見 3-4 章）。若改讀設定表，SELECT SINGLE 要帶完整主鍵；只帶部分鍵時 HANA 沒有預設排序，每次抓到的「第一筆」可能不同。

13. 依訂單類型計算工時：多型呼叫（9.10）

觀念：採樣器由生產訂單號碼查 AUFK-AUART，把訂單類型交給工廠取得處理物件，再呼叫 cal_work_hour( )——實際執行哪一個子類別的實作，由執行期物件決定（多型）。採樣器從頭到尾只認識抽象的 ZCL_PRD_ORDER。

METHOD cal_work_hour.
  SELECT SINGLE FROM aufk
    FIELDS auart
    WHERE aufnr = @iv_order_number          " AUFNR 是完整主鍵，SELECT SINGLE 結果唯一
    INTO @DATA(lv_auart).
  IF sy-subrc <> 0.
    rv_found = abap_false.              " 類別不彈訊息，交給呼叫端決定怎麼顯示
    RETURN.
  ENDIF.
  rv_found = abap_true.

  mo_prd_order = mo_factory_prd->get_order_instance( lv_auart ).   " 失敗會拋例外
  mo_prd_order->cal_work_hour( ).                                  " 多型：依子類別執行
ENDMETHOD.

" 抽象父類別與一個子類別（示意）
CLASS zcl_prd_order DEFINITION PUBLIC ABSTRACT CREATE PUBLIC.
  PUBLIC SECTION.
    METHODS cal_work_hour ABSTRACT.
ENDCLASS.

CLASS zcl_prd_order_pp01 DEFINITION PUBLIC
  INHERITING FROM zcl_prd_order CREATE PUBLIC.
  PUBLIC SECTION.
    METHODS cal_work_hour REDEFINITION.
ENDCLASS.

CLASS zcl_prd_order_pp01 IMPLEMENTATION.
  METHOD cal_work_hour.
    " 標準生產訂單的工時規則寫在這裡
  ENDMETHOD.
ENDCLASS.

與原範例的差異：

  • 原範例宣告了 iv_prod_id TYPE aufk-aufnr（在方法內用 iv_ 前綴宣告區域變數，而且完全沒用到）和 lv_class（也沒用到），改寫版刪除。
  • SELECT SINGLE auart FROM aufk INTO lv_prod_type WHERE aufnr = IV_ORDER_NUMBER 缺 @ 主機變數，改成 ABAP SQL 嚴格模式寫法。
  • 原範例拿到 mo_prd_order 後沒檢查是否為空就呼叫方法（見第 12 節），改寫版由工廠保證「要嘛回傳有效物件，要嘛拋例外」。
  • 「覆蓋」與「重載」的用語請依勘誤表第 3 條：ABAP 子類別重新實作父類別方法叫 Redefinition（覆寫，Overriding），ABAP 沒有同名不同參數的 Overloading（詳見 7-3 章）。
生產訂單號碼 AUFNR 有 ALPHA 轉換（內部 12 碼補前導零）。選擇畫面參照 AUFNR 時會自動轉換；若訂單號碼來自外部檔案或 IoT 平台，務必先 |{ lv_aufnr ALPHA = IN }| 再查詢，否則永遠查不到。

16. 從綜合實戰回看 Casper 的三條實務經驗

實務經驗本章對應的地方具體做法
