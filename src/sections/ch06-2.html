第 6-2 章 除錯的絕招（二）：顧問的除錯術——定位錯誤、找增強點、分析問題

業務（功能）顧問不必會寫 ABAP，但一定要會「看」ABAP：使用者丟來一個紅燈訊息，你要能在十分鐘內回答三個問題——是哪一行程式丟出來的？是配置／主資料問題還是程式問題？如果要改，該掛在哪個增強點？本章把 L35 素材裡散落的顧問除錯文章，整理成一套「訊息號 → 程式碼行 → 根因 → 標準或增強點 → 回報開發」的標準作業流程，並貫徹 Casper 的第三條實務經驗：先找標準，再想客製。

2. 顧問為什麼要會除錯：從訊息到根因的標準流程

情境：使用者在 ME22N 改採購單價格，跳出紅燈「4500000078 00010 由於已收貨，不允許修改價格」。你是 MM 顧問，第一反應應該是什麼？

素材 sap debugging for functional consultants 開宗明義：「只有在檢查配置（customizing）與主資料都無法判定根因時，才需要除錯。」除錯不是第一步，而是第三步。整理成流程：

  1. 讀訊息：點訊息看長文本與技術資訊（訊息類別＋編號＋類型），見第 3 節。
  2. 查 SAP 已知答案：訊息長文本的「程序（Procedure）」段落、SAP Note（用訊息號＋交易碼搜尋）。
  3. 定位程式碼：用第 4～7 節的武器找出丟訊息的那一行。
  4. 判斷類型：那一行在標準程式（SAPL*、LME* …）還是客製（Z*、ZX*、Y*）？前面讀了哪張表？見第 10 節。
  5. 決定處理方式：補配置／主資料 → 調整增強 → 最後才考慮改程式，見第 8、9 節。
  6. 回報：交給 ABAP 開發者時用第 15 節的範本，一次把資訊給齊。
Casper 實務經驗第 3 條：先找標準，再想客製。標準設定 → BAdI／Enhancement Spot → Enhancement Point → 修改標準，每往右一步升級成本高一個量級。顧問會除錯的最大價值，正是能在第 4 步就看出「這其實只是 T161P 少一筆配置」，而不是直接開需求單請開發者寫增強。

素材也點出顧問會除錯的三個好處：縮短問題分析時間、減少對 ABAP 團隊的過度依賴、讓工作量估算（effort estimation）更準確。寫功能規格書（FS）時，能指出「請在 BAdI ME_PROCESS_PO_CUST 的 CHECK 方法加檢查」的顧問，比只寫「系統要擋」的顧問值錢得多。

4. 武器一：SE91 Where-used 反查程式碼

情境：已拿到訊息號 MM899，想知道哪支程式會丟這個訊息。這是所有方法中不必重現錯誤的一招，適合先在測試機摸底。

操作步驟（依截圖整理，debug定位报错代码行 圖 1～10）：

  1. ME22N 修改 PO 4500000078 第 10 項淨價 → 出現紅燈，雙擊紅燈看訊息清單，再點長文本，記下訊息號 MM899。
  2. SE91：訊息類別輸入 MM，子物件選「訊息」，編號輸入 899。
  3. 按「使用位置清單（Where-Used List，Ctrl+Shift+F3）」，在「用於」勾選「程式」「類別」（必要時加 Web Dynpro 元件），執行（F8）。
  4. 結果：使用位置 訊息 MM 899（1 命中）——程式 ZXM06U43（Include ZXM06U43）。雙擊進入，看到第 28 行 MESSAGE E899(MM) WITH tekpo-ebeln tekpo-ebelp '由於已收貨，不允許修改價格'。
  5. 在該行設中斷點（Session Breakpoint），回到 ME22N 再改一次價格 → Debugger 停在這一行，確認就是它。

為什麼要最後再設中斷點確認？標準訊息常常被幾十個地方引用。七種武器一文以 DS017 為例，Where-used 列出 LDMC_DTLU02、LS38AU12、LSEDTATTRF10、MS38EF00…一大串。技巧是用訊息類型過濾：SE38 看到的 DS017 是綠勾（S 類型），所以只看 MESSAGE s017 的列，MESSAGE E017 直接略過；很快鎖定 Include LWBABAPF00 第 813 行，再用中斷點證實。（依截圖整理）

Where-used 靠的是靜態的交叉參照索引，所以下面這些寫法它找不到：

" (1) 找得到：訊息類別與編號寫死在 MESSAGE 敘述中
MESSAGE e899(mm) WITH ls_ekpo-ebeln ls_ekpo-ebelp.

" (2) 找不到：訊息類別／編號是變數（動態 MESSAGE）
DATA(lv_msgid) = CONV symsgid( 'MM' ).
DATA(lv_msgno) = CONV symsgno( '899' ).
MESSAGE ID lv_msgid TYPE 'E' NUMBER lv_msgno WITH ls_ekpo-ebeln.

" (3) 找不到：訊息被收進 BAPIRET2／應用日誌，而不是直接 MESSAGE
APPEND VALUE bapiret2( type       = 'E'
                       id         = 'MM'
                       number     = '899'
                       message_v1 = ls_ekpo-ebeln ) TO lt_return.

" (4) 找得到但會誤判：MESSAGE ... INTO 只是組字串，不一定會顯示給使用者
MESSAGE e899(mm) WITH ls_ekpo-ebeln INTO DATA(lv_text).
索引可能不完整：客製 Z 程式的 Where-used 索引在開發系統通常是最新的，但在 QAS／PRD 或剛升級的系統，標準程式的索引可能沒建（需 Basis 執行 SAPRSEUB／SAPRSEUC 建立）。Where-used 查不到不代表沒有，改用第 5～7 節的動態方法。

5. 武器二：Breakpoint at Message（最推薦的一招）

情境：錯誤可以重現、有訊息號。這是顧問最該練熟的方法，完全不需要看懂程式碼就能停在丟訊息的那一行。

操作步驟（依截圖整理，作为SAP顾问… 圖 1～4；debug定位报错代码行 圖 11～18）：

  1. 在出錯畫面（還沒按儲存前）的命令欄輸入 /h 按 Enter，狀態列顯示「除錯被啟動」。
  2. 再做一次會出錯的動作（改價格、按 Enter 或儲存）→ Debugger 開啟。
  3. 按 F9（或功能表「中斷點 → 中斷點位置 → 訊息處中斷點」／Breakpoints → Breakpoint at → Breakpoint at Message），在「建立中斷點」彈窗切到最右邊的「訊息」頁籤。
  4. ID 填訊息類別（例 ME），編號填 020，「型」可留空（代表任何類型都停）。
  5. 按 F8（繼續）→ Debugger 自動停在丟出該訊息的敘述。

ME020 實例的結論：Debugger 停在程式 SAPLMEPO、Include LMEPOF1V、FORM MEPO_ITEM_MAIN_CHECK_1 第 74 行。往上看三行就懂了：

*--- Kombination Bestellart/Bestelltyp/Positionstyp gegen T161P ---
SELECT SINGLE * FROM t161p WHERE bsart = ekko-bsart
                             AND bstyp = ekko-bstyp
                             AND pstyp = ekpo-pstyp.
IF sy-subrc NE 0.
  MESSAGE e020(me) WITH ekko-bsart ekko-bstyp msg_pstypl.   "<- 停在這裡
ENDIF.

（標準程式碼照截圖原樣抄錄，僅供閱讀；不是新程式的寫法範例。）程式讀配置表 T161P（採購憑證類型允許的項目類別），找不到「NB＋F＋U」的組合就報錯。所以根因是配置缺漏，到 SPRO「採購 → 採購訂單 → 定義憑證類型」底下的「允許的項目類別」補上即可，不需要任何開發。這正是第 2 節流程第 4 步的威力。

原文敘述的情境是「科目分配 A、項目類別 L」，但截圖實際是憑證類型 NB＋項目類別 U（庫存轉儲），原作者也註明「此處僅為示範」。本章以截圖為準。
停下來之後先看 Call Stack（ABAP 和畫面堆疊）。MM899 案例停住時，堆疊由下往上是：ME22N TRANSACTION → … → METHOD POST_DOCUMENT → METHOD SAVE → FUNCTION MEPO_DOC_CHECK → FORM PRUEFEN → FORM CUSTOMER_DATA_CHECK → FUNCTION EXIT_SAPMM06E_012。看到 EXIT_ 開頭的函數模組，就知道是 Customer Exit（第 8 節）。（依截圖整理）

6. 武器三：Breakpoint at Statement MESSAGE 與 Watchpoint SY-MSGNO

情境 A：錯誤沒有訊息號（例如彈窗文字是拼出來的、或你手上只有使用者的截圖）。改用「敘述中斷點」：

  1. /h 啟動 Debugger → 功能表「中斷點 → 中斷點位置 → 語句斷點處（Breakpoint at Statement，Shift+F5）」。
  2. 在「ABAP 命令」頁籤輸入 MESSAGE → 確認 → F8。
  3. Debugger 會停在每一個 MESSAGE 敘述。素材截圖中，先停在 FUNCTION AIP01_T001W_EXT_READ 的 MESSAGE e001 WITH i_werks RAISING plant_not_found，那不是我們要的 → 繼續 F8，直到停在與畫面錯誤文字一致的那一行（ZXM06U43 第 28 行）。（依截圖整理，debug定位报错代码行 圖 29～35）
上例中 AIP01 那一行雖然停了，但 MESSAGE … RAISING 在呼叫端有處理例外時不會顯示訊息，只會觸發例外。這就是為什麼 Breakpoint at Statement MESSAGE 會「停很多次」——很多 MESSAGE 根本沒到使用者眼前。同理可用 CALL FUNCTION、AUTHORITY-CHECK、COMMIT WORK、GET BADI 當關鍵字。

情境 B：想讓系統「自己停在」訊息被設定的瞬間。MESSAGE 執行時會填入 SY-MSGID／SY-MSGNO／SY-MSGTY／SY-MSGV1～4，所以對 SY-MSGNO 設 Watchpoint 也能定位：

  1. /h → 重現動作 → Debugger 中按「監視點（Watchpoint，Shift+F4）」。
  2. 「變數」輸入 SY-MSGNO，類型選「變數的觀察點」。
  3. 「自由條件輸入（Free Condition Entry）」填條件（見下方），確認 → F8。
  4. 狀態列出現「已到達監視點（SY-MSGNO）」，程式停在剛執行完的 MESSAGE 行。
* Watchpoint 條件範例（Free Condition Entry）
SY-MSGNO = '899'                          "只看編號
SY-MSGID = 'MM' AND SY-MSGNO = '899'      "類別＋編號同時成立（對 SY-MSGNO 設 WP，條件可引用其他欄位）
SY-MSGTY = 'E'                            "任何錯誤訊息（對 SY-MSGTY 設 WP）

* Breakpoint at Message 彈窗（F9 → 訊息頁籤）
ID   = MM
編號 = 899
型   = （空白 = 任何類型；填 E 則只停錯誤）
Watchpoint 會讓程式每執行一行都檢查條件，在大程式（例如 VA01、MIGO 過帳）上會明顯變慢。而且編號 899 在 MM 以外的類別也存在，只設 SY-MSGNO = '899' 可能誤停。能用 Breakpoint at Message 就先用它，Watchpoint 是備援。

7. 武器四～七：原始碼掃描、SAT、ST05、SAP Note

七種武器一文的後四招不靠 Debugger，而是「換個角度」找。其標題寫「七種武器」、內文卻說「六種方法」，實際是 6 種工具法＋第 7 種「搜尋引擎／問專家」。（依截圖整理）

武器四：原始碼靜態掃描。先用 SE93 查交易碼背後的程式與套件（SE38 → 程式 RSABAPPROGRAM、套件 SEDT），再用報表 RS_ABAP_SOURCE_SCAN（或交易 CODE_SCANNER）限定套件掃關鍵字：

RS_ABAP_SOURCE_SCAN 選擇畫面
  String searched for ....... MESSAGE S017          "純文字搜尋
  String is regular expression [X]                  "改用 Regex 時勾選
      例：MESSAGE\s+[EWSIAX]899\(MM\)              "任一類型的 899(MM)
  Package ................... SEDT                  "先限縮套件，否則全系統掃會跑很久
結果：LSEDTATTRF10 380 / LSEDTATTRIPP 239 / LWBABAPF00 813 → 第三筆即目標

CODE_SCANNER
  Packages .................. SEDT   [X] Packages Contained（含子套件）
  Search String 1 ........... MESSAGE S017

武器五：SAT 執行期分析。SAT 建立變式，Aggregation 一定要選 None（否則看不到完整呼叫樹）→ Transaction 填 SE38 → Execute → 重現錯誤 → 回 SAT 看結果，在 Call Hierarchy 用搜尋找「Message S017」即可跳到程式碼。SAT 的 Processing Blocks 樹狀圖也是學習複雜標準交易呼叫關係的利器。詳細用法見 6-3 章。

武器六：ST05 SQL Trace。推理：SE38 按 Display 時必然先查某張表，查不到才報錯，所以「查表的 SQL」與「丟訊息的程式行」一定很近。ST05 追蹤後，在結果中一眼看到 PROGDIR（存放所有 ABAP 程式名稱的表），SQL 為 SELECT WHERE "NAME" = 'ASDASDD' AND "STATE" = 'A'；按「Display ABAP Call Location」跳到 LWBABAPF00 第 774 行，往下捲到 813 行就是訊息。

原作者原話：「如果你在客戶生產系統開了 ST05 忘了關，你可能得跟你的工作說再見。」ST05 是系統層級開關（可限制使用者，但仍佔用追蹤檔），用完立刻關閉；正式機上使用前先取得 Basis 同意。

武器七：搜尋引擎、SAP Note、請教專家。用「訊息號＋交易碼」（例：ME020 ME21N、M7 021 MIGO）搜 SAP for Me（me.sap.com）的 Knowledge Base Article 與 Note，常常直接有答案。原作者提醒：這招最快，但也最容易錯過藉問題提升自己的機會。

訊息不是 MESSAGE 丟的怎麼辦？很多 BAPI 與新框架（MM 的 PO 物件、FI 的 BAPI、服務合約）把訊息收進 BAPIRET2 或應用日誌（SLG1）。素材 SAP 高效调试技巧 建議在函數模組 BALW_BAPIRETURN_GET2（組 BAPIRET2 的標準函數）或 BAL_LOG_MSG_ADD（寫應用日誌）設 Breakpoint at Function Module，觸發時看 Call Stack 最上層的呼叫者，就是產生訊息的地方。

8. 找增強點（一）：Customer Exit——從 ZX Include 反推 SMOD

情境：第 4 節找到的 ZXM06U43 是什麼？為什麼標準的 ME22N 會跑進 Z 程式？這是 Customer Exit（函數出口），詳細原理見 3-3 章。顧問要會的是從線索反推：

線索推得去哪裡看
Include 名稱 ZXM06U43屬於函數群 XM06 的客製 IncludeSE80 函數群 XM06
Call Stack 的 FUNCTION EXIT_SAPMM06E_012主程式 SAPMM06E 的第 012 號出口SE37
函數模組 → 增強增強 MM06E005（採購憑證的客戶欄位）表 MODSAP（MEMBER = EXIT_SAPMM06E_012）；SMOD
增強 → 專案哪個 CMOD 專案啟用了它、是否 ActiveCMOD；表 MODACT

主動找「這個交易有哪些 Customer Exit」的三種方法：

  • Debugger 設 Breakpoint at Statement CALL CUSTOMER-FUNCTION，走一遍交易，停到的每一處就是有機會掛程式的出口。
  • SE84 → 增強 → 客戶出口 → 增強，用套件（例：ME）搜尋。
  • 寫一支小報表：交易碼 → 程式（TSTC）→ 套件（TADIR）→ 該套件下的 SMOD 增強與 BAdI 定義。這是網路上流傳多年「找 User Exit 程式」的現代寫法：
REPORT zfind_enhancements.

PARAMETERS p_tcode TYPE tcode OBLIGATORY DEFAULT 'ME22N'.

START-OF-SELECTION.
  " 1) 交易碼 → 程式
  SELECT SINGLE pgmna FROM tstc
    WHERE tcode = @p_tcode
    INTO @DATA(lv_prog).
  IF sy-subrc <> 0.
    MESSAGE |交易碼 { p_tcode } 不存在| TYPE 'I'.
    RETURN.
  ENDIF.

  " 2) 程式 → 套件（函數群程式 SAPLxxxx 要用 FUGR 查）
  DATA(lv_obj_name) = COND sobj_name( WHEN lv_prog(4) = 'SAPL' THEN lv_prog+4
                                      ELSE lv_prog ).
  DATA(lv_object)   = COND trobjtype( WHEN lv_prog(4) = 'SAPL' THEN 'FUGR'
                                      ELSE 'PROG' ).
  SELECT SINGLE devclass FROM tadir
    WHERE pgmid = 'R3TR' AND object = @lv_object AND obj_name = @lv_obj_name
    INTO @DATA(lv_devclass).

  " 3) 套件底下的 Customer Exit（SMOD）與 BAdI 定義（SXSD）
  "    HANA 沒有預設排序：要穩定的清單就一定要 ORDER BY
  SELECT t~object, t~obj_name, m~modtext
    FROM tadir AS t
    LEFT OUTER JOIN modsapt AS m
      ON m~name = t~obj_name AND m~sprsl = @sy-langu
    WHERE t~pgmid    = 'R3TR'
      AND t~object   IN ( 'SMOD', 'SXSD', 'ENHS' )
      AND t~devclass = @lv_devclass
    ORDER BY t~object, t~obj_name
    INTO TABLE @DATA(lt_enh).

  cl_demo_output=>new(
    )->write( |{ p_tcode } → { lv_prog } → 套件 { lv_devclass }|
    )->write( lt_enh
    )->display( ).
這支報表只找「交易主程式所在套件」的增強，會漏掉放在其他套件的出口（例如 ME22N 的主程式 SAPLMEGUI 在套件 MEGUI，而 MM06E005 在套件 ME）。所以它只是起點，最終仍以 Debugger 實際走過的路徑為準。SXSD 是 Classic BAdI 定義、ENHS 是 Enhancement Spot（New BAdI 的容器）。

9. 找增強點（二）：BAdI 與 BTE——CL_EXITHANDLER、GET BADI、BF_FUNCTIONS_FIND

比 Customer Exit 更常見的是 BAdI（原理見 3-4 章）。要知道「這個交易在執行過程中呼叫了哪些 BAdI」，依 BAdI 種類用不同的中斷點：

要找的東西中斷點設在停下來看什麼
Classic BAdI方法 CL_EXITHANDLER=>GET_INSTANCE（SE24 開類別，在方法第一行設 Session Breakpoint；或 Debugger 的 Breakpoint at Method）參數 EXIT_NAME 的值就是 BAdI 定義名
New BAdI（Enhancement Spot）Breakpoint at Statement GET BADI（以及 CALL BADI）敘述中 BAdI 變數的型別（TYPE REF TO 的 BAdI 名）
Customer ExitBreakpoint at Statement CALL CUSTOMER-FUNCTION出口號碼（主程式名＋三碼）
BTE（FI 的 Business Transaction Event）函數模組 BF_FUNCTIONS_FIND（P/S 介面）、PC_FUNCTION_FIND（Process 介面）傳入的事件號碼，例如 00001025；對照 FIBF
隱含／顯式增強點Debugger「中斷點 → 在增強上」或 SE80 看 Enhancement ImplementationENHANCEMENT … ENDENHANCEMENT 區塊
 
" 你在標準程式裡會看到的兩種 BAdI 呼叫方式（知道長相，才知道中斷點要設在哪）

" (A) Classic BAdI：經由 CL_EXITHANDLER 取實例
DATA lo_badi_classic TYPE REF TO if_ex_me_process_po_cust.
cl_exithandler=>get_instance(
  EXPORTING exit_name = 'ME_PROCESS_PO_CUST'   "←在 GET_INSTANCE 看到的就是這個
  CHANGING  instance  = lo_badi_classic ).

" (B) New BAdI（Kernel BAdI）：GET BADI / CALL BADI 敘述，不經過 CL_EXITHANDLER
DATA lo_badi TYPE REF TO badi_sd_sales_item.    "示意：TYPE REF TO 後面就是 BAdI 名稱
TRY.
    GET BADI lo_badi.                            "←Breakpoint at Statement GET BADI
    CALL BADI lo_badi->some_method EXPORTING is_vbap = ls_vbap.
  CATCH cx_badi_not_implemented.
    " 沒有啟用的實作 → 標準行為
ENDTRY.
常見誤解：網路上很多教學只教「在 CL_EXITHANDLER=>GET_INSTANCE 設中斷點找 BAdI」。那只抓得到 Classic BAdI；S/4HANA 的新功能大量使用 New BAdI（GET BADI 由 Kernel 直接處理，不經過 CL_EXITHANDLER），只設前者會以為「這個交易沒有 BAdI」。兩個都要設。另外，SAP 已將 ME_PROCESS_PO_CUST 等 Classic BAdI 移入 Enhancement Spot 做相容遷移，實作時以 SE19 看到的類型為準。

BTE 的顧問視角：FI 的過帳、付款、催收常用 BTE。FIBF → 環境 → 資訊系統（P/S）可列出所有事件與範例函數（例：00001025 過帳前檢查、00001030 更新憑證），客製實作則是 Z 函數模組掛在「產品」下並啟用。標準程式中呼叫點長這樣：CALL FUNCTION 'OPEN_FI_PERFORM_00001025_E'，其內部用 BF_FUNCTIONS_FIND 找出啟用中的實作，所以在 BF_FUNCTIONS_FIND 設中斷點可以一次看到交易經過的所有 BTE。

找到出口後的決策（Casper 經驗第 3 條）：① 能不能用標準配置達成（訊息控制、欄位狀態、替代／驗證 GGB0／GGB1）？② 不行才用 BAdI／Enhancement Spot；③ 再不行才用隱含增強點；④ 修改標準（需 Access Key、升級時要 SPAU）是最後手段。每往右一步，測試與升級成本都高一個量級。

10. 配置問題還是程式問題？判斷流程與兩個對照案例

停在丟訊息的那一行後，顧問要回答的核心問題就是「這是誰的問題」。判斷準則：

觀察傾向下一步
程式是標準（SAPL*、SAPM*、L*），訊息前面剛讀了 T 開頭配置表（T161P、T001W、T156…）且 sy-subrc ≠ 0配置缺漏用 SE16 看該表、找對應 SPRO 路徑（SM30 表名 → 「Where-used in IMG」或 SPRO 的「附加資訊 → 顯示關鍵」）
標準程式，前面讀的是主資料表（MARA、MARC、LFA1、KNA1、A0xx 條件表）主資料問題用對應的交易（MM03、BP、VK13）確認資料
程式名是 Z*、Y*、ZX*、或 Call Stack 中有 EXIT_、BAdI 實作類別 ZCL_*客製邏輯找規格書與負責的開發者，見第 15 節
標準程式，邏輯看起來不合理、在 SAP Note 能搜到相同訊息＋程式名標準程式錯誤套 Note（SNOTE）或開 SAP Incident
訊息與權限有關（「沒有權限…」、訊息類別 00、M7 的權限訊息）權限立刻 SU53，見第 12 節

對照案例：

  • ME020（配置）：停在標準 LMEPOF1V，前一行 SELECT T161P 失敗 → 補「憑證類型允許的項目類別」配置。零開發。
  • MM899（客製）：停在 ZXM06U43，是某位開發者在 Customer Exit 寫的「已收貨不准改價」檢查。要不要放寬？是業務規則問題，找需求提出者與開發者討論。

ZXM06U43 原始碼（截圖）本身也值得顧問抓出幾個問題，交給開發者時可一併建議：

  • 用 SELECT … ENDSELECT 迴圈讀 EKBE 累加收貨數量（禁用寫法），且在 LOOP AT tekpo 裡逐筆 SELECT。
  • 客製檢查借用 SAP 標準訊息類別 MM 的 899 號，並把中文訊息文字塞在 WITH 參數裡——這會讓人以為是標準訊息，也讓 SE91 Where-used 的結果混淆。應建立自己的訊息類別（例 ZMM）。
  • 依 BEWTP = 'E'（收貨）並用 SHKZG 判斷借貸方累加，邏輯正確，但未考慮退貨沖銷後數量為 0 的情形是否仍要擋，需與業務確認。

改寫成 S/4HANA 寫法的參考如下（Customer Exit 的介面參數 TEKPO 為標準結構表；新專案建議改用 BAdI ME_PROCESS_PO_CUST 的 CHECK 方法）：

" Include ZXM06U43（EXIT_SAPMM06E_012）——現代寫法示意
" 規則：已有收貨數量的項目，不允許變更淨價
LOOP AT tekpo ASSIGNING FIELD-SYMBOL(<ls_item>).

  SELECT SINGLE netpr FROM ekpo
    WHERE ebeln = @<ls_item>-ebeln
      AND ebelp = @<ls_item>-ebelp
    INTO @DATA(lv_db_netpr).
  IF sy-subrc <> 0 OR <ls_item>-netpr = lv_db_netpr.
    CONTINUE.                                  "新項目或價格沒改，不檢查
  ENDIF.

  " 以 GROUP BY 彙總取代原本的逐筆 SELECT 迴圈：收貨（BEWTP = 'E'）借方 S 加、貸方 H 減
  SELECT shkzg, SUM( menge ) AS qty
    FROM ekbe
    WHERE ebeln = @<ls_item>-ebeln
      AND ebelp = @<ls_item>-ebelp
      AND bewtp = 'E'
    GROUP BY shkzg
    INTO TABLE @DATA(lt_gr).

  DATA(lv_gr_qty) = REDUCE menge_d( INIT q = CONV menge_d( 0 )
                                    FOR ls_gr IN lt_gr
                                    NEXT q = COND #( WHEN ls_gr-shkzg = 'S' THEN q + ls_gr-qty
                                                     ELSE q - ls_gr-qty ) ).

  IF lv_gr_qty <> 0.
    " 使用自己的訊息類別 ZMM，而非借用標準 MM 899
    MESSAGE e001(zmm) WITH <ls_item>-ebeln <ls_item>-ebelp.
  ENDIF.
ENDLOOP.

11. 看懂 ST22 短傾印：顧問也讀得懂的七個欄位

情境：使用者說「畫面突然跳出一大片英文就結束了」。那是 Runtime Error（短傾印），到 ST22 依日期、使用者篩選即可找到。顧問不必看懂每一行，但要會讀這幾段：

段落內容顧問要抓的重點
Short Text / Category一句話摘要與分類（ABAP Programming Error、Resource Shortage、Installation Error…）分類若是 Resource Shortage，多半找 Basis 而不是開發者
Runtime Error／Exception錯誤名稱與例外類別（如 CONVT_NO_NUMBER／CX_SY_CONVERSION_NO_NUMBER）用它＋程式名搜 SAP Note
What happened? / What can you do?白話說明是否提示「保存（Keep）此傾印」
Error analysis技術原因，常含出錯的值（例：'12,5' 不能轉成數字）這個值通常來自使用者輸入或上傳檔案——資料問題
How to correct the errorSAP 建議與 Note 搜尋關鍵字直接複製給開發者
Information on where terminated / Source Code Extract程式、Include、行號，並以「>>>>>」標示出錯行程式是 Z 還是標準？
Active Calls/Events、Chosen VariablesCall Stack 與當下變數值從下往上看，找第一個 Z 物件
常見 Runtime Error典型原因誰處理
MESSAGE_TYPE_X程式主動以 X 類型終止（一致性檢查失敗），看 Error analysis 裡的訊息號先查 Note，常是資料不一致
CONVT_NO_NUMBER、CONVT_OVERFLOW文字轉數字失敗（上傳檔格式、千分位、小數點）資料／開發者
GETWA_NOT_ASSIGNED、OBJECTS_OBJREF_NOT_ASSIGNED欄位符號或物件參考未指派就使用開發者
SAPSQL_ARRAY_INSERT_DUPREC、DBSQL_DUPLICATE_KEY_ERROR重複鍵寫入資料庫（常見於號碼範圍狀態錯誤）顧問先查 SNRO／號碼範圍
TIME_OUT前景執行超過 rdisp/max_wprun_time改背景作業或效能調校（6-3 章）
TSV_TNEW_PAGE_ALLOC_FAILED內表記憶體不足（選擇條件太寬）縮小條件；開發者改分批
UNCAUGHT_EXCEPTION類別型例外沒被 CATCH開發者

開發者修正 CONVT_NO_NUMBER 的正確方式是捕捉類別型例外並給使用者看得懂的訊息，而不是讓程式短傾印：

" 上傳檔的金額欄位 → 數字；錯了就回報第幾行，不要 DUMP
LOOP AT lt_upload ASSIGNING FIELD-SYMBOL(<ls_line>).
  DATA(lv_row) = sy-tabix.
  TRY.
      DATA(lv_amount) = CONV wrbtr( replace( val  = <ls_line>-amount_txt
                                              sub  = ','
                                              with = ''
                                              occ  = 0 ) ).
    CATCH cx_sy_conversion_no_number cx_sy_conversion_overflow INTO DATA(lx_conv).
      APPEND VALUE bapiret2( type    = 'E'
                             message = |第 { lv_row } 行金額「{ <ls_line>-amount_txt }」格式錯誤：{ lx_conv->get_text( ) }| )
        TO lt_messages.
      CONTINUE.
  ENDTRY.
  " ... 後續處理 lv_amount
ENDLOOP.
ST22 的傾印預設只保留約 14 天（依系統設定），重要的傾印要按「保存（Keep）」並截下 Header 與 Source Code Extract。回報時「傾印的日期時間＋使用者＋Runtime Error 名稱」三項就能讓開發者在 ST22 直接找到同一筆。

12. SU53 權限問題：先排除權限，再懷疑程式

情境：A 使用者可以做、B 使用者不行；或訊息是「您沒有 … 的權限」。這類問題九成跟程式無關，不要急著 /h。

  1. 請使用者在出錯後立刻（同一個 Session、不要再做其他動作）執行 /nSU53，截圖給你。畫面會列出最後一次失敗的權限檢查：權限物件（例 M_BEST_BSA）、欄位（ACTVT、BSART）、檢查值與使用者目前擁有的值。
  2. 較新版本的 SU53 可由管理者「顯示其他使用者的權限檢查」，不必叫使用者操作。
  3. SU53 只記得最後一次失敗，若程式先失敗一次又改走別的路，可能誤導。需要完整記錄時用 STAUTHTRACE（系統追蹤，只看權限）或 ST01，對該使用者開追蹤後重現。
  4. 把結果交給權限管理員在 PFCG 調整角色；標準交易的預設檢查值維護在 SU24。

客製程式也應用 AUTHORITY-CHECK 做權限檢查，且失敗時要讓 SU53 查得到——也就是不要自己寫死使用者名單：

" 客製報表：依採購組織檢查顯示權限（失敗的檢查會記錄在 SU53）
AUTHORITY-CHECK OBJECT 'M_BEST_EKO'
  ID 'EKORG' FIELD p_ekorg
  ID 'ACTVT' FIELD '03'.
IF sy-subrc <> 0.
  MESSAGE e002(zmm) WITH p_ekorg.   "ZMM 002：您沒有採購組織 &1 的顯示權限
ENDIF.

" 反例（不要這樣做）：寫死使用者，SU53 看不到、權限管理員也管不到
" IF sy-uname = 'USER01' OR sy-uname = 'USER02'. ... ENDIF.
在 Debugger 中用 Breakpoint at Statement AUTHORITY-CHECK 可以看到程式實際檢查了哪個物件、哪個值，適合 SU53 資訊不足時。但這是開發者或資深顧問的工具，一般仍以 SU53／STAUTHTRACE 為主。

13. 報表數字不對：順查法與倒查法；SmartForms 除錯

情境：客製 ALV 某一欄是空的或金額不對。素材 ABAP问题分析和排除经验之谈 提出兩種查法：

順查法倒查法（推薦）
做法找到輸出內表與欄位後，從程式開頭一路 Debug 下來，看值從哪來從輸出處往回推：找離輸出最近、與該欄位有關的賦值，一層層往上追到資料來源表
優點走完一遍，整支程式邏輯都懂了省大量時間，迅速鎖定問題
缺點程式大時非常耗時對整體邏輯不一定清楚
適合程式小、邏輯單純的自建程式所有自建程式

原文範例（依截圖整理）：ALV 內表 GS_ALV 的 BELNR 欄沒值 → 往上找到 GS_ALV 的值是從 GS_FYBX 搬過來 → GS_FYBX 來自內表 GT_FYBX 的迴圈 → GT_FYBX 直接 SELECT 自建表 ZFIT_FYBX → 用 SE16 看 ZFIT_FYBX 原始資料就沒有 BELNR，所以問題在「寫入 ZFIT_FYBX 的那支程式」，不是這支報表。

數字「時對時錯」要先想到排序（Casper 經驗第 1 條）。倒查到 SELECT SINGLE、READ TABLE … INDEX 1、UP TO 1 ROWS 卻沒有 ORDER BY 時，在 HANA 上每次取到的「第一筆」可能不同。成本評價同時有 item category H 與 cost component E 兩種角度，未排序就一下抓 H、一下抓 E，結果不穩定；該案最後固定抓 H。另外，若選擇條件用區間（BT）比對號碼，也要懷疑字典序與前導零造成的漏抓（經驗第 2 條：列舉優於區間）。

SmartForms 除錯（素材 SAP顾问的技能 與 经验之谈；SmartForms 開發見 4-3 章）：

  1. SMARTFORMS 顯示表單，在左側樹找到要查的「程式行（Program Lines）」節點，複製其中一行程式碼備用。
  2. 功能表「環境 → 函數模組名稱」取得產生的函數模組（/1BCDWB/SF000000xx，每個系統編號不同）。
  3. SE37 開該函數模組 → 跳到主程式 → 用「尋找」搜剛才複製的程式行 → 設 Session Breakpoint。
  4. 重新執行列印（例 ME9F、VF31，或輸出預覽）→ 停在表單邏輯中。
  5. 欄位沒印出來時用倒查法：值來自表單介面（驅動程式傳入）還是表單內的全域定義／程式行？前者去查驅動程式，後者在表單內查。
" 驅動程式取得 SmartForms 產生的函數模組名稱（名稱每個系統不同，不可寫死）
DATA lv_fm_name TYPE rs38l_fnam.

CALL FUNCTION 'SSF_FUNCTION_MODULE_NAME'
  EXPORTING
    formname           = 'ZMM_PO_FORM'
  IMPORTING

14. 危險操作：用 Debugger 改 SE16 資料、跳過程式碼

素材 利用ABAP调试模式修改SE16里数据库表的内容 示範了一招流傳甚廣、但絕不應該在正式環境使用的技巧。本節照實說明，目的是讓顧問認得出這種操作的痕跡、理解它的風險。

素材的做法（依截圖整理）：表 COMM_PRODUCT（CRM 產品主檔）在 SE11 的「Data Browser/Table View Maint.」設為「Display/Maintenance Allowed with Restrictions」，SE16 只能顯示不能改。

  1. SE16 進到該筆記錄的明細畫面，命令欄輸入 /h。
  2. 按 Enter，Debugger 停在程式 SAPLSETB、Include LSETBF01、FORM SET_STATUS_VAL 第 34 行 if code = 'SHOW'。
  3. 在變數區把 CODE 的值從 SHOW 改成 EDIT，按修改圖示。
  4. F8 繼續，明細畫面變成「Table COMM_PRODUCT Change」，欄位可編輯、可儲存。

同類手法還有：在 Debugger 把 SY-SUBRC 從 4 改成 0 繞過權限或檢查、用 Goto Statement（Shift+F12，5-4 章 §5）跳過檢查程式碼、跳過 COMMIT WORK 或更新任務。素材 SAP顾问的技能 把 Goto Statement 當成「繞過程式碼區塊」的用例介紹，同樣只能在沙箱中理解程式流程時使用。

正式環境一律禁止。
  • 權限：在 Debugger 修改變數值需要權限物件 S_DEVELOP，OBJTYPE = DEBUG、ACTVT = 02（只看變數是 03）。正式機的使用者本來就不應持有 DEBUG 02；持有的帳號（含 Firefighter／緊急帳號）必須受控並事後審查。
  • 留下紀錄：在 Debugger 修改變數值、跳行（Goto Statement）都會寫入 系統日誌 SM21（例如訊息「Field content changed」一類的 Debugger 事件，含使用者、時間、程式、變數），稽核人員一查就知道。
  • 稽核風險：直接改資料庫表繞過了應用程式的所有檢查與關聯表更新（例如 COMM_PRODUCT 還有對應的文字、設定表、變更文件、CDS／搜尋索引），也不會產生變更文件（CDHDR／CDPOS）。這在 SOX／ITGC 稽核中屬於重大缺失，可能造成資料不一致且無法追溯。
  • SE16N 的 &SAP_EDIT：早年另一個常見手法是在 SE16N 輸入 &SAP_EDIT 進入編輯模式；SAP 已透過 Note 1420281 關閉此功能，現行版本若確有編輯需求，須經專屬權限與核准流程（並有紀錄），不應視為日常工具。
正規替代做法：① 用業務交易本身修正（產品主檔用 COMMPR01、物料用 MM02、採購單用 ME22N）；② 大量修正用 BAPI／標準批次工具（LSMW、Migration Cockpit、Mass Change）並經傳輸的程式執行；③ SAP 提供修正報表的情況（很多 Note 附有 Z 修正程式）照 Note 執行；④ 真的只能改表時，寫一支經測試、經傳輸、有核准單的一次性修正程式，並在程式內記錄變更前後值。

練習與自我檢核

  1. 使用者回報 ME21N 出現 ME020。請寫出不看程式碼、只用 Debugger 就能定位的步驟。
    參考答案要點：在出錯畫面輸入 /h → 再按 Enter／儲存 → Debugger 中 F9 → 「訊息」頁籤 ID=ME、編號=020 → F8；停在 LMEPOF1V 的 MEPO_ITEM_MAIN_CHECK_1，前一行 SELECT T161P 失敗 → 配置缺漏。
  2. SE91 Where-used 找不到某訊息，是否代表系統沒有程式丟它？
    參考答案要點：否。可能是動態 MESSAGE ID … NUMBER、訊息收進 BAPIRET2／應用日誌、或 Where-used 索引未建立。改用 Breakpoint at Message、Watchpoint SY-MSGNO、在 BALW_BAPIRETURN_GET2／BAL_LOG_MSG_ADD 設中斷點，或 RS_ABAP_SOURCE_SCAN。
  3. DS017 在 Where-used 有十幾筆結果，如何快速篩選？
    參考答案要點：看畫面燈號判斷類型（綠勾＝S），只看 MESSAGE s017 的列；鎖定後設中斷點重現證實。
  4. 只在 CL_EXITHANDLER=>GET_INSTANCE 設中斷點，為什麼可能漏掉 BAdI？
    參考答案要點：它只攔得到 Classic BAdI；New BAdI 用 GET BADI 由 Kernel 處理，要另設 Breakpoint at Statement GET BADI。
  5. Call Stack 看到 FUNCTION EXIT_SAPMM06E_012，接下來查什麼？
    參考答案要點：主程式 SAPMM06E 的第 012 號 Customer Exit；由表 MODSAP 或 SMOD 查到增強 MM06E005；CMOD 查專案是否啟用；程式碼在 Include ZXM06U43。
  6. 判斷題：停在標準程式、前一行讀 T 開頭表失敗 → 應先開 SAP Incident。
    參考答案要點：錯。這通常是配置缺漏，先補 SPRO 配置；只有在 SAP Note 有相同症狀或邏輯明顯錯誤時才開 Incident。
  7. ST22 顯示 CONVT_NO_NUMBER，Error analysis 寫「'1,250.00' cannot be interpreted as a number」，誰該處理？
    參考答案要點：直接原因是上傳資料格式（千分位），但程式應該用 TRY … CATCH cx_sy_conversion_no_number 給友善訊息，兩邊都要處理。
  8. 使用者說「同事可以存檔，我不行」，第一步做什麼？
    參考答案要點：請他出錯後立刻執行 /nSU53 截圖，或用 STAUTHTRACE 追蹤；確認權限物件與欄位值後交給 PFCG 角色管理員。
  9. 客製報表的成本欄位每次執行結果不同，倒查到 SELECT … UP TO 1 ROWS，你的判斷？
    參考答案要點：HANA 沒有預設排序，缺 ORDER BY 導致「第一筆」不固定（H／E 兩種角度成本構成不同）；要明確排序或指定條件（該案固定抓 H）。
  10. 主管要你在 PRD 用 Debugger 把 SE16 的 CODE 改成 EDIT 修一筆資料，你怎麼回應？
    參考答案要點：拒絕並說明：需 S_DEVELOP DEBUG 02、會記入 SM21、繞過檢查且無變更文件、屬稽核重大缺失；改用業務交易、BAPI、SAP Note 修正報表或經核准傳輸的一次性修正程式。
  11. 請列出本章的「七種武器」並各用一句話說明適用時機。
    參考答案要點：Where-used（有訊息號、不必重現）；Watchpoint SY-MSGNO（備援、會變慢）；Breakpoint at Message／Statement MESSAGE（可重現，最推薦／無訊息號時）；RS_ABAP_SOURCE_SCAN／CODE_SCANNER（知道套件、靜態掃）；SAT（Aggregation=None 看完整呼叫樹）；ST05（從查表位置推訊息位置，PRD 用完要關）；搜尋引擎／SAP Note（最快但少了學習）。
