2. IDoc 介面全景：EDI、ALE 與三種資料流

IDoc（Intermediate Document）介面是 SAP 用來在兩個不同系統之間交換商業資料的標準機制，由兩部分組成：資料結構（IDoc 本身）與處理邏輯（出站、入站、狀態處理）。雙方系統都必須認得 IDoc 格式；IDoc 可以不經由應用程式直接進入 SAP Business Workflow 處理。需要 IDoc 介面的三種情境：

  • EDI（Electronic Data Interchange）：與客戶、供應商交換訂單、出貨通知、發票等電子單據，中間通常隔一個 EDI 子系統（負責 IDoc ↔ EDIFACT／ANSI X12 轉換）。
  • ALE（Application Link Enabling）：SAP 與 SAP 之間分散式資料交換，典型是主資料同步（物料 MATMAS、客戶 DEBMAS、供應商 CREMAS）。
  • 其他應用系統：PC 程式、外部 Workflow、MES、WMS 等任何能讀寫 IDoc 格式的系統。

IDoc 介面支援三種資料流：

資料流方向傳送內容
出站處理（Outbound）SAP → 接收系統控制記錄＋資料記錄
入站處理（Inbound）上游系統 → SAP控制記錄＋資料記錄
狀態處理（Status）接收系統 → SAP，回報出站 IDoc 的處理狀態狀態記錄（例外：用 IDoc 類型 SYSTAT01 回報時，是一張正常的入站 IDoc）

出錯時由 Workflow 工作項目（work item）啟動例外處理，送進「被允許的處理人員（permitted agent）」的整合收件匣——這是 1999 年的設計，也是 BIT750 說「錯誤都丟給 IT 看」的由來（第 16 節）。

面試口訣：ALE 是「業務分散的方法論」，IDoc 是「信封加內容的資料格式」，tRFC 是「ALE 預設的傳輸管道」。ALE 不一定要用 IDoc（也可以 BAPI），IDoc 也不一定走 ALE（EDI 走檔案埠）。RFC 各型態的差別見 4-1 章第 3 節與 5-12 章 BC415。

3. IDoc 結構：控制記錄、資料記錄、狀態記錄

每張 IDoc 由三種記錄類型（record type）組成，資料庫中各存一張表；對外（送給子系統）時則用三個「外部結構」：

記錄類型資料庫表外部結構（4.x 起）內容與重要欄位
控制記錄（Control Record）EDIDCEDI_DC40「信封／信頭」：DOCNUM（IDoc 號碼）、DIRECT（1＝出站、2＝入站）、MESTYP（訊息類型）、IDOCTP（基本類型）、CIMTYP（擴充）、SNDPOR/SNDPRT/SNDPRN（傳送埠、夥伴類型、夥伴號碼）、RCVPOR/RCVPRT/RCVPRN、STATUS（目前最後狀態）、CREDAT/CRETIM、MANDT
資料記錄（Data Record）EDID4（結構 EDIDD）EDI_DD40SEGNAM（區段名）、SEGNUM（區段序號）、PSGNUM（父區段序號）、HLEVEL（階層）、SDATA（區段內容，最長 1000 bytes）
狀態記錄（Status Record）EDIDSEDI_DS40DOCNUM、STATUS、COUNTR（序號）、LOGDAT/LOGTIM、STATXT、STAMID/STAMNO/STAPA1～4（訊息）、SEGNUM／SEGFLD（出錯的區段與欄位）、REPID/ROUTID

三個重點觀念：

  • 控制記錄的 STATUS 永遠是最新狀態。所以監控程式（統計、清單）為了效能只讀 EDIDC；只有「評估歷史」「測試 IDoc」這類要看全部狀態的程式才讀 EDIDS，較慢。
  • 狀態記錄不是 IDoc 的一部分，它不隨 IDoc 傳送，而是另外由「狀態處理」送回。
  • 區段的父子關係靠 PSGNUM 與 HLEVEL 實現。例如 E1EDPT1（明細文字）在 EXPINV01 是 E1EDP01 的子區段，在 DESADV01 卻是 E1EDP07 的子區段——同一個區段可以在不同 IDoc 類型有不同父親。

如果 IDoc 類型定義某區段為必要區段，但實際產生的 IDoc 沒有填，語法檢查會報錯，並把缺漏區段記在狀態記錄的 SEGNUM 欄位。語法檢查的開關在夥伴設定檔（出站、入站分開設定）。

版本與發布（Release）規則：每個版本只能有一個版本物件；後繼者必須包含前任的全部內容再「至少多一樣」（區段多一個欄位、基本類型多一個區段）。要建後繼者，前任必須先發布；發布後就不能再改，只有在尚無後繼者時才能取消發布。發布順序：先區段，再基本類型／擴充。

客戶擴充 vs 客戶自建：擴充過的基本類型在升級後仍被支援（SAP 保證基本類型不會少區段，所以向上相容）；自建的基本類型則不受升級影響，但可能要自己維護。

講義的區段設計準則（到今天仍適用）：

  • 不要重新發明輪子：先找既有區段，參考 EDIFACT／ANSI X12；代碼值用 ISO（國家 ISO 3166、幣別 ISO 4217、單位 ISO 31）。
  • 邏輯上相關的欄位放同一區段、相關區段組成區段群組；必要欄位放區段前面；儘量避免限定詞（qualifier）——它難以文件化、也讓區段失去通用性。
  • 區段所有欄位總長上限 1000 字元；區段越大，有效資料對管理資料的比率越好，並預留未來擴充空間。
  • IDoc 類型要扁平（不要太多代），必要區段往前放；一個區段在一個 IDoc 類型中只能出現一次定義（但可以設定重複次數）。
  • 別忘了對應的函數模組：入站模組必須能處理所有允許的區段，出站模組必須依正確順序與階層產生區段，否則語法檢查會報錯。

欄位格式規則：區段欄位只放英數字元（用字元型資料元素）、不分大小寫、靠左對齊；日期 YYYYMMDD（1996/2/28 → 19960228）、時間 HHMMSS（下午 8:35 → 203500）；定點數只用小數點、無千分位，負號放在數值後面（-2,097,152.64 → 2097152.64-）；浮點數一律帶指數（-23.4 → -2.34E+01）。

WE31 的鐵律：區段的「匯出長度（export length）」不要改——資料對外以該長度的字元欄位傳送，內部卻依資料元素型別存放，長度不一致會截掉資料。永遠用 WE31 建區段，不要直接在 SE11 建同名結構。區段啟用時系統會同時啟用 DDIC 中對應的結構（Z1xxx 與 Z2xxx 版本結構）。

5. 埠（Port）與 RFC 目的地：WE21

埠是 IDoc 通訊的根本前提：每個外部系統至少要有一個埠。埠定義「用什麼技術、送到哪裡」，並透過埠版本告訴 SAP 對方的版本（版本 1＝Release 2.1/2.2、版本 2＝3.0/3.1 與 R/2、版本 3＝4.x，預設值）。

埠類型（WE21）適用場景重點
交易式 RFC（tRFC）ALE 分散情境（SAP 對 SAP）指向 SM59 的 RFC 目的地（通常型別 3）；傳送狀態在 SM58；夥伴類型應為 LS（邏輯系統）
File大多數 EDI 子系統作業系統層的目錄與檔名；建議用 EDI_PATH_CREATE_CLIENT_DOCNUM（或邏輯目錄版 EDI_LPATH_CREATE_CLIENT_DOCNUM）產生唯一檔名，避免未處理的檔案被覆蓋；可設定出站後觸發接收系統
XML（檔案）電子商務IDoc 以 XML 檔輸出，標籤名稱對應記錄類型與區段（例如 <EDIDC_40-MESTYP>）；可選擇是否附 DTD；特殊字元（ä、ö、ü）可轉換但長度會變
ABAP 程式介面（ABAP-PI）自己寫傳送邏輯出站：填你寫的函數模組名，範本是 OWN_FUNCTION（成功寫狀態 18、失敗寫 20）；入站：你的模組必須呼叫 IDOC_INBOUND_ASYNCHRONOUS
Internet寄到 e-mail 位址透過 SAPconnect，IDoc 為 MIME 附件；入站由 SX_OBJECT_RECEIVE 接收
CPI-CR/2 系統已淘汰；入站需排程 RSEINB10

入站不需要在夥伴設定檔指定埠，但系統必須「認得」上游系統的埠（埠定義提供上游系統的唯一識別），其技術參數通常會被上游覆蓋。

S/4HANA 現況：CPI-C／R/2、Internet 埠已無實務意義。現在常見的是 tRFC 埠（SAP 對 SAP、或透過 SAP Integration Suite／PI 的 IDoc adapter）與 XML HTTP 埠（把 IDoc 以 XML 經 HTTP 送到 Integration Suite 或其他中介軟體，需 SM59 型別 G 目的地）。舊版相容用的「長名稱轉換表」與 DOCTYP 對照，只有在跟極舊系統或 EDI 子系統溝通時才會碰到（舊版限制：訊息類型 6 碼、IDoc 類型 8 碼、區段 7 碼）。

6. 夥伴設定檔：WE20

夥伴設定檔（Partner Profile）決定「跟誰、交換什麼訊息、走哪個埠、用哪個 Process Code 處理、出錯通知誰」。它由四張表構成：

8. 出站處理：訊息控制（MC）、直接出站與 ALE 分散模型

10. 入站處理：從接收到過帳

入站分兩步，這是 IDoc 可靠性的關鍵設計：第一步先把 IDoc「收下」存進資料庫（只要認得上游系統的埠就接受），讓外部系統能快速、可靠地完成傳送；第二步才獨立地轉成應用單據。

  1. 依埠類型由不同模組接收：tRFC 埠 → IDOC_INBOUND_ASYNCHRONOUS（4.0 長名稱，參數 IDOC_CONTROL_REC_40／IDOC_DATA_REC_40，結構 EDI_DC40／EDI_DD40；4.0 前是 INBOUND_IDOC_PROCESS）；File 埠 → EDI_DATA_INCOMING；同步 RFC → IDOC_INBOUND_SINGLE（舊版 IDOC_INBOUND_SYNCHRONOUS）；Internet → SX_OBJECT_RECEIVE。
  2. IDOC_INBOUND_WRITE_TO_DB 寫入資料庫，並依 Process Code 判斷是否走 ALE 服務。
  3. IDOC_START_INBOUND 依入站 Process Code 啟動函數模組（直接路徑）或 Workflow（間接路徑，單步或多步工作）。除了 tRFC 埠以外，都會觸發 Workflow 事件，啟動標準工作 TS30200090（所以要在 IMG 啟用一次「IDoc 入站的事件接收者連結」）。

講義例子：供應商收到 ORDERS01 採購單，Process Code ORDE 指向 IDOC_INPUT_ORDERS，把 IDoc 轉成銷售訂單（直接路徑）。只在 Basis 層處理的 TXTRAW02（文字郵件，單步工作 TS30000008，收件者取自區段 E1TXTAD）則只能走 Workflow。

入站函數模組要讓 ALE 認得，必須三處註冊（這也是 AIF 情境 2/3 要改的三個地方，見第 19 節）：

步驟TCODE內容
① 函數模組屬性BD51輸入類型：0＝大量處理、1＝逐張處理、2＝逐張且在交易中鎖 IDoc；是否允許對話（Dialog possible）
② 函數模組 ↔ 訊息類型／IDoc 類型WE57模組（類型 F）、基本類型、擴充、訊息類型、方向 2、BOR 物件類型（例如 BUS2032 銷售訂單）；此即「ALE 註冊」，存在 TBD52 等表
③ 入站 Process CodeWE42選「Processing with ALE」＋「Processing by function module」，指定函數模組、最大嘗試次數、IDoc 物件類型與事件 inputErrorOccurred／inputFinished；再掛到邏輯訊息
④ 夥伴設定檔WE20入站參數填這個 Process Code，選「立即處理」或「由背景程式觸發」

選「由背景程式觸發」時，IDoc 會停在狀態 64，由 RBDAPP01（BD20）排程處理——大量主資料或需要序列化時常用，可避免尖峰時段壓垮系統。

講義提醒：入站測試時，若函數模組內用 CALL TRANSACTION，必須把匯入參數 INPUT_METHOD 搭配 MODE 使用，才能在 WE19 選「前景」或「出錯才前景」除錯；否則交易永遠在背景跑。

16. AIF 是什麼：業務人員也能處理介面錯誤

BIT750 開宗明義：介面的本質永遠是「把資料帶進系統（IDoc、檔案⋯）→ 產生單據（例如銷售訂單）→ 讓人接著處理」。出錯是常態，而且錯誤多半是業務性的：

  • 收到的資料品質差、原始建檔打錯字；識別資訊無效（信用卡號、IBAN）；缺資料（地址）。
  • 格式轉換錯：日期 MM/DD/YYYY vs DD.MM.YYYY、小數點 100.00 vs 100,00、負數 (100) vs -100 vs 100-。
  • 缺對照資料：客戶主檔不存在、值對應表缺值。
  • 技術問題：資料被鎖、被移動或刪除；記憶體不足。

沒有 AIF：IT 人員在佇列或 BD87 看到錯誤，發現是業務問題，還得找出該負責的業務人員（錯誤不規則出現時更難找），溝通來回耗時耗錢；最糟的是 IT 乾脆等對方每週自動重送。有 AIF：負責的業務人員直接在 AIF 的監控畫面看到錯誤、自己修正、自己重處理，IT 專心做 IT 的事——結果是責任清楚、解決更快、資料品質更高、介面 TCO 降低。

AIF 兩大能力：介面開發（Design Time）——主要靠 Customizing 完成對應、檢查、動作，可重用、可做變體、可獨立測試；監控與錯誤處理（Runtime & Operations）——業務（power user）監控、可自訂授權、介面狀態總覽、依內容分派給不同人（例如依銷售組織分派）。

使用情境說明
情境 1 Runtime＋Monitoring「經典」用法：介面用 AIF 開發、也用 AIF 監控，綜效最大
情境 2 Monitoring only既有介面不改，只用 AIF 監控；需要一個「包覆用」的 AIF 介面告訴框架要監控什麼。見效最快
情境 3 Runtime only重用 AIF 的檢查、對應、動作，但不需要監控（例如同步呼叫，錯誤由呼叫端處理）

支援的底層技術：Proxy（XI Runtime）、AIF XML Runtime、檔案、ALE／IDoc、Web Service、Enterprise Service、BDoc；另可自寫程式擴充到 CIF、qRFC、bgRFC、MWB 等，而不必修改監控畫面。

Namespace（6 碼 CHAR，名稱不限）：所有介面、值對應、固定值、檢查、動作都必須屬於某個 namespace；Customizing 在 namespace 層級上鎖、授權也以 namespace 為單位。AIF 交付的範例 namespace /AIF/ 是唯讀的，不能拿來開發。建議用 <專案>_<應用元件>（XY_FIN、XY_CRM、XY 放共用物件）或依方向分（INB001、OUT001）。

Interface（名稱 10 碼＋版本）：唯一識別是 namespace＋介面名＋版本；AIF 不交付任何標準介面，清單預設是空的。必須定義 RAW 結構與 SAP 結構，而且都要存在於 ABAP Dictionary：

方向來源結構目的結構
入站RAW（長得像對方送來的資料；Proxy 時就是輸入參數型別）SAP（依要呼叫的 BAPI／方法設計，通常要自己建）
出站SAP（觸發端能提供的資料，例如選擇畫面欄位）RAW（對方要的格式；Proxy 時就是輸出參數型別）

何時開新版本？處理邏輯要改但目的不變、或要在指定日期切換而不能動一般設定時。AIF 預設選最高版本，也可用 Interface Determination 依內容決定版本（第 18 節）。

17. AIF 介面開發：Mapping、Check、Value Mapping、Action

課程練習情境：建一個 XML 介面，收到旅行社資料後建立航空客戶並替他們訂機位（RAW 結構 ZAIF_S###_RAW_FLIGHT，含 TRAVEL_AGENCY、CUSTOMER_DATA（客戶底下再掛 FLIGHT_BOOKINGS）、SALES_AGENT；SAP 結構 ZAIF_S###_SAP_FLIGHT，含 CUSTOMERS（BAPISCUNEW）與 FLIGHT_BOOKINGS（BAPISBONEW）平行兩張表）。

Structure Mapping：說明來源結構哪個節點對到目的結構哪個節點。來源選根結構時欄位留一個空白字元；兩邊結構相同時勾 Move Corresponding Fields（連子結構、子表一起搬；再勾 Copy Fields only 則只搬欄位）。只有根與第一層能直接對應，第二層以下、或兩邊層次不同（來源的明細在表頭底下、目的卻在同一層）都要用 Indirect Mapping：先對應父結構 → 在父結構的欄位對應中把子結構指為 Sub-Table → 為子結構建一筆勾選 Indirect Mapping 的結構對應。來源兩表平行、目的卻是巢狀時，還要設 Selection Field／Operator／Comparison Field（例如依客戶 ID 7411 篩出屬於他的機位）。

Field Mapping：目的欄位＋最多 5 個來源欄位（Field Name 1～5；引用目的結構欄位要加 @；直接給固定值用 %值，例如 %5）；可設 Offset／Length、分隔字串（多欄位不設定時預設串接）、Field Name for Data Link（出錯時標紅哪個欄位）、值對應、轉換常式（例 ALPHA、MATN1，須搭配方向：External→Internal 或反向；不填方向則忽略）或 Data Element for Conversion（例 DATS 把 STRING 日期轉 DATS）、檢查（預設檢查目的欄位，勾 Check Before Mapping 改檢查來源）。

Check：輸入最多 5 個欄位值、輸出成功與否，與情境無關所以可跨介面重用。內建簡單檢查（只含數字、非空白、全大寫、允許字元、運算子＋樣式）、資料庫檢查（表名＋WHERE，檢查存在或檢查欄位值）、或自寫函數模組（簽章必須與範本 /AIF/FILE_TEMPL_CHECK 相同）。一個可重用檢查可含多個單一檢查，彼此以 OR 連接。可設專屬錯誤訊息（訊息類別＋號碼＋最多 4 個變數，%value 為常數）。結構層級的檢查失敗有兩種反應：Ignore data（略過該行繼續）或 Treat as error（該行停止並記錯）。

Fix Value：namespace 層級的可重用常數（例：所有介面的客戶折扣 10% 改成 5%，改一處全部生效）。考題陷阱：本地固定值與可重用固定值同時存在時，AIF 採用全域（可重用）那個。

Value Mapping：最多 5 個輸入值 → 1 個輸出值，可跨 namespace 重用。三種做法：① 對照表（在 /AIF/VMAP 維護，可選「Customizing」隨傳輸、或「Master」在正式系統由業務維護）；② 直接 SELECT 資料庫表；③ 自寫函數模組。可設缺值時用預設或報錯；業務人員可從錯誤畫面直接導向 /AIF/VMAP，欄位已預填，補上缺值後重啟訊息。參數以 $1～$5 引用 Field Name 1～5 的值。Conditional Mapping：以 Check 為條件，成功時改用替代欄位／替代值對應／空值。

Test Tool 與 Analyzer：AIF 測試工具可建測試檔、填資料、按 Transform 看對應結果、按 Process 真正執行動作（重按不會在監控產生新訊息，視為重處理）；XML 介面還能「Process in XML Runtime」產生真訊息。Analyzer 只能用在由測試工具建立並執行的訊息，可逐步看對應順序（黃＝該步設定、紅＝設定用到的欄位、藍＝被改變的欄位）、查欄位在哪被用到／被改，但不能在執行中改欄位值。

Action：介面的業務邏輯，由一或多個動作函數（依 Function Number 順序執行）組成，可跨 namespace 重用（只要介面能提供該 DDIC 型別的資料）。定義時先填一般資訊（名稱、Commit Mode、Commit Level、可選的 Init Function、主元件型別），再定義函數。

設定選項與行為
Commit ModeCommit Work／Commit Work and Wait／No Commit Work
Commit Level每個函數後、每個動作（全部資料集）後、每個動作（每筆資料集）後、不提交（交給介面層）。「函數執行到一半」不是選項。出錯時 AIF 會 Rollback；重啟時已提交成功的函數不會再執行（例：兩個客戶，第一個成功、第二個失敗，修正後重啟只會建第二個）
Stop Processing on Error動作函數層：函數 10 出錯則該行的 20、30 不執行；指派動作層：動作 10 出錯則該行動作 20 不執行
Restart Always重啟時即使上次成功也再執行（只針對出錯的行）。內部編號的函數（例如建立單據）通常只該執行一次
Fields to Restore第一個函數建客戶（內部編號）成功、第二個建發票失敗；重啟時不會再建客戶，客戶號碼從 Field to Restore 取回傳給第二個函數
Changeable Fields設定哪些欄位業務可在監控中修改（仍需授權）；修改前後值、時間記錄在 /AIF/EDCHANGES；介面層級要先在 Namespace-Specific Features 建介面專屬項目才看得到設定

18. AIF 進階：Index Table、Alert、XML Runtime、Proxy、檔案、自訂物件

Index Table（僅適用 Selection Engine＝AIF Index Tables）：所有訊息預設記在標準單一索引表，可依 namespace、介面、版本、時間、狀態查。要依業務欄位（例如工廠、公司代碼）查詢，就建介面專屬的單一索引表（在 Namespace-Specific Features 的 Message Index Table Name 指定；訊息量大時建議每個介面一張）；關鍵欄位位於表格中時用多重索引表（Multi Index Table，Selection Type＝Multiple selection）。多重索引欄位不參與監控分組，也不能用來決定 Recipient——只有單一索引欄位可以。要在 /AIF/ERR 加上自訂查詢欄位，得寫一支 Module Pool 程式，用 SELECTION-SCREEN 語法（不能用 Screen Painter）定義成子畫面，再掛到 Namespace-Specific Features 的 Program Name／Screen Number（選擇畫面見 3-1 章）。

依關鍵欄位分派 Recipient 與警示：例如發票介面，公司代碼 1000 給 RECIPIENT_1、2000 給 RECIPIENT_2。前提是該欄位是單一索引欄位且勾 Relevant for Recipient Determination；複製 /AIF/T_ALRT_DEF 建自己的「收件者指派表」並加上該欄位，在 Configure Alerts 指定。預設警示類別 /AIF/ALERT_CAT_DEF；要給業務更多提示可在 ALRTCATDEF 建自己的類別，容器元素與預設類別同名時 AIF 會自動帶值。郵件通知三選一：下一個警示才寄（預設）、不寄、每筆錯誤都寄；設定以 recipient 為單位（同一介面你屬於兩個 recipient 時，關掉一個仍會收到另一個的信）。Hide Structures／Hide Fields 可在介面或 namespace 層級隱藏機敏資料。

AIF XML Runtime：步驟是建來源／目的結構 → 定義介面 → Application 與 Persistence Engine 設 XML → 結構對應 → 以 /AIF/CL_ENABLER_XML=>TRANSFER_TO_AIF（單筆）或 TRANSFER_TO_AIF_MULT（多筆；仍逐筆處理，同一次呼叫可以有成功也有失敗）交給 AIF。處理以 Runtime Configuration Group（/AIF/PERS_CGR，namespace＋3 碼）控制：預設每個 run 100 筆、每個 packet 20 筆；250 筆會產生 3 個 run（100／100／50），第三個 run 有 2 個 20 筆與 1 個 10 筆的 packet。勾 Run Scheduled 則以背景工作非同步執行（以 SY-UNAME 放行，需有 AIF 處理授權），勾 Schedule Packages 則 packet 另開工作；群組停用時訊息只入佇列，由 /AIF/PERS_RUN_EXECUTE 觸發（預設 run 滿了才執行）。

File Adapter：建立對應檔案的 RAW 結構（檔案是表格時，RAW 要含一個以欄位結構為列型別的表格；若 RAW 只代表一行，則每一行產生一則訊息）→ SAP 結構 → 介面（Application／Persistence＝XML、Selection＝AIF Index Tables、Logging＝AIF Application Log）→ 對應與動作 → File Adapter 設定（檔案型態 binary／text；內容 Flat、Complex（要設子結構判定）、User Defined（自寫對應函數）、XML（XSLT 或 Simple Transformation）；文字型態：分隔字元（CSV）、固定長度、每行一欄）。Block Size：1000 筆不設則成 1 則訊息，設 100 則成 10 則；只有扁平結構能設。交易：/AIF/LFA_UPLOAD_FILE（手動單檔，伺服器或本機，可預覽）、/AIF/LFA_CHECK_SEND（伺服器大量上傳，可排程，讀完搬到另一資料夾避免重讀）。

Custom Objects（簡化錯誤處理）：針對「某則日誌訊息＋某介面」建立 Custom Function（跳到其他交易，/AIF/CUST_FUNC）、Custom Hint（處理說明，/AIF/CUST_HINTS）、Custom Data Link（訊息連到資料欄位，/AIF/CUST_LINK）、Custom Message Text（換成業務看得懂的文字，/AIF/CUST_TEXT）。可見性：只限自己（預設）／使用者清單／所有人；範圍：此介面此訊息（預設）／此介面所有訊息／所有介面此訊息／全部。改過可見性或範圍後，只能到維護交易改，不能在監控畫面改。

Interface Variant：原介面不能改時，依傳送者追加額外的對應或檢查（例：三個傳送者各自有不同的公司代碼推導邏輯）；變體只能「加」，不能略過原介面已做的事（包括檢查）。

其他（Unit 14）：自動重處理用 /AIF/REP_AC_DEF（定義重處理動作，函數 /AIF/RESTART_MSG）與 /AIF/REP_AC_ASGN（依介面指定哪種錯誤自動重啟、最多幾次、最短／最長等待時間），例如「Object is locked by user &1」；Trace Level 預設 0，可在 view /AIF/V_FINF_TL 設定或從監控以較高層級重啟分析。授權：角色範本 SAP_AIF_ADMIN、SAP_AIF_ALL、SAP_AIF_ARCHITEXT（原文拼法）、SAP_AIF_DEVELOPER、SAP_AIF_POWER_USER、SAP_AIF_PROCESSING、SAP_AIF_TEST_TEMPL、SAP_AIF_USER；授權物件 /AIF/PROC（處理）、/AIF/CUST（Customizing）、/AIF/ERR（錯誤處理，可唯讀）、以及 /AIF/TECH、/AIF/EMC、/AIF/CFUNC、/AIF/HINTS、/AIF/IFDET、/AIF/VMAP、/AIF/LFA、/AIF/CDLOG、/AIF/CTEXT、/AIF/CLINK；資料內容層級授權（例如業務 A 只看 VKORG 1）需要對應的單一索引欄位。Interface Determination：同一 RAW 結構有多個 XML 介面、或同一「訊息類型／基本類型」有多個 IDoc 介面時，依欄位值決定用哪個介面；Proxy 只限入站（本地整合引擎）、IDoc 只限入站且不適用標準 IDoc runtime、XML 入出站皆可；自訂引擎類別實作 /AIF/IF_INF_DET_ENGINE 或繼承 /AIF/CL_INF_DET_ENGINE_BASE。

19. 用 AIF 處理與監控 IDoc：四種情境

先回顧標準 IDoc：入站通常經 RFM IDOC_INBOUND_ASYNCHRONOUS 把資料以字元形式存進資料庫（此時還不分物料、訂單）；技術傳輸與業務過帳分離，好處是錯誤可以在接收端處理。夥伴＋訊息類型決定 Process Code（WE20）；能用的函數模組必須先在 WE57 與訊息類型／基本類型連結，才能掛到 WE42 的 Process Code。

IDoc 區段在 DDIC 是一個個獨立結構，而 AIF 介面需要「一個根結構」當 RAW／SAP 結構，所以既有的 IDoc 結構不能直接用。產生報表 /AIF/IDOC_GEN 會依基本類型（含擴充）產生根結構，並直接建好 engines 設定正確的介面。

練習與自我檢核

  1. IDoc 的三種記錄各存在哪個資料表？哪一種不會隨 IDoc 傳給對方？
    參考答案：控制記錄 EDIDC、資料記錄 EDID4（結構 EDIDD）、狀態記錄 EDIDS；狀態記錄不隨 IDoc 傳送，而是另外經狀態處理（或 SYSTAT01）回報。
  2. 為什麼監控程式多半只讀 EDIDC 就能知道狀態？
    參考答案：控制記錄的 STATUS 欄位永遠存最新狀態；只有評估歷史、測試 IDoc 統計需要全部狀態時才讀 EDIDS。
  3. 說明基本類型、擴充、區段類型、區段定義、訊息類型的差別，以及各用哪個 TCODE 維護。
    參考答案：基本類型／擴充 WE30；區段類型（版本無關）與區段定義（版本相依、外部名稱）WE31；訊息類型（商業意義）WE81；兩者多對多指派 WE82。
  4. 夥伴設定檔由哪四張表構成？為什麼上線清單一定要列它？
    參考答案：EDPP1（一般）、EDP13（出站）、EDP12（MC 附加）、EDP21（入站）；夥伴設定檔不能傳輸，必須在正式系統建完主資料後維護。
  5. 系統 Process Code EDIS 與 EDIR 差在哪？
    參考答案：都處理子系統回報的錯誤狀態；EDIS（TS30000078）只能顯示，EDIR（TS70008125）還能重送出站 IDoc，但重送用控制記錄資料，不重讀夥伴設定檔。
  6. 寫一支程式用 MASTER_IDOC_DISTRIBUTE 送 IDoc，送完卻在 WE02 看不到／卡在 SM58，最可能漏了什麼？
    參考答案：漏了 COMMIT WORK（tRFC 在提交時才送出）；大量送時還要釋放 IDoc 鎖（EDI_DOCUMENT_DEQUEUE_LATER）。
  7. 自建入站函數模組要在哪三個地方註冊，再到哪裡掛給夥伴？
    參考答案：BD51 函數屬性（輸入類型）、WE57 函數 ↔ 訊息類型／基本類型（ALE 註冊，含 BOR 物件）、WE42 入站 Process Code；最後 WE20 入站參數。
  8. 入站函數模組如何通知 ALE 這張 IDoc 失敗？
    參考答案：在 IDOC_STATUS 附加狀態 51 的記錄（含訊息與 SEGNUM），RETURN_VARIABLES 附加 Error_IDOCs，WORKFLOW_RESULT 設 99999；不要自己 COMMIT。
  9. 講義 IDOC_OUTPUT_TESTER 範例中的 E1HEAD 填值有什麼錯？
    參考答案：配銷通路寫成 E1HEAD-VKORG = '10'，把銷售組織 '1000' 覆蓋掉，應為 E1HEAD-VTWEG = '10'；另有一個多餘的 ENDSELECT。
  10. IDoc 狀態 30、64、51、53、69、70 分別代表什麼？各用什麼程式／交易往下處理？
    參考答案：30 出站準備發送（RSEOUT00／WE14）；64 入站準備傳給應用（RBDAPP01／BD20）；51 應用單據未過帳（修正後 BD87 或 RBDMANI2）；53 已過帳；69 IDoc 已編輯（可再處理）、70 被編輯前的原件。
  11. AIF 的四個 Engine 是哪四個？（干擾選項：Adapter、Monitoring、Process、Integration）
    參考答案：Application、Persistence、Selection、Logging。
  12. AIF 何時需要 Indirect Mapping？Field Mapping 最多幾個來源欄位？固定值與目的欄位引用各用什麼符號？
    參考答案：結構在第二層以下或兩邊層次不同時；最多 5 個；固定值 %、引用目的結構欄位 @，值對應中以 $1～$5 引用參數。
  13. 動作的 Commit Level 有哪幾種？「Fields to Restore」解決什麼問題？
    參考答案：每個函數後、每個動作（全部資料集）後、每個動作（每筆資料集）後、不提交；沒有「函數中途」。Fields to Restore 讓重啟時不再執行已成功的內部編號函數，仍能取回它產生的號碼（例如客戶號碼）給後續函數用。
  14. AIF IDoc 情境 2 與情境 3 的差別？兩者都要改哪三個標準設定？
    參考答案：情境 2 動作裡呼叫原標準 IDoc 函數（透過 /AIF/IDOC_ACTION_FUNCTION），RAW＝SAP 結構；情境 3 動作自由呼叫 BAPI，需自建 SAP 結構與結構對應。都要改 WE57（指派 /AIF/IDOC_INB_PROCESS_FUNC_0）、WE42（Process Code）、WE20（夥伴改用新 Process Code）。
  15. 入站 Proxy 呼叫 /AIF/CL_ENABLER_PROXY=>PROCESS_MESSAGE 時，為什麼不能 CATCH 它的例外？
    參考答案：例外被吃掉（或方法沒有例外類別）時，AIF 的錯誤無法傳回 Proxy 框架，訊息被標為成功，之後的重啟與編輯都不正確。
  16. 實作題：寫一支 SALV 報表，列出過去 3 天某訊息類型的入站錯誤 IDoc 與最後一則錯誤訊息，並說明你如何確保「最後一則」真的是最後一則。
    參考答案要點：EDIDC 以 DIRECT = '2'、STATUS IN（列舉）與 CREDAT 篩選；EDIDS 取回後依 DOCNUM、COUNTR DESCENDING 排序再 DELETE ADJACENT DUPLICATES，或 SQL 端 ORDER BY COUNTR DESCENDING；不能依賴 HANA 的回傳順序（第 14 節範例）。
