3. R/3 三層架構與 SAP Gateway

SAP 採用模組化、軟體導向的主從式（Client/Server）架構，把表示層、應用層、資料庫層分散到不同主機，這是系統高延展性的基礎：

  • 資料庫層：RDBMS 管理主資料、交易資料，也存放 ABAP 程式與中繼資料（Repository）。
  • 應用層：執行 ABAP 程式；開發者可用 ABAP Workbench 補充 SAP 功能。
  • 表示層：SAP GUI，或其他前端（AFE：Alternative Front Ends）與介面。

實例（Instance）是一套系統的管理單元，定義該應用伺服器提供哪些服務：對話（Dialog）、更新（Update）、佇列（Enqueue）、背景（Background）、列印（Spool）、閘道（Gateway）。分派器（Dispatcher）在應用伺服器上協調工作程序，透過訊息伺服器（Message Server）與同系統的其他實例溝通，透過閘道服務與外部系統溝通。

  • SAP 的對外通訊一律經過 SAP Gateway，基於 TCP/IP。從 3.0 版起每個實例都有自己的閘道；閘道也可以裝在非 SAP 主機上。
  • 與 IBM R/2 或其他 LU6.2 系統通訊時，要在閘道加裝 SNA 功能（TCP/IP 與 LU6.2 之間的轉換），這種閘道稱為 SNA 閘道。把附加元件集中裝在一台專用主機，可以把設定與維護的影響降到最小。
  • 遠端 Windows NT 應用只能用「遠端閘道」啟動（因為遠端程式只能透過該閘道啟動）。筆記作者由此理解了為何 NetWeaver 2004s 安裝包裡有獨立、各平台版本的元件。
  • 閘道的即時狀態用 SMGW（Gateway Monitor）觀察，第 14 節詳述。
講義提到的 Interface Adviser（1998 年 4.5 版的線上選型工具）早已下線；現代等價物是 SAP API Business Hub（api.sap.com）與各產品的 Integration Guide。ALE 元件與預定義介面仍是維持分散式系統資料一致性的主要手段（見 5-22 章）。
S/4HANA 現況：R/2、SNA／LU6.2 已完全退場。閘道安全改由 secinfo／reginfo 存取控制清單管理（誰可以向閘道註冊外部程式、誰可以被閘道啟動），這是資安稽核必查項目，屬 Basis 範疇。

4. RFC 概覽：本地呼叫與遠端呼叫的差別

  • 本地呼叫函數模組時，它與呼叫程式跑在同一個工作程序。
  • 遠端呼叫時，若目標是 SAP 系統，函數在自己的工作程序執行（有自己的 SAP LUW）。目標可以是同一套或不同套 SAP、R/2，或外部非 SAP 系統上的伺服器程式。
  • 呼叫端在每一次 RFC 時都會 roll out，因此觸發一次隱式資料庫提交（implicit DB commit）。這句是整門課最重要的技術細節。
  • RFC 目的地用 SM59 維護，存在 RFCDES 表；ABAP 程式呼叫遠端函數時必須指定目的地，每個協作系統要有一筆。
  • 從 4.6C 起，可遠端呼叫的函數模組也可以傳巢狀結構（深層結構、字串、內表型參數也可以，但外部呼叫端要能處理）。

隱式提交的實務後果：① 在 OPEN CURSOR（未加 WITH HOLD）或 SELECT 迴圈中呼叫 sRFC，資料庫游標會被關掉，下一次 FETCH 直接 DUMP；② 你在本地已經 INSERT／UPDATE 但還不想提交的資料，會因為一次 sRFC 被「偷偷」提交，之後的 ROLLBACK WORK 撤不回來。更新相關的 LUW 規則請對照 5-11 章。

5. RFC 目的地（SM59）：型別、負載平衡與登入使用者

  • 目的地只在來源系統（呼叫端）維護，依遠端系統種類選擇型別。
  • 4.7／Web AS 6.20 起新增兩種 HTTP 目的地型別，可用 HTTP（取代 RFC 協定）與 Internet 上的應用交換資料。
型別名稱重點

筆記列的型別中有一項「互聯網連接」，與 SM59 樹狀結構對不上；依上下文推測是「內部連接（I）」的翻譯誤植，這裡以 SM59 實際型別為準。

型別 3 的兩種連線方式（（依講義步驟整理））：

  • 負載分配（Load Distribution，新版稱 Load Balancing）＝否：要連到特定應用伺服器，填目標主機（Target Host）與系統號（System Number）。
  • 負載分配＝是：填系統標識（SID）、訊息伺服器（Message Server）與登入群組（Logon Group）。這些資訊可在目標系統的 SM51（伺服器概覽）與 SMLG（登入群組）找到；訊息伺服器由參數 rdisp/mshost 決定，可用 RZ11 或報表 RSPFPAR 查。
  • Logon & Security 頁可存目標系統的登入資料，使用目的地時就能自動登入。使用者型別必須是對話（Dialog）或 CPIC（新版叫「通訊 Communication」）；現在一般再加上 System 型。

型別 T 的兩種變體：

  1. 啟動（Start）：實際通訊建立時才啟動外部程式。a) 在應用伺服器上：程式名要給完整路徑；b) 在明確主機（Explicit Host）上：要指定主機名與含程式名的完整路徑；c) 在前端工作站上：在目前 SAP GUI 的電腦上啟動，要給完整的絕對路徑。
  2. 註冊（Registered Server Program）：存取一個已經手動啟動、並用 RFC 呼叫向閘道註冊了程式標識（Program ID）的程式。不必每次啟動，適合常駐、頻繁呼叫的程式。要填 Program ID 與閘道主機／服務（閘道就是目前應用伺服器時可省略）。JCo／NCo／PyRFC 的伺服器模式都是這一種。

4.7／6.20 起，目的地還可以自動檢查目標應用所需的權限，適用所有目的地型別。

*&-------------------------------------------------------------*
*& 程式開頭先檢查 SM59 目的地是否存在、可連線
*& RFCDES：RFC 目的地主檔（SM59 維護的內容就存在這裡）
*&-------------------------------------------------------------*
PARAMETERS p_dest TYPE rfcdest OBLIGATORY DEFAULT 'QAS_CLNT300'.

START-OF-SELECTION.
  " 型別 3 的名稱區分大小寫：不要自作主張 TRANSLATE TO UPPER CASE
  SELECT SINGLE rfcdest, rfctype
    FROM rfcdes
    WHERE rfcdest = @p_dest
    INTO @DATA(ls_dest).
  IF sy-subrc <> 0.
    MESSAGE |目的地 { p_dest } 不存在（SM59 名稱區分大小寫）| TYPE 'E'.
  ENDIF.

  " 用標準 RFC 函數 RFC_PING 做最輕量的連線測試
  DATA lv_msg TYPE c LENGTH 255.
  CALL FUNCTION 'RFC_PING'
    DESTINATION p_dest
    EXCEPTIONS
      communication_failure = 1 MESSAGE lv_msg
      system_failure        = 2 MESSAGE lv_msg
      OTHERS                = 3.
  WRITE: / |{ ls_dest-rfcdest }（型別 { ls_dest-rfctype }）|,
         / COND string( WHEN sy-subrc = 0 THEN `連線正常`
                        ELSE |連線失敗 { sy-subrc }：{ lv_msg }| ).
S/4HANA 注意：目的地裡的密碼不要用個人帳號，一律用 Type = System／Communication 的技術帳號，並啟用 SNC（Secure Network Communications）加密。雲端與地端之間則透過 SAP Cloud Connector，不再直接開 SAProuter 埠。

6. 三個預定義目的地：SPACE、NONE、BACK

目的地意義用途
SPACE（空白）本地呼叫，等同於根本不寫 DESTINATION用變數當目的地時，變數為空就自動退化成本地呼叫
NONE也是本地，但請求會送到目前應用伺服器的預設閘道，像外部請求一樣處理（有自己的工作程序、會隱式提交）只有一套系統時測試 RFC 行為；要讓函數在獨立 session 跑（例如隔離函數群組全域資料）
BACK在被 A 呼叫的遠端函數（B 上）裡，再反向呼叫 A 的函數只支援同步 RFC；R/3 到 R/2 的連線不能用 BACK

三個標準目的地都不能從 R/2 系統使用。

*&-------------------------------------------------------------*
*& 被呼叫端（系統 B）的 RFC 函數：處理到一半，用 BACK 回呼叫端寫日誌
*& SE37 屬性頁：Processing Type = Remote-Enabled Module
*&-------------------------------------------------------------*
FUNCTION z_bc415_callee.
*"  IMPORTING
*"     VALUE(IV_MATNR) TYPE  MATNR
*"  EXPORTING
*"     VALUE(EV_MAKTX) TYPE  MAKTX
  SELECT SINGLE maktx
    FROM makt
    WHERE matnr = @iv_matnr
      AND spras = @sy-langu
    INTO @ev_maktx.

  " BACK：回到原呼叫端（系統 A）執行 Z_BC415_CALLER_LOG；只能是同步呼叫
  DATA lv_msg TYPE c LENGTH 255.
  CALL FUNCTION 'Z_BC415_CALLER_LOG'
    DESTINATION 'BACK'
    EXPORTING
      iv_text = |B 系統已讀取 { iv_matnr }|
    EXCEPTIONS
      communication_failure = 1 MESSAGE lv_msg
      system_failure        = 2 MESSAGE lv_msg
      OTHERS                = 3.
ENDFUNCTION.

*& 呼叫端（系統 A）只有一套系統時，先用 NONE 測試整條路徑
CALL FUNCTION 'Z_BC415_CALLEE'
  DESTINATION 'NONE'
  EXPORTING  iv_matnr = 'TG11'
  IMPORTING  ev_maktx = DATA(lv_maktx)
  EXCEPTIONS communication_failure = 1
             system_failure        = 2
             OTHERS                = 3.

7. 同步 RFC：語法、標準例外、遠端 Context 與遠端除錯

CALL FUNCTION … DESTINATION 可以呼叫遠端的 ABAP 函數模組，甚至是外部伺服器程式的 C 子程式。處理會停在呼叫端，等遠端函數處理完並回傳輸出後才繼續。

一定要處理兩個標準例外：

  • COMMUNICATION_FAILURE：呼叫端的 RFCDES 沒有維護該目的地，或無法建立與遠端的連線。
  • SYSTEM_FAILURE：遠端要啟動的函數模組或 C 子程式不存在；遠端發生 DUMP、遠端觸發 A／X 訊息，也都走這個例外。

遠端 Context：只要呼叫程式的 Context 還活著，對遠端目的地的連線就保持；遠端被載入的函數群組也保持活著（與本地呼叫相同）。所以連續呼叫同一函數群組的兩個函數，它們可以存取同一份函數群組全域資料。但每一次同步 RFC 呼叫都有自己的資料庫 LUW（遠端各自隱式提交）。

*&-------------------------------------------------------------*
*& 同步 RFC 的標準寫法：兩個系統例外 + MESSAGE 取回原因
*&-------------------------------------------------------------*
DATA lv_msg  TYPE c LENGTH 255.
DATA ls_info TYPE rfcsi.

CALL FUNCTION 'RFC_SYSTEM_INFO'          "標準 RFC：取目標系統資訊
  DESTINATION p_dest
  IMPORTING
    rfcsi_export          = ls_info
  EXCEPTIONS
    communication_failure = 1 MESSAGE lv_msg   "目的地不存在／連不上
    system_failure        = 2 MESSAGE lv_msg   "遠端函數不存在／遠端 DUMP
    OTHERS                = 3.

CASE sy-subrc.
  WHEN 0.
    WRITE: / |SID { ls_info-rfcsysid } 主機 { ls_info-rfchost } 版本 { ls_info-rfcsaprl }|.
  WHEN 1.
    MESSAGE |連線失敗：{ lv_msg }（檢查 SM59、網路、閘道）| TYPE 'I'.
  WHEN 2.
    MESSAGE |遠端系統錯誤：{ lv_msg }（到目標系統 ST22 看 DUMP）| TYPE 'I'.
  WHEN OTHERS.
    MESSAGE |未預期錯誤 { sy-subrc }| TYPE 'I'.
ENDCASE.

" 呼叫結束、不再需要遠端 Context 時，主動關閉連線（釋放遠端 session）
CALL FUNCTION 'RFC_CONNECTION_CLOSE'
  EXPORTING  destination = p_dest
  EXCEPTIONS OTHERS      = 1.

遠端除錯：SAP 對 SAP 的連線可以直接除錯被呼叫的遠端函數，從呼叫端的除錯器一步一步走進去。也可以在呼叫端除錯器中對每個 RFC 敘述前自動設中斷點：中斷點 → 敘述中斷點 → 進入 RFC（新版除錯器：Breakpoints → Breakpoint at → Statement，輸入 CALL FUNCTION DESTINATION）。條件是遠端登入使用者必須是對話型且有除錯權限，否則遠端函數會一步執行完畢（背景處理）。除錯細節見 5-4 章 BC403。

RFC 對話（RFC Dialog）：遠端函數若使用了畫面（CALL SCREEN、CALL TRANSACTION、顯示清單），畫面會顯示在呼叫端的 session。條件同樣是遠端登入使用者為對話型，否則觸發 SYSTEM_FAILURE。在背景作業中執行時，這種 RFC 對話會讓程式中止並觸發 SYSTEM_FAILURE。

技術帳號（System／Communication 型）無法除錯、也無法顯示遠端畫面。上線環境不要為了除錯把 RFC 帳號改成 Dialog 型——那等於開了一個可互動登入的萬用帳號。在 QAS 另建一個除錯用目的地才是正解。

8. 非同步 RFC：STARTING NEW TASK 與結果回收

加上 STARTING NEW TASK task，遠端函數啟動後呼叫端立即繼續執行，兩邊完全分開處理；輸出之後再收。任務名稱可自由取（但要唯一）。aRFC 用於程序的平行處理。

  • 被呼叫的函數在自己的工作程序執行；也可以在背景作業中使用 aRFC，但每個呼叫仍各自佔用工作程序。
  • 在 RFCDES 可用 aRFC 選項為每個目的地設定 aRFC 呼叫數量；超過後目標伺服器會做自動負載檢查，資源不足時系統會等一下，讓同一遠端伺服器平衡下一個呼叫。
  • 呼叫時不能寫 IMPORTING（呼叫不等結束），也只能處理 COMMUNICATION_FAILURE 與 SYSTEM_FAILURE；函數自己的輸出與特定例外要到回呼常式裡再處理（也可以不收）。

帶確認的 aRFC：原教材用 PERFORMING subr ON END OF TASK 指定一個 FORM，函數結束時自動呼叫它，FORM 裡用 RECEIVE RESULTS FROM FUNCTION 取回輸出。依本圖書館規範，新程式不再寫 FORM，改用 CALLING meth ON END OF TASK：方法必須是 public、且只有一個 IMPORTING p_task TYPE clike 參數，收到的就是任務名稱，可用來判斷是哪個 aRFC 剛結束。

回呼常式的限制（原教材強調）：

  • 不能包含會中斷目前程式的敘述：CALL SCREEN、SUBMIT、COMMIT WORK、WAIT、RFC、W 或 I 類訊息。
  • 回呼常式裡的 WRITE 沒有作用。
  • 只有在呼叫程式處於 roll-out 狀態時（也就是執行到 WAIT 時）回呼常式才會被自動執行。
  • RECEIVE RESULTS … KEEPING TASK：讓遠端載入的函數群組 Context 保留到呼叫程式結束，之後可在同一任務名稱下的 aRFC 繼續使用舊的遠端 Context。

WAIT 的運作：執行 WAIT … UNTIL 時先檢查條件，成立就直接往下；不成立就在 roll-out 狀態等 aRFC 回傳，回傳時執行回呼常式，再回到 WAIT 檢查。這個「檢查／等待」會一直重複，直到條件成立或已經沒有任何未完成的 aRFC。WAIT 會設定 sy-subrc，所以回呼常式裡 RECEIVE RESULTS 得到的 sy-subrc 必須先存到自己的變數。

10. 交易式 RFC（tRFC）：LUW 綁定、執行機制與自動重試

同步與非同步 RFC 每次呼叫都在遠端建立獨立的 LUW；tRFC 可以把多個遠端函數綁進同一個 LUW，出錯時自動回滾。語法是 IN BACKGROUND TASK，必須寫在 DESTINATION 之前；執行到 COMMIT WORK 時，之前登記的 tRFC 才綁成一個 LUW 送出（不等待）。

  • tRFC 也是非同步，但與 aRFC 不同，無法取回被呼叫函數的輸出：沒有 IMPORTING、沒有 ON END OF TASK、沒有 RECEIVE RESULTS。
  • 執行機制：tRFC 呼叫先存進本地表 ARFCSSTATE（LUW 執行狀態）與 ARFCSDATA（tRFC 的輸入資料）。來源系統用 SM58 顯示與管理這些 LUW。
  • 不想立即執行、要排到之後某個時間：在 COMMIT WORK 前本地呼叫 START_OF_BACKGROUNDTASK，指定日期與時間。COMMIT WORK 會自動判斷是立即作業還是排程作業；作業執行時從 tRFC 表讀出資料送出，成功就刪除表中條目，失敗就啟動自動重試或回滾。
  • 若 COMMIT WORK 同時觸發了本地更新（CALL FUNCTION … IN UPDATE TASK），tRFC 只會在本地更新成功後才執行。

成功或錯誤的自動機制：

  • 連不上目的地：記錄在 ARFCSSTATE（SM58 可見），作業重新排程。重試次數與間隔在目的地的 tRFC 選項設定，預設重試 30 次、每次間隔 15 分鐘。
  • 遠端執行時被 A／X 訊息中止或觸發例外：遠端目前 LUW 的所有修改都回滾，錯誤記在來源系統 ARFCSSTATE；這些條目留在 tRFC 表中，作業不會重新排程。你要用 SM58 找出錯誤、到遠端系統修正，再在 SM58 用功能「執行 LUW（Execute LUW）」重新觸發。
  • 想回滾遠端、又要讓來源系統重新排程（典型例子：要處理的主資料被鎖住，稍後再試就好）：在遠端函數中呼叫 RESTART_OF_BACKGROUNDTASK，不要用 MESSAGE A… 或 RAISE。

LUW 綁定規則：

  • COMMIT WORK 前送往不同目的地的 tRFC，會依目的地分成不同 LUW（例：X1、X2 送 B → LUW1；X3、X4 送 C → LUW2）。
  • 加 AS SEPARATE UNIT 的 tRFC 永遠自成一個 LUW。
  • 每個 tRFC LUW 有唯一的交易標識（TID）（SM58 可見）。COMMIT WORK 之前呼叫 ID_OF_BACKGROUNDTASK 取得 TID；COMMIT WORK 之後用 STATUS_OF_BACKGROUNDTASK 依 TID 查執行狀態。
  • 也可以呼叫外部 C 函數，但外部伺服器程式要自己實作回滾機制（見 RFC SDK 文件與範例）。

11. 佇列式 RFC（qRFC）：保證順序

要讓 tRFC 進入一個先進先出（FIFO）佇列，必須在每一個 tRFC 呼叫之前，用 TRFC_SET_QUEUE_NAME 指定佇列名稱。佇列名稱規則：

  • 最多 24 個字元；
  • 不能以空白或百分號（%）開頭；
  • 不能包含星號（*）。

資料存放與管理：同一佇列的 tRFC LUW 一樣存在 ARFCSSTATE／ARFCSDATA，但不能再用 SM58 管理，要改用佇列管理 SMQ1。佇列資料（佇列屬性以及指向 tRFC 表中相關 LUW 的指標）存在 TRFCQOUT。SMQ1 可以：列出佇列、顯示佇列中的 LUW 與含輸入資料的函數模組、開始或停止佇列傳輸、刪除佇列。

錯誤處理：遠端某個 LUW 出錯時，整個佇列都停下（回滾），該 LUW 與佇列中其後所有 LUW 都留在佇列與 tRFC 表中；修正錯誤後在 SMQ1 重新傳輸佇列。

13. RFC 型態怎麼選，以及 RFC 權限：S_RFC、信任關係、S_RFCACL

通訊錯誤時的處理狀態決定了型態選擇：

  • sRFC／aRFC：發生通訊錯誤時，遠端處理狀態未知（不知道對方到底做了沒）。所以適合「遠端處理狀態不重要」的資料讀取，出錯重讀即可。
  • tRFC／qRFC：一定會確認遠端處理狀態（持續嘗試直到確認成功），所以適合「處理狀態非常重要」的遠端資料修改。
實務口訣：讀用 sRFC，寫用 tRFC／qRFC／bgRFC。如果一定要用 sRFC 做寫入（例如外部系統同步呼叫 BAPI 建單），就要設計「冪等」：先以外部單號查詢是否已建立，再決定要不要建，避免通訊逾時後重送造成重複單據。

S_RFC 權限檢查：

  • 權限物件 S_RFC 定義每個 RFC 登入使用者可以啟動哪個函數群組的 RFC；該使用者只能執行被授權函數群組中的函數。
  • S_RFC 檢查預設自動啟用，可用設定檔參數關閉（參數名 auth/rfc_authority_check；上線系統絕不可關）。
  • 遠端函數內部行為的權限（例如 CALL TRANSACTION 的交易碼權限）會和 RFC 登入使用者的使用者主檔比對，不是呼叫端的使用者。
S_RFC 欄位內容
RFC_TYPE講義年代只有 FUGR（函數群組）；新版另有 FUNC（單一函數模組），可做更細的授權
RFC_NAME函數群組名（或 FUNC 時的函數名）。* 表示所有函數群組都可執行
ACTVT固定 16（執行）
講義說「後兩個值固定，只要改 RFC_NAME」，並舉例 RFC_NAME = * 代表全開。實務上 RFC 帳號給 * 是資安稽核的紅燈。依 Casper 第二條經驗，授權也要「列舉」：把介面實際會呼叫的函數群組（或 FUNC 層級的函數名）一筆一筆列出來，不要用萬用字元或名稱區間（如 Z*），因為新開的 Z 群組會被自動放行。SAP 另提供 STAUTHTRACE／STUSOBTRACE 收集實際用到的函數，協助產出最小授權。

信任關係（Trusted RFC，僅限 SAP 對 SAP）：

  • 兩套系統間宣告信任關係後，可在信任系統做特定 RFC 登入而不必傳密碼。
  • 名詞別弄反：信任系統（trusting）＝ RFC 目標系統，在這一端宣告；被信任系統（trusted）＝ RFC 來源系統。
  • SMT1：定義信任關係；SMT2：在被信任系統顯示「把本系統宣告為被信任」的信任系統。
  • 被信任系統的使用者要用 SM59 建一個信任目的地（Trusted System = Yes），只填遠端使用者名、不比對密碼；既有信任關係下仍可用一般（帶密碼）目的地。
  • 信任系統中要給被放行的使用者 S_RFCACL 授權。詳細設定見 SAP Note 128447。
S_RFCACL 欄位意義
RFC_SYSID呼叫端（被信任）系統 ID
RFC_CLIENT呼叫端用戶端（Client）
RFC_USER呼叫端使用者
RFC_EQUSER是否只允許同名使用者（Y／N）
RFC_TCODE呼叫端交易碼
RFC_INFO呼叫端附加資訊（保留未用）
ACTVT只能是 16（執行）
S/4HANA 注意：① S_RFCACL 的 RFC_USER = * 且 RFC_EQUSER = N 等於「來源系統任何人都能以任何身分登入」，是稽核最常抓的高風險授權；② 新版信任關係有新舊兩種安全方法，新建議搭配 SNC 並依 SAP Note 3089413 升級；③ 7.40 起的 UCON（UCONCOCKPIT）可把「允許被外部 RFC 呼叫的函數」限縮成白名單，先 Logging 一段時間再切 Final，是 S/4HANA 專案資安必做項目。

15. BAPI 概念：業務物件、BOR 與 BAPI 的性質

SAP 業務物件（Business Object）提供物件導向角度的業務資料與流程；業務物件資料庫（BOR, Business Object Repository）依應用元件階層管理業務物件、組織物件與技術物件（例：客戶訂單、客戶、發票、員工、申請、交貨）。

業務物件例屬性方法
員工姓名、地址、薪資修改地址、加薪
客戶訂單客戶、日期、項目清單建立、修改、封鎖

BOR 物件類型的元件：

  • 基本資料：內部標識、發佈層級、傳輸資料等技術細節。
  • 介面：物件類型採用的介面清單（其屬性、方法、事件）。
  • 鍵欄位：唯一識別物件的屬性，通常就是資料庫表的鍵。
  • 屬性：可以是資料庫欄位值（欄位參照）、執行時計算值（虛擬屬性）、指向其他物件的參照（物件參照；在 Workflow 中很好用）。
  • 方法：呼叫交易碼、函數模組或其他 ABAP；BAPI 被視為 API 方法。
  • 事件：給 Workflow 用，只在 BOR 定義。觸發方式：連到變更文件、狀態管理、訊息控制，或呼叫 SWE_EVENT_CREATE。

什麼是 BAPI：業務物件上特殊的、可遠端呼叫的方法，以 RFC 函數模組實作；可建立物件、查詢屬性、修改屬性——BAPI 是通往 SAP 資料的介面。用途包括 Internet 應用元件（給沒有 SAP 經驗的使用者）、SAP 元件間的業務物件通訊、VB／Java／C++ 外部用戶端。

BAPI 的性質：

  • 外部系統可以像呼叫物件方法一樣呼叫 BAPI。
  • SAP 保證 BAPI 介面不會做不相容的變更（這是 BAPI 相對於一般 RFC 函數最大的價值）。
  • 也可以在 SAP 系統內用 BAPI 存取業務資料，客戶與夥伴更容易擴充功能。
  • 顯示傳給 BAPI 或從 BAPI 回傳的資料，是呼叫程式的工作（BAPI 本身不能有畫面）。
  • 回傳參數 RETURN 帶成功或錯誤訊息，依版本是 BAPIRETURN、BAPIRETURN1、BAPIRET1、BAPIRET2 或 BAPIRET2_FIX，常用欄位：TYPE（S／E／W／I，另有 A）、ID（訊息類別）、NUMBER、MESSAGE、MESSAGE_V1～V4。
  • 成功時 RETURN 可能是完全空白，也可能只有 TYPE = S，要依各 BAPI 文件判讀。

BAPI 的資料庫更新：通常經由更新任務執行，同步或非同步在呼叫 commit BAPI 時決定。含資料庫更新的 BAPI 內部不能寫 COMMIT WORK 或 ROLLBACK WORK；BAPI LUW 的結束由服務物件 BapiService（物件類型 SAP0001）的特殊 BAPI 負責：

  • BapiService.TransactionCommit → BAPI_TRANSACTION_COMMIT
  • BapiService.TransactionRollback → BAPI_TRANSACTION_ROLLBACK

標準 BAPI 與 BAPI Explorer：很多業務物件都有 GetList、GetDetail、CreateFromData；個別物件另有專屬 BAPI（例如 Customer 的 CheckPassword）。交易碼 BAPI（BAPI Explorer）依應用分組顯示所有有 BAPI 的業務物件及完整介面；它是 BOR 的邏輯視圖，只顯示有 BAPI 的物件。BAPI 程式設計方針在 BAPI Explorer 的「專案（Project）」頁籤。SAP 另交付 VB、C++、Java 用的 BAPI 函式庫（課程 CA925、CA926、CA927）。

BAPIRET2 的判讀、BAPI_TRANSACTION_COMMIT 的 WAIT 參數、Extension In/Out 等實戰細節在 4-1 章第 8 節、第 9 節、第 15 節，這裡不重複。

16. 從 ABAP 呼叫 BAPI，尤其是跨系統呼叫

  • 講義年代只能用函數呼叫（本地或遠端）從 ABAP 存取 BAPI；SAP 當時計畫把 BOR 業務物件整合進 ABAP 類別庫，但這件事後來並沒有全面實現，而是走向 RAP 的 Business Object。
  • BAPI 函數模組命名規則：BAPI_<業務物件>_<方法>（例：BAPI_FLCUST_GETLIST）。
  • BAPI 函數模組沒有例外（EXCEPTIONS），成功或錯誤一律透過 RETURN 回傳。

跨系統呼叫會修改資料的 BAPI 時，最關鍵的一點：COMMIT 必須透過同一個目的地、在同一個遠端 session 裡呼叫。第 7 節說過每次 sRFC 在遠端有自己的資料庫 LUW，但 BAPI 在遠端登記的更新任務會留在遠端 session 裡，直到你透過同一連線呼叫 BAPI_TRANSACTION_COMMIT 才真正寫入。

*&-------------------------------------------------------------*
*& 跨系統呼叫 FlightCustomer.CreateFromData，並在遠端提交
*& （BAPI_FLCUST_* 為 SAP 航班訓練模型的標準 BAPI，參數與 BAPISCUNEW 欄位以 SE37/SE11 為準）
*&-------------------------------------------------------------*
DATA lt_return TYPE STANDARD TABLE OF bapiret2 WITH EMPTY KEY.
DATA ls_commit TYPE bapiret2.
DATA lv_custno TYPE s_customer.
DATA lv_msg    TYPE c LENGTH 255.
DATA(lv_dest)  = CONV rfcdest( 'QAS_CLNT300' ).

DATA(ls_new) = VALUE bapiscunew( custname = 'Casper Lin'
                                 city     = 'Taichung'
                                 countr   = 'TW'
                                 custtype = 'P'
                                 langu    = sy-langu ).

CALL FUNCTION 'BAPI_FLCUST_CREATEFROMDATA'
  DESTINATION lv_dest
  EXPORTING
    customer_data  = ls_new
  IMPORTING
    customernumber = lv_custno
  TABLES
    return         = lt_return
  EXCEPTIONS                                   "BAPI 自己沒有例外，這兩個是 RFC 的
    communication_failure = 1 MESSAGE lv_msg
    system_failure        = 2 MESSAGE lv_msg
    OTHERS                = 3.
IF sy-subrc <> 0.
  MESSAGE |RFC 失敗：{ lv_msg }| TYPE 'E'.
ENDIF.

IF line_exists( lt_return[ type = 'E' ] ) OR line_exists( lt_return[ type = 'A' ] ).
  " 在遠端回滾——同樣要走同一個 DESTINATION
  CALL FUNCTION 'BAPI_TRANSACTION_ROLLBACK'
    DESTINATION lv_dest
    EXCEPTIONS OTHERS = 1.
ELSE.
  CALL FUNCTION 'BAPI_TRANSACTION_COMMIT'
    DESTINATION lv_dest                        "少了這行 = 在本機 commit，遠端什麼都沒寫
    EXPORTING  wait   = abap_true
    IMPORTING  return = ls_commit
    EXCEPTIONS OTHERS = 1.
ENDIF.

" 結束遠端 session；之後再呼叫就是全新的 Context
CALL FUNCTION 'RFC_CONNECTION_CLOSE'
  EXPORTING  destination = lv_dest
  EXCEPTIONS OTHERS      = 1.

cl_demo_output=>display( lt_return ).
最常見的跨系統 BAPI 錯誤：BAPI 用 DESTINATION 呼叫，BAPI_TRANSACTION_COMMIT 卻忘了加 DESTINATION——結果 commit 的是本機，遠端的更新任務在 session 結束時被丟掉，BAPI 明明回 S 卻查不到單據。另外中間若先呼叫了 RFC_CONNECTION_CLOSE，遠端 session 也就不見了，commit 同樣無效。

17. 附錄：Web RFC、ITS 與 SAP Business Connector（已淘汰）

講義附錄原本有五個主題：R/2 的 RFC 目的地、Web RFC、CPI-C、透過佇列 API（QAPI）的非同步資料傳輸、CPI-C／QAPI 練習；筆記作者略過了 R/2、CPI-C、QAPI 與練習，只整理了 Web RFC 與 BAPI 工場。

五層主從架構：ITS（Internet Transaction Server）把 SAP 的三層架構與兩層的 HTTP 主從架構接起來：瀏覽器 ↔ HTTP 伺服器 ↔ ITS ↔ SAP 應用伺服器 ↔ 資料庫伺服器。從 SAP 角度看，ITS 與 HTTP 伺服器構成應用層與表示層之間的中間層；從網路使用者角度看，ITS 維護著執行時產生的互動式 HTML 頁面。

Web RFC：透過 ITS 呼叫 SAP 中特殊函數模組的術語。一律先呼叫服務函數 WWW_DISPATCH_REQUEST，由它代理執行實際呼叫。Web RFC 函數的特性：回傳 HTML 頁面或 MIME 物件、可讀寫資料庫、可呼叫業務物件；講義列「不能被 Internet 使用者使用」。SAP 交付了一批基礎功能的 Web RFC 函數，詳見 BC440（5-17 章）。

透過 Business Connector 以 XML 呼叫 RFC：SAP Business Connector（SAP 開發、客戶可免費使用的中介軟體）可設定一個指向 RFC 函數的服務；外部用 URL 呼叫時傳入 XML 檔，Business Connector 把資料轉給函數介面，再把回應轉成 XML 回傳。XML 範例當年放在 SAP Interface Repository（ifr.sap.com，已失效）；進一步內容見課程 BIT530。

S/4HANA 現況：ITS 自 6.40 起已整合進 Kernel（SAP GUI for HTML、SICF 的 webgui 服務仍在），但 Web RFC 與 ITS Flow Logic 已不再用於新開發；SAP Business Connector 已結束維護，由 SAP PI/PO、再到 SAP Integration Suite（Cloud Integration）取代。現在要讓外部用 HTTP 呼叫 ABAP 邏輯，選項依序是：① 標準 released OData／SOAP API（api.sap.com）→ ② RAP 自建 OData V4 服務 → ③ SEGW 的 OData V2 → ④ 自寫 ICF Handler（實作 IF_HTTP_EXTENSION）。這正是「先標準、再客製」。

18. 附錄：BAPI 工場（一）── GetList 與 GetDetail 函數模組

講義用航班訓練模型示範自建 BAPI。業務情境：先用一個 BAPI 列出航班客戶清單，從中選一位客戶，再用另一個 BAPI 顯示該客戶明細。對應業務物件 FlightCustomer（物件類型 SCUSTOMER），需要兩個 BAPI：GetList 與 GetDetail。兩者有明顯的先後依賴，卻仍保持功能獨立——已知客戶 ID 時可以直接呼叫 GetDetail，不必先呼叫 GetList。

操作步驟（（依講義步驟整理））：

  1. 訓練資料用報表 SAPBC_DATA_GENERATOR 產生（講義說可從 service.sap.com/ocs-download 下載課程程式，帳號 walldorf／training，筆記作者登入失敗，只好自己從頭做）。

  3. SE37 建函數群組 ZGBAPI（筆記作者原想取 ZG，但函數群組名至少 4 個字元）。

19. 附錄：BAPI 工場（二）── 用 SWO1 的 BOR/BAPI 精靈掛上業務物件

函數寫好後，要掛到 BOR 的業務物件上才算「BAPI」（（依講義步驟整理））：

  1. SWO1（Business Object Builder）→ 物件類型輸入 SCUSTOMER → 修改（系統要求變更請求時可選本地物件或建請求）。
  2. 選單「公用程式 → API 方法 → 新增方法」，輸入函數 ZBAPI_GET_CUSTOMER_LIST → 綠色勾 → 出現「建立 API 方法：方法特性」。
  3. 方法名 GetCustomerList，填說明文件；屬性段勾選「同步」與「實例無關（Instance-independent）」。
  4. 下一步「建立參數」：參數名每個單字首字母大寫（如 ScustList、CustDetail）；BOR 方法參數名必須與函數參數名相同（大小寫除外）；表參數要指定是輸入或輸出，並勾 Mline（Multiple Line）欄。練習中直接按下一步即可。
  5. 「擴充程式」：系統警告此 BAPI 尚未實作，選「是」產生模板，把「物件導向封裝」程式加進函數，使它成為業務物件的方法。
  6. 回到「修改物件類型」，展開「方法」，新方法出現且帶綠色圖示 → 選取後按工具列「產生（Generate）」→ 可按測試或 F8 測試。
  7. GetDetail 同樣流程（方法名 GetCustomerDetail），但生成前要雙擊方法，在「一般」頁籤「不要」勾選「實例無關」。

為什麼 GetDetail 不能勾「實例無關」？（筆記作者留給讀者的問題）因為 GetDetail 作用在某一個特定的客戶上：它是實例相關（instance-dependent）的方法，呼叫前必須先用鍵欄位（FlightCustomer 的鍵欄位就是客戶編號 ID）建立物件實例，BOR 會把鍵欄位對應到函數的 Import 參數。GetList、CreateFromData 這類方法在物件還不存在或跨多個物件時呼叫，所以是實例無關的（類似類別的 static 方法）。對照 ABAP Objects：實例相關 ≈ 實例方法、實例無關 ≈ 靜態方法（見 5-2 章 BC401）。

講義說 BAPI 開發方針在《BAPI Programming Guide》，筆記作者找不到並推測 BC417 會談到；該指南現在收在 SAP Help Portal 的「BAPI Programming Guide（CA-BFA）」。

S/4HANA 現況：BOR 與 SWO1 仍存在（Workflow 也還在用 BOR 物件），但 SAP 已不建議再用 BOR 新建 BAPI。S/4HANA 新的 API 路線是：CDS View Entity（7.54+ 用 DEFINE VIEW ENTITY，1809／7.53 用 DEFINE VIEW）＋ RAP Business Object（Behavior Definition 需 7.54+／S/4HANA 1909 以上較完整）＋ OData V4 Service Binding；1809 上常見做法是 CDS ＋ SEGW／@OData.publish。若只是要給外部系統一個可遠端呼叫的函數，直接做 Remote-Enabled 函數模組（4-1 章第 5 節）就好，不必掛 BOR。

練習與自我檢核

  1. 為什麼在 SELECT 迴圈或 OPEN CURSOR 之後呼叫同步 RFC 會出事？
    參考答案要點：呼叫端每次 RFC 都 roll out，觸發隱式資料庫提交，會關閉未加 WITH HOLD 的游標、並提交尚未打算提交的本地變更。
  2. SPACE、NONE、BACK 三個目的地的差異？BACK 有什麼限制？
    要點：SPACE＝本地呼叫（等同不寫 DESTINATION）；NONE＝本地但經預設閘道、當外部請求處理；BACK＝被呼叫函數反向呼叫原呼叫端，只支援同步，R/3 到 R/2 不可用。
  3. 同步 RFC 一定要處理哪兩個例外？各在什麼情況觸發？
    要點：COMMUNICATION_FAILURE（RFCDES 無此目的地、連不上）；SYSTEM_FAILURE（遠端函數不存在、遠端 DUMP、A/X 訊息、非對話帳號卻要顯示畫面）。
  4. aRFC 呼叫時為什麼不能寫 IMPORTING？結果要怎麼收？回呼常式何時執行？
    要點：呼叫不等結束；用 CALLING meth ON END OF TASK（舊式 PERFORMING）加 RECEIVE RESULTS FROM FUNCTION；只有在呼叫端 roll out（WAIT FOR ASYNCHRONOUS TASKS）時才執行；WAIT 會覆寫 sy-subrc。
  5. DESTINATION IN GROUP 的三條規則？群組沒資源時會怎樣？
    要點：寫在 STARTING NEW TASK 之後、只能同系統、不能與 DESTINATION 並用；觸發 RESOURCE_FAILURE。群組在 RZ12 維護。
  6. 寫一段 tRFC：兩個函數綁同一 LUW、第三個獨立 LUW，並在 COMMIT 前取 TID。
    要點：IN BACKGROUND TASK 在 DESTINATION 前；第三個加 AS SEPARATE UNIT；ID_OF_BACKGROUNDTASK 在 COMMIT WORK 前；STATUS_OF_BACKGROUNDTASK 在 COMMIT WORK 後。
  7. tRFC 失敗有哪兩種情況？各自會不會自動重試？遠端要「晚點再試」該怎麼寫？
    要點：連不上 → 記 ARFCSSTATE、依目的地設定重試（預設 30 次、每 15 分鐘）；遠端 A/X 或例外 → 回滾、不重排，要 SM58 Execute LUW；要重排就呼叫 RESTART_OF_BACKGROUNDTASK，不要 MESSAGE A 或 RAISE。
  8. tRFC 資料存哪兩張表？qRFC 多了哪張表、用什麼交易碼管理？佇列名有哪些規則？
    要點：ARFCSSTATE、ARFCSDATA；TRFCQOUT，用 SMQ1（入站 SMQ2）；≤24 字元、不以空白或 % 開頭、不含 *。
  9. 讀資料與改資料各該選哪一類 RFC？為什麼？
    要點：sRFC/aRFC 通訊錯誤時遠端狀態未知，適合讀；tRFC/qRFC 保證確認處理狀態，適合改。S/4HANA 新開發改用 bgRFC。
  10. S_RFC 三個欄位？為什麼 RFC_NAME 不該給 *？
    要點：RFC_TYPE（FUGR，新版另有 FUNC）、RFC_NAME、ACTVT=16；應列舉實際函數群組／函數，萬用字元與區間會自動放行新物件（Casper 經驗二）。
  11. 信任關係裡，哪一端是 trusting？在哪裡設定？被放行的使用者需要什麼授權？
    要點：trusting＝RFC 目標系統，用 SMT1 定義；SMT2 在被信任端檢視；使用者需 S_RFCACL（七個欄位）；參考 SAP Note 128447。
  12. BAPI 與一般 RFC 函數的差別？BAPI 裡可以寫 COMMIT WORK 嗎？
    要點：BAPI 是 BOR 業務物件的 API 方法、SAP 保證介面相容、沒有 EXCEPTIONS 只用 RETURN；內部不寫 COMMIT/ROLLBACK，由 BapiService（SAP0001）的 BAPI_TRANSACTION_COMMIT／ROLLBACK 結束 LUW。
  13. 跨系統呼叫 BAPI 後，BAPI 回 S 但目標系統查不到資料，最可能的原因？
    要點：BAPI_TRANSACTION_COMMIT 沒加同一個 DESTINATION（commit 到本機），或 commit 前已 RFC_CONNECTION_CLOSE 使遠端 session 消失。
  14. BAPI 工場中，GetList 與 GetDetail 在 SWO1 的「實例無關」要怎麼勾？為什麼？
    要點：GetList 勾實例無關；GetDetail 不勾，因為它作用在由鍵欄位（客戶 ID）識別的特定物件實例上。
  15. 把原教材 ZBAPI_GET_CUSTOMER_LIST 改寫成 S/4HANA 寫法時，除了語法之外還要補什麼？
    要點：SELECT 明列欄位並加 ORDER BY（HANA 無預設排序）；RETURN 改用 BAPIRET2 與 BALW_BAPIRETURN_GET2；不用 FORM 改區域類別；而且動手前先查標準 BAPI_FLCUST_GETLIST（先標準、再客製）。
