2. Web Dynpro 是什麼？宣告式開發與它在 S/4HANA 的地位

原廠開場的定位：Web Dynpro 用宣告式（declarative）方式、以 MVC 為基礎開發網頁 UI。你只要宣告「畫面上有哪些 UI 元素、資料從哪裡來、可以怎麼導覽」，框架就依 Meta Model 自動產生程式，替你處理 HTML 與 JavaScript；你的程式碼只放在框架預留的位置（Controller 方法）裡。

Web Dynpro 的哲學：手寫程式碼越少越好。具體做法有三：

  • 宣告式 Meta Model 定義 UI，開發環境從抽象定義產生程式；設計期不知道的變化，才用程式在執行期動態改 UI（§20）。
  • 框架內建國際化、無閃爍（flicker-free）互動、商業邏輯與 UI 乾淨分離（修改版的 MVC）。
  • 提供 Wizard（Web Dynpro Code Wizard）產生表單、表格與 Controller 方法中的程式。

Web Dynpro ABAP 應用程式可直接使用的資料來源：系統中的全域類別方法、本系統或經 RFC 呼叫後端系統的函數模組、透過 Web Service Client 物件呼叫的 Web Service。

原廠明確警告：不要在 Controller 方法裡直接寫 SELECT，那會把流程邏輯與商業邏輯混在一起。Web Dynpro ABAP 不支援 Model 物件，最好的做法是把商業邏輯封裝在全域 ABAP 類別中；若要跨元件重用非視覺邏輯，可做成沒有 View 的 Faceless Component。本章所有範例都遵守這一點。

3. 元件架構：Component、Window、View、Controller、Context、Application

Web Dynpro Component 是容器，裡面裝著與 UI 及程式有關的所有實體，是軟體模組化的單位：

  • View：瀏覽器上一塊矩形區域，包含 UI 元素（輸入欄、按鈕⋯）。一頁可以只由一個 View 組成，也可以由多個 View 組合。
  • Window：定義 View 的可能組合與 View 之間的流程。一個 Window 可含任意多個 View，一個 View 也可被嵌入任意多個 Window。
  • Controller：放 Web Dynpro 原始碼的地方；全域變數宣告成 Controller 屬性（Attribute）。
  • Context：每個 Controller 都有的階層式資料儲存區，存放「與 UI 相關」的全域資料（顯示在畫面上、或用來控制 UI 屬性）。

Component 可以被三種方式使用：① 透過 Web Dynpro Application 把元件綁到一個 URL，由瀏覽器或其他 Web Dynpro Client 呼叫；② 當作子元件，把它的視覺介面與主元件的畫面組合；③ 當作子元件，主元件存取它程式介面中的方法與資料。

MVC 與內外可見性

MVC 由挪威人 Trygve Reenskaug 於 1970 年代末在 Xerox PARC 提出，首次實作於 Smalltalk-80；SAP 修改並擴充了原始 MVC 規格來打造 Web Dynpro。一個元件的實體分成兩半：

可見性實體重點
內部可見View（Layout + View Controller）、Window（+ Window Controller）View Controller 可含導覽 Plug、方法、Context。Window 的 Outbound Plug 可接內嵌 View 的任何 Inbound Plug，View 的 Outbound Plug 也可接外層 Window 的 Inbound Plug；但同一元件的 Window 之間不能導覽。
Component Controller元件層級的 Controller；只跟某個 View 有關的邏輯（例如檢查輸入）寫在該 View Controller。View Controller 不能被宣告為 Used Controller（違反 MVC）。
Custom Controller選用，用來模組化元件內容：當某幾個 View 的區域控制器，或封裝某個 Model 類別的邏輯，減輕 Component Controller 的負擔。
外部可見Interface Controller每個元件只有一個；透過它把資料、方法、事件開放給其他元件。
Interface View與 Window 一對一，建立 Window 時自動產生；只開放勾了 Interface 屬性的 Plug，Window 的方法與 Context 不會經 Interface View 對外公開。沒有 View 的元件就不需要 Window，也沒有 Interface View，稱為 Faceless Component。
商業邏輯不應該寫在 Web Dynpro 元件裡，應該放在元件外（全域類別），才能被 Fiori/OData、RFC、背景作業重用——這也是日後把 WDA 換成 RAP 時，成本最低的寫法。

Web Dynpro Application 與應用程式參數

Application 是進入元件的入口，也是唯一能以 URL 定址的 Web Dynpro 實體。定義時要指定：① 要實例化的元件（Root Component）；② 使用的 Interface View（其預設 View 決定預設 View Assembly）；③ 入口 Inbound Plug（必須是 Startup 型）。就像一個 Module Pool 可以掛多個 TCODE，一個元件也可以定義多個 Application，各自指向不同 Interface View 或不同 Inbound Plug。

4. View 之間的導覽：Plug、Navigation Link 與 View Assembly

導覽靠「觸發 Outbound Plug」。觸發 Outbound Plug 會產生一個導覽事件，這是一種特殊的非同步事件，會被放進導覽佇列（navigation queue）；佇列在 Web Dynpro 處理階段的特定時點才執行，在那之前還可以再觸發更多 Plug，或整個清掉。

  • Outbound Plug：依「造成離開目前 View 的動作」命名；宣告後產生 FIRE_<plug>_PLG 方法。
  • Inbound Plug：依「為什麼顯示這個 View」命名；是導覽事件的處理方法，產生 HANDLE<plug> 方法。只有在目前 View Assembly 裡所有 View 都觸發完 Plug、且沒有驗證錯誤取消導覽時才會被呼叫。
  • Navigation Link：把 Inbound Plug 註冊到 Outbound Plug 的導覽事件上；定義在 Window 裡而不是 View 裡，所以同一個 View 在不同 Window 中可以有不同的導覽。
  • Plug 可以帶參數，用來在 View 之間傳資料。
  • Action：把用戶端事件（例如按按鈕）連到 View Controller 裡自動產生的事件處理方法 ONACTION<action>；要換 View 就在這個方法裡觸發 Outbound Plug。

View Assembly 與 ViewContainerUIElement

  • Window 是「所有可能組成可見畫面的 View 集合」，定義哪些 View 以何種組合顯示、觸發 Plug 時組合如何改變。
  • View 可用 ViewContainerUIElement 切出容器區域，實現巢狀 View；一個 ViewContainerUIElement 一次只能顯示一個 View，每個區域有一個啟動時的預設 View。
  • 所有可能出現的 View 都必須嵌入 Window；要清空某區域，嵌入元件自動建立的 EMPTYVIEW 並導覽過去。
  • 任一時刻實際看得到的那組 View 稱為 View Assembly。

5. Controller 類型、生命週期與共用規則

Controller數量說明實例化時機
Component Controller每元件 1 個全域、對所有 Controller 可見，驅動整個元件；沒有視覺介面應用啟動即建立，活到元件結束
Custom Controller0..n封裝 Component Controller 的子功能。框架自動實例化且順序不確定，所以程式不能依賴其他 Custom Controller 已存在延遲到第一次呼叫其方法；不能明確刪除

  • 執行期所有 Controller 實例相對其元件都是 Singleton，View Controller 也是——所以同一個 View 不能在一個 View Assembly 中嵌兩次。
  • Web Dynpro 是 stateful 技術，Controller 實例的生命不只一次請求（對照 ITS/BSP 無狀態的差異見 5-17 章）。
  • 每個 Controller 都有自己的 Context，Root Node 已存在；至少有 wddoinit( )、wddoexit( ) 兩個 Hook Method；兩個預設屬性 WD_THIS（Controller 功能）與 WD_CONTEXT（Context 根節點）。

Controller C1 宣告使用 C2（在 C1 的 Properties 頁籤）之後，C1 可以：映射 C2 的 Context 節點、呼叫 C2 的方法、存取 C2 的 Public 屬性、處理 C2 的事件。所有 Controller 預設都使用 Component Controller（可刪除）；View Controller 不能被使用，所以 View 的 Context 與方法永遠是私有的——View 只負責顯示與互動，產生資料是 Component／Custom Controller 的工作。

Component／Custom Controller 可以定義自訂事件，任何 Controller（含 View、Window）的事件處理方法都能訂閱。多個方法訂閱同一事件時，執行順序不確定——跟「HANA 沒有預設排序」是同一類陷阱：凡是框架沒有保證順序的地方，你的邏輯就不能依賴順序。

6. Context：節點、屬性、Cardinality、Lead Selection、Singleton

每個 Controller 有且只有一個階層式的 Context，資料只活在 Controller 的生命週期內。結構（metadata）通常在設計期定義，但執行期也能改內容與結構。

  • Context Root Node：固定屬性、不能刪除，Cardinality 為 1..1，永遠只有一個元素；執行期由 WD_CONTEXT 參照。
  • Node：主要的執行期資料儲存抽象，可有屬性與子節點。節點名稱在整個 Controller Context 中必須唯一。
  • Element：節點底下所有子實體組成的一個單位——節點像內表，元素像一列。
  • Attribute：不能有子實體，一定掛在某個節點（Root 或其他節點）底下。
  • Root 下的屬性會在執行期產生一個結構，參照存在元素的 STATIC_ATTRIBUTES；Root 下每個子節點自動產生 Node 物件，參照存在 Root 元素的 CHILD_NODES。

1..1恰好一個節點實例化時自動建立 index 1 元素；刪掉它或加第二個 → DUMP
1..n一個以上自動建立 index 1 元素；刪掉預設元素 → DUMP

Root 的直接子節點（獨立節點）在第一次被存取時自動實例化；非 Root 直接子節點（相依節點）必須依附父節點的元素，父節點集合是空的，子節點就不存在——所以相依節點的存在「不保證」。原廠拿內表比喻：內表的列數不是定義的一部分，但也沒有最小／最大列數限制，所以內表沒有 Cardinality 的對應物。

Lead Selection

每個節點都有整數屬性 LEAD_SELECTION_INDEX。節點屬性 Initialize Lead Selection = true 時，第一個元素一建立就自動設為 1；也可以由程式或使用者操作（例如點 Table 某列）設定。清除用常數 IF_WD_CONTEXT_NODE=>NO_SELECTION。它的用途：① 表格選列時自動跟著變，也可以反過來用程式改它來標示某列；② 表單欄位繫結到 0..n／1..n 節點時，顯示的是 Lead Selection 那個元素；③ 父節點 Lead Selection 改變時，框架會自動呼叫子節點的 Supply Function。

HANA 沒有預設排序 × Lead Selection：Lead Selection 預設就是「第 1 個元素」。如果 bind_table( ) 餵進來的內表是沒有 ORDER BY 的 SELECT 結果，在 HANA 上每次進畫面「預設選中的那一列」都可能不同，後面依 Lead Selection 帶出的明細（Supply Function）也跟著飄。這就是 Casper 在成本評價專案上遇到 H／E 兩種成本構成交替出現的同一個病：任何「取第一筆」的邏輯，包括 Lead Selection，都必須先明確排序。

Singleton 屬性

子節點 N2 在父節點 N1 底下：

  • Singleton = false（非 Singleton）：N1 有 n 個元素，就有 n 個獨立的 N2 實例，每個掛在對應的父元素上。原廠寫「non-singleton 是預設」。
  • Singleton = true：不管 N1 有幾個元素，執行期 N2 只有一個實例，永遠對應父節點的 Lead Selection 元素——搭配 Supply Function 做「表頭選哪列、明細就換哪批」是最常見的組合。
教材修正：原廠 p60 寫「Singleton = false 是預設值」，但在 SE80 新建節點時，Singleton 核取方塊實際上是預設勾選（true）的——這也是 Supply Function 範例不用特別設定就能動的原因。考 TAW12 時照教材答，實作時請看清楚節點屬性。

7. Context Mapping 與 Data Binding

兩個核心機制合起來，讓「不同 View 上的 UI 元素之間的資料傳遞」可以完全用宣告的方式完成：

  • Data Binding：把 UI 元素屬性連到同一個 View Controller 的 Context 節點／屬性，自動雙向搬資料。UI 元素不能繫結到其他 Controller 的 Context，UI 元素是 View Controller 私有的。
  • Context Mapping：讓一個 Controller 的節點直接參照另一個 Controller 的節點，不必複製資料，是 Controller 之間共用資料的主要機制。

Context Mapping 規則

  • 資料來源節點叫 Mapping Origin，被映射的叫 Mapped Node；Mapped Node 沒有自己的元素集合，參照的是 Origin 的集合。
  • 前提：Origin 節點必須存在；Origin Controller 不能是 View Controller；目標 Controller 必須把 Origin Controller 宣告為 Used Controller。
  • 操作：在目標 Controller 的 Context 頁籤，把右側（Used Controller）的節點拖到左側 Root → 複製結構並建立映射；若結構已存在，把兩節點互拖，Origin 永遠是右邊 Used Controller 那一個。
  • 被映射節點中 Origin 沒有的屬性會被刪掉；兩邊名稱可以不同；映射後所有元素、屬性、子節點一起映射。Origin 結構改了，用 Mapped Node 右鍵選單同步。
  • 兩端都在同一元件內叫 Internal Mapping；Origin 在元件外叫 External Mapping（§17）。

Data Binding 的執行過程

繫結後，畫面渲染時框架把 Context 值送到 UI 元素；使用者操作觸發下一次 HTTP round trip 時，把修改過的值搬回同一個節點／屬性。等框架把控制權交給你的 Action 處理方法時，Context 已經是最新值。使用者輸入會自動轉成內部格式並做型別檢查（含 Domain 固定值）；驗證失敗時資料不會寫進 Context，但框架會保留使用者輸入，在下一個 View Assembly 中連同錯誤訊息一起顯示。

定義繫結的最少步驟：① 在 View Controller 的 Context 建節點／屬性；② 在 Layout 建 UI 元素；③ 屬性右邊有黃色圖示＋空圓圈的按鈕，按下去選 Context；④ 繫結後空圓圈變綠色勾勾，屬性值顯示 Context 路徑。

用 Context 控制 UI 屬性（不要直接碰 UI 元素）

屬性若在設計期寫死，執行期只能在 wddomodifyview( ) 裡直接存取 UI 元素才改得動——原廠明說這是差勁的設計，應避免。正確做法：建一個型別與屬性相符的 Context 屬性（型別可在 Types of the Web Dynpro Runtime 頁籤找，例如 WDY_BOOLEAN、WDUI_VISIBILITY、WDUI_STATE），把 UI 屬性繫結過去，之後在任何能存取該 Context 的 Controller 方法中改值即可。常被繫結的屬性：主屬性（如 InputField 的 value）以及 enabled、readOnly、state、visible。7.0 SP12 起，繫結對話框多了一組選項按鈕，可以直接把 enabled／visible／readOnly／state 繫結到 Context 屬性本身的屬性（Attribute Properties），不必另外建屬性。

8. UI 元素與 Layout Manager

UI 元素是佔據 View Layout 一個位置的任何圖形實體——但不一定看得到：TransparentContainer、ViewContainerUIElement、InvisibleElement 都不可見，只用來組織結構。所有 UI 元素都能在執行期設成不可見，但不會釋放它佔的空間（隱藏 InputField 左邊的 Label，InputField 不會往左移）。UI 元素只是抽象描述，執行期才渲染，不等於某段 HTML。

9. Table、CTable、選取模式與靜態右鍵選單

Table 是複合 UI 元素：Table → 多個 TableColumn（也是複合元素）→ 每欄一個 Caption（標題，選用但型別固定）＋一個 Cell Editor（預設 TextView，也可用 InputField、DropDownByKey、CheckBox、Button⋯）。Group、Tray 只強制要一個 Caption 子元素；Table、Tree 則需要更複雜的強制結構。

  • Table 必須繫結 Cardinality 0..n 或 1..n 的節點，表格列數＝節點元素數；Lead Selection 元素以反白列顯示（有選取欄時）。
  • 用 Code Wizard 建表格會自動完成繫結；手動建的用右鍵 Create Binding 一次綁好。
  • Caption 的 text 留空且欄位屬性用 DDIC 資料元素 → 欄標題自動帶 DDIC 文字。
  • 點選取按鈕預設觸發 round trip 並改 Lead Selection；把 Action 綁到 onLeadSelect，就會依序執行 wddobeforeaction( ) → Action 處理方法 → wddoafteraction( )。
  • 多選：節點 Selection（選取 Cardinality）要設 0..n 或 1..n；預設是 0..1。

12. Supply Function 與 Lazy Data Instantiation

情境：上表是航班，下表是「目前選中航班」的訂位。每個 Context 節點都可以指派一個 Supply Function（節點屬性 Supply Function 填方法名，框架產生固定簽章的方法），框架會在以下情況自動呼叫它：

  • 節點集合還是初始（沒填過）時被存取；
  • 父節點的 Lead Selection 改變；
  • 節點集合被程式 invalidate( ) 過。

而且只在「真的需要」時才呼叫：子節點既沒被程式存取、也沒繫結到下一個 View Assembly 的任何 UI 元素，就不呼叫。Supply Function 不能從程式中直接呼叫，只有 Web Dynpro Runtime 能呼叫。簽章中 PARENT_ELEMENT 是父節點 Lead Selection 元素、NODE 是要填的節點。

這就是 Web Dynpro 的 Lazy Data Instantiation：只在需要時才建資料。以銷售訂單為例，使用者只會點一張訂單看明細，一次讀出所有訂單的所有明細既浪費處理時間也浪費記憶體；相依集合也不會為父節點每個元素都建立，而是延到該父元素取得 Lead Selection 時才建。

                        iv_carrid = ls_flight-carrid

13. 國際化：DDIC 文字、OTR 與 Assistance Class

要讓應用支援多語，所有字面值都要有翻譯，執行期依登入語言載入。I18N 是 internationalization 的縮寫：首字 I、中間 18 個字母、尾字 N。與語言相關的實體包括 Label 文字、Tooltip、按鈕文字、訊息文字與圖片。三種翻譯文字來源：

來源用法重點
ABAP DictionaryLabel 關聯到繫結 DDIC 型別的 InputField 時自動帶中文字標籤（medium）；表格欄標題同理；或在繫結對話框按 DDIC binding on/off 直接指定資料元素與短／中／長文字程式中可用函數 DDIF_FIELDLABEL_GET 讀任意語言的長標籤
OTR（Online Text Repository）中央文字庫，Web Dynpro、BSP、各類 ABAP 程式（type 1、M、K）都能用。分 OTR 長文字、無 Alias 短文字、有 Alias 短文字短文字上限 255 字元；直接打在 UI 屬性值裡的文字會存成無 Alias 短文字，不能重用。Alias 格式 <package>/<alias>，屬性值填 OTR 指令 $OTR:<package>/<alias>
Assistance Class 文字符號在類別 Goto → Text Symbols 定義，透過 WD_ASSIST 取用最適合程式中組訊息，可含佔位符
  • OTR Browser：從 Web Dynpro Explorer 的 Goto 選單開啟，可建立／修改／刪除本套件的 Alias 文字、看 metadata（作者、最後修改者、最大長度）與 where-used。屬性值欄位按 F4 會列出本套件與 SOTR_VOCABULARY_BASIC（SAP 標準詞彙）的文字，選了就自動填入 OTR 指令。
  • 用 SE63 翻譯 Web Dynpro 元件或應用時，相關 OTR 短文字（有無 Alias 都算）會一起被列入翻譯。
  • OTR 有應用伺服器緩衝：本機修改或傳輸進來的文字，清緩衝前看不到；在 SAP GUI 命令欄輸入 /$OTR 清除。

14. 訊息回報：Message Manager 與它對 Phase Model 的影響

訊息向使用者顯示狀態，依類型顯示不同圖示；嚴重狀況可以取消導覽；訊息可以連結到表單欄位，欄位會被反白，點訊息連結游標就跳到該欄位。使用者輸入與型別不符時，框架自動回報驗證錯誤：取消導覽、重顯上一個 View Assembly、錯誤自動連到那個欄位。

  • 訊息區位置：預設在畫面頂端；要放別處就用 MessageArea UI 元素（可放在任何容器下）。
  • NOTIFICATION_ICON（SAP_UI 7.50 SP1+）：WDUIGUIDELINE = FIORI 且沒指定其他設計時自動啟用——表頭顯示訊息計數，點了才以可移動、可縮放的 popover 顯示；可展開長文字、用權重圖示篩選。要放在 PageHeader，MessageArea 必須是 PageHeader 的子元素（只支援此設計）。沒有 PageHeader 也沒 MessageArea 時，FIORI 準則會自動嵌在表頭區。

訊息與 Phase Model

  • 能取消導覽的位置只有 View 的 wddobeforeaction( )、wddoafteraction( )、onaction<action>，以及 Component 的 wddobeforenavigation( )。
  • 沒連結 Context 屬性的 success/warning/error：不影響 Phase Model，下一個 View Assembly 顯示，不取消導覽。
  • Fatal error：中止目前 Hook Method、跳過後續 Action 相關 Hook；在 wddoafteraction( ) 之前回報則取消導覽。
  • 驗證錯誤：取消導覽，只執行 wddobeforeaction( )、wddobeforenavigation( )、wddopostprocessing( )。
  • 連結 Context 屬性的 error：Action 處理期間回報就取消導覽；在 wddobeforeaction( ) 回報，後續 Action 相關 Hook 全跳過。只與單一 View 欄位有關的檢查，放在該 View 的 wddobeforeaction( )。
  • 上述影響只對 Action 型別 standard 成立；validation-independent 型的 Action 不管欄位對不對都會導覽並跑完所有 Hook——「取消」「關閉對話框」「結束應用」按鈕就該用這一型。
  • 巢狀 View 時：所有 View 的 wddobeforeaction( ) 都在任何 Action 方法之前跑完，所有 wddoafteraction( ) 都在之後。

15. 輸入說明：Value Help、Value Suggestion 與 Value Selector

使用者不受限於固定值集、或值集很大需要過濾時，就該給 Value Help 按鈕。開發者用繫結 Context 屬性的 Input Help Mode 控制：

Input Help Mode說明
Deactivated不提供，與資料型別無關
Automatic由 Runtime 決定（見下）
Dictionary Search Help自選 DDIC Search Help（必須有一個 import 與一個 export 參數）
Object Value Selector（OVS）用預先做好、可設定的 Web Dynpro 元件 WDR_OVS 做搜尋對話框
User-Defined Programming自己寫一個 Web Dynpro 元件當搜尋說明

Automatic 模式的判斷順序（和經典 Dynpro 類似，但名稱與型別只在設計期決定一次）：① Context 屬性以 DDIC 表／結構欄位定型，且該欄位掛了 Search Help → 用它；② 該欄位有 Foreign Key 且 Check Table 有 Search Help → 用它；③ 有 Foreign Key 但 Check Table 沒 Search Help → 顯示 Check Table 鍵欄位；④ 資料元素的 Search Help；⑤ Domain 固定值／固定值範圍；⑥ 都沒有就不顯示。只用資料元素定型時，只有 Domain 固定值或 elementary Search Help 會生效；參照 Runtime 型別 DATA、F、I、OBJECT、STRING、STRING_TABLE、XSTRING 則不提供說明。

節點用 DDIC 結構定型時，多個屬性才會對應到同一結構的欄位——只有這樣，Search Help 才能帶入多個欄位當篩選條件、選一筆回填多個欄位（例如選航班同時填 CARRID、CONNID）。這是資料字典 Search Help 參數設計的價值，見 1-2 章與 5-16 章。
  • suppressValueHelp（WDY_BOOLEAN，預設 false，可繫結）：關掉某欄位的說明。
  • InputField 的 inputHelp 屬性：auto（依繫結屬性）、calculator（欄位內小計算機，不顯示歷史）、search（搜尋圖示，點了觸發 onEnter 回後端）、none。
  • Value Suggestion（邊打邊建議）四個條件：勾 suggestValue；屬性掛 DDIC elementary Search Help 或明確指派 Value Set；應用參數 WDALLOWVALUESUGGEST = X；關閉無障礙（WDACCESSIBILITY 為空）。建議值的 round trip 不跑 Phase Model，所以 Action 方法與 wddomodifyview( ) 影響不了結果；又因流量較大可能拖慢伺服器，才必須明確開啟。

Value Selector：Index Binding vs Key Binding

Value Selector 只允許從預定值集挑選（下拉框、選項按鈕群組、ItemListBox），值少於約 30 個時才適用。

Index Binding（DropDownByIndex 等）Key Binding（DropDownByKey 等）

round trip只有對應事件屬性綁了 Action 才會發生

17. 元件重用：Component Usage、Interface Controller 與跨元件 Mapping

真實的商業應用都由多個元件組成：客戶地址、訂單明細這類功能到處要用；框架本身也以通用元件提供功能——WDR_OVS（搜尋說明）、WDR_MESSAGE_AREA（訊息）、SALV_WD_TABLE（ALV）、WDR_SELECT_OPTIONS（選擇條件）。另一常見情境是設計期準備好多個候選子元件，執行期由使用者（例如點連結）決定嵌哪一個。

  • 元件介面＝一個 Interface Controller ＋ 任意個 Interface View。Interface Controller 可含 Component Controller 中的一般方法、事件與 Context 節點：方法、事件勾 Interface 欄；節點勾 Interface Node，再勾 Input Element (Ext.) 則可被消費端映射（External Mapping）。節點開放後，其所有子節點也一起開放。
  • 每個 Window 預設產生 Interface View；不要就在 Window 的 Properties 取消 Interface 勾選。
  • 宣告使用：消費端元件的 Used Components 頁籤；Component Use 欄填的名稱會成為執行期方法名的一部分。
  • 宣告 ≠ 實例化：除少數特例外，要自己在消費端某個 Controller 中實例化。框架為每個 Component Usage 建立一個 proxy 物件，由 wd_this->wd_cpuse_<usage>( ) 取得；有 has_active_component( )、create_component( )、delete_component( )（預設實例活到消費端元件結束）。做實例化的 Controller 本身也要宣告使用該元件。
  • Interface View：嵌入消費端的 Window；其 Inbound Plug 可接消費端 View／Window 的 Outbound Plug（經 Plug 參數傳資料進去），其 Outbound Plug 可接消費端的 Inbound Plug（把資料交回來）。
  • 呼叫介面方法：先把 Component Usage 的 Interface Controller 宣告為 Used Controller，再用 wd_this->wd_cpifc_<usage>( ) 取得參照；Code Wizard 可產生。
  • 訂閱介面事件：同樣要先宣告 Used Controller，然後在消費端事件處理方法中註冊。OVS 就是這樣運作：OVS 元件每需要資料就觸發事件，消費端處理方法依事件參數判斷階段，再呼叫 OVS 的介面方法把資料送回去。

19. Adaptation：Configuration、Customizing、Personalization 與增強

層級誰做範圍說明
Configuration開發人員所有 Client 所有使用者（可傳輸）建立設定資料集，覆寫 UI 屬性或 Context 屬性值，例如隱藏元素、表格交錯底色
Customizing有權限的關鍵使用者／管理員單一 Client、所有使用者（user-independent）比個人化更有彈性；以 URL 加 SAP-CONFIG-MODE=X 啟動，右鍵 Settings for Current Configuration。先檢查 S_DEVELOP，不夠再查 S_WDR_P13N
Personalization任何使用者使用者自己受限：簡單元素只能改可見性，Table 還能調欄位順序

優先順序：Personalization 覆寫 Customizing，Customizing 覆寫 Configuration。上層可把參數設為 Final，下層就不能再改。個人化與 Customizing 都依附在某個 Configuration 上；存檔時若沒載入 Configuration，系統會建一個不含調整資訊的預設 Configuration。

  • Built-in（implicit）：框架現成、不必寫程式。Component-defined（explicit）：需要程式，所有以 Context 屬性為基礎的調整都做得到。
  • Configuration Controller：建一個 Custom Controller → 右鍵 (Re)Set as Config. Controller。可設定的屬性定義在它的 Context，經 Mapping／Binding 影響 UI，在設定工具的 Configuration-Defined 頁籤維護。這些屬性不會自動出現在 Customizing／Personalization，要自己做維護對話框，並用 personalization manager 服務物件存檔。
  • Component Configuration：綁定某元件，一個元件可有任意多個；可改該元件所有 View 的 UI 屬性。Application Configuration：綁定應用，指定每個（子）元件要載入哪個 Component Configuration，一個應用也可有任意多個；要先為應用用到的每個元件建好 Component Configuration。
  • 指派 Application Configuration：動態＝URL 加 sap-wd-configId=<appl_config>；靜態＝應用參數 WDCONFIGURATIONID。

建立 Component Configuration（依講義步驟整理）：元件右鍵 Create/Change Configuration（瀏覽器開設定工具）→ 輸入全系統唯一 ID（客戶系統只能 Z／Y 開頭）→ New → 輸入說明 → 選 Local Object 或套件 → 選傳輸請求 → 在 Web Dynpro Built-In 面板展開 View 的 UI 元素樹、改屬性值並視需要勾 Final → Save → 關瀏覽器、在 Workbench 重新整理物件清單，Configuration 會出現在元件底下。Application Configuration 類似，在 Assign Web Dynpro Component 面板為每個元件（Usage）指派 Component Configuration。

補充：設定工具本身也是 Web Dynpro 應用（較新版本為 CONFIGURE_COMPONENT／CONFIGURE_APPLICATION），FPM 應用的「畫面長相」幾乎全靠這套 Component Configuration 定義——在 S/4HANA 調整 FPM 畫面時，第一步永遠是找對 Configuration ID。

Web Dynpro 的增強（Enhancement Framework）

直接改原始碼或 Layout 叫修改，升級時會衝突。7.0 起的 Enhancement Framework（工具：Workbench 內建的 Enhancement Builder）統一了各種免修改的增強方式；增強實作是獨立開發物件，原物件不變，升級照樣可以更新，衝突用 SPAU_ENH 處理。對 Web Dynpro ABAP：SAP 可提供 BAdI；除 BAdI 外尚無 explicit 增強選項，主要靠 implicit 增強（不需要 SAP 事先規劃）。可做的事：

  • 所有 Controller：方法前後加 Pre-Exit／Post-Exit、以 Overwrite-Exit 整段取代；新增一般方法、事件處理方法、Supply Function；新增屬性；在既有節點加屬性、新增節點、更新 Mapping；靜態擴充 Used Components／Controllers。
  • View：新增 Plug、Action、View；移除既有 UI 元素、加新 UI 元素。
  • Window：新增 Plug；移除／新增 Navigation Link；新增 Window。Component／Custom Controller：新增事件。元件：靜態擴充 Used Components。
  • 前提：元件所屬軟體元件在 SE06 的系統變更設定允許。增強實作只能透過 Switch Framework 停用：套件指派到 Switch（SFW1）→ Switch 指派 Business Function（SFW2）→ 在 SFW5 啟用／停用。
  • 操作：以顯示模式開 Controller → 工具列增強按鈕（或 Ctrl+F4）→ 輸入／選擇增強實作名稱；回顯示模式按 Display<->Change（Ctrl+F1）。
先找標準，再想客製（Casper 第三條），在 Web Dynpro 上的順序是：Configuration → Customizing（SAP-CONFIG-MODE）→ BAdI → Implicit Enhancement（Pre/Post-Exit、UI 元素隱藏）→ Overwrite-Exit → 修改。每往右一步，升級時要重測的東西就多一個量級。尤其 Overwrite-Exit 等於把 SAP 的方法整個接管，SAP 修了 Bug 你也吃不到。增強觀念詳見 3-4 章、5-14 章、5-15 章。

20. 動態程式設計：執行期修改 Context 與 UI

三類動態修改：動態 Context（建立／刪除節點與屬性、改 metadata）、動態 UI（建立／移除 UI 元素、改位置與屬性）、動態指派 Action（把設計期建好的 Action 指派給靜態或動態元素）。原廠建議：能在設計期做的盡量在設計期做，只有在資料結構設計期未知、畫面行為是泛用的、或要做泛用工具元件時才用動態程式。課程範例是做一個像 SE16 的應用：使用者輸入表名，動態建 Context、動態建 Table、動態讀資料。

動態 Context

  • 新增獨立節點：先 wd_context->get_node_info( ) 取得 Root 的 metadata，再 add_new_child_node( )；參數 is_static = abap_false 的節點才能在執行期刪除。
  • 加屬性：對節點 metadata 呼叫 add_attribute( )，一次一個。
  • 一次建好節點＋屬性：static_element_type（DDIC 平面結構／DB View／透明表）、static_element_rtti（RTTI 結構描述）、或 attributes 參數（每列一個屬性描述）。
  • 取相依節點 metadata 兩種寫法：節點實例 → get_node_info( )；或 Root metadata → get_child_node( )。原廠推薦第二種，因為不依賴父節點元素存在。
  • IF_WD_CONTEXT_NODE_INFO 其他方法：get_attributes( )、get_attribute( )、get_child_nodes( )、get_child_node( )、get_parent( )、remove_attribute( )、remove_dynamic_attributes( )、remove_child_node( )。

動態 UI（只能在 wddomodifyview( )）

  • 只有 View Controller 有 wddomodifyview( )，每次 round trip 結束、渲染前都會對目前 View Assembly 的每個 View 呼叫。
  • 原則：① 能用 Context 繫結控制就不要直接操作 UI 物件；② UI 操作只准寫在 wddomodifyview( )；③ 一般只在 first_time = abap_true 時建動態結構，避免重建；④ 不要在 wddomodifyview( ) 中修改 Context，把它當唯讀。
  • 取容器：view->get_root_element( ) 或 view->get_element( id )，回傳 IF_WD_VIEW_ELEMENT，要 down cast 成 CL_WD_UIELEMENT_CONTAINER（所有容器的父類）。所有 UI 元素類別繼承 CL_WD_UIELEMENT，整棵繼承樹的抽象根是 CL_WD_VIEW_ELEMENT。
  • 先設容器屬性（尤其 Layout，會影響子元素屬性），Layout 類別都繼承 CL_WD_LAYOUT；LayoutData 類別繼承 CL_WD_LAYOUT_DATA，命名 CL_WD_<kind> 與靜態方法 new_<kind>( )。
  • 建元素：CL_WD_<element>=>new_<element>( )，例如 CL_WD_LABEL=>new_label( )；add_child( ) 加入，index 參數決定位置。複合元素用 CL_WD_DYNAMIC_TOOL 的 create_table_from_node( ) 等一次建好。
  • 通用方法：get_<prop>、set_<prop>、bind_<prop>、bound_<prop>；事件：set_on<event>、get_on<event>；容器：get_child(ren)、remove_child、remove_all_children、add_child。
  • 動態 Action：只能指向既有的 Action 處理方法（不能動態產生程式碼）；建立時用 on_<event> 參數（例如 new_button( on_action = 'X' )），或之後 set_on_action( )。
  • 同一 Action 給多個元素時，用 Action 方法的參數 WDEVENT 分辨：wdevent->name（事件名，如 ON_ACTION）、wdevent->parameters（name/value 內表，一定含觸發元素的 ID，CheckBox 另有 CHECKED）；還不夠就用 Parameter Mapping 從 UI 元素多帶參數。

22. Web Dynpro Select Options（WD_SELECT_OPTIONS_20）

把 Select Options 元件 WD_SELECT_OPTIONS_20 整合到你的元件，就能顯示搜尋條件並以程式讀取使用者輸入。讀資料與顯示結果不是它的工作，它只負責渲染條件 UI 並觸發事件。使用者可以：選屬性（第一欄下拉，唯讀者為必填）、選運算子、輸入值（可用 * 萬用字元、下拉或 Value Help）、以 +／- 增刪列、從表格或文字編輯器 Ctrl+C／Ctrl+V 一次貼入多個值（自動展成多列）、儲存／載入搜尋（搜尋內容由呼叫端傳入，元件本身不保存）。

嵌入步驟：① 宣告 Component Usage 為 WD_SELECT_OPTIONS_20；② 建 View Container，把 View W_SELECT_OPTIONS 嵌入 Window；③ 在首次輸出前（例如 View 的 wddoinit）以 init_select_options 初始化——可設表頭等一般文字、Search 等標準按鈕的可見性、最大列數預設值等全域選項（結構 WDR_SO_S_GENERAL_TEXTS、WDR_SO_S_GENERAL_VISIBILITY、WDR_SO_S_GLOBAL_OPTIONS）；④ 以 add_attributes 定義搜尋屬性（index、mandatory 等，結構 WDR_SO_S_ATTRIBUTES）；⑤ 註冊事件 on_execute 的處理方法讀取輸入。

讀輸入有兩種格式：Range 格式（SIGN I/E、OPTION EQ/NE⋯，可直接用在 WHERE … IN）用 get_input_complete_as_range，回傳 range 資料物件的內表，以欄位 ATTRIBUTE 找對應的 range；或 Select Option 資料格式（運算子定義在 IF_WD_SELECT_OPTIONS_20=>E_OPERATORS，如 is、is_not、starts_with、does_not_equal）。CL_WD_SELOPT_UTIL_20 提供轉換：convert_ranges_into_data、convert_data_into_ranges、convert_abap_ops_in_so_ops、convert_so_ops_in_abap_ops 等。範例應用：WDR_TEST_SEL_OPT_AUTO_20。

*& on_execute 事件處理：把使用者輸入轉成 Range，交給 Model 查詢
*& （Select Options 20 各方法的完整簽章請以 SE24 IF_WD_SELECT_OPTIONS_20
*&   與範例 WDR_TEST_SEL_OPT_AUTO_20 為準，此處只示範 Range 的使用）

METHOD on_so_execute.
  DATA lt_carrid TYPE zcl_wd_flight_model=>tt_carrid_range.

  " 從 Select Options 取回完整輸入（Range 格式），依 ATTRIBUTE 找 CARRID
  DATA(lt_ranges) = wd_this->mo_select_options->get_input_complete_as_range( ).

    ASSIGN <ls_range>-range->* TO FIELD-SYMBOL(<lt_any>).
    lt_carrid = CORRESPONDING #( <lt_any> ).
  ENDLOOP.

練習與自我檢核

  1. （Unit 1）Web Dynpro 是以什麼設計典範、什麼方式開發？一個 ViewContainerUIElement 同時可以顯示幾個 View？同一元件的兩個 Window 之間可以導覽嗎？
    要點：MVC、宣告式；一次只顯示一個 View；不行——Window 的 Outbound Plug 可接內嵌 View 的 Inbound Plug、View 的 Outbound Plug 可接外層 Window 的 Inbound Plug、每個 View 可嵌入多個 Window，但同元件 Window 之間不能導覽。
  2. （Unit 1）元件中哪些實體對外可見？什麼叫 Faceless Component？Application 必須指定哪三樣東西？
    要點：只有 Interface Controller（每元件一個）與 Interface View（與 Window 一對一）；沒有 View 所以也沒有 Window、Interface View 的元件；Root Component、Interface View、Startup 型 Inbound Plug。
  3. （Unit 2）下列哪些是 Component Controller 的 Hook Method：wddobeforenavigation、wddopostprocessing、wddoonopen、wddoapplicationstatechange？為什麼 View Controller 不能被宣告為 Used Controller？
    要點：除 wddoonopen（Window Controller）外都是；違反 MVC——View 只負責顯示與互動，不負責產生資料，所以 View 的 Context 與方法永遠私有，也不能當 Mapping Origin。
  4. （Unit 3）Cardinality 1..n 的節點實例化時會發生什麼？哪兩種情況會因 Cardinality 違規而 DUMP？Singleton 子節點與非 Singleton 子節點在執行期的差異？
    要點：自動建立 index 1 元素；刪掉 1..1／1..n 的預設元素、對 0..1／1..1 加第二個元素；非 Singleton 每個父元素一份子節點，Singleton 只有一份、對應父節點 Lead Selection。
  5. （Unit 3、Casper 經驗）你的航班表格每次進畫面「預設選中的航班」都不一樣，下方訂位明細也跟著變。最可能的原因與修法？
    要點：Lead Selection 預設是第 1 個元素，而 bind_table 的內表來自沒有 ORDER BY 的 SELECT，HANA 不保證順序；在 Model 類別的 SELECT 加 ORDER BY（或 ORDER BY PRIMARY KEY）。
  6. （Unit 4）Table 要繫結哪種 Cardinality 的節點？要讓使用者 Shift／Ctrl 多選，節點哪個屬性要改成什麼？預設值是？selectionMode 設 none 會怎樣？
    要點：0..n 或 1..n；Selection 改 0..n 或 1..n，預設 0..1；不顯示選取欄、Lead Selection 列不反白。
  7. （Unit 4）GridLayout 有什麼缺點？什麼元素可以避免版面亂掉？contextMenuBehaviour 設 Inherit 的效果？
    要點：欄數靜態、不能指定換行、移除元素後面全部左移；用 InvisibleElement 佔位，能用 MatrixLayout 就別用；顯示父元素的右鍵選單（可跨多層），且此屬性不能繫結 Context。
  8. （Unit 5）寫出「把內表 lt_ctx 整批放進節點 FLIGHTS 並取代原有資料」的一行程式，以及讀取目前多選列的方法名與關鍵參數。
    要點：wd_context->get_child_node( wd_this->wdctx_flights )->bind_table( new_items = lt_ctx set_initial_elements = abap_true )；get_selected_elements( including_lead_selection = … )。
  9. （Unit 5）Supply Function 何時被呼叫？可以在程式中直接呼叫嗎？要強制重讀該怎麼做？

  12. （Unit 7）Value Suggestion 的四個條件？Index Binding 與 Key Binding 的 Value Selector 在使用者選值時各改變什麼？

  15. （Unit 10）Configuration、Customizing、Personalization 誰覆寫誰？一個元件可以有幾個 Configuration Controller、幾個 Component Configuration？Customizing 模式怎麼進入？

  16. （Unit 10、Casper 經驗）客戶要求在某個 S/4HANA 標準 FPM 畫面上隱藏一個欄位並加一段檢查。請依「先標準再客製」排出方案順序。

  18. （Unit 11）要顯示 ALV，Interface View 叫什麼名字？取得設定模型的方法與類別？

  20. （Unit 13）開 Performance Monitor 的按鍵？為什麼在 PRD 按了沒反應？啟動 RAT 前必須先做什麼？
