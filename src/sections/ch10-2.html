2. CDS 存取控制（DCL）：@AccessControl 與 DEFINE ROLE

傳統報表的權限檢查是在程式裡寫 AUTHORITY-CHECK OBJECT 'V_VBAK_VKO'，再把沒權限的資料一筆一筆刪掉。CDS 的做法是把檢查規則寫在 view 旁邊的 CDS role（DCL 原始碼）裡，由 ABAP SQL 執行時自動變成 WHERE 條件。這樣程式不用自己檢查，而且沒有權限的資料根本不會從資料庫讀出來。

要用 DCL 必須有兩樣東西：

  1. view 本身標 @AccessControl.authorizationCheck: #CHECK（預設值就是 #CHECK）。另外兩個常用值：#NOT_REQUIRED（不需要檢查，例如組態值；啟用時不會出現「沒有 role」的警告）、#NOT_ALLOWED（禁止為此 view 建 role）。
  2. 一個 Access Control 物件（ADT：New → Other ABAP Repository Object → Core Data Services → Access Control），裡面寫 DEFINE ROLE。
" 受保護的 view（DDIC-based，1809 可用）
@AbapCatalog.sqlViewName: 'ZVSOAUTH'
@AbapCatalog.compiler.compareFilter: true
@AccessControl.authorizationCheck: #CHECK
@EndUserText.label: '銷售訂單（含權限檢查）'
define view ZI_SalesOrderAuth
  as select from vbak
{
  key vbak.vbeln as SalesOrder,
      vbak.auart as SalesOrderType,
      vbak.vkorg as SalesOrganization,
      vbak.vtweg as DistributionChannel,
      vbak.spart as OrganizationDivision,
      vbak.kunnr as SoldToParty,
      vbak.ernam as CreatedByUser,
      vbak.erdat as CreationDate,
      @Semantics.amount.currencyCode: 'TransactionCurrency'
      vbak.netwr as TotalNetAmount,
      @Semantics.currencyCode: true
      vbak.waerk as TransactionCurrency
}
" 對應的 CDS role（Access Control 物件，名稱建議與 view 相同）
@EndUserText.label: '銷售訂單：依銷售範圍檢查 V_VBAK_VKO'
@MappingRole: true
define role ZI_SalesOrderAuth {
  grant select on ZI_SalesOrderAuth
    where ( SalesOrganization, DistributionChannel, OrganizationDivision ) =
          aspect pfcg_auth( V_VBAK_VKO, VKORG, VTWEG, SPART, actvt = '03' );
}

語法重點：

  • 左邊是 view 的元素，右邊 aspect pfcg_auth( 權限物件, 權限欄位… ) 依位置對應：SalesOrganization ↔ VKORG、DistributionChannel ↔ VTWEG、OrganizationDivision ↔ SPART。
  • actvt = '03' 是固定值過濾：只採用使用者權限中「活動 = 03 顯示」的那幾組值。
  • 權限物件 V_VBAK_VKO（Sales Document: Authorization for Sales Areas）的欄位是 VKORG、VTWEG、SPART、ACTVT。這是 VA01／VA03 本來就在檢查的物件，所以 CDS 與傳統交易的權限規則一致。
  • DCL 的物件名稱慣例與 view 同名，一個 view 可以有多個 role，多個 role 之間是 OR（任何一個 role 放行就看得到）。
DCL 只在透過 ABAP SQL 讀取 CDS entity 時才生效。程式直接 SELECT … FROM vbak、用 SE16N 看底層表、或在 AMDP／原生 SQL 裡讀，都完全不受 DCL 限制。所以「把權限做在 CDS」的前提是：所有讀取路徑都經過這個 CDS view。另外兩個常見誤會：①沒有權限時不會報錯，只是回傳 0 筆，使用者會以為「沒資料」，請教他看 SU53；② view 標了 #CHECK 卻沒有建 role，啟用時只有警告，執行時不做任何限制。
第 14 節的 OData／Fiori Elements 清單也是透過 SADL 以 ABAP SQL 讀 CDS，所以同一個 role 會自動套用到 Fiori。這是 CDS 權限最大的好處：報表、Fiori、分析查詢一套規則。
出處：ABAP Keyword Documentation 7.52：ABAP CDS - Access Control；7.53：DEFINE ROLE, pfcg_condition（範例 aspect pfcg_auth (s_carrid, carrid, actvt='03')）。V_VBAK_VKO 欄位與 CDS 元素的對應見 SAP PRESS：CDS Access Control Fundamentals，建議在系統 SU21 再確認一次。

3. DCL 的條件種類、組合與 WITH PRIVILEGED ACCESS

除了 PFCG 條件，1809 的 DCL 還能寫下列幾種條件，並用 and／or 組合：

條件寫法用途
PFCG 條件( a, b ) = aspect pfcg_auth( OBJ, F1, F2, actvt = '03' )對應傳統權限物件（最常用）
Literal 條件SalesOrderType = 'OR'固定值過濾，例如只開放某種訂單類型
使用者條件CreatedByUser = aspect user只看自己建立的資料；運算子可用 =、<>、?=

?= 的意思是「等於目前使用者，或該欄位是初始值／NULL」。

" 組合條件：有銷售範圍權限，而且（是一般訂單，或是自己建立的）
@EndUserText.label: '銷售訂單：組合條件示範'
@MappingRole: true
define role ZI_SalesOrderAuth_Own {
  grant select on ZI_SalesOrderAuth
    where ( SalesOrganization, DistributionChannel, OrganizationDivision ) =
            aspect pfcg_auth( V_VBAK_VKO, VKORG, VTWEG, SPART, actvt = '03' )
      and ( SalesOrderType = 'OR'
            or CreatedByUser = aspect user );
}
Literal 條件和 SQL 的 WHERE 一樣：用列舉（多個 = 以 or 串起來）比用區間安全。訂單類型、銷售組織這類代碼是字元欄位，區間比的是字典序，不是業務上的「一段範圍」。遇到號碼段不連續、前導零、編碼規則改過，就會多放行或少放行，而且權限錯了使用者不會察覺。

在 ABAP SQL 中略過 DCL：有些技術程式（例如背景整合、資料搬遷、已在前面做過檢查的程式）必須讀全部資料，這時在 FROM 後面加 WITH PRIVILEGED ACCESS：

" 背景作業：已用 AUTHORITY-CHECK 驗證過執行者，這裡要讀全部銷售範圍
SELECT SalesOrder, SalesOrganization, TotalNetAmount, TransactionCurrency
  FROM zi_salesorderauth WITH PRIVILEGED ACCESS
  WHERE SalesOrganization IN @s_vkorg
  ORDER BY SalesOrder
  INTO TABLE @DATA(lt_all_orders).
  • WITH PRIVILEGED ACCESS 會讓該 entity 上的所有role（SAP 交付的和自建的）失效。寫了它，ABAP SQL 從 7.52 起會以 strict mode 檢查語法。
  • 不能和 path expression 同時使用。
  • 對資料庫表與傳統 view 寫了也沒作用（它們本來就沒有 DCL）。
「略過權限」等於把資料開給執行這支程式的所有人。程式碼審查時要把 WITH PRIVILEGED ACCESS 當作必查項目，並在註解寫明「為什麼可以略過」「前面在哪裡做了什麼檢查」。
出處：7.53：DEFINE ROLE, user_condition（uname ?= aspect user）；7.53：SELECT, data_source（WITH PRIVILEGED ACCESS 的位置、7.52 strict mode、不可與 path expression 並用）。

4. 擴充 CDS：EXTEND VIEW 與 EXTEND VIEW ENTITY

要在既有 CDS view（包括 SAP 標準 view）加欄位或 association，不必複製一份 view，也不必修改標準，而是建立一個 view extension。這是 CDS 版的 Append Structure（見 1-2 章第 12 節）。

" 1809：擴充 DDIC-based view，必須給一個 append view 名稱
@AbapCatalog.sqlViewAppendName: 'ZXVSOAUTH'
@EndUserText.label: 'ZI_SalesOrderAuth 擴充：付款條件與出貨條件'
extend view ZI_SalesOrderAuth with ZX_SalesOrderAuth
  association [0..1] to I_Customer as _ZZSoldToParty
    on $projection.SoldToParty = _ZZSoldToParty.Customer
{
  vbak.zterm as ZZPaymentTerms,
  vbak.vsbed as ZZShippingCondition,
  _ZZSoldToParty
}
" 7.55（S/4HANA 2020）起：擴充 view entity，不需要 append view 名稱
extend view entity ZI_SalesOrderEntity with
{
  vbak.zterm as ZZPaymentTerms
}
EXTEND VIEW ENTITY 需 ABAP 7.55（S/4HANA 2020）以上；1809 只能用 EXTEND VIEW 擴充 DDIC-based view。7.55 的新寫法還允許「只加 association 不加欄位」，而且啟用速度快很多。

能不能擴充，取決於原 view 的 @AbapCatalog.viewEnhancementCategory：

值意思
#PROJECTION_LIST（預設）可擴充沒有聚合、沒有 UNION 的 view
#GROUP_BY（要和 #PROJECTION_LIST 一起寫）原 view 有聚合；擴充時要一併擴充 GROUP BY
#UNION（要和 #PROJECTION_LIST 一起寫）原 view 有 UNION；擴充時每個分支都要補
#NONE禁止擴充

其他限制：extension 本身不能再被擴充；有明確 name list 的 view 不能擴充；view entity 另外不能加 KEY 欄位、不能加參數、原 view 的 @AbapCatalog.extensibility.extensible 不可為 false（此註解屬較新版本）。傳輸之後，extension 名稱與 append view 名稱都不能再改，所以一開始就要用客戶命名空間與 ZZ 欄位前綴。

擴充標準 view 前先確認它對擴充的承諾。在 1809，技術上只要不是 #NONE 就能 EXTEND VIEW，但 SAP 並沒有保證該 view 的欄位名稱、結構在升級後不變，升級時要自己重測。S/4HANA 2022 起 SAP 以 C0 契約（released for extension）正式標示哪些 view 是穩定的擴充點，而且常提供專門的擴充 include view（E_ 開頭）。先找標準：先看 SAP 是否已提供該欄位（很多欄位標準 view 已經有，只是名稱不同）、是否有 Key User 擴充（Custom Fields）可用，最後才自己擴充；增強的升級成本層級見 3-4 章，特別是 第 17 節 Clean Core 三層擴充模型。
出處：7.53：EXTEND VIEW（語法、sqlViewAppendName、viewEnhancementCategory）；7.57：EXTEND VIEW ENTITY；ABAP CDS in Release 7.55；SAP Blog：C0 Developer Extensibility for CDS Data Models。

5. Metadata extension：把 UI 註解與資料模型分開

Fiori Elements 需要大量 @UI 註解（第 9 節），全部寫在 view 裡會讓資料模型很難讀。Metadata extension（MDE，ADT 中的 Metadata Extension 物件）讓你把這些註解放到另一個原始碼檔：

  • 被擴充的 view 必須寫 @Metadata.allowExtensions: true。
  • MDE 用 ANNOTATE VIEW view名 WITH { … }，只能寫註解，不能加欄位、不能改 SQL。
  • 只有註解定義中允許用在 MDE 的註解才能寫（@UI、@EndUserText、@Consumption 等可以；@AbapCatalog、@AccessControl 這類技術註解不行）。
  • 必須寫 @Metadata.layer，值由低到高是 #CORE → #LOCALIZATION → #INDUSTRY → #PARTNER → #CUSTOMER。同一個註解在多層都有時，高層覆蓋低層；view 本身寫的註解優先權最低。
" MDE：客戶層，只放 UI 註解
@Metadata.layer: #CUSTOMER
@UI.headerInfo: { typeName: '銷售訂單',
                  typeNamePlural: '銷售訂單',
                  title: { type: #STANDARD, value: 'SalesOrder' } }
annotate view ZI_SalesOrderAuth with
{
  @UI.lineItem:       [ { position: 10 } ]
  @UI.selectionField: [ { position: 10 } ]
  SalesOrder;

  @UI.lineItem:       [ { position: 20 } ]
  @UI.selectionField: [ { position: 20 } ]
  SalesOrganization;

  @UI.lineItem:       [ { position: 30 } ]
  TotalNetAmount;
}
在 SAP 標準 view 上，SAP 自己的 MDE 是 #CORE 等較低層；客戶若要調整標準 Fiori 應用的欄位順序，可以在 #CUSTOMER 層寫自己的 MDE 覆蓋（前提是該 view 有 @Metadata.allowExtensions: true）。這仍屬於「不修改標準」的擴充，但同樣要先確認 SAP 是否提供更正式的 UI 調整方式（例如 Fiori 的使用者個人化或 Key User adaptation）。
出處：7.53：ANNOTATE VIEW（@Metadata.layer 五個值、@Metadata.allowExtensions 前提、只能用 MetadataExtension.usageAllowed 的註解）。

6. CDS table function：CDS 的外殼、AMDP 的內容

CDS view 本質是一條 SELECT。遇到一條 SELECT 寫不出來的邏輯（多步驟運算、HANA 專屬函數、需要中間暫存結果），可以改用 CDS table function：在 CDS 裡宣告參數與回傳欄位，實作交給一個 AMDP function（BY DATABASE FUNCTION）。對消費端來說，它跟一般 CDS entity 一樣可以 SELECT、可以被別的 view 引用、可以掛 DCL。

" 7.50 起可用：客戶別訂單筆數排行
@EndUserText.label: '客戶別訂單筆數（table function）'
@ClientHandling.type: #CLIENT_DEPENDENT
define table function ZTF_SalesOrderCountByCustomer
  with parameters
    @Environment.systemField: #CLIENT
    p_client : abap.clnt,
    p_from   : abap.dats
  returns
  {
    client      : abap.clnt;
    SoldToParty : kunnr;
    OrderCount  : abap.int4;
  }
  implemented by method zcl_sd_so_tf=>get_count_by_customer;
" 消費端：p_client 由 @Environment.systemField: #CLIENT 自動帶入，不必傳
SELECT SoldToParty, OrderCount
  FROM ztf_salesordercountbycustomer( p_from = @p_datum )
  ORDER BY OrderCount DESCENDING, SoldToParty
  INTO TABLE @DATA(lt_rank)
  UP TO 20 ROWS.
  • 用戶端相依的 table function，回傳清單的第一個欄位必須是用戶端欄位。
  • 實作的 AMDP 類別要實作 IF_AMDP_MARKER_HDB，方法寫成 FOR TABLE FUNCTION ztf_…，SQLScript 裡要自己處理用戶端條件。詳細寫法見 10-3 章。
table function 的回傳沒有順序。上面範例在 ABAP SQL 端用 ORDER BY OrderCount DESCENDING, SoldToParty，第二個排序鍵是為了讓「同筆數」的客戶順序也固定。HANA 沒有預設排序，任何「取前 N 名、取第一筆」都要在最外層明確排序；只在 AMDP 裡排序、外層不排，結果不保證。
出處：7.53：DEFINE TABLE FUNCTION（語法與 @ClientHandling.type: #CLIENT_DEPENDENT、@Environment.systemField: #CLIENT 範例）。

7. Analytics：Cube、Dimension 與 Query

S/4HANA 的 Embedded Analytics 直接拿 CDS view 當 BW 的 InfoProvider 用，不必另建 BW 模型。三層結構：

角色註解內容
Dimension@Analytics.dataCategory: #DIMENSION主資料（客戶、物料），提供屬性與文字
Cube@Analytics.dataCategory: #CUBE交易資料＋量值（measure），元素用 @DefaultAggregation: #SUM 指定預設彙總
Query@Analytics.query: true選 cube 的欄位、指定列／欄軸，給分析工具使用

@Analytics.dataCategory 在 7.53 的值還有 #FACT、#AGGREGATIONLEVEL；@DefaultAggregation 的值有 #SUM、#MIN、#MAX、#AVG、#COUNT、#COUNT_DISTINCT、#FORMULA、#NONE。

" Cube（1809 可用）
@AbapCatalog.sqlViewName: 'ZVSOCUBE'
@AccessControl.authorizationCheck: #CHECK
@EndUserText.label: '銷售訂單分析 Cube'
@Analytics.dataCategory: #CUBE
@VDM.viewType: #COMPOSITE
define view ZI_SalesOrderCube
  as select from vbak
{
  vbak.vkorg as SalesOrganization,
  vbak.kunnr as SoldToParty,
  vbak.erdat as CreationDate,

  @Semantics.currencyCode: true
  vbak.waerk as TransactionCurrency,

  @DefaultAggregation: #SUM
  @Semantics.amount.currencyCode: 'TransactionCurrency'
  vbak.netwr as TotalNetAmount
}
" Query（1809 寫法）：@Analytics.query: true
@AbapCatalog.sqlViewName: 'ZVSOQRY'
@AccessControl.authorizationCheck: #CHECK
@EndUserText.label: '銷售組織 × 客戶 訂單金額'
@Analytics.query: true
@VDM.viewType: #CONSUMPTION
define view ZC_SalesOrderQuery
  as select from ZI_SalesOrderCube
{
  @AnalyticsDetails.query.axis: #ROWS
  SalesOrganization,
  @AnalyticsDetails.query.axis: #ROWS
  SoldToParty,
  @AnalyticsDetails.query.axis: #COLUMNS
  TotalNetAmount,
  TransactionCurrency
}

怎麼看結果：

  • RSRT：Query 名稱輸入 2C ＋ SQL view 名稱，本例是 2CZVSOQRY。「2C」前綴是為了避免和 BW 物件同名。
  • Fiori 應用 Query Browser：@Analytics.query: true 的 view 會出現在這裡，可以直接開成分析表格（需要對應的 Fiori 角色）。
  • 也可以用 Analysis for Office 連線。
" S/4HANA 2022（7.57）起的新寫法：analytical projection view（示意）
@EndUserText.label: '銷售組織 × 客戶 訂單金額'
@AccessControl.authorizationCheck: #NOT_ALLOWED
define transient view entity ZC_SalesOrderAQ
  provider contract analytical_query
  as projection on ZI_SalesOrderCubeVE
{
  @AnalyticsDetails.query.axis: #ROWS
  SalesOrganization,
  @AnalyticsDetails.query.axis: #COLUMNS
  TotalNetAmount
}
DEFINE TRANSIENT VIEW ENTITY … PROVIDER CONTRACT analytical_query 需 ABAP 7.57（S/4HANA 2022）以上。它不會在 HANA 產生 SQL view（所以叫 transient），被投影的必須是 analytical cube 或 dimension view（上例假設已把 cube 改寫成 view entity ZI_SalesOrderCubeVE）。transient view 的 DCL 註解在新版要求寫法可能不同，未能確認，請以系統的語法檢查為準。1809 請用上面的 @Analytics.query: true。
分析查詢常見的錯誤是在 cube 裡先把不同幣別的金額加總。@DefaultAggregation: #SUM 的量值一定要帶 @Semantics.amount.currencyCode，讓分析引擎依幣別分開彙總。
出處：7.53：Framework-Specific Annotations（Analytics.dataCategory、Analytics.query、DefaultAggregation 的值）；SAP Blog：Define the Analytical Query CDS View（RSRT 用 2C 前綴）；ABAP CDS in Release 7.57、DEFINE TRANSIENT VIEW ENTITY AS PROJECTION ON, Analytical Query。

10. Virtual elements：用 ABAP 算出來的欄位

有些欄位 SQL 算不出來或不該用 SQL 算（例如要呼叫函數模組、讀文字、依複雜規則判斷），可以宣告成 virtual element：CDS 裡只佔一個位置，值由一個 ABAP 類別在 OData 讀取後算好填進去。

" consumption view 中宣告 virtual element（1809 可用）
@AbapCatalog.sqlViewName: 'ZVSOLISTV'
@AccessControl.authorizationCheck: #CHECK
@EndUserText.label: '銷售訂單清單（含開單天數）'
define view ZC_SalesOrderListV
  as select from ZI_SalesOrderAuth
{
  key SalesOrder,
      CreationDate,
      @ObjectModel.virtualElement: true
      @ObjectModel.virtualElementCalculatedBy: 'ABAP:ZCL_SO_DAYS_OPEN'
      cast( 0 as abap.int4 ) as DaysSinceCreation
}
CLASS zcl_so_days_open DEFINITION PUBLIC FINAL CREATE PUBLIC.
  PUBLIC SECTION.
    INTERFACES if_sadl_exit_calc_element_read.
ENDCLASS.

CLASS zcl_so_days_open IMPLEMENTATION.
  METHOD if_sadl_exit_calc_element_read~get_calculation_info.
    " 告訴框架：要算 DaysSinceCreation，必須一起讀 CreationDate
    "（就算前端沒有要求 CreationDate 這一欄）
    IF line_exists( it_requested_calc_elements[ table_line = `DAYSSINCECREATION` ] ).
      INSERT `CREATIONDATE` INTO TABLE et_requested_orig_elements.
    ENDIF.
  ENDMETHOD.

  METHOD if_sadl_exit_calc_element_read~calculate.
    DATA lt_data TYPE STANDARD TABLE OF zc_salesorderlistv WITH EMPTY KEY.
    lt_data = CORRESPONDING #( it_original_data ).

    LOOP AT lt_data ASSIGNING FIELD-SYMBOL(<ls_data>).
      <ls_data>-dayssincecreation = COND #(
        WHEN <ls_data>-creationdate IS INITIAL THEN 0
        ELSE sy-datum - <ls_data>-creationdate ).
    ENDLOOP.

    ct_calculated_data = CORRESPONDING #( lt_data ).
  ENDMETHOD.
ENDCLASS.
Virtual element 只在 SADL 執行環境生效（@OData.publish、SEGW Referenced Data Source、RAP 的 OData 服務）。在 ABAP 程式用 SELECT … FROM zc_salesorderlistv 讀到的 DaysSinceCreation 永遠是 CAST 的預設值 0；分析查詢、其他 CDS view 也讀不到算好的值。另外它是讀出資料之後才算，所以不能拿來當篩選或排序條件（資料庫不知道它的值）。需要在 ABAP 報表中使用同樣的計算，請把邏輯寫成獨立方法，兩邊共用。
出處：SAP Help：Interface IF_SADL_EXIT_CALC_ELEMENT_READ（方法 GET_CALCULATION_INFO、CALCULATE）；7.53：Framework-Specific Annotations（ObjectModel.virtualElement、virtualElementCalculatedBy）。參數名稱（it_original_data、ct_calculated_data、it_requested_calc_elements、et_requested_orig_elements）請在系統中以 F2 確認。

11. Released API 與 C1 契約：先找標準 view 再自建

S/4HANA 內建數千個 CDS view，組成 VDM（Virtual Data Model），命名有規則：I_ 開頭是 interface view（可重用的基礎模型，例如 I_SalesOrder、I_SalesOrderItem、I_Customer）、C_ 開頭是 consumption view（給特定應用用）、P_ 開頭是私有輔助 view（不該被客戶引用）、E_ 開頭是擴充 include view。

但「存在」不等於「可以放心用」。SAP 對 view 的穩定性承諾稱為 release contract：

契約ADT 顯示名稱承諾
C0Extend可在指定擴充點擴充，升級時擴充點穩定
C1Use System-Internally (Contract C1)可在同一系統內引用（ABAP 程式、自建 CDS），升級時欄位與行為穩定
C2Use as Remote API可作為遠端 API 對外提供

在 ADT 開啟 view → Properties 視窗 → API State 頁籤，可看到 Release State（Released／Deprecated）與是否勾選 Use in Cloud Development（可在 ABAP Cloud 開發中使用）、Use in Key User Apps。

" 直接用 released 標準 view 讀銷售訂單，不自己 JOIN VBAK/VBAP
" I_SalesOrder 本身帶有 SAP 交付的 DCL，報表自動套用銷售範圍權限
SELECT SalesOrder,
       SalesOrderType,
       SalesOrganization,
       SoldToParty,
       CreationDate,
       TotalNetAmount,
       TransactionCurrency
  FROM i_salesorder
  WHERE SalesOrganization IN @s_vkorg
    AND CreationDate      IN @s_erdat
  ORDER BY SalesOrder
  INTO TABLE @DATA(lt_so)
  UP TO 500 ROWS.
1809 的 API State 頁籤與 release contract 的呈現方式，與 2020／2022 以後的系統不同：C0／C1 的完整標示和「Use in Cloud Development」主要是隨 ABAP Cloud（S/4HANA 2022 起的 on-premise 開發者擴充）普及的。1809 系統上該頁籤是否存在、內容為何，未能確認，請以系統為準；查不到時，可到 SAP Business Accelerator Hub（api.sap.com）查該 view 是否列為 released，或看 view 原始碼的 @VDM.viewType 與 SAP Note。
先找標準，再想客製：要做銷售訂單清單，先查 I_SalesOrder／I_SalesOrderItem 是否已有需要的欄位，再決定用 EXTEND VIEW 補欄位，最後才考慮從 VBAK／VBAP 自建。自建 view 直接讀底層表，SAP 改表結構（例如 S/4HANA 把 VBUK／VBUP 的狀態欄位併入 VBAK／VBAP）時要自己改；引用 released view 則由 SAP 負責相容。另外 SAP 標準 view 的名稱與欄位在不同版本可能不同，本章範例中的 I_ view 欄位請以系統中 ADT 開啟的定義為準。
出處：SAP Help（ADT User Guide）：Contract C1 - Use System-Internally；SAP-samples：ABAP cheat sheet - ABAP for Cloud Development；SAP Blog：C0 Developer Extensibility for CDS Data Models。

12. 效能：usageType 註解、association、非 SARGable 函數與分析工具

(1) 效能註解：@ObjectModel.usageType 不會改變執行計畫，它是給消費者看的「使用說明」，也是 SAP 內部 VDM 審查的依據。

註解7.53 允許值意思
serviceQuality#A、#B、#C、#D、#P、#X（預設 #X）預期的效能等級。依 SAP 的 VDM 指引，#A 的 view 底層表不超過 3 個、#B 不超過 5 個；#D 用於分析、不支援交易處理；#X 表示未分類。各值完整定義請在 ADT 按 F1 查看
sizeCategory#S、#M、#L、#XL、#XXL（預設 #S）預期筆數量級：#S 約 1,000 筆以下、#M 約 100,000 筆以下，其餘依序更大（細部門檻請按 F1）
dataClass#TRANSACTIONAL、#MASTER、#ORGANIZATIONAL、#CUSTOMIZING、#META、#MIXED（預設 #MIXED）資料性質，影響快取與使用情境判斷
 
@AbapCatalog.sqlViewName: 'ZVSOPERF'
@AccessControl.authorizationCheck: #CHECK
@EndUserText.label: '銷售訂單（效能註解示範）'
@ObjectModel.usageType: { serviceQuality: #B,
                          sizeCategory:   #L,
                          dataClass:      #TRANSACTIONAL }
define view ZI_SalesOrderPerf
  as select from vbak
  association [0..*] to vbap as _Item
    on $projection.SalesOrder = _Item.vbeln
{
  key vbak.vbeln as SalesOrder,
      vbak.vkorg as SalesOrganization,
      vbak.erdat as CreationDate,
      _Item          " 只曝露，不在這裡使用 → 不產生 JOIN
}

(2) Association 是「用到才 JOIN」：只曝露 _Item 不會讓 SQL 多一個 JOIN；消費者在 select list 或 WHERE 用到 _Item.matnr 這種 path 時才會產生。要注意的是 to-many（[0..*]）的 path 會讓結果筆數倍增：從表頭 view 取 _Item.matnr，一張有 10 行的訂單就變成 10 筆，接著任何以表頭為單位的加總都會算錯。

(3) 避免非 SARGable 的寫法：在欄位上套函數後再比較，資料庫就不能直接用欄位的索引／欄式字典做過濾，必須先把每一筆都算出來。

" ✗ 在 CDS 中把日期轉成年份字串，再讓消費者用年份篩選
"   → WHERE OrderYear = '2025' 時，HANA 必須先對每一筆 erdat 做 substring
define view ZI_SalesOrderYearBad
  as select from vbak
{
  key vbak.vbeln                    as SalesOrder,
      substring( vbak.erdat, 1, 4 ) as OrderYear
}

" ✓ 保留原始欄位讓消費者直接篩選；年份欄位只用來顯示
"   SELECT … FROM zi_salesorderyear
"     WHERE CreationDate BETWEEN @lv_from AND @lv_to   日期是連續值，用區間沒問題
define view ZI_SalesOrderYear
  as select from vbak
{
  key vbak.vbeln                    as SalesOrder,
      vbak.erdat                    as CreationDate,
      substring( vbak.erdat, 1, 4 ) as OrderYear
}
上面兩段在真實系統中還需要 @AbapCatalog.sqlViewName 等表頭註解，此處省略以突顯差異。日期是真正的連續值，可以用區間；但訂單類型、物料群組這類代碼請用列舉（IN 明列值），理由見第 3 節。

(4) 分析工具：

  • ADT 在 view 上右鍵 Open With → Dependency Analyzer：SQL Dependency Tree／Graph 與 Complexity Metrics（底層用了幾張表、幾個 JOIN、UNION、函數），是檢查 view 疊太多層最快的方法。
  • ADT 在 view 上右鍵 Show SQL CREATE Statement：看 CDS 最後產生的 SQL，確認 association 有沒有變成預期的 JOIN。
  • ST05 SQL trace：錄下執行的 SQL，用 Explain 看執行計畫（HANA 上可進一步看 PlanViz）；SAT 看 ABAP 端時間分佈。ST05 的操作見 5-21 章第 9 節，SQL Monitor 見 第 8 節。
HANA 沒有預設排序，而且 CDS view 定義裡不能寫 ORDER BY。所以排序永遠是消費端的責任：ABAP SQL 要寫 ORDER BY，OData 要帶 $orderby。Casper 的專案實例：成本評價資料同時有 item category「H」與 cost component「E」兩種角度，兩者的成本構成欄位數量不同，程式取第一筆卻沒排序，結果時而是 H、時而是 E，成本不穩定；最後的做法是條件固定抓 H，並明確排序。把這種查詢改寫成 CDS 也一樣：view 裡用 WHERE 固定角度，消費端用 ORDER BY 固定順序。詳見 5-21 章第 24 節。
出處：7.53：Framework-Specific Annotations（usageType 三個註解的允許值與預設值）；SAP Blog：Safeguard Performance of ABAP CDS Views – Part 1（serviceQuality 與底層表數、Dependency Analyzer）；SAP Help：Dependency Analyzer。

13. CDS 的測試：CDS Test Double Framework

CDS 的邏輯在資料庫執行，一般的 ABAP 測試替身（test double）插不進去。CDS Test Double Framework（7.51 起）的做法是：為被測 view 所依賴的表或 view 在資料庫建立暫時的替身表，測試期間把讀取導向替身表，你只要塞入測試資料、比對 view 的輸出。

" 本地測試類別（放在任一全域類別或程式的 Test Classes 中）
CLASS ltc_sales_order_auth DEFINITION FINAL
  FOR TESTING RISK LEVEL HARMLESS DURATION SHORT.
  PRIVATE SECTION.
    CLASS-DATA go_env TYPE REF TO if_cds_test_environment.
    CLASS-METHODS class_setup.
    CLASS-METHODS class_teardown.
    METHODS setup.
    METHODS maps_header_fields FOR TESTING.
ENDCLASS.

CLASS ltc_sales_order_auth IMPLEMENTATION.
  METHOD class_setup.
    " 自動找出 ZI_SalesOrderAuth 依賴的 VBAK，建立替身
    go_env = cl_cds_test_environment=>create( i_for_entity = 'ZI_SALESORDERAUTH' ).
  ENDMETHOD.

  METHOD class_teardown.
    go_env->destroy( ).
  ENDMETHOD.

  METHOD setup.
    go_env->clear_doubles( ).       " 每個測試方法都從空資料開始
  ENDMETHOD.

  METHOD maps_header_fields.
    " Given：兩張訂單
    DATA lt_vbak TYPE STANDARD TABLE OF vbak WITH EMPTY KEY.
    lt_vbak = VALUE #(
      ( vbeln = '0000000001' auart = 'OR' vkorg = '1000' netwr = '100.00' waerk = 'TWD' )
      ( vbeln = '0000000002' auart = 'OR' vkorg = '2000' netwr = '250.00' waerk = 'TWD' ) ).
    go_env->insert( cl_cds_test_data=>create( i_data = lt_vbak ) ).

    " When：讀被測 view（略過 DCL，讓結果不受執行測試者的權限影響）
    SELECT SalesOrder, SalesOrganization, TotalNetAmount
      FROM zi_salesorderauth WITH PRIVILEGED ACCESS
      ORDER BY SalesOrder
      INTO TABLE @DATA(lt_act).

    " Then：筆數與欄位對應正確（有 ORDER BY，才能用索引 [ 2 ] 比對）
    cl_abap_unit_assert=>assert_equals( act = lines( lt_act ) exp = 2 ).
    cl_abap_unit_assert=>assert_equals( act = lt_act[ 2 ]-SalesOrganization exp = '2000' ).
  ENDMETHOD.
ENDCLASS.
  • create( i_for_entity = … )：預設替身化被測 entity 的直接依賴。
  • insert( cl_cds_test_data=>create( i_data = … ) ) 是最早（7.51）的 API；較新版本另有 insert_test_data( i_data = … ) 的簡寫。1809 兩者是否都有，未能確認，請在系統中以 F2 查看 IF_CDS_TEST_ENVIRONMENT。
  • DCL：本例在測試的 SELECT 用 WITH PRIVILEGED ACCESS 避開權限。框架本身也提供測試 DCL 的選項（官方部落格建議正式測試時在 create 關閉 DCL），參數名稱各版本不同，未能確認，請以系統為準。
斷言中取 lt_act[ 2 ] 之前一定要有 ORDER BY，否則測試會「有時過、有時不過」，這正是 HANA 沒有預設排序在測試中的表現。
出處：SAP Help（7.52）：ABAP CDS Test Double Framework；SAP Blog：Introduction to CDS Test Double Framework（7.51 起、cl_cds_test_data=>create 與 insert、clear_doubles、destroy）；SAP-samples：ABAP cheat sheet - ABAP Unit Tests（insert_test_data）。

          aspect pfcg_auth( V_VBAK_VKO, VKORG, VTWEG, SPART, actvt = '03' );
}
從 ZC 讀資料時，DCL 檢查的是 ZC 本身的 role；ZC 內部去讀 ZI 時，ZI 的 role 不會再套一次。所以每一層有 #CHECK 的 view 都要有自己的 role，否則繞過上層直接讀下層就能看到全部資料。較新版本的 DCL 另有 inheriting conditions from entity 可以沿用下層條件，1809 是否可用未能確認，本例直接重寫同樣的條件。
