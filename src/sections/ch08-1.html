3. MV45AFZZ 總覽：每個 USEREXIT 的觸發時機與限制

MV45AFZZ 是 SAPMV45A（VA01～VA03、VA21～VA23、VA41…，以及 BAPI_SALESORDER_CREATEFROMDAT2 等 BAPI）所 include 的「保留給客戶修改」的子程式集合。它是第一代增強（見 3-3 章第 6 節）：技術上屬於修改 SAP 物件，直接改要向 SAP 註冊 SSCR 物件鍵。本案例的寫法值得學：絕大部分客製都放在 FORM 結尾的隱式增強點（ENHANCEMENT … ZIM_MV45AFZZ_USEREXIT、ZSD_LGORT、ZSD_ZWLCB、ZLIFNR、ZPP_MPS、ZVA01_B…，見 3-4 章第 13 節），不需要物件鍵，升級時由 SPAU_ENH 處理；只有少數幾行（MOVE_FIELD_TO_VBAK 開頭、SAVE_DOCUMENT_PREPARE 開頭）是直接改在 FORM 本體。

MV45AFZZ 的 COMMIT 鐵律：整個 SAPMV45A 是一個 LUW，存檔時由 SAP 自己執行 COMMIT WORK。任何 USEREXIT 裡都不可以 COMMIT／ROLLBACK，也不可以呼叫內含 COMMIT 的 BAPI（例如在出口裡同步呼叫 BAPI_PR_CHANGE ＋ BAPI_TRANSACTION_COMMIT），否則訂單會「存一半」。要做後續動作，一律用 IN UPDATE TASK、IN BACKGROUND TASK（tRFC）或 bgRFC，讓它跟著 SAP 的 COMMIT 一起生效或一起取消。
S/4HANA 現況：S/4HANA（on-premise 與 private cloud）中 MV45AFZZ 等 SD User Exit 仍然被呼叫、仍可使用，這也是本案例在 S/4HANA 環境（傳輸請求編號為 S4 開頭）運作的原因。但它屬於 Clean Core 分級中最不乾淨的一層；S/4HANA 另提供給 Key User 擴充用的 Cloud BAdI（例如 SD_SLS_MODIFY_HEAD、SD_SLS_MODIFY_ITEM、SD_SLS_CHECK_HEAD 等，在 Custom Logic App 中實作），新需求若能用它們達成應優先考慮；S/4HANA Cloud Public Edition 完全不能用 MV45AFZZ。詳見 3-4 章第 17 節。另外 VBUK／VBUP 在 S/4HANA 已併入 VBAK／VBAP，出口裡若有讀取狀態表的舊寫法要一併改。

4. MV45AFZZ（一）：MOVE_FIELD_TO_VBAK／VBAP——帶預設值的正確寫法

業務情境：報價單（訂單類型 ZQT1／ZQT2）要依「客戶＋銷售組織＋訂單類型」自動算出有效截止日 BNDDT；銷售訂單項目沒填倉位時要依自建表 ZSDT024（物料＋銷售組織＋訂單類型＋訂單原因）帶出；項目要帶入年度物料成本（自建表 ZFIT019）與物料主檔上的客製欄位。

原程式的問題與改進：

  • 用 sy-tcode 判斷情境：經由 BAPI、EDI（IDoc）、或自建交易碼建立報價單時，sy-tcode 不是 VA21，預設值就不會帶。SAPMV45A 內應看 T180-TRTYP（H 新增、V 修改、A 顯示）與 VBAK-VBTYP／訂單類型。
  • 年度取 sy-datum：跨年補單、12 月 31 日建的單隔天修改，都會拿到不同年度的成本；應以單據日期 AUDAT 或定價日期為準。
  • 自建欄位命名：原程式 VBAP 附加欄位叫 ZWLCB、VBAK 附加欄位叫 ZNAME／ZAEDAT／ZADRNR，沒有依 SAP 建議用 ZZ／YY 開頭，將來 SAP 新增同名欄位時會衝突。
  • IMPORT FROM MEMORY 帶成本中心：依賴「一定有某支前置程式先 EXPORT」，使用者直接進 VA01 就拿不到；而且 ABAP Memory 在 BAPI／背景下行為不同。能改成畫面欄位或 BAPI 的 EXTENSIONIN 傳入就不要用記憶體。
  • MOVE_FIELD_TO_VBAP 裡用 READ_TEXT ＋ POPUP_TO_DISPLAY_TEXT 顯示物料注意事項：此出口每次項目變更都會跑，使用者會一直被彈窗；在 BAPI／背景處理下彈窗更會造成作業中斷。改用 MESSAGE … TYPE 'I' 只在新增項目時出一次，或乾脆用 SD 的物料注意事項（Material Info Record／銷售文字）標準功能。
HANA 沒有預設排序（Casper 經驗 1）的活教材：原程式在 MOVE_FIELD_TO_VBAP 裡從自建表 ZWMT002 抓出同一材質編碼的多筆資料，然後用迴圈找「日期最接近訂單建立日」的那筆，判斷式是 IF l_gap <= l_gap_min。當兩筆距離相同（例如前後各差 3 天），誰會被選中取決於 SELECT 回來的順序——在 HANA 上這個順序不保證穩定，同一張訂單今天和明天帶出的材質號可能不同。正確做法是 SELECT … ORDER BY 明確排序（例如距離、再加日期、再加主鍵），或把「平手時取較新日期」寫成規則。

上線注意：MOVE_FIELD_TO_* 系列在一次交易中會被呼叫很多次，裡面的 SELECT 請確認有用到主鍵或索引，必要時用全域內表緩衝（例如在 SAVE_DOCUMENT 清除）。自建表 ZSDT024／ZSDT033 請開 SM30 維護畫面並設權限群組。

5. MV45AFZZ（二）：PRICING_PREPARE_TKOMK／TKOMP——定價出口只負責「準備資料」

業務情境：某個海外銷售組織要依「客戶在兩家快遞承運商是否有自己的帳號」「出貨方式 VSART」「客戶群組 KVGR1」決定是否收取運費條件（原程式條件類型 ZMU3）；另外特定訂單類型＋項目類別組合才收運費，其餘一律歸零。表頭另外要把客戶群組 KVGR2、以及某夥伴功能（1D）的客戶放進 TKOMK，供存取順序使用。

原程式的做法：TKOMK 的部分寫法正確（只填 TKOMK 欄位）。TKOMP 的部分則是直接 LOOP AT xkomv WHERE kschl = 'ZMU3' … xkomv-kbetr = '0'. MODIFY xkomv.——在「準備定價資料」的出口裡改定價「結果」。

這有三個問題：① 定價之後若重新定價（例如改數量、按「更新定價」），出口不一定再跑到同一個時點，金額可能又回來；② 條件歸零但條件仍然存在，條件值 0 與「不適用」在帳務、報表上意義不同；③ 判斷邏輯寫死 16 個訂單類型／項目類別組合與 15 個出貨方式代碼，業務一新增就要改程式。正確分工是：出口只把「判斷依據」放進通訊結構，是否適用交給條件需求常式（VOFM）。

原程式的問題與改進：

  • 旗標沒有逐項重算：原程式在迴圈外建立 ls_zsdt016，迴圈內只在「有內部訂單」時把 AUFNR 旗標設成 X，從不清除；第一個項目有內部訂單，後面所有項目都會被當成有。這是很典型、測試時不容易發現的 bug。
  • 兩個銷售組織的邏輯各複製一份（一段給 1000／1001、一段給 1010，後者多了「查不到就依計畫行類別從 TVEP 取」），應抽成一個方法、差異放進設定。
  • xvbak 可能是空的：原程式註解「只修改條件時此為空」，所以先判斷 xvbak 是否初始、再退回 yvbak。這個觀察是對的：XVBAK 在只改定價的情境下不一定有值，讀表頭請以 VBAK 工作區為準。
  • 移動類型本來是標準設定：計畫行類別決定移動類型（VOV6），計畫行類別由項目類別＋MRP 類型決定（VOV5）。本案例需要「成本中心／內部訂單」兩個維度，標準沒有，才走到出口；這種「在儲存前覆寫標準決定結果」的出口，務必在文件中寫清楚，否則顧問查設定會一直對不上。
在 SAVE_DOCUMENT_PREPARE 同步呼叫外部 API 的風險：原程式在這裡組出貨地址、稅務分類、每個項目金額與運費行，再呼叫 Z 函數同步呼叫外部稅務計算服務，回來後改寫稅額條件 ZMU2／ZMU7 與表頭返利稅 ZMR1。問題是：① 外部服務慢或斷線，使用者存檔就卡住；② 使用者存檔被後續檢查擋下再存一次，外部系統會收到重複交易；③ 呼叫發生在 COMMIT 之前，外部系統已記錄交易、SAP 卻可能回滾。較穩健的做法是：定價時用 SAP 標準的外部稅務介面（稅務管轄碼＋外部稅務系統整合）取得稅額，「交易確認」則在 COMMIT 之後以 bgRFC／事件送出。金鑰、端點一律放在 SM59 目的地與 STRUST，不寫在程式裡（見 4-1 章）。

7. MV45AFZZ（四）：SAVE_DOCUMENT 的後續動作與「呼叫標準內部 FORM」的禁區

業務情境 A：第三方訂單（訂單類型 ZTPS）存檔時，要把訂單表頭上的自建欄位「指定供應商」寫到系統自動產生的請購單上（固定供應商 FIXED_VEND）。情境 B：特定訂單類型、沒有交貨凍結時，把項目清單丟給一支 Z 函數觸發生產排程（MPS）。

原程式：情境 A 用 CALL FUNCTION 'BAPI_PR_CHANGE' IN BACKGROUND TASK，請購項目號碼自己用 10、20、30 往上加；情境 B 用 CALL FUNCTION 'ZPPFM001' STARTING NEW TASK。

* ---- FORM USEREXIT_SAVE_DOCUMENT：此時已給號，COMMIT 尚未發生 ----
IF vbak-auart = 'ZTPS' AND vbak-zzlifnr IS NOT INITIAL.
  DATA lt_pritem  TYPE STANDARD TABLE OF bapimereqitemimp WITH EMPTY KEY.
  DATA lt_pritemx TYPE STANDARD TABLE OF bapimereqitemx   WITH EMPTY KEY.

  " 請購項目號碼以計畫行上的實際 BANFN/BNFPO 為準，不要自己 10、20、30 往上算

       WHERE banfn IS NOT INITIAL AND bnfpo IS NOT INITIAL AND updkz <> 'D'.

    lt_pritemx = VALUE #( BASE lt_pritemx ( preq_item = ls_ep-bnfpo fixed_vend = abap_true ) ).

            iv_banfn   = lv_banfn
            it_pritem  = lt_pritem

* Z_SD_PR_SET_FIXED_VENDOR 內：先 ENQUEUE 等待請購單鎖釋放，再呼叫 BAPI_PR_CHANGE，
* 依 RETURN 決定 BAPI_TRANSACTION_COMMIT 或 ROLLBACK，錯誤寫應用日誌（SLG1）。

原程式的問題與改進：

  • IN BACKGROUND TASK（tRFC）本身沒錯，它確實會在 SAP 的 COMMIT 後才送出；但 tRFC 啟動時，訂單的更新工作可能還沒寫完，請購單仍被鎖，BAPI 就會失敗並停在 SM58。包一層 Z 函數處理鎖等待與錯誤記錄，並在 S/4HANA 改用 bgRFC（SBGRFCMON 監控）。
  • 請購項目號碼自己算：假設請購項目恰好是 10、20、30 對應訂單每一個項目，遇到非第三方項目、已刪除項目或請購單項目號碼規則不同就錯位。
  • STARTING NEW TASK 是 aRFC，立刻在另一個工作階段執行，不受本 LUW 控制：訂單可能還沒寫進資料庫，Z 函數讀不到；訂單存檔失敗回滾時，排程卻已觸發。要改成 IN UPDATE TASK 或 bgRFC。
  • SAVE_DOCUMENT 裡的 MESSAGE i001（提醒「這是預收款訂單」）在 BAPI／背景下沒有意義，建議移到 SAVE_DOCUMENT_PREPARE 並加上「是否在對話模式」判斷（例如 sy-binpt、sy-batch 與呼叫來源）。
禁區：在出口裡呼叫 SAPMV45A 的內部 FORM。原程式 MOVE_FIELD_TO_VBAK 中有一段「項目換算拆分」：對未交貨的項目呼叫 Z 函數算出替代物料與數量，然後直接呼叫標準程式 SAPFV45P／SAPFV45E 內部的十餘個子程式（刪除項目、建立項目、檢查物料、檢查項目類別、填計畫行⋯），模擬使用者在畫面上刪一行、加數行。這在技術上能動，但：① 這些內部子程式不是公開介面，任何支援包都可能改參數或行為；② 在 VBAK 出口裡新增、刪除項目，會與 SAPMV45A 自身的項目迴圈互相干擾，極易產生不一致；③ BAPI 建單時同一段也會被執行。正解通常是：以 BOM／物料決定（VB11）／產品替代等標準功能處理，或在訂單存檔後以 BAPI_SALESORDER_CHANGE 另外調整。本書不提供此段的改寫範例，因為它本身就不該存在。
原程式在 VBAK 出口還有一段：讀客戶 BP 的聯絡地址（BUT020 ＋ ADR6 ＋ ADRT，以地址備註 'ORD' 篩選），把所有訂單通知 email 串起來用 MESSAGE s002 顯示在狀態列。思路（用 BP 地址用途／備註分類聯絡人）可以參考；但每次 PAI 都查一次，且 email 屬個人資料，不宜在狀態列顯示。

原程式的問題與改進：

練習與自我檢核

  1. MV45AFZZ 中哪兩個 FORM 最適合做「儲存前檢查」與「儲存後通知外部系統的登記」？各自能不能 COMMIT？
    參考答案：檢查用 USEREXIT_SAVE_DOCUMENT_PREPARE（還能以 E 訊息擋下並改 XVBAK／XVBAP）；登記後續動作用 USEREXIT_SAVE_DOCUMENT（已給號，用 IN UPDATE TASK 或 bgRFC）。兩者都不能 COMMIT，由 SAPMV45A 統一 COMMIT。
  2. 為什麼原程式用 sy-tcode = 'VA21' 判斷報價單建立是不可靠的？應改看什麼？

  3. 在 PRICING_PREPARE_TKOMP 把 XKOMV 某條件金額改成 0，和用 VOFM 需求常式讓條件不適用，差在哪裡？

  6. 清除 LIKP-VLSTK 讓交貨可以沖銷，這種做法有什麼風險？正確方向為何？
    參考答案：VLSTK 是分散式倉儲的分配狀態，清掉等於抹除「已分配給外部倉儲」的事實，可能造成 SAP 與外部倉儲不一致；應檢討為何這些交貨被標記為需分配（倉庫號碼／交貨類型設定），而非每次變更都清狀態。
  7. AC_DOCUMENT 的 CHANGE_INITIAL 中，為什麼要先 CORRESPONDING 整行再改 SGTXT？「讀下一行」的寫法錯在哪？
