2. 業務情境與整體架構：一支程式、三種入口

業務情境：某醫療器材公司的美國子公司，客服（Customer Care）開報價單與訂單、會計開發票。客戶多是醫院與診所，要的是「一收到單據 PDF 就能在信裡點連結線上付款」。於是 IT 做了兩支程式，讓同一份資料可以從三個方向被觸發：

標準函數它做了什麼（依原始碼）實務意義
SSF_FUNCTION_MODULE_NAME① 查 STXFADM 確認表單存在（否則 NO_FORM）② 查 STXFPCUST：若該 SmartForm 被設定為改用 Adobe（TYPE = 'FP'），改呼叫 FP_FUNCTION_MODULE_NAME 回傳 Adobe 表單的函數名 ③ 查 STXFADMI 取函數編號，比對內部版本、STXFVARI 的產生 release 與系統 ID、D010SINF 的產生時間，任一不符就呼叫 FB_GENERATE_FORM 重新產生 ④ 組出 /1BCDWB/SF0000xxxx 函數名函數名在每個系統都不同，絕不可寫死；表單傳輸到新系統後第一次呼叫會自動重新產生，所以第一次會比較慢。STXFPCUST 是「SmartForm 不改程式、切換成 Adobe Form」的鉤子

11. 寄送記錄 ZSDT019 與「最後一次寄送」的讀法

ZSDF002 寄信成功後寫 ZSDT019（CRDAT、CRTIM、VBELN、CRNAM），ALV 上的「郵件寄送日期」就是從這裡讀：先 SORT gt_zsdt019 BY vbeln crdat DESCENDING，再 READ TABLE … WITH KEY vbeln（沒有 BINARY SEARCH）取第一筆。ZFIT002 也用同樣手法：SORT BY vbeln crdat DESCENDING crtim DESCENDING 後 READ TABLE 取「最新」的 PayPal 記錄。

這種「靠 SORT 讓 READ TABLE 剛好讀到最新一筆」的寫法能動，但意圖隱藏在兩行程式的組合裡，後人只要把 SORT 改成 BY vbeln、或加上 BINARY SEARCH，就會悄悄讀到任意一筆。把「取最大值」交給資料庫的 GROUP BY / MAX 才是明確的寫法。

" ZSDT019 寄送記錄：原表 key 是 (CRDAT, CRTIM, VBELN)，VBELN 卻套了「交貨單」資料元素 VBELN_VL
" 建議新表 ZSDT019N：key = MANDT + VBELN(VBELN_VF) + SENT_AT(TIMESTAMPL)，並加 CHANNEL / RECIPIENTS
METHOD write_send_log.
  GET TIME STAMP FIELD DATA(lv_ts).
  DATA(lt_log) = VALUE zsdt019n_tab(
                   FOR d IN it_sent
                   ( vbeln      = d-vbeln
                     sent_at    = lv_ts
                     channel    = 'MAIL'
                     recipients = concat_lines_of( table = d-to sep = `;` )
                     sent_by    = sy-uname ) ).
  IF lt_log IS NOT INITIAL.
    INSERT zsdt019n FROM TABLE @lt_log ACCEPTING DUPLICATE KEYS.
  ENDIF.
ENDMETHOD.

" 讀「最後一次寄送時間」：不要依賴先 SORT 再 READ TABLE 的隱性順序
SELECT FROM zsdt019n
  FIELDS vbeln, MAX( sent_at ) AS last_sent
  WHERE vbeln IN @lt_vbeln_range
  GROUP BY vbeln
  INTO TABLE @DATA(lt_last_sent).
原表的 key 設計也值得檢討：① VBELN 用了交貨單的資料元素 VBELN_VL，F1 說明與搜尋說明都會錯 ② 同一秒寄兩次同一張發票會主鍵衝突，MODIFY 會把前一筆蓋掉 ③ 沒有記錄寄給誰，客戶說「沒收到」時無從查起。SOST 雖然有 BCS 的寄送記錄，但無法直接用發票號查詢，所以自建記錄表是合理的，只是欄位要設計完整。

業務情境：客戶收到訂單確認或發票 PDF 時，信裡同時附「View & Pay」按鈕，點進 PayPal 的線上帳單頁以信用卡或 ACH 付款；ZFIT002 保留了 BELNR / GJAHR / BUKRS 欄位，推測收款後由另一支程式過帳並清帳。這兩支程式只負責三件事：建立草稿並寄出連結、取消、刪除，實際呼叫 PayPal API 的是自建函數：

  3. 背景 JOB 用變式＋動態日期：與其在程式裡改 s_audat，不如在變式中用「動態日期計算」（例如 current date − 1），讓 JOB 行為看得見、可調整。
  4. PayPal 沙箱與正式分離：SM59 目的地在各系統指向不同端點；傳輸只帶目的地名稱，不帶秘密。第一次上線先用「只建草稿不寄出」的模式跑一週，再開放寄送。
  5. 表單傳輸：SmartForm、SmartStyle、SE78 圖檔、SO10 文字要一起傳；到新系統第一次呼叫會重新產生函數（第 8 節）。
  6. 條件用列舉：訂單類型、條件類型、發票類型原程式都用 IN 列舉，這是對的；背景日期也應是 EQ 單日，不要用 BT 區間（Casper 經驗 #2）。

練習與自我檢核

  1. NACE 入口為什麼仍要寫 FORM？新程式要怎麼把它的影響範圍降到最小？
    要點：RSNAST00 以 PERFORM (TNAPR-RONAM) IN PROGRAM (TNAPR-PGNAM) 呼叫，並透過 RVADTABL 的共用工作區傳 NAST、TNAPR；FORM 只留兩三行，立刻呼叫類別方法，錯誤以 NAST_PROTOCOL_UPDATE 記錄並回傳 return_code。
  2. 找出 ZSDF001 背景 JOB 的日期 bug，說明它在正式機會造成什麼後果，並寫出修正版。
    要點：先取數後改 s_audat → 日期條件無效；可能大量重寄；修正為先算當地日期、以 EQ 設定範圍再取數，或改用變式動態日期。
  3. USER_SETTINGS = 'X' 對 OUTPUT_OPTIONS 有什麼影響？
    要點：SSF_CREATE_COMPOSER_INPUT 會把 TDDEST、TDIMMED、TDDELETE 改成 '*'，改用使用者預設值，程式指定的印表機被忽略；要用程式值必須傳 space。
  4. SSF_FUNCTION_MODULE_NAME 在什麼情況下會重新產生函數？STXFPCUST 有什麼用途？
    要點：從未產生、內部版本不同、產生時的 release 或系統 ID 不同（傳輸）、表單修改時間晚於函數產生時間；STXFPCUST 可把 SmartForm 名稱導向 Adobe 表單（TYPE = 'FP'）。
  5. 比較 Spool 轉 PDF 與 GETOTF 轉 PDF，各適合什麼情境？
    要點：Spool 路線留下 Spool、需權限，但可一次產生兩用；GETOTF 無副作用，適合純寄信。
  6. 為什麼從 VBPA-ADRNR 取地址比從 KNA1-ADRNR 正確？JOIN ADRC 還要注意哪個欄位？
    要點：單據上手動改過的地址存在 VBPA-ADRNR；ADRC 的 key 含 NATION（國際版本）與 DATE_FROM，未限定可能一筆變多筆。
  7. 指出下列判斷式的錯誤：IF gs_auart-auart = 'ZEVU' OR gs_auart = 'ZDEU'、IF a = 'X' OR b = 'Y' AND c <> 0。
    要點：第一個拿整個結構比字串，比到的是第一個欄位；第二個 AND 先於 OR，應加括號表達原意。
  8. 設計 ZFIT002 的狀態轉移：哪些狀態可以刪除？刪除 S 狀態為什麼要兩步？
    要點：N、C 直接刪；S 已寄給客戶，須先 cancel 讓客戶端連結失效再 delete；P、G 已收款不可刪。
  9. PayPal 的 client secret 應該放在哪裡？列出至少兩種做法與不能放的地方。
    要點：SM59 目的地登入資料（SECSTORE）、OA2C_CONFIG、SSF 安全儲存；不可寫在程式常數、自建明文表、選擇畫面預設值或傳輸請求。
  10. 業務員 email 取自 ADR6，同一人有兩個 email 時會發生什麼？與 Casper 的哪條經驗相關？
    要點：沒有排序或預設旗標，HANA 回傳順序不固定，寄給誰不穩定——HANA 沒有預設排序；應以 FLGDEFAULT 或 ORDER BY 明確指定。
  11. ZSDT019 的欄位設計有哪些問題？請設計一張新的寄送記錄表。
    要點：VBELN 用錯資料元素（VBELN_VL）、同秒重寄主鍵衝突、沒有收件人與管道欄位；新表 key 用 VBELN_VF＋TIMESTAMPL，加 CHANNEL、RECIPIENTS、SENT_BY。
  12. S/4HANA 新專案要不要照抄這兩支程式？請依「先標準再客製」的順序說明評估步驟。
    要點：先評估 Output Management（BRFplus／OPD／Adobe／Email Template）與 SAP Digital Payments；不足處再用 BAdI 或輸出管理的擴充點補；最後才考慮完全客製的清單＋寄信程式。
