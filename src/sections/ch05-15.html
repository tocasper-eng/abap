2. 第一單元：增強的基本概念與傳統增強技術

增強（Enhancement）的定義：SAP 在標準程式中預留（或系統自動提供）一個「跳到客戶程式碼」的位置，讓客戶補充或替代功能，而不需要修改（Modification）SAP 物件。强晟筆記把傳統（NW 7.0 以前）技術分成三類出口：

出口類型作用可用技術可否多重使用
程式出口（Program Exit）從 SAP 程式跳到客戶原始碼，補充或替代功能副程式（User Exit，USEREXIT_* FORM）、函數模組（Customer Exit，EXIT_<程式>_nnn）、函數模組（BTE，Business Transaction Events）、方法（BAdI）BTE、BAdI 可定義為多重使用
選單出口（Menu Exit）在 SAP 畫面加一個執行客戶功能的選單項目Customer Exit、BAdI只能使用一次
畫面出口（Screen Exit）在 SAP 畫面加客戶欄位（SAP 欄位與客戶追加欄位皆可顯示）Customer Exit、BAdI只能使用一次

為什麼會有這麼多種技術？（p8）這是 SAP 增強方法不斷演進的結果：

  • User Exit → Customer Exit：為了模組化，並加入新的增強型態（選單出口、畫面出口）。
  • BTE：用於財務（FI），實現程式出口的多重使用（交易碼 FIBF）。
  • BAdI：物件導向的模組化，綜合前面各種技術的優點。

多重使用的出口在執行時可能有多個啟用中的實作，依序（輪流）被處理——而且順序不保證，這一點到了 Enhancement Point 也一樣（第 5 節）。

User Exit、Customer Exit（SMOD／CMOD）、BTE 的操作細節請看 3-3 章 User Exit 與 Customer Exit；本章聚焦 NW 7.0 之後的新框架。選技術時請記得 Casper 的第三條實務經驗：先找標準設定 → 再找 BAdI／Enhancement Spot → 再考慮 Enhancement Point → 最後才是修改標準，每往右一步，升級成本高一個量級。

3. Enhancement Framework 全貌：點、選項、段與 Enhancement Spot

NW 7.0 的 Enhancement Framework 把下列五種東西放在同一個管理架構下（p9）：

增強元素顯式／隱式誰提供用途
隱式增強點（Implicit Enhancement Point）隱式系統自動存在，SAP 開發者不必預設在程式、函數、方法、副程式、Include 的特定位置（多半是開頭／結尾）插入原始碼
隱式增強選項（Implicit Enhancement Option）永遠是隱式系統自動存在替函數模組與方法加可選參數、替類別加屬性與方法、pre/post/overwrite 方法
顯式增強點（Explicit Enhancement Point）顯式SAP 開發者以 ENHANCEMENT-POINT 預留在指定位置補充程式碼
顯式增強段（Explicit Enhancement Section）永遠是顯式SAP 開發者以 ENHANCEMENT-SECTION … END-ENHANCEMENT-SECTION 標出整段替換 SAP 原始碼
New BAdI顯式SAP 開發者在 Enhancement Spot 中定義物件導向的程式／選單／畫面出口
Classic BAdI顯式SE18 舊定義由框架「一起管理」，但不屬於任何 Enhancement Spot

Enhancement Spot（增強場所）是 Repository 物件，把顯式增強點、顯式增強段與 New BAdI 收在一起管理；Composite Enhancement Spot（集合增強場所）則由簡單 Spot 和／或其他集合 Spot 組成，提供語意上的綁定，方便全域搜尋。實作端也對稱：

  • Enhancement Implementation（增強實作）：客戶要用任何增強元素（顯式點、段、New BAdI、隱式增強）都必須先建立它。通常同一個 Spot 的所有點與段放在同一個增強實作裡，系統會自動編號（ENHANCEMENT 1、ENHANCEMENT 2…）。
  • Composite Enhancement Implementation：把多個簡單增強實作語意分組。不需要因為 Spot 屬於集合 Spot 就建立集合實作；反過來，不屬於任何集合 Spot 的實作也可以被放進集合實作。
  • Spot 與實作是 m:n：一個 Spot 的點可以被多個增強實作實作；一個增強實作也可以涵蓋一個或多個 Spot 的點。
BC425 的例子：集合 Spot ESC_CK_ECP 由 6 個簡單 Spot 組成。實務上，一支程式所有顯式增強所屬的 Spot 常命名為 ES_<SAP 程式名>，例如 ES_SAPMV45A。顯式增強點與段無法全域搜尋，只能搜尋它們所屬的 Spot：SE84 → Enhancements → Enhancement Spots，或用 Enhancement Browser SPAU_ENH。

集合增強實作的典型用法（BC425 p247）：你用隱式增強替某個標準 FM 加了參數並補了程式碼，又在呼叫這支 FM 的標準程式裡，用顯式增強段替換呼叫方式——兩個增強實作在語意上是一組，就用一個 Composite Enhancement Implementation 綁在一起，日後找得到、傳輸也不會漏。

4. 第二單元：ABAP 字典的增強——Extension Index 與 Fixed Value Append

NW 7.0 之前，下面兩件事即使用客戶命名空間也算修改；NW 7.0 起變成免修改的增強，升級時自動帶過、不需要修改調整（SPDD）。

項目Extension Index（擴充索引）Fixed Value Append（固定值追加）
解決什麼替 SAP 標準表建立次要索引，加快讀取替 SAP 標準 Domain 追加固定值，讓 F4 多出選項
操作SE11 顯示表 → 應用工具列 Indexes → ALV 工具列「建立」→ 選 Create Extension Index → 定義欄位 → 啟用SE11 顯示 Domain → Goto → Fixed Value Append → 輸入追加名稱（客戶命名空間）→ 短文 → Value Range 頁籤輸入值（可按 Show Domain Values 看原值）→ 存檔啟用
限制仍要評估寫入成本一個 Append 只能掛在一個 Domain；一個 Domain 可以有多個 Append
傳輸獨立物件在 Domain 原始系統以外的系統建立，屬於獨立的傳輸物件；在 Repository 資訊系統搜 Domain 時會和一般 Domain 一起出現
別把 Fixed Value Append 和 Append Structure 搞混：前者加「值」到 Domain，後者加「欄位」到表或結構（見 1-2 章、5-16 章 BC430）。
S/4HANA 的 HANA 是記憶體欄式資料庫，大多數查詢不需要次要索引，SAP 甚至在 S/4 轉換時刪掉了許多舊索引。要建 Extension Index 前，先用 ST05／SQL Monitor 證明瓶頸真的在索引（見 5-21 章 BC490）。

程式裡讀取 Domain 固定值時，追加的值會和原固定值一起回傳。下列寫法用 RTTS 讀出資料元素 KOART（科目類型）所屬 Domain 的所有固定值，適合做自訂下拉選單或檢核：

*&-------------------------------------------------------------*
*& 讀 Domain 固定值（含 Fixed Value Append）——RTTS 寫法
*&-------------------------------------------------------------*
DATA(lo_elem) = CAST cl_abap_elemdescr(
                  cl_abap_typedescr=>describe_by_name( 'KOART' ) ).

lo_elem->get_ddic_fixed_values(
  EXPORTING  p_langu        = sy-langu
  RECEIVING  p_fixed_values = DATA(lt_fixval)
  EXCEPTIONS not_found      = 1
             no_ddic_type   = 2
             OTHERS         = 3 ).
IF sy-subrc <> 0.
  MESSAGE |資料元素 KOART 沒有固定值（subrc={ sy-subrc }）| TYPE 'I'.
  RETURN.
ENDIF.

" 檢核使用者輸入是否為合法值：用 line_exists，不要自己寫迴圈
DATA(lv_input) = CONV koart( 'K' ).
IF NOT line_exists( lt_fixval[ low = lv_input ] ).
  MESSAGE |科目類型 { lv_input } 不在固定值清單內| TYPE 'E'.
ENDIF.

" 組成「值 - 說明」清單（HANA 沒有預設排序，要自己排）
SORT lt_fixval BY low.
DATA(lt_text) = VALUE string_table(
                  FOR ls_fv IN lt_fixval ( |{ ls_fv-low } - { ls_fv-ddtext }| ) ).
cl_demo_output=>display( lt_text ).
固定值本身存在 DD07L（值）與 DD07T（多語說明）；用 RTTS 讀取比直接 SELECT 這兩張表安全，因為它會處理啟用版本與語言回退。

5. 第三單元（一）：顯式增強點與增強段

顯式增強點用 ENHANCEMENT-POINT 標記，讓客戶在該處補充程式碼；顯式增強段用 ENHANCEMENT-SECTION … END-ENHANCEMENT-SECTION 包住一段 SAP 程式碼，讓客戶整段替換。兩者都一定嵌在 Enhancement Spot 裡，可用在動態（可執行）程式碼，也可用在靜態宣告。

附加語法意義
SPOTS spot1 spot2 …指定所屬的 Enhancement Spot（必填）
STATIC用於增強資料宣告（DATA、TYPES、CONSTANTS…）；不加就是增強可執行程式碼（dynamic）
INCLUDE BOUND增強定義在一支會被多個主程式引用的 Include 中，而且希望實作對所有引用它的程式都生效時使用。不加的話，原始碼增強只歸屬一個編譯單元（compilation unit），要在 Enhancement Builder 指定是哪一支主程式
  • 一支 Include 不能同時有 include-bound 與非 include-bound 的增強（它再引用其他 Include 時也一樣）。
  • 一支 Include 若在同一主程式中被引用多次，只允許 include-bound 的原始碼增強。
  • 夥伴或客戶想替自己的程式提供顯式增強，要在修改模式下用編輯器的專用選單建立，不要手打 ENHANCEMENT-POINT 敘述（手打的不會登記到 Spot）。

建立顯式增強實作的步驟（强晟 p18、BC425 p221）：

  1. 顯示 SAP 物件（程式、函數模組、方法）。
  2. 用「編輯 → 搜尋／取代」找 ENHANCEMENT-POINT 或 ENHANCEMENT-SECTION。
  3. 按應用工具列的增強（Enhance，螺旋圖示）按鈕進入增強模式。
  4. 游標放在增強點／段上，右鍵選 Create Enhancement Implementation。
  5. 輸入增強實作名稱（客戶命名空間 Y*／Z*）與套件、傳輸請求。
  6. 在 ENHANCEMENT … ENDENHANCEMENT 之間輸入程式碼。
  7. 按 Activate Enhancements（不是一般的啟用按鈕）。
多重實作的風險（BC425 p221～p223）：
① 增強點可以有多個啟用中的實作，但執行順序不保證。因此不同實作之間不能有相依，更不能同時改同一個變數——這和 Casper 提醒的「HANA 沒有預設排序」是同一類陷阱：只要依賴「剛好先執行到誰」，結果就會不穩定。
② 增強段在執行時只會執行一個實作；若有多個啟用實作，系統不會 Dump，只給語法警告，而你無法確定會跑哪一個。要控制就得用 Switch Framework 的衝突開關（第 15 節）。
除錯時看不到增強實作的程式碼，因為它放在獨立的軟體層（和修改助理 Modification Assistant 一樣）。Debugger 停在增強點或增強段時，按 F5（單步）才會進入增強實作。其他除錯技巧見 5-4 章 BC403。

6. 第三單元（二）：函數模組的隱式增強

隱式增強不需要 SAP 開發者預先準備，NW 7.0 以前建立的 SAP 物件也有。函數模組提供兩種：

種類內容限制
隱式增強選項：增強介面新增 IMPORTING／EXPORTING／CHANGING／TABLES 參數新增參數一律為可選（optional）；不能新增 EXCEPTIONS
隱式增強點：增強原始碼在函數原始碼的開頭與結尾插入程式只有開頭與結尾兩處，中間要插只能靠 SAP 預留的顯式點

增強介面步驟（p20）：SE37 顯示函數 → 選單 Function Module → Enhance Interface → 指定（或建立）增強實作 → 在對應頁籤加入新參數與型別 → Activate Enhancements。啟用後，每個新參數旁都會顯示增強實作名稱，一眼分得出哪些是標準參數。

增強原始碼步驟（p21）：顯示原始碼 → 按增強按鈕 → Edit → Enhancement Operations → Show Implicit Enhancement Options（編輯器中會出現一排雙引號 """""" 標示位置）→ 在該行右鍵 Create Enhancement Implementation → 輸入程式 → Activate Enhancements。

7. 第三單元（三）：全域類別的隱式增強與 pre／post／overwrite 方法

全域類別（SE24）可以做的隱式增強：

  • 增強選項：替方法加可選參數（IMPORTING、EXPORTING、CHANGING，不能加 RETURNING 與例外）；新增 public／protected／private 屬性與方法；替某個 SAP 方法定義 pre-method、post-method，或以 overwrite-method 取代。
  • 增強點：在方法開頭與結尾加入程式（可使用上面新增的參數、屬性、方法）；實作新增的方法。

增加屬性／方法／參數（p22）：SE24 顯示類別 → 選單 Class → Enhance 建立增強實作 → 加入新屬性、方法、參數 → 雙擊新方法名稱進入方法編輯器寫程式 → Activate Enhancements。

定義 pre／post／overwrite 方法（p23～p24）：SE24 顯示類別 → Class → Enhance → 游標標記 SAP 方法 → Edit → Enhancement Operations → 選 Insert Pre-Method／Insert Post-Method／Add Overwrite Method → 在「Pre-／Post-／Overwrite-Exit」欄按新建按鈕實作 → 存檔 → Activate Enhancements。

規則說明
數量每個 SAP 方法可以有一個 pre + 一個 post，或一個 overwrite；有 overwrite 時不能再有 pre／post
生成物系統自動產生本地類別 LCL_<增強名>，附在原類別本地類別實作區的最後；它實作介面 IPR_<增強名>（pre）、IPO_<增強名>（post）、IOW_<增強名>（overwrite）
存取原物件透過實例屬性 CORE_OBJECT（在本地建構子中填入），它指向應用程式中目前正在使用的那個 SAP 類別實例
參數差異pre-method 沒有 EXPORTING；post-method 也沒有 EXPORTING，原方法的 EXPORTING 在 post 中變成 CHANGING；功能方法的 RETURNING 也變成 CHANGING
中斷鏈pre-method 丟出例外 → 原方法與 post 都不執行；原方法丟出例外 → post 不執行

兩條硬規則（p28）：
① 在結構宣告 END OF 之前做增強，必須寫成 DATA: 欄位1 TYPE 型別1, 欄位2 TYPE 型別2.——要有 DATA 與結尾句點，且只能用 TYPE；不能用 LIKE <dbtab-field> 或 INCLUDE STRUCTURE。
② 隱式增強點不適用於 SAP Basis 核心物件。强晟的解讀是「D 開頭的字典表與視圖、S 開頭的交易碼與程式等處理底層的元素」——這是他的推測，原廠只寫「SAP Basis objects」，實際判斷以系統是否顯示隱式增強選項為準。另外强晟寫「隱式增強點和段」，但依定義增強段永遠是顯式的，這裡應理解為「隱式增強點與選項」。

升級時（SAP 重新交付被增強的程式），增強實作雖然免修改，但仍要把它們「放回」程式中，也就是增強調整（第 16 節）。

9. 第四單元（一）：Classic BAdI 架構與呼叫語法

在 SE18 定義 Classic BAdI 並指定 BAdI 介面時，系統自動產生適配器類別（Adapter Class，CL_EX_<BAdI 名>）與對應的橋接方法（Bridge Method）。SAP 應用程式呼叫橋接方法，而橋接方法唯一的任務，就是依序呼叫行業解決方案（IS）、合作夥伴、客戶已啟用的實作——順序無法指定。

呼叫語法：宣告一個型別為 BAdI 介面的參照變數，以 CL_EXITHANDLER=>GET_INSTANCE 建立適配器類別實例（BAdI 實例），再呼叫橋接方法：

*&-------------------------------------------------------------*
*& Classic BAdI 呼叫（讀懂舊標準程式用；新程式請定義 New BAdI）
*& 參照變數型別是「BAdI 介面」，不是 BAdI 名稱
*&-------------------------------------------------------------*
DATA lo_exit TYPE REF TO zif_ex_bc427_classic.     "IF_EX_<BAdI> 介面

CALL METHOD cl_exithandler=>get_instance
  EXPORTING
    exit_name              = 'ZBC427_CLASSIC'
    null_instance_accepted = abap_true      "沒有實作時回傳 INITIAL
  CHANGING
    instance               = lo_exit
  EXCEPTIONS
    OTHERS                 = 1.

IF sy-subrc = 0 AND lo_exit IS BOUND.
  " 呼叫橋接方法 → 依序執行 IS／夥伴／客戶的啟用實作
  lo_exit->check_item( EXPORTING is_item = ls_item
                       CHANGING  ct_msg  = lt_msg ).

找 Classic BAdI 的方法（p34）：自由搜尋用 SE84；依應用元件用 SE81 → SE84；依程式：① 在程式中全域搜尋 GET_INSTANCE；② 雙擊參照變數找到宣告；③ 雙擊 BAdI 介面；④ 在類別 CL_EX_<BAdI 名> 用「使用處清單（Where-Used List）」；⑤ 在 SE18 讀 BAdI 文件。

實作 Classic BAdI（p35）：顯示 BAdI 定義 → Implementation → Create（或直接用 SE19）→ 指定實作名稱 → 雙擊實作類別的方法寫程式 → 啟用方法與實作類別 → 啟用 BAdI 實作。完整操作與實戰（BADI_MATERIAL_CHECK、ME_PROCESS_PO_CUST）見 3-4 章。

Classic BAdI 是 R/3 4.6 的技術，SAP 從 NW 7.0 起只會用 New BAdI 提供新增強；系統裡仍有大量 Classic BAdI 出口，所以要看得懂，但自己不要再定義新的 Classic BAdI。已存在的自訂 Classic BAdI 可在 SE18 遷移成 New BAdI（第 16 節）。另外，Classic BAdI 本身不可被 Switch Framework 切換（第 15 節有變通方法）。

10. 第四單元（二）：New BAdI——GET BADI／CALL BADI、例外與實作

為什麼要 New BAdI（p30、BC425 p176～p178）：① 提升效能；② 附加功能——增強的過濾器概念、可從範例實作類別繼承（只重新定義需要的方法）、Context 等；③ 整合進 Enhancement Framework，New BAdI 一定屬於某個 Enhancement Spot 並由它管理，而且可被切換（switchable）。

架構差異：New BAdI 不再產生適配器類別，應用程式不必實例化它；執行時由核心（kernel）產生 BAdI 句柄（BAdI Handle），功能等同適配器類別，但呼叫實作方法時更有效率。語法上，參照變數的型別是 BAdI 名稱本身，而不是 BAdI 介面。

  CATCH cx_badi_filter_error.         "過濾值型別不符等

② ENDTRY 是一個字，筆記寫成 END TRY；

找 New BAdI 的方法（p39、BC425 p181～p182）：SE84 自由搜尋 BAdI 或 Spot；SE81 → SE84 依應用元件；依程式：① 全域搜尋 GET BADI（或 CALL BADI）；② 雙擊參照變數找宣告；③ 雙擊 BAdI 名稱跳到所屬 Enhancement Spot。標準程式呼叫的 FM 與方法內也可能有，必要時一併搜尋；也可以在 Debugger 對 GET BADI 敘述設中斷點（Breakpoint at Statement）直接攔。

實作 New BAdI（p40、BC425 p183）：

  1. 顯示對應的 Enhancement Spot（SE18）。
  2. 選 Implement Enhancement Spot（F6），建立增強實作（SE19 也可以）。
  3. 指定增強實作名稱、BAdI 實作名稱與實作類別名稱；若 BAdI 有 Sample Class，可選擇繼承或複製。
  4. 維護 BAdI 實作屬性（過濾值、是否為 Default Implementation）。
  5. 在該 BAdI 的導覽區選「Implementing Class」，雙擊方法實作或調整。
  6. 啟用方法與所有相關物件，包含增強實作本身。

12. 過濾器、Instance Creation Mode 與 Context BAdI

依賴過濾器的 BAdI（p41）：概念和 Classic BAdI 相同，但功能加強了——一個 BAdI 可以定義多個過濾器；實作的過濾條件不只是單值，還能用 <>、>、<、>=、<=、CP、NP 運算子；也支援數值過濾器。講義的圖例：同一個 BAdI 分別為 'DE'、'GB'、'CN' 實作方法 ABC，執行時依 GET BADI … FILTERS country = <目前國家> 決定叫哪一個。

Instance Creation Mode（實例建立模式）控制 GET BADI 時如何產生實作類別的物件（object plug-in），選對了對效能影響很大：

模式行為適用
Newly Creating Instantiation每一個 BAdI 句柄都產生新的實作類別實例實作類別不需保留狀態
Reusing Instantiation同一個 internal session 內重複使用既有實例畫面出口 BAdI 必須用此模式；需要跨呼叫保留狀態
Context-Specific Instantiation對同一個 Context 物件，永遠使用同一個實作類別實例（對「實作類別＋Context」而言是 singleton）同一程式多處呼叫 BAdI、需依編譯單元區分狀態

14. BAdI 畫面出口（Screen Exit）

原理（p45～p47、BC425 p192～p195）：SAP 畫面開發者保留一個子畫面區域（Subscreen Area）；客戶的子畫面必須定義在客戶自己的函數群組中，放要顯示的追加欄位（典型是 Append Structure 的 ZZ 欄位）。BAdI 實作中指定「函數群組主程式 + 子畫面號碼」，SAP 在 PBO 取得並嵌入。畫面出口也只能有一個啟用實作。

15. 第五單元：Switch Framework——SFW1／SFW2／SFW5

觀念（p50～p51、BC425 p310）：客戶拿到的是一個包含所有行業解決方案的完整系統，只啟用自己需要的部分，其他雖然存在但不被使用。Switch Framework 用開關（Switch）從外部控制 Repository 物件或其元件的可見性；SAP 也決定往後以增強套件（Enhancement Package，EhP）交付新功能，由客戶決定要開哪些。

客戶自訂開關的步驟（p53、BC425 p312～p315）：

  1. SFW1：輸入開關名稱 → 建立 → 短文 → 在 Package 欄填入放增強實作的套件 → Activate（注意：這只是啟用「開關物件」本身，不代表套件裡的增強已被開啟）。
  2. SFW2：建立業務功能；不含行業解決方案元件時，類型用 G（Enterprise Business Function）。
  3. 把開關指派給業務功能，並選指派類型：Activation（套件與開關的所有物件都生效；控制增強實作時選這個）或 Standby（强晟譯為「使能但備用」：只啟用宣告性的增強，例如 DDIC 的表 Append 與靜態程式增強）。
  4. Properties 頁籤勾選 Reversible（可逆），才能在啟用後再關掉。
  5. 啟用業務功能物件。
  6. SFW5：啟用或停用業務功能（同一時間只能有一個使用者在 SFW5 的修改模式）。
强晟筆記 p52 寫反了：「對於啟用，有一些先決條件，首先業務功能要定義為可逆的，並且包中不包含任何字典物件」。原廠寫的是 停用（deactivation）的先決條件——業務功能必須是 Reversible，且不含 ABAP Dictionary 物件。所有業務功能都可以開，只有可逆的才能關。行業解決方案與 EhP 啟用時會產生程式並建立 DDIC 物件，所以它們都是不可逆的；在正式機上 SFW5 啟用 SAP 業務功能前一定要評估，開了就關不掉。

停用業務功能時，其開關所屬套件中的所有增強實作都失效，但仍存在系統中。增強實作一旦啟用，在原始碼中永遠顯示為「active」，看不出會不會執行；要雙擊程式中的增強實作名稱，到 Properties 頁籤看它有沒有指派開關、開關狀態為何。

讓非 Enhancement Framework 的增強也能被開關控制（BC425 p315）：只有 Enhancement Framework 的增強實作可切換；Customer Exit、Classic BAdI、User Exit、BTE 都不受影響。變通做法：例如 Classic BAdI，照常在 SE19 實作並建立實作類別，但寫方法時從修改模式切到顯示模式，改用方法開頭或結尾的隱式增強寫程式——這段隱式增強就能掛在開關的套件下。其他舊技術同理。講義也提醒不要每次都這樣做，只在確實需要納入開關時使用。

16. 衝突開關、增強調整（SPAU_ENH）與 Classic BAdI 遷移

衝突與衝突開關（BC425 Unit 12 L2）：兩個以上的開關，各自包含同一個增強段或單一使用 BAdI 的實作，而這些開關同時開啟時就產生衝突（這兩種增強只允許一個啟用實作）。解法是衝突開關（Conflict Switch）：

  • 一個衝突開關可指派多個一般開關；所有指派的開關都開時它才是 ON，只要有一個關就是 OFF。
  • 指派了衝突開關（而不是一般開關）的增強實作稱為衝突解決增強實作，它要反映所有可能同時開啟的實作的共同語意，並優先於其他已開啟的實作；多個衝突解決實作時，解決最多衝突的那個優先。
  • 每一種可能同時開啟而衝突的組合，都需要一個衝突開關與一個衝突解決實作。

增強調整：升級、匯入 Support Package 或用 Note Assistant 匯入修正時，被增強的 SAP 物件可能改變，增強實作需要調整。工具是 Enhancement Browser（Enhancement Information System），交易碼 SPAU_ENH，也可從 SE80 開啟（若沒顯示，Utilities → Settings → Workbench (General) → 勾 Enhancement Info System）。

需要調整的典型情況說明
原始碼含增強選項的物件或程序被刪除；ENHANCEMENT-POINT／SECTION 定義被刪；增強段內的 SAP 原始碼改變；增強選項之前的程式碼改變；FM 搬到別的函數群組；程序搬到別的 Include；增強段的外掛衝突；program-bound ↔ include-bound 互換；static ↔ dynamic 互換
函數模組SAP 新增了與增強參數同名的 IMPORTING 參數；被增強的 FM 被刪除或搬移；RFC-enabled 屬性改變
類別／介面方法名、參數名、事件名、型別名與匯入的物件衝突；被增強的類別、介面、方法、事件被刪除
BAdIBAdI 介面改變、過濾器被刪除；Classic BAdI 被遷移成 New BAdI

調整步驟：SPAU_ENH → Enhancements (Upgrade View) → 選一個增強 → Adjustment 頁籤看衝突清單（按 Long Text 看衝突原因與解法）→ 依技術調整原始碼外掛、類別／介面／函數群組、BAdI 實作 → 按 Adjust Enhancement Implementation（綠燈的衝突會自動解決）→ 啟用。Adjustment Preparation 會執行程式 ENH_SAPRUPGM，把表 ENHOBJ 的旗標轉成表 ENHHEADER 的旗標並計算調整狀態（BC425 p301 把程式名印成 ENH_SARUPGM，應為同一支 ENH_SAPRUPGM）。狀態種類：自動調整、工具輔助調整、手動調整、已調整、語意變更、被增強物件已刪除、空的增強實作、未知（問號）。

Classic BAdI 遷移（BC425 p301～p303）：因為 New BAdI 呼叫快得多，建議只定義 New BAdI，並把自己的 Classic BAdI 遷移過去：

17. S/4HANA 現況：Enhancement Framework 在 Clean Core 時代的位置

强晟在後記說：「技術總是越來越簡單，難的是用現有技術實現千變萬化的業務需求。」這句話到了 S/4HANA 依然成立，但「該用哪一種技術」的答案變了：

New BAdI可用；優先選 SAP 標為 Released 的 BAdI只能實作 Released（C0 contract）的 BAdI（Cloud BAdI）
Classic BAdI、Customer Exit、User Exit、BTE可用，但屬 Tier 3 經典擴充不可用
隱式／顯式原始碼增強、pre/post/overwrite可用，但對 Clean Core 最不友善，升級要 SPAU_ENH 調整不可用
Extension Index、Fixed Value Append可用；索引要先評估 HANA 是否需要改用 Key User 擴充與 CDS 擴充

選型順序請背起來（Casper 第三條經驗，也是 Clean Core 的精神）：標準設定（Customizing）→ Key User 擴充／Released BAdI → 其他 BAdI 與 Enhancement Spot → 隱式／顯式增強點 → 修改標準。本章教的隱式增強非常強大（幾乎任何 FM、方法、FORM 的頭尾都能插），正因如此最容易被濫用：一個專案累積上百個隱式增強，每次升級 SPAU_ENH 都是一場災難。能在 BAdI 解決就不要用增強點，能用 pre/post 方法就不要直接在方法結尾塞程式。

練習與自我檢核

  1. 顯式增強點與增強段有什麼差別？各有什麼多重實作風險？
    答案要點：點用 ENHANCEMENT-POINT「補充」程式碼，段用 ENHANCEMENT-SECTION … END-ENHANCEMENT-SECTION「替換」程式碼；兩者都屬 Enhancement Spot。點可多個實作但執行順序不保證，實作間不可相依；段只會執行一個實作，多個啟用時只出語法警告不 Dump，需衝突開關控制。
  2. STATIC 與 INCLUDE BOUND 兩個附加語法的用途？
    答案要點：STATIC 用於增強資料宣告，不加則是增強可執行程式碼；INCLUDE BOUND 用於定義在多支主程式共用的 Include 中、且實作要對所有主程式生效的增強；同一 Include 不能混用兩種。
  3. 替標準 FM 用隱式增強加參數，有哪些限制？
    答案要點：新增參數一律 optional；可加 IMPORTING／EXPORTING／CHANGING／TABLES，不能加 EXCEPTIONS；原始碼只能在開頭與結尾插入；程式中應先用 IS SUPPLIED 判斷。
  4. 寫出 pre-method、post-method 與原方法的參數差異，以及例外如何中斷執行鏈。
    答案要點：pre 沒有 EXPORTING；post 沒有 EXPORTING，原 EXPORTING 與 RETURNING 變成 CHANGING；有 overwrite 就不能有 pre/post；pre 丟例外則原方法與 post 都不跑，原方法丟例外則 post 不跑；以 CORE_OBJECT 存取原實例；生成 LCL_<增強名>、介面 IPR_／IPO_／IOW_。
  5. 在結構宣告 END OF 之前做隱式增強，以下哪個寫法正確？(a) zz_f TYPE c, (b) DATA zz_f LIKE mara-matnr. (c) DATA: zz_f TYPE matnr. (d) INCLUDE STRUCTURE zs.
    答案要點：(c)。必須用 DATA、TYPE 與句點；不可用 LIKE 表欄位與 INCLUDE STRUCTURE。
  6. Classic BAdI 與 New BAdI 的呼叫方式、參照變數型別、執行架構有何不同？
    答案要點：Classic 用 CL_EXITHANDLER=>GET_INSTANCE，參照型別是 BAdI 介面，經 SE18 產生的適配器類別 CL_EX_<名> 與橋接方法；New 用 GET BADI／CALL BADI，參照型別是 BAdI 名稱，由核心產生 BAdI 句柄，較快，屬於 Enhancement Spot，可被開關切換。
  7. GET BADI 在什麼情況丟 cx_badi_not_implemented？CALL BADI 何時丟 cx_badi_initial_reference？
    答案要點：單一使用 BAdI 找不到符合的實作且無 fallback 時丟前者（多重使用不丟）；句柄參照為 INITIAL（例如 GET BADI 失敗）時 CALL BADI 丟後者。强晟筆記拼成 regerence 是筆誤。
  8. 一般實作、Default Implementation、Fallback Class 的執行優先順序？
    答案要點：所有符合條件的一般實作都執行；沒有任何一般實作執行時才用 Default；連 Default 也沒有時才用定義上的 Fallback Class。
  9. 提供選單出口與畫面出口的 New BAdI 各有什麼定義限制？
    答案要點：選單出口 BAdI 不能有過濾器、不能多重使用、不能指派開關；畫面出口 BAdI 必須是 Reusing Instantiation、不能多重使用；兩者都只能有一個啟用實作；選單功能碼以「+」開頭；畫面出口主程式是 SAPL＋函數群組名。
  10. 說明 Instance Creation Mode 三種模式，以及 Context BAdI 的寫法。
    答案要點：Newly Creating（每個句柄新實例）、Reusing（同 internal session 共用）、Context-Specific（同一 Context 物件共用同一實例）；Context 類別實作 IF_BADI_CONTEXT，GET BADI … CONTEXT ctx；CL_BADI_REPORT_CONTEXT=>GET_INSTANCE 是通用的 Context 產生器。
  11. 用 Switch Framework 控制自己的增強實作，要走哪些 TCODE？停用的前提是什麼？
    答案要點：SFW1 建開關並指派套件（不能指派單一增強實作）→ SFW2 建業務功能（類型 G）、指派開關（Activation／Standby）、勾 Reversible → SFW5 啟用／停用。停用前提：業務功能為可逆，且不含 DDIC 物件（强晟筆記誤寫成「啟用」的前提）。行業解決方案與 EhP 不可逆。
  12. 你想讓一個 Classic BAdI 實作能被開關控制，怎麼做？
    答案要點：照常在 SE19 實作並建立實作類別，寫方法時切到顯示模式，改在方法開頭或結尾用隱式增強寫程式，把這個隱式增強實作放在開關所控制的套件裡。
  13. 升級後哪些情況要用 SPAU_ENH 調整增強實作？自己的 Classic BAdI 要怎麼遷移？
    答案要點：增強段內原始碼改變、增強點定義被刪、FM 新增同名參數或 RFC 屬性改變、被增強方法刪除、BAdI 介面改變等；用 Upgrade View → Adjustment 頁籤 → Adjust Enhancement Implementation。遷移在 SE18、只在原始系統、只遷移自己的 BAdI，之後刪除 Classic 定義並把 CL_EXITHANDLER 呼叫改成 GET BADI／CALL BADI；SAP 遷移過的 BAdI，客戶實作用 SPAU 的 Migrated Objects 處理。
