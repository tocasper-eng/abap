3. 事後分析第一站：ST22 讀 Dump 的順序

情境：ITL 講義第 6 張的截圖是一個經典 Dump——SYSTEM_NO_ROLL：「Unable to fulfil request for 6708 bytes of memory space」，上方還有一行「Short dump has not been completely stored (too big)」。這代表程式把記憶體用光了（通常是巨大內表），連 Dump 本身都大到存不完整。

操作步驟：

  1. ST22 → 依日期、使用者、程式名過濾（預設只列今天與昨天）。
  2. 先看 Short Text 與 Runtime Error 名稱（例如 SYSTEM_NO_ROLL、TSV_TNEW_PAGE_ALLOC_FAILED、DBSQL_SQL_ERROR、ITAB_DUPLICATE_KEY、CONVT_NO_NUMBER、MESSAGE_TYPE_X）。
  3. What happened? → Error analysis：例外類別名稱（CX_SY_…）就在這裡；若是 MESSAGE_TYPE_X，這裡會寫出訊息類別與編號。
  4. Information on where terminated：程式、Include、行號，以及是否在 Update Task。
  5. Source Code Extract：標記 >>>>> 的就是出事那一行。
  6. Active Calls/Events（呼叫堆疊）與 Chosen Variables（當時的變數值）——這兩段才是真正定位原因的地方。
  7. 要保留證據：按「Keep／保留」，避免被系統定期清除（清除由 Basis 排程的重整作業處理，保留天數依系統設定）。
  8. 可重現時，直接在 ST22 按「ABAP Debugger」進入斷點位置重現（詳細操作見 5-4 章第 12 節）。

為什麼這樣做：大多數人只看 Short Text 就去改程式，但真正的原因常常在呼叫堆疊的上一層——例如除以零的那一行沒錯，錯在呼叫者傳進來的數量是 0。

常見 Dump第一個懷疑實務改法
TSV_TNEW_PAGE_ALLOC_FAILED、SYSTEM_NO_ROLL內表太大（SELECT 沒 WHERE、空的 FOR ALL ENTRIES 驅動表）分批（PACKAGE SIZE）、只選需要欄位、用 ST02 看記憶體
DBSQL_SQL_ERRORSQL 太長（巨大 RANGES）、欄位型別不合、HANA 記憶體不足RANGES 改為子查詢或 JOIN；看 Error analysis 裡的 DB 錯誤碼
ITAB_DUPLICATE_KEYUNIQUE KEY 內表插入重複鍵先檢查 line_exists( ) 或改用 INSERT … INTO TABLE 看 sy-subrc
MESSAGE_TYPE_X標準程式刻意中止（通常是資料不一致）依 Error analysis 的訊息號碼搜 SAP Note，不要先想客製
TIME_OUT對話工作處理程序超過 rdisp/max_wprun_time回到第 5 節分析效能，或改背景執行

新程式應該用 class-based exception 把「可預期」的錯誤接住並記錄，不要讓使用者看到 Dump：

*&---------------------------------------------------------------*
*& 可預期錯誤要接住並留下證據，不要讓使用者看到 Dump
*&---------------------------------------------------------------*
TRY.
    DATA(lv_unit_cost) = ls_cost-amount / ls_cost-quantity.
    DATA(ls_mat)       = lt_material[ matnr = ls_cost-matnr ].
  CATCH cx_sy_zerodivide INTO DATA(lx_div).
    " 數量為 0：記錄到應用日誌（見第 4 節），不是直接 Dump
    MESSAGE |物料 { ls_cost-matnr } 數量為 0，已略過| TYPE 'S' DISPLAY LIKE 'W'.
  CATCH cx_sy_itab_line_not_found.
    MESSAGE |物料 { ls_cost-matnr } 不在主檔清單中| TYPE 'S' DISPLAY LIKE 'W'.
ENDTRY.

" 真的不可能發生、一發生就代表資料錯亂的情況，才用 ASSERT
" 配合 ASSERT ID + SAAB，可以在正式機設定成「只記錄、不中止」
ASSERT ID zcost_check CONDITION ls_cost-quantity >= 0.
ASSERT 沒有 ID 時永遠啟用，條件不成立就產生 ASSERTION_FAILED Dump。正式機上建議一律用 ASSERT ID，並在 SAAB 設定 Checkpoint Group 的行為（Inactive／Log／Abort），這樣可以不改程式就收集證據。

4. SM21 系統日誌、SM13 更新中止與 SLG1 應用日誌

5. STAD：先判斷時間花在哪一層，再決定開哪個追蹤

情境：「這支報表很慢」。在開 ST05 或 SAT 之前，先用 STAD 看使用者剛剛那一次執行的統計記錄。它不用事先開關、正式機也有，而且能告訴你該用哪個追蹤工具。

效能講義第 3～5 張把一次使用者請求拆成 8 步：① 請求進入 Dispatcher 佇列 → ② 佇列分派 → ③ 交給工作處理程序 → ④ 與使用者內容（Roll 區）交換 → ⑤ 讀表緩衝與程式緩衝 → ⑥ 交給資料庫處理程序 → ⑦ 讀資料庫快取 → ⑧ 資料庫快取與磁碟交換。回應時間就是這些階段的加總（詳細公式見 5-21 章第 5 節）。講義第 6 張附了一張參考值表：

時間項參考值（講義第 6 張）偏高時代表

操作步驟：STAD → 輸入使用者、時間區間（抓寬一點，前後 10 分鐘）、交易或程式 → 找到那一筆 → 雙擊看 Time 與 DB 分頁。DB 分頁若 Requests 與 Database rows 幾乎相同，程式多半是在迴圈裡 SELECT SINGLE。

實戰判斷口訣：DB 時間大開 ST05，CPU 時間大開 SAT，兩個都大或分不清就開 ST12。但若同一時段每步平均 DB 時間都異常高（例如所有交易都慢），先請 Basis 檢查 DB，這時 SQL 追蹤的數字不可信。

7. ST05 實戰（一）：四種追蹤與錄製步驟

ITL 講義第 3、4 張是 ST05 的主畫面與顯示條件 （依截圖整理）。主畫面（Performance Analysis）：

  • Select Trace：SQL Trace、Enqueue Trace、RFC Trace、Table Buffer Trace（新版另有 HTTP Trace、Stack Trace 選項）。
  • Select Trace Function：Activate Trace、Activate Trace with Filter、Deactivate Trace、Display Trace、Enter SQL Statement（手動輸入 SQL 看 Explain）。
  • Trace Status：例如「All Traces are Switched Off」。

四種追蹤各自回答不同的問題：

追蹤回答的問題實戰情境
SQL Trace程式對資料庫發了哪些 SQL、各花多久、回幾筆效能分析；反查交易讀寫哪些表（第 9 節）
Enqueue Trace程式設了哪些 SAP 鎖（鎖物件、鎖引數、模式）、何時釋放「使用者 A 開著單據，B 就不能改」的原因；找出交易用哪個鎖物件（進而知道主表）
RFC Trace呼叫了哪些遠端函數、目的地、傳送／接收位元組介面慢、跨系統呼叫次數太多
Table Buffer Trace哪些存取由 SAP 表緩衝滿足、哪些繞過緩衝設定表明明有緩衝卻一直打 DB（例如用了 BYPASSING BUFFER、聚合函數、ORDER BY 非主鍵）

9. 用追蹤反查「這個交易寫了哪些表」

情境：顧問問「VA01 存檔時到底寫了哪些表？」「畫面上這個欄位是存在哪裡？」F1 → 技術資訊常常只顯示畫面結構（例如 RV45A、KOMV），不是資料庫表。這時最可靠的方法是：讓系統自己告訴你。

操作步驟：

  1. 在測試機準備好要執行的交易，先把所有欄位填好、停在「存檔」前一刻。
  2. 另開模式 ST05 → 勾 SQL Trace 與 Enqueue Trace → Activate Trace with Filter，只填使用者，不要限制工作處理程序或交易。
  3. 回原模式按存檔，等狀態列出現「已儲存」訊息，再多等幾秒（讓 Update Task 跑完）。
  4. ST05 → Deactivate → Display Trace。顯示條件的 Operations 只留 INSERT、UPDATE、DELETE（新版可在清單上依 Operation 欄過濾，或切到 Table Access 彙總看每張表的操作次數）。
  5. 把 Obj. name 欄列成清單，就是這筆交易寫入的所有表；Enqueue Trace 的鎖物件（例如銷售單的 EVVBAKE）則告訴你「主表」是誰。
  6. 若要知道畫面某欄位來自哪張表，改成在顯示交易（例如 VA03）進入該分頁時錄 SELECT，再對照欄位值。

為什麼要「只填使用者」：S/4HANA 的單據存檔大多透過 Update Task（CALL FUNCTION … IN UPDATE TASK 再 COMMIT WORK），真正的 INSERT 是在更新工作處理程序（UPD）裡以同一個使用者名稱執行的。如果你在 Filter 中限制了對話工作處理程序或交易碼，更新模組寫的表就全部漏掉——這是新手最常得出「VA01 只寫了 NRIV」這種錯誤結論的原因。

反查手法優點盲點

ST05 Enqueue Trace一眼看出主表（鎖物件以主表命名）只看到有上鎖的表
SAT（勾選 DB 存取事件）能看到是哪個函數／方法寫的更新任務要另外勾選「量測 RFC 與更新任務」
變更文件 CDHDR／CDPOS事後也查得到「哪個欄位從什麼值改成什麼值」只有該物件有定義變更文件、且欄位有勾 Change Document 才有

10. 資料從哪裡來：Debugger 追資料與「參數存成測試資料」

情境：報表上某個金額不對，你需要知道它在程式裡是在哪一步被算錯的。ST05 告訴你讀了哪些表，但計算邏輯要靠 Debugger。

  1. 從值反推：在 Debugger 對結果內表設 Watchpoint，條件寫成「欄位 = 那個錯的值」，F8 跑下去，停下來的位置就是寫入那個值的語句（Watchpoint 用法見 5-4 章第 7 節）。
  2. 從表正推：在 Debugger 的 Break at → Statement 輸入 SELECT（ITL 講義第 17 張「ABAP 命令中斷點」），每個 SELECT 都會停下；搭配 F6 看回傳筆數。講義第 18～22 張另外示範了 Method、Function、Form、Source code、Message 五種動態中斷點。
  3. 保存現場：ITL 講義第 31 張示範在函數模組除錯時，於變數視窗的 Services（服務）選單選 Save Parameters as Test Data (SE37) （依截圖整理：截圖中停在 SE16N_INTERFACE，Variable Fast Display Services → Tool-Specific → Save Parameters as Test Data (SE37)）。這會把當下的輸入參數存成 SE37 的測試資料，之後可以在 SE37 反覆重跑同一組參數，不必每次都從交易重新操作。
  4. 彈出視窗也要能進 Debugger：彈出的對話框沒有指令欄，打不了 /h。ITL 講義第 32 張的做法是準備一個文字檔，拖放到彈出視窗上：
[FUNCTION]
Command=/H
Title=Debugger
Type=SystemCommand

存成例如 debug.txt（有人存成 .sap 也可以），出現彈出視窗時從檔案總管拖到該視窗上，SAP GUI 就會執行 /H 開啟除錯模式，按下視窗上的按鈕即進入 Debugger。同理 Command=/HS 可開啟系統除錯（除錯標準系統程式）。講義第 15 張列出的三個指令：/H 啟動 Debugger、/HS 啟動系統除錯、/HA 跳過畫面處理直接除錯。

在 Debugger 中改變數值來「驗證假設」只能在開發／測試機做。正式機改值需要 S_DEVELOP 的 DEBUG 物件、ACTVT = 02 權限，每次改值都會寫入 SM21 系統日誌，屬於稽核重點；繞過檢查寫進資料庫的資料可能與 SAP 標準邏輯不一致。正規替代：用 Save Parameters as Test Data 把現場帶回測試機重現，或用應用日誌（第 4 節）與 SQLM 收集證據。

12. ST12 與 SQLM：一次錄兩種、在正式機看長期

ST12（Single Transaction Analysis）把 SAT 的 ABAP Trace 與 ST05 的 SQL Trace 一次錄製、一個畫面分析，是 SAP 支援工程師的標準工具（需 ST-A/PI 附加元件；工具說明見 5-21 章第 20 節）。實戰步驟：

  1. ST12 → 選 User／Tasks（追某使用者）、Current mode（在本模式執行交易或程式）或 Workprocess（追執行中的工作處理程序）。
  2. 勾選 ABAP Trace 與 Performance Traces（SQL、Enqueue、RFC），填上說明文字（之後才認得出是哪一次）。
  3. Start Trace → 執行 → 結束後 Collect Traces（很重要：沒有收集，追蹤會被覆寫）。
  4. 在同一個分析畫面切換 ABAP Hit List 與 SQL Summary，SQL 可直接帶出 Explain 與呼叫位置。

SQLM（SQL Monitor）用在「正式機某些時候很慢、但測試機重現不了」的情境：在正式機低開銷地長期記錄所有 SQL 與其進入點（交易、報表、RFC、URL）。啟用、背景作業、四種分析觀點都寫在 5-21 章第 8 節。實戰只要記三件事：

  • 先開一到兩週，用 SQLMD 依 Source Position 過濾 Z*／Y* 套件、依 Total Time 排序，得到「客製程式最貴的 SQL 前十名」。
  • Executions 很高、每次筆數很少＝巢狀 SELECT；max 筆數等於整表筆數＝空的 FOR ALL ENTRIES 驅動表或沒有 WHERE。
  • 改善後重新量一輪，用數字證明改善有效；再用 SWLT 把 SQLM 數據與 ATC 靜態檢查結果合併，排定下一批要改的程式。

15. 平行處理：aRFC 分派到伺服器群組

情境：SQL 與內表都已最佳化，但資料量就是很大（例如全廠物料的成本重算），單一工作處理程序要跑好幾小時。效能講義第 59～62 張的做法：用非同步 RFC 把資料拆塊，分派到伺服器群組平行處理。

  1. Basis 在 RZ12 定義 RFC 伺服器群組（例如 parallel_generators 或自訂群組），並設定配額。
  2. 用 SPBT_INITIALIZE 讀取群組目前可用的空閒工作處理程序數（講義第 60 張）。
  3. 把資料拆塊，每塊以 CALL FUNCTION … STARTING NEW TASK … DESTINATION IN GROUP … 發出（第 61 張）。
  4. 各任務完成時以回呼收集結果；在資源充足時彼此不影響，完成順序不固定——講義第 62 張的截圖就是 TASK7 比 TASK6 先完成、TASK6 比 TASK5 先完成。
*&---------------------------------------------------------------*
*& aRFC 平行處理骨架（被呼叫的 Z 函數必須是 Remote-Enabled）
*&---------------------------------------------------------------*
CLASS lcl_parallel DEFINITION.
  PUBLIC SECTION.
    DATA mv_running TYPE i.
    DATA mt_result  TYPE ztt_cost_result.
    METHODS run IMPORTING it_chunks TYPE ztt_matnr_chunks.
    METHODS on_end IMPORTING p_task TYPE clike.
ENDCLASS.

CLASS lcl_parallel IMPLEMENTATION.
  METHOD run.
    DATA lv_max  TYPE i.
    DATA lv_free TYPE i.
    CALL FUNCTION 'SPBT_INITIALIZE'
      EXPORTING  group_name     = 'ZPARALLEL'
      IMPORTING  max_pbt_wps    = lv_max
                 free_pbt_wps   = lv_free
      EXCEPTIONS OTHERS         = 1.
    IF sy-subrc <> 0 OR lv_free = 0.
      RETURN.                              " 沒有資源就改走序列處理（略）
    ENDIF.
    DATA(lv_limit) = nmax( val1 = 1 val2 = lv_free - 2 ).  " 留一點給線上使用者

    LOOP AT it_chunks INTO DATA(ls_chunk).
      WAIT UNTIL mv_running < lv_limit.    " 控制同時執行的任務數
      DATA(lv_task) = |T{ sy-tabix WIDTH = 4 ALIGN = RIGHT PAD = '0' }|.
      CALL FUNCTION 'Z_COST_CALC_CHUNK'
        STARTING NEW TASK lv_task
        DESTINATION IN GROUP 'ZPARALLEL'
        CALLING on_end ON END OF TASK
        EXPORTING  it_matnr = ls_chunk-matnr
        EXCEPTIONS system_failure        = 1
                   communication_failure = 2
                   resource_failure      = 3
                   OTHERS                = 4.
      IF sy-subrc = 0.
        mv_running = mv_running + 1.       " 7.54 以上可寫 mv_running += 1
      ENDIF.
    ENDLOOP.
    WAIT UNTIL mv_running = 0.             " 等所有任務回來
  ENDMETHOD.

  METHOD on_end.
    DATA lt_part TYPE ztt_cost_result.
    RECEIVE RESULTS FROM FUNCTION 'Z_COST_CALC_CHUNK'
      IMPORTING  et_result = lt_part
      EXCEPTIONS OTHERS    = 1.
    mv_running = mv_running - 1.
    APPEND LINES OF lt_part TO mt_result.
  ENDMETHOD.
ENDCLASS.
  • 講義原寫法 PERFORMING <subroutine> ON END OF TASK 依賴 FORM，新程式請用 CALLING meth ON END OF TASK。
  • 多工作處理程序不是越多越好（講義原話）：它會吃掉對話工作處理程序，白天在正式機大量平行會讓線上使用者排隊。務必與 Basis 協調群組與配額，並在 SM66 監控。
  • 各任務回傳順序不固定，彙總後的 mt_result 也沒有順序——任何依賴順序的後續處理都要先 SORT。這和下一節「HANA 沒有預設排序」是同一個道理。
  • 每個任務是獨立的 LUW，一個失敗不會讓其他任務回滾；要自己設計重跑與錯誤記錄（寫入應用日誌，見第 4 節）。

16. 資料對不上：HANA 沒有預設排序（成本評價 H／E 案例）

情境：這是 Casper 在專案上真的踩過的坑。一支成本報表，同一個物料、同樣的選擇條件，今天跑和明天跑的單位成本不一樣；在開發機、測試機都重現不了，只在正式機偶爾出現。

追查過程（照本章的流程走一次）：

  1. 分流（第 2 節）：沒有 Dump、沒有權限問題、也不慢——是「資料對不上」。
  2. ST05 看實際 SQL（第 7、8 節）：同一條 SELECT 兩次錄製的 WHERE 與變數值完全相同，Recs 也相同——代表 DB 回的資料集合一樣，差別只能在順序。
  3. Debugger 比對兩次執行（第 10 節）：在「取第一筆」的地方停下，發現內表第一筆一次是成本估算的 item category H 角度，一次是 cost component E 角度。兩種角度的成本構成欄位數量不同，程式取到哪一筆就用哪一筆算，結果自然不同。
  4. 根因：程式用了沒有完整主鍵的 SELECT SINGLE／沒有 ORDER BY 的 UP TO 1 ROWS，再加上 READ TABLE … INDEX 1。舊資料庫依索引讀取時「剛好」有順序，HANA 欄式儲存、平行執行、分割區，不保證任何順序。
  5. 結論：業務上確認應固定抓 H，把條件寫死在 WHERE，並加上明確排序。

    AND werks = @lv_werks
  INTO TABLE @DATA(lt_bad)

    參考答案要點：開 ST05 SQL Trace（限定該使用者），切到結構相同語句彙總，依總時間找前五名，看 Executions 與每次筆數判斷是否迴圈內 SELECT，對最貴的語句按 Explain 看索引。
  2. ITL 講義說 ST05 的 Duration「以毫秒計」，截圖中某 FETCH 為 71,507。這是多少時間？
    參考答案要點：Duration 單位是微秒，71,507 µs ≈ 71.5 ms，不是 71 秒。
  3. 用 ST05 反查 VA01 存檔寫了哪些表，結果只看到 NRIV 與幾張讀取的表。最可能的原因是什麼？
    參考答案要點：Filter 限制了交易或工作處理程序，錄不到更新工作處理程序（Update Task）執行的 INSERT；應只以使用者過濾，並在存檔後多等幾秒再關閉追蹤。
  4. 一支長時間執行中的背景程式，你想知道它現在卡在哪，但不能讓它停下來。用什麼？
    參考答案要點：SM50／SM66 看目前動作與表；SAT 的 In Parallel Session 或 ST12 的 Workprocess 模式錄一段；避免直接附掛 Debugger（會暫停程序、留下 SM21 記錄）。
  5. 彈出視窗沒有指令欄，要怎麼進入 Debugger？
    參考答案要點：準備內容為 [FUNCTION]／Command=/H／Title=Debugger／Type=SystemCommand 的文字檔，拖放到彈出視窗上，再按視窗按鈕。
  6. 指出效能講義關於內表的兩處錯誤。
    參考答案要點：① STANDARD 表主鍵不能是 UNIQUE（第 30 張寫「允許」）；② 函數的 TABLES 參數是傳參考不是傳值（第 42 張）；另外 SORTED 表以鍵讀取不需加 BINARY SEARCH。
  7. FOR ALL ENTRIES 最致命的陷阱是什麼？講義漏了哪一點？
    參考答案要點：驅動內表為空時 WHERE 條件被忽略、讀全表；一定要先檢查 IS NOT INITIAL。另外結果會去重、沒有順序。
  8. 同一物料的成本報表每次跑結果不同，ST05 顯示兩次 SQL 與回傳筆數完全相同。你會懷疑什麼？怎麼修？
    參考答案要點：HANA 沒有預設排序，程式「取第一筆」時一次取到 H、一次取到 E；修正為業務上固定條件（抓 H）並加 ORDER BY，內表後續處理前先 SORT。
  9. 為什麼選擇條件「列舉優於區間」？
    參考答案要點：區間比的是字典序，遇到號碼不連續、ALPHA 前導零、編碼規則改變會漏抓或多抓；列舉語意明確且能用索引。筆數很多時改用 JOIN／子查詢。
  10. 平行處理完成後，結果內表直接用 BINARY SEARCH 讀取，偶爾讀不到資料。原因？
    參考答案要點：各任務完成順序不固定，APPEND LINES OF 後的結果沒有排序；BINARY SEARCH 前必須先 SORT（或改用 SORTED／HASHED 表接收）。
  11. SQLM 與 ST05 各適合什麼情境？
    參考答案要點：ST05 追單次、可重現的流程，看得到變數值與 Explain；SQLM 在正式機長期、低開銷地記錄所有 SQL 與進入點，適合找「最貴的客製 SQL」與只在正式機出現的問題，但看不到單次細節。
  12. 介面程式偶爾失敗、但事後沒人知道失敗原因。你會在程式中加上什麼？事後用哪個 TCODE 查？
    參考答案要點：用 BAL 函數（BAL_LOG_CREATE／BAL_LOG_MSG_ADD／BAL_DB_SAVE）把 BAPIRET2 等訊息寫入應用日誌，External ID 放業務鍵；事後用 SLG1 依物件／External ID 查詢。
