RAP 的一筆交易分成兩個階段。第一個是 interaction phase：資料只寫進 transactional buffer，可以暫時不一致。第二個是 save sequence，又分成可以退回的 early save 和不能退回的 late save。每一種 behavior 零件都掛在固定的時間點上，先把這張表記住，後面各節就容易理解了：

3. Determination：建立時帶預設狀態、自動計算總金額

Determination 會在觸發條件成立時，由框架自動呼叫，用來計算或補值。觸發條件可以是作業（create、update、delete），也可以是欄位（field …）。有兩種執行時機：

  • on modify：資料一寫進 buffer 就執行，結果馬上反映在 UI 上。適合預設值、小計。
  • on save：在 save sequence 的 finalize 執行。適合只在存檔時才做一次的事，例如配正式號碼。on save 的 update 條件必須和 create 一起寫。
// ZI_Quote（表頭）
determination setStatusOpen on modify { create; }
determination setQuoteID    on save   { create; }

// ZI_QuoteItem（明細）：數量或單價變動 → 重算表頭總金額
determination calcTotal on modify { create; field Quantity, NetPrice; }

實作寫在 behavior pool ZBP_I_Quote 的 local handler class 裡。實作裡讀寫 BO 一律用 EML 加 IN LOCAL MODE，這樣會略過 feature control、權限檢查與 precheck。例如 OverallStatus 是 readonly，只有 LOCAL MODE 才寫得進去：

4. Validation：客戶必須存在、數量必須大於 0

Validation 在 early save 的 check_before_save 階段執行。只要有一筆填了 failed，整個 transactional buffer 都不會存檔，連沒有錯的資料也一樣，這是 all-or-nothing。錯誤訊息放在 reported，用 %element 指出是哪個欄位錯，Fiori 會把該欄位標紅：

// 表頭
validation validateCustomer on save { create; field SoldToParty; }
// 明細
validation validateQuantity on save { create; field Quantity; }
// draft BO：要登記進 Prepare，按 Save（Activate）時才會對 draft 執行
draft determine action Prepare
{
  validation validateCustomer;
  validation Item~validateQuantity;
}

檢查客戶是否存在時，先找標準的 released view，不要直接讀 KNA1。S/4HANA 的客戶主檔有 released CDS view I_Customer，鍵值欄位是 Customer：

METHOD validateCustomer.   " 宣告：METHODS validateCustomer FOR VALIDATE ON SAVE IMPORTING keys FOR Quote~validateCustomer.
  READ ENTITIES OF ZI_Quote IN LOCAL MODE
    ENTITY Quote
      FIELDS ( SoldToParty )
      WITH CORRESPONDING #( keys )
    RESULT DATA(quotes).

  " 收集要查的客戶：唯一鍵的 SORTED 表，重複值 INSERT 時自動略過
  DATA customers TYPE SORTED TABLE OF I_Customer-Customer WITH UNIQUE KEY table_line.
  LOOP AT quotes INTO DATA(q) WHERE SoldToParty IS NOT INITIAL.
    INSERT q-SoldToParty INTO TABLE customers.
  ENDLOOP.

  IF customers IS NOT INITIAL.        " FOR ALL ENTRIES 前一定要檢查非空
    SELECT FROM I_Customer
      FIELDS Customer
      FOR ALL ENTRIES IN @customers
      WHERE Customer = @customers-table_line
      INTO TABLE @DATA(existing_customers).
  ENDIF.

  LOOP AT quotes INTO DATA(quote).
    " 先清掉這個 state area 的舊訊息（draft 重跑 validation 時才不會殘留）
    APPEND VALUE #( %tky        = quote-%tky
                    %state_area = 'VALIDATE_CUSTOMER' ) TO reported-quote.

    IF quote-SoldToParty IS INITIAL
       OR NOT line_exists( existing_customers[ Customer = quote-SoldToParty ] ).
      APPEND VALUE #( %tky = quote-%tky ) TO failed-quote.
      APPEND VALUE #( %tky        = quote-%tky
                      %state_area = 'VALIDATE_CUSTOMER'
                      %msg        = new_message( id       = 'ZQUOTE'
                                                 number   = '001'   " 客戶 &1 不存在
                                                 v1       = quote-SoldToParty
                                                 severity = if_abap_behv_message=>severity-error )
                      %element-SoldToParty = if_abap_behv=>mk-on ) TO reported-quote.

7. Feature control：狀態是 Accepted 時停用編輯與 action

static feature control 寫死在 BDEF，不需要實作：field ( readonly )、field ( mandatory )、field ( mandatory : create, readonly : update )。其中 mandatory : create 與 readonly : update 從 7.55 起提供。dynamic feature control 是依實例狀態決定，BDEF 寫 features : instance，再實作 FOR INSTANCE FEATURES：

// static

field ( mandatory ) SoldToParty, SalesOrganization;

// dynamic（每一項都要在 get_instance_features 回傳）
update ( features : instance );
delete ( features : instance );
association _Item { create ( features : instance ); with draft; }

action ( features : instance ) acceptQuote result [1] $self;
action ( features : instance ) rejectQuote parameter ZA_QuoteReject result [1] $self;

    ENTITY Quote

    " 已接受、已拒絕或已結案 → 全部停用（狀態用列舉判斷）

                    %action-rejectQuote = op

draft 與鎖的交互作用：
  • 建立 draft（Edit）時，框架會對 active 實例上排他鎖。這個鎖在 ABAP session 結束後仍然保留一段可設定的時間。所以使用者按了「編輯」就關掉瀏覽器，同一張報價單在這段時間內其他人都改不了，傳統程式或 BAPI 去改也會遇到鎖。支援人員要會用 SM12 查鎖。
  • 排他鎖過期之後進入樂觀鎖階段。使用者回來繼續編輯時會執行 Resume，框架比對 draft 與 active 的 total etag。如果期間 active 已經被別人改過，這份 draft 就不能再繼續。
  • 如果還有傳統 Dynpro、報表或 BAPI 也會改 ZQUOTE_H，它們用的自建鎖物件和 RAP 框架的鎖是否互斥，未能確認，請在 SM12 實測。確認之前，不要讓兩套程式同時維護同一張表。
  • draft 會一直累積在 draft table。沒有人 Discard 的 draft 要靠框架的清理機制，保留天數與清理作業請以系統文件為準（未能確認）。
validation 要登記進 Prepare：on save validation 如果沒有寫在 draft determine action Prepare { … } 裡，draft 期間就不會跑，要等到 Activate 才會出現錯誤。子實體的 validation 用 validation Item~validateQuantity; 登記。draft action Activate optimized; 可以減少重複執行 determination 與 validation，這個 optimized 關鍵字的版本門檻未能確認。

RAP 交易模型的限制（saver 與 handler 都適用）：
  • 不可以 COMMIT WORK／ROLLBACK WORK，也不可以呼叫內部會 COMMIT 的函數，例如 BAPI_TRANSACTION_COMMIT。RAP 是交易的擁有者，COMMIT 由 COMMIT ENTITIES（Fiori 情境由框架）統一執行。
  • 改資料庫只允許在 late save，也就是 save、save_modified、adjust_numbers。CALL FUNCTION … IN UPDATE TASK 與 bgRFC 也只能在 late save 註冊。許多 BAPI 內部會註冊 update task，所以 BAPI 的正式呼叫只能放在 save／save_modified；放在 action 或 validation 會 runtime error（官方 RAP640 教材明文說明）。
  • sRFC／aRFC 不可以用在 late save；CALL TRANSACTION、SUBMIT、Dynpro 相關語法，以及 MESSAGE（不帶 INTO）在所有階段都禁止。
  • SET UPDATE TASK LOCAL 不需要自己下：COMMIT ENTITIES 本身就會強制 local update（本地更新失敗才退回 COMMIT WORK AND WAIT），所以 BAPI 註冊的更新模組會在同一個交易內同步執行。在 behavior pool 裡自己下 SET UPDATE TASK LOCAL 是否被允許，未能確認，建議不要寫。
  • late save 原則上不可以失敗。如果不得不在 late save 呼叫可能失敗的 BAPI，官方提供基底類別 CL_ABAP_BEHAVIOR_SAVER_FAILED，讓 saver 可以回報 failed／reported。此時 COMMIT ENTITIES 的 sy-subrc 會是 8，消費端必須 ROLLBACK ENTITIES（版本門檻未能確認）。
  • BAPI_SALESORDER_CREATEFROMDAT2 的 TESTRUN 模式是否完全不註冊 update task，未能確認。如果在 validation 呼叫時 dump，就只能拿掉預檢，改用前一點的 CL_ABAP_BEHAVIOR_SAVER_FAILED 回報錯誤。

12. 錯誤處理與訊息：failed、reported、%tky、%msg、%state_area

handler 與 saver 的方法都有隱含的 CHANGING 參數，稱為 response parameter，名稱是固定的：

參數結構常用元件用途
mapped每個實體一張表（mapped-quote）%cid、%tky／鍵、late numbering 的 %pid／%tmp新建實例的 %cid 與鍵的對應（只有會新建實例的作業才有）

情境建議理由
新的主檔或單據維護、需要 Fiori、手機、draft、對外 APIRAP（2020 以上）一次開發同時得到 UI 服務與 Web API，權限、鎖、交易由框架統一處理

改的是標準單據（銷售訂單、採購單）先找標準 RAP BO 或 BAPI，不自建見下一段

先找標準（Casper 實務經驗第 3 條）：新版 S/4HANA 的許多標準單據已經有 SAP 提供的 RAP BO interface，可以直接用 EML 呼叫，取代 BAPI。銷售訂單對應 I_SalesOrderTP，社群文章指出它從 S/4HANA 2022 起在地端提供，用來取代 BAPI_SALESORDER_CREATEFROMDAT2。這個名稱與版本只在社群文章中看到，未能以 SAP 官方文件確認。請在 ADT 的 Released Objects 樹或 SAP Business Accelerator Hub 查詢該 BO 在你的版本是否 released，以及支援哪些作業。

擴充標準（或自己的）RAP BO：BDEF extension（7.57／2022 起）。原 BDEF 要先宣告 extensible { … } 開放哪些擴充點，擴充方再建立一個 extension BDEF。以下結構取自官方 Flight 範例的 agency 擴充，名稱已改成報價單的例子：

// 原 BDEF（提供方）：開放擴充點
managed implementation in class zbp_i_quote unique;
strict ( 2 );
with draft;
extensible
{
  with determinations on modify;
  with determinations on save;
  with validations on save;
  with additional save;
}
define behavior for ZI_Quote alias Quote
...
extensible
{ ... }

// 擴充 BDEF（擴充方，另一個物件）：用 interface 擴充
extension using interface zi_quotetp
implementation in class zbp_x_quote_check unique;

extend behavior for Quote
{
  validation zz_validateCreditLimit on save { field SoldToParty; }
  extend draft determine action Prepare
  {
    validation zz_validateCreditLimit;
  }
}
