2. 設計模式總覽：ABAP 的特殊條件與本章地圖

設計模式（Design Pattern）是「反覆出現的設計問題 ＋ 經過驗證的解法結構」。GoF（Gang of Four）把 23 個模式分成三類：建立型（怎麼產生物件）、結構型（物件怎麼組合）、行為型（物件怎麼分工與溝通）。本章六個模式的歸屬如下：

分類模式一句話意圖書中情境SAP 標準中看得到的影子
建立型Singleton一個類別只允許一個實例，並提供全域存取點日誌 ZCL_LOG持久化服務的類別代理 ZCA_xxx=>AGENT；RTTI 對同一型別只產生一個描述物件（CL_ABAP_TYPEDESCR=>DESCRIBE_BY_NAME）
結構型Adapter把既有介面轉成客戶端期待的介面把函數模組包成 ZIF_TARGETClean Core 建議：以自建 wrapper 類別包裝未釋出的 API 再給 ABAP Cloud 程式使用
結構型Bridge抽象與實作分離，兩個維度各自擴充訂單類型 × 輸出文件類型概念上類似輸出控制的「輸出類型 × 傳送媒體」兩維組合
結構型Facade給複雜子系統一個簡單的統一入口供應商評估BAPI 本身：一個 BAPI_PO_CREATE1 背後是整套採購單處理邏輯
行為型Observer一對多相依，狀態改變時自動通知所有觀察者庫存變動通知採購組ABAP 事件；CL_GUI_ALV_GRID 的 DOUBLE_CLICK／TOOLBAR 事件；BOR／工作流程事件
行為型Strategy一族演算法各自封裝、執行期可互換MRP 策略 Z1／Z2／Z3帶過濾器（Filter）的 BAdI：同一介面多個實作，依過濾值挑一個執行

把 Java／C# 教科書上的模式搬到 ABAP，要先認清 ABAP 的幾個先天條件，後面每一節都會用到：

  • 沒有方法多載（Overloading）：同一類別不能有同名方法（勘誤表第 3 條也特別更正了「覆蓋 Overriding／重載 Overloading」的中英對照）。需要多種建立方式時用多個 factory 方法或 OPTIONAL 參數。
  • 靜態屬性的生命週期是「內部工作階段」（internal session）：Singleton 只在同一支程式的同一次執行中唯一，不是跨使用者、跨應用伺服器的唯一。
  • 語言內建事件：EVENTS／RAISE EVENT／SET HANDLER 就是語言層的 Observer，多數情況不必自己維護觀察者清單（第 13 節）。
  • 動態建立物件：CREATE OBJECT ref TYPE (類別名變數) 讓 Bridge／Strategy 可以「由設定表決定用哪個類別」。這是少數 NEW 做不到、必須保留 CREATE OBJECT 的地方（第 8 節）。
  • 單一繼承＋多重介面：模式裡的「抽象角色」優先用介面（INTERFACE）表達，抽象類別只在需要共用實作時使用。
本章示範程式的輸出方式：原範例全部用 WRITE 清單輸出，而且把 WRITE 寫在業務類別的方法裡。改寫版一律讓方法「回傳文字（string_table）」，由呼叫端的 REPORT 用 CL_DEMO_OUTPUT 顯示。這樣業務類別不綁畫面技術，同一個類別可以被 ALV、Fiori、背景作業、ABAP Unit 重用（單一職責原則，見 7-4 章）。
CL_DEMO_OUTPUT 是 SAP 提供給示範與測試用的類別，不可用於正式程式。正式報表請用 CL_SALV_TABLE（見 2-3 章），日誌請寫應用日誌（Application Log，SLG1 查詢）。

3. Singleton（一）：ZCL_LOG 的結構（7.1～7.3）

觀念：系統中某些物件只該有一份：日誌收集器、設定快取、與外部系統的連線管理員。如果任何人都能 NEW，就會出現多個日誌物件各記各的，最後誰也拼不出完整訊息。Singleton 的三個要件：

  1. 類別宣告 CREATE PRIVATE：外界不能建立實例。
  2. 私有靜態屬性保存唯一實例。
  3. 公開靜態方法 GET_INSTANCE 回傳那個實例（沒有就先建立）。

另外強烈建議加 FINAL：若允許繼承，子類別可能繞過唯一性。

UML（文字版）
+---------------------------------------------+
| ZCL_LOG            {FINAL, CREATE PRIVATE}  |
+---------------------------------------------+
| - go_instance : REF TO zcl_log   {static}   |
| - mv_msg      : string                      |
+---------------------------------------------+
| + get_instance( ) : REF TO zcl_log {static} |
| + set_msg( iv_msg : string )                |
| + get_msg( ) : string                       |
+---------------------------------------------+
Client ---uses---> ZCL_LOG=>get_instance( )   （沒有人能直接 NEW zcl_log( )）

範例（改寫後）：7.1 的 GET_INSTANCE、7.2 的 SET_MSG 原樣保留語意；7.3 的 PRINT_MSG 改為 GET_MSG 回傳字串。

CLASS zcl_log IMPLEMENTATION.

    " 延遲建立（lazy）：第一次被要求時才 NEW
    IF go_instance IS NOT BOUND.

    ENDIF.

  METHOD set_msg.
    mv_msg = iv_msg.
  ENDMETHOD.

  METHOD get_msg.
    rv_msg = mv_msg.
  ENDMETHOD.
ENDCLASS.

  • 7.1 用 CREATE OBJECT mo_log，改為 NEW #( )；另外原範例把「靜態屬性」命名為 MO_LOG，MO_ 前綴在一般命名慣例表示「實例屬性（member）」，靜態屬性應用 GO_（或 SO_）以免誤讀，改寫版改為 GO_INSTANCE。原範例 ro_log = mo_log. 的縮排跑到 IF 裡，看起來像在 IF 內，其實在外面，屬於排版問題。

實務提醒：Singleton 的「唯一」到哪裡為止？

範圍是否唯一說明
同一支程式、同一次執行是靜態屬性存在內部工作階段（internal session）
SUBMIT／CALL TRANSACTION 叫起的另一支程式否新的 internal session，重新建立
同一使用者的另一個 GUI 視窗、另一位使用者、背景作業否完全不同的工作階段
RFC 呼叫進來的遠端程式否遠端系統自己的工作階段
  • 真正要「跨使用者共用一份資料」，要用共用記憶體物件（Shared Objects，SHMA）或資料庫表，不是 Singleton。
  • Singleton 等於一個全域變數，會讓單元測試變難（前一個測試留下的狀態會影響下一個）。常見折衷：GET_INSTANCE 回傳介面型別，並提供測試用的注入點（例如 ABAP Unit 的 FOR TESTING 友誼類別替換實例），詳見 7-6 章。
  • 日誌類別在正式專案中通常不是自己寫 WRITE，而是包裝應用日誌（Application Log）：7.53 可用函數 BAL_LOG_CREATE／BAL_LOG_MSG_ADD／BAL_DB_SAVE，較新版本另有類別 API CL_BALI_LOG（ABAP Cloud 用；在 on-premise 需較新的 S/4HANA 版本才有，1809 請用 BAL 函數）。這時 ZCL_LOG 做 Singleton 就很合理：整支程式共用一個 log handle，最後一次存檔。

5. Adapter（一）：觀念與被轉接的舊函數模組（7.5）

觀念：新程式希望透過一個乾淨的介面（Target）工作，但實際能做事的是一段介面不相容的既有程式（Adaptee，這裡是函數模組）。Adapter 實作 Target 介面，內部去呼叫 Adaptee，負責參數對應與錯誤轉換。客戶端從頭到尾只認得 Target。

UML（文字版，物件轉接器 Object Adapter）
 Client ----------> «interface» ZIF_TARGET
                     + create_doc( iv_output_device ) : host_name
                              ^
                              | implements
                     ZCL_ADAPTER
                     + zif_target~create_doc( )  ---calls--->  FUNCTION ZFM_CREATE_DOC_DB
                                                                (Adaptee：舊介面、傳統例外)

GoF 另有「類別轉接器（Class Adapter）」：Adapter 同時繼承 Adaptee 類別並實作 Target 介面。ABAP 是單一繼承，但 Adaptee 若是類別，仍可「繼承 Adaptee ＋ 實作 Target 介面」。本例 Adaptee 是函數模組，只能用物件轉接器（組合／呼叫）。

範例（改寫後）：函數模組依輸出裝置名稱讀取 TSP03D（輸出裝置主檔，SPAD 維護）的 PAPROSNAME，當作「文件資料庫主機」回傳。

*"*"Local Interface:
*"  IMPORTING
*"     VALUE(OUTPUT_DEVICE) TYPE  TSP03D-NAME
*"  EXPORTING
*"     VALUE(HOST_NAME) TYPE  TSP03D-PAPROSNAME
*"  EXCEPTIONS
*"      DEVICE_NOT_FOUND
*"----------------------------------------------------------------------
  CLEAR host_name.

  IF output_device IS INITIAL.
    RAISE device_not_found.
  ENDIF.

  " 原範例用迴圈式 SELECT 讀一筆；只要一筆就用 SELECT SINGLE
  SELECT SINGLE paprosname
    FROM tsp03d
    WHERE name = @output_device
    INTO @host_name.
  IF sy-subrc <> 0.
    RAISE device_not_found.
  ENDIF.

  " 模擬：連線文件資料庫 → 建立文件 → 中斷連線
  " （原範例在此用 WRITE 印三行；函數模組不應直接輸出畫面，改由呼叫端記錄）
ENDFUNCTION.

與原範例的差異（含範例錯誤修正）：

  • 邏輯錯誤：原範例的 IF sy-subrc = 0. 寫在 IF output_device IS NOT INITIAL ... ENDIF. 之外。當輸入空白時根本沒有執行 SELECT，sy-subrc 是「前一個敘述」留下的值，很可能剛好是 0，就會印出「連接到文件資料庫：（空白）」。改寫版在空白時直接 RAISE。
  • 原範例用 SELECT ... INTO (host_name) ... WHERE ... 的迴圈式寫法（以 ENDSELECT 收尾）只為讀一筆，改為 SELECT SINGLE＋@ 主機變數，並把 INTO 放在最後（7.40 SP08 以後的嚴格模式寫法）。
  • 原範例 WRITE: / '連接到文檔數據庫:', host_name.. 多打了一個句點（多出來的句點在 ABAP 是一個空敘述，不會報錯，但屬於筆誤）。
  • 原範例沒有定義任何例外，呼叫端無法得知失敗；改寫版加上傳統例外 DEVICE_NOT_FOUND，因為這支是「舊介面」，刻意保留傳統例外，讓下一節的 Adapter 示範「把傳統例外轉成類別式例外」。
  • 欄位語意提醒：TSP03D-PAPROSNAME 在標準系統中是輸出裝置在主機（作業系統）端的印表機名稱，書中只是借用這個欄位「模擬」文件資料庫主機名，並非 SAP 有這種用途。TSP03D 的主鍵是 PADEST（短名）；NAME 是長名稱，在 SPAD 中同樣不可重複，所以用 SELECT SINGLE 讀取沒有問題。

6. Adapter（二）：轉接器類別與呼叫端（7.6、7.7）

14. Strategy（一）：MRP 策略的結構（7.24～7.26）

觀念：MRP 計劃可以用不同演算法（策略 Z1、Z2、Z3⋯），而且要能在執行期切換。Strategy 把每個演算法封裝成一個類別，實作同一個抽象；使用演算法的 Context（ZCL_MRP）只持有「目前策略」的參照並委派呼叫。新增演算法 = 新增一個類別，ZCL_MRP 不用改（開放封閉原則）。

SAP 標準做法：帶過濾器的 BAdI 就是 Strategy。「同一個介面、多個實作、執行期依某個值挑一個」正是新式 BAdI 的過濾器機制：BAdI 定義就是 Strategy 抽象，每個 BAdI 實作是一個具體策略，過濾值就是策略代碼，GET BADI 則取代了自建的對照表與動態 CREATE OBJECT。好處是有 Enhancement Spot 管理、可切換啟用、傳輸與升級工具（SPAU_ENH）都支援。完整建立步驟見 3-4 章 第 9～11 節。

" SE18：Enhancement Spot ZES_MRP_STRATEGY，BAdI 定義 ZBADI_MRP_STRATEGY（單一使用）
"       介面 ZIF_BADI_MRP_STRATEGY：METHODS call_algorithm EXPORTING ev_result TYPE string.
"       過濾器 STRATEGY（CHAR2）
" SE19：為 Z1 / Z2 / Z3 各建一個 BAdI 實作，分別設定過濾值

DATA lo_badi   TYPE REF TO zbadi_mrp_strategy.
DATA lv_result TYPE string.

TRY.
    GET BADI lo_badi FILTERS strategy = p_code.      "依過濾值選出一個實作＝選策略
    CALL BADI lo_badi->call_algorithm IMPORTING ev_result = lv_result.
    MESSAGE lv_result TYPE 'S'.
  CATCH cx_badi_not_implemented.
    MESSAGE |策略 { p_code } 沒有任何啟用中的實作| TYPE 'I' DISPLAY LIKE 'E'.
  CATCH cx_badi_multiply_implemented.
    MESSAGE |策略 { p_code } 有多個實作同時啟用（單一使用 BAdI 不允許）| TYPE 'I' DISPLAY LIKE 'E'.
ENDTRY.
先標準再客製（Casper 的第三條經驗）：書中以「MRP 策略」為題材，但真實的 MRP 演算法不要自己重寫。SAP 標準以設定提供了大量「策略」：MRP 類型（MARC-DISMM，如 PD、VB、VM、ND；設定 OMDQ）、批量程序（MARC-DISLS，如 EX、FX、HB；設定 OMI4）、計劃策略（策略群組）。順序永遠是：標準設定 → BAdI／Enhancement Spot → Enhancement Point → 修改標準，每往右一步升級成本高一個量級。自建 Strategy 模式適合用在「確實沒有標準、且你自己的 Z 程式有多種演算法要切換」的情境，例如自建報表的多種成本分攤方式。
又是 HANA 排序的坑：如果策略是「從設定表讀出第一筆符合的規則」，例如同一物料同時符合兩條規則，就必須在 SELECT 加 ORDER BY（或在設定表加優先順序欄位），否則 HANA 今天給你 Z1、明天給你 Z2，MRP 結果就會不穩定——這和 Casper 遇到的成本評價「一下抓到 H、一下抓到 E」是同一種問題，結論也一樣：明確排序、固定規則。

16. 六個模式的比較與選用

模式要解決的痛點ABAP 關鍵語法什麼時候不要用
Singleton某個物件只能有一份（日誌、快取、連線）CREATE PRIVATE、FINAL、CLASS-DATA、CLASS_CONSTRUCTOR只是懶得傳參數時；需要跨使用者共用時（改用 Shared Objects 或 DB）
Adapter現成功能的介面跟我要的不一樣INTERFACES、CALL FUNCTION、例外轉換 RAISE EXCEPTION TYPE已有 released API 可以直接用時
Bridge兩個維度組合造成類別爆炸（m × n）抽象類別＋介面參照、動態 CREATE OBJECT TYPE (name)只有一個會變的維度（那是 Strategy）
Facade子系統太複雜，呼叫端要知道太多一個公開方法、建構子組裝子系統Facade 開始長出業務邏輯、變成「上帝類別」時
Observer一個狀態改變要通知不特定多個對象EVENTS、RAISE EVENT、SET HANDLER（或自建清單）通知對象固定且有先後依賴時（直接依序呼叫更清楚）
Strategy同一件事有多種演算法，要在執行期切換抽象類別／介面、setter 注入、BAdI 過濾器標準設定已提供選項時；只有兩種且不會再增加時（COND／SWITCH 就夠）

模式之間的組合在實務中很常見：本章的 Bridge 抽象類別內含 Template Method；Strategy 物件常由 Factory 建立；Facade 常做成 Singleton；Adapter 常藏在 Facade 後面。模式是溝通用的詞彙——在設計文件寫「ZCL_MRP 用 Strategy，策略由 BAdI 過濾器提供」，團隊成員一眼就懂結構。

舊語法對照（本章範例出現過的）：CREATE OBJECT x. → x = NEW #( ).；CREATE OBJECT x TYPE zcl_y. → x = NEW zcl_y( ).；CREATE OBJECT x TYPE (lv_name). → 維持不變（動態）；CALL METHOD super->m EXPORTING iv = v. → super->m( v ).；在類別方法內 WRITE → 方法回傳資料、由呼叫端決定輸出；迴圈式 SELECT 讀單筆 → SELECT SINGLE ... INTO @var。更多對照見 附錄 ap-01。

練習與自我檢核

  1. Singleton 的三個要件是什麼？若 ZCL_LOG 忘了設 CREATE PRIVATE，7.4 的測試結果會改變嗎？
    參考答案：CREATE PRIVATE（外界不能 NEW）、私有靜態屬性保存實例、公開靜態 GET_INSTANCE；建議再加 FINAL。忘了設 CREATE PRIVATE 時，7.4 仍印出 Equal（因為兩次都走 GET_INSTANCE），但別的程式可以 NEW 出第二個實例，唯一性沒有被強制——測試通過不代表設計正確。
  2. 使用者 A 與使用者 B 同時執行同一支用 ZCL_LOG 的報表，他們共用同一個日誌物件嗎？
    參考答案：不共用。靜態屬性存在各自的 internal session；跨使用者共用要用 Shared Objects（SHMA）或資料庫。
  3. 指出 7.5 函數模組的邏輯錯誤並修正。
    參考答案：IF sy-subrc = 0 放在 IF output_device IS NOT INITIAL 之外，輸入空白時 sy-subrc 是前一敘述留下的值；應在空白時直接回報錯誤，並把迴圈式 SELECT 改為 SELECT SINGLE ... WHERE name = @output_device INTO @host_name。另有「host_name..」多一個句點的筆誤。
  4. Adapter 除了「轉呼叫」之外還應該負責什麼？在 S/4HANA Clean Core 中它扮演什麼角色？
    參考答案：參數與型別對應、把傳統例外／BAPIRET2 轉成類別式例外、交易邊界不在 wrapper 內 COMMIT。Clean Core 中，為未釋出的舊 API 建立 Tier 2 wrapper 類別給 ABAP Cloud 使用，就是 Adapter。
  5. 生產訂單有 4 種類型、輸出文件有 5 種，用純繼承與用 Bridge 各需要幾個具體類別？
    參考答案：純繼承 4 × 5 = 20 個；Bridge 為 4 ＋ 5 = 9 個（另加一個抽象類別與一個介面）。
  6. 為什麼 7.12、7.27 不能把 CREATE OBJECT 改成 NEW？動態建立要注意什麼？
    參考答案：NEW 的型別必須編譯期確定，不支援 TYPE (變數)。注意：類別名要大寫；允許的類別要逐筆列舉成白名單而不是用前綴或區間放行；每筆各自 TRY CATCH cx_sy_create_object_error。
  7. 7.16 的 TRY … CATCH cx_sy_create_object_error 包住靜態 CREATE OBJECT，有作用嗎？
    參考答案：沒有。這個例外只在動態建立（類別不存在、抽象、不可建立）時發生，靜態建立已存在的類別在編譯期就檢查過了。
  8. 找出 7.17～7.20 之間的兩個不一致。
    參考答案：① 結構元件在 7.17 叫 GI_GROUP，7.18／7.20 卻使用 GROUP；② 7.17 的 attach／detach／notify_reorder 定義沒有參數，但實作用到 II_PURCHASING_GROUP、IV_GROUP_ID、IV_STATUS。另外觀察者清單放在 PUBLIC、非唯一鍵、區域變數用 MS_ 前綴，也都需要調整。
  9. 7.22 的採購組編號 '1001'、'3023'、'4045' 放到標準欄位 EKGRP 會發生什麼事？
    參考答案：EKGRP 是 CHAR3，會被截成 '100'、'302'、'404'，不同的四碼值可能截成相同三碼而互相覆蓋，應直接使用三碼的真實採購組並以 T024 驗證。
  10. 手工 Observer（7.17～7.22）與原生事件（7.23）各有什麼優缺點？什麼情況下只能選手工版？
    參考答案：原生事件耦合更低、不用自建清單、支援 FOR ALL INSTANCES，但事件處理方法無法回傳值給觸發者；需要收集觀察者的回應（例如每個採購組回報處理結果）時，用手工版（介面方法有 RETURNING）。
  11. 自建 Strategy 讀設定表「取第一筆符合規則」時要注意什麼？
    參考答案：HANA 沒有預設排序，必須 ORDER BY 或設優先順序欄位，否則結果不穩定（同 Casper 成本評價 H／E 案例）。
  12. SAP 標準中哪個機制最接近 Strategy？哪些模式可以在 OOALV 中看到？
    參考答案：帶過濾器的新式 BAdI（GET BADI … FILTERS）。CL_GUI_ALV_GRID 的事件（DOUBLE_CLICK、TOOLBAR、USER_COMMAND）是 Observer；CL_SALV_TABLE=>FACTORY 是 Factory，SALV 本身對 ALV 的複雜功能而言也是一種 Facade。
  13. 實作題：把第 13 節的 ZCL_SUBJECT 改寫成「庫存物件」，事件帶出 MATNR、WERKS 與可用量；寫兩個觀察者：一個在可用量低於安全庫存時記錄訊息、另一個統計被通知次數，並示範 FOR ALL INSTANCES 註冊。
