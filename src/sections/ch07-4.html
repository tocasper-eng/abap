3. 反例：用 IF／ELSEIF 寫死物料類型（範例 6.1）

觀念：範例 6.1 是典型的「程序式分支」：讀出物料類型 MARA-MTART 後，用 IF／ELSEIF 判斷是原料（ROH）就提示檢查採購合約、是成品（FERT）就提示檢查銷售合約。問題不在它今天能不能跑，而在明天多一種物料類型（例如半成品 HALB）時，你必須打開這支已經上線的程式改 IF——每改一次就要重測、重傳輸，改的人越多，分支越長。這正是 OCP 要避免的「對修改開放」。

" 範例 6.1 的現代寫法（仍是反例，用來對照）
REPORT zrep_cls_021.

PARAMETERS p_matnr TYPE matnr OBLIGATORY.

START-OF-SELECTION.
  SELECT SINGLE mtart
    FROM mara
    WHERE matnr = @p_matnr
    INTO @DATA(lv_mtart).
  IF sy-subrc <> 0.
    MESSAGE |物料 { p_matnr ALPHA = OUT } 不存在| TYPE 'S' DISPLAY LIKE 'E'.
    RETURN.
  ENDIF.

  " 每新增一種物料類型，就得回來改這裡 —— 違反開放封閉
  DATA(lv_text) = SWITCH string( lv_mtart
    WHEN 'ROH'  THEN `此物料為原料，需檢查採購合約`
    WHEN 'FERT' THEN `此物料為成品，需檢查銷售合約`
    ELSE             |物料類型 { lv_mtart } 未定義處理方式| ).

  MESSAGE lv_text TYPE 'I'.

與原範例的差異：原範例用 PARAMETERS … LIKE mara-matnr、SELECT SINGLE … INTO gv_material_type（無 @）與 WRITE 清單輸出；宣告了 gv_material 卻沒用到；找不到物料或類型不是 ROH／FERT 時畫面一片空白，沒有任何提示。改寫版用 TYPE matnr（帶 ALPHA／MATN1 轉換）、內嵌宣告與 SWITCH，並補上 ELSE 分支。

改成 SWITCH 只是「比較好讀的 IF」，並沒有解決 OCP 問題——新增類型時依然要改這段程式。真正的解法是把「每種類型各自的行為」搬進各自的類別，並把「哪個類型對應哪個類別」搬到資料（註冊表）裡，見下面第 4～7 節。

成品類別多了一個 SHOW_MATERIAL_FIN。呼叫端手上是 REF TO zcl_material，看不到這個方法，必須先判斷型別再向下轉型：IF lo_mat IS INSTANCE OF zcl_material_fin.（7.50 起）→ CAST zcl_material_fin( lo_mat )->show_material_fin( )。如果呼叫端到處都在做這種判斷，代表抽象設計不夠，又走回第 3 節的 IF 分支老路了。

觀念：OCP 的關鍵一步是把「哪個物料類型用哪個類別」從程式碼搬到資料。範例用一張自建表 ZINSP_DESC_T 當註冊表（registry），欄位名可從範例的 SELECT 看出：MATERIAL_TYPE（物料類型）與 CLASS_TYPE（類別名）。

欄位Key資料元素（建議）說明
MANDT✔MANDT用戶端，讓 SM30 依用戶端維護
MATERIAL_TYPE✔MTART物料類型，check table 可設 T134

建立與維護步驟 （依講義步驟整理）：

  1. SE11 建表 ZINSP_DESC_T，交付類別（Delivery Class）建議 C（客製化資料，會進客製化請求 Customizing Request），技術設定可設完全緩衝（筆數極少、幾乎只讀）。
  2. SE11 選單 Utilities → Table Maintenance Generator（或 SE54）產生維護畫面：授權群組、函數群組、一步式（One step）維護。

6. 工廠方法 GET_MATERIAL_OBJ：查註冊表＋動態建立（範例 6.2、6.4 下半）

觀念：工廠類別 ZCL_MATL_SPL_FACTORY 提供靜態方法 GET_MATERIAL_OBJ：① 依物料號碼查 MARA 取得物料類型 → ② 依物料類型查註冊表取得類別名 → ③ 用 CREATE OBJECT … TYPE (變數) 動態建立物件，以父類型別回傳。之後新增物料類型，工廠本身一行都不用改。

CLASS zcl_matl_spl_factory DEFINITION PUBLIC FINAL CREATE PRIVATE.
  PUBLIC SECTION.
    "! 依物料類型建立對應的物料物件；未登記時回傳未繫結的參考
    CLASS-METHODS get_material_obj
      IMPORTING iv_material_id     TYPE matnr
      RETURNING VALUE(ro_material) TYPE REF TO zcl_material
      RAISING   cx_sy_create_object_error.
ENDCLASS.

CLASS zcl_matl_spl_factory IMPLEMENTATION.
  METHOD get_material_obj.
    " ① 物料號碼 → 物料類型
    SELECT SINGLE mtart
      FROM mara
      WHERE matnr = @iv_material_id
      INTO @DATA(lv_mtart).
    IF sy-subrc <> 0.
      RETURN.
    ENDIF.

    " ② 物料類型 → 類別名（以完整主鍵讀取，結果唯一，不受 HANA 排序影響）
    SELECT SINGLE class_type
      FROM zinsp_desc_t
      WHERE material_type = @lv_mtart
      INTO @DATA(lv_class).
    IF sy-subrc <> 0.
      RETURN.   "未登記：由呼叫端決定如何提示
    ENDIF.

    " ③ 動態建立。類別名必須大寫；類別不存在、是抽象類、
    "    或不是 ZCL_MATERIAL 的子類，都會丟 CX_SY_CREATE_OBJECT_ERROR
    DATA(lv_type_name) = to_upper( condense( lv_class ) ).
    CREATE OBJECT ro_material TYPE (lv_type_name)
      EXPORTING iv_matnr = iv_material_id.
  ENDMETHOD.
ENDCLASS.

與原範例的差異：

  • 原範例宣告了 lv_material、lv_method_name 兩個沒用到的變數；用 TRANSLATE … TO UPPER CASE 轉大寫，改寫為 to_upper( )。
  • 原範例的第二個 IF sy-subrc = 0 同時承接「查不到物料」與「註冊表沒登記」兩種情況，靠的是 sy-subrc 碰巧沒被覆蓋；結構一改就可能判斷錯。改寫版每個 SELECT 後立即檢查。
  • 原範例在工廠內 CATCH cx_sy_create_object_error 後用 MESSAGE … TYPE 'I' 彈窗——工廠是模型層，不該碰畫面（背景作業或 RFC 呼叫時彈窗會出問題），而且吞掉例外後呼叫端只拿到未繫結參考，分不出是「沒登記」還是「類別名打錯」。改寫版在簽章宣告 RAISING，讓呼叫端處理。
  • 原範例建立物件時沒傳物料號碼，子類的 MV_MATERIAL 永遠是空的；改寫版以 EXPORTING iv_matnr 傳給建構子。
  • 書中範例 6.2 與 6.4 下半段是同一個方法，只差一句註解措辭，本章合併講解。
為什麼這裡還是 CREATE OBJECT？ 本部規定以 NEW 取代 CREATE OBJECT，但 NEW 運算子只接受靜態型別（NEW zcl_x( ) 或 NEW #( )），類別名放在變數裡的動態建立，到 7.5x 為止仍只能用 CREATE OBJECT … TYPE (name)。這是現代 ABAP 中 CREATE OBJECT 唯一的正當用途。動態型別與 RTTI 的其他寫法見 5-2 章第 20 節。
Casper 經驗第 1 條「HANA 沒有預設排序」：這裡兩個 SELECT SINGLE 都是用完整主鍵讀（MARA 的 MATNR、註冊表的 MANDT＋MATERIAL_TYPE），結果唯一，所以安全。如果日後註冊表加了「工廠」「有效日期」之類的鍵欄位，而程式只用部分鍵讀 SELECT SINGLE，HANA 回哪一筆就不保證了——那時必須改成 ORDER BY 明確排序後取第一筆（UP TO 1 ROWS），否則同一個物料今天建出 A 類、明天建出 B 類。

7. 呼叫端程式：只認識抽象類別（範例 6.3）

觀念：呼叫端不必建立工廠實例，直接用類別名呼叫靜態方法取得物件，再呼叫抽象方法。它從頭到尾不知道有 RAW、FIN、SEMI 這些子類——這就是「對修改封閉」：新增子類時，這支報表不用動。

REPORT zrep_cls_022.

PARAMETERS p_matnr TYPE matnr OBLIGATORY.

START-OF-SELECTION.
  TRY.
      " 不必建立工廠實例，直接呼叫靜態方法取得子類物件
      DATA(lo_material) = zcl_matl_spl_factory=>get_material_obj( p_matnr ).

      IF lo_material IS NOT BOUND.
        MESSAGE |物料 { p_matnr ALPHA = OUT } 不存在，或其物料類型未在 ZINSP_DESC_T 登記|
          TYPE 'S' DISPLAY LIKE 'W'.
        RETURN.
      ENDIF.

      " 多型：實際執行哪個子類的實作，由註冊表決定
      MESSAGE lo_material->get_insp_desc( ) TYPE 'I'.

      " 子類獨有的方法要先確認型別再向下轉型（7.50 起的 IS INSTANCE OF）
      IF lo_material IS INSTANCE OF zcl_material_fin.
        MESSAGE CAST zcl_material_fin( lo_material )->show_material_fin( ) TYPE 'S'.
      ENDIF.

    CATCH cx_sy_create_object_error INTO DATA(lx_create).
      " 註冊表登記的類別名打錯、類別未啟用、或不是 ZCL_MATERIAL 的子類
      MESSAGE lx_create->get_text( ) TYPE 'S' DISPLAY LIKE 'E'.
  ENDTRY.

與原範例的差異：原範例 CATCH cx_root 一網打盡，還留了一個空的 CLEANUP 區塊（在最外層 TRY 中沒有意義，CLEANUP 只在例外「往外傳」時才執行）；輸出用 WRITE。改寫版只抓工廠宣告的例外，其他非預期錯誤就讓它 DUMP 到 ST22，比默默印一行字好追。

擴充演練——新增半成品只需兩步：① SE24 建立 ZCL_MATERIAL_SEMI（範例 6.4 已提供）；② SM30 在 ZINSP_DESC_T 加一筆 HALB → ZCL_MATERIAL_SEMI。報表 ZREP_CLS_022、工廠 ZCL_MATL_SPL_FACTORY、既有子類全部不動、不必重測。這就是勘誤 7 所說：「開放－封閉」原則，即軟體擴充時只新增程式碼，而不是修改原有程式碼。

8. OCP 在 SAP 標準裡的樣子：BAdI 就是官方版的註冊表

把第 4～7 節的結構和 SAP 增強框架並排，你會發現幾乎一對一：

" 過濾器 MTART；每個物料類型在 SE19 建一個帶過濾值的實作）
DATA lo_badi TYPE REF TO zbadi_matl_insp.

    GET BADI lo_badi

Casper 經驗第 3 條「先找標準，再想客製」＝對擴充開放、對修改封閉。 標準設定 → BAdI／Enhancement Spot → Enhancement Point → 修改標準，這條升級路線本身就是 OCP：越左邊越是「在 SAP 預留的擴充點上加新程式碼」，越右邊越是「打開別人已上線的程式來改」。修改標準（Modification）之所以成本高一個量級，正是因為違反了「對修改封閉」——每次升級都要在 SPAU 重新比對。自己寫 Z 程式時也一樣：先設計出擴充點（註冊表、介面、BAdI），日後需求變動就只是「加」，不是「改」。
什麼時候用自建註冊表、什麼時候自建 BAdI？註冊表簡單、業務顧問用 SM30 就能維護，適合「同一套程式、不同組織單位要不同行為」；BAdI 有 SE18／SE19 的工具支援、可跨套件交付、有 Fallback Class，適合「要讓別的團隊或客戶擴充」。兩者都比第 3 節的 IF／SWITCH 好。

9. 里氏替換原則：長方形與正方形（範例 6.5、6.6）

觀念：LSP 說的是「凡是用父類別的地方，換成子類別物件，程式仍然正確」。數學上正方形是一種長方形，所以直覺上 ZCL_SQUARE 繼承 ZCL_RECTANGLE 很合理；但長方形的行為契約是「設定寬度不會改變高度」，正方形為了保持四邊相等，重定義 setter 讓寬高連動，就把這個契約打破了。「is-a」要看行為，不是看名詞。

" 範例 6.5：長方形（改寫：屬性改為 PROTECTED，避免外部繞過 setter）
CLASS zcl_rectangle DEFINITION PUBLIC CREATE PUBLIC.
  PUBLIC SECTION.
    METHODS set_width  IMPORTING iv_width  TYPE i.
    METHODS set_height IMPORTING iv_height TYPE i.
    METHODS get_area   RETURNING VALUE(rv_area) TYPE i.
  PROTECTED SECTION.
    DATA mv_width  TYPE i.
    DATA mv_height TYPE i.
ENDCLASS.

CLASS zcl_rectangle IMPLEMENTATION.
  METHOD set_width.
    mv_width = iv_width.
  ENDMETHOD.
  METHOD set_height.
    mv_height = iv_height.
  ENDMETHOD.
  METHOD get_area.
    rv_area = mv_width * mv_height.
  ENDMETHOD.
ENDCLASS.

" 範例 6.6：正方形繼承長方形，重定義兩個 setter 讓寬高同步
CLASS zcl_square DEFINITION PUBLIC INHERITING FROM zcl_rectangle FINAL CREATE PUBLIC.
  PUBLIC SECTION.
    METHODS set_width  REDEFINITION.
    METHODS set_height REDEFINITION.
ENDCLASS.

CLASS zcl_square IMPLEMENTATION.
  METHOD set_width.
    mv_width  = iv_width.
    mv_height = iv_width.     "改寬也改高 → 打破長方形的契約
  ENDMETHOD.
  METHOD set_height.
    mv_height = iv_height.
    mv_width  = iv_height.
  ENDMETHOD.
ENDCLASS.

與原範例的差異：原範例把 MV_WIDTH／MV_HEIGHT 放在 PUBLIC SECTION，外部可以直接 lo->mv_width = 5 繞過正方形的 setter，連「正方形寬高相等」都保證不了。改成 PROTECTED（子類仍可存取）；若要讓外部讀，可用 PUBLIC SECTION … DATA … READ-ONLY。其餘邏輯與原範例相同，這兩支範例本來就是「刻意示範錯誤設計」。

10. 驗證 LSP 被打破：從 ASSERT 到 ABAP Unit（範例 6.7、6.8）

觀念：範例 6.7 用長方形跑「寬 3、高 6，面積應為 18」，ASSERT 通過；範例 6.8 把同一段程式換成正方形，set_height( 6 ) 把寬也改成 6，面積變 36，ASSERT 失敗、程式短傾印（ASSERTION_FAILED）。同一段「以長方形為前提」的程式，換成子類就壞掉——LSP 被違反的鐵證。

比起在報表裡寫 ASSERT，更好的作法是把「長方形的行為契約」寫成 ABAP Unit 測試，並讓每個子類都跑同一組測試（契約測試）。ABAP Unit 的原廠說明見 5-2 章第 17 節。

" 放在 ZCL_RECTANGLE 的 Local Test Classes（SE24／ADT 的 Test Classes 頁籤）
CLASS ltc_rectangle_contract DEFINITION FINAL FOR TESTING
  RISK LEVEL HARMLESS DURATION SHORT.
  PRIVATE SECTION.
    METHODS check_contract IMPORTING io_rect TYPE REF TO zcl_rectangle.
    METHODS rectangle_keeps_contract FOR TESTING.   "對應範例 6.7
    METHODS square_keeps_contract    FOR TESTING.   "對應範例 6.8
ENDCLASS.

CLASS ltc_rectangle_contract IMPLEMENTATION.
  METHOD check_contract.
    " 長方形的契約：寬、高互不影響
    io_rect->set_width( 3 ).
    io_rect->set_height( 6 ).
    cl_abap_unit_assert=>assert_equals(
      act = io_rect->get_area( )
      exp = 18
      msg = |{ cl_abap_classdescr=>get_class_name( io_rect ) } 不符合長方形的行為契約| ).
  ENDMETHOD.

  METHOD rectangle_keeps_contract.
    check_contract( NEW zcl_rectangle( ) ).        "通過：18
  ENDMETHOD.

  METHOD square_keeps_contract.
    check_contract( NEW zcl_square( ) ).           "失敗：實際 36
  ENDMETHOD.
ENDCLASS.

與原範例的差異：

  • 範例 6.7 與 6.8 的 REPORT 名稱都是 ZREP_CLS_023，實際上是同一支程式的兩個版本；兩支都宣告了 go_rectangle 與 go_square 但各只用到一個。
  • 範例 6.8 直接用 go_square 呼叫，嚴格說還不是「替換」。真正的 LSP 情境是變數型別仍是長方形、物件卻是正方形：DATA lo_rect TYPE REF TO zcl_rectangle. lo_rect = NEW zcl_square( ).——呼叫端以為自己拿的是長方形，結果行為不同。上面的契約測試正是這樣寫（參數型別是 ZCL_RECTANGLE）。
  • 原範例的 CREATE OBJECT go_square. 改為 NEW zcl_square( )；WRITE: / 'Area is:', lv_area. 改由測試框架報告結果。
ASSERT 在正式程式中失敗會直接短傾印，使用者看到的是 ST22 的 ASSERTION_FAILED。要在正式程式留斷言，請用 ASSERT ID <checkpoint group> CONDITION … 搭配 SAAB 控制是否啟用；驗證設計契約則交給 ABAP Unit（Ctrl+Shift+F10 執行，或 ATC 一併跑）。

11. 修正 LSP：共同介面＋不可變物件

正方形不該繼承「可以分別改寬高」的長方形。常見兩種修法：① 抽出共同介面 ZIF_SHAPE，只保證「能算面積」，長方形與正方形各自實作、互不繼承；② 讓形狀成為不可變物件（值在建構子給定、沒有 setter），就不存在「改寬連帶改高」的問題。

INTERFACE zif_shape PUBLIC.
  METHODS get_area RETURNING VALUE(rv_area) TYPE i.
ENDINTERFACE.

CLASS zcl_rect_v2 DEFINITION PUBLIC FINAL CREATE PUBLIC.
  PUBLIC SECTION.
    INTERFACES zif_shape.
    METHODS constructor IMPORTING iv_width TYPE i iv_height TYPE i.
    DATA mv_width  TYPE i READ-ONLY.
    DATA mv_height TYPE i READ-ONLY.
ENDCLASS.
CLASS zcl_rect_v2 IMPLEMENTATION.
  METHOD constructor.
    mv_width  = iv_width.
    mv_height = iv_height.
  ENDMETHOD.
  METHOD zif_shape~get_area.
    rv_area = mv_width * mv_height.
  ENDMETHOD.
ENDCLASS.

CLASS zcl_square_v2 DEFINITION PUBLIC FINAL CREATE PUBLIC.
  PUBLIC SECTION.
    INTERFACES zif_shape.
    METHODS constructor IMPORTING iv_side TYPE i.
    DATA mv_side TYPE i READ-ONLY.
ENDCLASS.

  ENDMETHOD.

使用端只依賴介面，任何形狀都能放進來替換，而不改變正確性：

  ( NEW zcl_rect_v2( iv_width = 3 iv_height = 6 ) )
  ( NEW zcl_square_v2( iv_side = 6 ) ) ).

DATA(lv_total) = REDUCE i( INIT s = 0
                           FOR lo_shape IN lt_shapes
                           NEXT s = s + lo_shape->get_area( ) ).

MESSAGE |面積合計：{ lv_total }| TYPE 'I'.   "18 + 36 = 54
SAP 業務物件上的 LSP 陷阱更常見：例如寫一個「採購單」父類，再讓「寄售採購單」「外包採購單」繼承並重定義過帳邏輯，結果某個子類在 post( ) 裡偷偷不做 GR／IR 檢查——呼叫端依父類假設寫的對帳程式就會出錯。判斷準則：子類的前置條件不可以更嚴、後置條件不可以更鬆、不可以丟父類沒宣告的例外。做不到，就改用組合或介面，不要硬繼承。

12. 依賴反轉：反例——操作類直接依賴資料庫讀取類（範例 6.9）

觀念：DIP 有兩句話：「高層模組不應依賴低層模組，兩者都應依賴抽象」「抽象不應依賴細節，細節應依賴抽象」。範例 6.9 中，高層的「訂單操作類」ZCL_ORDER_OPERATOR_1 的 READ_ORDER 方法參數型別直接寫死成低層的具體類別 ZCL_READ_ORDER_DB_1——今天訂單來源從資料庫改成 XML、Excel 或 OData，就必須打開操作類修改方法簽章與內容。

範例只提供了呼叫端報表，兩個類別的本體沒有附上；依呼叫方式推定其結構如下（依範例推定）：

13. 依賴反轉：介面 ZIF_READ_ORDER 與 DB／XML 兩種實作（範例 6.10，勘誤 9）

觀念：在高層與低層之間插入介面 ZIF_READ_ORDER。操作類只認識介面；資料庫讀取類、XML 讀取類都「往上」實作這個介面——依賴的箭頭從「高層 → 低層」反轉成「低層 → 抽象 ← 高層」，這就是「反轉」二字的由來。以下類別本體同樣依範例 6.10 的呼叫方式推定（依範例推定），訂單資料以 VBAK 為例：

INTERFACE zif_read_order PUBLIC.
  TYPES: BEGIN OF ty_order,
           vbeln TYPE vbak-vbeln,
           erdat TYPE vbak-erdat,
           kunnr TYPE vbak-kunnr,
           netwr TYPE vbak-netwr,
           waerk TYPE vbak-waerk,
         END OF ty_order,
         tt_order TYPE STANDARD TABLE OF ty_order WITH EMPTY KEY.
  METHODS read_order RETURNING VALUE(rt_order) TYPE tt_order.
ENDINTERFACE.

" 低層實作一：從資料庫讀
CLASS zcl_read_order_db DEFINITION PUBLIC FINAL CREATE PUBLIC.
  PUBLIC SECTION.
    INTERFACES zif_read_order.
ENDCLASS.
CLASS zcl_read_order_db IMPLEMENTATION.
  METHOD zif_read_order~read_order.
    SELECT vbeln, erdat, kunnr, netwr, waerk
      FROM vbak
      WHERE erdat >= @( sy-datum - 7 )
      ORDER BY vbeln                    "HANA 無預設排序，一定要明確排序
      INTO TABLE @rt_order
      UP TO 500 ROWS.
  ENDMETHOD.
ENDCLASS.

" 低層實作二：從 XML 字串讀（asXML 格式，用恆等轉換 ID 反序列化）
CLASS zcl_read_order_xml DEFINITION PUBLIC FINAL CREATE PUBLIC.
  PUBLIC SECTION.
    INTERFACES zif_read_order.
    METHODS constructor IMPORTING iv_xml TYPE string.
  PRIVATE SECTION.
    DATA mv_xml TYPE string.
ENDCLASS.
CLASS zcl_read_order_xml IMPLEMENTATION.
  METHOD constructor.
    mv_xml = iv_xml.
  ENDMETHOD.
  METHOD zif_read_order~read_order.
    TRY.
        CALL TRANSFORMATION id
          SOURCE XML mv_xml
          RESULT orders = rt_order.
      CATCH cx_transformation_error INTO DATA(lx_xml).
        MESSAGE lx_xml->get_text( ) TYPE 'S' DISPLAY LIKE 'E'.
        CLEAR rt_order.
    ENDTRY.
  ENDMETHOD.
ENDCLASS.

" 高層：訂單操作類只依賴介面
CLASS zcl_order_operator DEFINITION PUBLIC FINAL CREATE PUBLIC.
  PUBLIC SECTION.
    METHODS read_order    IMPORTING io_reader TYPE REF TO zif_read_order.
    METHODS process_order RETURNING VALUE(rt_order) TYPE zif_read_order=>tt_order.
  PRIVATE SECTION.
    DATA mt_order TYPE zif_read_order=>tt_order.
ENDCLASS.
CLASS zcl_order_operator IMPLEMENTATION.
  METHOD read_order.
    mt_order = io_reader->read_order( ).     "多型：DB 或 XML 由傳入物件決定
  ENDMETHOD.
  METHOD process_order.
    " 業務處理示意：只留金額大於 0 的訂單
    rt_order = VALUE #( FOR ls IN mt_order WHERE ( netwr > 0 ) ( ls ) ).
  ENDMETHOD.
ENDCLASS.
上面 ZCL_READ_ORDER_XML 在 CATCH 裡用 MESSAGE 只是為了讓範例短；正式程式應該在介面方法宣告 RAISING 自訂例外（例如 ZCX_ORDER_READ），讓每個實作把各自的錯誤（SQL、XML 解析、檔案不存在）轉成同一種例外往上丟——否則「依賴抽象」只做了一半，呼叫端還得知道每種實作會丟什麼。

  • 原範例宣告了介面參考 gi_read_order TYPE REF TO zif_read_order 卻完全沒用，而是宣告兩個具體類別的變數 go_read_order_db／go_read_order_xml 分別傳入——呼叫端自己其實仍依賴具體類別。改寫版讓呼叫端只持有一個介面參考 lo_reader，真正把「選擇實作」集中到一個地方。
  • 原範例用 CALL METHOD … ( … ). 混合寫法、沒有任何輸出；改寫版輸出用 CL_SALV_TABLE。ZCL_ORDER_XML_SOURCE=>GET( ) 為示意，代表「從檔案／介面取得 XML 字串」的來源。
範例的注入方式是方法注入（read_order( reader )）。實務上更常見的是建構子注入：NEW zcl_order_operator( io_reader = lo_reader )，保證物件一建立就有可用的依賴，不會出現「忘了先呼叫 read_order 就呼叫 process_order」的時序錯誤。

14. DIP 的紅利：用測試替身做單元測試

依賴介面最大的實務好處是可測試。ZCL_ORDER_OPERATOR 只認識 ZIF_READ_ORDER，測試時就能塞一個「假的讀取類」給它，不必連資料庫、不必準備 XML 檔，也不受 HANA 回傳順序影響，每次測試結果都一樣。

" ZCL_ORDER_OPERATOR 的 Local Test Classes
CLASS ltd_reader DEFINITION FINAL FOR TESTING.      "測試替身（Test Double）
  PUBLIC SECTION.
    INTERFACES zif_read_order.
ENDCLASS.
CLASS ltd_reader IMPLEMENTATION.
  METHOD zif_read_order~read_order.
    rt_order = VALUE #( ( vbeln = '0000000001' netwr = '100.00' waerk = 'TWD' )
                        ( vbeln = '0000000002' netwr = '0.00'   waerk = 'TWD' ) ).
  ENDMETHOD.
ENDCLASS.

CLASS ltc_order_operator DEFINITION FINAL FOR TESTING
  RISK LEVEL HARMLESS DURATION SHORT.
  PRIVATE SECTION.
    METHODS zero_amount_is_filtered FOR TESTING.
ENDCLASS.
CLASS ltc_order_operator IMPLEMENTATION.
  METHOD zero_amount_is_filtered.
    DATA(lo_cut) = NEW zcl_order_operator( ).        "CUT = Class Under Test
    lo_cut->read_order( NEW ltd_reader( ) ).
    DATA(lt_result) = lo_cut->process_order( ).

    cl_abap_unit_assert=>assert_equals( act = lines( lt_result ) exp = 1 ).
    cl_abap_unit_assert=>assert_true(
      act = xsdbool( line_exists( lt_result[ vbeln = '0000000001' ] ) ) ).
  ENDMETHOD.
ENDCLASS.
不想手寫替身類別時，可用 ABAP Test Double Framework：cl_abap_testdouble=>create( 'ZIF_READ_ORDER' ) 產生替身，再用 cl_abap_testdouble=>configure_call( ) 設定回傳值（7.40 SP09 起）。要替換的是資料庫本身時（例如想測 ZCL_READ_ORDER_DB 的 SQL），則用 cl_osql_test_environment（OSQL Test Double Framework，7.51 起）。

15. 設計原則檢查清單與常見誤用

你在程式裡看到可能違反處方
一長串 CASE mtart／bsart／auart，而且常常要回來加 WHENOCP子類＋註冊表／BAdI 過濾器（第 4～8 節）
類別方法裡有 WRITE、MESSAGE TYPE 'I'、CALL SCREENSRP商業類別只回傳資料或丟例外，畫面交給呼叫端
子類重定義後，呼叫端需要 IS INSTANCE OF 判斷「如果是某子類就別這樣呼叫」LSP改用組合或共同介面（第 11 節）
實作類別有一堆空方法只為了通過啟用ISP拆小介面，或 DEFAULT IGNORE（第 2 節）
方法參數型別是 REF TO zcl_具體類，而且想換實作DIP改為 REF TO zif_…，由外部注入（第 13 節）
單元測試非得連資料庫、準備真實單據才能跑DIP把資料存取抽到介面後面，用測試替身（第 14 節）
別為原則而原則。 只會有兩種情況、而且五年內不會變的判斷，一個 SWITCH 就夠了；為它建抽象類、三個子類、註冊表、SM30 維護畫面，反而增加維護成本（YAGNI）。原則是用來處理「已知會變動」的地方：物料類型、訂單類型、組織單位、外部系統介面——這些在 SAP 專案裡偏偏又是最常變的。
書中下一章把這些原則組合成設計模式：範例 6.2 的工廠方法、6.10 的「依介面切換實作」分別對應簡單工廠與策略模式，見 7-5 章。

練習與自我檢核

  1. 範例 6.1 違反哪個原則？新增物料類型 HALB 時需要改哪些地方？
    參考答案要點：違反開放封閉原則；必須修改報表 ZREP_CLS_021 的 IF／ELSEIF，並重測、重新傳輸這支已上線的程式。
  2. 在第 4～7 節的設計中，新增 HALB 需要做哪兩件事？哪些物件完全不用改？
    參考答案要點：① SE24 建立 ZCL_MATERIAL_SEMI 繼承 ZCL_MATERIAL 並重定義方法；② SM30 在 ZINSP_DESC_T 加 HALB → ZCL_MATERIAL_SEMI。報表、工廠、其他子類都不改。
  3. 勘誤 8 說圖 6-18 的 SE11 應為 SM30，兩者差在哪？
    參考答案要點：SE11 定義表結構；SM30 維護表內容（需先用 Table Maintenance Generator／SE54 產生維護程式），且客製化表的變更會記錄到客製化請求。
  4. 為什麼 GET_MATERIAL_OBJ 仍用 CREATE OBJECT 而不是 NEW？哪些情況會丟 CX_SY_CREATE_OBJECT_ERROR？
    參考答案要點：NEW 只能用靜態型別，類別名在變數中必須用 CREATE OBJECT … TYPE (name)。類別不存在／未啟用、類別是抽象類、類別不是 ZCL_MATERIAL 的子類、建構子不可見等情況都會丟。
  5. 原範例把 CX_SY_CREATE_OBJECT_ERROR 在工廠內 CATCH 並彈訊息，有什麼問題？
    參考答案要點：模型層不該碰 UI（背景／RFC 時會出問題）；吞掉例外後呼叫端分不出「未登記」與「類別名錯」；應以 RAISING 宣告，讓呼叫端處理。
  6. 正方形繼承長方形為什麼違反 LSP？範例 6.8 的 ASSERT 會得到多少？
    參考答案要點：長方形的契約是寬高互不影響；正方形 set_height( 6 ) 同時把寬改成 6，面積 36 ≠ 18，ASSERT 失敗（ASSERTION_FAILED 短傾印）。
  7. 範例 6.8 為什麼還不算「完整的」LSP 示範？請寫出真正的替換情境。
    參考答案要點：它直接用 ZCL_SQUARE 型別的變數；真正的替換是 DATA lo_rect TYPE REF TO zcl_rectangle. lo_rect = NEW zcl_square( ). 然後以長方形的假設使用它。
  8. 請指出範例 6.9 的兩個多餘或無效的寫法。
    參考答案要點：CREATE OBJECT 後的 IS NOT INITIAL 檢查永遠成立；CATCH cx_sy_dyn_call_error 對靜態呼叫無效且是空 CATCH；另外 CALL METHOD 與函數式括號混用。
  9. 勘誤 9 修正了範例 6.10 的什麼？除此之外 6.10 還有什麼沒做到位？
    參考答案要點：第二段註解「資料庫讀取訂單類」應為「XML 讀取訂單類」。另外宣告了介面參考 gi_read_order 卻沒用，呼叫端仍以具體類別變數傳入。
  10. DIP 對 ABAP Unit 有什麼幫助？請說明 ltd_reader 的角色。
    參考答案要點：操作類只依賴介面，測試時可注入不連資料庫的測試替身 ltd_reader，資料固定、結果可重現，也不受 HANA 無預設排序影響。
  11. 勘誤 6：介面繼承與實作繼承在「必須實作」這件事上差在哪？
    參考答案要點：實作介面的類別必須實作介面所有方法（除非標 DEFAULT IGNORE／FAIL 或類別為抽象）；一般繼承的子類只有在父類方法是 ABSTRACT 時才必須重定義。
  12. 用一句話說明「先找標準，再想客製」和開放封閉原則的關係。
    參考答案要點：BAdI／Enhancement Spot 是 SAP 預留的「擴充點」（對擴充開放），修改標準等於打開已上線的程式來改（違反對修改封閉），所以升級成本高一個量級。
  13. 自建註冊表若加上「工廠」鍵欄位但程式仍只用 MATERIAL_TYPE 讀 SELECT SINGLE，會發生什麼事？
    參考答案要點：部分鍵讀取可能有多筆，HANA 不保證回傳哪一筆，同一物料可能今天建出 A 類、明天建出 B 類；必須補齊鍵條件，或 ORDER BY 明確排序後取一筆。
