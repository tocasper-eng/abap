2. Debugger 概觀：New Debugger 與 Classic Debugger

ABAP Debugger 是分析 ABAP 程式最重要的工具，兩大用途：

  • 開發期間分析錯誤：runtime error（短傾印，ST22）與「不如預期的行為」。
  • 分析既有程式、理解程式流程——這是修改或擴充程式（尤其是 SAP 標準程式）之前的必要功課。

雙程序架構的結果：Debugger 開著時，畫面上會同時有兩個視窗——debuggee 的最後一個對話畫面與 Debugger 畫面，但同一時間只有一個是作用中的：要嘛程式在等使用者輸入（兩個對話步驟之間），要嘛 Debugger 在等使用者輸入（對話步驟進行中）。程式輸出最後畫面後，Debugger 仍保留（不作用），只要 debuggee 的 session 還活著，Debugger 就不會關閉。

5. 控制程式執行：F5～F8、Goto Statement、Step Size、Call Stack

原始碼中的黃色箭頭指向「下一個要執行、但還沒執行」的敘述。

按鍵名稱行為
F5Single Step執行下一個敘述後停；遇到呼叫會進入被呼叫單元
F6Execute執行下一個敘述後停；被呼叫的單元（subroutine、FM、方法、dialog module）整個執行完才停
F7Return跑完目前單元，回到呼叫端後停
F8Continue一直跑到下一個中斷點或 Watchpoint
Shift+F8Continue to Cursor跑到游標所在敘述

Goto Statement（右鍵敘述 → Goto Statement，或 Debugger → Goto Statement）：可以跳過某段程式（避免會導致 runtime error 的敘述）或重跑已執行過的程式碼（換個變數值再試一次，不用重啟應用程式），前提是技術上可行。這是權限 ACTVT 02 以上才有的功能（第 15 節）。

Step Size（敘述級除錯）：長長的 IF 有很多子條件，你以為是 TRUE 結果是 FALSE，要知道是哪個子條件失敗。按 Step Size 按鈕切換為 Statement Debugging，Debugger 會逐一執行子條件，各子條件的回傳值顯示在 Variables 窗格的 Auto 頁籤；再按一次回到逐行模式。7.40 以後的巢狀運算式（COND、VALUE、REDUCE、方法鏈）也很適合用這個功能拆開看。

6. 中斷點：Persistent、Session、External、Debugger 四種

每位使用者最多 30 個中斷點。中斷點有不同的範圍與生命週期，選錯種類是「中斷點設了卻不停」的主因。
種類設定方式適用範圍生命週期
Persistent（寫在程式碼裡）BREAK-POINT（不分使用者，可加 ID 綁 Checkpoint Group）；BREAK <user>（只對該使用者）HTTP／RFC 呼叫的程式中會被忽略，除非開啟外部除錯跟著原始碼，直到刪掉
SessionEditor：Ctrl+Shift+F12、Set/Delete Session Breakpoint 按鈕、點左側狀態欄；Debugger：右鍵 Create Session Breakpoint只對設定者本人，在該使用者 session 的所有主模式有效；不能用在只經 HTTP 呼叫的程式（Web Dynpro controller 方法、BSP event handler）登出即刪除

條件式中斷點（7.0 EHP 2 起，不必改程式碼）：已知行號的中斷點可在 Source Code 工具右鍵 → Create Breakpoint Condition、建立時填 Free Condition Entry、或在 Breakpoints 工具按 Create Breakpoint Condition。未知位置（例如「在 ABAP 命令 SELECT」）的中斷點則要在 Breakpoints 工具點 Define Filter 連結。可用的條件依命令而定：SELECT 只能依資料表篩選、APPEND 只能依內表篩選，有些命令完全不能加條件。

LINES( LT_ITEM ) = 0                                  " 內表為空才停（內建函式可用）
SY-SUBRC <> 0                                         " 只在失敗時停

※ 條件建議用「多個 EQ 列舉」而不是區間：
   MATNR = 'TG11' OR MATNR = 'TG12' 比 MATNR BETWEEN 'TG11' AND 'TG19' 安全，
   區間比的是字典序，遇到 ALPHA 前導零或編碼規則改過就會停錯地方。

7. Watchpoint 與 Debugger Session 的存取

Watchpoint：當被監看的變數值改變時停下。

  • 只能在 Debugger session 裡定義，session 結束一律刪除。
  • 建立：Shift+F4、Create Watchpoint 按鈕、或 Breakpoints → Create Watchpoint；游標若停在變數上，名稱自動帶入 Variable 欄位。
  • 區域變數可選只監看目前這個 subroutine／FM／方法實例，或該單元的所有實例。
  • Free Condition Entry 可加條件；留空則任何變化都停。
  • 多個 Watchpoint 之間是 OR。
  • 7.0 EHP 2 起有 Watchpoint Type：物件屬性改變時，參考變數的值（只是位址）不會變，所以監看參考變數沒用；選 Watchpoint at Object Attribute 可一次監看某一類屬性（例如所有 public instance 屬性、所有 private static 屬性）。
  • Break./Watchpoints 頁籤的 Watchpoints 子頁會顯示目前值與前一個值；按 Compare Variables 會用 Diff 工具比較兩者。

9. 資料分析（二）：內表、物件、Data Explorer 與 Diff 比較

Table 工具分 Tables（使用者選過的內表清單與狀態歷程）與 Table Content（內容）兩個頁籤。鍵值欄位以藍字標示，按鑰匙圖示看鍵值定義。Attributes 欄位例如 Standard [1000x68(2056)] 代表：Standard 內表、1000 列、每列 68 欄、每列長度 2056 bytes。

10. 記憶體分析：Memory Analysis、Memory Object Explorer、Loaded Programs

最快的方法：Variable Fast Display 的 Memory Analysis 頁籤輸入多個變數名，看 allocated 與 used（bytes）。7.0 EHP 2 起另有 Memory Object Explorer 與 Application Specific Memory Views。

記憶體類型意義
Bound Memory刪除該實體後會被釋放的記憶體；包含它自己，以及只被它參考的物件
Used Memory實體本身實際使用的記憶體
Allocated Memory系統保留的記憶體，永遠 ≥ Used；字串與內表會先多配，讓成長更有效率
Object vs BoundObject memory 只算直接屬於該變數的部分。例：內表有一欄是字串參考，Object memory = 內表管理資料 + 每個字串參考（各 8 bytes），不含字串內容；Bound memory 才會算進去

Memory Object Explorer：以某個記憶體物件為起點（輸入參考變數名如 GO_ALV，或參考值如 {O:1276...}），選方向 Memory Objects Contained（往下看子物件）或 Higher-Level Memory Objects（往上看誰參照它）。每個節點顯示 Bound (Alloc.)、Bound (Used)、Object Size (Alloc.)、Object Size (Used)。右鍵 Use As Start Point 換起點；多條連線時 All Edges 欄出現按鈕。物件類型代碼：字串 {S:id}、內表 {T:id}、Box {B:id}、物件 {O:id}、匿名資料物件 {A:id}；循環參考顯示 Recursive Reference 圖示。教材提醒：記憶體突然暴增，常是共享的值語意物件（例如內表）變成不共享（copy-on-write 被觸發）。

Memory Analysis 工具（目前 internal session）三個頁籤：

  • Memory Sizes：ABAP Application（Static Variables、Stack (Used)、Dyn. Memory Objects (Used)，加總為 Total；另有 Stack／Dyn. Memory Objects 的 Allocated）；Total: Internal Session（Used、Allocated、Peak (Used)）；Total: External Session（所有 internal session 的配置總和與 internal session 數）。預設要按 Refresh 才計算。
  • Memory Objects：依大小排序的動態記憶體物件清單，View 可選 Memory Objects、Types（依類別／型別加總，類別含 static 屬性）、Aggregates (Cycles)（Strongly Connected Component，SCC）。
  • Dominator Tree（7.0 EHP 2 起）：考慮交互參照，第一層只列沒有被別人參照的物件，節點記憶體含所有子節點。

動態記憶體物件包括：內表、string／xstring、類別實例、匿名資料物件、boxed components——都是 deep 資料物件。SCC：一組互相可經參考到達彼此的物件（例如雙向鏈結串列、兩個物件互相持有對方參考），Garbage Collector 只能整組一起回收，且只有在外部沒有任何參考指進來時才回收；長時間執行又快取大量物件的程式，大型 SCC 就可能造成記憶體問題。

Services of the Tool → Create Memory Snapshot 可建立快照，再用 S_MEMORY_INSPECTOR 比較兩個快照，找記憶體洩漏。Loaded Programs 工具列出目前 internal session 載入的所有程式（黃色箭頭 = 目前程式、帽子圖示 = program group 首、系統程式藍色、Load Size、最後修改日期時間、載入順序 Index），Global Data 頁籤可看任一載入程式的全域變數——除錯 User Exit 時要讀取主程式的全域資料，就從這裡看。

14. 更新除錯、tRFC 與存取資料庫的程式

更新（Update）機制把使用者對話與資料庫變更分開，由不同程式、不同工作程序處理：

  1. 對話程式以 CALL FUNCTION … IN UPDATE TASK 呼叫更新函數模組——不立即執行，而是把 FM 名稱與傳入資料寫進更新記錄（log）。
  2. 多筆記錄組成一個 SAP LUW；更新保證所有更新 FM 在一個資料庫 LUW 內執行（all or nothing）。
  3. COMMIT WORK 時關閉這個 request queue，通知 Basis 有待處理的請求。
  4. Basis 程式讀出 LUW 記錄交給更新程式執行；成功後刪除該 LUW 的記錄。

因為更新 FM 不在目前被除錯的使用者 session 裡執行，預設不會進入除錯。要除錯就得在 Settings 勾 Update Debugging，COMMIT WORK 後會另開 Debugger 處理更新工作程序。更新與 LUW 的完整觀念見 5-11 章 BC414。

*&---------------------------------------------------------------*
*& 更新除錯與 tRFC 除錯的練習程式
*&---------------------------------------------------------------*
DATA(ls_log) = VALUE zpp_conf_log( aufnr = lv_aufnr
                                   budat = sy-datum
                                   ernam = sy-uname ).

" ① 更新 FM：F5 不會進去；要勾 Settings → Update Debugging
CALL FUNCTION 'Z_PP_CONF_LOG_UPDATE' IN UPDATE TASK
  EXPORTING is_log = ls_log.

" ② tRFC：勾 Settings → TRFC (in Background Task): Block Sending
"    → 呼叫被收集但不送出，之後到 SM58 對該 LUW 啟動除錯
CALL FUNCTION 'Z_IF_MES_NOTIFY' IN BACKGROUND TASK
  DESTINATION 'MES_SYSTEM'
  EXPORTING iv_aufnr = lv_aufnr.

COMMIT WORK.   "← Update Debugging 開啟時，這行之後另一個 Debugger 視窗會停在更新 FM
               "   更新失敗記錄看 SM13；tRFC 卡住看 SM58

存取資料庫的程式除錯風險：每支程式在一個工作程序中執行；遇到等待狀態時程式被 roll out、工作程序釋放給別人用，資料庫連線必須結束目前 DB session → 觸發隱含 DB commit，之後就不能 rollback。在 Debugger 中：

  • 在 SELECT 迴圈中發生等待 → 連線關閉、DB cursor 遺失，繼續除錯會 runtime error。
  • 在修改資料庫的敘述中或之後發生等待 → 上次 DB commit 以來的變更全部寫入、無法回復。在正式環境這是致命的。

正常執行不會有、只有除錯才有的等待，就是 Debugger 自己的對話步驟：每次在中斷點或 Watchpoint 停下，對應工作程序都會觸發隱含 DB commit。唯一的避免方法：debuggee 的工作程序在除錯期間不釋放——系統會自動把對話工作程序轉成獨佔（exclusive）除錯工作程序，數量上限由 rdisp/wpdbug_max_no 決定，且最多只能用一半的對話工作程序。

  • 成功時 GUI 標題顯示 (exclusive)(<host> <SID> <sys.no.>)；失敗顯示 (NOT exclusive)，此時應延後除錯，等可以時用 Debugger → Exclusive Debugging Mode On 手動轉換。
  • 獨佔模式下可從 Debugger 觸發 Edit → Database → Commit (unlock) 或 Rollback：變更可以先試再回滾，或在除錯中確定提交。
用完立刻離開 Debugger：獨佔工作程序數量有限，掛著不關會卡住別人。教材中的舊寫法 SELECT … ENDSELECT 正是「迴圈中遇等待就 DB cursor 遺失」的高風險寫法，本館一律改用 SELECT … INTO TABLE @DATA( ) 一次取回再 LOOP（2-2 章）。

16. Layer Aware Debugging（SLAD）：只看你關心的那一層

現代架構是多層的：Web Dynpro 應用在 Web Dynpro framework 上，framework 又建在 ICF（Internet Communication Framework）上，應用層與 ABAP kernel 之間至少還隔兩層框架程式碼；實際的複雜應用層數更多。以前只能用「關閉 System Debugging」排除 kernel 層，對非 kernel 的框架程式碼沒辦法選擇性排除。Software Layer Aware Debugging 解決這件事，適用：

  • 只除錯你負責的程式碼，隱藏框架程式碼，並能看到所有進入點（誰呼叫你這層、帶什麼參數）。
  • 大步前進：從一層跳到另一層、從一個元件跳到另一個元件，而不是一路 F5。

Object Set（物件集）：在 SLAD 定義，持久保存、可重用（也可在 Debugger 中直接定義，見下）；Object Set 是 Repository 物件。由 Selection Set 與 Selection Set Expression 組成：

  • 一個 Selection Set（例如 S1）只能是下列其中一種條件：單一 Package、Package 含子 Package、Program（程式名／類別名）、Function Module、Implemented Interface。條件用 select-options 定義，可做排除與區間。
  • Selection Set Expression 用 AND / OR 組合 Selection Set。
SLAD Object Set 範例（教材 p99）
Selection Set  BC400_BC403  : Package  BC400 ~ BC403
Selection Set  CL_BC_CLASS  : Program  CL_BC*
Selection Set  BC490        : Package  BC490
Expression                  : CL_BC_CLASS AND ( BC400_BC403 OR BC490 )
→ 結果：名稱以 CL_BC 開頭、且屬於 package BC400~BC403 或 BC490 的類別

實務建議（Casper：列舉優於區間）
Selection Set  ZMM_PKGS : Package with subpackages  ZMM_MAIN, ZMM_IF   （逐一列出）
Selection Set  ZBADI    : Implemented Interface     IF_EX_ME_PROCESS_PO_CUST
Expression              : ZMM_PKGS OR ZBADI
→ 用 Package 區間 BC400~BC403 很方便，但也會把字典序落在中間、名稱意外的 package 一起包進來

Debugger Profile：組合多個 Object Set，並對每個 Object Set 設定：

設定說明
Visibility可見則照常除錯；隱藏則 Debugger 不進入（類似系統程式）
Point of Entry進入該 Object Set 的程式碼時停
Point of Exit離開該 Object Set 後立刻停
Including System Code包含該 Object Set 內的系統程式

每個 Profile 都有預設 Object Set <<%REST%>>，代表「不屬於自訂 Object Set 的所有 ABAP 程式碼」，可設定其行為或直接刪除（只關心自訂 Object Set 之間的呼叫時很好用）。持久 Profile 也是 Repository 物件，在 SLAD 建立／顯示／修改／複製／刪除；Debugger 中可載入但不能修改，只能衍生出暫時 Profile（session 結束即刪）。

在 Debugger 使用 Profile（只有 New Debugger 可以）：

  1. 按 Configure Debugger Layer（Ctrl+Shift+F4）。
  2. 勾 Layer-Aware Debugger Active。
  3. 選 Use of Predefined Object Set using Debugger Profile（載入持久 Profile）。
  4. 在 Profl. 欄位輸入名稱，或 F4／Profile Library 按鈕瀏覽。
  5. 按 Continue 只在本次生效；按 Save Settings 每次啟動都生效。

啟用後工具列多一個開關 Layer Aware Debugging 的按鈕，但新的 Debugger session 啟動時一律是關閉的。關閉步驟相同，取消勾選即可。在 Debugger 中建立 Profile 的方法：Direct Definition of Visible Object Set（定義一個 Object Set，session 結束即刪）、以目前 Profile 為範本按 Change（開 SLAD，可 Save 持久或 Continue 暫時）、Temp. Profile（從零或複製既有 Profile）。這個設定對話框也包含在一般 Debugger 設定裡。

標準程式很深（例如 ME21N、VA01）時，建一個「只看 Z 開頭 Package + 自己實作的 BAdI 介面」的 Profile，按 F8 就會直接停在自己的增強程式進入點，不必在標準程式裡迷路。這也是先找標準、再想客製的最佳前置動作：先用 Layer Aware 看清楚標準流程在哪些 BAdI／Enhancement Spot 會呼叫出來（3-4 章、5-15 章）。

17. Request-Based Debugging：用 Terminal ID 鎖定「這一個人的請求」

HTTP 型應用（Web Dynpro、BSP、Web Service、ICF 服務）只能用外部除錯。傳統外部中斷點綁使用者 ID，但處理過程可能換帳號（例如透過 RFC 到另一系統取資料，RFC 帳號與原使用者不同），就停不下來。SAP NetWeaver 7.02 起的新型外部中斷點綁 Terminal ID（TID），確保：

  • 哪一台應用伺服器處理請求都沒關係。
  • 使用者名稱不重要。
  • 不影響其他使用者的請求——在正式系統這點是關鍵。

適用於「一個通用系統帳號處理各個用戶端請求」的 client-server 架構。例：支援人員在遠端 SAP GUI 設中斷點，瀏覽器則在客戶網路內的 WTS 上執行。

設定 Terminal ID：SE80 Utilities → Settings → ABAP Editor → Debugging，選 Terminal ID 單選鈕，右邊自動顯示產生的 TID。之後所有外部中斷點都自動帶上此 TID；只有請求的 TID 與中斷點的 TID 相符時 Debugger 才啟動。請求經過多個 ABAP 系統時，TID 會自動轉送，所以可以跨系統追同一個請求。

TID 代表 Windows 使用者在該作業系統上的登入，第一次啟用時產生並存在 Windows 登錄檔 HKEY_CURRENT_USER\Software\SAP\ABAP Debugging，直到手動刪除為止都有效。
  • 同一台 PC（設中斷點的人就是送請求的人）：在發起請求的 SAP GUI 視窗輸入 /htid，之後此主模式發出的請求都帶自己的 TID，狀態列有訊息。
  • 不同人／不同 PC：送請求者在 SAP GUI 輸入 /hset tid=<TID>（覆寫從登錄檔讀到的 TID）。TID 很長，可從 Utilities → Settings 對話框複製後 email 給對方。/hdel tid 刪除手動指派，/hget tid 查目前指派。
  • HTTP 應用：① 取得 Microsoft Internet Explorer 用的 SAP HTTP Plug-in（SAP Note 1041556）；② 用 Plug-in 啟動 IE，會開瀏覽器視窗並有 Plug-in 視窗在前景；③ 在 Terminal-ID 欄輸入中斷點的 TID（同一台 PC 不必）；④ 按 Start Transaction，不要關 Plug-in 視窗；⑤ 在瀏覽器照常操作。到達同 TID 的外部中斷點時，Debugger 在開發者電腦上開新視窗。
現況：Internet Explorer 已停止支援，教材的 IE Plug-in 做法在現代環境基本上不可行。S/4HANA 上除錯 Fiori／OData／HTTP 請求的常見做法：對實際執行請求的使用者設外部中斷點（SE80 Settings 的 User 欄位改成 Gateway 服務帳號或使用者本人）、或在 ADT 中設中斷點（Eclipse 的中斷點預設就是外部中斷點，5-5 章）。/htid、/hset tid 對 SAP GUI 發起的 RFC 情境仍然有用。

18. Debugger Scripting（一）：概念與預設腳本

Debugger Scripting 自 SAP NetWeaver 7.0 EHP 2 起提供：凡是你在 Debugger 手動能做的事，都能寫成腳本自動化，還能產生各種 Trace 檔。

腳本用途例子
分析與修改程式中的變數、物件每次停在 AUTHORITY-CHECK、執行後把 SY-SUBRC 改為 0，略過失敗的權限檢查（僅限開發／測試系統！）
各種 Trace記錄每個執行過的 ABAP 敘述；追呼叫堆疊（可用來決定 Layer Aware 的 Profile 要包含什麼）；自訂 Trace 內容，例如追某個參數在呼叫鏈上被誰改錯
複雜的中斷點／WatchpointRFC 回來的資料有誤：每次 RFC 呼叫時觸發腳本 → 執行呼叫 → 檢查回傳 → 有問題就寫 Trace 或停下
控制被除錯程式的執行讓腳本執行停住的敘述；發現值得互動分析的狀況時動態建立中斷點
分析與呈現複雜資料逐列讀巢狀內表、檢查資料一致性，錯了就停
  • 腳本使用 ABAP Debugger Interface（ADI），在 Debugger 端執行，只能透過 ADI 操作應用程式，不能直接影響它。
  • Debugger 腳本技術上是一個 subroutine pool（有專屬程式類型），裡面只有本地類別 LCL_DEBUGGER_SCRIPT，可自行加屬性與方法。
  • 預設腳本依用途分類：物件分析、通用中斷點、資料流分析、記憶體使用分析、runtime error 分析、Trace、特殊 Watchpoint、其他（依講義步驟整理：教材此處為三張截圖，完整清單請在 Script 頁籤按 Load Script 瀏覽，腳本名稱多以 RSTPDA_SCRIPT_ 開頭）。

LCL_DEBUGGER_SCRIPT 的四個方法：

方法時機用途
PROLOGUE腳本啟動後第一個，只一次技術初始化：預設實作把 abap_source（CL_TPDA_SCRIPT_ABAPDESCR 實例）註冊到 debug_step 事件，確保取得的原始碼資訊是最新的。自己的初始化不要寫這裡
INITPROLOGUE 之後，只一次自己的初始化；可放使用者互動（對話框詢問參數，ABAP Objects 允許的 UI 元素都能用）
SCRIPT每次觸發主要邏輯；匯入參數 p_trigger 帶觸發類型。可同時定義多個觸發（例如 SELECT 中斷點 ＋ stack change ＋ Watchpoint）
END腳本結束或使用者停止時，一次收尾：顯示結果、關閉資源、彙總資料（腳本因錯誤中止或 Debugger 被使用者結束時不呼叫）
  • 引發 cx_tpda_stop_scripting_request 停止腳本；引發 cx_tpda_script_continue 不經使用者互動繼續到下個觸發。
  • me->break( )：讓使用者決定停止或繼續（腳本內的中斷點）；me->raise_error( )：不經使用者互動終止腳本。
教材的 Caution：不要改類別名稱、不要改繼承、不要改 INIT／SCRIPT／END 的宣告、不要改 tag 註解——那些 tag 在儲存腳本時自動產生，改了腳本就壞掉。

19. Debugger Scripting（二）：自訂腳本、Trigger、ADI、Trace 與 SAS

腳本可以在 Debugger 的 Script 頁籤（Debugger Scripting 工具）直接寫，也可以事先在交易 SAS（ABAP Debugger Scripting and Tracing）的 Script Editor 頁籤準備——用 SAS 事先寫好的好處是不會長時間佔住 Debugger 工作程序。工具一開始顯示範本腳本（四個方法空實作），可以此為基礎或載入既有腳本修改後另存；存於資料庫或檔案系統。腳本可在 Object Navigator 顯示、修改、複製、刪除，也能寫程式文件，在工具中按 Help for Script 顯示。

Trigger 設定：

  • Execute Directly：按 Start Script 立即執行一次。每次執行都產生新的 Trace 檔；me->break( ) 不會中斷；執行完後回到一般除錯（若 Script 頁籤作用中時按 F8，會問要再跑一次腳本還是不帶腳本繼續）。
  • After Debugging Events：Single Step in Debugger（每步之後）、Breakpoint Reached（任一 script breakpoint）、Watchpoint Reached（任一 script watchpoint）。按核取方塊右邊的按鈕，在下方頁籤的 Breakpoints／Watchpoints 定義觸發點。每次觸發都寫同一個 Trace 檔。腳本不會因 Debugger 關閉而自動停止，所以要在應用程式接近結尾處設個中斷點，以便手動停止腳本。
  • Script breakpoint／watchpoint 只觸發腳本，不中斷應用程式。

執行中 Script 頁籤只剩兩個按鈕：Exit Script（停止腳本、繼續除錯）與 Continue Script（每次觸發繼續執行）。按 F5／F6／F7／F8 則繼續除錯但觸發時不執行腳本，腳本仍未停止、可稍後繼續。只有在 Debugger 取得控制權時（應用程式的中斷點或 Watchpoint、或腳本中的 me->break( )）才能要求停止腳本。要除錯腳本本身，必須在腳本方法中寫 BREAK-POINT。

ADI 存取方式：大部分功能在以 CL_TPDA_SCRIPT_ 開頭的類別的 static 元件；部分是 instance 元件，經由 me-> 存取——本地腳本類別繼承自 CL_TPDA_SCRIPT_CLASS_SUPER，執行時由 Debugger framework 實例化。類別名稱不必背，Script Wizard 可自動產生重要的方法呼叫。

此範例要設兩個一般中斷點：一個在觸發點之前（用來進 Debugger、載入並啟動腳本），一個在迴圈之後（讓開發者有機會結束腳本、關閉 Trace 檔）。教材列出使用的方法：debugger_controller->debug_step（執行 F5／F6／F7／F8）、cl_tpda_script_data_descr=>get_simple_value（以字串取簡單變數值）、cl_tpda_script_data_descr=>change_value（改簡單變數值）、trace->add_custom_info（寫自訂 Trace）。

互動腳本：腳本就是一個本地類別的原始碼，所以不限於 ADI，大部分 ABAP 能力都能用。延伸上例：啟動時問使用者「要不要顯示訊息」「要不要寫 Trace」，只問一次 → 寫在 INIT。用函數模組 POPUP_GET_VALUES：傳給 FIELDS 表格參數幾列就出現幾個輸入欄，每個欄位的長度與型別必須參照 ABAP Dictionary 的結構／表欄位（不能獨立定義）；要做兩個布林欄位，就要找型別合適的字典欄位。關閉對話框後從同一張表讀使用者輸入。使用者輸入要在 SCRIPT 方法使用，所以必須存成類別屬性，不能是 INIT 的區域變數。

  METHOD init.
    " POPUP_GET_VALUES 的欄位必須參照字典欄位；這裡借用 SVAL 常見的做法
    DATA(lt_fields) = VALUE ty_sval_tab(
      ( tabname = 'BAPIFLAG' fieldname = 'BAPIFLAG' fieldtext = 'Show messages (X/blank)'  value = 'X' )
      ( tabname = 'BAPIFLAG' fieldname = 'BAPIFLAG' fieldtext = 'Write trace file (X/blank)' value = 'X' ) ).

    CALL FUNCTION 'POPUP_GET_VALUES'
      EXPORTING  popup_title     = 'Debugger script options'
      TABLES     fields          = lt_fields
      EXCEPTIONS error_in_fields = 1
                 OTHERS          = 2.
    IF sy-subrc <> 0.
      RETURN.
    ENDIF.

    " 存成屬性，SCRIPT 方法每次觸發都讀得到
    mv_show_msg  = xsdbool( lt_fields[ 1 ]-value = 'X' ).
    mv_write_trc = xsdbool( lt_fields[ 2 ]-value = 'X' ).
  ENDMETHOD.
上例的 ty_sval_tab 請宣告為 TYPES ty_sval_tab TYPE STANDARD TABLE OF sval WITH EMPTY KEY.（放在類別 PRIVATE SECTION）；借用哪個字典欄位當布林欄位只要長度 1 的 CHAR 即可，教材原圖所用的欄位為截圖，此處以 BAPIFLAG-BAPIFLAG 示意。

執行期智慧中斷點：需求是「每次到 LOOP … ENDLOOP 且處理的內表叫 GT_FLIGHT 才停，而且每個 LOOP 只停一次」——標準的「Breakpoint at ABAP statement」做不到，腳本可以：

  METHOD script.
    " 觸發：Script breakpoint at statement LOOP AT（優於 Single Step 觸發）
    TRY.
        " ① 掃描目前這一行
        DATA(lo_scan) = cl_tpda_script_scan=>scan(
                          p_program = abap_source->program( )
                          p_include = abap_source->include( )
                          p_line    = abap_source->line( ) ).

        " ② 是 LOOP 才能 cast 成 CL_TPDA_SCRIPT_SCAN_ITAB_LOOP
        DATA(lo_loop) = CAST cl_tpda_script_scan_itab_loop( lo_scan ).

        " ③ 取這一行所有 LOOP 的內表名稱，比對目標
        DATA(lt_itabs) = lo_loop->it_tables( ).
        IF NOT line_exists( lt_itabs[ table_line = 'GT_FLIGHT' ] ).
          RETURN.
        ENDIF.

        " ④ 每個 LOOP 只停一次：記住已停過的行號（mt_loop_lines 為類別屬性）
        DATA(lv_line) = abap_source->line( ).
        IF line_exists( mt_loop_lines[ table_line = lv_line ] ).
          RETURN.
        ENDIF.
        INSERT lv_line INTO TABLE mt_loop_lines.
        me->break( ).                                  "中斷應用程式，交給開發者互動分析

      CATCH cx_sy_move_cast_error.                     "不是 LOOP 敘述 → 略過
      CATCH cx_tpda_scan INTO DATA(lx_scan).
        RAISE EXCEPTION NEW cx_tpda_script_continue( ).
    ENDTRY.
  ENDMETHOD.
上述 scan 類別的方法名稱依教材 p139 描述（factory method SCAN、cast 成 CL_TPDA_SCRIPT_SCAN_ITAB_LOOP、方法 IT_TABLES）；參數名稱與 abap_source 取得行號的方法請以系統中 Script Wizard 產生的程式為準。啟動方式：在應用程式開頭設一個中斷點，進 Debugger 後載入並啟動腳本。

Trace 檔的產生與分析：介面 IF_TPDA_SCRIPT_TRACE_WRITE 的方法可寫入最後一個 ABAP 敘述、呼叫階層、或任意自訂內容。腳本結束後，檔案出現在 Trace File 頁籤（新的在上），可 Display（管理資料對話框 → Continue 看明細，Components 單選鈕選要顯示的內容；Start Standalone Trace Analys. 另開 SAS 分析）、Delete、Start analysis in a new session。

交易 SAS 三個頁籤：

  • Trace Files：Own Trace Files 與 Trace Files of Other Users，依日期時間排序，雙擊在 Trace Display 開啟。
  • Trace Display：Trace Selection 區有 Statements、Hierarchy、Custom 三個按鈕，組合型 Trace 會有多個按鈕可用。
  • Script Editor：具備 Debugger Script 頁籤的所有功能，但沒有 Save 與 Start Script。
