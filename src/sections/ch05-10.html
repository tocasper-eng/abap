2. 介紹 Enjoy SAP 控制項：最小可跑的 ALV Grid

Basis 4.6A 起，ABAP Workbench 提供一批 Enjoy SAP 控制項，把對話功能從應用伺服器「搬」到展示層（SAP GUI）。每個控制項在 ABAP 端都有一個全域類別（前綴 CL_GUI_），程式透過方法呼叫指揮控制項，展示層上的使用者動作則以事件回報給 ABAP 程式。強晟在前言點出本課最重要的一句：這些控制項在 Screen Painter 裡沒有，只能用程式碼加到畫面上。

原課程第 2 單元用一張圖說明實作 ALV Grid 的三件事：① Screen Painter 畫一個 Custom Control 區域（例：CCA1）；② PBO 裡建立 Custom Container 並綁到這個區域；③ 建立 ALV Grid 並以容器為 parent，呼叫 set_table_for_first_display 傳資料。

3. 控制框架（CFW）架構：代理物件、兩個世界、類別階層

SAP GUI 的使用者對話原本以「畫面（Dynpro）」為單位：ABAP 行程與畫面行程透過 SAP GUI 的服務（視窗管理、對話層級、資料傳輸）溝通，畫面總是以一個整體單元傳輸。R/3 4.5 起可在 SAP GUI 視窗中使用圖形元素（控制項）；4.6A 起，所有控制項的通訊通道統一為 SAP Control Framework（CFW）。

  • CFW 由兩個服務組成：應用伺服器上 runtime system 的 CFW 服務，以及 SAP GUI 上的 Automation Controller（自動化控制器）。
  • CFW 維護三份資料：① 所有需要通訊的控制項實例清單；② Automation Queue（自動化佇列）；③ 應用程式要處理的控制項事件清單。
  • 控制項安裝在展示層，可以是 ActiveX（Windows）或 Java Beans（SAP GUI for Java）；Automation Controller 透過 OLE 或 Java 介面跟它們溝通，兩者之間走 GUI RFC。
  • CFW 的目標：最佳化控制項與應用程式之間的通訊（少來回、批次送）。

控制項與 ABAP 物件——兩個世界、四個實例：用一個控制項時，實際上有兩個物件：ABAP 程式裡的代理物件（Proxy，也稱 Control Wrapper），以及展示層上的控制項實例。ABAP 程式永遠只跟代理物件說話（呼叫方法、設定／讀取屬性），代理物件再透過 CFW 在展示層執行；展示層傳來的動作，CFW 會定位到對應的代理物件，再由它通知 ABAP 程式。加上容器也是一個控制項，所以「一個 ALV 放在一個容器裡」實際是 ABAP 端 2 個 ＋ 展示層 2 個 ＝ 4 個實例。

類別角色
CL_GUI_OBJECT所有代理類別的根；提供 free 等共用方法
CL_GUI_CONTROL控制項共同父類別；set_registered_events、set_visible 等
CL_GUI_CONTAINER容器共同父類別；所有 CL_GUI_*_CONTAINER 都由此衍生，是「有特殊功能的控制項包裝者」
CL_GUI_CFW服務類別：flush、dispatch、set_new_ok_code、get_living_dynpro_controls…可直接在程式中呼叫
CL_GUI_PICTURE、CL_GUI_HTML_VIEWER、CL_GUI_TEXTEDIT、CL_GUI_ALV_GRID、CL_GUI_TOOLBAR、CL_GUI_SIMPLE_TREE…各控制項的代理類別
要看繼承階層，在 SE24 開類別後按「類別瀏覽器／Superclass」，或在 SE80 的類別樹展開。實務上最常見的誤會是想直接實例化父類別（例如 CL_GUI_ALV_GRID_BASE）——永遠實例化最底層的具體類別，筆記 p157 也特別強調。

4. 控制項與畫面：Custom Control 區域、容器、LIFETIME、只建立一次

控制項不能單獨存在於展示層，必須有一個畫面和一個容器：畫面上保留一塊區域（就像子畫面區域），程式把 CL_GUI_CUSTOM_CONTAINER 的實例指派到這塊區域，再把要顯示的控制項放進容器。前兩步讓控制項融入一般的畫面處理（PBO、PAI、視窗縮放）。

建立 Custom Control 區域 （依講義步驟整理）：SE51 → Layout（圖形化版面編輯器）→ 左側元素工具列點「Custom Control」→ 在畫面上按住左鍵拖出區域 → 命名（例：CONTROL_AREA1）。屬性「Resizing Vertical／Horizontal」讓區域隨視窗縮放，並可用「Min. Lines／Min. Columns」設定最小尺寸；最大尺寸就是畫的時候的大小。

LIFETIME 參數（容器建構子的選填參數）三選一：

常數意義
cl_gui_container=>lifetime_imode只要內部階段（internal session）還開著、沒執行 LEAVE PROGRAM，控制項就活著
cl_gui_container=>lifetime_dynpro跟畫面實例同生死（留在畫面堆疊中就活著）；也控制可見性——只在建立它的畫面啟用時顯示
cl_gui_container=>lifetime_default沿用容器的生存期；若本身就是容器（沒有上層容器），則視為 lifetime_imode

確保控制項只建立一次——這是本單元最重要的觀念。容器畫面的下一個畫面通常是自己，每按一次 Enter 都會 PAI → PBO 再跑一次；若每次 PBO 都 CREATE OBJECT，就會不斷把新實例接到畫面上，PAI 對舊實例呼叫的方法結果永遠看不到。筆記用 IF my_container IS INITIAL 當開關，現代寫法用 IS NOT BOUND。

5. Picture 與 HTML Viewer：URL、資料提供者、顯示模式、釋放資源

SAP 圖片控制項（CL_GUI_PICTURE）與 HTML 瀏覽器（CL_GUI_HTML_VIEWER）都用 URL 指向要顯示的資料。URL 在 ABAP 裡就是字元變數。資料來源分兩類：

來源存放位置怎麼變成 URL
外部本機檔案、網路共用、HTTP、FTP直接寫 URL，控制項自己去讀（與應用伺服器無關）。格式：服務://主機.網域:埠/目錄/檔名，如 file://c:/public/pictures/logo.gif、http://www.sap.com/index.html
SAP Web RepositorySMW0（工具 → Web 開發 → Web Repository）HTML Viewer 的 load_html_document／load_mime_object；Picture 用函數 DP_PUBLISH_WWW_URL
Business Document Server（BDS）OAWD（辦公室 → 業務文件）CL_BDS_DOCUMENT_SET 的 get_with_url
資料庫叢集表／內表先讀進內表函數 DP_CREATE_URL（或 HTML Viewer 的 load_data）送到資料提供者（Data Provider），它回傳一個 URL

資料提供者是 SAP GUI 裡的一個控制項：資料送給它後在本機管理，並回傳指向這份資料的 URL；圖片與 HTML 控制項用這個 URL 存取時，它的表現就跟外部資料源一樣。

HTML Viewer 顯示資料的方法（通常要呼叫兩個）：外部來源 show_url／show_url_in_browser；SMW0 load_html_document／load_mime_object；資料提供者 load_data ＋ show_data（或 show_url）。Picture 的方法：load_picture_from_url（GIF、JPG、BMP）、顯示 SAP 圖示用 load_picture_from_sap_icons（筆記寫成單數 _icon）、清除用 clear_picture、外觀用 set_3d_border、set_display_mode。

顯示模式常數（CL_GUI_PICTURE=>…）效果
display_mode_normal原尺寸；大於區域自動出捲軸，小於則留白
display_mode_normal_center原尺寸、置中
display_mode_stretch拉伸填滿整個區域（會變形）
display_mode_fit縮放到區域內、保持長寬比（不變形）
display_mode_fit_center同 fit，再置中

6. Automation Queue 與 flush：效能與除錯的關鍵

每次跟展示層控制項溝通都要走網路，而且跟一般畫面元素的傳輸是分開的。為了效能，代理物件上的方法呼叫與屬性讀取都先緩衝在 Automation Queue，直到同步點才一次送到前端（稱為 flush），前端收集到的回傳值也在同一步傳回。整個 CFW 只有一個自動化佇列，flush 時所有控制項的操作一起送出。

  • 自動 flush：畫面 PBO 結束時由 runtime 自動 flush。有子畫面時，只在最上層主畫面的 PBO 結束後 flush 一次（巢狀子畫面亦同）。
  • 相依呼叫要手動 flush：第二個方法需要第一個方法的結果時，中間必須 cl_gui_cfw=>flush( )；否則讀回的變數還是空的。
  • 不必每次都 flush：若查詢的值已在佇列中（方法 A 設了屬性 a1=v1，方法 B 要讀 a1），CFW 直接從佇列回答，不必跟前端通訊。只在絕對需要時才 flush。
  • 控制項之間搬資料：「先從控制項 1 讀、再寫到控制項 2」放在同一個佇列裡，複製會直接在前端完成，不必經過應用伺服器。大量資料交換時一定要這樣做。
  • 佇列為空時 flush 不會產生任何來回。

筆記舉的例子很有畫面感：衛星連線下每次來回 0.5 秒，一個畫面 10 次來回就要等 5 秒以上。PAI 的建議結構：先把所有控制項的屬性一次讀完 → flush 一次 → 再一次設定所有屬性 → 交給 PBO 結束時的自動 flush。對照「讀 1 → flush → 設 1 → flush → 讀 2 → flush → 設 2 → flush」的寫法，前者只要兩次同步。

*&---------------------------------------------------------------*
*& PAI：兩個 TextEdit 先讀完 → flush 一次 → 再處理
*&---------------------------------------------------------------*
MODULE user_command_0100 INPUT.
  DATA lt_note1 TYPE STANDARD TABLE OF tdline WITH EMPTY KEY.
  DATA lt_note2 TYPE STANDARD TABLE OF tdline WITH EMPTY KEY.

  " ① 讀取：這兩行只是排進佇列，此刻 lt_note1 / lt_note2 仍是空的
  go_edit1->get_text_as_r3table( IMPORTING table = lt_note1 EXCEPTIONS OTHERS = 1 ).
  go_edit2->get_text_as_r3table( IMPORTING table = lt_note2 EXCEPTIONS OTHERS = 1 ).

  " ② 同步點：一次來回把兩份結果帶回來
  cl_gui_cfw=>flush( EXCEPTIONS cntl_system_error = 1
                                cntl_error        = 2
                                OTHERS            = 3 ).
  IF sy-subrc <> 0.
    MESSAGE |前端同步失敗（{ sy-subrc }），請洽管理員檢查 SAP GUI| TYPE 'A'.
  ENDIF.

  " ③ 現在才能用結果做判斷，設定類的呼叫交給 PBO 結束時自動 flush
  IF lt_note1 IS INITIAL AND lt_note2 IS INITIAL.
    go_edit1->set_readonly_mode( readonly_mode = cl_gui_textedit=>false ).
  ENDIF.
  CLEAR ok_code.

例外在哪裡爆？ 方法呼叫只是排隊，真正的前端錯誤要到 flush 時才發生；佇列處理中任何一步出錯，整個佇列中止並在 flush 拋出例外。所以 cl_gui_cfw=>flush 的 EXCEPTIONS 一定要接。控制項沒裝好時，每次 flush 都會失敗——此時用 A 或 X 型訊息徹底終止，交給管理員修前端安裝。
除錯兩招：① ABAP 除錯器設定勾選「Automation Controller：總是同步處理請求」，每個方法呼叫後都自動 flush，錯誤會停在真正出錯那一行；確認後再在適當位置補 flush 與 sy-subrc 檢查。② SAP GUI 選項的 Trace 勾選 Automation，所有自動化呼叫與參數寫進 trace 檔，錯誤以 HRESULT 記錄；還能數出每個 PBO/PAI 有幾次同步，刪掉多餘的 flush。注意 trace 裡看到的是前端的自動化方法名，跟 ABAP 方法名不同，一個 ABAP 方法可能對應多個自動化呼叫。

7. 控制項事件：事件過濾、系統事件與應用事件、dispatch

展示層控制項觸發的事件，經過好幾層才到 ABAP：控制項 → SAP GUI 的 Automation Controller（以特殊功能碼＋附加資料送出）→ Basis 的 CFW 服務 → ABAP 代理物件 → 以 ABAP Objects 的 RAISE EVENT 通知已註冊的處理方法。每一層都有必要設定：

  1. ABAP 端：寫事件處理方法（METHODS on_xxx FOR EVENT xxx OF cl_gui_…），並用 SET HANDLER 把它和觸發物件連起來。命名慣例 on_<事件名>；處理方法的參數只能取自事件宣告，不必全收；每個實例事件都有隱含參數 SENDER，可以知道是誰觸發的。
  2. 前端過濾器：Automation Controller 是事件過濾器，初始狀態一個事件都不傳。要處理哪些事件，必須把事件 ID 填進 CNTL_SIMPLE_EVENTS 內表（欄位 EVENTID、APPL_EVENT），用 set_registered_events 送給代理物件，下次 flush 時送到前端。

事件 ID 常數在各控制項類別的屬性裡找（SE24 → 屬性頁籤）。筆記吐槽：Picture 叫 eventid_picture_click，HTML Viewer 卻叫 m_id_sapevent——SAP 早期命名不統一，用之前一定要去類別裡確認。ALV Grid 例外：它的代理物件會自己向 CFW 註冊事件，程式只要 SET HANDLER 即可。

系統事件（System Event，預設）應用事件（Application Event，APPL_EVENT = 'X'）
觸發 PAI？不觸發；Basis 服務直接通知代理物件控制權回到容器畫面，觸發 PAI
畫面欄位不會傳回程式（只活在 OO 世界裡）PAI 開頭照常從畫面傳到程式
處理方法何時執行立即PAI 結束時由 CFW 自動呼叫 cl_gui_cfw=>dispatch；也可在 PAI 中提前手動 dispatch
想回到 PAI在處理方法裡呼叫 cl_gui_cfw=>set_new_ok_code，處理完會以新功能碼觸發 PAI（此時事件處理早於欄位傳輸）—

8. SAP 容器全家族：Custom／Dialogbox／Docking／Splitter／Easy Splitter

容器是「能裝其他控制項的控制項」，負責跟畫面溝通；容器本身也是控制項，所以可以巢狀；放在容器裡的控制項通常跟容器一樣大。所有容器都繼承 CL_GUI_CONTROL → CL_GUI_CONTAINER，介面統一。

容器類別依附對象重點參數／方法適用情境
CL_GUI_CUSTOM_CONTAINER畫面上的 Custom Control 區域container_name（必填）、parent、repid、dynnr、lifetime；link 重新連結最常用；版面由 SE51 決定
CL_GUI_DIALOGBOX_CONTAINER整個畫面之上的非模態可移動對話框width、height、caption、top、left；set_caption；事件 close浮動明細視窗
CL_GUI_DOCKING_CONTAINER黏在畫面四邊之一side（預設左邊）、extension、ratio；dock_at、get_extension／set_extension、link不必畫 Custom Control；甚至可黏在選擇畫面上
CL_GUI_SPLITTER_CONTAINER另一個容器之內rows、columns（初始 0×0，最大 16×16）；get_container、set_row_height、set_column_width、set_row_mode／set_column_mode（絕對像素／相對百分比，預設相對）、set_row_sash／set_column_sash（分隔條固定或可移動）、set_border、add_control／remove_control主檔／明細多格版面
CL_GUI_EASY_SPLITTER_CONTAINER另一個容器之內orientation（orientation_vertical／orientation_horizontal）；set_sash_position；儲存格在屬性 top_left_container、bottom_right_container只要切兩半時最省事

對話層級與頂層容器：容器建立時就被指定一個對話層級（dialog level），之後不能改。對話層級由 CALL SCREEN nnnn STARTING AT … ENDING AT … 產生；類別建構子會建立 SCREEN0～SCREEN9 十個頂層容器（CL_GUI_CONTAINER=>SCREEN0…），分別對應層級 0～9，作為 Custom／Docking／Dialogbox 容器的 parent。容器裡的控制項只在容器顯示時才顯示；要用 link 搬到新畫面、或在函數模組裡建立容器時，必須知道它屬於哪一層。

Custom Container 在 CFW 中由四個值唯一決定：程式名、畫面號、區域名、對話層級。沒給 parent／repid／dynnr 時，系統取執行當下的值。link 可把容器改接到同一程式或其他程式的另一個畫面區域，但只能是同一對話層級。

10. 文字編輯控制項（CL_GUI_TEXTEDIT）

TextEdit 是純文字編輯器：不能設定格式、不能插圖；可用暫時性的附加資訊（例如醒目提示），這些由展示層管理、不回傳給程式。畫面由三部分組成：應用工具列（尋找／取代、復原、重做、另存本機檔…）、編輯視窗、狀態列（選取範圍資訊、游標位置、插入／覆寫切換）；工具列與狀態列都可以隱藏。同樣的功能也出現在它自帶的本地上下文選單裡。

資料交換兩種格式：

  • R/3 Table：內表一行 ＝ 編輯器一行（換行即新列）。方法 set_text_as_r3table、get_text_as_r3table、set_selected_text_as_r3table、get_selected_text_as_r3table。
  • Stream：一樣放在內表，但以資料流傳輸，換行以控制字元存在流裡。方法 set_text_as_stream、get_text_as_stream、set_selected_text_as_stream、get_selected_text_as_stream。

get_*_as_r3table 會忽略換行資訊（軟換行的處理方式在建構子中定義）；內表行長度小於控制項定義會截斷，大於則補空白。set 系列會覆蓋現有文字（selected 版本只覆蓋選取範圍）。

用途方法
本機檔案open_local_file、save_as_local_file（沒給 file_name 就跳對話框）

11. ALV Grid（一）：特性、資料保持與 set_table_for_first_display

ALV Grid 以標準方式顯示與列印非階層清單。使用者可自行調整版面並存成顯示變式（Display Variant／Layout）；開發者決定使用者能否存「使用者專屬」或「全域」變式。應用工具列預設就有這些功能，不必自己寫：明細（模態對話框顯示所選列）、升冪／降冪排序、尋找、篩選、合計（總和、平均、最大、最小）、小計、列印、預覽、匯出、版面設定、圖形、使用者文件。開發者可以隱藏任何一項，也可以加上自己的功能。

畫面三區：頂端應用工具列（可隱藏部分或全部）→ 一行標題 → 資料區（Grid）。資料區超出範圍自動出捲軸；鍵欄（key column）顏色不同且水平捲動時固定不動（任何欄位都能設成鍵欄）；可選儲存格、儲存格群、整列、整欄，設定「儲存格選擇」時會自動多一欄列選擇按鈕。列印版面沿用傳統 ABAP 清單：邏輯封面頁、內容頁（各有頁首、頁尾）、封底頁，都能用事件處理。

最重要的一句（筆記 p158）：代理物件不複製資料，只保存指向你內表的指標。排序、篩選等互動都直接作用在呼叫程式的內表上——在 Grid 上排序會改變你的內表順序，其他操作才是唯讀。所以：① 輸出內表必須是全域或與代理物件同生命週期，不能是區域變數；② 在 user_command 裡用 get_selected_rows 拿到的 index，要對應「目前內表」的順序；③ 這也是 Casper 提醒的「HANA 沒有預設排序」的延伸：SELECT 要 ORDER BY，而且別假設內表順序在使用者操作後還維持原樣。

呼叫程式必須提供代理物件無法封裝的三類資訊：要顯示的資料、如何顯示的規則（Field Catalog）、附加設定。相關全域型別：

15. 樹控制項（二）：尋找列印、事件、延遲載入、工具列、Column／List Tree

樹模型附加功能：print_tree（all_nodes = ' ' 只印畫面上可見的節點、'X' 全印；title、preview）先從節點表產生 ABAP 列印清單、送 spool 再進清單畫面。find 跳出對話框讓使用者輸入字串或樣式，回傳 result_type（與 cl_simple_tree_model=>find_match 比對）與 result_node_key；find_next 從上次命中處繼續、不再跳對話框。命中節點可累積到內表後用 select_nodes 一次標記、unselect_nodes 清除——要做多選命中，建立模型時就要設 node_sel_mode_multiple。

事件：雙擊節點觸發 node_double_click（註冊用 eventid_node_double_click，參數 node_key）。事件發生時要從節點 ID 反推應用資料：用 SPLIT … AT ';' 拆回應用鍵。筆記特別提醒：SPLIT 的目標要是字元型；分隔符比目標欄位少時，剩下的目標欄位會被填空白（即使是 N 型別），所以要先初始化目標；字元處理要確保 Unicode 相容。

只在使用者要求時才讀資料——EXPAND_NO_CHILDREN：EXPANDER = 'X' 的節點被展開時才觸發，樹模型自己判斷：只有該資料夾的子節點還沒傳給模型時才把事件傳給程式。所以先傳一個「基本集合」（例如兩層），其餘在事件中從資料庫讀出再 add_nodes——這就是「增量後續讀取」。

16. 拖放（Drag & Drop）：Flavor、控制類型、資料傳輸物件與三個事件

原課程的範例情境：① 從 ALV Grid 拖一筆客戶到 Simple Tree 的航線節點 ＝ 替客戶訂位（複製）；② 從訂位樹拖一個訂位節點到一張回收桶圖片 ＝ 取消訂位（移動）。課程只做控制項層面，不更新資料庫。實作至少四步：

  1. 定義行為類型（Flavor）：每個 flavor 有名稱（任意）、是拖曳來源（dragsrc）還是放下目標（droptarget）、滑鼠效果（effect：cl_dragdrop=>copy／move／none）、控制項內部的效果（effect_in_ctrl）。多個 flavor 收在一個 CL_DRAGDROP 實例裡，這個實例就是一個「控制類型（行為表）」。
  2. 把控制項（或子物件）指派給控制類型：get_handle 取得整數 handle，再依控制項各自的方式掛上——Grid 用 LVC_S_LAYO-S_DRAGDROP（ROW_DDID／CNTR_DDID／GRID_DDID／COL_DDID）或 Field Catalog 的 DRAGDROPID；樹節點填 DRAGDROPID；Picture 直接 set_dragdrop_picture 傳 CL_DRAGDROP 實例。
  3. 定義資料傳輸類別：系統在每次拖放產生一個「拖放服務實例」（CL_DRAGDROPOBJECT），它的 object 屬性可指向任何物件；所以要寫一個（通常是本地）類別，在 PUBLIC SECTION 放要傳的資料。
  4. 寫處理方法：至少來源的 drag 與目標的 drop，需要時再加來源的 drop_complete（放下完成後回頭更新來源，例如「移動」後把來源節點刪掉）。

放下時系統的判斷流程：找出來源與目標子物件 → 依指派找出兩者共同的 flavor 名稱 → 依 flavor 的 effect 決定滑鼠效果（兩種都允許時，按 Ctrl 是複製、否則是移動）→ 處理方法中可讀 drag_drop_object->flavor 分流。若兩個 flavor 效果相同而無法判斷，就要在 ongetflavor 類事件中於執行時指定。

自我檢核：

#問題參考答案要點
1一個 ALV Grid 放在 Custom Container 裡，執行時總共有幾個實例？分別在哪裡？4 個：ABAP 端兩個代理物件（容器、Grid），展示層兩個控制項實例；ABAP 只跟代理物件溝通，透過 CFW／Automation Controller 送到前端。
2為什麼建立控制項的程式碼一定要包在「只做一次」的判斷裡？不包會怎樣？容器畫面的下一畫面通常是自己，每次 PAI 後都會再跑 PBO；每次 CREATE 都會把新實例接到畫面，PAI 對舊實例的方法呼叫看不到結果，還會累積前端資源。用 IS NOT BOUND 判斷。
3get_text_as_r3table 之後馬上讀內表卻是空的，原因與解法？方法呼叫只排進 Automation Queue，要到 flush 才真正執行並回傳；需要結果時立刻 cl_gui_cfw=>flush( )，且要接它的 EXCEPTIONS。PAI 中先把所有讀取排好再 flush 一次。
4系統事件與應用事件的差異？何時要用 dispatch、何時用 set_new_ok_code？系統事件不觸發 PAI、畫面欄位不傳回；應用事件觸發 PAI，處理方法在 PAI 結束時（或手動 cl_gui_cfw=>dispatch）執行。系統事件處理完想回到 PAI 用 set_new_ok_code。
5為什麼 Picture 控制項設了 SET HANDLER 卻收不到 picture_click？前端過濾器初始不傳任何事件，必須先用 set_registered_events 註冊 eventid_picture_click（ALV Grid 例外，代理會自己註冊）。
6ALV Grid 的輸出內表可以宣告成區域變數嗎？使用者在 Grid 上排序後，內表會怎樣？不行，代理物件只保存指標，內表要與 Grid 同生命週期。排序直接作用在內表上，所以內表順序會改變；讀選取列 index 時要以目前順序為準，也呼應「HANA 無預設排序、取第一筆前先確認排序」。
7i_save 的 'U'、'X'、'A' 各代表什麼？is_variant 的 handle 何時必填？U：只能存使用者專屬；X：只能存全域；A：兩者皆可。同一程式有多個 Grid 時用 handle 區分各自的變式。
8refresh_table_display 的 is_stable 與 i_soft_refresh 各有什麼作用？什麼情況不能只 refresh？is_stable（row/col = 'X'）保留捲動位置；i_soft_refresh = 'X' 只重送資料、保留排序篩選。內表行結構改變時必須重新 set_table_for_first_display。
9建立樹節點時為什麼建議一律用 relat_last_child？節點表順序有什麼限制？節點依節點表順序處理，參考節點必須先出現；first_child 會讓後加入的節點插到前面，畫面順序與節點表相反。last_child 讓兩者一致。
10EXPAND_NO_CHILDREN 解決什麼問題？要搭配節點的哪個欄位？延遲載入（增量後續讀取），只在使用者展開時才讀資料庫、傳子節點；節點要設 EXPANDER = 'X'，樹模型只在該資料夾尚無子節點時才傳事件。
11拖放的最少實作步驟？WAN 環境下怎麼最佳化？定義 flavor（CL_DRAGDROP->add）→ get_handle 指派給子物件 → 資料傳輸類別 → drag／drop（必要時 drop_complete）處理方法。控制類型表越少越好，行為相同的子物件共用同一個 CL_DRAGDROP 實例。
12筆記 p162 關於 i_appl_events 的註解錯在哪？寫成「空白＝全部註冊成應用事件」，實際上空白（預設）是系統事件，'X' 才是應用事件。
13一個只讀的航班清單，要不要用 BC412 的 CL_GUI_ALV_GRID？不必；先找標準（Fiori App／標準報表），再用 CL_SALV_TABLE（可放進任何容器）；只有需要編輯或細控事件時才用 CL_GUI_ALV_GRID——Casper 的「先標準再客製」。
14S/4HANA 專案若使用者都從 Fiori Launchpad 進 GUI 交易，BC412 技術有什麼風險？會以 SAP GUI for HTML 執行，部分控制項功能（特別是拖放、部分樹與前端檔案操作）受限，上線前務必在 WebGUI 實測；新需求優先 Fiori Elements／RAP；ABAP Cloud 完全不能用 CL_GUI_*。
