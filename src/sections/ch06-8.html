2. 採購單變更文件：CDHDR／CDPOS 與物件類別 EINKBELEG

ME22N 每次存檔，只要有欄位的資料元素勾了「Change document」，系統就會寫一筆變更文件：

表角色重要欄位
CDHDR變更檔頭：一次存檔一筆OBJECTCLAS（採購單固定 'EINKBELEG'）、OBJECTID（採購單號 EBELN，CHAR90 靠左）、CHANGENR、USERNAME、UDATE、UTIME、TCODE、CHANGE_IND（I 新增／U 修改）
CDPOS變更明細：一個欄位一筆TABNAME（EKKO／EKPO／EKET…）、TABKEY、FNAME（'KEY' 表示整筆新增）、CHNGIND、VALUE_OLD／VALUE_NEW、UNIT_OLD／UNIT_NEW、CUKY_OLD／CUKY_NEW
DD03M欄位＋資料元素文字的檢視TABNAME、FIELDNAME、DDLANGUAGE、SCRTEXT_L（原程式拿來把 FNAME 翻成欄位說明）

TABKEY 的組法是「該表完整主鍵」直接串接：MANDT(3)＋EBELN(10)，EKPO 再接 EBELP(5)，EKET 再接 ETENR(4)。原程式對 EKET 取 TABKEY+18(5)，但 ETENR 只有 4 碼。因為搬進 NUMC 欄位時會自動去空白，結果碰巧是對的，但長度寫錯了，改寫時要修正成 +18(4)。

CHNGIND 有五種值：U（修改）、I（新增）、D（刪除）、E（刪除單一欄位的文件）、J（新增單一欄位的文件）。原程式只判斷 'I'，其他全顯示成 'Modification'，所以刪除項目也會被當成「修改」。這是業務最在意的一種變更，一定要分開顯示。

先找標準（Casper 經驗第 3 條）：ME23N →「環境 → 表頭變更」可以看單張採購單的變更。跨單查詢可以用標準報表 RM06EAEN（採購單變更清單），或是函數 CHANGEDOCUMENT_READ（第 5 節）。確定標準做不到「多條件、多單、同時看輸出紀錄」，才值得寫 ZMMR0002。物件類別的定義可以在 SCDO 查。

3. ZMMR0002 的業務情境、選擇畫面與輸出

業務情境：採購主管要稽核「誰在什麼時候改了哪張採購單的哪個欄位」，例如改單價、改交期、刪項目。另外還要看改完之後採購單有沒有重新輸出給供應商（S/4HANA 的 Output Management）。

選擇畫面（截圖標題「PO change and Output Log」）：

  • 第一區（MODIF ID SC1）：採購文件類型 BSART、採購組織 EKORG、供應商 LIFNR、採購單號 EBELN、物料 MATNR、變更日期 UDATE、變更時間 UTIME
  • 第二區（MODIF ID SC2）：Application Object ID、Output Request Item Status、Output Channel
  • 模式選項：Data Change Log（預設）或 Output Log。AT SELECTION-SCREEN OUTPUT 會依選到的模式把另一區設成不可輸入
  • 變更類型：只看新增、只看修改、兩者都看（預設）；表範圍：EKKO／EKPO／EKET 三個勾選框

輸出：用 CL_SALV_TABLE 顯示。變更模式的欄位有採購單號、項目、計畫行、表名與說明、欄位名與說明、變更類型、舊值新值（含單位與幣別）、交易碼、使用者、日期、時間。雙擊一列就用 SET PARAMETER ID 'BES' 開 ME23N。輸出模式則把時間戳轉成本地日期時間，依最後變更時間倒排。

程式架構：PREPARE_DATA（依勾選框組表名 range、讀 DD03M）→ GET_DATA（CDHDR，再用 FOR ALL ENTRIES 讀 CDPOS）→ CRT_CHANGELOG（用 AT NEW CHANGENR 組輸出列）→ FILTER_IT_DATA（事後用 EKKO JOIN EKPO 套用 BSART／EKORG／LIFNR／MATNR）→ DISPLAY_ALV。輸出模式則走 GET_DATA_OUTPUT。以下用 local class 改寫，取代 FORM。

4. 關鍵段落改寫（一）：一次 JOIN 讀 CDHDR＋CDPOS，條件在資料庫端就套用

ECC 時代的 CDPOS 是 cluster table（實體存在 CDCLS），不能 JOIN，只能先讀 CDHDR 再用 FOR ALL ENTRIES 讀 CDPOS。所以原程式才會寫成兩段，而且表名條件是讀回來之後才用 DELETE … WHERE NOT ( TABNAME IN R_TABLE ) 過濾。S/4HANA 的 CDPOS 已經是透明表，可以直接 JOIN，表名、變更類型都在 WHERE 裡處理。

另一個問題是採購組織、供應商、物料這些條件。原程式是讀完變更文件才用 EKKO 回頭過濾，等於「先把所有採購單的變更抓回來，再丟掉九成」。改寫版反過來做：先用 EKKO／EKPO 算出符合條件的採購單號，再拿這批單號去讀變更文件。

條件選取的兩個坑（Casper 經驗第 1、2 條）
  • 列舉比區間安全。採購單號、文件類型、採購組織最好用多筆 EQ 列舉。區間比的是字典序，不是業務語意：單號段不連續、編碼規則改過（例如 45 開頭改成 46 開頭）、內外部編號混用時，BT 會多抓或漏抓。上面的表範圍也刻意用 EQ 列舉。
  • HANA 沒有預設排序。原程式在讀取後有 SORT，這點是對的。但同一個 CHANGENR 底下欄位的順序、同一秒內兩次存檔的先後，都必須靠 CHANGENR（遞增號碼）排序，不能靠「讀出來的順序」。任何「取最後一次變更值」的邏輯，都要先依 udate utime changenr 明確排序，再讀最後一筆。

5. 關鍵段落改寫（二）：TABKEY 拆解、欄位文字、變更類型，以及標準函數 CHANGEDOCUMENT_READ

原程式用 AT NEW CHANGENR 搭配 header line，把檔頭欄位「殘留」到後續各列。邏輯雖然成立，但很難讀。改寫版每一列都直接帶入檔頭欄位，欄位文字改用 hashed table 查詢：

    " 欄位文字：DD03M 一次讀進 hashed table

      WHERE tabname    IN @lt_tab
        AND ddlanguage = @sy-langu
      INTO TABLE @DATA(lt_dd).
    TYPES: BEGIN OF lty_text,
             tabname   TYPE dd03m-tabname,
             fieldname TYPE dd03m-fieldname,
             text      TYPE dd03m-scrtext_l,
           END OF lty_text,
           lty_text_tab TYPE HASHED TABLE OF lty_text WITH UNIQUE KEY tabname fieldname.
    DATA(lt_ftext) = VALUE lty_text_tab( FOR d IN lt_dd ( tabname = d-tabname fieldname = d-fieldname text = d-scrtext_l ) ).

    rt_out = VALUE #( FOR r IN lt_raw
      ( ebeln     = r-tabkey+3(10)
        ebelp     = COND #( WHEN r-tabname = 'EKPO' OR r-tabname = 'EKET' THEN r-tabkey+13(5) )

輸出紀錄：S/4HANA 的採購單輸出改走新的 Output Management（BRF+ 決定輸出類型），紀錄存在 APOC_D_OR_ITEM，不再是 NAST。原程式用 APPL_OBJECT_TYPE = 'PURCHASE_ORDER' 讀取，時間戳用 CONVERT TIME STAMP … TIME ZONE sy-zonlo 轉成本地時間。改寫版把狀態與通道條件也放進 WHERE，並明確排序：

SELECT appl_object_id, item_id, status, output_type, channel,
       crea_date_time, lchg_date_time
  FROM apoc_d_or_item
  WHERE appl_object_type = 'PURCHASE_ORDER'
    AND appl_object_id  IN @s_appl
    AND ( @p_status IS INITIAL OR status  = @p_status )
    AND ( @p_chnl   IS INITIAL OR channel = @p_chnl )
  ORDER BY lchg_date_time DESCENDING, appl_object_id, item_id
  INTO TABLE @DATA(lt_output).

LOOP AT lt_output ASSIGNING FIELD-SYMBOL(<o>).
  CONVERT TIME STAMP <o>-lchg_date_time TIME ZONE sy-zonlo

7. ZMMB0009：把變更紀錄同步到外部資料庫 ZEXT_POCHANGE（摘要）

業務情境：公司的 BI 或採購入口網站要在 SQL Server 上查採購單變更，所以每天排背景作業，把變更紀錄寫到外部表 ZEXT_POCHANGE。

8. VK11 條件價格的資料模型：條件表 A###、KONH、KONP 與存取順序

銷售價格用的是條件技術。定價程序裡的條件類型（例如 PR00）掛著一個存取順序（V/07），存取順序依序列出多張條件表（V/03 建立，實體表名是 A＋三碼表號），系統依序找到第一筆有效的條件記錄就停。VK11 維護的就是這些條件記錄：

表內容本案用到的欄位
A005條件表「銷售組織／配銷通路／客戶／物料」，是一張 key 表KAPPL（V＝銷售）、KSCHL、VKORG、VTWEG、KUNNR、MATNR、DATAB、DATBI、KNUMH
KONH條件記錄檔頭（一個 KNUMH 一筆）KNUMH、ERDAT、ERNAM、KOTABNR、KSCHL
KONP條件記錄項目（金額）KNUMH、KOPOS、KBETR、KONWA、KPEIN、KMEIN、LOEVM_KO（刪除標記）
KONM／KONW數量／金額級距本案未處理，如有級距價要另外讀
CDHDR條件記錄的變更文件OBJECTCLAS 'COND_A'、OBJECTID＝KNUMH
S/4HANA 的單據定價結果從 KONV 改存到 PRCD_ELEMENTS，但主檔條件記錄仍然是 A###／KONH／KONP，所以本案的讀法在 S/4HANA 依然成立。另外要注意，一張 A005 只是存取順序中的一層。如果客戶實際的價格來自另一張條件表（例如「價格表類型／物料」），只讀 A005 就會漏掉。要輸出「客戶實際成交價」，應該用定價模擬，而不是讀單一條件表。

9. ZSDI0006 的業務情境、選擇畫面與程式架構

業務情境：外部的經銷商系統或電商平台每天要同步「客戶專屬價格」。SAP 把 VK11 的條件記錄整理成 CSV，放到 FTP 主機的 /Export Data/VK11.csv，對方再來取。

選擇畫面（截圖標題「Download VK11」）：Customer（S_KUNNR）、Created on（P_ERDAT）、勾選框「整批下載」（P_CB）。

程式架構（Events 截圖可以看到 INITIALIZATION、AT SELECTION-SCREEN OUTPUT、ON BLOCK B1 都是空的，只有 START-OF-SELECTION 在做事）：

  1. 沒勾整批→ COLLECT_VK11_TO_ADDON：先用 GET_CHANGE_LOG 從 CDHDR（COND_A、UDATE = P_ERDAT）收集當天有變更的 KNUMH，組成 RANGES；再讀 A005＋KONP＋KONH，條件是「KONH-ERDAT = P_ERDAT（當天新建）或 KNUMH 在變更清單內」。
  2. 有勾整批→ COLLECT_ALL_VK11：讀 A005＋KONP，條件是 P_ERDAT 落在有效期間內。
  3. 兩條路都呼叫 APPEND_VK11_TO_ADDON，把結果 MODIFY 進暫存表 ZSDPR0001（ERDAT／ERTIM 蓋成當下時間），然後 COMMIT WORK AND WAIT。
  4. GET_VK11_DATA：再從 ZSDPR0001 以 ERDAT = P_ERDAT 讀回來，用 CONVERSION_EXIT_CUNIT_OUTPUT 把單位轉成外部格式。
  5. CONVERT_TO_CSV：用 SAP_CONVERT_TO_TEX_FORMAT，以分號分隔。
  6. SERVER_CONN → FTP_CONNECT；R3_FTP → FTP_R3_TO_SERVER。

11. 關鍵段落改寫（五）：組 CSV，金額與單位要轉成外部格式

SAP_CONVERT_TO_TEX_FORMAT 會把欄位原樣輸出。金額是內部格式：對 JPY 這類零小數位幣別，SAP 內部存的值是「÷100」後的數字，直接輸出會差 100 倍。每單位 KPEIN 也常被對方系統忽略。改寫版逐欄組字串，先把金額轉成外部金額：

METHOD to_csv.   " IMPORTING it_price TYPE tt_price RETURNING VALUE(rt_csv) TYPE string_table
  rt_csv = VALUE #( ( `KSCHL;VKORG;VTWEG;KUNNR;MATNR;DATAB;DATBI;KBETR;KONWA;KPEIN;KMEIN` ) ).

  LOOP AT it_price INTO DATA(ls).
    DATA lv_ext TYPE bapicurr-bapicurr.
    CALL FUNCTION 'BAPI_CURRENCY_CONV_TO_EXTERNAL'
      EXPORTING
        currency        = ls-konwa
        amount_internal = ls-kbetr
      IMPORTING
        amount_external = lv_ext.

    DATA lv_unit TYPE meins.
    CALL FUNCTION 'CONVERSION_EXIT_CUNIT_OUTPUT'
      EXPORTING
        input  = ls-kmein
      IMPORTING
        output = lv_unit
      EXCEPTIONS
        unit_not_found = 1
        OTHERS         = 2.
    IF sy-subrc <> 0.
      lv_unit = ls-kmein.
    ENDIF.

    APPEND |{ ls-kschl };{ ls-vkorg };{ ls-vtweg };{ ls-kunnr ALPHA = OUT };{ ls-matnr ALPHA = OUT };| &&
           |{ ls-datab DATE = ISO };{ ls-datbi DATE = ISO };{ lv_ext NUMBER = RAW };| &&
           |{ ls-konwa };{ ls-kpein };{ lv_unit }| TO rt_csv.
  ENDLOOP.
ENDMETHOD.
輸出格式要跟對方寫成規格書：分隔符號、有沒有標題列、日期格式（ISO 的 YYYY-MM-DD 最不會出錯）、小數點、前導零（客戶與物料號碼要不要 ALPHA OUT）、編碼（UTF-8 有沒有 BOM）。原程式用 DATS 的內部格式 YYYYMMDD、保留前導零，這些都是對方隱性依賴的格式。改寫時如果改動，必須跟對方同步，否則對方的匯入程式會出錯。

12. 關鍵段落改寫（六）：FTP 上傳封裝成類別，並說明明文風險與替代方案

SAP 的 FTP 函數群（SFTP 函數群，名稱雖然有 SFTP，但協定是明文 FTP）標準流程是：HTTP_SCRAMBLE 加擾密碼 → FTP_CONNECT（經由 RFC destination SAPFTPA，也就是在應用伺服器上執行的 FTP 用戶端；SAPFTP 則是在前端 GUI 執行）→ FTP_R3_TO_SERVER（內表上傳成檔案）→ FTP_DISCONNECT → RFC_CONNECTION_CLOSE。完整說明見 4-4 章第 12 節。

CLASS lcl_ftp_client DEFINITION FINAL.
  PUBLIC SECTION.
    CONSTANTS c_dest TYPE rfcdest VALUE 'SAPFTPA'.
    METHODS constructor IMPORTING iv_host TYPE csequence
                                  iv_user TYPE csequence
                                  iv_pwd  TYPE csequence
                        RAISING   cx_t100_msg.
    METHODS put_text    IMPORTING iv_file TYPE csequence
                                  it_text TYPE string_table
                        RAISING   cx_t100_msg.
    METHODS close.
  PRIVATE SECTION.
    CONSTANTS c_key TYPE i VALUE 26101957.      " SAP 範例報表 RSFTP002 用的固定 key，只是加擾不是加密
    DATA mv_handle TYPE i.
ENDCLASS.

CLASS lcl_ftp_client IMPLEMENTATION.
  METHOD constructor.
    DATA lv_pwd TYPE c LENGTH 64.
    lv_pwd = iv_pwd.
    DATA(lv_len) = strlen( lv_pwd ).
    CALL FUNCTION 'HTTP_SCRAMBLE'
      EXPORTING
        source      = lv_pwd
        sourcelen   = lv_len
        key         = c_key
      IMPORTING
        destination = lv_pwd.

    CALL FUNCTION 'FTP_CONNECT'
      EXPORTING
        user            = CONV char64( iv_user )
        password        = lv_pwd
        host            = CONV char64( iv_host )
        rfc_destination = c_dest
      IMPORTING
        handle          = mv_handle
      EXCEPTIONS
        not_connected   = 1
        OTHERS          = 2.
    IF sy-subrc <> 0.
      RAISE EXCEPTION TYPE cx_t100_msg EXPORTING t100_msgid = sy-msgid t100_msgno = sy-msgno
        t100_msgv1 = sy-msgv1 t100_msgv2 = sy-msgv2 t100_msgv3 = sy-msgv3 t100_msgv4 = sy-msgv4.
    ENDIF.
  ENDMETHOD.

  METHOD put_text.
    TYPES ty_line TYPE c LENGTH 1024.
    DATA lt_data TYPE STANDARD TABLE OF ty_line WITH EMPTY KEY.
    lt_data = VALUE #( FOR s IN it_text ( CONV #( s ) ) ).
    CALL FUNCTION 'FTP_R3_TO_SERVER'
      EXPORTING
        handle         = mv_handle
        fname          = CONV char255( iv_file )
        character_mode = abap_true
      TABLES
        text           = lt_data
      EXCEPTIONS
        tcpip_error    = 1
        command_error  = 2
        data_error     = 3
        OTHERS         = 4.
    IF sy-subrc <> 0.
      RAISE EXCEPTION TYPE cx_t100_msg EXPORTING t100_msgid = sy-msgid t100_msgno = sy-msgno
        t100_msgv1 = sy-msgv1 t100_msgv2 = sy-msgv2 t100_msgv3 = sy-msgv3 t100_msgv4 = sy-msgv4.
    ENDIF.
  ENDMETHOD.

  METHOD close.
    CALL FUNCTION 'FTP_DISCONNECT' EXPORTING handle = mv_handle.
    CALL FUNCTION 'RFC_CONNECTION_CLOSE'
      EXPORTING  destination = c_dest
      EXCEPTIONS OTHERS      = 1.
  ENDMETHOD.
ENDCLASS.

原程式在 FTP 這一段的問題：

  • 帳號密碼寫死在原始碼：任何有 SE38 顯示權限的人都看得到，而且會隨傳輸請求進到每個系統。HTTP_SCRAMBLE 只是讓密碼不在網路上以原文出現在 SAPFTPA 的呼叫參數裡，key 是公開的固定值，完全不算保護。
  • 沒有 FTP_DISCONNECT：連線留在 SAPFTPA，背景作業一多就會把 gateway 連線用光。
  • 錯誤被吃掉：MESSAGE … INTO l_err 只把訊息寫進變數，沒有顯示、也沒有寫進 log。上傳失敗時 job 還是顯示成功，對方收不到新價格也沒人知道。
  • 固定檔名 VK11.csv 每天覆蓋，對方還在讀取時被覆寫就會讀到半個檔。建議加上日期，或先上傳成 .tmp 再改名。
FTP 是明文協定。帳號、密碼和檔案內容（本案是客戶專屬價格，屬於商業機密）在網路上都以原文傳送，同網段的任何人都能側錄。建議的替代方案依優先順序如下：
  1. SAP Integration Suite（CPI）或 SAP PI/PO：ABAP 端只負責送出（Proxy、IDoc 或 OData），由中介層的 SFTP adapter 處理加密傳輸、重送、監控和金鑰管理。這是正式的企業級做法。
  2. SFTP 透過 SM69 外部作業系統指令：ABAP 先用 OPEN DATASET 把檔案寫到應用伺服器（AL11 可查），再用 SXPG_COMMAND_EXECUTE 呼叫在 SM69 定義好的指令（例如 sftp -b 批次腳本）。認證改用 SSH 金鑰，ABAP 程式裡完全不需要密碼（見下方程式碼）。
  3. 在過渡期真的只能用 FTP：至少限制在內網專線、帳號權限只開單一目錄的寫入，帳密放在受 S_TABU_NAM 權限保護的設定表中，而且不要傳送個資。
ABAP 本身沒有標準的 SFTP 用戶端函數，網路上的「ABAP SFTP 函數」大多是外部指令的包裝，或是協力廠商的套件。

13. ZFIP001 的業務情境、選擇畫面與程式架構

業務情境：財務付款給員工（費用報銷、代墊款）時，需要員工的公司代碼、身分證號、銀行代碼（Bank Key）和銀行帳號。公司把員工建成 BP（號碼段 8000 開頭），另外建了一張自訂表 ZFIBPDTHD0001 存這些付款資訊，供 FI 的付款和報表使用。這張表有兩個維護入口：SM30 維護檢視（截圖「Change View "FI HR BP Info."」），以及報表 ZFIP001。

ZFIBPDTHD0001 欄位（依素材）：MANDT、PARTNER、NAME_FIRST、NICKNAME（Known As）、NAME_LAST2（Name at Birth，實際被拿來放電子郵件）、L_COMCODE、L_IDNO、L_BANKKEY、L_BANK、AUTH（鎖定旗標）。

選擇畫面（截圖「FI HR BP Information」）：DISPLAY／MODIFY／CREATE 三選一；下方九個 PARAMETERS 對應表格欄位（單筆新增用）；最後是 Excel 檔案路徑 S_FILE（F4_FILENAME）。

程式架構：

  • DISPLAY：ALLOW_CONFIRM → GETALVDATA（讀整張表）→ DISPLAY_ALV（REUSE_ALV_FIELDCATALOG_MERGE ＋ REUSE_ALV_GRID_DISPLAY，GUI status ZSTANDARD，按鈕 Mark／Call Up Report）
  • MODIFY：使用者名稱含「IT」的人一律可以改；其他人要 AUTH 旗標是解鎖狀態才能改。可編輯欄位：公司代碼、Bank Key、帳號、ID、NICKNAME、NAME_LAST2。存檔 &DATA_SAVE → MODIFY ZFIBPDTHD0001 FROM TABLE；按鈕 &EXE2 切換全表的 AUTH 旗標
  • CREATE：有給 Excel 路徑就走 TEXT_CONVERT_XLS_TO_SAP 上傳，並比對 BUT000 確認 BP 存在；沒給路徑就用畫面欄位新增單筆
  • 未被呼叫的 FORM：GETDATA（從 BUT000 重建整張表）、SET_VAR／CALL_VIEW_MAINTENANCE（VIEW_RANGETAB_TO_SELLIST＋VIEW_MAINTENANCE_CALL 帶條件開 SM30）

14. ZFIP001 的原程式問題與現代改寫

原寫法問題改寫方向
IF SY-UNAME CS 'IT'用「帳號名稱包含 IT」判斷權限。任何帳號含 IT 字樣的人（例如 KITTY、SMITH）都拿得到修改權AUTHORITY-CHECK，用自訂權限物件或 S_TABU_NAM
ALLOW_CONFIRM：SELECT SINGLE auth … WHERE partner <> ''用任意一筆的 AUTH 代表「全表鎖定狀態」。HANA 沒有預設排序，SELECT SINGLE 沒有完整 key 時抓到哪一筆是不確定的；只要各筆 AUTH 不一致，今天能改、明天不能改鎖定狀態獨立存成一筆設定（例如 TVARVC 或一張單筆設定表），不要藏在資料列裡
AUTH 的語意程式碼中 '0' 是解鎖、'1' 是鎖定（按 &EXE2 時從 0 設成 1 會顯示「lock」）；但截圖上的說明卻寫「1 表示可更改」。文件和程式互相矛盾改用有語意的欄位（例如 LOCKED TYPE abap_bool），並在資料元素說明中寫清楚
Excel 比對：兩層 LOOP ＋ '00' && col1 = partnerO(n×m) 效能；假設 BP 號碼永遠是 8 碼、前面補 2 個零就等於 10 碼，號碼長度一改就全部比對失敗|{ col1 ALPHA = IN }| ＋ hashed table
GETDATA：DELETE FROM zfibpdthd0001（沒有 WHERE）＋ PARTNER CS '8000'刪掉整張表；而且 CS 是「包含」不是「開頭」，會誤抓到 00018000 這類號碼。這個 FORM 目前沒被呼叫，但任何人加一行 PERFORM 就會清光付款資料直接移除；真的需要時用 LIKE '8000%' 或列舉號碼段
MODIFY FROM TABLE 前沒有鎖SM30 和 ZFIP001 同時維護時，後存的人會蓋掉先存的人存檔前 ENQUEUE_E_TABLE（或自訂鎖物件）
REUSE_ALV_GRID_DISPLAY 編輯模式本專案禁用；而且回呼存檔時沒有呼叫 CHECK_CHANGED_DATA，最後一格剛改的值可能沒被寫回CL_GUI_ALV_GRID（需要編輯才用它）或 SM30 維護檢視

15. 與 FI 資料表的關係：BKPF／BSEG 與 S/4HANA 的 ACDOCA

ZFIP001 維護的是付款主資料，真正的應付與付款會記錄在會計文件裡。寫這類 FI 周邊程式時，一定會碰到的資料表關係如下（依 SAP 標準補寫）：

表S/4HANA 的角色讀取建議
BKPF會計文件檔頭（公司代碼＋文件號碼＋會計年度）照舊使用
BSEG總帳觀點的原始行項目，仍然存在，但只保存「入帳時」的行，不含 CO 分攤、外幣評價等後續產生的明細要看文件原貌、付款條件、稅碼時才讀
ACDOCAUniversal Journal：FI、CO、AA、ML 合一的唯一真相，含分類帳 RLDNR、所有幣別、利潤中心、成本中心、段落報表、餘額、分析一律以 ACDOCA 為主；要加 RLDNR 條件（通常是主分類帳 '0L'），否則多分類帳會重複計算
BSIK／BSAK、BSID／BSAD、BSIS／BSASECC 的索引表，在 S/4HANA 變成相容性 CDS view（讀取時即時從 BSEG／ACDOCA 計算）舊程式仍能讀，但效能不如直接查 ACDOCA；新程式請改用 ACDOCA 或 released CDS（例如 I_OperationalAcctgDocItem）
BUT000／BUT0BKBP 一般資料／BP 銀行明細取代 LFA1／LFBK 的主資料來源（LFA1 仍存在，由 CVI 同步）
 
" 查員工 BP（供應商角色）在某公司代碼的未清應付：S/4HANA 以 ACDOCA 為主
SELECT rbukrs, gjahr, belnr, docln, lifnr, budat, hsl, rhcur, augbl
  FROM acdoca
  WHERE rldnr   = '0L'                       " 主分類帳：少了這行，多分類帳會重複計算
    AND rbukrs  = @p_bukrs                   " 例：'1000'
    AND lifnr  IN @lt_lifnr                  " 列舉 EQ，不要 BT '8000000000'～'8999999999'
    AND koart   = 'K'
    AND augbl   = @space                     " 未清
  ORDER BY rbukrs, lifnr, budat, gjahr, belnr, docln   " HANA 沒有預設排序
  INTO TABLE @DATA(lt_open_items).

" 要看文件原貌（付款條件、原始行文字）時才回頭讀 BSEG
IF lt_open_items IS NOT INITIAL.
  SELECT bukrs, belnr, gjahr, buzei, zterm, zfbdt, sgtxt
    FROM bseg
    FOR ALL ENTRIES IN @lt_open_items
    WHERE bukrs = @lt_open_items-rbukrs
      AND belnr = @lt_open_items-belnr
      AND gjahr = @lt_open_items-gjahr
    INTO TABLE @DATA(lt_bseg).
ENDIF.
ACDOCA 的 DOCLN（6 碼）和 BSEG 的 BUZEI（3 碼）不是一對一對應，因為 ACDOCA 可能比 BSEG 多出 CO 或評價產生的行。要把兩邊連起來，請用文件號碼加上 ACDOCA 的 BUZEI 欄位，不要用行號位置去對。員工 BP 的號碼段也要用列舉，不要用區間：員工離職後號碼可能被重用，或者號碼段曾經調整過，用 BT 會把非員工的供應商一起抓進來。

16. 上線注意總表

程式上線前上線後監控
ZMMR0002變更日期設成必填；確認採購相關欄位的資料元素都有勾 Change document（自訂欄位 CI_EKPODB 也要）；用 SE30／SAT 量測一個月資料量的執行時間使用者如果習慣「不給日期」，要教育改用 variant
ZMMB0009增量同步機制；外部表主鍵；第一次全量搬遷另外寫一支一次性程式分批執行；DBCO 連線帳號只給 INSERT／UPDATE 權限SM37 job log、同步筆數與外部表筆數每日對帳
ZSDI0006有效期間改成含邊界；KSCHL 列舉；跟對方確認 CSV 規格；帳密移出程式；優先改走 SFTP 或 CPI上傳失敗時 job 要顯示紅燈；每週全量比對一次，補抓被刪除的條件記錄
ZFIP001刪除 GETDATA；權限物件取代 CS 'IT'；釐清 AUTH 語意；加鎖；評估搬回 BUT0BK變更文件或 SM30 的表格紀錄（SCU3，需開啟表格 logging）定期稽核
