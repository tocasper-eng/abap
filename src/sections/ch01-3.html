1. 為什麼要學三層維護？先看 SAP 自己怎麼做

SAP 標準系統裡有一大類畫面長得都一樣：左邊一個樹狀或清單，選一筆，雙擊進去下一層，再選一筆，再進去更下一層。這種畫面叫做多階維護視圖（View Cluster，中文常稱「維護視圖群組」），不是有人手工刻的 Dialog 程式，而是用 SE54 產生出來的。

  • NACE　輸出控制（Output Determination）。應用別 → 輸出類型 → 存取順序 → 條件記錄，典型的多階維護。講義第二節就是叫你先去 NACE 點一遍，體會「原來這是產生出來的」。
  • OKKP　管控範圍（Controlling Area）維護，也是三層式：管控範圍 → 分派公司代碼 → 啟動元件／控制指標。
  • OMT3　把倉庫號碼指派到工廠／儲存地點（Assign Warehouse Number to Plant/Storage Location），是 WM 與 IM 整合的重要設定。路徑：SPRO → Enterprise Structure → Assignment → Logistics Execution → Assign Warehouse Number to Plant/Storage Location。它其實就是一支「參數交易」，背後跑的是 View Cluster。
老師的重點：學完這一章，以後看到類似的畫面就能知道他是如何設計的了。這是 ABAP 顧問跟一般 Coder 的分水嶺 —— 能配置解決的就不要寫程式，而多階維護畫面根本不用寫程式，用產生的就好。

2. 三層式維護的觀念地圖：表 → 維護視圖 → 維護對話框 → View Cluster

整條鏈路一共四個物件，缺一不可。很多同學做不出來，都是因為搞不清楚自己現在在做哪一層。

層次物件建立工具用途
① 資料層透明表 Transparent Table（ZMARA／ZMARC／ZMARD）SE11真正存資料的地方；表跟表之間用外部索引鍵（Foreign Key）串起來
② 視圖層維護視圖 Maintenance View（ZMV_MARA／ZMV_MARC／ZMV_MARD）SE11 → View → Maintenance View決定「這一層要維護哪些欄位」，並帶 Delivery Class 與 Data Browser/Table View Maint. 設定
③ 畫面層維護對話框 Table Maintenance Dialog（Function Group + Screen + 事件）SE54（Generated Table Maintenance）產生 SM30 可以叫得動的畫面；一步式或兩步式
④ 群組層維護視圖群組 View Cluster（例如 ZMV_MARA_000）SE54 → Edit View Cluster把三個維護對話框串成「上層選一筆 → 下層只顯示相關資料」的階層畫面，用 SM34 執行
名詞對照：SE54 的正式名稱是「Generate Table Maintenance Dialog」，也可以從 SE11 的選單 Utilities → Table Maintenance Generator 進去，兩者是同一件事。SM30 執行「單一維護視圖」，SM34 執行「View Cluster」。

3. 第一步：SE11 建三張表 ZMARA / ZMARC / ZMARD 與外部索引鍵

這三張表在模仿 SAP 標準物料主檔的三層結構：ZMARA（一般資料，Key = MANDT + MATNR）→ ZMARC（工廠資料，Key = MANDT + MATNR + WERKS）→ ZMARD（儲存地點／庫存資料，Key = MANDT + MATNR + WERKS + LGORT）。

表主鍵建議欄位外部索引鍵
ZMARAMANDT、MATNRMTART（物料類型）、MATKL（物料群組）、MEINS（基本單位）、ERSDA、ERNAMMTART → T134、MEINS → T006
ZMARCMANDT、MATNR、WERKSDISMM（MRP 類型）、EKGRP（採購群組）、BESKZ（採購類型）MANDT、MATNR → ZMARA；WERKS → T001W
ZMARDMANDT、MATNR、WERKS、LGORTLABST（未受限庫存）、INSME（品檢庫存）、SPEME（凍結庫存）MANDT、MATNR、WERKS → ZMARC；LGORT → T001L

建外部索引鍵的操作：在 SE11 的 Fields 頁籤把游標停在該欄位 → 按工具列的 Foreign Keys 鑰匙圖示 → Check table 填上層表名 → 系統會自動提出欄位對應（Key fields）→ 確認 Field assignment 正確 → Cardinality 通常填 1 : CN（上層一筆對下層多筆）→ Foreign key field type 選 Key fields of a text table / Non-key-fields 視情況。（依講義步驟整理）

外部索引鍵不是裝飾品。SE54 產生 View Cluster 時，就是靠外部索引鍵自動推導上下層的關聯鍵。外鍵沒建或建錯，SE54 抓出來的關聯欄位就會是錯的，做到最後一定卡住。這也是講義 6-04 心得第 2 點在講的事。

三張表建好之後，先用一段 ABAP 驗證資料串得起來。這是現代寫法的 JOIN，一次把三層撈出來：

REPORT zmm_zmard_check.

" 三層 JOIN：ZMARA(一般) → ZMARC(工廠) → ZMARD(儲存地點)
" 注意：ABAP SQL 一律用 @ 逸出主機變數；不要用 SELECT *
PARAMETERS: p_werks TYPE t001w-werks OBLIGATORY.

SELECT a~matnr,
       a~mtart,
       a~matkl,
       a~meins,
       c~werks,
       c~dismm,
       c~ekgrp,
       d~lgort,
       d~labst,
       d~insme
  FROM zmara AS a
  INNER JOIN zmarc AS c ON c~matnr = a~matnr
  INNER JOIN zmard AS d ON d~matnr = c~matnr
                       AND d~werks = c~werks
  WHERE c~werks = @p_werks
  ORDER BY a~matnr, c~werks, d~lgort
  INTO TABLE @DATA(lt_stock).

IF lt_stock IS INITIAL.
  MESSAGE |工廠 { p_werks } 沒有任何資料| TYPE 'S' DISPLAY LIKE 'W'.
  RETURN.
ENDIF.

" 用 REDUCE 直接算總庫存，不要再寫迴圈累加
DATA(lv_total) = REDUCE zmard-labst( INIT s = CONV zmard-labst( 0 )
                                     FOR <ls> IN lt_stock
                                     NEXT s = s + <ls>-labst ).
WRITE: / |工廠 { p_werks } 未受限庫存合計：{ lv_total NUMBER = USER }|.
MANDT 不需要出現在 JOIN 條件裡。ABAP SQL 對 client-dependent 的表會自動加上目前 client 的條件（若真的要跨 client，才用 USING ALL CLIENTS 或 USING CLIENT @lv_mandt）。

4. 第二步：SE11 建三個維護視圖 ZMV_MARA / ZMV_MARC / ZMV_MARD

路徑：SE11 → View → 輸入 ZMV_MARA → Create → 選 Maintenance View。

  1. Tables/Join Conditions：Tables 只放一張表（ZMARA）。三層維護的每一個維護視圖各自對應一張表，不要在這裡就 JOIN 起來，JOIN 是 View Cluster 的工作。
  2. View Flds：按 Table fields 把要維護的欄位全部帶進來。Key 欄位一定要在。
  3. Maint.Status（維護狀態）頁籤：Access = Read and change（可讀可改）；Delivery class 通常設 A（Application table）或 C（Customizing table，會產生傳輸請求）。
  4. 存檔 → 指定 Package（三個 View 必須放同一個 Package）→ Activate。
  5. ZMV_MARC、ZMV_MARD 重複同樣動作。
講義 6-04 心得第 3 點的「S」：在建 Maintenance View 與建 Cluster View 的欄位清單裡，都有一欄要勾成 S（代表該欄位是上層傳下來的「Selection／Sub-set 欄位」，也就是用來把下層資料限縮成「只屬於上層那一筆」的欄位）。兩個地方都要勾，只勾一邊做不出階層效果。
Delivery Class 選 C 還是 A 的實務差別：設定型資料（客戶自訂的組態）選 C，維護時會跳出傳輸請求視窗，可以從 DEV 傳到 PRD；交易型／主資料選 A，資料留在各系統不跟著傳輸。做客戶專案時選錯，會變成「PRD 的資料被 DEV 覆蓋」或「設定傳不過去」。

" Event 01：Before saving —— 存檔前檢核
FORM check_before_save.
  " 物料類型必須存在於 T134，否則擋下
  FIELD-SYMBOLS <ls_row> TYPE zmv_mara.

  LOOP AT total ASSIGNING FIELD-SYMBOL(<ls_total>).
    " TOTAL 的第 1 個字元是動作旗標，資料本體從第 2 個字元起
    ASSIGN <ls_total>+1 TO <ls_row> CASTING.
    IF sy-subrc <> 0.
      CONTINUE.
    ENDIF.

    SELECT SINGLE @abap_true FROM t134
      WHERE mtart = @<ls_row>-mtart
      INTO @DATA(lv_exists).

    IF lv_exists <> abap_true.
      MESSAGE |物料類型 { <ls_row>-mtart } 不存在於 T134| TYPE 'E'.

7. 第四步：SE54 建 View Cluster（三層）與 SM34 執行

路徑：SE54 → 在初始畫面選 Edit View Cluster（維護視圖群組）→ 輸入名稱 ZMV_MARA_000 → Create。

  1. Object Structure（物件結構）：依序把三個維護視圖登記進來
    • ZMV_MARA　Position 1、Dep. = 上層（起始節點）、Predecessor 留空
    • ZMV_MARC　Position 2、Predecessor = ZMV_MARA
    • ZMV_MARD　Position 3、Predecessor = ZMV_MARC
  2. 每一列雙擊進 Field-Dependence（欄位相依）：把上層傳下來的 Key 欄位對應好，並勾上前面說的 S。ZMARC 要對 MANDT + MATNR；ZMARD 要對 MANDT + MATNR + WERKS。系統自動抓的關聯鍵可能不準，要會自己調整。
  3. Header Entry：填 View Cluster 的說明文字。
  4. 存檔 → 指定 Package（跟三個 View 同一個 Package）→ 返回上一頁之後，要再按 ACTIVATE 鈕（老師特別提醒，很多人漏掉這一步，結果 SM34 打不開）。

執行：SM34 → 輸入 ZMV_MARA_000 → Maintain。應該看到左邊 Dialog Structure 樹狀，點 ZMARA 選一筆物料 → 雙擊左樹的「工廠」節點 → 只出現該物料的工廠資料 → 再往下就是儲存地點。

三層維護實作心得（老師的三條鐵律）

  1. 所有的 View 都要在同一個 Package。跨 Package 會在啟用或傳輸時出問題。
  2. SE54 讓系統自動抓關聯鍵時，可能不準，要會自己調整。自動推導靠的是外部索引鍵，外鍵設計不完整就會抓錯。
  3. 「S」設定在建 Maintenance View 與 Cluster View 時都要勾。

SE11 改良修正（6-03）

  • 執行結果應該是 MANDT 不必勾成 S。MANDT 是 client 欄位，系統自己會處理，勾成 S 反而會多出一個沒用的相依條件。
  • 有些欄位的抬頭（Column heading）不正確，這是資料元素的短文字問題。只能在 Screen Layout（畫面配置）上修飾 —— 進 SE51 或從 SE54 的產生畫面雙擊欄位，改 Text 屬性；或者回到 SE11 把 Data Element 的 Field Label（Short／Medium／Long／Heading）補齊，再重新產生一次維護對話框。
改完 Data Element 的欄位標籤後，維護對話框不會自動更新，要回 SE54 對該 view 執行「重新產生（Generated Objects → Change → 重新產生）」。如果你已經在產生的畫面上手工改過東西，重新產生會蓋掉，這也是為什麼自訂邏輯要寫在 Events 而不是寫在畫面裡。

9. SE39：分割螢幕編輯器與程式比較

SE39 是 ABAP Splitscreen Editor（分割螢幕編輯器）：左右各開一支程式，同一個畫面對照著看、對照著改。做客製最常用在「客戶版程式 vs 標準程式」、「新版 vs 舊版」的比對。

  • 開啟：SE39 → 左欄輸入程式 A、右欄輸入程式 B → Display／Change。也可以從 SE38 的選單 Utilities → Splitscreen Editor 進去。
  • 比對：左右都載入之後按 Compare（比較）鈕，系統會標出差異行；Next difference / Previous difference 逐段跳。
  • 搬程式碼：選取左邊的段落 → 用剪下貼上直接放進右邊，做版本移植時很省事。
  • 版本管理：真正要看「同一支程式的不同版本」差異，用 SE38 → Utilities → Versions → Version Management，選兩個版本按 Compare；跨系統比對可以按 Remote comparison 指定 RFC 目的地，比對 DEV 與 PRD 的同一支程式。
  • Eclipse/ADT：在 ADT 裡是 Compare With → Another ABAP Object / Local History，功能更好用，但 SE39 在只有 SAP GUI 的客戶現場仍然是必備技能。
老師的用法：把「上課寫的版本」跟「自己回家改的版本」用 SE39 並排，一邊比一邊記，比單純重看程式有效得多。另外，做增強（User Exit／BAdI）前，先用 SE39 把標準程式跟自己要改的 Include 並排，可以避免改錯地方。

10. 查資料的兩把刀：SE16N 與 SE16H；以及怎麼由畫面欄位反查資料表

SE16 / SE16N / SE16H 的差別

TCODE特色什麼時候用
SE16最原始的 Data Browser，畫面陽春權限只給到 SE16 時
SE16NGeneral Table Display。可自選輸出欄位、可存 Variant、可直接輸出成 ALV／Excel、支援 &SAP_EDIT（多數 S/4 系統已鎖住或需 Debug 才能開）日常查資料的主力
SE16HHANA 版。多了 Group by／Aggregation（SUM、MAX、MIN、AVG、COUNT）、Having、Order by、多表 JOIN（Table Join 頁籤）、以及「Total」「Sort」欄位設定要做小計、分群、快速驗證統計數字時 —— 不用寫程式就能當一次性報表
SE16H 的隱藏技：勾 Outer Join 可以做左外接；Number of Hits 設 0 代表不限筆數（大表小心）；輸入條件時用列舉（逗號分隔的多個單值）比用區間（BETWEEN）安全，因為某些欄位（例如版本、成本類別）在區間裡會夾進你不想要的值。
SE16N 的 &SAP_EDIT 直接改資料庫、不會走任何應用邏輯、不會寫變更文件，在生產機是重大事故來源。任何時候都不要在 PRD 用它「修資料」。

由畫面欄位反查資料表（四招）

  1. F1 → 技術資訊（Technical Information）：把游標放在欄位上按 F1 → 按小鎚子（Technical Information）→ 會顯示 Table Name（畫面結構名）、Field Name、Data Element、Screen field、Program name / Screen number。注意這裡看到的常常是畫面結構（例如 RM03M、VBAK 的 dialog structure），不一定是真正的資料庫表。
  2. 從 Data Element 反查：拿到 Data Element 之後，SE11 顯示該 Data Element → 按 Where-Used List（Ctrl+Shift+F3） → 勾 Table Fields → 就會列出所有用到這個資料元素的資料表。
  3. SE84（Repository Information System）：ABAP Dictionary → Database Tables／Views，可以用名稱樣式、Package、Application Component 搜尋。例如想找 SD 的表就用 Application Component = SD 去撈。SE84 也可以反查「某個 Table 被哪些程式用到」。
  4. SDBE / ST05（追 SQL）：
    • ST05 SQL Trace：Activate Trace → 去畫面做一次操作 → 回來 Deactivate Trace → Display Trace。追出來的每一行都是真正打到 DB 的 SQL，表名一目瞭然。這是最可靠的一招。
    • SDBE Explain SQL Statement：把一段 SQL 貼進去看執行計畫（Explain Plan），用來判斷有沒有走到索引。ST05 的 trace 明細上按 Explain 也會轉到同樣的功能。

也可以用程式查字典。下面這段用 DDIC 表反查「哪些資料表含有某個欄位」：

       t~tabclass,
       f~fieldname,
       f~keyflag,
       f~rollname,

  INTO TABLE @DATA(lt_tab).

IF lt_tab IS INITIAL.
  MESSAGE |找不到含欄位 { p_field } 的透明表| TYPE 'S' DISPLAY LIKE 'W'.
  RETURN.
ENDIF.

12. 使用者主檔：USR21 / ADRP / USR02 與 ZUSER 實作（ALV 版）

這是講義 7-01 的核心：以 USR21 為核心，往兩邊接。

表關聯鍵重要欄位
USR21（使用者 ↔ 位址對照）核心表BNAME 用戶代碼、PERSNUMBER 員工（人員）編號、ADDRNUMBER 地址編號、KOSTL 成本中心、START_MENU 初始選單
ADRP（人員位址）USR21-PERSNUMBER = ADRP-PERSNUMBERNAME_FIRST 名字、NAME_LAST 姓氏、NAME_TEXT 全名、DATE_FROM／DATE_TO 有效期間

ADRP 是時間相依的：同一個 PERSNUMBER 可能有多筆（不同 DATE_FROM／DATE_TO），還有 NATION 欄位（''＝標準格式、'I'＝國際格式、'K'＝漢字格式）。原講義用 SELECT SINGLE 抓 ADRP，如果剛好有多筆就會抓到不確定的那一筆 —— 這正是「SELECT SINGLE 沒有排序保證」的經典陷阱。正解是加上 date_from <= @sy-datum AND date_to >= @sy-datum 與 nation = @space。

原講義寫法的問題（要看得懂、但不要照抄）

  • TABLES: USR02, USR21, ADRP. —— 只為了 SELECT-OPTIONS 的參照就宣告 TABLES，會產生同名的全域工作區，是舊寫法。改用 SELECT-OPTIONS s_bname FOR gv_bname 搭配 DATA gv_bname TYPE usr21-bname.。
  • 在 LOOP 裡對每一筆做兩次 SELECT SINGLE —— 典型的 N+1 查詢。1000 個使用者就打 2000 次 DB。正解是一次 JOIN，或先用 FOR ALL ENTRIES 撈進兩張 hash 內表再對照。
  • SELECT * ... INTO CORRESPONDING FIELDS OF TABLE —— 欄位靠名字硬對，欄位改名就默默出錯，而且傳整列浪費 IO。
  • ALV 版裡 i_callback_pf_status_set = 'STATUS_SET'，但實際 FORM 叫 FORM_PF_STATUS_SET，名字對不上，事件不會觸發。這是原程式的實際 Bug，抄的時候要注意。
  • lt_event 都填好了卻又同時傳 i_callback_*，兩套機制重複；REUSE_ALV_GRID_DISPLAY 在 S/4 已不建議新開發使用。

15. Infotype 與 HR 資料表

什麼是 Infotype

Infotype（資訊類型）是把內容相似的資料分組管理的單位，用四位數字當代碼，例如 0001 組織分派、0002 個人資料。從技術面看，一個 Infotype 同時是一組資料分群、一個畫面、一張資料庫表、以及一個結構；它還帶著系統控制屬性，例如時間限制（Time Constraint）、追溯計算相關性等。

為什麼 HR 要用 Infotype？講義給了兩個理由：

  • Security（安全）：HR 資料的敏感度差很多。地址、稅務資料員工可以自己看自己改；薪資、考評不行。切成不同 Infotype 才能對每一組資料套不同的權限設定 —— 誰能看、誰能改。
  • History（歷史）：HR 資料是時間相依的。你現在的薪資是一個數字，下個月一號調薪之後是另一個數字；七月一日搬家。舊資料必須保留，Payroll 才知道今天該付多少、下個月該付多少；報表也才回答得出「YuLin 從到職到現在的薪資變化」。所以每一個 Infotype 記錄都有起始日（BEGDA）與結束日（ENDDA）。
Infotype內容
0000Events（人事異動措施）
0001Org assignment（組織分派）：PERNR、姓名、員工群組／次群組、職位、人事範圍／次範圍、成本中心
0002Personal info（個人資料）

Infotype 與內表的差別：Infotype 是一筆「記錄／畫面」，掛在員工或 PD 物件（職位、組織單位）上；資料表存的是這個 Infotype 的值與行為設定。HR 的主程式（邏輯資料庫 PNP／PNPCE）會在執行期自動幫每個 Infotype 產生對應的內表（Pnnnn，例如 P0001），程式用 GET PERNR 事件搭配 INFOTYPES: 0001, 0002. 取用。

17. 總結練習：從零做出一整套（第一節的驗收題）

講義開宗明義給的練習順序，是把 1-2 章的資料字典與這一章的維護畫面串起來的完整流程：

  1. Domain（域）—— 定資料型態、長度、值範圍（Value Range／Fixed Values）
  2. Data Element（資料元素）—— 掛 Domain，定四種欄位標籤與 F1 說明文件
  3. Master Table（主檔表）—— 例如 Z00_KNA1
  4. Transaction Table（交易表）—— 例如 Z00_VBAK
  5. Foreign Key（外部索引鍵）—— 把交易表接回主檔表
  6. Search Help（搜尋說明）—— 掛在欄位或 Data Element 上，F4 才有東西
  7. Maintenance View（維護視圖）＋ SE54 產生維護畫面

驗收成果：用 SM30 打開 Z00_VBAK，能新增、修改、刪除，且外鍵欄位按 F4 會跳出正確的搜尋說明。

做完之後，可以寫一支小程式驗證資料的參照完整性（下層有、上層沒有的孤兒資料）：

*&---------------------------------------------------------------------*
*& Report ZMM_CHECK_ORPHAN —— 檢查三層表的參照完整性
*&---------------------------------------------------------------------*
REPORT zmm_check_orphan.

" 先把上層 Key 撈成 HASHED，查找 O(1)
SELECT matnr FROM zmara
  INTO TABLE @DATA(lt_mara).

DATA lt_mara_key TYPE HASHED TABLE OF zmara-matnr WITH UNIQUE KEY table_line.
lt_mara_key = VALUE #( FOR <m> IN lt_mara ( <m>-matnr ) ).

SELECT matnr, werks FROM zmarc
  ORDER BY matnr, werks
  INTO TABLE @DATA(lt_marc).

DATA lt_bad TYPE TABLE OF string.

LOOP AT lt_marc INTO DATA(ls_marc).
  " line_exists 判斷內表是否有該筆，取代 READ TABLE ... TRANSPORTING NO FIELDS + sy-subrc
  IF NOT line_exists( lt_mara_key[ table_line = ls_marc-matnr ] ).
    APPEND |ZMARC 有孤兒資料：MATNR = { ls_marc-matnr }，WERKS = { ls_marc-werks }| TO lt_bad.
  ENDIF.
ENDLOOP.

IF lt_bad IS INITIAL.
  MESSAGE '參照完整性檢查通過' TYPE 'S'.
ELSE.
  LOOP AT lt_bad INTO DATA(lv_msg).
    WRITE: / lv_msg.
  ENDLOOP.
  WRITE: / |共 { lines( lt_bad ) } 筆異常 —— 表示外部索引鍵沒有設好，或有人繞過維護畫面直接改資料庫|.
ENDIF.
FOR ALL ENTRIES 空表陷阱：如果上面改用 SELECT ... FOR ALL ENTRIES IN lt_mara，而 lt_mara 是空的，SAP 會忽略整個 WHERE 條件把全表撈回來。任何 FOR ALL ENTRIES 之前一定要先 IF lt_x IS INITIAL. RETURN. ENDIF.，並且對驅動內表先做 SORT + DELETE ADJACENT DUPLICATES。
