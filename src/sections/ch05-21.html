第 5-21 章 BC490 ABAP 效能調校

BC490 是 ABAP 開發者的「體檢與開刀」課：先用工具量出程式慢在哪裡（CPU、資料庫、記憶體還是網路），再依問題分類改寫 SQL、設計索引、使用緩衝、選對內表型別。本章以原廠 Col19 教材的九個單元為骨架，逐一對照强晟 2008 年筆記（R/3 4.6～ECC 6.0、Oracle 為例），並補上 S/4HANA 時代必備的 SQL Monitor、SWLT、ATC、Code Pushdown、CDS 與 AMDP。貫穿全章的一句話：資料庫是整個 SAP 系統唯一不能靠加機器擴充的資源——能不打資料庫就不打，要打就一次打準。

2. 效能分析的出發點：架構、存取成本與工具地圖

SAP 是三層主從架構：展示層、應用層、資料庫層。展示層與應用層可以水平擴充（硬體不夠就加前端、加應用伺服器），資料庫是中央資源，無法靠「多加幾台資料庫」擴充。因此 ABAP 效能分析有兩個主要目標：

  • 降低應用伺服器 CPU 負荷——主要來自內表處理（大內表、巢狀迴圈）。
  • 降低資料庫負荷——主要來自 SQL（讀太多、讀太頻繁、存取路徑錯）。這是重中之重。

3. 記憶體管理：使用者內容、Extended Memory 與 PRIV 模式

對話工作處理程序遠少於線上使用者，因此一個工作處理程序只在「處理某個對話步驟」期間屬於某位使用者（工作處理程序多工 Work Process Multiplexing）。使用者的變數、內表、權限資料存在使用者內容（User Context），每個對話步驟開始時 Roll-in、結束時 Roll-out。

記憶體區性質存放內容
SAP Local（WP）Memory／Local Roll AreaOS Local執行中的 runtime object、stack、DB 傳輸緩衝、指向其他記憶體區的指標
SAP Extended Memory（EM）OS Shared交易資料的主要存放處；預設以 1,024 KB 為區塊配置；7.40 起取代舊的 global Roll Area
SAP Heap Memory（PRIV memory）OS LocalEM 用完或達使用者配額後的「緊急備援」
SAP BuffersOS Shared程式（PXA）、Nametab、表緩衝等約 40 種緩衝
SAP Global Extended Memory（EG）OS Shared跨使用者內容共用，例如 Shared Objects
SAP Paging AreaShared＋檔案EXPORT TO MEMORY（舊）、EXTRACT、SUBMIT／CALL TRANSACTION 傳參

對話工作處理程序的配置順序：Roll-in → 用 EM 直到使用者配額（參數 ztta/roll_extension）→ 改用 Heap，此時進入 PRIV 模式（Private Mode）：Heap 無法 Roll-out，該工作處理程序被這位使用者獨占，其他人只能排隊。一兩個 PRIV 無妨，很多個同時 PRIV 時全系統都會變慢。相關參數：rdisp/wppriv_max_no、rdisp/max_priv_time、abap/heaplimit（預設 40 MB，超過則交易結束後重啟該工作處理程序以歸還 OS 記憶體）。背景工作處理程序一開始就用 Heap，沒有 PRIV 問題（它本來就不多工）。

其他觀念：外部模式（External Mode＝一個 SAP GUI 視窗）數量由 rdisp/max_alt_modes 控制（2～16，預設 6）；每個外部模式最多 9 層內部模式（Internal Mode，SUBMIT AND RETURN／CALL TRANSACTION 堆疊）；SAP Virtual Memory 合計不宜超過實體 RAM 的 125%。

ST02 → Detail Analysis → SAP memory → Mode List 可看每個 session 用了多少 EM／Heap；有 Heap 的 session 就代表一個 PRIV 中的工作處理程序。記憶體不足的典型 ST22 短傾印：

  • 使用者內容用盡：TSV_TNEW_PAGE_ALLOC_FAILED、TSV_TNEW_BLOCKS_NO_ROLL_MEMORY、SYSTEM_ROLL_IN_ERROR
  • 與資料庫溝通時記憶體不足：DBIF_RTAB_NO_MEMORY、DBIF_RSQL_NO_MEMORY
  • Paging 用盡：SYSTEM_NO_MORE_PAGING；啟動時共享記憶體違規：PXA_NO_SHARED_MEMORY、STORAGE_PARAMETERS_WRONG_SET
  • 跑太久：TIME_OUT（對話工作處理程序超過 rdisp/max_wprun_time）——大量資料應改背景作業（見 4-4 章）

除錯器的記憶體分析（詳見 5-4 章 BC403）：新除錯器的 Memory Analysis 工具可列出前 25 大記憶體物件，區分 Bound Memory（刪掉這個物件能釋放多少）與 Referenced Memory；Stack、Dynamic Memory Objects、Static Variables 分開統計。强晟筆記的舊路徑是「設定 → 表記憶體」與「轉到 → 系統 → 系統區域，區域輸入 ITAB」。

4. 設計期檢查：Code Inspector（SCI）與 ATC

Code Inspector（SCI）檢查 Repository 物件的靜態內容，涵蓋效能、安全、語法、命名規範。它整合在 SE80／SE38／SE37／SE24／SE11（選單「程式 → 檢查 → Code Inspector」，使用檢查變式 DEFAULT）；對傳輸請求則在 SE09 執行，使用變式 TRANSPORT。

SCI 的三個元素：檢查變式（Check Variant）＋物件集（Object Set）＝檢驗（Inspection）。全域元素人人可用、可傳輸；區域元素只有擁有者能改；區域的 DEFAULT 變式會覆蓋全域 DEFAULT。大物件集（>50 個）可平行執行：每包 10～50 個物件、每台伺服器最多 12 個 task。命名檢驗與靜態物件集預設 50 天後刪除。

與效能相關的重要檢查項目（Col19 列出，7.40 起新增多項）：

  • 沒有 WHERE 條件的 SELECT；WHERE 未用到任何索引欄位；WHERE 未用到索引第一個欄位
  • CLIENT SPECIFIED 但 WHERE 沒有用戶端欄位
  • 繞過表緩衝的 SELECT（刻意的 BYPASSING BUFFER、FOR UPDATE 不報）
  • 有問題的 SELECT *（實際使用欄位低於門檻，預設 20%）
  • 可改寫成 JOIN 的 FOR ALL ENTRIES；跨模組化單元的迴圈內 DB 操作；巢狀迴圈
  • SELECT 之後緊接 CHECK；SELECT…ENDSELECT 迴圈中用 EXIT／RETURN
  • 標準表的循序讀取（內表 O(n) 存取）

5. 對話步驟與回應時間：STAD 與 ST03N

對話處理中，一次畫面切換＝一個對話步驟（Dialog Step）；更新、Spool 的每個請求也各算一步；背景作業可視為一個或多個步驟。一個使用者請求的 13 個處理階段：

  1. 使用者請求送到應用伺服器
  2. 若工作處理程序全忙，放進 Dispatcher 佇列
  3. 分派到工作處理程序
  4. Roll-in 使用者內容
  5. 先嘗試由 SAP 表緩衝滿足 SQL
  6. 緩衝沒有才把 SQL 送到資料庫
  7. 嘗試由資料庫快取滿足
  8. 把缺少的資料區塊從磁碟讀進資料庫快取（强晟筆記「導入確實的資料塊」應為「缺少的」之誤譯）
  9. 必要時從資料庫快取置換掉舊區塊
  10. 結果傳回應用伺服器
  11. 若資料有異動，更新本機表緩衝
  12. 結果經 Dispatcher 傳回展示層
  13. Roll-out 使用者內容

回應時間的組成（SAP Note 8963）：回應時間＝Dispatcher 等待＋Roll-in＋Load/Generation＋DB 請求時間＋Enqueue＋Roll-wait＋處理時間。其中處理時間不是量的，是用減法算出來的；CPU 時間由作業系統量測，不是回應時間的加總項，而是橫跨各段的另一個維度。

時間項偏高代表什麼
Dispatcher Wait工作處理程序被卡太久（多半不是設定數量不足）；SM51 → Queue information 看 Requests waiting
Roll-wait同步 RFC、GUI Roundtrip（見第 21 節）、要求資料量過大
Load/Generation程式、CUA、畫面緩衝太小
DB RequestDB 伺服器 CPU/記憶體瓶頸、昂貴 SQL、鎖、缺索引、統計資訊過期、DB 快取太小
CPU 高大內表、低效率程式邏輯
處理時間 > 2 × CPU 時間應用伺服器 CPU 瓶頸（差值稱 Lost Time）

經驗法則：全系統平均對話回應時間應 < 1,000 ms；平衡系統中「處理時間：DB 時間：Roll-wait」約 40：40：20。强晟筆記的路線圖：若某對象 CPU 時間 > 40% ×（回應時間－Dispatcher 等待）→ 走 ABAP Runtime Analysis；若 DB 時間 > 40% ×（回應時間－Dispatcher 等待）→ 走 SQL 效能追蹤。

STAD（舊稱 STAT）顯示單筆統計記錄：資料由各工作處理程序在每步結束時寫入共享緩衝，再 flush 到 OS 檔案（參數 stat/file，每小時一個檔，stat/max_files 預設保留 48 個）。背景工作 SAP_COLLECTOR_FOR_PERFMONITOR（報表 RSCOLL00，依表 TCOLL 呼叫 RSSTAT90）把資料彙總進表 MONI，供 ST03N 使用。STAD 的使用步驟：

  1. Step 0：先執行目標程式幾次，讓緩衝與快取填滿（Transferred kBytes 穩定）。
  2. Step 1：正式執行（統計記錄自動寫，不用開關）。
  3. Step 2：STAD 依時間、依交易 ID 分組、或 Business Transaction Totals 顯示。
  4. Step 3：看細節：Time、DB（Direct read／Sequential read／Update／Insert／Delete 各自筆數與時間）、Task/Memory、RFC、Bytes、Table（需參數 stat/tabrec > 0）。
STAD 的 DB 小節兩個判斷：Avg. time/row 循序讀 > 10 ms 或異動 > 50 ms 就該開 ST05；Requests ≈ Database rows 表示程式大概是一筆一筆 SELECT SINGLE，應改成陣列讀取。强晟筆記的舊標準：循序讀每筆約 10 ms、SELECT SINGLE 約 5 ms、異動約 20 ms（出自 L29 2001 版 PDF p31，當時的交易是 STAT；磁碟時代數字；HANA 上正常值低一到兩個數量級，但「相對比例」判斷法不變）。

6. 內嵌量測：GET RUN TIME 與 CL_ABAP_RUNTIME 測試框架

想比較兩種寫法誰快，最直接的方法是在程式裡量。GET RUN TIME FIELD f 第一次執行時把 f 歸零，之後每次寫入「距第一次的微秒數」（强晟筆記寫毫秒，是誤植）。SET RUN TIME CLOCK RESOLUTION HIGH|LOW 設精度，只能在第一次 GET RUN TIME 之前執行一次，否則無法攔截的短傾印。

6.40 起可改用 CL_ABAP_RUNTIME 工廠類別：create_hr_timer( )（高精度）／create_lr_timer( )（低精度）回傳 IF_ABAP_RUNTIME 物件，方法 get_runtime( )。優點是可同時開多個不同精度的計時器；缺點是每次呼叫約慢 2 µs，量極短的程式碼時要注意。

正確的測試框架（原廠練習題答案 A）：外圈重複多次取最小值／平均值以濾掉系統負載；內圈重複執行被測語句以放大太短的時間；另外量一次「空的基準方法」（呼叫開銷、初始化）再扣掉。原講義用 FORM f0/f1/f2 與 WITH HEADER LINE 內表實作，Col19 改為類別 CL_BC490_TIME_MEAS_FWK（singleton、方法 do_measurement）與 CL_BC490_TIME_MEAS_S。以下改寫成現代 ABAP：

*&---------------------------------------------------------------*
*& 微型效能測試框架：外圈抗干擾、內圈放大、扣除基準時間
*&---------------------------------------------------------------*
INTERFACE lif_variant.
  METHODS execute.
ENDINTERFACE.

CLASS lcl_meas DEFINITION FINAL.
  PUBLIC SECTION.
    TYPES: BEGIN OF ty_result,
             variant TYPE string,
             min_us  TYPE decfloat34,
             avg_us  TYPE decfloat34,
           END OF ty_result.
    CLASS-METHODS run
      IMPORTING iv_variant       TYPE string
                io_code          TYPE REF TO lif_variant
                iv_cnt_out       TYPE i DEFAULT 20
                iv_cnt_in        TYPE i DEFAULT 100
      RETURNING VALUE(rs_result) TYPE ty_result.
ENDCLASS.

CLASS lcl_meas IMPLEMENTATION.
  METHOD run.
    DATA(lo_timer) = cl_abap_runtime=>create_hr_timer( ).
    DATA lv_sum TYPE decfloat34.
    DATA lv_min TYPE i VALUE 2147483647.

    DO iv_cnt_out TIMES.                          "外圈：消除系統負載、換 WP 的干擾
      DATA(lv_t1) = lo_timer->get_runtime( ).
      DO iv_cnt_in TIMES.                         "內圈：讓 <1 µs 的語句也量得到
        io_code->execute( ).
      ENDDO.
      DATA(lv_run) = lo_timer->get_runtime( ) - lv_t1.
      lv_min = nmin( val1 = lv_min val2 = lv_run ).
      lv_sum = lv_sum + lv_run.
    ENDDO.

    rs_result = VALUE #( variant = iv_variant
                         min_us  = lv_min / iv_cnt_in
                         avg_us  = lv_sum / iv_cnt_out / iv_cnt_in ).
  ENDMETHOD.
ENDCLASS.

" 使用：先量空方法當基準，再量各變體，淨時間 = 變體 - 基準
" DATA(ls_base) = lcl_meas=>run( iv_variant = `BASE`       io_code = NEW lcl_empty( ) ).
" DATA(ls_v1)   = lcl_meas=>run( iv_variant = `READ BINARY` io_code = NEW lcl_read_bin( ) ).
" DATA(ls_v2)   = lcl_meas=>run( iv_variant = `READ HASHED` io_code = NEW lcl_read_hash( ) ).
" cl_demo_output=>display( |V1 淨時間 { ls_v1-avg_us - ls_base-avg_us } µs| ).
量測結果會受系統負載與「這次剛好從緩衝讀、下次從 DB 讀」影響，一定要取多次的最小值或平均值。要做長期、可重複的比較，ABAP Unit 搭配 ADT 的 ABAP Profiler 會比自寫框架更方便。

7. 資料庫端觀察：ST04／DBACOCKPIT 與 SQL 快取分析

每個 SAP 工作處理程序在資料庫端都有一個 1:1 的 Shadow Process。ABAP SQL 先經工作處理程序內的資料庫介面（DBIF）翻譯成原生 SQL，拆成原子操作：

操作說明
DECLARE定義游標（結果集名稱）
PREPARE解析 SQL、由優化器決定存取路徑；變數以佔位符（Oracle 的 :A0、MaxDB/DB6 的 ?）表示。SAP 游標快取讓相同結構的 SQL 可略過 PREPARE
OPEN／REOPEN代入實際值、開游標；REOPEN＝存取路徑仍在快取的相似 SQL
FETCH以 32 KB 的容器批次傳回資料（舊參數 dbs/io_buf_size = 33,792 位元組 ÷ 每筆長度 ＝ 每次 FETCH 筆數）
EXEC／REEXEC寫入類操作（取代 OPEN＋FETCH）
CLOSE關閉游標

成本式優化器（CBO）依 WHERE 條件、可用索引、欄位選擇性（統計資訊）與表大小估算每條存取路徑的成本，選最便宜的。統計資訊過期，優化器就會做錯決定——統計更新由 DBA 透過 DB13（DBA Planning Calendar）排程，Oracle 可在 DB20 查上次更新日期（報表 RSANAORA 可手動更新）。

ST04 的關鍵指標（Col19 以 Oracle 為例；7.0 SP12 起 ST04 即 DBACOCKPIT，舊畫面為 ST04OLD、DB02OLD）：

  • Buffer Quality ＝（邏輯讀－實體讀）÷ 邏輯讀：CBO 下至少 94%，平衡系統 97% 以上。但不可為了提高命中率而狂加 DB 快取，OS paging 的傷害遠大於小一點的快取。
  • Reads / User Calls：平均每條 SQL 讀幾個區塊。CBO 約 15 以下、RBO 約 20 以下為佳；大於 20:1 就急需做 SQL 快取分析。系統與 DB 要先運轉數天，快取數據才具代表性。

SQL 快取（Oracle 稱 Shared Cursor Cache；HANA 稱 SQL Plan Cache）分析——路徑：ST04 → Performance → SQL Statement Analysis → Shared Cursor Cache。判斷昂貴 SQL：

觀點門檻意義
Buffer Gets（邏輯讀，DB CPU）單一 SQL 佔全部邏輯讀 > 5%吃掉 5% 以上 DB 伺服器 CPU
Disk Reads（實體讀，I/O）Col19：> 2%；强晟筆記與 L29 2001 版（PDF p262）：> 3%兩版門檻不同，以新版 2% 較嚴格為準
Buffer Gets / Record< 5 → 存取路徑合適；> 5 → 不合適（也有文獻用 30）決定走「改程式」還是「改索引」路線
Rows Processed / Execution偏高傳回太多筆，通常是 ABAP 邏輯問題
Executions次數極多迴圈內 SELECT SINGLE，每次都佔一個 32 KB 容器與一次往返

兩種昂貴 SQL 要對症下藥：

  • Type 1：存取路徑不合適（讀很多區塊、只回很少筆）——更新統計、建立／調整／刪除索引、強制使用者輸入重要索引欄位、改寫 WHERE。
  • Type 2：存取路徑合適但仍昂貴（讀很多、也回很多）——資料庫層已無可優化，只能改 ABAP 邏輯或業務流程（最後手段）。

從快取找回 ABAP 原始碼：快取中的 Open SQL 以大寫、變數名在雙引號中識別（小寫無引號且含 $ 的是 Oracle 遞迴呼叫；大寫無引號的是 SAP 工具或 Native SQL）。按「ABAP Display」可跳到程式，但注意它指向的是「DB 重啟後第一個 PREPARE 這個結構的程式」，未必是真正的元兇。找不到時：SE11／SE12 所用處清單（可限定 SELECT、ORDER BY 等關鍵字）、檢查投影視圖（Col19 案例：KBED 的昂貴 SQL 其實來自投影視圖 KBED_AVCHK）、報表 RSSTATUS 找應用領域、SM66＋Oracle Session Monitor 抓現行犯。動態 SQL、Native SQL（EXEC SQL 區塊不進所用處索引表 WBCROSSGT）、空的 RANGES 表都會讓所用處清單找不到。

S/4HANA 上 ST04 直接進入 HANA 版 DBA Cockpit：常用的是 SQL Plan Cache（依 Total Execution Time 排序）、Expensive Statements Trace、Threads。HANA 是記憶體內欄式資料庫，「實體讀／Buffer Quality」這類 Oracle 指標不再適用，改看執行時間、記憶體與 CPU 使用；但「Type 1／Type 2 分類」與「先找元兇程式再改」的方法論不變。

8. SQL Monitor（SQLM）與 SQL Performance Tuning Worklist（SWLT）

既有工具各有盲點：ST05、SAT 只能追單一流程且開銷大；STAD、ST03N 看全系統但沒有 SQL 細節；DB 快取有細節但會被覆蓋、不同程式的相同 SQL 會被合併、也連不回業務流程。SQL Monitor 補上這個缺口：在正式機長期、低開銷（平均 < 3%）地記錄每一條 ABAP 發出的 SQL（Open SQL、Native SQL、核心發出的 SQL），並記錄其進入點（Request Entry Point）——交易、報表、RFC 模組或 URL。

彙總鍵：DB 表名、SQL 在原始碼的位置（程式／Include／行號）、流程類型與名稱（例如交易 VA01）。收集數據：執行次數、執行時間與讀寫筆數的最大／最小／平均／標準差。版本：NW 7.02 以上標準內建，更舊版本可透過 ST-PI 附加元件（SAP Note 1885926）。

正式機啟用步驟：

  1. 授權：管理者與檢視者分開，授權物件 S_ADMI_FCD，值 SQMA（管理、開關）與 SQMD（顯示）；交易 SQLM、SQLMD。
  2. RZ11 確認 abap/sqlm/main_switch = on（預設）。
  3. SQLM → SQL Monitor → Activate → All servers，設定到期日（一天／一週／兩週；預設 7 天後自動關閉）。
  4. Server State → Check／Ensure Server State 確認各伺服器狀態一致。
  5. 確認背景作業：RTM_PERIODIC_JOB（每小時把共享記憶體資料寫入 DB）、SQLM_UPDATE_DATA/SCHEDULE（每小時複寫到 SQLM 表，若跑太久可改成 4 小時）、SQLM_DEACTIVATE/SCHEDULE（到期關閉）。
原廠建議：一個量測期最多兩週（太長會被程式變更稀釋意義）；啟用後前幾小時盯住筆數，超過 200 萬筆就先關掉（例如大量含 GUID 的 URL 讓資料無法彙總）。刪除資料前記得先做 Snapshot，改善後重開一輪比較前後的 SQL Profile。

分析四招（SQLMD）：

  1. 流程觀點：Aggregation by Request，依 Executions／Total Time／Total Records 排序找前十大流程，再下鑽看該流程的 SQL Profile——經驗上前五條 SQL 就佔了八成。
  2. 系統觀點：Aggregation by Source Position、套件限定 Z*／Y*，依 Total Time 排序＝客製程式裡最貴的 SQL；看 min/max/標準差可分辨「條條都慢」還是「偶爾卡鎖」；Executions/Internal Session 很高＝巢狀 SELECT。
  3. 資料量觀點：依 Total Records 排序；max＝min＝整表筆數→大概沒有 WHERE；max 與 min 差很大→偶爾遇到空的 FOR ALL ENTRIES 驅動表或空 RANGES。
  4. 指定流程：依 Request Type／Entry Point（例如 VA01）過濾，下鑽產出調校清單。

SWLT（SQL Performance Tuning Worklist）則是把 SQLM 的執行期數據與 SCI/ATC 的靜態檢查結果（例如「迴圈內 SELECT」「SELECT * 只用少數欄位」）依原始碼位置合併，讓你一眼看到「又貴、又有已知壞味道」的語句，優先處理。這是 S/4HANA 遷移前後做客製程式效能整頓的標準組合。（SWLT 不在 BC490 任何一版教材中，依 SAP 官方文件補寫）

9. ST05 效能追蹤：錄製、彙總與逐條分析

ST05 追蹤的是「程式向工作處理程序外部要求的資源」：SQL Trace（黃色）、Table Buffer Trace（藍色）、Enqueue Trace、RFC Trace、HTTP Trace（RFC、HTTP 可追進出兩向）。它適合分析單一應用；整個系統或 DB 伺服器都慢時不是 ST05 的舞台。可以在正式機開啟，不會造成錯誤或不一致。

使用步驟：

  1. Step 0 預跑：先執行目標程式幾次，避免表緩衝、程式緩衝的載入動作混進追蹤。
  2. Step 1 錄製：Activate Trace（可 with Filter：指定使用者、交易／程式、最多 5 張包含或排除的表、工作處理程序號碼）→ 執行 → Deactivate。勾選 Stack Trace 可記錄 ABAP 呼叫堆疊（每筆多約 30 µs、檔案大 50%），追 Enqueue（都在 SAPLSENA）或框架內的 SQL 特別有用。
  3. Step 2 顯示：明細清單（Detailed Trace List）、結構相同的 SQL（Structure-Identical，Shift+F8）、值相同的 SQL（Value-Identical，Ctrl+Shift+F8）、表存取彙總、應用元件階層。
  4. Step 3 逐條分析：語句明細與變數值、DDIC 資訊（緩衝設定、索引）、Explain（執行計畫）、ABAP 原始碼、呼叫堆疊；還可把追蹤丟給 Code Inspector 檢查（連動態 SQL、ADBC 都涵蓋）。

追蹤檔參數（新版）：rstr/filename、rstr/buffer_size_kB（預設 200）、rstr/max_filesize_MB（預設 16）、rstr/max_files（預設 10，循環覆寫）。每筆記錄約 880 位元組、開銷 < 3%；錄太久會覆蓋自己的開頭。强晟筆記的舊說法是「每台應用伺服器只有一個追蹤檔、同時只能一人追蹤、預設 8KB、建議 rstr/max_diskspace = 16384000」——L29 2001 版原文（PDF p36）寫的是「預設 800 KB」，强晟筆記少抄了兩個零；原文同樣建議把 rstr/max_diskspace 設為 16,384,000（16 MB）。這套「單一追蹤檔、一次一人」的機制已被上述多檔循環取代，以新版為準。Col10（Unit 4 L3，印刷頁 p193／PDF p203）的參數與預設值和 Col19 相同，並補一句：同一台伺服器已有追蹤在錄時，無法再開另一個錄製；顯示與分析也必須在錄製的同一台伺服器上做。

10. 資料庫索引：存取策略、設計規則與選擇性分析

在 ABAP 字典建表時，鍵欄位放在最前面，啟用後資料庫自動建立主索引（唯一）；另可定義二級索引（唯一或不唯一）。資料庫以多層 B* 樹組織索引區塊：根區塊 → 分支區塊 → 葉區塊（含索引欄位值與指向表記錄的 ROWID）。索引記錄依索引欄位排序，表區塊本身不排序。

存取策略觸發條件成本特性
Index Unique Scan唯一索引的所有欄位都用「=」指定最多讀約 4 個區塊（3 索引＋1 表），回 0 或 1 筆，最快
Index Range Scan只指定索引前段欄位（例：VBAP 只給 VBELN）讀一段連續葉區塊；選擇性差時會比全表掃描還慢，且把大量區塊推到 LRU 清單頂端擠掉別人的快取
ConcatenationIN 清單、OR：同一索引用多個搜尋字串各掃一次再串接去重每個值各做一次 range/unique scan
Full Table Scan無可用索引，或要讀的比例高（約 > 5%）每個表區塊讀一次、放 LRU 尾端不擠快取；讀大比例資料時反而最有效

强晟筆記的經典反例：SELECT … FROM vbap WHERE matnr = …，VBAP 主索引是 MANDT/VBELN/POSNR，優化器卻選了主索引做 range scan——唯一可用的條件只有 MANDT = '001'，等於把整個用戶端的索引全掃一遍。這類「無選擇性的 Index Range Scan」最多要讀「表區塊數 × 索引區塊數」，比全表掃描更糟。

索引設計規則（兩份教材合併）：

  • 只有能把結果篩到約 5% 以下時，索引才有意義，否則優化器寧可全表掃描。
  • 每張表索引宜少（約 5 個以內）、每個索引欄位宜少（約 4 個以內）；索引之間不要互相包含。
  • 選擇性高、且用「=」查詢的欄位放前面。Col19 範例：10 個工廠 × 各 1,000 物料，查 WERKS = 102、MATNR 1～500：索引（WERKS, MATNR）只掃 500 筆；索引（MATNR, WERKS）要掃約 5,000 筆才篩出 500 筆。用戶端欄位放第一個不是因為它有選擇性，而是它永遠用等號。
  • 循序掃描的索引範圍盡量小（經驗值：< 1,000 列），高頻 SQL 要求更嚴。
  • 欄位語意分類：識別碼（單據號、物件號，高選擇性）、組織單位（銷售組織、公司代碼、工廠，低選擇性）、狀態欄位（查少數狀態時高選擇性，如未結訂單）、分類欄位（訂單類型，低）、日期時間（通常可用）、文字欄位（選擇性高但太寬，不要放）。
  • 自建程式查交易資料表（主資料、交易資料會線性成長）時，避免對 SAP 標準表加二級索引，改找索引表、輔助表或別的存取路徑；不要對 Basis 表（NAST、D010、D020、DD*）加二級索引；不要改 SAP 標準索引，除非 SAP Note 建議（先搜 Note，關鍵字「表名／程式名 AND performance/index」）。

選擇性分析：DB02（Space → Segments → Detailed analysis → Table columns）看每欄 distinct values；DB05 算欄位組合的分佈直方圖。Col19 的 COSS 案例：112,181 筆，索引候選（USPOB, GJAHR, WRTTP, VERSN）——USPOB 有 3,060 個值、加 GJAHR 變 5,028、加 WRTTP 只到 5,135、加 VERSN 仍是 5,135；平均每組合回 22 筆，且有 4 個組合會回 10,000～100,000 筆。結論：不建（後兩欄不增加選擇性、且有會造成無選擇性 range scan 的組合）。規則：加入某欄後 distinct 值沒增加，該欄就不該放進索引。强晟筆記的 VBAK 例（AUART/AUDAT/VKORG）：1,352,728 筆、全組合 965,325 個值，平均 1.4 筆，是好索引。

衝突分析（Interference Analysis）：新增／修改／刪除索引可能讓其他 SQL 變慢。步驟：SE12 所用處清單找出引用該表的所有 View → 修改前做「限定該表與 View」的 SQL 快取分析並下載 → DBA 修改索引並更新統計 → 重設 SQL 快取 → 約兩天後再分析一次 → 若某 SQL 每次執行的邏輯／實體讀增加超過約 30%，撤銷修改。建索引會鎖表，請在離峰時段；缺索引（DDIC 與 DB 不一致，常見於表重組後）用 DB02 的 Missing Indexes 檢查。

S/4HANA 的索引觀念要更新。HANA 是欄式儲存，每一欄本身就像一個壓縮字典索引，全欄掃描非常快；大多數情況不需要、也不建議加二級索引（每個索引都佔記憶體並拖慢寫入）。先用 SQLM／Plan Cache 證明某條高頻 SQL 真的受益，再考慮建立。索引定義與緩衝設定的操作見 5-16 章 BC430 與 1-2 章。

11. 不合適的存取路徑：改寫 WHERE、列舉優於區間、Hint 是最後手段

强晟筆記「修改 ABAP 程式碼」路線圖列出索引用不上的五大原因：缺 WHERE 條件（索引缺口）、錯用 CLIENT SPECIFIED、否定表達（NOT、<>）、使用 BETWEEN／LIKE／<／>、上述運算子再用 OR 串接。WHERE 裡條件的順序不影響存取路徑（這不是指索引欄位順序），但會影響 SQL 文字是否與快取中已有的相同——所以建議一律依 DDIC 欄位順序書寫，提高重用率。

12. 單表存取四大規則（合適存取路徑下的最佳化）

存取路徑合適但仍昂貴時，Col19 歸納四條規則（强晟筆記稱「減少傳輸的列、減少傳輸的欄、減少資料傳輸、避免不必要的 SQL」）：

  1. 讓搜尋範圍小——讓優化器找得到好的存取路徑（第 10、11 節）。
  2. 讓結果集小——WHERE 寫足、寫穩定；條件放 WHERE 不放 CHECK；只要前 n 筆就用 UP TO n ROWS。
  3. 讓傳輸量小——明列欄位不用 SELECT *；聚合在 DB 做；UPDATE 只 SET 要改的欄。
  4. 讓傳輸次數少——陣列讀取、FOR ALL ENTRIES、JOIN；大量寫入用 FROM TABLE。
*&---------------------------------------------------------------*
*& 規則 2、3 的標準寫法
*&---------------------------------------------------------------*
" 規則 2：穩定的 WHERE —— RESB 每月可成長數百 MB。
"   只給 MATNR 會隨時間越抓越多（不穩定）；加上 KZEAR（最終發料）只抓未結預留，筆數才會穩定
SELECT rsnum, rspos, matnr, werks, bdmng, bdter FROM resb
  WHERE matnr IN @s_matnr
    AND kzear = @abap_false
  INTO TABLE @DATA(lt_resb).

" 規則 2：條件寫在 WHERE。舊講義在 SELECT 迴圈內用 CHECK 過濾 → 整張 VBAK 傳過網路才丟掉
SELECT vbeln, erdat, kunnr FROM vbak
  WHERE vbeln BETWEEN @lv_low AND @lv_high
  INTO TABLE @DATA(lt_vbak).

" 規則 2：只要前 n 筆 → UP TO n ROWS（用 sy-dbcnt 自己中斷，最後一個 32 KB 容器還是整包傳了）
"   HANA 上「前 n 筆」一定要配 ORDER BY，否則每次回來的 n 筆可能不同（見第 24 節）
SELECT vbeln, erdat, kunnr FROM vbak
  WHERE vbeln IN @s_vbeln
  ORDER BY erdat DESCENDING, vbeln DESCENDING
  INTO TABLE @DATA(lt_latest)
  UP TO @p_limit ROWS.

" 規則 3：聚合在 DB 做，每張訂單只傳一筆（ABAP 端控制層處理要傳所有明細）
SELECT vbeln, MAX( kwmeng ) AS max_qty, MIN( matnr ) AS min_matnr
  FROM vbap
  WHERE vbeln IN @s_vbeln
  GROUP BY vbeln
  INTO TABLE @DATA(lt_agg).

" 規則 3：HAVING 在 DB 端過濾群組
"   ※ 教材原例寫成 SELECT MAX( matnr ) vbeln AVG( zmeng ) … GROUP BY matnr，
"     非聚合欄 vbeln 不在 GROUP BY 中，且 MAX( matnr ) 對分組欄取最大無意義 → 語法錯誤。
"     題意是「每個物料的最大單據號與平均目標數量」，應寫成：
SELECT matnr, MAX( vbeln ) AS max_vbeln, AVG( zmeng ) AS avg_zmeng
  FROM vbap
  WHERE vbeln IN @s_vbeln
  GROUP BY matnr
  HAVING AVG( zmeng ) >= @p_min AND AVG( zmeng ) <= @p_max
  INTO TABLE @DATA(lt_stat).
聚合函數的注意事項：DB 與 ABAP 的捨入規則不同（F 轉 I 尤其明顯）；DB 認得 NULL、ABAP 只有初始值，AVG 遇到 NULL 的結果會與在 ABAP 算的不同；AVG 目標用 F 型別（inline 宣告預設即是）、SUM 目標長度要大於來源以免溢位；含聚合、DISTINCT、GROUP BY 的 SQL 一律繞過表緩衝。HAVING 本身會增加 DB 負荷，能寫在 WHERE 的條件不要放 HAVING。INTO CORRESPONDING FIELDS 比依位置 INTO 多一點欄名比對成本（很小），目標結構與欄位清單一致時直接 INTO TABLE。

13. FOR ALL ENTRIES、RANGES 表與內表當資料來源

FOR ALL ENTRIES（FAE）是為了把 SELECT 從迴圈中拿出來而生的歷史產物（當年並非所有 SAP 支援的資料庫都能 JOIN）。它本質上是「內表與 DB 表之間的 JOIN，但在 ABAP 端完成」：DBIF 依參數把驅動表拆成多條原生 SQL（6.10 起多用 IN 清單），在 DBIF 端緩衝結果、去除重複列後再交給程式。

  • rsdb/max_blocking_factor、rsdb/min_blocking_factor：OR 串接的條件數（Oracle 約 5～15，强晟筆記記為 15；MS SQL 約 50）。
  • rsdb/max_in_blocking_factor、rsdb/min_in_blocking_factor：IN 清單的值數。7.00 起 RZ11 不顯示部分 DB 參數預設值（Note 1296224；另見 48230、634263、881083）。

四大陷阱（完整說明見 2-2 章第 17 節）：

  1. 驅動表為空＝整張表全抓，而且與驅動表無關的 WHERE 條件也不會被評估。對照：WHERE key1 IN rangetab AND f1 = X 在 rangetab 為空時只會「不限制 key1」，仍會套用 f1 = X。
  2. 驅動表要先去重，否則同樣的資料重讀好幾次。
  3. 結果會被去重：SELECT 欄位若沒包含完整鍵，業務上不同的列可能被當重複刪掉（例如數量相同的兩筆明細）。
  4. 不要與大 RANGES 表合用：產生大量不同 SQL（毒害游標快取）、WHERE 極複雜、甚至超過語句長度上限（Oracle 32 位元版 32 KB）而 DUMP。RANGES 建議固定上限約 15～20 列。
*&---------------------------------------------------------------*
*& FAE 的安全寫法，以及 7.52 起「內表當資料來源」的替代方案
*&---------------------------------------------------------------*
" ① 驅動表去重（GROUP BY 一次到位），並用 SORTED UNIQUE 保證不重複
DATA lt_kunnr TYPE SORTED TABLE OF kunnr WITH UNIQUE KEY table_line.
lt_kunnr = VALUE #( FOR GROUPS g OF ls_v IN lt_vbak GROUP BY ls_v-kunnr ( g ) ).

" ② ★ 空表檢查：少了這行，驅動表空的那天就是把整張 KNA1 讀進來
IF lt_kunnr IS NOT INITIAL.
  SELECT kunnr, name1, adrnr FROM kna1
    FOR ALL ENTRIES IN @lt_kunnr
    WHERE kunnr = @lt_kunnr-table_line
    INTO TABLE @DATA(lt_kna1).
ENDIF.

" ③ 7.52 起：內表可當資料來源直接與 DB 表 JOIN（HANA 上內表會整包傳到 DB 端）
"    不必自己擔心空表、也不會有 FAE 的隱性去重
SELECT DISTINCT k~kunnr, k~name1, k~adrnr
  FROM @lt_vbak AS v
  INNER JOIN kna1 AS k ON k~kunnr = v~kunnr
  INTO TABLE @DATA(lt_kna1_join).

" ④ 結果要依鍵讀取：FAE 的結果沒有順序，放進 SORTED/HASHED 表再用
DATA lt_kna1_h TYPE HASHED TABLE OF kna1 WITH UNIQUE KEY kunnr.
何時 FAE 還是好選擇：驅動表不大、WHERE 指向一小塊區域、有合適索引、要讀的表是有緩衝的（JOIN 一律繞過表緩衝，FAE 與逐筆 SELECT 則可用緩衝）。驅動表很大或要讀大量資料時，JOIN、CDS View 或內表資料來源通常更好。在 HANA 上，新版核心會以 FDA（Fast Data Access）把 FAE 驅動表整包送到 DB 端處理，但「空表陷阱」依舊存在。

14. 多表存取：巢狀 SELECT、JOIN、View、子查詢與邏輯資料庫

ABAP 實作「JOIN 邏輯」的方式：巢狀 SELECT、FOR ALL ENTRIES、資料庫 View、ABAP JOIN、子查詢、顯式游標、邏輯資料庫。最具擴充性、通常也最快的是在資料庫層做 JOIN（View、ABAP JOIN、子查詢），因為存取順序由優化器依統計資訊動態決定；巢狀 SELECT 與 FAE 的順序則被寫死在程式裡——使用者輸入不同（例如這次只給客戶、下次只給單號）時，寫死的順序可能正好相反。

巢狀 SELECT 的三大問題：① 傳輸開銷大——外層每一筆都讓內層 REOPEN 一次，每次只回一筆，32 KB 容器幾乎是空的；② 相同 SQL 重複執行——外層非鍵欄位（如訂單上的客戶）對應內層鍵欄位時，同一客戶被讀很多次；③ 存取順序寫死。

資料庫層 JOIN 的兩種執行策略：Nested Loop（先選外表——WHERE 估算回傳最少的那張，再依 JOIN 條件逐筆找內表）與 Sort Merge Join（各表先依 WHERE 取結果集、依 JOIN 條件排序再合併；兩表都有選擇性 WHERE、或 JOIN 條件本身沒有選擇性時較有利）。JOIN 條件欄位至少在內表要有索引。

*&---------------------------------------------------------------*
*& 巢狀 SELECT → 資料庫層 JOIN
*&   原講義：外層 SELECT vbak 迴圈內再 SELECT SINGLE kna1（已不示範）
*&---------------------------------------------------------------*
" ✓ INNER JOIN：只留兩邊都有的
SELECT v~vbeln, v~kunnr, k~name1, k~adrnr
  FROM vbak AS v
  INNER JOIN kna1 AS k ON k~kunnr = v~kunnr
  WHERE v~vbeln IN @s_vbeln
  INTO TABLE @DATA(lt_inner).

" ✓ LEFT OUTER JOIN：沒有客戶主檔的訂單也要保留（右表欄位回初始值）
SELECT v~vbeln, v~kunnr, k~name1
  FROM vbak AS v
  LEFT OUTER JOIN kna1 AS k ON k~kunnr = v~kunnr
  WHERE v~vbeln IN @s_vbeln
  INTO TABLE @DATA(lt_outer).

" ✓ 子查詢：只要「在這批訂單中出現過的客戶」
SELECT kunnr, adrnr FROM kna1
  WHERE kunnr IN ( SELECT DISTINCT kunnr FROM vbak WHERE vbeln IN @s_vbeln )
  INTO TABLE @DATA(lt_cust).

" ✓ 需要依結果做 EXISTS 判斷時，EXISTS 通常比 IN 子查詢更直覺
SELECT kunnr, name1 FROM kna1 AS k
  WHERE EXISTS ( SELECT vbeln FROM vbak WHERE kunnr = k~kunnr AND erdat >= @lv_from )
  INTO TABLE @DATA(lt_active_cust).
教材錯誤修正：强晟筆記 p83 的 JOIN 例 ON vbuk~vbeln = vbuk~vbeln 是自己等於自己（應為 vbak~vbeln = vbuk~vbeln）；p183 的 WHERE t1~vben 為 vbeln 之誤。另外 VBUK／VBUP 在 S/4HANA 已廢除，狀態欄位併入 VBAK／VBAP／LIKP 等表頭與明細，舊程式 JOIN VBUK 的寫法要改。
  • 資料庫 View（SE11）：只能做 INNER JOIN；不能自建索引（用基礎表的索引）；可重用、對 SQL 快取友善；預設繞過表緩衝，但 4.0 起可對 View 本身設定緩衝。
  • ABAP JOIN：可做 INNER 與 LEFT OUTER；欄位一律加表別名前綴；別串太多表。舊限制（右邊必須是表或 View、ON 只能用 AND、每個比較都要含右表欄位、LEFT OUTER JOIN 的 WHERE 不可用右表欄位）在 7.40 SP05 之後多數已放寬。
  • 邏輯資料庫（LDB）：節點階層決定讀取順序，GET 事件就像巢狀迴圈；只需低層資料時仍會讀經過的所有上層節點；可用 GET node FIELDS f1 f2 限縮欄位。
邏輯資料庫在 S/4HANA 屬過時技術（强晟筆記當年就註明「已屬過時技術，代碼略」），新程式一律自己寫 SQL 或使用 CDS View；LDB 的歷史與維護見 5-6 章 BC405。多表查詢的語法細節見 2-2 章第 15 節。

15. Pool 表與 Cluster 表（S/4HANA 已退場）

强晟筆記（Col19 已刪除此段）說明：除了透明表，ABAP 字典可把多張邏輯表放進一張實體表——Pool 表（多張小表放進表池，如 KAPOL；鍵為 TABNAME＋VARKEY，非鍵欄位壓縮存於 VARDATA，所以池表的鍵欄位必須是 C 型）與 Cluster 表（功能相關的資料依共同的簇鍵放一起，如 BSEG 放在表簇 RFBLG；欄位 PAGENO、TIMESTMP、PAGELG、VARDATA）。

  • 優點：壓縮省空間與網路；表數量少、管理容易；Cluster 表一次讀出相依資料。
  • 缺點：非鍵欄位不能建索引；不能用 View、ABAP JOIN、Native SQL；只有鍵欄位（Cluster 是簇鍵）的條件會送到 DB，ORDER BY／GROUP BY 非鍵欄位也不會送。
  • 經典反例：SELECT … FROM bseg WHERE kunnr = …——KUNNR 壓在 VARDATA 裡，DB 只收到 WHERE MANDT，整個用戶端的 RFBLG 全讀回來在 DBIF 過濾。當年的解法是改讀二級索引表 BSID（應收未清項）。
  • 池表 AA005 例：WHERE 沒從最左鍵連續指定，VARKEY 只能用 'AA005001%' 前綴 LIKE；解法依序是補條件 → 完整緩衝該表 → 把表移出表池轉透明表再建索引（須先詢問 SAP）。
" S/4HANA：BSEG 已是透明表（不再有 RFBLG 簇），但仍是超大表
" 查客戶未清項目：BSID 在 S/4HANA 是相容 View（名稱保留，底層讀 BSEG/ACDOCA），
" 舊程式不必改名；新開發建議直接用 ACDOCA 或 SAP 發佈的 CDS View
SELECT bukrs, belnr, gjahr, buzei, zfbdt, dmbtr
  FROM bsid
  WHERE bukrs = @lv_bukrs
    AND kunnr = @lv_kunnr
  INTO TABLE @DATA(lt_open_items).

16. SAP 表緩衝：類型、同步、繞過條件與 ST10

表緩衝把表內容放在每台應用伺服器的共享記憶體，存取比資料庫快 10～100 倍（强晟筆記：緩衝約 0.2～6 ms 對上 DB 8～600 ms）。緩衝資料依主鍵排序存放，只能用主鍵存取，不能用二級索引。三種類型可統一理解為「有 n 個鍵欄位的通用緩衝」：

類型n載入／失效單位讀得到緩衝的條件
全緩衝（Full）0整張表任何只含主鍵條件的讀取
通用緩衝（Generic）0 < n < 全部鍵一個通用區（前 n 個鍵欄位的值組合）通用區所有欄位都要用「=」指定
單筆緩衝（Single record）全部鍵一筆完整主鍵（7.02 起不寫 SINGLE、用陣列讀取也會走緩衝）

跨伺服器同步：① 在本機 DB 修改，同時更新（工作區模式）或失效（集合模式）本機緩衝；② DBIF 寫一筆同步記錄到表 DDLOG；③ 其他伺服器定期（約每 1～2 分鐘）讀 DDLOG，把受影響的緩衝失效，下次存取再重載。兩次同步之間，其他伺服器可能讀到舊資料。失效後有「pending period」：接下來數次（目前 5 次）存取直接走 DB，第 6 次才重載，避免載入／失效反覆震盪。

失效範圍：全緩衝→整表；通用緩衝在工作區模式（單筆 UPDATE/INSERT/MODIFY/DELETE dbtab FROM wa）→同一通用區，集合模式（FROM TABLE、UPDATE…SET…WHERE、DELETE…WHERE）→整表；單筆緩衝在工作區模式→那一筆，集合模式→整表。

一定繞過緩衝的語句：BYPASSING BUFFER、SELECT … FOR UPDATE、DISTINCT、聚合函數（COUNT/SUM/MAX/MIN/AVG）、IS NULL、ORDER BY 非主鍵（ORDER BY PRIMARY KEY 可以）、GROUP BY／HAVING、子查詢、JOIN 與多表 View、Native SQL、WHERE 中兩欄互相比較；單筆緩衝表則是沒給完整主鍵的讀取；通用緩衝表則是沒用「=」填滿通用區（例如加了 CLIENT SPECIFIED 卻沒給 MANDT）。

" ✓ 單筆緩衝表 T100：完整主鍵 → 讀應用伺服器緩衝
SELECT SINGLE text FROM t100
  WHERE sprsl = @sy-langu
    AND arbgb = 'BC490'
    AND msgnr = '050'
  INTO @DATA(lv_text).
" ※ 强晟筆記 p217 寫成 SELECT SINGLE * … INTO TABLE，SINGLE 不能搭 INTO TABLE，為筆誤。

" ✓ 通用緩衝表 TCURR（通用區＝MANDT）：不寫 CLIENT SPECIFIED，DBIF 自動補 MANDT → 讀緩衝

" ✓ 需要保證最新值（例如取得鎖之後重讀）→ 明確繞過緩衝，並讓 Code Inspector 看得出是刻意的

該不該緩衝：

  • 技術面：表要小（經驗上 < 1 MB 最理想，10 MB 以上要特別評估共享記憶體）；讀多寫少（異動 < 讀取的 1%）；能容忍短暫不一致；存取以主鍵為主。緩衝前先與 Basis 確認共享記憶體夠大，否則緩衝會 swap。
  • 語意面：交易資料（VBAK、LIKP、MKPF、RESB）不緩衝；主資料（MARA、KNA1、LFA1）通常也不緩衝（會長到上百 MB、常用二級索引路徑存取）；客製化設定表（T000、T001、T001W、TVKO）最適合緩衝。改 SAP 標準表的緩衝設定要有 SAP Note 依據並需修改金鑰。

分析工具：ST02（命中率應接近 100%、Swaps 應避免；只看目前登入的那台伺服器）、ST10（Table Call Statistics）、ST05 Buffer Trace、AL12（SAP 支援用的專家工具，無文件）、SE17、DB05、SAT、SCI。ST10 的判讀：依 DB activity 的 Rows affected 排序，緩衝表出現在前面就代表太大常被失效或存取方式與緩衝類型不符；依 Invalidations 排序，小表（< 1 MB）失效次數對讀取次數比例不應超過約 1%，1～10 MB 的表約 0.1%；未緩衝表中讀多寫少的客製表與條件表應考慮緩衝。緩衝狀態：valid、invalid、pending、loadable、loading、absent/displaced、multiple、error（常見原因是表太大放不進緩衝）。

緩衝設定本身在 SE11 技術設定中維護（見 1-2 章、5-16 章）。HANA 雖然很快，應用伺服器緩衝仍比跨網路到 DB 快得多，設定表的緩衝在 S/4HANA 依然重要。

17. 資料物件緩衝：緩衝模組、Shared Memory／Buffer、Shared Objects

表緩衝只適用少數表；主資料、交易資料太大或變動太頻繁，只能在程式裡自己緩衝——Col19 稱為緩衝模組（Buffer Module），也叫讀取模組、Data Provider、交易緩衝。SAP 標準大量使用（例如函數群組 V45I 的單筆讀取模組、STATUS_CHECK）。一個好的緩衝模組要有：

  • Not-found 緩衝：查不到的鍵也要記住，否則同一個不存在的鍵會一直打 DB。
  • 可繞過：在 Enqueue 保護下需要 committed read 時要能強制重讀。
  • 顯式 refresh 與大小上限（超過上限時在未命中的那次才清空）。
  • 緩衝內表用 HASHED 或 SORTED，不用標準表。
  • 資料只用一次就不要緩衝；已在表緩衝的表不要再緩衝一次（記憶體花兩份、效益可忽略）。

Shared Objects 的適用情境只有兩種：共享緩衝（型錄：一天最多改一次、多人同時讀）與獨占緩衝（購物車：一人寫、之後另一人讀）。頻繁寫入或大量並行讀寫不適合（鎖機制會拒絕大部分存取）。經驗值：Area 約 200～500 KB 才划算，重用率很高時可低到約 50 KB；首次 attach_for_read 約 260～280 µs、之後約 80～90 µs，而緩衝表的 SELECT SINGLE 只要 20～50 µs——簡單設定資料用表緩衝，複雜物件結構才用 Shared Objects。版本管理與程式細節見 5-3 章 BC402。

18. 內表：型別選擇與存取成本

內表屬性由行型別、鍵、唯一性、表類型完整決定。三種表類型（基礎語法見 2-2 章）：

操作（n 筆，處理 m 筆）STANDARDSORTEDHASHED
依鍵 READ／MODIFY／DELETE 單筆O(n)（BINARY SEARCH 後 O(log n)）O(log n)O(1)
依鍵 INSERTO(1)O(log n)O(1)
COLLECTO(1)～O(n)（內建暫時雜湊，被 DELETE/INSERT/SORT 破壞後退化為線性）O(log n)O(1)
LOOP … WHERE（鍵左側連續）O(n)O(m + log n)O(n)
索引存取 READ INDEXO(1)O(1)不允許
SORTO(n log n)不必要O(n log n)

選型路線圖：幾乎都用完整主鍵做單筆存取 → HASHED；多半用主鍵、且能從最左鍵連續指定做單筆或部分循序處理 → SORTED；主要用索引存取、或同一張表要用多種不同欄位組合存取 → STANDARD（可依需要 SORT 再 BINARY SEARCH，或加二級鍵）。雜湊表單筆鍵存取比索引存取慢約 2.5～3 倍，但與筆數無關；雜湊表筆數上限受作業系統限制。

*&---------------------------------------------------------------*
*& 建表與填表：陣列讀取、批次附加、COLLECT vs DB 聚合
*&---------------------------------------------------------------*
TYPES: BEGIN OF ty_item,
         vbeln  TYPE vbeln_va,
         posnr  TYPE posnr_va,
         matnr  TYPE matnr,
         kwmeng TYPE kwmeng,
       END OF ty_item.

" 陣列讀取（ARRAY FETCH）直接進 SORTED 表：系統自動依鍵排序插入
" ※ 內表鍵只取 DB 主鍵的一部分時不可宣告 UNIQUE，否則重複列會 DUMP
DATA lt_item TYPE SORTED TABLE OF ty_item WITH UNIQUE KEY vbeln posnr
               WITH NON-UNIQUE SORTED KEY by_matnr COMPONENTS matnr.
SELECT vbeln, posnr, matnr, kwmeng FROM vbap
  WHERE vbeln IN @s_vbeln
  INTO TABLE @lt_item.

" 內表對內表：批次附加，不要 LOOP + APPEND
APPEND LINES OF lt_item_extra TO lt_item_std.
INSERT LINES OF lt_item_extra FROM 1 TO 100 INTO TABLE lt_item.

" 累計：COLLECT 的非鍵欄位必須全為數值；HASHED 表成本固定
TYPES: BEGIN OF ty_sum,
         ernam TYPE ernam,
         waerk TYPE waerk,
         netwr TYPE netwr_ak,
       END OF ty_sum.
DATA lt_sum TYPE HASHED TABLE OF ty_sum WITH UNIQUE KEY ernam waerk.
LOOP AT lt_vbak ASSIGNING FIELD-SYMBOL(<ls_vbak>).
  DATA(ls_sum) = VALUE ty_sum( ernam = <ls_vbak>-ernam
                               waerk = <ls_vbak>-waerk
                               netwr = <ls_vbak>-netwr ).
  COLLECT ls_sum INTO lt_sum.
ENDLOOP.

" 更好的做法：資料本來就來自 DB 時，直接在 DB 聚合（第 12 節規則 3）
SELECT ernam, waerk, SUM( netwr ) AS netwr FROM vbak
  WHERE erdat IN @s_erdat
  GROUP BY ernam, waerk
  INTO TABLE @DATA(lt_sum_db).
陣列讀取不能用於深結構（行內含內表）的目標；唯一內表的建法：先以非唯一表陣列讀取、SORT 後 DELETE ADJACENT DUPLICATES（加 COMPARING 指定比較欄位，且必須與 SORT 欄位一致），比 SELECT 迴圈裡逐筆檢查是否存在快得多。資料庫表的全部鍵都要出現在內表但又不當鍵時，不能用 SELECT DISTINCT 取代。

19. 巢狀操作、二級鍵與 ASSIGNING

巢狀操作（Nested Operations）比「巢狀迴圈」更精確：在 DO 迴圈裡用 READ TABLE INDEX 模擬 LOOP，或在 LOOP 裡對標準表做非最佳化的 READ（它內部就是一個全表迴圈），都是巢狀操作。兩層都是 O(n) 時，總成本是 O(n²)——Col19 的量測中，二次方解法比其他解法慢約 100 倍。注意：這與巢狀 SELECT 是兩回事（一個是 CPU、一個是 DB）。

*&---------------------------------------------------------------*
*& 表頭 × 明細：三種不會變成 O(n²) 的寫法
*&---------------------------------------------------------------*
" ✗ lt_item_std 是標準表：外層每一圈，內層 LOOP WHERE 都全表掃描一次

" ✓ 解法 A：內層用 SORTED 表，WHERE 從最左鍵連續指定 → O(log n + m)
LOOP AT lt_head ASSIGNING FIELD-SYMBOL(<ls_head>).
  LOOP AT lt_item ASSIGNING FIELD-SYMBOL(<ls_item>) WHERE vbeln = <ls_head>-vbeln.
    " …
  ENDLOOP.
ENDLOOP.

" ✓ 解法 B：平行游標（兩表都依 VBELN 排序、明細必須都有對應表頭），內層從上次停下的位置繼續
DATA lv_idx TYPE i VALUE 1.
LOOP AT lt_head ASSIGNING <ls_head>.
  LOOP AT lt_item_std ASSIGNING FIELD-SYMBOL(<ls_it>) FROM lv_idx.
    IF <ls_it>-vbeln <> <ls_head>-vbeln.
      lv_idx = sy-tabix.
      EXIT.
    ENDIF.
    " … 處理同一張訂單的明細
  ENDLOOP.
ENDLOOP.

" ✓ 解法 C：二級鍵——同一張表還要用物料找明細；必須明寫 USING KEY（沒有優化器幫你選）
LOOP AT lt_item ASSIGNING <ls_item> USING KEY by_matnr WHERE matnr = lv_matnr.
  " …
ENDLOOP.

" 只判斷是否存在：line_exists / TRANSPORTING NO FIELDS，不搬任何資料
IF line_exists( lt_item[ KEY by_matnr matnr = lv_matnr ] ).
  " …
ENDIF.

" 直接改表體：ASSIGNING 後賦值即可，不要再 MODIFY
LOOP AT lt_item ASSIGNING <ls_item> WHERE vbeln = lv_vbeln.
  <ls_item>-kwmeng = <ls_item>-kwmeng * 2.
ENDLOOP.

二級鍵（Secondary Keys，7.0 EhP2 起）：最多 15 個；SORTED 或 HASHED；可在程式或 SE11 表類型中定義；READ／LOOP／DELETE／MODIFY 可用，INSERT／APPEND／COLLECT 不能指定。非唯一二級鍵採延遲更新：第一次使用時才建立、之後再用到時才更新，所以第一次 READ 在 SAT 裡看起來特別貴；唯一二級鍵則是即時更新（它是約束）。使用 USING KEY 時 sy-tabix 是「該鍵的順序」，之後的索引操作也要改成 USING KEY，建議把索引存下來並以 idx／idx_k2 命名區分。DELETE … USING KEY k2 對標準表仍有 O(n) 成分（要找主索引位置）。

建議（Col19）：新開發先用有主鍵的 SORTED/HASHED 表，需要第二種最佳化存取時再加二級鍵；二級鍵優先選 SORTED（HASHED 要求唯一且立即更新）；標準表只用於很小的表或無法改表型的舊程式。ASSIGNING 在以下情況一定用：行內含內表（深結構）、工作區 > 1 KB、要修改內容；在 LOOP 中即使工作區較小也划算（開銷只有一次）；只有「工作區極小、單筆 READ 在大型巢狀迴圈中執行極多次」時 INTO wa 才較快——所以强晟筆記「超過 10 行的表，ASSIGNING 一律比 INTO 快，無論表多寬」的說法對 LOOP 大致成立，對單筆 READ 則不盡然。

其他程式風格要點：任何對標準表的操作（不只 READ、LOOP，還有 INSERT、MODIFY、DELETE）都要最佳化，所以用 SORTED 表比較強健；SORT 一定明寫排序欄位（預設鍵可能改變）；DELETE ADJACENT DUPLICATES 與 SORT 用相同欄位；BINARY SEARCH 前的排序順序必須正確；SORT 次數越少越好（SORT … STABLE 可保留相同鍵的原順序）；不要把大型巢狀操作拆進很細的模組化單元（呼叫開銷會大於內表操作本身）；不要用表頭行（header line）。巢狀迴圈的更多寫法見 2-2 章第 12 節。

20. SAT（原 SE30）ABAP Trace 與 ST12

SAT 分析的是 ABAP 語句本身的執行時間（可選記憶體），用來找：不必要的處理區塊呼叫、昂貴的內表操作、長時間的模組化單元、巢狀迴圈。它不是整個系統都慢時的工具。追蹤開啟時對被測程式影響明顯，追越少事件、越短時間越好；有些昂貴動作追不到（指派標準表給排序表時的隱式 SORT、二級鍵的延遲建立、XSLT/Simple Transformation），其時間會算進呼叫者的淨時間。

使用步驟：

  1. Step 0：建立／選擇量測變式（名為 DEFAULT 的變式會自動套用），先預跑幾次。
  2. 變式設定：
    • 彙總（Aggregation）：None（每個事件一筆，資訊完整、有呼叫階層）或 Per Call Position（同一呼叫位置合併。例：迴圈 1,000 次呼叫同一方法，不彙總是 1,002 筆、彙總後 3 筆；檔案小、快，但沒有呼叫階層）。
    • 事件類型：處理區塊、畫面、內表（會讓追蹤暴增，需要時才開）、產生與載入、DB 存取、資料傳輸（EXPORT/IMPORT）、其他。
    • 程式元件限制：不限、依 Hotspot 定義（表 HOTSPOT_DEF）、指定最多 10 個處理區塊。
    • 選項：量測 RFC 與更新任務（在對方伺服器以 SAPSYS 記錄）、顯式開關（OK code 輸入 /ron、/roff；或語句 SET RUN TIME ANALYZER ON/OFF；舊版 TCODE RON／ROFF）、量測記憶體（需參數 rstr/accept_remote_trace）。
  3. Step 1 錄製：三種方式——In Dialog（直接執行交易／程式／函數）、In Parallel Session（對正在跑的工作處理程序開追蹤，適合抓長時間執行中的程式）、For User/Service（排程：符合使用者、用戶端、流程類型 DIA/UPD/BGD/RFC/HTTP、物件等條件時自動開始；適合瀏覽器應用與背景作業）。勾 Determine Names of Internal Tables 才會顯示內表真名而不是 IT_n。
  4. Step 2 評估：Hit List（依呼叫位置彙總的毛／淨時間）、DB Tables、Profile（依內部／外部處理區塊、資料存取或套件、元件分組）、Processing Blocks（可一鍵展開 Critical Processing Blocks，預設門檻 5%）、Call Hierarchy、Times；另可比較兩次追蹤。Expert Mode 的 % Internal 指出時間花在 SAP 內部還是外部（DB、RFC），決定先改哪邊。

毛時間（Gross）與淨時間（Net）：毛時間＝該事件的全部時間；淨時間＝毛時間扣掉其下呼叫的子單元與個別語句。兩者相同時只顯示一個。路線圖（强晟筆記）：先用全彙總、無過濾量一次 → 找出佔總時間 > 10% 的程式段或語句 → 限縮到這些段、改成「無彙總或每呼叫位置」再量 → 若是內表問題就走內表路線圖，否則用除錯器或內嵌量測細查（由上而下）。

舊版 SE30 的說法（强晟筆記）：結果檔存於應用伺服器最多 8 天（新版 SAT 預設 50 天後刪除）、參數 abap/atrasizequota（保留空間）與 abap/atrapath（存放路徑）、全集合／每呼叫位置集合／無集合三種集合方式、命中清單、組命中清單、表命中清單、內表命中清單、呼叫階層。SE30 已由 SAT 取代，功能對應。

ST12（Single Transaction Analysis）來自 ST-A/PI 附加元件，把 ABAP Trace 與 ST05 SQL Trace 一次錄製、一個畫面分析，並能直接帶出 SQL 的 Explain 與呼叫位置，SAP 支援工程師做效能服務時幾乎都用它。系統有裝 ST-A/PI 就可以用；分析流程與 SAT＋ST05 相同。ADT 中另有 ABAP Profiler（本質就是 SAT）與 SQL Trace 視圖（見 5-5 章）。（ST12 不在 BC490 任何一版教材中——2001、Col10、Col19 都只教 SE30／SAT＋ST05——本段依 SAP 官方文件補寫）

L29 版本補充：

  • 2001 版 SE30（PDF p48–57）：入口是「System → Utilities → Runtime analysis → Execute」；三個分頁 Program parts／Statements／Duration & type，可設最大檔案大小（預設 1,000 KB）與最長量測時間（預設 1,800 秒）。彙總分三級：Full aggregation（每個程式段或語句只留 1 筆）、Per calling position、None；原廠範例 DO 1000 TIMES 呼叫程式段 X：不彙總 1,001 筆、全彙總 1 筆、依呼叫位置 2 筆。SAT 已取消「全彙總」，只剩 None 與 Per Call Position（Col10 p594 的例子變成 1,002 筆對 3 筆），所以强晟筆記路線圖的「先全彙總量一次」在 SAT 上改用 Per Call Position＋Hit List 代替。
  • 2001 版的評估畫面是 Hit list、Group hit list、Table hit list、內表 Hit list、Call hierarchy 五種；開頭有一張 ABAP／DB／R/3 三段的長條圖，這就是 SAT「Profile」頁與 Expert Mode 的 % Internal 的前身。
  • Col10 Unit 8 L4 的追蹤比較（印刷頁 p618–622／PDF p628–632）：兩次追蹤的 Hit List 比較，Code 欄 T1_＝只在第一次、T_2＝只在第二次、T12＝兩次都有（有意義的比較要以 T12 為主）；預設依 Net 2/1 比值遞減排序，可依事件類別（Events）或呼叫／被呼叫程式（Programs）濃縮，Swap 按鈕可對調兩次追蹤。改寫前後各錄一次再比較，是證明「改善有效」最直接的方法。

21. RFC 與 GUI Roundtrip 的效能

同步 RFC（sRFC）期間，呼叫端工作處理程序會 Roll-out 等待，這段時間記為 Roll-wait time；在對方系統花的時間（含建立連線）稱 RFC+CPIC time。除了 sRFC，COMMIT WORK（不結束對話步驟時）、同步更新、WAIT UP TO n SECONDS、COMMIT WORK AND WAIT 也會造成 Roll-wait。非同步 RFC（STARTING NEW TASK）不等待，沒有 Roll-wait。RFC 型態與語法見 4-1 章、5-12 章 BC415。

GUI Roundtrip：4.6A 起的 GUI Controls（ALV Grid、Textedit、HTML control、下拉清單）在一個對話步驟內可能與前端做多次同步 RFC（工作處理程序是 RFC client、SAP GUI 是 server），全部 Roundtrip 的時間累計為 GUI time（包含在 Roll-wait 內）。判讀：

  • ST05 的 RFC Trace 中出現 OLE_FLUSH_CALL＝一次到前端的 Roundtrip。
  • 每個對話步驟平均應只有 1 次 Roundtrip（一般畫面 2 次可接受）；每次最多傳 32 KB；複雜畫面每步約 2～10 KB 為宜。
  • 頻寬加大無助於 Roundtrip 效能（延遲與防火牆才是關鍵）；SAP GUI 狀態列可顯示 Roundtrip 與 Flush 次數。
  • 寫 Control 程式時，把多個方法呼叫累積後一次 cl_gui_cfw=>flush( )，不要每個呼叫都 flush（見 5-10 章 BC412、3-2 章）。

aRFC 平行處理會大量消耗對話工作處理程序，必須用 RZ12 定義 RFC 伺服器群組並設定配額（Quota）——多個配額參數同時檢查，以最嚴格者為準（SAP Note 74141）。同步 RFC 的連線重試次數在 SM59 設定。

22. 系統層被動分析：工作量、快照與資料庫鎖

强晟筆記第五單元「R/3 系統分析」是在正式機被動執行的分析（系統需已上線一段時間、在典型使用者活動時段進行），目的是找出影響效能的關鍵對象，把分析所需資訊交給開發者。需要蒐集的資訊：

  • 資料庫問題：SQL 文字（尤其 WHERE）、DDIC 資訊（表／View 名、技術設定、索引）、優化器存取策略（Explain）、觸發 SQL 的 ABAP 程式碼。
  • CPU 問題：關鍵程式段或語句；內表問題則要表名與相關程式碼。

① 工作量分析（ST03N，舊 ST03）：選伺服器與期間，看 Dialog steps、平均回應時間、平均 CPU 時間、平均 DB 時間；交易概要依總回應時間排序，找「佔總回應時間最大宗」的對象。對話交易與背景作業分開看——白天與線上使用者同時跑的長背景報表特別傷。路線圖：CPU > 40% → SAT；DB > 40% → ST05。若每步平均 DB 回應時間 > 600 ms，多半是 Basis 或 DB 本身的問題，SQL 追蹤結果此時不可信，應先請 Basis／DBA 處理。

② SQL 快取分析（ST04）：見第 7 節。

③ 快照分析：SM50（本機）／SM66（全系統）連續重新整理數次，仍佔著同一個對話工作處理程序的程式就是嫌疑犯；看「動作」欄（直接讀取、循序讀取、插入、更新、刪除、提交）與「表」欄。若是 DB 等待，進 ST04 的 Session Monitor（依 OS 程序 ID 對應 SQL）看正在執行的 SQL 並 Explain；若是鎖等待，進 DB01（排他鎖等待）找出持鎖者，請他釋放或必要時刪除（被回滾的交易要重做）。

資料庫鎖通常在對話步驟結束的隱式 DB Commit 時釋放；要跨多個對話步驟鎖定資料請用 SAP 鎖（Enqueue，見 5-11 章 BC414）。原則：DB 鎖越晚取得越好，取得後避免長時間的 SQL 或內表處理。

23. HANA 時代：Code Pushdown、CDS View 與 AMDP

BC490 的傳統黃金規則是「資料庫是瓶頸，能在 ABAP 做的就不要丟給 DB」（强晟筆記：「由於資料庫不可擴充，應盡可能在 ABAP 中排序」）。在 HANA 上這條規則部分反轉：HANA 是記憶體內、欄式、可平行運算的資料庫，把資料密集的運算下推到資料庫（Code-to-Data／Code Pushdown），只把結果傳回應用伺服器，通常快得多。調整後的原則：

傳統規則（BC490）HANA 時代的調整
結果集小、傳輸量小、次數少完全不變，而且更重要（網路往返成本相對變得更顯著）
SELECT * 只是多傳一點欄式儲存下每多一欄就多一次欄重組，SELECT * 代價更高
在 ABAP 排序、聚合，減輕 DB聚合、JOIN、計算、排序盡量在 DB 做（ABAP SQL 運算式、CDS、AMDP）
建二級索引加速多數不需要；先證明再建
FAE 取代巢狀 SELECTJOIN、CDS View、內表資料來源（7.52）通常更好
SQL 回傳順序「看起來」固定沒有 ORDER BY 就沒有順序（第 24 節）

Code Pushdown 的三個層次（由易到難，能用上一層就不要用下一層）：

  1. ABAP SQL 強化（7.40 SP05 起）：SQL 運算式、CASE、字串與日期函數、JOIN 擴充、子查詢、UNION（7.50）、內表資料來源（7.52）。語法見 2-2 章第 16 節。
  2. CDS View：在 ADT 定義、可重用的語意資料模型，支援關聯（Association）、聚合、參數、存取控制（DCL）；也是 Fiori／RAP 的基礎。

24. HANA 沒有預設排序：「取第一筆」一定要先排序

Oracle 等列式資料庫依索引讀取時，結果「常常剛好」依主鍵排好，舊程式因此默默依賴這個巧合：SELECT 完直接 READ TABLE … BINARY SEARCH、SELECT SINGLE 不給完整鍵就當作「第一筆」、UP TO 1 ROWS 不寫 ORDER BY。HANA 沒有這種巧合：欄式儲存、平行執行、分割區，同一條 SQL 每次回傳順序都可能不同。

Casper 的專案實例：成本評價資料同時存在 item category「H」與 cost component「E」兩種角度，兩者的成本構成欄位數量不同。程式「取第一筆」卻沒有排序，HANA 一下回 H、一下回 E，同一個物料每次跑出來的成本不一樣，而且在開發機、測試機都很難重現。最後的結論是：條件固定抓 H，並加上明確排序。任何「取第一筆／取最新一筆／取最大一筆」的邏輯，都必須先明確排序（或直接用 MAX/MIN 聚合）。
*&---------------------------------------------------------------*
*& 「取第一筆」的正確寫法
*&---------------------------------------------------------------*
" ✗ 沒有完整主鍵的 SELECT SINGLE：HANA 回哪一筆不保證
SELECT SINGLE kalnr, kadky FROM keko
  WHERE matnr = @lv_matnr
    AND werks = @lv_werks
  INTO @DATA(ls_any_costing).

" ✓ 明確排序 + UP TO 1 ROWS：語意是「最新成本估算日的那一筆」
SELECT kalnr, kadky, bwvar FROM keko
  WHERE matnr = @lv_matnr
    AND werks = @lv_werks
  ORDER BY kadky DESCENDING, kalnr DESCENDING
  INTO TABLE @DATA(lt_latest)
  UP TO 1 ROWS.
DATA(ls_latest) = VALUE #( lt_latest[ 1 ] OPTIONAL ).

" ✓ Casper 案例的做法（示意，Z 表與欄位名為示範）：先把「角度」固定，再排序
SELECT cost_elem, cost_value FROM zco_cost_source
  WHERE matnr    = @lv_matnr
    AND src_type = 'H'                 "固定抓 item category H，不讓 H/E 混在一起
  ORDER BY cost_elem
  INTO TABLE @DATA(lt_cost).

" ✓ 讀進內表後要 BINARY SEARCH／AT NEW／DELETE ADJACENT DUPLICATES → 先 SORT
"   （或直接用 SORTED 表接收；FAE 的結果尤其沒有順序）
SORT lt_cost BY cost_elem.

在 HANA 遷移專案中，SAP 提供 ATC／SCI 的功能性檢查（例如「Search problematic statements for result of SELECT/OPEN CURSOR without ORDER BY」，收在 SAP 交付的 HANA 遷移檢查變式中），專門找出「依賴隱含順序」的語句：SELECT 後接 READ … BINARY SEARCH、DELETE ADJACENT DUPLICATES、AT NEW／AT END OF 控制層處理、SELECT SINGLE 或 UP TO 1 ROWS 沒有 ORDER BY 等。遷移前一定要跑、而且逐條處理，不是加虛擬註解了事。詳細比較另見 2-2 章第 18 節。

三條實務心法在效能調校中的位置：① HANA 無預設排序——效能改寫（例如把巢狀 SELECT 改 JOIN、改 FAE）後結果順序一定會變，改完要驗證依賴順序的邏輯；② 列舉優於區間——既快（索引串接）又準（不受字典序誤導）；③ 先找標準再客製——標準程式慢，先搜 SAP Note、看有無 SAP 發佈的索引或 CDS View，再考慮 BAdI／Enhancement，最後才改標準（見 3-4 章、5-14 章 BC425）。

25. 其他技巧與課程總路線圖

强晟筆記「其他方法」路線圖：

  • 程式內緩衝：能用緩衝避免相同 SQL 就緩衝（第 17 節）。
  • 強健的使用者介面：選擇畫面的關鍵欄位設 OBLIGATORY、在開始選資料前檢查最低輸入條件；自建搜尋說明依 SAP 標準設計（最常用欄位放上面）；選擇畫面空白的 SELECT-OPTIONS 不會出現在 SQL 中，可能讓最重要的索引欄位消失（見 3-1 章）。

  • 熟悉業務與資料表關係：强晟在後記強調，SAP 常把同一份資料寫進多張相關表，某張表查不快時，換一張（索引表、狀態表）效率可能有質的飛躍——這需要多學業務邏輯。

「在 ABAP 排序」這條舊規則要重新理解。2001 版 p105：「資料庫是中央資源、無法擴充，能在 ABAP 排序就在 ABAP 排序；只有選取與排序可共用同一索引時才在 DB 排序。」這是磁碟式資料庫、單一 DB 伺服器時代的最佳化。到了 HANA，排序在 DB 端做通常更便宜，而且更重要的是正確性：HANA 沒有預設順序（第 24 節），凡是依賴順序的邏輯都必須有人明確排序——在 DB 用 ORDER BY 或在 ABAP 用 SORT／SORTED 表都可以，就是不能「兩邊都沒做」。

  1. 把 VVBAK＋VVBAP 的 ABAP JOIN 擴成 VVBAK＋VVBAP＋VVBEP 三表 JOIN，提早讀到排程行。

改寫成 JOIN 後有兩件事要驗證：① 結果筆數——INNER JOIN 會把沒有排程行或沒有 MARC 的項目濾掉，原程式若要保留它們就改 LEFT OUTER JOIN；② 順序——原程式靠 SORT 保證的順序，現在由 ORDER BY 保證，千萬別因為「看起來已經排好」就把 ORDER BY 也拿掉（Casper 經驗第一條：HANA 沒有預設排序）。另外，WHERE 條件若來自使用者輸入，s_vbeln 請引導使用者輸入單號清單（列舉）而不是大區間（Casper 經驗第二條）。
2001 版把這個練習放在最後，傳達的觀念至今不變：先用工具確認每條 SQL 都已經最佳化，最後才動業務邏輯；而業務邏輯的改寫要找懂流程的人一起確認，這和「先標準、再 BAdI、最後才改標準」是同一種升級成本的思考（Casper 經驗第三條）。

練習與自我檢核

  1. STAD 顯示某報表 DB 時間佔（回應時間－Dispatcher 等待）的 65%，下一步用什麼工具？若 CPU 時間佔 70% 呢？
    參考答案：DB 高 → ST05 SQL Trace（或 ST12）；CPU 高 → SAT（先全彙總找 > 10% 的熱點，再細量）。依據是强晟筆記的 40% 門檻。
  2. SQL Monitor 為何能在正式機長期開啟？建議量測多久？哪個指標最能抓出巢狀 SELECT？
    參考答案：資料先在 session 記憶體彙總、再進共享記憶體、由背景作業非同步寫 DB，開銷平均 < 3%；建議最長兩週；Executions/Internal Session 偏高＝迴圈內 SELECT。
  3. ST05 某條 SELECT 的 Executions = 5,000、Rec/Exec = 1、Identical = 80%，代表什麼？怎麼改？
    參考答案：迴圈內逐筆 SELECT SINGLE，且八成是重複值。改成驅動表去重後的 FAE／JOIN，或用緩衝模組避免重複讀。
  4. 為什麼 WHERE belnr = @x 查 BKPF 很慢？
    參考答案：主鍵 MANDT/BUKRS/BELNR/GJAHR，缺 BUKRS 形成索引缺口，只剩 MANDT 可用。即使只有一個公司代碼也要寫進 WHERE。
  5. DB05 顯示加入第三個欄位後 distinct 組合數幾乎不變，該怎麼處理？
    參考答案：該欄不增加選擇性，不應放進索引；若仍有組合會回大量筆數，整個索引都不該建（COSS 案例）。
  6. 列出 FOR ALL ENTRIES 的四個陷阱與 7.52 起的替代方案。
    參考答案：空驅動表抓全表、驅動表未去重、結果隱性去重、與大 RANGES 合用超長 SQL；替代：JOIN、CDS View、SELECT … FROM @itab JOIN。
  7. 哪些語句會繞過表緩衝？至少列六種。
    參考答案：BYPASSING BUFFER、FOR UPDATE、DISTINCT、聚合函數、IS NULL、ORDER BY 非主鍵、GROUP BY/HAVING、子查詢、JOIN、Native SQL；單筆緩衝表未給完整鍵、通用緩衝表未用 = 填滿通用區。
  8. ST10 中一張已緩衝的客製表排在 Rows affected 的最前面，可能原因？
    參考答案：表太大、常被異動而失效（重載與 pending period 期間的 DB 讀取累積），或存取方式與緩衝類型不符（例如單筆緩衝表被循序讀）。考慮取消緩衝或改緩衝類型。
  9. 一張內表要同時用 VBELN 與 MATNR 兩種鍵大量讀取，該怎麼設計？
    參考答案：主鍵 SORTED（vbeln, posnr）＋ 非唯一 SORTED 二級鍵 by_matnr，存取時明寫 USING KEY；若兩種存取可分階段，也可用標準表 SORT 切換。
  10. 何時一定要用 ASSIGNING？何時 INTO wa 反而較快？
    參考答案：深結構、工作區 > 1 KB、要修改內容時一定用；工作區極小且單筆 READ 在巨大巢狀迴圈中執行極多次時 INTO wa 較快。
  11. ACCEPTING DUPLICATE KEYS 遇到重複鍵時會發生什麼？（指出教材錯誤）
    參考答案：重複列不寫入、sy-subrc = 4、sy-dbcnt 為實寫筆數，不會 DUMP；Col19 p303 寫「導致短傾印」是錯的。
  12. ST05 清單中 GUI 相關的 OLE_FLUSH_CALL 每步出現 6 次，代表什麼？
    參考答案：每個對話步驟 6 次 Roundtrip，遠超建議的 1～2 次；應合併 Control 方法呼叫、減少 flush。
  13. 舊程式 SELECT SINGLE（未給完整鍵）在 Oracle 上一直正確，遷到 HANA 後結果時對時錯，為什麼？怎麼修？
    參考答案：HANA 沒有預設排序，「第一筆」不固定。改為 ORDER BY ＋ UP TO 1 ROWS（或 MAX/MIN 聚合），必要時像 Casper 的 H/E 案例先把條件固定；遷移前用 ATC 的「沒有 ORDER BY」檢查全面掃描。
  14. 什麼情況下該寫 AMDP，而不是 CDS 或 ABAP SQL？寫 AMDP 要注意什麼？
    參考答案：只有需要 SQLScript 專屬能力的複雜多步驟運算時；注意綁死 HANA、要自己處理用戶端、除錯較難、繞過表緩衝。
  15. ST04 顯示 Reads/User calls = 35，你會怎麼做？在 HANA 上又看什麼？
    參考答案：> 20 表示急需 SQL 快取分析：依 Buffer Gets 找 > 5% 的語句、以 Buffer Gets/Record 分為 Type 1/Type 2 對症處理。HANA 上改看 SQL Plan Cache 的 Total/Average Execution Time 與 Expensive Statements Trace。
  16. 强晟筆記說 ST05 追蹤檔「預設 8KB」、昂貴 SQL 門檻「200,000 毫秒」，對照 L29 2001 原文，這兩個數字各有什麼問題？
    參考答案：2001 原文（PDF p36）是 800 KB，筆記少抄兩個零；200,000 ms 則是原廠 2001 版投影片本身就寫錯單位（p44），Duration 是微秒，應為 200,000 µs＝200 ms。今天以 rstr/* 多檔循環機制為準。
  17. SQLM 畫面上 Total DB Time 顯示「2.220,570」，這條 SQL 花了多久？哪個比值最能指出值得做 SQL 最佳化的程式碼？
    參考答案：SQLM 時間單位是毫秒、顯示小數 3 位，德式格式下是約 2,220.57 ms（約 2.2 秒）；Col10 p184 的 Hint 對這個例子的換算寫錯。Total DB Time ÷ Total Time 比值高的程式碼最有 SQL 最佳化空間（Col10 p183）。
  18. 2001 版說「能在 ABAP 排序就在 ABAP 排序」，在 S/4HANA 上還成立嗎？
    參考答案：效能上不再絕對（HANA 端排序常更便宜），但正確性上更要緊：HANA 無預設順序，依賴順序的邏輯一定要有 ORDER BY、SORT 或 SORTED 表其中之一；把巢狀 SELECT 改成 JOIN 之後原本的 SORT 可以省，但要改由 ORDER BY 保證順序。
  19. ATC、SWLT、ST12、CDS、AMDP 出現在哪一版 BC490 原廠教材？
    參考答案：都沒有。2001、2017 Col10、2022 Col19 三版都只教 SCI、SQLM、SE30/SAT、ST05，例子以 Oracle 為主；本章相關內容是依 SAP 官方文件與實務補寫，已在各節標註。
